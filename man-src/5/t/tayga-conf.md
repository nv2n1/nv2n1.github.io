<p>tayga.conf &#8211; configuration file of the TAYGA stateless NAT64 daemon</p>
<h2>Description</h2>
<p>This file contains the configuration parameters for the TAYGA stateless NAT64 daemon. It must exist and contain the mandatory configuration items or TAYGA will refuse to run. The configuration directives are listed below. With the exception of the <code>map</code> directive, only one instance of each directive may appear in tayga.conf.</p>
<dl>
<dt><code>tun-device </code><i>device</i></p>
<dd>Name of the network interface that will be created by the kernel TUN module for TAYGA to exchange IPv4 and IPv6 packets with the in-kernel TCP/IP stack. If <i>device</i> does not already exist as a persistent interface (created by the <code>&#8211;mktun</code> flag to <a href="/docs/linux/man/8-tayga/">tayga</a>(8), for example), it will be created automatically when the TAYGA daemon starts and destroyed when the daemon exits.</p>
<dd>Note that TAYGA does not configure the host-side parameters of <i>device.</i> This must be done by the system administrator using the <a href="/docs/linux/man/8-ifconfig/">ifconfig</a>(8), <a href="/docs/linux/man/8-route/">route</a>(8), and/or <a href="/docs/linux/man/8-ip/">ip</a>(8) commands.</p>
<dd>This configuration directive is mandatory.</p>
<dt><code>ipv4-addr </code><i>ipv4_address</i></p>
<dd>IPv4 address that TAYGA will use as the source address for ICMPv4 errors generated by the translation process. TAYGA will also respond to ICMP echo requests (pings) at this address.</p>
<dd><i>ipv4_address</i> is permitted to overlap with the prefix specified in the <code>dynamic-pool</code> directive, in which case <i>ipv4_address</i> will be removed from the pool of available addresses.</p>
<dd>This configuration directive is mandatory.</p>
<dt><code>ipv6-addr </code><i>ipv6_address</i></p>
<dd>IPv6 address that TAYGA will use as the source address for ICMPv6 errors generated by the translation process. TAYGA will also respond to ICMPv6 echo requests (pings) at this address.</p>
<dd>This configuration directive is mandatory unless the NAT64 prefix is specified with the <code>prefix</code> directive, in which case TAYGA will generate its IPv6 address by mapping the address specified in <code>ipv4-addr</code> into the NAT64 prefix.</p>
<dt><code>prefix </code><i>ipv6_address/length</i></p>
<dd>NAT64 prefix for mapping IPv4 addresses into the IPv6 address space. TAYGA performs address translation as specified in RFC 6052, and only prefix lengths allowed in that document will be permitted in the <code>prefix</code> directive.</p>
<dd>The use of either a Network-Specific Prefix or the Well-Known Prefix (64:ff9b::/96) is allowed, <code>however,</code> as required by RFC 6052, TAYGA will refuse to translate packets with a source or destination address composed of the Well-Known Prefix and a non-global IPv4 address (10.x.x.x, 192.168.x.x, etc).</p>
<dd>Use of the <code>prefix</code> directive is optional. If it is not specified, all addresses to be translated must be listed individually with the <code>map</code> directive.</p>
<dt><code>map </code><i>ipv4_address ipv6_address</i></p>
<dd>Creates a static mapping between <i>ipv4_address</i> and <i>ipv6_address</i> to be used when translating IPv4 packets to IPv6 or IPv6 packets to IPv4. Multiple <code>map</code> directives are permitted in the tayga.conf file.</p>
<dd><i>ipv4_address</i> is permitted to overlap with the prefix specified in the <code>dynamic-pool</code> directive, in which case <i>ipv4_address</i> will be removed from the pool of available addresses.</p>
<dd><i>ipv6_address</i> <code>must not</code> overlap with the prefix specified in the <code>prefix</code> directive.</p>
<dt><code>dynamic-pool </code><i>ipv4_address/length</i></p>
<dd>Address prefix containing addresses available to be assigned to IPv6 hosts. <i>length</i> must be 31 or less, as the lowest-numbered address in the prefix is considered reserved and will not be used for dynamic assignment.</p>
<dd>If TAYGA receives an IPv6 packet to be translated with an IPv6 source address that does not match any existing mapping rules (as specified by the <code>map</code> directive or the <code>prefix</code> directive), TAYGA will create a dynamic mapping between the IPv6 address and an IPv4 address drawn from the prefix specified by the <code>dynamic-pool</code> directive. This mapping will be valid for two hours and four minutes after the last packet matching the mapping is translated.</p>
<dd>The <code>dynamic-pool</code> directive is optional. If it is not specified, all IPv6 addresses appearing in packets passing through TAYGA must match the NAT64 prefix or a static mapping rule.</p>
<dt><code>data-dir </code><i>path</i></p>
<dd>The absolute path of a directory where TAYGA should store its data files. Presently the only data file that TAYGA will store is the <i>dynamic.map</i> file, which tracks dynamic address assignments made from the dynamic pool.</p>
<dd><i>path</i> is also the directory that will be used as a <a href="/docs/linux/man/2-chroot/">chroot</a>(2) &quot;jail&quot; if the <code>&#8211;chroot</code> command-line option is specified to the TAYGA daemon.</p>
<dd>The TAYGA daemon must have full permissions (rwx) to <i>path</i> after it has dropped superuser privileges. Generally this means that the owner of <i>path</i> should be the user specified in the <code>&#8211;user</code> command-line option.</p>
<dd>The <code>data-dir</code> directive is optional, but without it, dynamic mappings will be lost when the TAYGA daemon is stopped. Also, use of the <code>&#8211;chroot</code> command-line option will not be possible.</p>
<dt><code>strict-frag-hdr </code><i>on|off|true|false|1|0</i></p>
<dd>Flag to control whether TAYGA adds fragmentation headers to IPv6 packets that do not require fragmentation. RFC 6145 stipulates that the fragmentation header SHOULD be added to all translated packets when the sender has not set the DF (Don&#8217;t Fragment) flag, to indicate that the sender allows fragmentation and may not support path MTU discovery. Unfortunately, some firewall implementations drop IPv6 packets that are fragmented into a single fragment, most notably Linux netfilter conntrack in kernels older than 2.6.34.</p>
<dd>When <code>strict-frag-hdr</code> is set to <code>true, on,</code> or <code>1,</code> fragmentation headers will be added to all translated packets where the DF bit in the original packet is clear. This is the RFC-complaint behavior.</p>
<dd>When <code>strict-frag-hdr</code> is set to <code>false, off,</code> or <code>0,</code> fragmentation headers will be suppressed when the translated packet fits entirely within the IPv6 network MTU (1280 bytes). This is the default behavior.</p>
<dd>This setting does not affect packets that arrive at TAYGA already fragmented, or packets that must be fragmented to fit within the IPv6 network MTU. </p>
