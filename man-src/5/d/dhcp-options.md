<p>dhcp-options &#8211; Dynamic Host Configuration Protocol options</p>
<h2>Description</h2>
<p>The Dynamic Host Configuration protocol allows the client to receive <code>options</code> from the DHCP server describing the network configuration and various services that are available on the network. When configuring <code><a href="/docs/linux/man/8-dhcpd/">dhcpd</a>(8)</code> or <code><a href="/docs/linux/man/8-dhclient/">dhclient</a>(8) ,</code> options must often be declared. The syntax for declaring options, and the names and formats of the options that can be declared, are documented here.</p>
<h2>Reference: Option Statements</h2>
<p>DHCP <i>option</i> statements always start with the <i>option</i> keyword, followed by an option name, followed by option data. The option names and data formats are described below. It is not necessary to exhaustively specify all DHCP options &#8211; only those options which are needed by clients must be specified. </p>
<p> Option data comes in a variety of formats, as defined below: </p>
<p> The <code>ip-address</code> data type can be entered either as an explicit IP address (e.g., 239.254.197.10) or as a domain name (e.g., haagen.isc.org). When entering a domain name, be sure that that domain name resolves to a single IP address. </p>
<p> The <code>ip6-address</code> data specifies an IPv6 address, like ::1 or 3ffe:bbbb:aaaa:aaaa::1. </p>
<p> The <code>int32</code> data type specifies a signed 32-bit integer. The <code>uint32</code> data type specifies an unsigned 32-bit integer. The <code>int16</code> and <code>uint16</code> data types specify signed and unsigned 16-bit integers. The <code>int8</code> and <code>uint8</code> data types specify signed and unsigned 8-bit integers. Unsigned 8-bit integers are also sometimes referred to as octets. </p>
<p> The <code>text</code> data type specifies an NVT ASCII string, which must be enclosed in double quotes &#8211; for example, to specify a root-path option, the syntax would be </p>
<pre>option root-path &quot;10.0.1.4:/var/tmp/rootfs&quot;;</pre>
<p>The <code>domain-name</code> data type specifies a domain name, which must not be enclosed in double quotes. The domain name is stored just as if it were a text option. </p>
<p> The <code>domain-list</code> data type specifies a list of domain names, enclosed in double quotes and separated by commas (&quot;example.com&quot;, &quot;foo.example.com&quot;). </p>
<p> The <code>flag</code> data type specifies a boolean value. Booleans can be either true or false (or on or off, if that makes more sense to you). </p>
<p> The <code>string</code> data type specifies either an NVT ASCII string enclosed in double quotes, or a series of octets specified in hexadecimal, separated by colons. For example: </p>
<pre> option dhcp-client-identifier &quot;CLIENT-FOO&quot;;
or
 option dhcp-client-identifier 43:4c:49:45:54:2d:46:4f:4f;</pre>
<h2>Setting Option Values Using Expressions</h2>
<p>Sometimes it&#8217;s helpful to be able to set the value of a DHCP option based on some value that the client has sent. To do this, you can use expression evaluation. The <code><a href="/docs/linux/man/5-dhcp-eval/">dhcp-eval</a>(5)</code> manual page describes how to write expressions. To assign the result of an evaluation to an option, define the option as follows: </p>
<pre> <code>option </code><i>my-option </i><code>= </code><i>expression </i><code>;</code></pre>
<p>For example: </p>
<pre> option hostname = binary-to-ascii (16, 8, &quot;-&quot;,
 substring (hardware, 1, 6));</pre>
<h2>Including Option Definitions</h2>
<p>Starting with 4.3.0 when ISC adds new option definitions those definitions will be included in the code based on the definition of an argument for the RFC that defines the option in includes/site.h. This provides you with a method for over-riding the ISC definitions if necessary &#8211; for example if you have previously defined the option with a different format using the mechanism from DEFINING NEW OPTIONS below. </p>
<p> By default all of the options are enabled. In order to disable an option you would edit the includes/site.h file and comment out the definition for the proper RFC.</p>
<h2>Standard Dhcpv4 Options</h2>
<p>The documentation for the various options mentioned below is taken from the latest IETF draft document on DHCP options. Options not listed below may not yet be implemented, but it is possible to use such options by defining them in the configuration file. Please see the DEFINING NEW OPTIONS heading later in this document for more information. </p>
<p> Some of the options documented here are automatically generated by the DHCP server or by clients, and cannot be configured by the user. The value of such an option can be used in the configuration file of the receiving DHCP protocol agent (server or client), for example in conditional expressions. However, the value of the option cannot be used in the configuration file of the sending agent, because the value is determined only <i>after</i> the configuration file has been processed. In the following documentation, such options will be shown as &quot;not user configurable&quot; </p>
<p> The standard options are: </p>
<p> <code>option all-subnets-local</code> <i>flag</i><code>;</code></p>
<dl>
<dd>This option specifies whether or not the client may assume that all subnets of the IP network to which the client is connected use the same MTU as the subnet of that network to which the client is directly connected. A value of true indicates that all subnets share the same MTU. A value of false means that the client should assume that some subnets of the directly connected network may have smaller MTUs.</dl>
<p> <code>option arp-cache-timeout</code> <i>uint32</i><code>;</code></p>
<dl>
<dd>This option specifies the timeout in seconds for ARP cache entries.</dl>
<p> <code>option associated-ip</code> <i>ip-address</i> [<code>,</code> <i>ip-address</i>&#8230; ]<code>;</code></p>
<dl>
<dd>This option is part of lease query. It is used to return all of the IP addresses associated with a given DHCP client. </p>
<p> This option is not user configurable.</dl>
<p> <code>option bcms-controller-address</code> <i>ip-address</i> [<code>,</code> <i>ip-address</i>&#8230; ]<code>;</code></p>
<dl>
<dd>This option configures a list of IPv4 addresses for use as Broadcast and Multicast Controller Servers (&quot;BCMS&quot;).</dl>
<p> <code>option bcms-controller-names</code> <i>domain-list</i><code>;</code></p>
<dl>
<dd>This option contains the domain names of local Broadcast and Multicast Controller Servers (&quot;BCMS&quot;) controllers which the client may use.</dl>
<p> <code>option bootfile-name</code> <i>text</i><code>;</code></p>
<dl>
<dd>This option is used to identify a bootstrap file. If supported by the client, it should have the same effect as the <code>filename</code> declaration. BOOTP clients are unlikely to support this option. Some DHCP clients will support it, and others actually require it.</dl>
<p> <code>option boot-size</code> <i>uint16</i><code>;</code></p>
<dl>
<dd>This option specifies the length in 512-octet blocks of the default boot image for the client.</dl>
<p> <code>option broadcast-address</code> <i>ip-address</i><code>;</code></p>
<dl>
<dd>This option specifies the broadcast address in use on the client&#8217;s subnet. Legal values for broadcast addresses are specified in section 3.2.1.3 of STD 3 (RFC1122).</dl>
<p> <code>option</code> <code>capwap-ac-v4</code> <i>ip-address </i>[<code>,</code> <i>ip-address </i>&#8230; ] <code>;</code></p>
<dl>
<dd>A list of IPv4 addresses of CAPWAP ACs that the WTP may use. The addresses are listed in preference order. </p>
<p> This option is included based on RFC 5417.</dl>
<p> <code>option client-last-transaction-time</code> <i>uint32</i><code>;</code></p>
<dl>
<dd>This option is part of lease query. It allows the receiver to determine the time of the most recent access by the client. The value is a duration in seconds from when the client last communicated with the DHCP server. </p>
<p> This option is not user configurable.</dl>
<p> <code>option cookie-servers</code> <i>ip-address</i> [<code>,</code> <i>ip-address</i>&#8230; ]<code>;</code></p>
<dl>
<dd>The cookie server option specifies a list of RFC 865 cookie servers available to the client. Servers should be listed in order of preference.</dl>
<p> <code>option default-ip-ttl</code> <i>uint8;</i></p>
<dl>
<dd>This option specifies the default time-to-live that the client should use on outgoing datagrams.</dl>
<p> <code>option default-tcp-ttl</code> <i>uint8</i><code>;</code></p>
<dl>
<dd>This option specifies the default TTL that the client should use when sending TCP segments. The minimum value is 1.</dl>
<p> <code>option default-url</code> <i>string</i><code>;</code></p>
<dl>
<dd>The format and meaning of this option is not described in any standards document, but is claimed to be in use by Apple Computer. It is not known what clients may reasonably do if supplied with this option. Use at your own risk.</dl>
<p> <code>option dhcp-client-identifier</code> <i>string</i><code>;</code></p>
<dl>
<dd>This option can be used to specify a DHCP client identifier in a host declaration, so that dhcpd can find the host record by matching against the client identifier. </p>
<p> Please be aware that some DHCP clients, when configured with client identifiers that are ASCII text, will prepend a zero to the ASCII text. So you may need to write: </p>
<pre> option dhcp-client-identifier &quot;
