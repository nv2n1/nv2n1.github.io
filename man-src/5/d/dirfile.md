<p>dirfile &#8212; a filesystem based database format for time-ordered binary data</p>
<h2>Description</h2>
<p>The <i>dirfile</i> database format is designed to provide a fast, simple format for storing and reading binary time-ordered data. Dirfiles can be read using the GetData library. The dirfile database is centred around one or more time-ordered data streams (a <i>time stream</i>). Each time stream is written to disk in a separate file, in its native binary format. The name of these binary files correspond to the time stream&#8217;s <i>field name</i>. Two time streams may have different constant sampling frequencies and mechanisms exist within the dirfile format to ensure these time streams remain properly sequenced in time. To do this, the time streams in the dirfile are subdivided into <i>frames</i>. Each frame contains an integer number of samples of each time stream. When synchronous retrieval of data from more than one time stream is required, position in the dirfile can be specified in frames, which will ensure synchronicity. The binary files are all located in a central directory, known as the <i>dirfile directory</i>. The dirfile as a whole may be referred to by its dirfile directory path. Included in the dirfile along with the time streams is the <i>dirfile format specification</i>, which is an ASCII text file called <code>format</code> located in the dirfile directory. This file fully specifies the dirfile&#8217;s metadata. For the syntax of this file, see <code><a href="/docs/linux/man/5-dirfile-format/">dirfile-format</a></code>(5). Version 3 of the Dirfile Standards introduced the <i>large dirfile</i> extension. This extension added the ability to distribute the dirfile metadata among multiple files (called <i>fragments</i>) in addition to the <code>format</code> file, as well as the ability to house portions of the database in <i>subdirfiles</i>. These subdirfiles may be fully fledged dirfiles in their own right, but may also be contained within a larger, parent dirfile. See <code><a href="/docs/linux/man/5-dirfile-format/">dirfile-format</a></code>(5) for information on specifying these subdirfiles. In addition to the raw fields on disk, the dirfile format specification may also specify <i>derived fields</i> which are calculated from one or more raw or derived time streams. Derived fields behave identically to raw fields when read via GetData. See <code><a href="/docs/linux/man/5-dirfile-format/">dirfile-format</a></code>(5) for a complete list of derived field types. Dirfiles may also contain both numerical and character string constant <i>scalar fields</i>, also further outlined in <code><a href="/docs/linux/man/5-dirfile-format/">dirfile-format</a></code>(5). Dirfiles are designed to be written to and read simultaneously. The dirfile specification dictates that one particular raw field (specified either explicitly or implicitly by the format file) is to be used as the <i>reference field</i>: all other vector fields are assumed to have at least as many frames as the reference field has, and the size (in frames) of the reference field is used as the size of the dirfile as a whole. Version 6 of the Dirfile Standards added the ability to encode the binary files on disk. Each <i>fragment</i> may have its own encoding scheme. Notably this can be used to compress these files. See <code><a href="/docs/linux/man/5-dirfile-encoding/">dirfile-encoding</a></code>(5) for information on encoding schemes.</p>
<h3>Complex Number Storage Format</h3>
<p>Version 7 of the Dirfile Standards added support for complex valued data. Two types of complex valued data are supported by the Dirfile Standards:</p>
<dl>
<dt>*</p>
<dd>A 64-bit complex number consisting of a IEEE-754 standard 32-bit single precision floating point real part and a IEEE-754 standard 32-bit single precision floating point imaginary part, and</p>
<dt>*</p>
<dd>A 128-bit complex number consisting of a IEEE-754 standard 64-bit double precision floating point real part and a IEEE-754 standard 64-bit double precision floating point imaginary part.</dl>
<p> No integer-type complex numbers are supported. Unencoded complex numbers are stored on disk in &quot;Fortran order&quot;, that is with the IEEE-754 real part followed by the IEEE-754 imaginary part. The specified endianness of the two components follows that of purely real floating point numbers. Endianness does not affect the ordering of the real and imaginary parts. This format also conforms to the C99 standard. The latest C++ standard (C++98) does not specify a standard storage format for native complex numbers, but the upcoming standard, (C++0x) is intended to specify the above format for compatibility with C99 (<i>see</i>: ISO/IEC JTC1/SC22/WG21/N1388). To aid in using complex valued data, dirfile field codes may contain a <i>representation suffix</i> which specifies a norm to apply to the complex valued data to convert it into purely real data. See <code><a href="/docs/linux/man/5-dirfile-format/">dirfile-format</a></code>(5). </p>
