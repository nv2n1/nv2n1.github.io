<p>cjdroute.conf &#8211; Cjdns configuration file</p>
<h2>Description</h2>
<p>The <i>cjdroute.conf</i> file configures the cjdns routing engine, <code><a href="/docs/linux/man/8-cjdns/">cjdns</a></code>(8), generally through <code><a href="/docs/linux/man/1-cjdroute/">cjdroute</a></code>(1). The configuration is written in a variation of the JSON format that also accepts traditional C-like comments such as single line comments (//) and multiline comments (/* and */). Additionally, unused JSON values found in <i>cjdroute.conf</i> are ignored by cjdns and can be used as a form of JSON-compliant comments. </p>
<h2>Configuration</h2>
<p><code>&quot;privateKey&quot;:</code> &quot;&#8230;&quot;</p>
<dl>
<dd>Your node&#8217;s private key. It should be kept secret because your confidentiality and data integrity depend on it.</dl>
<p> <code>&quot;publicKey&quot;:</code> &quot;&#8230;&quot;</p>
<dl>
<dd>Your node&#8217;s public key. Based on your private key It is fine for anyone to know this.</dl>
<p> <code>&quot;ipv6&quot;:</code> &quot;&#8230;&quot;</p>
<dl>
<dd>Your node&#8217;s IPv6 address when it is on the network. It is generated by using the first 16 bytes of a double SHA-512 of your public key. All cjdns IPv6 addresses must begin with &quot;fc&quot; or else they are invalid.</dl>
<p> <code>&quot;authorizedPasswords&quot;:</code> [&#8230;]</p>
<dl>
<dd>An array of passwords that may be used to connect (peer) to your node. </p>
<p> <i>&quot;password&quot;:</i> &quot;&#8230;&quot;</p>
<dl>
<dd>A password which can be used to peer with your node.</dl>
<p> <i>&quot;user&quot;:</i> &quot;&#8230;&quot;</p>
<dl>
<dd>An optional human-readable string that identifies what password a peer is using on the admin interface. If omitted, the password will be identified by its position within the array (starting from 0)</dl>
<p> Example:<br />
 &quot;authorizedPasswords&quot;:<br />
 [<br />
&nbsp;<wbr>{&nbsp;<wbr>&quot;password&quot;:&nbsp;<wbr>&quot;AnExamplePassword&quot;,&nbsp;<wbr>&quot;user&quot;:&nbsp;<wbr>&quot;Bob&quot;&nbsp;<wbr>},<br />
&nbsp;<wbr>{&nbsp;<wbr>&quot;password&quot;:&nbsp;<wbr>&quot;YetAnotherExample&quot;,&nbsp;<wbr>&quot;user&quot;:&nbsp;<wbr>&quot;Alice&quot;&nbsp;<wbr>},<br />
&nbsp;<wbr>{&nbsp;<wbr>&quot;password&quot;:&nbsp;<wbr>&quot;j3fus4r3gkhv80xdz1yqc0qvn1p91hr&quot;,&nbsp;<wbr>&quot;user&quot;:&nbsp;<wbr>&quot;Eve&quot;&nbsp;<wbr>}<br />
 ]</dl>
<p> <code>&quot;admin&quot;:</code> {&#8230;}</p>
<dl>
<dd>An object which defines where to bind to the admin RPC server as well as the password for the admin RPC server. The two required strings are &quot;bind&quot;, which should be in the format &quot;IP:PORT&quot;, and &quot;password&quot;, which should preferably be a long random string of characters.</dl>
<p> <code>&quot;interfaces&quot;:</code> {&#8230;}</p>
<dl>
<dd>An object that defines which interfaces cjdns will bind to and what peers to connect to. There are two different interfaces, UDPInterface and ETHInterface, both of which are arrays. Within each array there are a variety of different options </p>
<p> <i>&quot;bind&quot;:</i> &quot;&#8230;&quot;</p>
<dl>
<dd>Defines what the interface should bind to. In UDPInterface, the bind is an IP:PORT string, such as &quot;0.0.0.0:12345&quot;, while in ETHInterface the bind is a network interface, such as &quot;eth0&quot;.</dl>
<p> <i>&quot;beacon&quot;:</i> Integer</p>
<dl>
<dd>This option is only found in ETHInterface and defines whether auto-connecting beacons should be sent or listened to. This is useful for a zeroconf local network. </p>
<dl>
<dd>0 &#8212; Disabled.<br />
 1 &#8212; Accept incoming beacons and try connecting to the sender.<br />
 2 &#8212; Accept incoming beacons and broadcast beacons to the local network.</dl>
</dl>
<p> <i>&quot;connectTo&quot;:</i> {&#8230;}</p>
<dl>
<dd>Defines which nodes cjdns should connect to with the specified interface. Multiple nodes may be placed in a single &quot;connectTo&quot; as long as each are seperated by commas. If a node happens to be offline or become offline during runtime, cjdns will attempt to reconnect at regular intervals. The one difference in this option between UDPInterface and ETHInterface is that UDPInterface connects to an &quot;IP:PORT&quot; while ETHInterface connects to a MAC address. </p>
<p> UDPInterface Example:<br />
 &quot;connectTo&quot;:<br />
 {</p>
<dl>
<dd>&quot;1.2.3.4:54321&quot;:<br />
 {<br />
&nbsp;<wbr>&quot;password&quot;:&nbsp;<wbr>&quot;password From Your Peer&#8217;s authorizedPasswords&quot;,<br />
&nbsp;<wbr>&quot;publicKey&quot;:&nbsp;<wbr>&quot;Your Peer&#8217;s publicKey.k&quot;<br />
 },<br />
 &quot;5.6.7.8:46321&quot;:<br />
 {<br />
&nbsp;<wbr>&quot;password&quot;:&nbsp;<wbr>&quot;Correct Horse Battery Staple&quot;,<br />
&nbsp;<wbr>&quot;publicKey&quot;:&nbsp;<wbr>&quot;Other Peer&#8217;s publicKey.k&quot;<br />
 }</dl>
<p> }</dl>
</dl>
<p> <code>&quot;router&quot;:</code> {&#8230;}</p>
<dl>
<dd>An object that holds configuration information on the router </p>
<p> <i>&quot;interface&quot;:</i> {&#8230;}</p>
<dl>
<dd>Defines the type of interface used for connecting to the cjdns network. It requires a &quot;type&quot; string, and optionally a &quot;tunDevice&quot; string. The &quot;type&quot; string defines the type of interface used, however only &quot;TUNInterface&quot; is supported at the moment. The &quot;tunDevice&quot; string defines the name of a persistent TUN device to use, which is helpful for starting cjdroute as its own user instead of root.</dl>
<p> <i>&quot;ipTunnel&quot;:</i> {&#8230;}</p>
<dl>
<dd>A system for tunneling ICANN IPv4 and ICANN IPv6 through cjdns. This is using the cjdns switch layer as a VPN carrier. </p>
<p> <code>NOTE:</code> Simply editing your configuration file is not sufficient to setting up an ipTunnel gateway. Please read through tunnel/README.md in the cjdns git tree for more information </p>
<p> <i>&quot;allowedConnections&quot;:</i> [&#8230;]</p>
<dl>
<dd>Nodes allowed to connect to us, specified by their public key, and what IP address(es) to give them. It is fine to only specify one address. </p>
<p> Example: </p>
<p> &quot;allowedConnections&quot;:<br />
 [ </p>
<p>&nbsp;<wbr>{<br />
&nbsp;<wbr>&nbsp;<wbr>&quot;publicKey&quot;:&nbsp;<wbr>&quot;f64hfl7c4uxt6krmhPutTheRealAddressOfANodeHere7kfm5m0.k&quot;,<br />
&nbsp;<wbr>&nbsp;<wbr>&quot;ip4Address&quot;:&nbsp;<wbr>&quot;192.168.1.24&quot;,<br />
&nbsp;<wbr>&nbsp;<wbr>&quot;ip4Prefix&quot;: 24,<br />
&nbsp;<wbr>&nbsp;<wbr>&quot;ip6Address&quot;:&nbsp;<wbr>&quot;2001:123:ab::10&quot;,<br />
&nbsp;<wbr>&nbsp;<wbr>&quot;ip6Prefix&quot;: 0 </p>
<p>&nbsp;<wbr>}, </p>
<p>&nbsp;<wbr>{<br />
&nbsp;<wbr>&nbsp;<wbr>&quot;publicKey&quot;:&nbsp;<wbr>&quot;ydq8csdk8p8ThisIsJustAnExampleAddresstxuyqdf27hvn2z0.k&quot;,<br />
&nbsp;<wbr>&nbsp;<wbr>&quot;ip4Address&quot;:&nbsp;<wbr>&quot;192.168.1.25&quot;,<br />
&nbsp;<wbr>&nbsp;<wbr>&quot;ip4Prefix&quot;: 24 </p>
<p>&nbsp;<wbr>}<br />
 ]</dl>
<p> <i>&quot;outgoingConnections&quot;:</i> [&#8230;]</p>
<dl>
<dd>An array of nodes to connect and ask for IP addresses. </p>
<p> Example: </p>
<p> &quot;outgoingConnections&quot;:<br />
 [<br />
&nbsp;<wbr>&quot;6743gf5tw80ExampleExampleExampleExamplevlyb23zfnuzv0.k&quot;,<br />
&nbsp;<wbr>&quot;pw9tfmr8pcrExampleExampleExampleExample8rhg1pgwpwf80.k&quot;,<br />
&nbsp;<wbr>&quot;g91lxyxhq0kExampleExampleExampleExample6t0mknuhw75l0.k&quot;<br />
 ] </p>
</dl>
</dl>
</dl>
<p> <code>&quot;security&quot;:</code> [&#8230;]</p>
<dl>
<dd>An array that defines what user to change to after startup and whether to exempt the Angel process from this user change. </p>
<p> <i>&quot;setuser&quot;:</i> &quot;username&quot;</p>
<dl>
<dd>User to switch to after startup, for security purposes. Default value is &quot;nobody&quot;. </p>
</dl>
<p> <i>&quot;exemptAngel&quot;:</i> Integer</p>
<dl>
<dd>Whether or not to exempt the Angel process from the user change. The Angel is a small isolated piece of code which exists outside of the core&#8217;s strict sandbox but does not handle network traffic. This option must be enabled for ipTunnel to automatically set IP addresses for the TUN device. </p>
<p> 0 &#8212; False<br />
 1 &#8212; True</dl>
</dl>
<p> <code>&quot;logging&quot;:</code> {&#8230;}</p>
<dl>
<dd>Add or uncomment &quot;logTo&quot;:&quot;stdout&quot; to have cjdns log to stdout rather than making logs available via the admin socket</dl>
<p> <code>&quot;noBackground&quot;:</code> Integer</p>
<dl>
<dd>If set to a non-zero value, cjdns will not fork to the background. Recommended for use in conjunction with &quot;logTo&quot;:&quot;stdout&quot;.</dl>

<dl>
<dd>This section is used to configure the dns capabilities being added to cjdns. Unfortunetly, there is no documentation for this DNS section at this time. </p>
