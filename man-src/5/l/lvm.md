<p>lvm.conf &#8212; Configuration file for LVM2</p>
<h2>Synopsis</h2>
<p><code>/etc/lvm/lvm.conf</code></p>
<h2>Description</h2>
<p><code>lvm.conf</code> is loaded during the initialisation phase of <code><a href="/docs/linux/man/8-lvm/">lvm</a></code>(8). This file can in turn lead to other files being loaded &#8211; settings read in later override earlier settings. File timestamps are checked between commands and if any have changed, all the files are reloaded. The settings defined in lvm.conf can be overridden by any of these extended configuration methods:</p>
<dl>
<dt><code>direct config override on command line</code></p>
<dd>The <code>&#8211;config ConfigurationString</code> command line option takes the ConfigurationString as direct string representation of the configuration to override the existing configuration. The ConfigurationString is of exactly the same format as used in any LVM configuration file.</p>
<dt><code>profile config</code></p>
<dd>A profile is a set of selected customizable configuration settings that are aimed to achieve a certain characteristics in various environments or uses. It&#8217;s used to override existing configuration. Normally, the name of the profile should reflect that environment or use. There are two groups of profiles recognised: <code>command profiles</code> and <code>metadata profiles</code>. The <code>command profile</code> is used to override selected configuration settings at global LVM command level &#8211; it is applied at the very beginning of LVM command execution and it is used throughout the whole time of LVM command execution. The command profile is applied by using the <code>&#8211;commandprofile ProfileName</code> command line option that is recognised by all LVM2 commands. The <code>metadata profile</code> is used to override selected configuration settings at Volume Group/Logical Volume level &#8211; it is applied independently for each Volume Group/Logical Volume that is being processed. As such, each Volume Group/Logical Volume can store the profile name used in its metadata so next time the Volume Group/Logical Volume is processed, the profile is applied automatically. If Volume Group and any of its Logical Volumes have different profiles defined, the profile defined for the Logical Volume is preferred. The metadata profile can be attached/detached by using the <code>lvchange</code> and <code>vgchange</code> commands and their <code>&#8211;metadataprofile ProfileName</code> and <code>&#8211;detachprofile</code> options or the <code>&#8211;metadataprofile</code> option during creation when using <code>vgcreate</code> or <code>lvcreate</code> command. The <code>vgs</code> and <code>lvs</code> reporting commands provide <code>-o vg_profile</code> and <code>-o lv_profile</code> output options to show the metadata profile currently attached to a Volume Group or a Logical Volume. The set of options allowed for command profiles is mutually exclusive when compared to the set of options allowed for metadata profiles. The settings that belong to either of these two sets can&#8217;t be mixed together and LVM tools will reject such profiles. LVM itself provides a few predefined configuration profiles. Users are allowed to add more profiles with different values if needed. For this purpose, there&#8217;s the <code>command_profile_template.profile</code> (for command profiles) and <code>metadata_profile_template.profile</code> (for metadata profiles) which contain all settings that are customizable by profiles of certain type. Users are encouraged to copy these template profiles and edit them as needed. Alternatively, the <code>lvm dumpconfig &#8211;file &lt;ProfileName.profile&gt; &#8211;type profilable-command &lt;section&gt;</code> or <code>lvm dumpconfig &#8211;file &lt;ProfileName.profile&gt; &#8211;type profilable-metadata &lt;section&gt;</code> can be used to generate a configuration with profilable settings in either of the type for given section and save it to new ProfileName.profile (if the section is not specified, all profilable settings are reported). The profiles are stored in /etc/lvm/profile directory by default. This location can be changed by using the <code>config/profile_dir</code> setting. Each profile configuration is stored in <code>ProfileName.profile</code> file in the profile directory. When referencing the profile, the <code>.profile</code> suffix is left out.</p>
<dt><code>tag config</code></p>
<dd>See <code>tags</code> configuration setting description below.  When several configuration methods are used at the same time and when LVM looks for the value of a particular setting, it traverses this <code>config cascade</code> from left to right: <code>direct config override on command line</code> -&gt; <code>command profile config</code> -&gt; <code>metadata profile config</code> -&gt; <code>tag config</code> -&gt; <code>lvm.conf</code> No part of this cascade is compulsory. If there&#8217;s no setting value found at the end of the cascade, a default value is used for that setting. Use <code>lvm dumpconfig</code> to check what settings are in use and what the default values are.</p>
<h2>Syntax</h2>
<p>This section describes the configuration file syntax. </p>
<p> Whitespace is not significant unless it is within quotes. This provides a wide choice of acceptable indentation styles. Comments begin with # and continue to the end of the line. They are treated as whitespace. </p>
<p> Here is an informal grammar:</p>
<dl>
<dt><code>file</code> = <code>value</code>*</p>
<dd>A configuration file consists of a set of values.</p>
<dt><code>value</code> = <code>section</code> | <code>assignment</code></p>
<dd>A value can either be a new section, or an assignment.</p>
<dt><code>section</code> = <code>identifier</code> &#8216;<code>{</code>&#8216; <code>value</code>* &#8216;<code>}</code>&#8216;</p>
<dd>A section is groups associated values together.<br />
 It is denoted by a name and delimited by curly brackets.<br />
 e.g.<tt>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr></tt>backup {</p>
<p> <tt>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr></tt><tt>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr></tt>&#8230;</p>
<p> <tt>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr></tt>}</p>
<dt><code>assignment</code> = <code>identifier</code> &#8216;<code>=</code>&#8216; ( <code>array</code> | <code>type</code> )</p>
<dd>An assignment associates a type with an identifier.<br />
 e.g.<tt>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr></tt>level = 7</p>
<dt><code>array</code> = &#8216;<code>[</code>&#8216; ( <code>type</code> &#8216;<code>,</code>&#8216;)* <code>type</code> &#8216;<code>]</code>&#8216; | &#8216;<code>[</code>&#8216; &#8216;<code>]</code>&#8216;</p>
<dd>Inhomogeneous arrays are supported.<br />
 Elements must be separated by commas.<br />
 An empty array is acceptable.</p>
<dt><code>type</code> = <code>integer</code> | <code>float</code> | <code>string</code></p>
<dd><code>integer</code> = [0-9]*<br />
 <code>float</code> = [0-9]*&#8217;<code>.</code>&#8216;[0-9]*<br />
 <code>string </code>= &#8221;.*&#8221;</p>
<dd>Strings must be enclosed in double quotes. </p>
</dl>
<h2>Sections</h2>
<p>The sections that may be present in the file are:</p>
<dl>
<dt><code>devices</code> &#8212; Device settings</p>
<dd>
<dd><code>dir</code> &#8212; Directory in which to create volume group device nodes. Defaults to &quot;/dev&quot;. Commands also accept this as a prefix on volume group names.</p>
<dd><code>scan</code> &#8212; List of directories to scan recursively for LVM physical volumes. Devices in directories outside this hierarchy will be ignored. Defaults to &quot;/dev&quot;.</p>
<dd><code>preferred_names</code> &#8212; List of patterns compared in turn against all the pathnames referencing the same device in in the scanned directories. The pathname that matches the earliest pattern in the list is the one used in any output. As an example, if device-mapper multipathing is used, the following will select multipath device names:<br />
 <code>devices { preferred_names = [ &quot;^/dev/mapper/mpath&quot; ] }</code></p>
<dd><code>filter</code> &#8212; List of patterns to apply to devices found by a scan. Patterns are regular expressions delimited by any character and preceded by <code>a</code> (for accept) or <code>r</code> (for reject). The list is traversed in order, and the first regex that matches determines if the device will be accepted or rejected (ignored). Devices that don&#8217;t match any patterns are accepted. If you want to reject patterns that don&#8217;t match, end the list with &quot;r/.*/&quot;. If there are several names for the same device (e.g. symbolic links in /dev), if the first matching pattern in the list for any of the names is an <code>a</code> pattern, the device is accepted; otherwise if the first matching pattern in the list for any of the names is an <code>r</code> pattern it is rejected; otherwise it is accepted. As an example, to ignore /dev/cdrom you could use:<br />
 <code>devices { filter=[&quot;r|cdrom|&quot;] }</code></p>
<dd><code>global_filter</code> &#8212; Since &quot;filter&quot; might get overridden from the command line, it is not suitable for system-wide device filtering (udev rules, lvmetad). To hide devices from LVM-specific udev processing and/or from lvmetad, you need to set global_filter. The syntax is the same as for normal &quot;filter&quot; above. Devices that fail the global_filter are not even opened by LVM.</p>
<dd><code>cache_dir</code> &#8212; Persistent filter cache file directory. Defaults to &quot;/etc/lvm/cache&quot;.</p>
<dd><code>write_cache_state</code> &#8212; Set to 0 to disable the writing out of the persistent filter cache file when <code>lvm</code> exits. Defaults to 1.</p>
<dd><code>types</code> &#8212; List of pairs of additional acceptable block device types found in /proc/devices together with maximum (non-zero) number of partitions (normally 16). By default, LVM2 supports ide, sd, md, loop, dasd, dac960, nbd, ida, cciss, ubd, ataraid, drbd, power2, i2o_block and iseries/vd. Block devices with major numbers of different types are ignored by LVM2. Example: <code>types = [&quot;fd&quot;, 16]</code>. To create physical volumes on device-mapper volumes created outside LVM2, perhaps encrypted ones from <code>cryptsetup</code>, you&#8217;ll need <code>types = [&quot;device-mapper&quot;, 16]</code>. But if you do this, be careful to avoid recursion within LVM2. The figure for number of partitions is not currently used in LVM2 &#8211; and might never be.</p>
<dd><code>sysfs_scan</code> &#8212; If set to 1 and your kernel supports sysfs and it is mounted, sysfs will be used as a quick way of filtering out block devices that are not present.</p>
<dd><code>md_component_detection</code> &#8212; If set to 1, LVM2 will ignore devices used as components of software RAID (md) devices by looking for md superblocks. This doesn&#8217;t always work satisfactorily e.g. if a device has been reused without wiping the md superblocks first.</p>
<dd><code>md_chunk_alignment</code> &#8212; If set to 1, and a Physical Volume is placed directly upon an md device, LVM2 will align its data blocks with the md device&#8217;s stripe-width.</p>
<dd><code>data_alignment_detection</code> &#8212; If set to 1, and your kernel provides topology information in sysfs for the Physical Volume, the start of data area will be aligned on a multiple of the ’minimum_io_size’ or ’optimal_io_size’ exposed in sysfs. minimum_io_size is the smallest request the device can perform without incurring a read-modify-write penalty (e.g. MD&#8217;s chunk size). optimal_io_size is the device&#8217;s preferred unit of receiving I/O (e.g. MD&#8217;s stripe width). minimum_io_size is used if optimal_io_size is undefined (0). If both <code>md_chunk_alignment</code> and <code>data_alignment_detection</code> are enabled the result of <code>data_alignment_detection</code> is used.</p>
<dd><code>data_alignment</code> &#8212; Default alignment (in KB) of start of data area when creating a new Physical Volume using the <code>lvm2</code> format. If a Physical Volume is placed directly upon an md device and <code>md_chunk_alignment</code> or <code>data_alignment_detection</code> is enabled this parameter is ignored. Set to 0 to use the default alignment of 64KB or the page size, if larger.</p>
<dd><code>data_alignment_offset_detection</code> &#8212; If set to 1, and your kernel provides topology information in sysfs for the Physical Volume, the start of the aligned data area of the Physical Volume will be shifted by the alignment_offset exposed in sysfs. </p>
<p> To see the location of the first Physical Extent of an existing Physical Volume use <code>pvs -o +pe_start</code> . It will be a multiple of the requested <code>data_alignment</code> plus the alignment_offset from <code>data_alignment_offset_detection</code> (if enabled) or the pvcreate commandline.</p>
<dd><code>disable_after_error_count</code> &#8212; During each LVM operation errors received from each device are counted. If the counter of a particular device exceeds the limit set here, no further I/O is sent to that device for the remainder of the respective operation. Setting the parameter to 0 disables the counters altogether.</p>
<dd><code>pv_min_size</code> &#8212; Minimal size (in KB) of the block device which can be used as a PV. In clustered environment all nodes have to use the same value. Any value smaller than 512KB is ignored. Up to and include version 2.02.84 the default was 512KB. From 2.02.85 onwards it was changed to 2MB to avoid floppy drives by default.</p>
<dd><code>issue_discards</code> &#8212; Issue discards to a logical volumes&#8217;s underlying physical volume(s) when the logical volume is no longer using the physical volumes&#8217; space (e.g. lvremove, lvreduce, etc). Discards inform the storage that a region is no longer in use. Storage that supports discards advertise the protocol specific way discards should be issued by the kernel (TRIM, UNMAP, or WRITE SAME with UNMAP bit set). Not all storage will support or benefit from discards but SSDs and thinly provisioned LUNs generally do. If set to 1, discards will only be issued if both the storage and kernel provide support.</p>
<dd>
<dt><code>allocation</code> &#8212; Space allocation policies</p>
<dd>
<dd><code>cling_tag_list</code> &#8212; List of PV tags matched by the <code>cling</code> allocation policy.</p>
<dd>When searching for free space to extend an LV, the <code>cling</code> allocation policy will choose space on the same PVs as the last segment of the existing LV. If there is insufficient space and a list of tags is defined here, it will check whether any of them are attached to the PVs concerned and then seek to match those PV tags between existing extents and new extents.</p>
<dd>The @ prefix for tags is required. Use the special tag &quot;@*&quot; as a wildcard to match any PV tag and so use all PV tags for this purpose.</p>
<dd>For example, LVs are mirrored between two sites within a single VG. PVs are tagged with either @site1 or @site2 to indicate where they are situated and these two PV tags are selected for use with this allocation policy:</p>
<dd>cling_tag_list = [ &quot;@site1&quot;, &quot;@site2&quot; ]</p>
<dt><code>log</code> &#8212; Default log settings</p>
<dd>
<dd><code>file</code> &#8212; Location of log file. If this entry is not present, no log file is written.</p>
<dd><code>overwrite</code> &#8212; Set to 1 to overwrite the log file each time a tool is invoked. By default tools append messages to the log file.</p>
<dd><code>level</code> &#8212; Log level (0-9) of messages to write to the file. 9 is the most verbose; 0 should produce no output.</p>
<dd><code>verbose</code> &#8212; Default level (0-3) of messages sent to stdout or stderr. 3 is the most verbose; 0 should produce the least output.</p>
<dd><code>silent</code> &#8212; Set to 1 to suppress all non-essential tool output. When set, display and reporting tools will still write the requested device properties to standard output, but messages confirming that something was or wasn&#8217;t changed will be reduced to the &#8216;verbose&#8217; level and not appear unless -v is supplied.</p>
<dd><code>syslog</code> &#8212; Set to 1 (the default) to send log messages through syslog. Turn off by setting to 0. If you set to an integer greater than one, this is used &#8211; unvalidated &#8211; as the facility. The default is LOG_USER. See /usr/include/sys/syslog.h for safe facility values to use. For example, LOG_LOCAL0 might be 128.</p>
<dd><code>indent</code> &#8212; When set to 1 (the default) messages are indented according to their severity, two spaces per level. Set to 0 to turn off indentation.</p>
<dd><code>command_names</code> &#8212; When set to 1, the command name is used as a prefix for each message. Default is 0 (off).</p>
<dd><code>prefix</code> &#8212; Prefix used for all messages (after the command name). Default is two spaces.</p>
<dd><code>activation</code> &#8212; Set to 1 to log messages while devices are suspended during activation. Only set this temporarily while debugging a problem because in low memory situations this setting can cause your machine to lock up.</p>
<dt><code>backup</code> &#8212; Configuration for metadata backups.</p>
<dd>
<dd><code>archive_dir</code> &#8212; Directory used for automatic metadata archives. Backup copies of former metadata for each volume group are archived here. Defaults to &quot;/etc/lvm/archive&quot;.</p>
<dd><code>backup_dir</code> &#8212; Directory used for automatic metadata backups. A single backup copy of the current metadata for each volume group is stored here. Defaults to &quot;/etc/lvm/backup&quot;.</p>
<dd><code>archive</code> &#8212; Whether or not tools automatically archive existing metadata into <code>archive_dir</code> before making changes to it. Default is 1 (automatic archives enabled). Set to 0 to disable. Disabling this might make metadata recovery difficult or impossible if something goes wrong.</p>
<dd><code>backup</code> &#8212; Whether or not tools make an automatic backup into <code>backup_dir</code> after changing metadata. Default is 1 (automatic backups enabled). Set to 0 to disable. Disabling this might make metadata recovery difficult or impossible if something goes wrong.</p>
<dd><code>retain_min</code> &#8212; Minimum number of archives to keep. Defaults to 10.</p>
<dd><code>retain_days</code> &#8212; Minimum number of days to keep archive files. Defaults to 30.</p>
<dt><code>shell</code> &#8212; LVM2 built-in readline shell settings</p>
<dd>
<dd><code>history_size</code> &#8212; Maximum number of lines of shell history to retain (default 100) in $HOME/.lvm_history</p>
<dt><code>global</code> &#8212; Global settings</p>
<dd>
<dd><code>test</code> &#8212; If set to 1, run tools in test mode i.e. no changes to the on-disk metadata will get made. It&#8217;s equivalent to having the -t option on every command.</p>
<dd><code>activation</code> &#8212; Set to 0 to turn off all communication with the device-mapper driver. Useful if you want to manipulate logical volumes while device-mapper is not present in your kernel.</p>
<dd><code>proc</code> &#8212; Mount point of proc filesystem. Defaults to /proc.</p>
<dd><code>umask</code> &#8212; File creation mask for any files and directories created. Interpreted as octal if the first digit is zero. Defaults to 077. Use 022 to allow other users to read the files by default.</p>
<dd><code>format</code> &#8212; The default value of <code>&#8211;metadatatype</code> used to determine which format of metadata to use when creating new physical volumes and volume groups. <code>lvm1</code> or <code>lvm2</code>.</p>
<dd><code>fallback_to_lvm1</code> &#8212; Set this to 1 if you need to be able to switch between 2.4 kernels using LVM1 and kernels including device-mapper. The LVM2 tools should be installed as normal and the LVM1 tools should be installed with a .lvm1 suffix e.g. vgscan.lvm1. If an LVM2 tool is then run but unable to communicate with device-mapper, it will automatically invoke the equivalent LVM1 version of the tool. Note that for LVM1 tools to manipulate physical volumes and volume groups created by LVM2 you must use <code>&#8211;metadataformat lvm1</code> when creating them.</p>
<dd><code>library_dir</code> &#8212; A directory searched for LVM2&#8217;s shared libraries ahead of the places <code>dlopen</code> (3) searches.</p>
<dd><code>format_libraries</code> &#8212; A list of shared libraries to load that contain code to process different formats of metadata. For example, liblvm2formatpool.so is needed to read GFS pool metadata if LVM2 was configured <code>&#8211;with-pool=shared</code>.</p>
<dd><code>locking_type</code> &#8212; What type of locking to use. 1 is the default, which use flocks on files in <code>locking_dir</code> (see below) to avoid conflicting LVM2 commands running concurrently on a single machine. 0 disables locking and risks corrupting your metadata. If set to 2, the tools will load the external <code>locking_library</code> (see below). If the tools were configured <code>&#8211;with-cluster=internal</code> (the default) then 3 means to use built-in cluster-wide locking. Type 4 enforces read-only metadata and forbids any operations that might want to modify Volume Group metadata. All changes to logical volumes and their states are communicated using locks.</p>
<dd><code>wait_for_locks</code> &#8212; When set to 1, the default, the tools wait if a lock request cannot be satisfied immediately. When set to 0, the operation is aborted instead.</p>
<dd><code>locking_dir</code> &#8212; The directory LVM2 places its file locks if <code>locking_type</code> is set to 1. The default is <code>/var/lock/lvm</code>.</p>
<dd><code>locking_library</code> &#8212; The name of the external locking library to load if <code>locking_type</code> is set to 2. The default is <code>liblvm2clusterlock.so</code>. If you need to write such a library, look at the lib/locking source code directory.</p>
<dd><code>use_lvmetad</code> &#8212; Whether to use (trust) a running instance of lvmetad. If this is set to 0, all commands fall back to the usual scanning mechanisms. When set to 1 <code>and</code> when lvmetad is running (it is not auto-started), the volume group metadata and PV state flags are obtained from the lvmetad instance and no scanning is done by the individual commands. In a setup with lvmetad, lvmetad udev rules <code>must</code> be set up for LVM to work correctly. Without proper udev rules, all changes in block device configuration will be <code>ignored</code> until a manual &#8216;pvscan &#8211;cache&#8217; is performed.<br />
 If lvmetad has been running while use_lvmetad was 0, it <code>MUST</code> be stopped before changing use_lvmetad to 1 and started again afterwards.</p>
<dt><code>tags</code> &#8212; Host tag settings</p>
<dd>
<dd><code>hosttags</code> &#8212; If set to 1, create a host tag with the machine name. Setting this to 0 does nothing, neither creating nor destroying any tag. The machine name used is the nodename as returned by <code>uname</code> (2).</p>
<dd>Additional host tags to be set can be listed here as subsections. The @ prefix for tags is optional. Each of these host tag subsections can contain a <code>host_list</code> array of host names. If any one of these entries matches the machine name exactly then the host tag gets defined on this particular host, otherwise it doesn&#8217;t.</p>
<dd>After lvm.conf has been processed, LVM2 works through each host tag that has been defined in turn, and if there is a configuration file called lvm_<code>&lt;host_tag&gt;</code>.conf it attempts to load it. The activation/volume_list, devices/filter and devices/types settings are merged (these all are lists), otherwise any settings read in override settings found in earlier files. Any additional host tags defined get appended to the search list, so in turn they can lead to further configuration files being processed. Use <code>lvm dumpconfig</code> to check the result of config file processing.</p>
<dd>The following example always sets host tags <code>tag1</code> and sets <code>tag2</code> on machines fs1 and fs2:</p>
<dd>tags { tag1 { } tag2 { host_list = [ &quot;fs1&quot;, &quot;fs2&quot; ] } }</p>
<dd>These options are useful if you are replicating configuration files around a cluster. Use of <code>hosttags = 1</code> means every machine can have static and identical local configuration files yet use different settings and activate different logical volumes by default. See also <code>volume_list</code> below and <code>&#8211;addtag</code> in <code>lvm</code> (8).</p>
<dt><code>activation</code> &#8212; Settings affecting device-mapper activation</p>
<dd>
<dd><code>missing_stripe_filler</code> &#8212; When activating an incomplete logical volume in partial mode, this option dictates how the missing data is replaced. A value of &quot;error&quot; will cause activation to create error mappings for the missing data, meaning that read access to missing portions of the volume will result in I/O errors. You can instead also use a device path, and in that case this device will be used in place of missing stripes. However, note that using anything other than &quot;error&quot; with mirrored or snapshotted volumes is likely to result in data corruption. For instructions on how to create a device that always returns zeros, see <code>lvcreate</code> (8).</p>
<dd><code>mirror_region_size</code> &#8212; Unit size in KB for copy operations when mirroring.</p>
<dd><code>readahead</code> &#8212; Used when there is no readahead value stored in the volume group metadata. Set to <code>none</code> to disable readahead in these circumstances or <code>auto</code> to use the default value chosen by the kernel.</p>
<dd><code>reserved_memory</code>, <code>reserved_stack</code> &#8212; How many KB to reserve for LVM2 to use while logical volumes are suspended. If insufficient memory is reserved before suspension, there is a risk of machine deadlock.</p>
<dd><code>process_priority</code> &#8212; The nice value to use while devices are suspended. This is set to a high priority so that logical volumes are suspended (with I/O generated by other processes to those logical volumes getting queued) for the shortest possible time.</p>
<dd><code>volume_list</code> &#8212; This acts as a filter through which all requests to activate a logical volume on this machine are passed. A logical volume is only activated if it matches an item in the list. Tags must be preceded by @ and are checked against all tags defined in the logical volume and volume group metadata for a match. @* is short-hand to check every tag set on the host machine (see <code>tags</code> above). Logical volume and volume groups can also be included in the list by name e.g. vg00, vg00/lvol1. If this setting is not present but at least one host tag is defined then a default single-entry list containing @* is assumed.</p>
<dd><code>auto_activation_volume_list</code> &#8212; This acts as a filter through which all requests to autoactivate a logical volume on this machine are passed. A logical volume is autoactivated if it matches an item in the list. Volumes must also pass the <code>volume_list</code> filter, if present. Tags must be preceded by @ and are checked against all tags defined in the logical volume and volume group metadata for a match. @* is short-hand to check every tag set on the host machine (see <code>tags</code> above). Logical volume and volume groups can also be included in the list by name e.g. vg00, vg00/lvol1.</p>
<dd><code>read_only_volume_list</code> &#8212; This acts as a filter through which all requests to activate a logical volume on this machine are passed. A logical volume is activated in read-only mode (instead of read-write) if it matches an item in the list. Volumes must first pass the <code>volume_list</code> filter, if present. Tags must be preceded by @ and are checked against all tags defined in the logical volume and volume group metadata for a match. @* is short-hand to check every tag set on the host machine (see <code>tags</code> above). Logical volume and volume groups can also be included in the list by name e.g. vg00, vg00/lvol1.</p>
<dt><code>metadata</code> &#8212; Advanced metadata settings</p>
<dd>
<dd><code>pvmetadatacopies</code> &#8212; When creating a physical volume using the LVM2 metadata format, this is the default number of copies of metadata to store on each physical volume. Currently it can be set to 0, 1 or 2. The default is 1. If set to 2, one copy is placed at the beginning of the disk and the other is placed at the end. It can be overridden on the command line with <code>&#8211;pvmetadatacopies</code> (see <code>pvcreate</code>). If creating a volume group with just one physical volume, it&#8217;s a good idea to have 2 copies. If creating a large volume group with many physical volumes, you may decide that 3 copies of the metadata is sufficient, i.e. setting it to 1 on three of the physical volumes, and 0 on the rest. Every volume group must contain at least one physical volume with at least 1 copy of the metadata (unless using the text files described below). The disadvantage of having lots of copies is that every time the tools access the volume group, every copy of the metadata has to be accessed, and this slows down the tools.</p>
<dd><code>pvmetadatasize</code> &#8212; Approximate number of sectors to set aside for each copy of the metadata. Volume groups with large numbers of physical or logical volumes, or volumes groups containing complex logical volume structures will need additional space for their metadata. The metadata areas are treated as circular buffers, so unused space becomes filled with an archive of the most recent previous versions of the metadata.</p>
<dd><code>pvmetadataignore</code> When creating a physical volume using the LVM2 metadata format, this states whether metadata areas should be ignored. The default is &quot;n&quot;. If metadata areas on a physical volume are ignored, LVM will not not store metadata in the metadata areas present on newly created Physical Volumes. The option can be overridden on the command line with <code>&#8211;metadataignore</code> (See <code>pvcreate</code> and <code>pvchange</code>). Metadata areas cannot be created or extended after Logical Volumes have been allocated on the device. If you do not want to store metadata on this device, it is still wise always to allocate a metadata area (use a non-zero value for <code>&#8211;pvmetadatacopies</code>) in case you need it in the future and to use this option to instruct LVM2 to ignore it.</p>
<dd><code>vgmetadatacopies</code> &#8212; When creating a volume group using the LVM2 metadata format, this is the default number of copies of metadata desired across all the physical volumes in the volume group. If set to a non-zero value, LVM will automatically set or clear the metadataignore flag on the physical volumes (see <code>pvcreate</code> and <code>pvchange</code> <code>&#8211;metadataignore</code>) in order to achieve the desired number of metadata copies. An LVM command that adds or removes physical volumes (for example, <code>vgextend</code>, <code>vgreduce</code>, <code>vgsplit</code>, or <code>vgmerge</code>), may cause LVM to automatically set or clear the metadataignore flags. Also, if physical volumes go missing or reappear, or a new number of copies is explicitly set (see <code>vgchange &#8211;vgmetadatacopies</code>), LVM may adjust the metadataignore flags. Set <code>vgmetadatacopies</code> to 0 instructs LVM not to set or clear the metadataignore flags automatically. You may set a value larger than the sum of all metadata areas on all physical volumes. The value can be overridden on the command line with <code>&#8211;vgmetadatacopies</code> for various commands (for example, <code>vgcreate</code> and <code>vgchange</code>), and can be queryied with the <code>vg_mda_copies</code> field of <code>vgs</code>. This option is useful for volume groups containing large numbers of physical volumes with metadata as it may be used to minimize metadata read and write overhead.</p>
<dd><code>dirs</code> &#8212; List of directories holding live copies of LVM2 metadata as text files. These directories must not be on logical volumes. It is possible to use LVM2 with a couple of directories here, preferably on different (non-logical-volume) filesystems and with no other on-disk metadata, <code>pvmetadatacopies = 0</code>. Alternatively these directories can be in addition to the on-disk metadata areas. This feature was created during the development of the LVM2 metadata before the new on-disk metadata areas were designed and no longer gets tested. It is not supported under low-memory conditions, and it is important never to edit these metadata files unless you fully understand how things work: to make changes you should always use the tools as normal, or else vgcfgbackup, edit backup, vgcfgrestore.</dl>
