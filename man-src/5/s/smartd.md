<p><code>smartd.conf</code> &#8211; SMART Disk Monitoring Daemon Configuration File </p>
<h2>Full Path</h2>
<p><code>/etc/smartmontools/smartd.conf</code></p>
<h2>Package Version</h2>
<p>smartmontools-6.2 2014-07-16 r3952</p>
<h2>Description</h2>
<p>[This man page is generated for the Linux version of smartmontools. It does not contain info specific to other platforms.] <code>/etc/smartmontools/smartd.conf</code> is the configuration file for the <code>smartd</code> daemon. If the configuration file <code>/etc/smartmontools/smartd.conf</code> is present, <code>smartd</code> reads it at startup, before <code><a href="/docs/linux/man/2-fork/">fork</a></code>(2)ing into the background. If <code>smartd</code> subsequently receives a <code>HUP</code> signal, it will then re-read the configuration file. If <code>smartd</code> is running in debug mode, then an <code>INT</code> signal will also make it re-read the configuration file. This signal can be generated by typing <code>&lt;CONTROL-C&gt;</code> in the terminal window where <code>smartd</code> is running. In the absence of a configuration file <code>smartd</code> will try to open all available devices (see <code><a href="/docs/linux/man/8-smartd/">smartd</a></code>(8) man page). A configuration file with a single line <code>&#8216;DEVICESCAN -a&#8217;</code> would have the same effect. This can be annoying if you have an ATA or SCSI device that hangs or misbehaves when receiving SMART commands. Even if this causes no problems, you may be annoyed by the string of error log messages about devices that can&#8217;t be opened. One can avoid this problem, and gain more control over the types of events monitored by <code>smartd</code>, by using the configuration file <code>/etc/smartmontools/smartd.conf.</code> This file contains a list of devices to monitor, with one device per line. An example file is included with the <code>smartmontools</code> distribution. You will find this sample configuration file in <code>/usr/share/doc/smartmontools/</code>. For security, the configuration file should not be writable by anyone but root. The syntax of the file is as follows:</p>
<dl>
<dt>&bull;</p>
<dd>There should be one device listed per line, although you may have lines that are entirely comments or white space.</p>
<dt>&bull;</p>
<dd>Any text following a hash sign &#8216;#&#8217; and up to the end of the line is taken to be a comment, and ignored.</p>
<dt>&bull;</p>
<dd>Lines may be continued by using a backslash &#8216;\&#8217; as the last non-whitespace or non-comment item on a line.</p>
<dt>&bull;</p>
<dd>Note: a line whose first character is a hash sign &#8216;#&#8217; is treated as a white-space blank line, <code>not</code> as a non-existent line, and will <code>end</code> a continuation line.</dl>

<h2>Configuration File Directives</h2>
<p>If a non-comment entry in the configuration file is the text string <code>DEVICESCAN</code> in capital letters, then <code>smartd</code> will ignore any remaining lines in the configuration file, and will scan for devices. <code>DEVICESCAN</code> may optionally be followed by Directives that will apply to all devices that are found in the scan. Please see below for additional details. </p>
<p> [NEW EXPERIMENTAL SMARTD FEATURE] If an entry in the configuration file starts with <code>DEFAULT</code> instead of a device name, then all directives in this entry are set as defaults for the next device entries. </p>
<p> This configuration: </p>
<pre>&nbsp;<wbr>&nbsp;<wbr>DEFAULT -a -R5! -W 2,40,45 -I 194 -s L/../../7/00 -m admin [at] example.com
&nbsp;<wbr>&nbsp;<wbr>/dev/sda
&nbsp;<wbr>&nbsp;<wbr>/dev/sdb
&nbsp;<wbr>&nbsp;<wbr>/dev/sdc
&nbsp;<wbr>&nbsp;<wbr>DEFAULT -H -m admin [at] example.com
&nbsp;<wbr>&nbsp;<wbr>/dev/sdd
&nbsp;<wbr>&nbsp;<wbr>/dev/sde -d removable</pre>
<p>has the same effect as: </p>
<pre>&nbsp;<wbr>&nbsp;<wbr>/dev/sda -a -R5! -W 2,40,45 -I 194 -s L/../../7/00 -m admin [at] example.com
&nbsp;<wbr>&nbsp;<wbr>/dev/sdb -a -R5! -W 2,40,45 -I 194 -s L/../../7/00 -m admin [at] example.com
&nbsp;<wbr>&nbsp;<wbr>/dev/sdc -a -R5! -W 2,40,45 -I 194 -s L/../../7/00 -m admin [at] example.com
&nbsp;<wbr>&nbsp;<wbr>/dev/sdd -H -m admin [at] example.com
&nbsp;<wbr>&nbsp;<wbr>/dev/sde -d removable -H -m admin [at] example.com</pre>
<p>The following are the Directives that may appear following the device name or <code>DEVICESCAN</code> or <code>DEFAULT</code> on any line of the <code>/etc/smartmontools/smartd.conf</code> configuration file. Note that <code>these are NOT command-line options for </code> <code>smartd</code>. The Directives below may appear in any order, following the device name. </p>
<p> <code>For an ATA device,</code> if no Directives appear, then the device will be monitored as if the &#8216;-a&#8217; Directive (monitor all SMART properties) had been given. </p>
<p> <code>If a SCSI disk is listed,</code> it will be monitored at the maximum implemented level: roughly equivalent to using the &#8216;-H -l selftest&#8217; options for an ATA disk. So with the exception of &#8216;-d&#8217;, &#8216;-m&#8217;, &#8216;-l selftest&#8217;, &#8216;-s&#8217;, and &#8216;-M&#8217;, the Directives below are ignored for SCSI disks. For SCSI disks, the &#8216;-m&#8217; Directive sends a warning email if the SMART status indicates a disk failure or problem, if the SCSI inquiry about disk status fails, or if new errors appear in the self-test log. </p>
<p> <code>If a 3ware controller is used</code> then the corresponding SCSI (/dev/sd?) or character device (/dev/twe?, /dev/twa?, /dev/twl? or /dev/tws?) must be listed, along with the &#8216;-d 3ware,N&#8217; Directive (see below). The individual ATA disks hosted by the 3ware controller appear to <code>smartd</code> as normal ATA devices. Hence all the ATA directives can be used for these disks (but see note below). </p>
<p> <code>If an Areca controller is used</code> then the corresponding device (SCSI /dev/sg? on Linux or /dev/arcmsr0 on FreeBSD) must be listed, along with the &#8216;-d areca,N&#8217; Directive (see below). The individual SATA disks hosted by the Areca controller appear to <code>smartd</code> as normal ATA devices. Hence all the ATA directives can be used for these disks. Areca firmware version 1.46 or later which supports smartmontools must be used; Please see the <code><a href="/docs/linux/man/8-smartctl/">smartctl</a></code>(8) man page for further details.</p>
<dl>
<dt><code>-d TYPE</code></p>
<dd>Specifies the type of the device. The valid arguments to this directive are: </p>
<p> <i>auto</i> &#8211; attempt to guess the device type from the device name or from controller type info provided by the operating system or from a matching USB ID entry in the drive database. This is the default. </p>
<p> <i>ata</i> &#8211; the device type is ATA. This prevents <code>smartd</code> from issuing SCSI commands to an ATA device. </p>
<p> <i>scsi</i> &#8211; the device type is SCSI. This prevents <code>smartd</code> from issuing ATA commands to a SCSI device. </p>
<p> <i>sat[,auto][,N]</i> &#8211; the device type is SCSI to ATA Translation (SAT). This is for ATA disks that have a SCSI to ATA Translation (SAT) Layer (SATL) between the disk and the operating system. SAT defines two ATA PASS THROUGH SCSI commands, one 12 bytes long and the other 16 bytes long. The default is the 16 byte variant which can be overridden with either &#8216;-d sat,12&#8217; or &#8216;-d sat,16&#8217;. </p>
<p> If &#8216;-d sat,auto&#8217; is specified, device type SAT (for ATA/SATA disks) is only used if the SCSI INQUIRY data reports a SATL (VENDOR: &quot;ATA &quot;). Otherwise device type SCSI (for SCSI/SAS disks) is used. </p>
<p> <i>usbcypress</i> &#8211; this device type is for ATA disks that are behind a Cypress USB to PATA bridge. This will use the ATACB proprietary scsi pass through command. The default SCSI operation code is 0x24, but although it can be overridden with &#8216;-d usbcypress,0xN&#8217;, where N is the scsi operation code, you&#8217;re running the risk of damage to the device or filesystems on it. </p>
<p> <i>usbjmicron[,p][,x][,PORT]</i> &#8211; this device type is for SATA disks that are behind a JMicron USB to PATA/SATA bridge. The 48-bit ATA commands (required e.g. for &#8216;-l xerror&#8217;, see below) do not work with all of these bridges and are therefore disabled by default. These commands can be enabled by &#8216;-d usbjmicron,x&#8217;. If two disks are connected to a bridge with two ports, an error message is printed if no PORT is specified. The port can be specified by &#8216;-d usbjmicron[,x],PORT&#8217; where PORT is 0 (master) or 1 (slave). This is not necessary if the device uses a port multiplier to connect multiple disks to one port. The disks appear under separate /dev/ice names then. CAUTION: Specifying &#8216;,x&#8217; for a device which does not support it results in I/O errors and may disconnect the drive. The same applies if the specified PORT does not exist or is not connected to a disk. </p>
<p> [NEW EXPERIMENTAL SMARTD FEATURE] The Prolific PL2507/3507 USB bridges with older firmware support a pass-through command similar to JMicron and work with &#8216;-d usbjmicron,0&#8217;. Newer Prolific firmware requires a modified command which can be selected by &#8216;-d usbjmicron,p&#8217;. Note that this does not yet support the SMART status command. </p>
<p> <i>usbsunplus</i> &#8211; this device type is for SATA disks that are behind a SunplusIT USB to SATA bridge. </p>
<p> <i>marvell</i> &#8211; [Linux only] interact with SATA disks behind Marvell chip-set controllers (using the Marvell rather than libata driver). </p>
<p> <i>megaraid,N</i> &#8211; [Linux only] the device consists of one or more SCSI/SAS disks connected to a MegaRAID controller. The non-negative integer N (in the range of 0 to 127 inclusive) denotes which disk on the controller is monitored. This interface will also work for Dell PERC controllers. In log files and email messages this disk will be identified as megaraid_disk_XXX with XXX in the range from 000 to 127 inclusive. It is possible to set RAID device name as /dev/bus/N, where N is a SCSI bus number. Please see the <code><a href="/docs/linux/man/8-smartctl/">smartctl</a></code>(8) man page for further details. </p>
<p> <i>3ware,N</i> &#8211; [FreeBSD and Linux only] the device consists of one or more ATA disks connected to a 3ware RAID controller. The non-negative integer N (in the range from 0 to 127 inclusive) denotes which disk on the controller is monitored. In log files and email messages this disk will be identified as 3ware_disk_XXX with XXX in the range from 000 to 127 inclusive. </p>
<p> Note that while you may use <code>any</code> of the 3ware SCSI logical devices /dev/tw* to address <code>any</code> of the physical disks (3ware ports), error and log messages will make the most sense if you always list the 3ware SCSI logical device corresponding to the particular physical disks. Please see the <code><a href="/docs/linux/man/8-smartctl/">smartctl</a></code>(8) man page for further details. </p>
<p> <i>areca,N</i> &#8211; [FreeBSD, Linux, Windows and Cygwin only] the device consists of one or more SATA disks connected to an Areca SATA RAID controller. The positive integer N (in the range from 1 to 24 inclusive) denotes which disk on the controller is monitored. In log files and email messages this disk will be identifed as areca_disk_XX with XX in the range from 01 to 24 inclusive. Please see the <code><a href="/docs/linux/man/8-smartctl/">smartctl</a></code>(8) man page for further details. </p>
<p> <i>areca,N/E</i> &#8211; [FreeBSD, Linux, Windows and Cygwin only] [NEW EXPERIMENTAL SMARTD FEATURE] the device consists of one or more SATA or SAS disks connected to an Areca SAS RAID controller. The integer N (range 1 to 128) denotes the channel (slot) and E (range 1 to 8) denotes the enclosure. Important: This requires Areca SAS controller firmware version 1.51 or later. </p>
<p> <i>cciss,N</i> &#8211; [FreeBSD and Linux only] the device consists of one or more SCSI/SAS or SATA disks connected to a cciss RAID controller. The non-negative integer N (in the range from 0 to 15 inclusive) denotes which disk on the controller is monitored. In log files and email messages this disk will be identified as cciss_disk_XX with XX in the range from 00 to 15 inclusive. Please see the <code><a href="/docs/linux/man/8-smartctl/">smartctl</a></code>(8) man page for further details. </p>
<p> <i>hpt,L/M/N</i> &#8211; [FreeBSD and Linux only] the device consists of one or more ATA disks connected to a HighPoint RocketRAID controller. The integer L is the controller id, the integer M is the channel number, and the integer N is the PMPort number if it is available. The allowed values of L are from 1 to 4 inclusive, M are from 1 to 128 inclusive and N from 1 to 4 if PMPort available. And also these values are limited by the model of the HighPoint RocketRAID controller. In log files and email messages this disk will be identified as hpt_X/X/X and X/X/X is the same as L/M/N, note if no N indicated, N set to the default value 1. Please see the <code><a href="/docs/linux/man/8-smartctl/">smartctl</a></code>(8) man page for further details. </p>
<p> <i>ignore</i> &#8211; [NEW EXPERIMENTAL SMARTD FEATURE] the device specified by this configuration entry should be ignored. This allows to ignore specific devices which are detected by a following DEVICESCAN configuration line. It may also be used to temporary disable longer multi-line configuration entries. This Directive may be used in conjunction with the other &#8216;-d&#8217; Directives. </p>
<p> <i>removable</i> &#8211; the device or its media is removable. This indicates to <code>smartd</code> that it should continue (instead of exiting, which is the default behavior) if the device does not appear to be present when <code>smartd</code> is started. This Directive may be used in conjunction with the other &#8216;-d&#8217; Directives.</p>
<dt><code>-n POWERMODE[,N][,q]</code></p>
<dd>[ATA only] This &#8216;nocheck&#8217; Directive is used to prevent a disk from being spun-up when it is periodically polled by <code>smartd</code>. </p>
<p> ATA disks have five different power states. In order of increasing power consumption they are: &#8216;OFF&#8217;, &#8216;SLEEP&#8217;, &#8216;STANDBY&#8217;, &#8216;IDLE&#8217;, and &#8216;ACTIVE&#8217;. Typically in the OFF, SLEEP, and STANDBY modes the disk&#8217;s platters are not spinning. But usually, in response to SMART commands issued by <code>smartd</code>, the disk platters are spun up. So if this option is not used, then a disk which is in a low-power mode may be spun up and put into a higher-power mode when it is periodically polled by <code>smartd</code>. </p>
<p> Note that if the disk is in SLEEP mode when <code>smartd</code> is started, then it won&#8217;t respond to <code>smartd</code> commands, and so the disk won&#8217;t be registered as a device for <code>smartd</code> to monitor. If a disk is in any other low-power mode, then the commands issued by <code>smartd</code> to register the disk will probably cause it to spin-up. </p>
<p> The &#8216;<code>-n</code>&#8216; (nocheck) Directive specifies if <code>smartd</code>&#8216;s periodic checks should still be carried out when the device is in a low-power mode. It may be used to prevent a disk from being spun-up by periodic <code>smartd</code> polling. The allowed values of POWERMODE are: </p>
<p> <i>never</i> &#8211; <code>smartd</code> will poll (check) the device regardless of its power mode. This may cause a disk which is spun-down to be spun-up when <code>smartd</code> checks it. This is the default behavior if the &#8216;-n&#8217; Directive is not given. </p>
<p> <i>sleep</i> &#8211; check the device unless it is in SLEEP mode. </p>
<p> <i>standby</i> &#8211; check the device unless it is in SLEEP or STANDBY mode. In these modes most disks are not spinning, so if you want to prevent a laptop disk from spinning up each time that <code>smartd</code> polls, this is probably what you want. </p>
<p> <i>idle</i> &#8211; check the device unless it is in SLEEP, STANDBY or IDLE mode. In the IDLE state, most disks are still spinning, so this is probably not what you want. </p>
<p> Maximum number of skipped checks (in a row) can be specified by appending positive number &#8216;,N&#8217; to POWERMODE (like &#8216;-n standby,15&#8217;). After N checks are skipped in a row, powermode is ignored and the check is performed anyway. </p>
<p> When a periodic test is skipped, <code>smartd</code> normally writes an informal log message. The message can be suppressed by appending the option &#8216;,q&#8217; to POWERMODE (like &#8216;-n standby,q&#8217;). This prevents a laptop disk from spinning up due to this message. </p>
<p> Both &#8216;,N&#8217; and &#8216;,q&#8217; can be specified together.</p>
<dt><code>-T TYPE</code></p>
<dd>Specifies how tolerant <code>smartd</code> should be of SMART command failures. The valid arguments to this Directive are: </p>
<p> <i>normal</i> &#8211; do not try to monitor the disk if a mandatory SMART command fails, but continue if an optional SMART command fails. This is the default. </p>
<p> <i>permissive</i> &#8211; try to monitor the disk even if it appears to lack SMART capabilities. This may be required for some old disks (prior to ATA-3 revision 4) that implemented SMART before the SMART standards were incorporated into the ATA/ATAPI Specifications. [Please see the <code>smartctl -T</code> command-line option.]</p>
<dt><code>-o VALUE</code></p>
<dd>[ATA only] Enables or disables SMART Automatic Offline Testing when <code>smartd</code> starts up and has no further effect. The valid arguments to this Directive are <i>on</i> and <i>off</i>. </p>
<p> The delay between tests is vendor-specific, but is typically four hours. </p>
<p> Note that SMART Automatic Offline Testing is <code>not</code> part of the ATA Specification. Please see the <code>smartctl -o</code> command-line option documentation for further information about this feature.</p>
<dt><code>-S VALUE</code></p>
<dd>Enables or disables Attribute Autosave when <code>smartd</code> starts up and has no further effect. The valid arguments to this Directive are <i>on</i> and <i>off</i>. Also affects SCSI devices. [Please see the <code>smartctl -S</code> command-line option.]</p>
<dt><code>-H</code></p>
<dd>[ATA only] Check the SMART health status of the disk. If any Prefailure Attributes are less than or equal to their threshold values, then disk failure is predicted in less than 24 hours, and a message at loglevel <code>&#8216;LOG_CRIT&#8217;</code> will be logged to syslog. [Please see the <code>smartctl -H</code> command-line option.]</p>
<dt><code>-l TYPE</code></p>
<dd>Reports increases in the number of errors in one of three SMART logs. The valid arguments to this Directive are: </p>
<p> <i>error</i> &#8211; [ATA only] report if the number of ATA errors reported in the Summary SMART error log has increased since the last check. </p>
<p> <i>xerror</i> &#8211; [ATA only] report if the number of ATA errors reported in the Extended Comprehensive SMART error log has increased since the last check. </p>
<p> If both &#8216;-l error&#8217; and &#8216;-l xerror&#8217; are specified, smartd checks the maximum of both values. </p>
<p> [Please see the <code>smartctl -l xerror</code> command-line option.] </p>
<p> <i>selftest</i> &#8211; report if the number of failed tests reported in the SMART Self-Test Log has increased since the last check, or if the timestamp associated with the most recent failed test has increased. Note that such errors will <code>only</code> be logged if you run self-tests on the disk (and it fails a test!). Self-Tests can be run automatically by <code>smartd</code>: please see the <code>&#8216;-s&#8217;</code> Directive below. Self-Tests can also be run manually by using the <code>&#8216;-t short&#8217;</code> and <code>&#8216;-t long&#8217;</code> options of <code>smartctl</code> and the results of the testing can be observed using the <code>smartctl &#8216;-l selftest&#8217;</code> command-line option. [Please see the <code>smartctl -l</code> and <code>-t</code> command-line options.] </p>
<p> [ATA only] Failed self-tests outdated by a newer successful extended self-test are ignored. The warning email counter is reset if the number of failed self tests dropped to 0. This typically happens when an extended self-test is run after all bad sectors have been reallocated. </p>
<p> <i>offlinests[,ns]</i> &#8211; [ATA only] report if the Offline Data Collection status has changed since the last check. The report will be logged as LOG_CRIT if the new status indicates an error. With some drives the status often changes, therefore &#8216;-l offlinests&#8217; is not enabled by &#8216;-a&#8217; Directive. Appending &#8216;,ns&#8217; (no standby) to this directive is not implemented on Linux. </p>
<p> <i>selfteststs[,ns]</i> &#8211; [ATA only] report if the Self-Test execution status has changed since the last check. The report will be logged as LOG_CRIT if the new status indicates an error. Appending &#8216;,ns&#8217; (no standby) to this directive is not implemented on Linux. </p>
<p> <i>scterc,READTIME,WRITETIME</i> &#8211; [ATA only] sets the SCT Error Recovery Control settings to the specified values (deciseconds) when <code>smartd</code> starts up and has no further effect. Values of 0 disable the feature, other values less than 65 are probably not supported. For RAID configurations, this is typically set to 70,70 deciseconds. [Please see the <code>smartctl -l scterc</code> command-line option.] </p>
<dt><code>-e NAME[,VALUE]</code></p>
<dd>Sets non-SMART device settings when <code>smartd</code> starts up and has no further effect. [Please see the <code>smartctl &#8211;set</code> command-line option.] Valid arguments are: </p>
<p> <i>aam,[N|off]</i> &#8211; [ATA only] Sets the Automatic Acoustic Management (AAM) feature. </p>
<p> <i>apm,[N|off]</i> &#8211; [ATA only] Sets the Advanced Power Management (APM) feature. </p>
<p> <i>lookahead,[on|off]</i> &#8211; [ATA only] Sets the read look-ahead feature. </p>
<p> <i>security-freeze</i> &#8211; [ATA only] Sets ATA Security feature to frozen mode. </p>
<p> <i>standby,[N|off]</i> &#8211; [ATA only] Sets the standby (spindown) timer and places the drive in the IDLE mode. </p>
<p> <i>wcache,[on|off]</i> &#8211; [ATA only] Sets the volatile write cache feature. </p>
<dt><code>-s REGEXP</code></p>
<dd>Run Self-Tests or Offline Immediate Tests, at scheduled times. A Self- or Offline Immediate Test will be run at the end of periodic device polling, if all 12 characters of the string <code>T/MM/DD/d/HH</code> match the extended regular expression <code>REGEXP</code>. Here:</p>
<dl>
<dd>
<dl>
<dt><code>T</code></p>
<dd>is the type of the test. The values that <code>smartd</code> will try to match (in turn) are: &#8216;L&#8217; for a <code>L</code>ong Self-Test, &#8216;S&#8217; for a <code>S</code>hort Self-Test, &#8216;C&#8217; for a <code>C</code>onveyance Self-Test (ATA only), and &#8216;O&#8217; for an <code>O</code>ffline Immediate Test (ATA only). As soon as a match is found, the test will be started and no additional matches will be sought for that device and that polling cycle. </p>
<p> To run scheduled Selective Self-Tests, use &#8216;n&#8217; for <code>n</code>ext span, &#8216;r&#8217; to <code>r</code>edo last span, or &#8216;c&#8217; to <code>c</code>ontinue with next span or redo last span based on status of last test. The LBA range is based on the first span from the last test. See the <code>smartctl -t select,[next|redo|cont]</code> options for further info. </p>
<p> Some disks (e.g. WD) do not preserve the selective self test log accross power cycles. If state persistence (&#8216;-s&#8217; option) is enabled, the last test span is preserved by smartd and used if (and only if) the selective self test log is empty. </p>
<dt><code>MM</code></p>
<dd>is the month of the year, expressed with two decimal digits. The range is from 01 (January) to 12 (December) inclusive. Do <code>not</code> use a single decimal digit or the match will always fail!</p>
<dt><code>DD</code></p>
<dd>is the day of the month, expressed with two decimal digits. The range is from 01 to 31 inclusive. Do <code>not</code> use a single decimal digit or the match will always fail!</p>
<dt><code>d</code></p>
<dd>is the day of the week, expressed with one decimal digit. The range is from 1 (Monday) to 7 (Sunday) inclusive.</p>
<dt><code>HH</code></p>
<dd>is the hour of the day, written with two decimal digits, and given in hours after midnight. The range is 00 (midnight to just before 1am) to 23 (11pm to just before midnight) inclusive. Do <code>not</code> use a single decimal digit or the match will always fail!</dl>
</dl>
<dd>Some examples follow. In reading these, keep in mind that in extended regular expressions a dot <code>&#8216;.&#8217;</code> matches any single character, and a parenthetical expression such as <code>&#8216;(A|B|C)&#8217;</code> denotes any one of the three possibilities <code>A</code>, <code>B</code>, or <code>C</code>. </p>
<p> To schedule a short Self-Test between 2-3am every morning, use: </p>
<pre><code> -s S/../.././02</code></pre>
<p>To schedule a long Self-Test between 4-5am every Sunday morning, use: </p>
<pre><code> -s L/../../7/04</code></pre>
<p>To schedule a long Self-Test between 10-11pm on the first and fifteenth day of each month, use: </p>
<pre><code> -s L/../(01|15)/./22</code></pre>
<p>To schedule an Offline Immediate test after every midnight, 6am, noon,and 6pm, plus a Short Self-Test daily at 1-2am and a Long Self-Test every Saturday at 3-4am, use: </p>
<pre><code> -s (O/../.././(00|06|12|18)|S/../.././01|L/../../6/03)</code></pre>
<p>If Long Self-Tests of a large disks take longer than the system uptime, a full disk test can be performed by several Selective Self-Tests. To setup a full test of a 1TB disk within 20 days (one 50GB span each day), run this command once: </p>
<pre> smartctl -t select,0-99999999 /dev/sda</pre>
<p>To run the next test spans on Monday-Friday between 12-13am, run smartd with this directive: </p>
<pre><code> -s n/../../[1-5]/12</code></pre>
<p>Scheduled tests are run immediately following the regularly-scheduled device polling, if the current local date, time, and test type, match <code>REGEXP</code>. By default the regularly-scheduled device polling occurs every thirty minutes after starting <code>smartd</code>. Take caution if you use the &#8216;-i&#8217; option to make this polling interval more than sixty minutes: the poll times may fail to coincide with any of the testing times that you have specified with <code>REGEXP</code>. In this case the test will be run following the next device polling. </p>
<p> Before running an offline or self-test, <code>smartd</code> checks to be sure that a self-test is not already running. If a self-test <code>is</code> already running, then this running self test will <code>not</code> be interrupted to begin another test. </p>
<p> <code>smartd</code> will not attempt to run <code>any</code> type of test if another test was already started or run in the same hour. </p>
<p> To avoid performance problems during system boot, <code>smartd</code> will not attempt to run any scheduled tests following the very first device polling (unless &#8216;-q onecheck&#8217; is specified). </p>
<p> Each time a test is run, <code>smartd</code> will log an entry to SYSLOG. You can use these or the &#8216;-q showtests&#8217; command-line option to verify that you constructed <code>REGEXP</code> correctly. The matching order (<code>L</code> before <code>S</code> before <code>C</code> before <code>O</code>) ensures that if multiple test types are all scheduled for the same hour, the longer test type has precedence. This is usually the desired behavior. </p>
<p> If the scheduled tests are used in conjunction with state persistence (&#8216;-s&#8217; option), smartd will also try to match the hours since last shutdown (or 90 days at most). If any test would have been started during downtime, the longest (see above) of these tests is run after second device polling. </p>
<p> If the &#8216;-n&#8217; directive is used and any test would have been started during disk standby time, the longest of these tests is run when the disk is active again. </p>
<p> Unix users: please beware that the rules for extended regular expressions [<a href="/docs/linux/man/7-regex/">regex</a>(7)] are <code>not</code> the same as the rules for file-name pattern matching by the shell [<a href="/docs/linux/man/7-glob/">glob</a>(7)]. <code>smartd</code> will issue harmless informational warning messages if it detects characters in <code>REGEXP</code> that appear to indicate that you have made this mistake.</p>
<dt><code>-m ADD</code></p>
<dd>Send a warning email to the email address <code>ADD</code> if the &#8216;-H&#8217;, &#8216;-l&#8217;, &#8216;-f&#8217;, &#8216;-C&#8217;, or &#8216;-O&#8217; Directives detect a failure or a new error, or if a SMART command to the disk fails. This Directive only works in conjunction with these other Directives (or with the equivalent default &#8216;-a&#8217; Directive). </p>
<p> To prevent your email in-box from getting filled up with warning messages, by default only a single warning will be sent for each of the enabled alert types, &#8216;-H&#8217;, &#8216;-l&#8217;, &#8216;-f&#8217;, &#8216;-C&#8217;, or &#8216;-O&#8217; even if more than one failure or error is detected or if the failure or error persists. [This behavior can be modified; see the &#8216;-M&#8217; Directive below.] </p>
<p> To send email to more than one user, please use the following &quot;comma separated&quot; form for the address: <code>user1 [at] add1,user2 [at] add2,&#8230;,userN [at] addN</code> (with no spaces). </p>
<p> To test that email is being sent correctly, use the &#8216;-M test&#8217; Directive described below to send one test email message on <code>smartd</code> startup. </p>
<p> By default, email is sent using the system <code>mail</code> command. In order that <code>smartd</code> find the mail command (normally /bin/mail) an executable named <code>&#8216;mail&#8217;</code> must be in the path of the shell or environment from which <code>smartd</code> was started. If you wish to specify an explicit path to the mail executable (for example /usr/local/bin/mail) or a custom script to run, please use the &#8216;-M exec&#8217; Directive below. </p>
<p> Note also that there is a special argument <code>&lt;nomailer&gt;</code> which can be given to the &#8216;-m&#8217; Directive in conjunction with the &#8216;-M exec&#8217; Directive. Please see below for an explanation of its effect. </p>
<p> If the mailer or the shell running it produces any STDERR/STDOUT output, then a snippet of that output will be copied to SYSLOG. The remainder of the output is discarded. If problems are encountered in sending mail, this should help you to understand and fix them. If you have mail problems, we recommend running <code>smartd</code> in debug mode with the &#8216;-d&#8217; flag, using the &#8216;-M test&#8217; Directive described below. </p>
<p> [NEW EXPERIMENTAL SMARTD FEATURE] If a word of the comma separated list has the form &#8216;@plugin&#8217;, a custom script /etc/smartmontools/smartd_warning.d/plugin is run and the word is removed from the list before sending mail. The string &#8216;plugin&#8217; may be any valid name except &#8216;ALL&#8217;. If &#8216;@ALL&#8217; is specified, all scripts in /etc/smartmontools/smartd_warning.d/* are run instead. This is handled by the script /etc/smartmontools/smartd_warning.sh (see also &#8216;-M exec&#8217; below).</p>
<dt><code>-M TYPE</code></p>
<dd>These Directives modify the behavior of the <code>smartd</code> email warnings enabled with the &#8216;-m&#8217; email Directive described above. These &#8216;-M&#8217; Directives only work in conjunction with the &#8216;-m&#8217; Directive and can not be used without it. </p>
<p> Multiple -M Directives may be given. If more than one of the following three -M Directives are given (example: -M once -M daily) then the final one (in the example, -M daily) is used. </p>
<p> The valid arguments to the -M Directive are (one of the following three): </p>
<p> <i>once</i> &#8211; send only one warning email for each type of disk problem detected. This is the default unless state persistence (&#8216;-s&#8217; option) is enabled. </p>
<p> <i>daily</i> &#8211; send additional warning reminder emails, once per day, for each type of disk problem detected. This is the default if state persistence (&#8216;-s&#8217; option) is enabled. </p>
<p> <i>diminishing</i> &#8211; send additional warning reminder emails, after a one-day interval, then a two-day interval, then a four-day interval, and so on for each type of disk problem detected. Each interval is twice as long as the previous interval. </p>
<p> If a disk problem is no longer detected, the internal email counter is reset. If the problem reappears a new warning email is sent immediately. </p>
<p> In addition, one may add zero or more of the following Directives: </p>
<p> <i>test</i> &#8211; send a single test email immediately upon <code>smartd</code> startup. This allows one to verify that email is delivered correctly. Note that if this Directive is used, <code>smartd</code> will also send the normal email warnings that were enabled with the &#8216;-m&#8217; Directive, in addition to the single test email! </p>
<p> <i>exec PATH</i> &#8211; run the executable PATH instead of the default mail command, when <code>smartd</code> needs to send email. PATH must point to an executable binary file or script. </p>
<p> By setting PATH to point to a customized script, you can make <code>smartd</code> perform useful tricks when a disk problem is detected (beeping the console, shutting down the machine, broadcasting warnings to all logged-in users, etc.) But please be careful. <code>smartd</code> will <code>block</code> until the executable PATH returns, so if your executable hangs, then <code>smartd</code> will also hang. Some sample scripts are included in /usr/share/doc/smartmontools/examplescripts/. </p>
<p> The return status of the executable is recorded by <code>smartd</code> in SYSLOG. The executable is not expected to write to STDOUT or STDERR. If it does, then this is interpreted as indicating that something is going wrong with your executable, and a fragment of this output is logged to SYSLOG to help you to understand the problem. Normally, if you wish to leave some record behind, the executable should send mail or write to a file or device. </p>
<p> Before running the executable, <code>smartd</code> sets a number of environment variables. These environment variables may be used to control the executable&#8217;s behavior. The environment variables exported by <code>smartd</code> are:</p>
<dl>
<dd>
<dl>
<dt><code>SMARTD_MAILER</code></p>
<dd>is set to the argument of -M exec, if present or else to &#8216;mail&#8217; (examples: /bin/mail, mail).</p>
<dt><code>SMARTD_DEVICE</code></p>
<dd>is set to the device path (examples: /dev/hda, /dev/sdb).</p>
<dt><code>SMARTD_DEVICETYPE</code></p>
<dd>is set to the device type specified by &#8216;-d&#8217; directive or &#8216;auto&#8217; if none.</p>
<dt><code>SMARTD_DEVICESTRING</code></p>
<dd>is set to the device description. For SMARTD_DEVICETYPE of ata or scsi, this is the same as SMARTD_DEVICE. For 3ware RAID controllers, the form used is &#8216;/dev/sdc [3ware_disk_01]&#8217;. For HighPoint RocketRAID controller, the form is &#8216;/dev/sdd [hpt_1/1/1]&#8217; under Linux or &#8216;/dev/hptrr [hpt_1/1/1]&#8217; under FreeBSD. For Areca controllers, the form is &#8216;/dev/sg2 [areca_disk_09]&#8217; on Linux or &#8216;/dev/arcmsr0 [areca_disk_09]&#8217; on FreeBSD. In these cases the device string contains a space and is NOT quoted. So to use $SMARTD_DEVICESTRING in a bash script you should probably enclose it in double quotes.</p>
<dt><code>SMARTD_DEVICEINFO</code></p>
<dd>is set to device identify information. It includes most of the info printed by <code>smartctl -i</code> but uses a brief single line format. This device info is also logged when <code>smartd</code> starts up. The string contains space characters and is NOT quoted.</p>
<dt><code>SMARTD_FAILTYPE</code></p>
<dd>gives the reason for the warning or message email. The possible values that it takes and their meanings are: <i>EmailTest</i>: this is an email test message. <i>Health</i>: the SMART health status indicates imminent failure. <i>Usage</i>: a usage Attribute has failed. <i>SelfTest</i>: the number of self-test failures has increased. <i>ErrorCount</i>: the number of errors in the ATA error log has increased. <i>CurrentPendingSector</i>: one of more disk sectors could not be read and are marked to be reallocated (replaced with spare sectors). <i>OfflineUncorrectableSector</i>: during off-line testing, or self-testing, one or more disk sectors could not be read. <i>Temperature</i>: Temperature reached critical limit (see -W directive). <i>FailedHealthCheck</i>: the SMART health status command failed. <i>FailedReadSmartData</i>: the command to read SMART Attribute data failed. <i>FailedReadSmartErrorLog</i>: the command to read the SMART error log failed. <i>FailedReadSmartSelfTestLog</i>: the command to read the SMART self-test log failed. <i>FailedOpenDevice</i>: the open() command to the device failed.</p>
<dt><code>SMARTD_ADDRESS</code></p>
<dd>is determined by the address argument ADD of the &#8216;-m&#8217; Directive. If ADD is <code>&lt;nomailer&gt;</code>, then <code>SMARTD_ADDRESS</code> is not set. Otherwise, it is set to the comma-separated-list of email addresses given by the argument ADD, with the commas replaced by spaces (example:admin [at] example.com root). If more than one email address is given, then this string will contain space characters and is NOT quoted, so to use it in a bash script you may want to enclose it in double quotes.</p>
<dt><code>SMARTD_MESSAGE</code></p>
<dd>is set to the one sentence summary warning email message string from <code>smartd</code>. This message string contains space characters and is NOT quoted. So to use $SMARTD_MESSAGE in a bash script you should probably enclose it in double quotes.</p>
<dt><code>SMARTD_FULLMESSAGE</code></p>
<dd>is set to the contents of the entire email warning message string from <code>smartd</code>. This message string contains space and return characters and is NOT quoted. So to use $SMARTD_FULLMESSAGE in a bash script you should probably enclose it in double quotes.</p>
<dt><code>SMARTD_TFIRST</code></p>
<dd>is a text string giving the time and date at which the first problem of this type was reported. This text string contains space characters and no newlines, and is NOT quoted. For example: Sun Feb 9 14:58:19 2003 CST</p>
<dt><code>SMARTD_TFIRSTEPOCH</code></p>
<dd>is an integer, which is the unix epoch (number of seconds since Jan 1, 1970) for <code>SMARTD_TFIRST</code>.</p>
<dt><code>SMARTD_PREVCNT</code></p>
<dd>is an integer specifying the number of previous messages sent. It is set to &#8216;0&#8217; for the first message.</p>
<dt><code>SMARTD_NEXTDAYS</code></p>
<dd>is an integer specifying the number of days until the next message will be sent. It it set to empty on &#8216;-M once&#8217; and set to &#8216;1&#8217; on &#8216;-M daily&#8217;.</dl>
</dl>
<dd>The shell which is used to run PATH is system-dependent. For vanilla Linux/glibc it&#8217;s bash. For other systems, the man page for <code><a href="/docs/linux/man/3-popen/">popen</a></code>(3) should say what shell is used. </p>
<p> If the &#8216;-m ADD&#8217; Directive is given with a normal address argument, then the executable pointed to by PATH will be run in a shell with STDIN receiving the body of the email message, and with the same command-line arguments: </p>
<pre>-s &quot;$SMARTD_SUBJECT&quot; $SMARTD_ADDRESS</pre>
<p>that would normally be provided to &#8216;mail&#8217;. Examples include: </p>
<pre><code>-m user [at] home -M exec /bin/mail</code>
<code>-m admin [at] work -M exec /usr/local/bin/mailto</code>
<code>-m root -M exec /Example_1/bash/script/below</code></pre>
<p>If the &#8216;-m ADD&#8217; Directive is given with the special address argument <code>&lt;nomailer&gt;</code> then the executable pointed to by PATH is run in a shell with <code>no</code> STDIN and <code>no</code> command-line arguments, for example: </p>
<pre><code>-m &lt;nomailer&gt; -M exec /Example_2/bash/script/below</code></pre>
<p>If the executable produces any STDERR/STDOUT output, then <code>smartd</code> assumes that something is going wrong, and a snippet of that output will be copied to SYSLOG. The remainder of the output is then discarded. </p>
<p> Some EXAMPLES of scripts that can be used with the &#8216;-M exec&#8217; Directive are given below. Some sample scripts are also included in /usr/share/doc/smartmontools/examplescripts/. </p>
<p> [NEW EXPERIMENTAL SMARTD FEATURE] The executable is run by the script /etc/smartmontools/smartd_warning.sh. This script formats subject and full message based on SMARTD_MESSAGE and other environment variables set by <code>smartd</code>. The environment variables SMARTD_SUBJECT and SMARTD_FULLMESSAGE are set by the script before running the executable. </p>
<dt><code>-f</code></p>
<dd>[ATA only] Check for &#8216;failure&#8217; of any Usage Attributes. If these Attributes are less than or equal to the threshold, it does NOT indicate imminent disk failure. It &quot;indicates an advisory condition where the usage or age of the device has exceeded its intended design life period.&quot; [Please see the <code>smartctl -A</code> command-line option.]</p>
<dt><code>-p</code></p>
<dd>[ATA only] Report anytime that a Prefail Attribute has changed its value since the last check. [Please see the <code>smartctl -A</code> command-line option.]</p>
<dt><code>-u</code></p>
<dd>[ATA only] Report anytime that a Usage Attribute has changed its value since the last check. [Please see the <code>smartctl -A</code> command-line option.]</p>
<dt><code>-t</code></p>
<dd>[ATA only] Equivalent to turning on the two previous flags &#8216;-p&#8217; and &#8216;-u&#8217;. Tracks changes in <i>all</i> device Attributes (both Prefailure and Usage). [Please see the <code>smartctl</code> -A command-line option.]</p>
<dt><code>-i ID</code></p>
<dd>[ATA only] Ignore device Attribute number <code>ID</code> when checking for failure of Usage Attributes. <code>ID</code> must be a decimal integer in the range from 1 to 255. This Directive modifies the behavior of the &#8216;-f&#8217; Directive and has no effect without it. </p>
<p> This is useful, for example, if you have a very old disk and don&#8217;t want to keep getting messages about the hours-on-lifetime Attribute (usually Attribute 9) failing. This Directive may appear multiple times for a single device, if you want to ignore multiple Attributes.</p>
<dt><code>-I ID</code></p>
<dd>[ATA only] Ignore device Attribute <code>ID</code> when tracking changes in the Attribute values. <code>ID</code> must be a decimal integer in the range from 1 to 255. This Directive modifies the behavior of the &#8216;-p&#8217;, &#8216;-u&#8217;, and &#8216;-t&#8217; tracking Directives and has no effect without one of them. </p>
<p> This is useful, for example, if one of the device Attributes is the disk temperature (usually Attribute 194 or 231). It&#8217;s annoying to get reports each time the temperature changes. This Directive may appear multiple times for a single device, if you want to ignore multiple Attributes.</p>
<dt><code>-r ID[!]</code></p>
<dd>[ATA only] When tracking, report the <i>Raw</i> value of Attribute <code>ID</code> along with its (normally reported) <i>Normalized</i> value. <code>ID</code> must be a decimal integer in the range from 1 to 255. This Directive modifies the behavior of the &#8216;-p&#8217;, &#8216;-u&#8217;, and &#8216;-t&#8217; tracking Directives and has no effect without one of them. This Directive may be given multiple times. </p>
<p> A common use of this Directive is to track the device Temperature (often ID=194 or 231). </p>
<p> If the optional flag &#8216;!&#8217; is appended, a change of the Normalized value is considered critical. The report will be logged as LOG_CRIT and a warning email will be sent if &#8216;-m&#8217; is specified.</p>
<dt><code>-R ID[!]</code></p>
<dd>[ATA only] When tracking, report whenever the <i>Raw</i> value of Attribute <code>ID</code> changes. (Normally <code>smartd</code> only tracks/reports changes of the <i>Normalized</i> Attribute values.) <code>ID</code> must be a decimal integer in the range from 1 to 255. This Directive modifies the behavior of the &#8216;-p&#8217;, &#8216;-u&#8217;, and &#8216;-t&#8217; tracking Directives and has no effect without one of them. This Directive may be given multiple times. </p>
<p> If this Directive is given, it automatically implies the &#8216;-r&#8217; Directive for the same Attribute, so that the Raw value of the Attribute is reported. </p>
<p> A common use of this Directive is to track the device Temperature (often ID=194 or 231). It is also useful for understanding how different types of system behavior affects the values of certain Attributes. </p>
<p> If the optional flag &#8216;!&#8217; is appended, a change of the Raw value is considered critical. The report will be logged as LOG_CRIT and a warning email will be sent if &#8216;-m&#8217; is specified. An example is &#8216;-R 5!&#8217; to warn when new sectors are reallocated.</p>
<dt><code>-C ID[+]</code></p>
<dd>[ATA only] Report if the current number of pending sectors is non-zero. Here <code>ID</code> is the id number of the Attribute whose raw value is the Current Pending Sector count. The allowed range of <code>ID</code> is 0 to 255 inclusive. To turn off this reporting, use ID&nbsp;<wbr>=&nbsp;<wbr>0. If the <code>-C ID</code> option is not given, then it defaults to <code>-C 197</code> (since Attribute 197 is generally used to monitor pending sectors). If the name of this Attribute is changed by a &#8216;-v 197,FORMAT,NAME&#8217; directive, the default is changed to <code>-C 0</code>. </p>
<p> If &#8216;+&#8217; is specified, a report is only printed if the number of sectors has increased between two check cycles. Some disks do not reset this attribute when a bad sector is reallocated. See also &#8216;-v 197,increasing&#8217; below. </p>
<p> The warning email counter is reset if the number of pending sectors dropped to 0. This typically happens when all pending sectors have been reallocated or could be read again. </p>
<p> A pending sector is a disk sector (containing 512 bytes of your data) which the device would like to mark as &#8220;bad&quot; and reallocate. Typically this is because your computer tried to read that sector, and the read failed because the data on it has been corrupted and has inconsistent Error Checking and Correction (ECC) codes. This is important to know, because it means that there is some unreadable data on the disk. The problem of figuring out what file this data belongs to is operating system and file system specific. You can typically force the sector to reallocate by writing to it (translation: make the device substitute a spare good sector for the bad one) but at the price of losing the 512 bytes of data stored there.</p>
<dt><code>-U ID[+]</code></p>
<dd>[ATA only] Report if the number of offline uncorrectable sectors is non-zero. Here <code>ID</code> is the id number of the Attribute whose raw value is the Offline Uncorrectable Sector count. The allowed range of <code>ID</code> is 0 to 255 inclusive. To turn off this reporting, use ID&nbsp;<wbr>=&nbsp;<wbr>0. If the <code>-U ID</code> option is not given, then it defaults to <code>-U 198</code> (since Attribute 198 is generally used to monitor offline uncorrectable sectors). If the name of this Attribute is changed by a &#8216;-v 198,FORMAT,NAME&#8217; (except &#8216;-v 198,FORMAT,Offline_Scan_UNC_SectCt&#8217;), directive, the default is changed to <code>-U 0</code>. </p>
<p> If &#8216;+&#8217; is specified, a report is only printed if the number of sectors has increased since the last check cycle. Some disks do not reset this attribute when a bad sector is reallocated. See also &#8216;-v 198,increasing&#8217; below. </p>
<p> The warning email counter is reset if the number of offline uncorrectable sectors dropped to 0. This typically happens when all offline uncorrectable sectors have been reallocated or could be read again. </p>
<p> An offline uncorrectable sector is a disk sector which was not readable during an off-line scan or a self-test. This is important to know, because if you have data stored in this disk sector, and you need to read it, the read will fail. Please see the previous &#8216;-C&#8217; option for more details.</p>
<dt><code>-W DIFF[,INFO[,CRIT]]</code></p>
<dd>Report if the current temperature had changed by at least <code>DIFF</code> degrees since last report, or if new min or max temperature is detected. Report or Warn if the temperature is greater or equal than one of <code>INFO</code> or <code>CRIT</code> degrees Celsius. If the limit <code>CRIT</code> is reached, a message with loglevel <code>&#8216;LOG_CRIT&#8217;</code> will be logged to syslog and a warning email will be send if &#8216;-m&#8217; is specified. If only the limit <code>INFO</code> is reached, a message with loglevel <code>&#8216;LOG_INFO&#8217;</code> will be logged. </p>
<p> The warning email counter is reset if the temperature dropped below <code>INFO</code> or <code>CRIT</code>-5 if <code>INFO</code> is not specified. </p>
<p> If this directive is used in conjunction with state persistence (&#8216;-s&#8217; option), the min and max temperature values are preserved across boot cycles. The minimum temperature value is not updated during the first 30 minutes after startup. </p>
<p> To disable any of the 3 reports, set the corresponding limit to 0. Trailing zero arguments may be omitted. By default, all temperature reports are disabled (&#8216;-W 0&#8217;). </p>
<p> To track temperature changes of at least 2 degrees, use: </p>
<pre><code>-W 2</code></pre>
<p>To log informal messages on temperatures of at least 40 degrees, use: </p>
<pre><code>-W 0,40</code></pre>
<p>For warning messages/mails on temperatures of at least 45 degrees, use: </p>
<pre><code>-W 0,0,45</code></pre>
<p>To combine all of the above reports, use: </p>
<pre><code>-W 2,40,45</code></pre>
<p>For ATA devices, smartd interprets Attribute 194 or 190 as Temperature Celsius by default. This can be changed to Attribute 9 or 220 by the drive database or by the &#8216;-v 9,temp&#8217; or &#8216;-v 220,temp&#8217; directive.</p>
<dt><code>-F TYPE</code></p>
<dd>[ATA only] Modifies the behavior of <code>smartd</code> to compensate for some known and understood device firmware bug. This directive may be used multiple times. The valid arguments are: </p>
<p> <i>none</i> &#8211; Assume that the device firmware obeys the ATA specifications. This is the default, unless the device has presets for &#8216;-F&#8217; in the drive database. Using this directive will over-ride any preset values. </p>
<p> <i>nologdir</i> &#8211; Suppresses read attempts of SMART or GP Log Directory. Support for all standard logs is assumed without an actual check. Some Intel SSDs may freeze if log address 0 is read. </p>
<p> <i>samsung</i> &#8211; In some Samsung disks (example: model SV4012H Firmware Version: RM100-08) some of the two- and four-byte quantities in the SMART data structures are byte-swapped (relative to the ATA specification). Enabling this option tells <code>smartd</code> to evaluate these quantities in byte-reversed order. Some signs that your disk needs this option are (1) no self-test log printed, even though you have run self-tests; (2) very large numbers of ATA errors reported in the ATA error log; (3) strange and impossible values for the ATA error log timestamps. </p>
<p> <i>samsung2</i> &#8211; In some Samsung disks the number of ATA errors reported is byte swapped. Enabling this option tells <code>smartd</code> to evaluate this quantity in byte-reversed order. </p>
<p> <i>samsung3</i> &#8211; Some Samsung disks (at least SP2514N with Firmware VF100-37) report a self-test still in progress with 0% remaining when the test was already completed. If this directive is specified, <code>smartd</code> will not skip the next scheduled self-test (see Directive &#8216;-s&#8217; above) in this case. </p>
<p> <i>xerrorlba</i> &#8211; This only affects <code>smartctl</code>. </p>
<p> [Please see the <code>smartctl -F</code> command-line option.]</p>
<dt><code>-v ID,FORMAT[:BYTEORDER][,NAME]</code></p>
<dd>[ATA only] Sets a vendor-specific raw value print FORMAT, an optional BYTEORDER and an optional NAME for Attribute ID. This directive may be used multiple times. Please see <code>smartctl -v</code> command-line option for further details. </p>
<p> The following arguments affect smartd warning output: </p>
<p> <i>197,increasing</i> &#8211; Raw Attribute number 197 (Current Pending Sector Count) is not reset if uncorrectable sectors are reallocated. This sets &#8216;-C 197+&#8217; if no other &#8216;-C&#8217; directive is specified. </p>
<p> <i>198,increasing</i> &#8211; Raw Attribute number 198 (Offline Uncorrectable Sector Count) is not reset if uncorrectable sector are reallocated. This sets &#8216;-U 198+&#8217; if no other &#8216;-U&#8217; directive is specified.</p>
<dt><code>-P TYPE</code></p>
<dd>[ATA only] Specifies whether <code>smartd</code> should use any preset options that are available for this drive. The valid arguments to this Directive are: </p>
<p> <i>use</i> &#8211; use any presets that are available for this drive. This is the default. </p>
<p> <i>ignore</i> &#8211; do not use any presets for this drive. </p>
<p> <i>show</i> &#8211; show the presets listed for this drive in the database. </p>
<p> <i>showall</i> &#8211; show the presets that are available for all drives and then exit. </p>
<p> [Please see the <code>smartctl -P</code> command-line option.]</p>
<dt><code>-a</code></p>
<dd>Equivalent to turning on all of the following Directives: <code>&#8216;-H&#8217; </code> to check the SMART health status, <code>&#8216;-f&#8217; </code> to report failures of Usage (rather than Prefail) Attributes, <code>&#8216;-t&#8217; </code> to track changes in both Prefailure and Usage Attributes, <code>&#8216;-l error&#8217;</code> to report increases in the number of ATA errors, <code>&#8216;-l selftest&#8217;</code> to report increases in the number of Self-Test Log errors, <code>&#8216;-l selfteststs&#8217;</code> to report changes of Self-Test execution status, <code>&#8216;-C 197&#8217;</code> to report nonzero values of the current pending sector count, and <code>&#8216;-U 198&#8217;</code> to report nonzero values of the offline pending sector count. </p>
<p> Note that -a is the default for ATA devices. If none of these other Directives is given, then -a is assumed.</p>
<dt><code>#</code></p>
<dd>Comment: ignore the remainder of the line.</p>
<dt><code>\</code></p>
<dd>Continuation character: if this is the last non-white or non-comment character on a line, then the following line is a continuation of the current one.</dl>
<p> If you are not sure which Directives to use, I suggest experimenting for a few minutes with <code>smartctl</code> to see what SMART functionality your disk(s) support(s). If you do not like voluminous syslog messages, a good choice of <code>smartd</code> configuration file Directives might be: </p>
<pre><code>-H -l selftest -l error -f.</code></pre>
<p>If you want more frequent information, use: <code>-a.</code> </p>
<dl>
<dt><code>ADDITIONAL DETAILS ABOUT DEVICESCAN</code></p>
<dd>If a non-comment entry in the configuration file is the text string <code>DEVICESCAN</code> in capital letters, then <code>smartd</code> will ignore any remaining lines in the configuration file, and will scan for devices (see also <code><a href="/docs/linux/man/8-smartd/">smartd</a></code>(8) man page). </p>
<p> If <code>DEVICESCAN</code> is not followed by any Directives, then smartd will scan for both ATA and SCSI devices, and will monitor all possible SMART properties of any devices that are found. </p>
<p> <code>DEVICESCAN</code> may optionally be followed by any valid Directives, which will be applied to all devices that are found in the scan. For example </p>
<pre><code>DEVICESCAN -m root [at] example.com</code></pre>
<p>will scan for all devices, and then monitor them. It will send one email warning per device for any problems that are found. </p>
<pre><code>DEVICESCAN -d ata -m root [at] example.com</code></pre>
<p>will do the same, but restricts the scan to ATA devices only. </p>
<pre><code>DEVICESCAN -H -d ata -m root [at] example.com</code></pre>
<p>will do the same, but only monitors the SMART health status of the devices, (rather than the default -a, which monitors all SMART properties). </p>
<p> [NEW EXPERIMENTAL SMARTD FEATURE] Configuration entries for specific devices may precede the <code>DEVICESCAN</code> entry. For example </p>
<pre><code>DEFAULT -m root [at] example.com</code>
<code>/dev/sda -s S/../.././02</code>
<code>/dev/sdc -d ignore</code>
<code>DEVICESCAN -s L/../.././02</code></pre>
<p>will scan for all devices except /dev/sda and /dev/sdc, monitor them, and run a long test between 2-3am every morning. Device /dev/sda will also be monitored, but only a short test will be run. Device /dev/sdc will be ignored. Warning emails will be sent for all monitored devices. </p>
<dt><code>EXAMPLES OF SHELL SCRIPTS FOR &#8216;-M exec&#8217;</code></p>
<dd>These are two examples of shell scripts that can be used with the &#8216;-M exec PATH&#8217; Directive described previously. The paths to these scripts and similar executables is the PATH argument to the &#8216;-M exec PATH&#8217; Directive. </p>
<p> Example 1: This script is for use with &#8216;-m ADDRESS -M exec PATH&#8217;. It appends the output of <code>smartctl -a</code> to the output of the smartd email warning message and sends it to ADDRESS. </p>
<pre><code>#! /bin/bash
# Save the email message (STDIN) to a file:
cat &gt; /root/msg
# Append the output of smartctl -a to the message:
/usr/sbin/smartctl -a -d $SMART_DEVICETYPE $SMARTD_DEVICE &gt;&gt; /root/msg
 
# Now email the message to the user at address ADD:
/bin/mail -s &quot;$SMARTD_SUBJECT&quot; $SMARTD_ADDRESS &lt; /root/msg</code></pre>
<p>Example 2: This script is for use with &#8216;-m &lt;nomailer&gt; -M exec PATH&#8217;. It warns all users about a disk problem, waits 30 seconds, and then powers down the machine. </p>
<pre><code>#! /bin/bash
# Warn all users of a problem
wall 'Problem detected with disk: ' &quot;$SMARTD_DEVICESTRING&quot;
wall 'Warning message from smartd is: ' &quot;$SMARTD_MESSAGE&quot;
wall 'Shutting down machine in 30 seconds... '
 
# Wait half a minute
sleep 30
 
# Power down the machine
/sbin/shutdown -hf now</code></pre>
<p>Some example scripts are distributed with the smartmontools package, in /usr/share/doc/smartmontools/examplescripts/. </p>
<p> Please note that these scripts typically run as root, so any files that they read/write should not be writable by ordinary users or reside in directories like /tmp that are writable by ordinary users and may expose your system to symlink attacks. </p>
<p> As previously described, if the scripts write to STDOUT or STDERR, this is interpreted as indicating that there was an internal error within the script, and a snippet of STDOUT/STDERR is logged to SYSLOG. The remainder is flushed. </p>
