<p>masq &#8211; Shorewall Masquerade/SNAT definition file</p>
<h2>Synopsis</h2>
<dl>
<dt> <code>/etc/shorewall/masq</code></dl>
<h2>Description</h2>
<dd>This file is used to define dynamic NAT (Masquerading) and to define Source NAT (SNAT). While still supported, its use is deprecated in favor of m[blue]<code>shorewall-snat</code>m[]<font SIZE="-2">[1]</font>(5) which was introduced in Shorewall 5.0.14.</p>
<dl>
<dd><font SIZE="+1"> <code>Warning</code> </font><br />
 The entries in this file are order-sensitive. The first entry that matches a particular connection will be the one that is used. </p>
<dl>
<dd><font SIZE="+1"> <code>Warning</code> </font><br />
 If you have more than one ISP link, adding entries to this file will <code>not</code> force connections to go out through a particular link. You must use entries in m[blue]<code>shorewall-rtrules</code>m[]<font SIZE="-2">[2]</font>(5) or PREROUTING entries in m[blue]<code>shorewall-mangle</code>m[]<font SIZE="-2">[3]</font>(5) to do that.  The columns in the file are as follows. <code>INTERFACE:DEST</code> &#8211; {[<code>+</code>]<i>interfacelist</i>[<code>:</code>[<i>digit</i>]][<code>:</code>[<i>dest-address</i>[<code>,</code><i>dest-address</i>]&#8230;[<i>exclusion</i>]]|?COMMENT}</p>
<dl>
<dd>Outgoing <i>interfacelist</i>. This may be a comma-separated list of interface names. This is usually your internet interface. If ADD_SNAT_ALIASES=Yes in m[blue]<code>shorewall.conf</code>m[]<font SIZE="-2">[4]</font>(5), you may add &quot;:&quot; and a <i>digit</i> to indicate that you want the alias added with that name (e.g., eth0:0). This will allow the alias to be displayed with ifconfig. <code>That is the only use for the alias name; it may not appear in any other place in your Shorewall configuration.</code> Each interface must match an entry in m[blue]<code>shorewall-interfaces</code>m[]<font SIZE="-2">[5]</font>(5). Shorewall allows loose matches to wildcard entries in m[blue]<code>shorewall-interfaces</code>m[]<font SIZE="-2">[5]</font>(5). For example, ppp0 in this file will match a m[blue]<code>shorewall-interfaces</code>m[]<font SIZE="-2">[5]</font>(5) entry that defines ppp+. Where m[blue]<code>more that one internet provider share a single interface</code>m[]<font SIZE="-2">[6]</font>, the provider is specified by including the provider name or number in parentheses:</p>
<dl>
<dd>
<pre> eth0(Avvanta)</pre>
</dl>
<p> In that case, you will want to specify the interface&#8217;s address for that provider in the ADDRESS column. The interface may be qualified by adding the character &quot;:&quot; followed by a comma-separated list of destination host or subnet addresses to indicate that you only want to change the source IP address for packets being sent to those particular destinations. Exclusion is allowed (see m[blue]<code>shorewall-exclusion</code>m[]<font SIZE="-2">[7]</font>(5)) as are ipset names preceded by a plus sign &#8216;+&#8217;; If you wish to inhibit the action of ADD_SNAT_ALIASES for this entry then include the &quot;:&quot; but omit the digit:</p>
<dl>
<dd>
<pre> eth0(Avvanta):
 eth2::192.0.2.32/27</pre>
</dl>
<p> Normally Masq/SNAT rules are evaluated after those for one-to-one NAT (defined in m[blue]<code>shorewall-nat</code>m[]<font SIZE="-2">[8]</font>(5)). If you want the rule to be applied before one-to-one NAT rules, prefix the interface name with &quot;+&quot;:</p>
<dl>
<dd>
<pre> +eth0
 +eth0:192.0.2.32/27
 +eth0:2</pre>
</dl>
<p> This feature should only be required if you need to insert rules in this file that preempt entries in m[blue]<code>shorewall-nat</code>m[]<font SIZE="-2">[8]</font>(5). Comments may be attached to Netfilter rules generated from entries in this file through the use of ?COMMENT lines. These lines begin with ?COMMENT; the remainder of the line is treated as a comment which is attached to subsequent rules until another ?COMMENT line is found or until the end of the file is reached. To stop adding comments to rules, use a line containing only ?COMMENT. Beginning with Shorewall 4.6.0, a new syntax is also accepted. With the exception of the leading &#8216;+&#8217;, the interfacelist and qualifiers may appear within the parentheses of <code>INLINE</code>(&#8230;). Example:</p>
<dl>
<dd>
<pre> +INLINE(eth0)</pre>
</dl>
<p> When this is done, you may augment the rule generated by Shorewall with iptables matches of your own. These matches appear after a semicolon (&#8216;;&#8217;) at the end of the line. See example 8 below.</dl>
<p> <code>SOURCE</code> (Formerly called SUBNET &#8211; Optional) &#8211; [<i>interface</i>|<i>address</i>[<code>,</code><i>address</i>][<i>exclusion</i>]]</p>
<dl>
<dd>Set of hosts that you wish to masquerade. You can specify this as an <i>address</i> (net or host) or as an <i>interface</i> (use of an <i>interface</i> is deprecated). If you give the name of an interface, the interface must be up before you start the firewall and the Shorewall rules compiler will warn you of that fact. (Shorewall will use your main routing table to determine the appropriate addresses to masquerade). The preferred way to specify the SOURCE is to supply one or more host or network addresses separated by comma. You may use ipset names preceded by a plus sign (+) to specify a set of hosts.</dl>
<p> <code>ADDRESS</code> (Optional) &#8211; [<code>&#8211;</code>|<code>NONAT</code>|[<i>address-or-address-range</i>][:<i>lowport</i><code>&#8211;</code><i>highport</i>][<code>:random</code>][:persistent]|<code>detect</code>|<code>random</code>]</p>
<dl>
<dd>If you specify an address here, SNAT will be used and this will be the source address. If ADD_SNAT_ALIASES is set to Yes or yes in m[blue]<code>shorewall.conf</code>m[]<font SIZE="-2">[4]</font>(5) then Shorewall will automatically add this address to the INTERFACE named in the first column. You may also specify a range of up to 256 IP addresses if you want the SNAT address to be assigned from that range in a round-robin fashion by connection. The range is specified by <i>first.ip.in.range</i>&#8211;<i>last.ip.in.range</i>. You may follow the port range with<code> :random</code> in which case assignment of ports from the list will be random. <code>random</code> may also be specified by itself in this column in which case random local port assignments are made for the outgoing connections. Example: 206.124.146.177-206.124.146.180 You may follow the port range (or <code>:random</code>) with <code>:persistent</code>. This is only useful when an address range is specified and causes a client to be given the same source/destination IP pair. This feature replaces the SAME modifier which was removed from Shorewall in version 4.4.0. Unlike <code>random</code>, <code>persistent</code> may not be used by itself. You may also use the special value &quot;detect&quot; which causes Shorewall to determine the IP addresses configured on the interface named in the INTERFACES column and substitute them in this column. Finally, you may also specify a comma-separated list of ranges and/or addresses in this column. This column may not contain DNS Names. Normally, Netfilter will attempt to retain the source port number. You may cause netfilter to remap the source port by following an address or range (if any) by &quot;:&quot; and a port range with the format <i>lowport</i>&#8211;<i>highport</i>. If this is done, you must specify &quot;tcp&quot; or &quot;udp&quot; in the PROTO column. Examples:</p>
<dl>
<dd>
<pre> 192.0.2.4:5000-6000
 :4000-5000</pre>
</dl>
<p> If you simply place <code>NONAT</code> in this column, no rewriting of the source IP address or port number will be performed. This is useful if you want particular traffic to be exempt from the entries that follow in the file. If you want to leave this column empty but you need to specify the next column then place a hyphen (&quot;-&quot;) here.</dl>
<p> <code>PROTO</code> (Optional) &#8211; {<code>&#8211;</code>|[!]{<i>protocol-name</i>|<i>protocol-number</i>}[,&#8230;]|+<i>ipset</i>}</p>
<dl>
<dd>If you wish to restrict this entry to a particular protocol then enter the protocol name (from <a href="/docs/linux/man/5-protocols/">protocols</a>(5)) or number here. Beginning with Shorewall 4.5.12, this column can accept a comma-separated list of protocols. Beginning with Shorewall 4.6.0, an <i>ipset</i> name can be specified in this column. This is intended to be used with bitmap:port ipsets.</dl>
<p> <code>PORT</code> (Optional) &#8211; {-|[!]<i>port-name-or-number</i>[,<i>port-name-or-number</i>]&#8230;|+<i>ipset</i>}</p>
<dl>
<dd>If the PROTO column specifies TCP (6), UDP (17), DCCP (33), SCTP (132) or UDPLITE (136) then you may list one or more port numbers (or names from <a href="/docs/linux/man/5-services/">services</a>(5)) or port ranges separated by commas. Port ranges are of the form <i>lowport</i>:<i>highport</i>. Beginning with Shorewall 4.6.0, an <i>ipset</i> name can be specified in this column. This is intended to be used with bitmap:port ipsets.</dl>
<p> <code>IPSEC</code> (Optional) &#8211; [<i>option</i>[<code>,</code><i>option</i>]&#8230;]</p>
<dl>
<dd>If you specify a value other than &quot;-&quot; in this column, you must be running kernel 2.6 and your kernel and iptables must include policy match support. Comma-separated list of options from the following. Only packets that will be encrypted via an SA that matches these options will have their source address changed. <code>reqid=</code><i>number</i></p>
<dl>
<dd>where <i>number</i> is specified using <a href="/docs/linux/man/8-setkey/">setkey</a>(8) using the &#8216;unique:<i>number</i> option for the SPD level.</dl>
<p> <code>spi=</code>&lt;number&gt;</p>
<dl>
<dd>where <i>number</i> is the SPI of the SA used to encrypt/decrypt packets.</dl>
<p> <code>proto=</code><code>ah</code>|<code>esp</code>|<code>ipcomp</code></p>
<dl>
<dd>IPSEC Encapsulation Protocol</dl>
<p> <code>mss=</code><i>number</i></p>
<dl>
<dd>sets the MSS field in TCP packets</dl>
<p> <code>mode=</code><code>transport</code>|<code>tunnel</code></p>
<dl>
<dd>IPSEC mode</dl>
<p> <code>tunnel-src=</code><i>address</i>[/<i>mask</i>]</p>
<dl>
<dd>only available with mode=tunnel</dl>
<p> <code>tunnel-dst=</code><i>address</i>[/<i>mask</i>]</p>
<dl>
<dd>only available with mode=tunnel</dl>
<p> <code>strict</code></p>
<dl>
<dd>Means that packets must match all rules.</dl>
<p> <code>next</code></p>
<dl>
<dd>Separates rules; can only be used with strict</dl>
<p> <code>yes</code></p>
<dl>
<dd>When used by itself, causes all traffic that will be encrypted/encapsulated to match the rule.</dl>
</dl>
<p> <code>MARK</code> &#8211; [<code>!</code>]<i>value</i>[/<i>mask</i>][<code>:C</code>]</p>
<dl>
<dd>Defines a test on the existing packet or connection mark. The rule will match only if the test returns true. If you don&#8217;t want to define a test but need to specify anything in the following columns, place a &quot;-&quot; in this field. !</p>
<dl>
<dd>Inverts the test (not equal)</dl>
<p> <i>value</i></p>
<dl>
<dd>Value of the packet or connection mark.</dl>
<p> <i>mask</i></p>
<dl>
<dd>A mask to be applied to the mark before testing.</dl>
<p> <code>:C</code></p>
<dl>
<dd>Designates a connection mark. If omitted, the packet mark&#8217;s value is tested.</dl>
</dl>
<p> <code>USER</code> (Optional) &#8211; [<code>!</code>][<i>user-name-or-number</i>][<code>:</code><i>group-name-or-number</i>][<code>+</code><i>program-name</i>]</p>
<dl>
<dd>This column was formerly labelled USER/GROUP. Only locally-generated connections will match if this column is non-empty. When this column is non-empty, the rule matches only if the program generating the output is running under the effective <i>user</i> and/or <i>group</i> specified (or is NOT running under that id if &quot;!&quot; is given). Examples: joe</p>
<dl>
<dd>program must be run by joe</dl>
<p> :kids</p>
<dl>
<dd>program must be run by a member of the &#8216;kids&#8217; group</dl>
<p> !:kids</p>
<dl>
<dd>program must not be run by a member of the &#8216;kids&#8217; group</dl>
<p> +upnpd</p>
<dl>
<dd>#program named upnpd</p>
<dl>
<dd><font SIZE="+1"> <code>Important</code> </font><br />
 The ability to specify a program name was removed from Netfilter in kernel version 2.6.14.  <code>SWITCH &#8211; [!]</code><i>switch-name</i><code>[={0|1}]</code></p>
<dl>
<dd>Added in Shorewall 4.5.1 and allows enabling and disabling the rule without requiring <code>shorewall restart</code>. The rule is enabled if the value stored in /proc/net/nf_condition/<i>switch-name</i> is 1. The rule is disabled if that file contains 0 (the default). If &#8216;!&#8217; is supplied, the test is inverted such that the rule is enabled if the file contains 0. Within the <i>switch-name</i>, &#8216;@0&#8217; and &#8216;@{0}&#8217; are replaced by the name of the chain to which the rule is a added. The <i>switch-name</i> (after &#8216;@&#8230;&#8217; expansion) must begin with a letter and be composed of letters, decimal digits, underscores or hyphens. Switch names must be 30 characters or less in length. Switches are normally <code>off</code>. To turn a switch <code>on</code>:</p>
<dl>
<dd><code>echo 1 &gt;<br />
&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>/proc/net/nf_condition/</code><i>switch-name</i></dl>
<p> To turn it <code>off</code> again:</p>
<dl>
<dd><code>echo 0 &gt;<br />
&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>/proc/net/nf_condition/</code><i>switch-name</i></dl>
<p> Switch settings are retained over <code>shorewall restart</code>. Beginning with Shorewall 4.5.10, when the <i>switch-name</i> is followed by <code>=0</code> or <code>=1</code>, then the switch is initialized to off or on respectively by the <code>start</code> command. Other commands do not affect the switch setting.</dl>
<p> <code>ORIGDEST</code> &#8211; [<code>&#8211;</code>|<i>address</i>[,<i>address</i>]&#8230;[<i>exclusion</i>]|<i>exclusion</i>]</p>
<dl>
<dd>(Optional) Added in Shorewall 4.5.6. This column may be included and may contain one or more addresses (host or network) separated by commas. Address ranges are not allowed. When this column is supplied, rules are generated that require that the original destination address matches one of the listed addresses. It is useful for specifying that SNAT should occur only for connections that were acted on by a DNAT when they entered the firewall. This column was formerly labelled ORIGINAL DEST.</dl>
<p> <code>PROBABILITY</code> &#8211; [<i>probability</i>]</p>
<dl>
<dd>Added in Shorewall 5.0.0. When non-empty, requires the Statistics Match capability in your kernel and ip6tables and causes the rule to match randomly but with the given <i>probability</i>. The <i>probability</i> is a number 0 &lt; <i>probability</i> &lt;= 1 and may be expressed at up to 8 decimal points of precision.</dl>
<h2>Examples</h2>
<p>Example 1:</p>
<dl>
<dd>You have a simple masquerading setup where eth0 connects to a DSL or cable modem and eth1 connects to your local network with subnet 192.168.0.0/24. Your entry in the file will be:</p>
<dl>
<dd>
<pre> #INTERFACE SOURCE
 eth0 192.168.0.0/24</pre>
</dl>
</dl>
<p> Example 2:</p>
<dl>
<dd>You add a router to your local network to connect subnet 192.168.1.0/24 which you also want to masquerade. You then add a second entry for eth0 to this file:</p>
<dl>
<dd>
<pre> #INTERFACE SOURCE
 eth0 192.168.1.0/24</pre>
</dl>
</dl>
<p> Example 3:</p>
<dl>
<dd>You have an IPSEC tunnel through ipsec0 and you want to masquerade packets coming from 192.168.1.0/24 but only if these packets are destined for hosts in 10.1.1.0/24:</p>
<dl>
<dd>
<pre> #INTERFACE SOURCE
 ipsec0:10.1.1.0/24 196.168.1.0/24</pre>
</dl>
</dl>
<p> Example 4:</p>
<dl>
<dd>You want all outgoing traffic from 192.168.1.0/24 through eth0 to use source address 206.124.146.176 which is NOT the primary address of eth0. You want 206.124.146.176 to be added to eth0 with name eth0:0.</p>
<dl>
<dd>
<pre> #INTERFACE SOURCE ADDRESS
 eth0:0 192.168.1.0/24 206.124.146.176</pre>
</dl>
</dl>
<p> Example 5:</p>
<dl>
<dd>You want all outgoing SMTP traffic entering the firewall from 172.20.1.0/29 to be sent from eth0 with source IP address 206.124.146.177. You want all other outgoing traffic from 172.20.1.0/29 to be sent from eth0 with source IP address 206.124.146.176.</p>
<dl>
<dd>
<pre> #INTERFACE SOURCE ADDRESS PROTO DPORT
 eth0 172.20.1.0/29 206.124.146.177 tcp smtp
 eth0 172.20.1.0/29 206.124.146.176</pre>
</dl>
<dl>
<dd><font SIZE="+1"> <code>Warning</code> </font><br />
 The order of the above two rules is significant!  Example 6:</p>
<dl>
<dd>Connections leaving on eth0 and destined to any host defined in the ipset <i>myset</i> should have the source IP address changed to 206.124.146.177.</p>
<dl>
<dd>
<pre> #INTERFACE SOURCE ADDRESS
 eth0:+myset[dst] - 206.124.146.177</pre>
</dl>
</dl>
<p> Example 7:</p>
<dl>
<dd>SNAT outgoing connections on eth0 from 192.168.1.0/24 in round-robin fashion between addresses 1.1.1.1, 1.1.1.3, and 1.1.1.9 (Shorewall 4.5.9 and later).</p>
<dl>
<dd>
<pre>/etc/shorewall/tcrules:
 #ACTION SOURCE DEST PROTO DPORT SPORT USER TEST
 1-3:CF 192.168.1.0/24 eth0 ; state=NEW
/etc/shorewall/masq:
 #INTERFACE SOURCE ADDRESS ...
 eth0 192.168.1.0/24 1.1.1.1 ; mark=1:C
 eth0 192.168.1.0/24 1.1.1.3 ; mark=2:C
 eth0 192.168.1.0/24 1.1.1.9 ; mark=3:C</pre>
</dl>
</dl>
<p> Example 8:</p>
<dl>
<dd>Your eth1 has two public IP addresses: 70.90.191.121 and 70.90.191.123. You want to use the iptables statistics match to masquerade outgoing connections evenly between these two addresses.</p>
<dl>
<dd>
<pre>/etc/shorewall/masq:
 #INTERFACE SOURCE ADDRESS 
 INLINE(eth1) 0.0.0.0/0 70.90.191.121 ; -m statistic --mode random --probability 0.50
 eth1 0.0.0.0/0 70.90.191.123 </pre>
</dl>
<p> If INLINE_MATCHES=Yes in m[blue]<code><a href="/docs/linux/man/5-shorewall-conf/">shorewall.conf</a>(5)</code>m[]<font SIZE="-2">[4]</font>, then these rules may be specified as follows:</p>
<dl>
<dd>
<pre>/etc/shorewall/masq:
 #INTERFACE SOURCE ADDRESS 
 eth1 0.0.0.0/0 70.90.191.121 ; -m statistic --mode random --probability 0.50
 eth1 0.0.0.0/0 70.90.191.123 </pre>
</dl>
</dl>
