<p>shorewall.conf &#8211; Shorewall global configuration file</p>
<h2>Synopsis</h2>
<dl>
<dt> <code>/etc/shorewall/shorewall.conf</code></dl>
<h2>Description</h2>
<dd>This file sets options that apply to Shorewall as a whole. </p>
<p> The file consists of Shell comments (lines beginning with &#8216;#&#8217;), blank lines and assignment statements (<i>variable</i>=<i>value</i>). If the <i>value</i> contains shell meta characters or white-space, then it must be enclosed in quotes. Example: MACLIST_LOG_LEVEL=&quot;NFLOG(1,0,1)&quot;.</p>
<h2>Options</h2>
<p>Many options have as their value a <i>log-level</i>. Log levels are a method of describing to syslog (8) the importance of a message and a number of parameters in this file have log levels as their value. </p>
<p> These levels are defined by syslog and are used to determine the destination of the messages through entries in /etc/syslog.conf (5). The syslog documentation refers to these as &quot;priorities&quot;; Netfilter calls them &quot;levels&quot; and Shorewall also uses that term. </p>
<p> Valid levels are: </p>
<dl>
<dd>
<pre> 7 debug
 6 info
 5 notice
 4 warning
 3 err
 2 crit
 1 alert
 0 emerg</pre>
</dl>
<p> For most Shorewall logging, a level of 6 (info) is appropriate. Shorewall log messages are generated by NetFilter and are logged using facility &#8216;kern&#8217; and the level that you specify. If you are unsure of the level to choose, 6 (info) is a safe bet. You may specify levels by name or by number. </p>
<p> If you have built your kernel with ULOG and/or NFLOG target support, you may also specify a log level of ULOG and/or NFLOG (must be all caps). Rather than log its messages to syslogd, Shorewall will direct netfilter to log the messages via the ULOG or NFLOG target which will send them to a process called &#8216;ulogd&#8217;. ulogd is available with most Linux distributions (although it probably isn&#8217;t installed by default). Ulogd is also available from m[blue]<code><a rel="nofollow" href="http://www.netfilter.org/projects/ulogd/index.html">http://www.netfilter.org/projects/ulogd/index.html</a></code>m[] and can be configured to log all Shorewall messages to their own log file. </p>
<dl>
<dd><font SIZE="+1"> <code>Note</code> </font> </p>
<p> If you want to specify parameters to ULOG or NFLOG (e.g., NFLOG(1,0,1)), then you must quote the setting. </p>
<p> Example: </p>
<dl>
<dd>
<pre>MACLIST_LOG_LEVEL=&quot;NFLOG(1,0,1)&quot;</pre>
</dl>
</dl>
<p> Beginning with Shorewall 5.0.0, the log level may be followed by a colon (&quot;:&quot;) and a log tag. The log tag normally follows the packet disposition in Shorewall-generated Netfilter log messages, separated from the disposition by a colon (e.g, &quot;DROP:mytag&quot;). See LOGTAGONLY below for additional information. </p>
<p> Beginning with Shorewall 4.4.22, LOGMARK is also a valid level which logs the packet&#8217;s mark value along with the other usual information. The syntax is:</p>
<dl>
<dd><code>LOGMARK[</code><i>(priority)</i><code>]</code></dl>
<p> where <i>priority</i> is one of the levels listed in the list above. If omitted, the default is info (6). </p>
<p> The following options may be set in shorewall.conf. </p>
<p> <code>ACCEPT_DEFAULT=</code>{<i>action</i>[(<i>parameters</i>)][:<i>level</i>]|<code>none</code>}</p>
<dl>
<dd></dl>
<p> <code>DROP_DEFAULT=</code>{<i>action</i>[(<i>parameters</i>)][:<i>level</i>]|<code>none</code>}</p>
<dl>
<dd></dl>
<p> <code>NFQUEUE_DEFAULT=</code>{<i>action</i>[(<i>parameters</i>)][:<i>level</i>]|<code>none</code>}</p>
<dl>
<dd></dl>
<p> <code>QUEUE_DEFAULT=</code>{<i>action</i>[(<i>parameters</i>)][:<i>level</i>]|<code>none</code>}</p>
<dl>
<dd></dl>
<p> <code>REJECT_DEFAULT=</code>{<i>action</i>[(<i>parameters</i>)][:<i>level</i>]|<code>none</code>}</p>
<dl>
<dd>In earlier Shorewall versions, a &quot;default action&quot; for DROP and REJECT policies was specified in the file /usr/share/shorewall/actions.std. </p>
<p> In Shorewall 4.4.0, the DROP_DEFAULT, REJECT_DEFAULT, ACCEPT_DEFAULT, QUEUE_DEFAULT and NFQUEUE_DEFAULT options were added. </p>
<p> DROP_DEFAULT describes the rules to be applied before a connection request is dropped by a DROP policy; REJECT_DEFAULT describes the rules to be applied if a connection request is rejected by a REJECT policy. The other three are similar for ACCEPT, QUEUE and NFQUEUE policies. </p>
<p> The value applied to these may be: </p>
<p> The default values are:</p>
<dl>
<dd>DROP_DEFAULT=&quot;Drop&quot;</dl>
<dl>
<dd>REJECT_DEFAULT=&quot;Reject&quot;</dl>
<dl>
<dd>ACCEPT_DEFAULT=&quot;none&quot;</dl>
<dl>
<dd>QUEUE_DEFAULT=&quot;none&quot;</dl>
<dl>
<dd>NFQUEUE_DEFAULT=&quot;None&quot;</dl>
<p> If you set the value of either option to &quot;None&quot; then no default action will be used and the default action or macro must be specified in m[blue]<code>shorewall-policy</code>m[]<font SIZE="-2">[1]</font>(5). </p>
<p> You can pass <i>parameters</i> to the specified action (e.g., <i>myaction(audit,DROP)</i>). </p>
<p> Beginning with Shorewall 4.5.10, the action name can be followed optionally by a colon and a log <i>level</i>. The level will be applied to each rule in the action or body that does not already have a log level.</dl>
<p> <code>ACCOUNTING=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>Added in Shorewall 4.4.7. If set to Yes, Shorewall accounting is enabled (see m[blue]<code>shorewall-accounting</code>m[]<font SIZE="-2">[2]</font>(5)). If not specified or set to the empty value, ACCOUNTING=Yes is assumed.</dl>
<p> <code>ACCOUNTING_TABLE=</code>[<code>filter</code>|<code>mangle</code>]</p>
<dl>
<dd>Added in Shorewall 4.4.20. This setting determines which Netfilter table the accounting rules are added in. By default, ACCOUNTING_TABLE=filter is assumed. See also m[blue]<code>shorewall-accounting</code>m[]<font SIZE="-2">[2]</font>(5).</dl>
<p> <code>ADD_IP_ALIASES=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>This parameter determines whether Shorewall automatically adds the external address(es) in m[blue]<code>shorewall-nat</code>m[]<font SIZE="-2">[3]</font>(5). If the variable is set to <code>Yes</code> or <code>yes</code> then Shorewall automatically adds these aliases. If it is set to <code>No</code> or <code>no</code>, you must add these aliases yourself using your distribution&#8217;s network configuration tools. </p>
<p> If this variable is not set or is given an empty value (ADD_IP_ALIASES=&quot;&quot;) then ADD_IP_ALIASES=Yes is assumed. </p>
<dl>
<dd><font SIZE="+1"> <code>Warning</code> </font><br />
 Addresses added by ADD_IP_ALIASES=Yes are deleted and re-added during <code>shorewall reload</code> and <code>shorewall restart</code>. As a consequence, connections using those addresses may be severed. </p>
</dl>
</dl>
<p> <code>ADD_SNAT_ALIASES=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>This parameter determines whether Shorewall automatically adds the SNAT ADDRESS in m[blue]<code>shorewall-masq</code>m[]<font SIZE="-2">[4]</font>(5). If the variable is set to <code>Yes</code> or <code>yes</code> then Shorewall automatically adds these addresses. If it is set to <code>No</code> or <code>no</code>, you must add these addresses yourself using your distribution&#8217;s network configuration tools. </p>
<p> If this variable is not set or is given an empty value (ADD_SNAT_ALIASES=&quot;&quot;) then ADD_SNAT_ALIASES=No is assumed. </p>
<dl>
<dd><font SIZE="+1"> <code>Warning</code> </font><br />
 Addresses added by ADD_SNAT_ALIASES=Yes are deleted and re-added during <code>shorewall reload</code> and <code>shorewall restart</code>. As a consequence, connections using those addresses may be severed. </p>
</dl>
</dl>
<p> <code>ADMINISABSENTMINDED=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>The value of this variable affects Shorewall&#8217;s stopped state. The behavior differs depending on whether m[blue]<code>shorewall-routestopped</code>m[]<font SIZE="-2">[5]</font>(5) or m[blue]<code>shorewall-stoppedrules</code>m[]<font SIZE="-2">[6]</font>(5) is used: </p>
<p> routestopped</p>
<dl>
<dd>When ADMINISABSENTMINDED=No, only traffic to/from those addresses listed in routestopped is accepted when Shorewall is stopped. When ADMINISABSENTMINDED=Yes, in addition to traffic to/from addresses in routestopped, connections that were active when Shorewall stopped continue to work and all new connections from the firewall system itself are allowed. </p>
<p> Note that the routestopped file is not supported in Shorewall 5.0 and later versions.</dl>
<p> stoppedrules</p>
<dl>
<dd>All existing connections continue to work. To sever all existing connections when the firewall is stopped, install the conntrack utility and place the command <code>conntrack -F</code> in the stopped user exit (/etc/shorewall/stopped). </p>
<p> If ADMINISABSENTMINDED=No, only new connections matching entries in stoppedrules are accepted when Shorewall is stopped. Response packets and related connections are automatically accepted. </p>
<p> If ADMINISABSENTMINDED=Yes, in addition to connections matching entries in stoppedrules, all new connections from the firewall system itself are allowed when the firewall is stopped. Response packets and related connections are automatically accepted.</dl>
<p> If this variable is not set or is given the empty value then ADMINISABSENTMINDED=No is assumed.</dl>
<p> <code>ARPTABLES=</code>[<i>pathname</i>]</p>
<dl>
<dd>Added in Shorewall 4.5.12. This parameter names the arptables executable to be used by Shorewall. If not specified or if specified as a null value, then the arptables executable located using the PATH option is used. </p>
<p> Regardless of how the arptables utility is located (specified via arptables= or located via PATH), Shorewall uses the arptables-restore and arptables-save utilities from that same directory.</dl>
<p> <code>AUTOCOMMENT=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>Formerly named AUTO_COMMENT. If set, if there is not a current comment when a macro is invoked, the behavior is as if the first line of the macro file was &quot;COMMENT &lt;macro name&gt;&quot;. The AUTO_COMMENT option has a default value of &#8216;Yes&#8217;.</dl>
<p> <code>AUTOHELPERS=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>Added in Shorewall 4.5.7. When set to <code>Yes</code> (the default), the generated ruleset will automatically associate helpers with applications that require them (FTP, IRC, etc.). When configuring your firewall on systems running kernel 3.5 or later, it is recommended that you: </p>
<dl>
<dd>1. Set AUTOHELPERS=No.</dl>
<dl>
<dd>2. Modify the HELPERS setting (see below) to list the helpers that you need.</dl>
<dl>
<dd>3. Either: </p>
<dl>
<dd>1. Modify m[blue]<code>shorewall-conntrack</code>m[]<font SIZE="-2">[7]</font> (5) to only apply helpers where they are required; or</dl>
<dl>
<dd>2. Specify the appropriate helper in the HELPER column in m[blue]<code>shorewall-rules</code>m[]<font SIZE="-2">[8]</font> (5). </p>
<dl>
<dd><font SIZE="+1"> <code>Note</code> </font><br />
 The macros for those applications requiring a helper automatically specify the appropriate HELPER where required. </p>
</dl>
</dl>
</dl>
</dl>
<p> <code>AUTOMAKE=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>If set, the behavior of the <code>start</code>, <code>reload</code> and <code>restart</code> commands are changed; if no files in CONFIG_PATH (see below) have been changed since the last successful <code>start, reload</code> or <code>restart</code> command, then the compilation step is skipped and the compiled script that executed the last <code>start</code>, <code>reload</code> or <code>restart</code> command is used. The default is AUTOMAKE=No. </p>
<p> The setting of the AUTOMAKE option is ignored if the <code>start</code>, <code>reload</code> or <code>restart</code> command includes a directory name (e.g.,<code> shorewall restart /etc/shorewall.new</code>).</dl>
<p> <code>BASIC_FILTERS=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>Added in Shorewall-4.6.0. When set to <code>Yes</code>, causes entries in m[blue]<code><a href="/docs/linux/man/5-shorewall-tcfilters/">shorewall-tcfilters</a>(5)</code>m[]<font SIZE="-2">[9]</font> to generate a basic filter rather than a u32 filter. This setting requires the Basic Ematch capability in your kernel and iptables. </p>
<dl>
<dd><font SIZE="+1"> <code>Note</code> </font><br />
 One of the advantages of basic filters is that ipset matches are supported in newer iproute2 and kernel versions. Because Shorewall cannot reliably detect this capability, use of basic filters is controlled by this option. </p>
</dl>
<p> The default value is <code>No</code> which causes u32 filters to be generated.</dl>
<p> <code>BLACKLIST=</code>[{<code>ALL</code>|<i>state</i><code>[,&#8230;]</code>}]</p>
<dl>
<dd>where state is one of NEW, ESTABLISHED, RELATED, INVALID,or UNTRACKED. </p>
<p> Added in Shorewall 4.5.13 to replace the BLACKLISTNEWONLY option. Specifies the connection tracking states that are to be subject to blacklist screening. If BLACKLIST is not specified then the states subject to blacklisting are NEW,ESTABLISHED,INVALID,UNTRACKED. </p>
<p> ALL sends all packets through the blacklist chains. </p>
<p> Note: The ESTABLISHED state may not be specified if FASTACCEPT=Yes is specified.</dl>
<p> <code>BLACKLIST_DISPOSITION=</code>[<code>DROP</code>|A_DROP|<code>REJECT|A_REJECT</code>]</p>
<dl>
<dd>This parameter determines the disposition of packets from blacklisted hosts. It may have the value DROP if the packets are to be dropped or REJECT if the packets are to be replied with an ICMP port unreachable reply or a TCP RST (tcp only). If you do not assign a value or if you assign an empty value then DROP is assumed. </p>
<p> A_DROP and A_REJECT are audited versions of DROP and REJECT respectively and were added in Shorewall 4.4.20. They require AUDIT_TARGET in the kernel and iptables. </p>
<p> The BLACKLIST_DISPOSITION setting has no effect on entries in the BLACKLIST section of m[blue]<code>shorewall-rules</code>m[]<font SIZE="-2">[8]</font> (5). It determines the disposition of packets sent to the <code>blacklog</code> target of m[blue]<code>shorewall-blrules</code>m[]<font SIZE="-2">[10]</font>(5).</dl>
<p> <code>BLACKLIST_LOG_LEVEL=</code>[<i>log-level</i>[:<i>log-tag</i>]]</p>
<dl>
<dd>Formerly named BLACKLIST_LOGLEVEL. This parameter determines if packets from blacklisted hosts are logged and it determines the syslog level that they are to be logged at. Its value is a syslog level (Example: BLACKLIST_LOG_LEVEL=debug). If you do not assign a value or if you assign an empty value then packets from blacklisted hosts are not logged. The setting determines the log level of packets sent to the <code>blacklog</code> target of m[blue]<code>shorewall-blrules</code>m[]<font SIZE="-2">[10]</font>(5).</dl>
<p> <code>CHAIN_SCRIPTS=</code>{<code>Yes</code>|<code>No</code>}</p>
<dl>
<dd>Added in Shorewall 4.5.16. Prior to the availability of BEGIN PERL&#8230;.END PERL in configuration files, the only way to execute a chain-specific script was to create a script file with the same name as the chain and place it in a directory on the CONFIG_PATH. That facility has the drawback that the compiler will attempt to run a non-script file just because it has the same name as a chain. To disable this facility, set CHAIN_SCRIPTS=No. If not specified or specified as the empty value, CHAIN_SCRIPTS=Yes is assumed.</dl>
<p> <code>CLAMPMSS=[</code><code>Yes</code>|<code>No</code>|<i>value</i>]</p>
<dl>
<dd>This parameter enables the TCP Clamp MSS to PMTU feature of Netfilter and is usually required when your internet connection is through PPPoE or PPTP. If set to <code>Yes</code> or <code>yes</code>, the feature is enabled. If left blank or set to <code>No</code> or <code>no</code>, the feature is not enabled. </p>
<p> <code>Important</code>: This option requires CONFIG_IP_NF_TARGET_TCPMSS in your kernel. </p>
<p> You may also set CLAMPMSS to a numeric <i>value</i> (e.g., CLAMPMSS=1400). This will set the MSS field in TCP SYN packets going through the firewall to the <i>value</i> that you specify.</dl>
<p> <code>CLEAR_TC=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>If this option is set to <code>No</code> then Shorewall won&#8217;t clear the current traffic control rules during [<code>re</code>]<code>start</code> or <code>reload</code>. This setting is intended for use by people who prefer to configure traffic shaping when the network interfaces come up rather than when the firewall is started. If that is what you want to do, set TC_ENABLED=Yes and CLEAR_TC=No and do not supply an /etc/shorewall/tcstart file. That way, your traffic shaping rules can still use the &#8220;fwmark&#8221; classifier based on packet marking defined in m[blue]<code>shorewall-tcrules</code>m[]<font SIZE="-2">[11]</font>(5). If not specified, CLEAR_TC=Yes is assumed.</dl>
<p> <code>COMPLETE=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>Added in Shorewall 4.4.12. When you set this option to Yes, you are asserting that the configuration is complete so that your set of zones encompasses any hosts that can send or receive traffic to/from/through the firewall. This causes Shorewall to omit the rules that catch packets in which the source or destination IP address is outside of any of your zones. Default is No. It is recommended that this option only be set to Yes if: </p>
<dl>
<dd>&bull; You have defined an interface whose effective physical setting is &#8216;+&#8217;.</dl>
<dl>
<dd>&bull; That interface is assigned to a zone.</dl>
<dl>
<dd>&bull; You have no CONTINUE policies or rules.</dl>
</dl>
<p> <code>CONFIG_PATH</code>=[<i>directory</i>[:<i>directory</i>]&#8230;]</p>
<dl>
<dd>Specifies where configuration files other than shorewall.conf may be found. CONFIG_PATH is specifies as a list of directory names separated by colons (&quot;:&quot;). When looking for a configuration file: </p>
<dl>
<dd>&bull; If the command is &quot;try&quot; or a &quot;&lt;configuration directory&gt;&quot; was specified in the command (e.g., <code>shorewall check ./gateway</code>) then the directory given in the command is searched first.</dl>
<dl>
<dd>&bull; Next, each directory in the CONFIG_PATH setting is searched in sequence.</dl>
<p> If CONFIG_PATH is not given or if it is set to the empty value then the contents of /usr/share/shorewall/configpath are used. As released from shorewall.net, that file sets the CONFIG_PATH to /etc/shorewall:/usr/share/shorewall but your particular distribution may set it differently. See the output of shorewall show config for the default on your system.</dl>
<p> <code>DEFER_DNS_RESOLUTION=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>Added in Shorewall 4.5.12. When set to &#8216;Yes&#8217; (the default), DNS names are validated in the compiler and then passed on to the generated script where they are resolved by iptables-restore. This is an advantage if you use AUTOMAKE=Yes and the IP address associated with the DNS name is subject to change. When DEFER_DNS_RESOLUTION=No, DNS names are converted into IP addresses by the compiler. This has the advantage that when AUTOMAKE=Yes, the <code>start</code>, <code>reload</code> and <code>restart</code> commands will succeed even if no DNS server is reachable (assuming that the configuration hasn&#8217;t changed since the compiled script was last generated).</dl>
<p> <code>DELETE_THEN_ADD=</code>{<code>Yes</code>|<code>No</code>}</p>
<dl>
<dd>If set to Yes (the default value), entries in the /etc/shorewall/rtrules files cause an &#8216;ip rule del&#8217; command to be generated in addition to an &#8216;ip rule add&#8217; command. Setting this option to No, causes the &#8216;ip rule del&#8217; command to be omitted.</dl>
<p> <code>DETECT_DNAT_IPADDRS=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>If set to <code>Yes</code> or <code>yes</code>, Shorewall will detect the first IP address of the interface to the source zone and will include this address in DNAT rules as the original destination IP address. If set to <code>No</code> or <code>no</code>, Shorewall will not detect this address and any destination IP address will match the DNAT rule. If not specified or empty, &#8220;DETECT_DNAT_IPADDRS=Yes&#8221; is assumed.</dl>
<p> <code>DISABLE_IPV6=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>If set to <code>Yes</code> or <code>yes</code>, IPv6 traffic to, from and through the firewall system is disabled. If set to <code>No</code> or <code>no</code>, Shorewall will take no action with respect to allowing or disallowing IPv6 traffic. If not specified or empty, &#8220;DISABLE_IPV6=No&#8221; is assumed. </p>
<p> It is important to note that changing DISABLE_IPV6=Yes to DISABLE_IPV6=No does <i>not</i> enable IPV6. The recommended approach for enabling IPv6 on your system is: </p>
<dl>
<dd>&bull; Install, configure and start m[blue]<code>Shorewall6</code>m[]<font SIZE="-2">[12]</font>.</dl>
<dl>
<dd>&bull; Change DISABLE_IPV6=Yes to DISABLE_IPV6=No</dl>
<dl>
<dd>&bull; Reload Shorewall</dl>
</dl>
<p> <code>DOCKER=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>Added in Shorewall 5.0.6. When set to <code>Yes</code>, the generated script will save Docker-generated rules before and restore them after executing the <code>start</code>, <code>stop</code>, <code>reload</code> and <code>restart</code> commands. If set to <code>No</code> (the default), the generated script will delete any Docker-generated rules when executing those commands. Seem[blue]<code><a rel="nofollow" href="http://www.shorewall.net/Docker.html">http://www.shorewall.net/Docker.html</a></code>m[]<font SIZE="-2">[13]</font> for additional information.</dl>
<p> <code>DONT_LOAD=</code>[<i>module</i>[,<i>module</i>]&#8230;]</p>
<dl>
<dd>Causes Shorewall to not load the listed kernel modules.</dl>
<p> <code>DYNAMIC_BLACKLIST=</code>{<code>Yes</code>|<code>No</code>||<code>ipset</code>[<code>-only</code>][<i>,option</i>[,&#8230;]][:[<i>setname</i>][:<i>log_level</i>|:l<i>og_tag</i>]]]}</p>
<dl>
<dd>Added in Shorewall 4.4.7. When set to <code>No</code> or <code>no</code>, chain-based dynamic blacklisting using <code>shorewall drop</code>, <code>shorewall reject</code>, <code>shorewall logdrop</code> and <code>shorewall logreject</code> is disabled. Default is <code>Yes</code>. Beginning with Shorewall 5.0.8, ipset-based dynamic blacklisting using the <code>shorewall blacklist</code> command is also supported. The name of the set (<i>setname</i>) and the level (<i>log_level</i>), if any, at which blacklisted traffic is to be logged may also be specified. The default set name is SW_DBL4 and the default log level is <code>none</code> (no logging). If <code>ipset-only</code> is given, then chain-based dynamic blacklisting is disabled just as if DYNAMIC_BLACKLISTING=No had been specified. </p>
<p> Possible <i>option</i>s are: </p>
<p> src-dst</p>
<dl>
<dd>Normally, only packets whose source address matches an entry in the ipset are dropped. If <code>src-dst</code> is included, then packets whose destination address matches an entry in the ipset are also dropped.</dl>
<p> <code>disconnect</code></p>
<dl>
<dd>The <code>disconnect</code> option was added in Shorewall 5.0.13 and requires that the conntrack utility be installed on the firewall system. When an address is blacklisted using the <code>blacklist</code> command, all connections originating from that address are disconnected. if the <code>src-dst</code> option was also specified, then all connections to that address are also disconnected.</dl>
<p> <code>timeout</code>=<i>seconds</i></p>
<dl>
<dd>Added in Shorewall 5.0.13. Normally, Shorewall creates the dynamic blacklisting ipset with timeout 0 which means that entries are permanent. If you want entries in the set that are not accessed for a period of time to be deleted from the set, you may specify that period using this option. Note that the <code>blacklist</code> command can override the ipset&#8217;s timeout setting. </p>
<dl>
<dd><font SIZE="+1"> <code>Important</code> </font><br />
 Once the dynamic blacklisting ipset has been created, changing this option setting requires a complete restart of the firewall; <code>shorewall restart</code> if RESTART=restart, otherwise <code>shorewall stop &amp;&amp; shorewall start</code> </p>
</dl>
</dl>

<p> <code>OPTIMIZE=</code>[<i>value</i>]</p>
<dl>
<dd>The specified <i>value</i> enables certain optimizations. Each optimization category is associated with a power of two. To enable multiple optimization categories, simply add their corresponding numbers together. </p>
<p> Beginning with Shorewall 4.5.20, you may specify OPTIMIZE=All to enable all optimization categories, and you may also specify OPTIMIZE=None to disable optimization. </p>
<dl>
<dd>&bull; Optimization category 1 &#8211; Traditionally, Shorewall has created rules for m[blue]<code>the complete matrix of host groups defined by the zones, interfaces and hosts files</code>m[]<font SIZE="-2">[26]</font>. Any traffic that didn&#8217;t correspond to an element of that matrix was rejected in one of the built-in chains. When the matrix is sparse, this results in lots of largely useless rules. </p>
<p> These extra rules can be eliminated by setting the 1 bit in OPTIMIZE. </p>
<p> The 1 bit setting also controls the suppression of redundant wildcard rules (those specifying &quot;all&quot; in the SOURCE or DEST column). A wildcard rule is considered to be redundant when it has the same ACTION and Log Level as the applicable policy. </p>
<dl>
<dd><font SIZE="+1"> <code>Note</code> </font><br />
 Optimization level 1 is ignored when optimization level 4 is also selected, since level 4 performs similar optimizations in a more robust way. </p>
</dl>
</dl>
<dl>
<dd>&bull; Optimization category 2 &#8211; Added in Shorewall 4.4.7. When set, suppresses superfluous ACCEPT rules in a policy chain that implements an ACCEPT policy. Any ACCEPT rules that immediately precede the final blanket ACCEPT rule in the chain are now omitted.</dl>
<dl>
<dd>&bull; Optimization category 4 &#8211; Added in Shorewall 4.4.7. When set, causes short chains (those with less than 2 rules) to be optimized away. The following chains are excluded from optimization: </p>
<dl>
<dd>&bull; accounting chains (unless OPTIMIZE_ACCOUNTING=Yes)</dl>
<dl>
<dd>&bull; action chains (user-defined)</dl>
<dl>
<dd>&bull; &#8216;blacklst&#8217; chain</dl>
<dl>
<dd>&bull; dynamic</dl>
<dl>
<dd>&bull; forwardUPnP</dl>
<dl>
<dd>&bull; UPnP (nat table)</dl>
<p> Additionally: </p>
<dl>
<dd>&bull; If a built-in chain has a single rule that branches to a second chain, then the rules from the second chain are moved to the built-in chain and the target chain is omitted.</dl>
<dl>
<dd>&bull; Chains with no references are deleted.</dl>
<dl>
<dd>&bull; Accounting chains are subject to optimization if the OPTIMIZE_ACCOUNTING option is set to &#8216;Yes&#8217;.</dl>
<dl>
<dd>&bull; If a chain ends with an unconditional branch to a second chain (other than to &#8216;reject&#8217;), then the branch is deleted from the first chain and the rules from the second chain are appended to it.</dl>
<p> An additional optimization was added in Shorewall 4.5.4. If the last rule in a chain is an unqualified jump to a simple target, then all immediately preceding rules with the same simple target are omitted. </p>
<p> For example, consider this chain: </p>
<dl>
<dd>
<pre> -A fw-net -p udp --dport 67:68 -j ACCEPT
 -A fw-net -p udp --sport 1194 -j ACCEPT
 -A fw-net -p 41 -j ACCEPT
 -A fw-net -j ACCEPT</pre>
</dl>
<p> Since all of the rules are jumps to the simple target ACCEPT, this chain is totally optimized away and jumps to the chain are replace with jumps to ACCEPT.</dl>
<dl>
<dd>&bull; Optimization category 8 &#8211; Added in Shorewall 4.4.9. When set, causes chains with identical rules to be collapsed into a single chain.</dl>
<dl>
<dd>&bull; Optimization category 16 &#8211; Added in Shorewall 4.4.26. When set, causes sequences of compatible rules to be combined into a single rule. Rules are considered compatible if they differ only in their destination ports and comments. </p>
<p> A sequence of compatible rules is often generated when macros are invoked in sequence. </p>
<p> The ability to combine adjacent rules is limited by two factors: </p>
<dl>
<dd>&bull; Destination port lists may only be combined up to a maximum of 15 ports, where a port-pair counts as two ports.</dl>
<dl>
<dd>&bull; Rules may only be combined until the length of their concatenated comment reaches 255 characters.</dl>
<p> When either of these limits would be exceeded, the current combined rule is emitted and the compiler attempts to combine rules beginning with the one that would have exceeded the limit. Adjacent combined comments are separated by &#8216;, &#8216;. Empty comments at the front of a group of combined comments are replaced by &#8216;Others and&#8217;. Empty comments at the end of a group of combined comments are replaced by &#8216;and others&#8217;. </p>
<p> Beginning in Shorewall 4.5.10, this option also suppresses duplicate adjacent rules and duplicate non-adjacent rules that don&#8217;t include <code>mark</code>, <code>connmark</code>, <code>dscp</code>, <code>ecn</code>, <code>set</code>, <code>tos</code> or <code>u32</code> matches. </p>
<p> Example 1:</p>
<dl>
<dd>Rules with comments &quot;FOO&quot;, &lt;empty&gt; and &quot;BAR&quot; would result in the combined comment &quot;FOO and others, BAR&quot;.</dl>
<p> Example 2:</p>
<dl>
<dd>Rules with comments &lt;empty&gt;, &quot;FOO&quot; and &quot;BAR&quot; would result in the combined comment &quot;Others and FOO, BAR&quot;. Note: Optimize level 16 requires &quot;Extended Multi-port Match&quot; in your iptables and kernel.</dl>
</dl>
<p> The default value is zero which disables all optimizations.</dl>

INLINE - - 58 ;; -j REJECT --reject-with icmp6-addr-unreachable

The default is <code>info</code>. If you don&#8217;t wish for these packets to be logged, use SFILTER_LOG_LEVEL=none.</dl>
<p> <code>SHOREWALL_SHELL=</code>[<i>pathname</i>]</p>
<dl>
<dd>This option is used to specify the shell program to be used to interpret the compiled script. If not specified or specified as a null value, /bin/sh is assumed. Using a light-weight shell such as ash or dash can significantly improve performance.</dl>
<p> <code>SMURF_DISPOSITION=</code>[<code>DROP</code>|A_DROP]</p>
<dl>
<dd>Added in Shorewall 4.4.20. The default setting is DROP which causes smurf packets (see the nosmurfs option in m[blue]<code>shorewall-interfaces</code>m[]<font SIZE="-2">[21]</font>(5)) to be dropped. A_DROP causes the packets to be audited prior to being dropped and requires AUDIT_TARGET support in the kernel and iptables.</dl>
<p> <code>SMURF_LOG_LEVEL=</code>[<i>log-level</i>[:<i>log-tag</i>]]</p>
<dl>
<dd>Specifies the logging level for smurf packets (see the nosmurfs option in m[blue]<code>shorewall-interfaces</code>m[]<font SIZE="-2">[21]</font>(5)). If set to the empty value ( SMURF_LOG_LEVEL=&quot;&quot; ) then smurfs are not logged.</dl>
<p> <code>STARTUP_ENABLED=</code>{<code>Yes</code>|<code>No</code>}</p>
<dl>
<dd>Determines if Shorewall is allowed to start. As released from shorewall.net, this option is set to <code>No</code>. When set to <code>Yes</code> or <code>yes</code>, Shorewall may be started. Used as a guard against Shorewall being accidentally started before it has been configured.</dl>
<p> <code>STARTUP_LOG=</code>[<i>pathname</i>]</p>
<dl>
<dd>If specified, determines where Shorewall will log the details of each <code>start</code>, <code>reload</code>, <code>restart</code>, <code>refresh</code>, <code>try</code>, and <code>safe-</code>* command. Logging verbosity is determined by the setting of LOG_VERBOSITY above.</dl>
<p> <code>SUBSYSLOCK=</code>[<i>pathname</i>]</p>
<dl>
<dd>This parameter should be set to the name of a file that the firewall should create if it starts successfully and remove when it stops. Creating and removing this file allows Shorewall to work with your distribution&#8217;s initscripts. For RedHat and OpenSuSE, this should be set to /var/lock/subsys/shorewall. For Debian, the value is /var/lock/shorewall and in LEAF it is /var/run/shorewall.</dl>
<p> <code>TC</code>=[<i>pathname</i>]</p>
<dl>
<dd>If specified, gives the pathname of the &#8216;tc&#8217; executable. If not specified, &#8216;tc&#8217; is assumed and the utility will be located using the current PATH setting.</dl>
<p> <code>TC_BITS</code>=[<i>number</i>]</p>
<dl>
<dd>The number of bits at the low end of the 32-bit packet mark to be used for traffic shaping marking. May be zero. See MASK_BITS above for default value.</dl>
<p> <code>TC_ENABLED=</code>[<code>Yes</code>|<code>No</code>|<code>Internal</code>|<code>Simple</code>|<code>Shared</code>]</p>
<dl>
<dd>If you say <code>Yes</code> or <code>yes</code> here, Shorewall will use a script that you supply to configure traffic shaping. The script must be named &#8216;tcstart&#8217; and must be placed in a directory on your CONFIG_PATH. </p>
<p> If you say <code>No</code> or <code>no</code> then traffic shaping is not enabled. </p>
<p> If you set TC_ENABLED=Simple (Shorewall 4.4.6 and later), simple traffic shaping using m[blue]<code>shorewall-tcinterfaces</code>m[]<font SIZE="-2">[30]</font>(5) and m[blue]<code>shorewall-tcpri</code>m[]<font SIZE="-2">[31]</font>(5) is enabled. </p>
<p> If you set TC_ENABLED=Internal or internal or leave the option empty then Shorewall will use its builtin traffic shaper (tc4shorewall written by Arne Bernin. </p>
<p> Beginning with Shorewall 4.4.15, you can set TC_ENABLED=Shared. This allows you to configure the tcdevices and tcclasses in your Shorewall6 configuration yet make them available to the compiler when compiling your Shorewall configuration. In addition to setting TC_ENABLED=Shared, you need to create symbolic links from your Shorewall configuration directory (normally /etc/shorewall/) to the tcdevices and tcclasses files in your Shorewall6 configuration directory (normally /etc/shorewall6/).</dl>
<p> <code>TC_EXPERT=</code>{<code>Yes</code>|<code>No</code>}</p>
<dl>
<dd>Normally, Shorewall tries to protect users from themselves by preventing PREROUTING and OUTPUT tcrules from being applied to packets that have been marked by the &#8216;track&#8217; option in m[blue]<code>shorewall-providers</code>m[]<font SIZE="-2">[32]</font>(5). </p>
<p> If you know what you are doing, you can set TC_EXPERT=Yes and Shorewall will not include these cautionary checks.</dl>
<p> <code>TC_PRIOMAP</code>=<i>map</i></p>
<dl>
<dd>Added in Shorewall 4.4.6. Determines the mapping of a packet&#8217;s TOS field to priority bands. See m[blue]<code>shorewall-tcpri</code>m[]<font SIZE="-2">[31]</font>(5). The <i>map</i> consists of 16 space-separated digits with values 1, 2 or 3. A value of 1 corresponds to Linux priority 0, 2 to Linux priority 1, and 3 to Linux Priority 2. The first entry gives the priority of TOS value 0, the second of TOS value 1, and so on. See <a href="/docs/linux/man/8-tc-prio/">tc-prio</a>(8) for additional information. </p>
<p> The default setting is TC_PRIOMAP=&quot;2 3 3 3 2 3 1 1 2 2 2 2 2 2 2 2&quot;.</dl>
<p> <code>TCP_FLAGS_DISPOSITION=</code>[<code>ACCEPT</code>|<code>DROP</code>|<code>REJECT</code>|A_DROP|A_REJECT]</p>
<dl>
<dd>Determines the disposition of TCP packets that fail the checks enabled by the <code>tcpflags</code> interface option (see m[blue]<code>shorewall-interfaces</code>m[]<font SIZE="-2">[21]</font>(5)) and must have a value of ACCEPT (accept the packet), REJECT (send an RST response) or DROP (ignore the packet). If not set or if set to the empty value (e.g., TCP_FLAGS_DISPOSITION=&quot;&quot;) then TCP_FLAGS_DISPOSITION=DROP is assumed. </p>
<p> A_DROP and A_REJECT are audited versions of DROP and REJECT respectively and were added in Shorewall 4.4.20. They require AUDIT_TARGET in the kernel and iptables.</dl>
<p> <code>TCP_FLAGS_LOG_LEVEL=</code>[<i>log-level</i>[:<i>log-tag</i>]]</p>
<dl>
<dd>Determines the syslog level for logging packets that fail the checks enabled by the tcpflags interface option. The value must be a valid syslogd log level. If you don&#8217;t want to log these packets, set to the empty value (e.g., TCP_FLAGS_LOG_LEVEL=&quot;&quot;).</dl>
<p> <code>TRACK_PROVIDERS=</code>{<code>Yes</code>|<code>No</code>}</p>
<dl>
<dd>Added in Shorewall 4.4.3. When set to Yes, causes the <code>track</code> option to be assumed on all providers defined in m[blue]<code>shorewall-providers</code>m[]<font SIZE="-2">[32]</font>(5). May be overridden on an individual provider through use of the <code>notrack</code> option. The default value is &#8216;No&#8217;. </p>
<p> Beginning in Shorewall 4.4.6, setting this option to &#8216;Yes&#8217; also simplifies PREROUTING rules in m[blue]<code>shorewall-tcrules</code>m[]<font SIZE="-2">[11]</font>(5). Previously, when TC_EXPERT=No, packets arriving through &#8216;tracked&#8217; provider interfaces were unconditionally passed to the PREROUTING tcrules. This was done so that tcrules could reset the packet mark to zero, thus allowing the packet to be routed using the &#8216;main&#8217; routing table. Using the main table allowed dynamic routes (such as those added for VPNs) to be effective. The rtrules file was created to provide a better alternative to clearing the packet mark. As a consequence, passing these packets to PREROUTING complicates things without providing any real benefit. Beginning with Shorewall 4.4.6, when TRACK_PROVIDERS=Yes and TC_EXPERT=No, packets arriving through &#8216;tracked&#8217; interfaces will not be passed to the PREROUTING rules. Since TRACK_PROVIDERS was just introduced in 4.4.3, this change should be transparent to most, if not all, users.</dl>
<p> <code>TRACK_RULES=</code>{<code>Yes</code>|<code>No</code>|File}</p>
<dl>
<dd>Added in Shorewall 4.5.20. If set to <code>Yes</code>, causes the compiler to add a comment to iptables rules to indicate the file name and line number of the configuration entry that generated the rule. If set to <code>No</code> (the default), then no such comments are added. </p>
<p> Setting this option to <code>Yes</code> requires the Comments capability in iptables and kernel. </p>
<p> Beginning with Shorewall 5.0.5, the option may also be set to <code>File</code>. That setting causes similar comments to be added to the .iptables-restore-input file, which is normally created in /var/lib/shorewall.</dl>
<p> <code>UNTRACKED_DISPOSITION=[ACCEPT|A_ACCEPT|A_DROP|A_REJECT|DROP|REJECT|CONTINUE]</code></p>
<dl>
<dd>Added in Shorewall 4.5.13. Shorewall has traditionally passed UNTRACKED packets through the NEW section of m[blue]<code>shorewall-rules</code>m[]<font SIZE="-2">[8]</font> (5). When a packet in UNTRACKED state fails to match any rule in the UNTRACKED section, the packet is disposed of based on this setting. The default value is CONTINUE for compatibility with earlier versions.</dl>
<p> <code>UNTRACKED_LOG_LEVEL=</code><i>log-level</i>[:<i>log-tag</i>]</p>
<dl>
<dd>Added in Shorewall 4.5.13. Packets in the UNTRACKED state that do not match any rule in the UNTRACKED section of m[blue]<code>shorewall-rules</code>m[]<font SIZE="-2">[8]</font> (5) are logged at this level. The default value is empty which means no logging is performed.</dl>
<p> <code>USE_DEFAULT_RT=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>When set to &#8216;Yes&#8217;, this option causes the Shorewall multi-ISP feature to create a set of routing rules which are resilient to changes in the main routing table. Such changes can occur for a number of reasons, VPNs going up and down being an example. The idea is to send packets through the main table prior to applying any of the Shorewall-generated routing rules. So changes to the main table will affect the routing of packets by default. </p>
<p> When USE_DEFAULT_RT=Yes: </p>
<dl>
<dd>1. Both the DUPLICATE and the COPY columns in m[blue]<code>providers</code>m[]<font SIZE="-2">[32]</font>(5) file must remain empty (or contain &quot;-&quot;).</dl>
<dl>
<dd>2. The default route is added to the the &#8216;default&#8217; table rather than to the main table.</dl>
<dl>
<dd>3. <code>balance</code> is assumed unless <code>loose</code> is specified.</dl>
<dl>
<dd>4. Packets are sent through the main routing table by a rule with priority 999. In m[blue]<code>routing_rules</code>m[]<font SIZE="-2">[33]</font>(5), the range 1-998 may be used for inserting rules that bypass the main table.</dl>
<dl>
<dd>5. All provider gateways must be specified explicitly in the GATEWAY column. <code>detect</code> may not be specified..if n </p>
<dl>
<dd><font SIZE="+1"> <code>Note</code> </font><br />
 <code>detect</code> may be specified for interfaces whose configuration is managed by dhcpcd. Shorewall will use dhcpcd&#8217;s database to find the interface&#8217;s gateway. </p>
</dl>
</dl>
<dl>
<dd>6. You should disable all default route management outside of Shorewall. If a default route is added to the main table while Shorewall is started, then all policy routing will stop working (except for those routing rules in the priority range 1-998).</dl>
<p> Prior to Shorewall 4.6.0, if USE_DEFAULT_RT was not set or if it was set to the empty string then USE_DEFAULT_RT=No was assumed. Beginning with Shorewall 4.6.0, the default is USE_DEFAULT_RT=Yes and use of USE_DEFAULT_RT=No is deprecated. </p>
<dl>
<dd><font SIZE="+1"> <code>Warning</code> </font><br />
 The <code>enable</code>, <code>disable</code> and <code>reenable</code> commands do not work correctly when USE_DEFAULT_RT=No. </p>
</dl>
</dl>
<p> <code>USE_PHYSICAL_NAMES=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>Added in Shorewall 4.4.27. Normally, when Shorewall creates a Netfilter chain that relates to an interface, it uses the interface&#8217;s logical name as the base of the chain name. For example, if the logical name for an interface is OAKLAND, then the input chain for traffic arriving on that interface would be &#8216;OAKLAND_in&#8217;. If this option is set to Yes, then the physical name of the interface will be used the base of the chain name.</dl>
<p> <code>USE_RT_NAMES=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>Added in Shorewall 4.5.15. When set to &#8216;Yes&#8217;, Shorewall will use routing table (provider) names in the generated script rather than table numbers. When set to &#8216;No&#8217; (the default), routing table numbers will be used. </p>
<dl>
<dd><font SIZE="+1"> <code>Caution</code> </font><br />
 If you set USE_RT_NAMES=Yes and KEEP_RT_TABLES=Yes, then you must insure that all of your providers have entries in /etc/iproute2/rt_tables as well as the following entries:</p>
<dl>
<dd>255 local</dl>
<dl>
<dd>254 main</dl>
<dl>
<dd>253 default</dl>
<dl>
<dd>250 balance</dl>
<dl>
<dd>0 unspec</dl>
<p> Without these entries, the firewall will fail to start. </p>
</dl>
</dl>
<p> <code>VERBOSE_MESSAGES=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>Added in Shorewall 5.0.9. When Yes (the default), messages produced by the ?INFO and ?WARNING directives include the filename and linenumber of the directive. When set to No, that additional information is omitted. The setting may be overridden on a directive by directive basis by following ?INFO or ?WARNING with &#8216;!&#8217; (no intervening white space).</dl>
<p> <code>VERBOSITY=</code>[<i>number</i>]</p>
<dl>
<dd>Shorewall has traditionally been very noisy (produced lots of output). You may set the default level of verbosity using the VERBOSITY OPTION. </p>
<p> Values are:</p>
<dl>
<dd>0 &#8211; Silent. You may make it more verbose using the -v<br />
&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>option</dl>
<dl>
<dd>1 &#8211; Major progress messages displayed</dl>
<dl>
<dd>2 &#8211; All progress messages displayed (pre Shorewall-3.2.0<br />
&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>behavior)</dl>
<p> If not specified, then 2 is assumed.</dl>
<p> <code>WARNOLDCAPVERSION=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>Added in Shorewall 4.5.12. When set to <code>Yes</code> (the default), the compiler issues a warning when it finds a capabilities file that doesn&#8217;t specify all of the capabilities supported by the compiler. When WARNOLDCAPVERSION is set to <code>No</code>, no warning is issued.</dl>
<p> <code>WORKAROUNDS=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>Added in Shorewall 4.6.11. Over time, there have been a number of changes in Shorewall that work around defects in other products such as iptables and ipset. When WORKAROUNDS=Yes, these workarounds are enabled; when WORKAROUNDS=No, they are disabled. If not specified or if specified as empty, WORKAROUNDS=Yes is assumed. </p>
<dl>
<dd><font SIZE="+1"> <code>Warning</code> </font><br />
 Do not set WORKAROUNDS=Yes if you need to be able to use Shorewall-generated scripts (such as created by the <code>save</code> command) built by Shorewall 4.4.7 or older. </p>
</dl>
</dl>
<p> <code>ZERO_MARKS=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>Added in Shorewall 5.0.12, this is a workaround for an issue where packet marks are not zeroed by the kernel. It should be set to No (the default) unless you find that incoming packets are being mis-routed for no apparent reasons. </p>
<dl>
<dd><font SIZE="+1"> <code>Caution</code> </font><br />
 Do not set this option to Yes if you have IPSEC software running on the firewall system. </p>
</dl>
</dl>
<p> <code>ZONE_BITS</code>=[<i>number</i>]</p>
<dl>
<dd>Added in Shorewall 4.4.26. When non-zero, enables automatic packet marking by source zone and determines the number of bits in the 32-bit packet mark to be used for the zone mark. Default value is 0.</dl>
<p> <code>ZONE2ZONE</code>=[<code>2</code>|<code>&#8211;</code>]</p>
<dl>
<dd>Added in Shorewall 4.4.4. This option determines how Shorewall constructs chain names involving zone names and/or &#8216;all&#8217;. Beginning with Shorewall 4.6.0, the default is &#8216;-&#8216; (e.g., fw-net); prior to that release, the default was &#8216;2&#8217; (e.g., fw2net).</dl>
