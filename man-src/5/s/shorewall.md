<p>shorewall.conf &#8211; Shorewall global configuration file</p>
<h2>Synopsis</h2>
<dl>
<dt> <code>/etc/shorewall/shorewall.conf</code></dl>
<h2>Description</h2>
<dd>This file sets options that apply to Shorewall as a whole. </p>
<p> The file consists of Shell comments (lines beginning with &#8216;#&#8217;), blank lines and assignment statements (<i>variable</i>=<i>value</i>). If the <i>value</i> contains shell metacharacters or white-space, then it must be enclosed in quotes. Example: MACLIST_LOG_LEVEL=&quot;NFLOG(1,0,1)&quot;.</p>
<h2>Options</h2>
<p>Many options have as their value a <i>log-level</i>. Log levels are a method of describing to syslog (8) the importance of a message and a number of parameters in this file have log levels as their value. </p>
<p> These levels are defined by syslog and are used to determine the destination of the messages through entries in /etc/syslog.conf (5). The syslog documentation refers to these as &quot;priorities&quot;; Netfilter calls them &quot;levels&quot; and Shorewall also uses that term. </p>
<p> Valid levels are: </p>
<dl>
<dd>
<pre> 7 debug
 6 info
 5 notice
 4 warning
 3 err
 2 crit
 1 alert
 0 emerg</pre>
</dl>
<p> For most Shorewall logging, a level of 6 (info) is appropriate. Shorewall log messages are generated by NetFilter and are logged using facility &#8216;kern&#8217; and the level that you specify. If you are unsure of the level to choose, 6 (info) is a safe bet. You may specify levels by name or by number. </p>
<p> If you have built your kernel with ULOG and/or NFLOG target support, you may also specify a log level of ULOG and/or NFLOG (must be all caps). Rather than log its messages to syslogd, Shorewall will direct netfilter to log the messages via the ULOG or NFLOG target which will send them to a process called &#8216;ulogd&#8217;. ulogd is available with most Linux distributions (although it probably isn&#8217;t installed by default). Ulogd is also available from <i><a rel="nofollow" href="http://www.netfilter.org/projects/ulogd/index.html">http://www.netfilter.org/projects/ulogd/index.html</a></i> and can be configured to log all Shorewall messages to their own log file </p>
<p> The following options may be set in shorewall.conf. </p>
<p> <code>ACCEPT_DEFAULT=</code>{<i>action</i>|<i>macro</i>|<code>none</code>}</p>
<dl>
<dd></dl>
<p> <code>DROP_DEFAULT=</code>{<i>action</i>|<i>macro</i>|<code>none</code>}</p>
<dl>
<dd></dl>
<p> <code>REJECT_DEFAULT=</code>{<i>action</i>|<i>macro</i>|<code>none</code>}</p>
<dl>
<dd></dl>
<p> <code>QUEUE_DEFAULT=</code>{<i>action</i>|<i>macro</i>|<code>none</code>}</p>
<dl>
<dd></dl>
<p> <code>NFQUEUE_DEFAULT=</code>{<i>action</i>|<i>macro</i>|<code>none</code>}</p>
<dl>
<dd>In earlier Shorewall versions, a &quot;default action&quot; for DROP and REJECT policies was specified in the file /usr/share/shorewall/actions.std. </p>
<p> To allow for default rules to be applied when USE_ACTIONS=No, the DROP_DEFAULT, REJECT_DEFAULT, ACCEPT_DEFAULT, QUEUE_DEFAULT and NFQUEUE_DEFAULT options have been added. </p>
<p> DROP_DEFAULT describes the rules to be applied before a connection request is dropped by a DROP policy; REJECT_DEFAULT describes the rules to be applied if a connection request is rejected by a REJECT policy. The other three are similar for ACCEPT, QUEUE and NFQUEUE policies. </p>
<p> The value applied to these may be:</p>
<dl>
<dd>a) The name of an<br />
&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr><i>action</i>.</p>
<dd>b) <code>None</code> or <code>none</code> The default values are:</p>
<dd>DROP_DEFAULT=&quot;Drop&quot;</p>
<dd>REJECT_DEFAULT=&quot;Reject&quot;</p>
<dd>ACCEPT_DEFAULT=&quot;none&quot;</p>
<dd>QUEUE_DEFAULT=&quot;none&quot;</p>
<dd>NFQUEUE_DEFAULT=&quot;None&quot; If USE_ACTIONS=Yes, then these values refer to action.Drop and action.Reject respectively. If USE_ACTIONS=No, then these values refer to macro.Drop and macro.Reject. </p>
<p> If you set the value of either option to &quot;None&quot; then no default action will be used and the default action or macro must be specified in <i>shorewall-policy</i>[1](5).</dl>
</dl>
<p> <code>ACCOUNTING=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>Added in Shorewall 4.4.7. If set to Yes, Shorewall accounting is enabled (see <i>shorewall-accounting</i>[2](5)). If not specified or set to the empty value, ACCOUNTING=Yes is assumed.</dl>
<p> <code>ADD_IP_ALIASES=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>This parameter determines whether Shorewall automatically adds the external address(es) in <i>shorewall-nat</i>[3](5). If the variable is set to <code>Yes</code> or <code>yes</code> then Shorewall automatically adds these aliases. If it is set to <code>No</code> or <code>no</code>, you must add these aliases yourself using your distribution&#8217;s network configuration tools. </p>
<p> If this variable is not set or is given an empty value (ADD_IP_ALIASES=&quot;&quot;) then ADD_IP_ALIASES=Yes is assumed. </p>
<p> Warning Addresses added by ADD_IP_ALIASES=Yes are deleted and re-added during shorewall restart. As a consequence, connections using those addresses may be severed.</dl>
<p> <code>ADD_SNAT_ALIASES=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>This parameter determines whether Shorewall automatically adds the SNAT ADDRESS in <i>shorewall-masq</i>[4](5). If the variable is set to <code>Yes</code> or <code>yes</code> then Shorewall automatically adds these addresses. If it is set to <code>No</code> or <code>no</code>, you must add these addresses yourself using your distribution&#8217;s network configuration tools. </p>
<p> If this variable is not set or is given an empty value (ADD_SNAT_ALIASES=&quot;&quot;) then ADD_SNAT_ALIASES=No is assumed. </p>
<p> Warning Addresses added by ADD_SNAT_ALIASES=Yes are deleted and re-added during shorewall restart. As a consequence, connections using those addresses may be severed.</dl>
<p> <code>ADMINISABSENTMINDED=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>The value of this variable affects Shorewall&#8217;s stopped state. When ADMINISABSENTMINDED=No, only traffic to/from those addresses listed in <i>shorewall-routestopped</i>[5](5) is accepted when Shorewall is stopped. When ADMINISABSENTMINDED=Yes, in addition to traffic to/from addresses in <i>shorewall-routestopped</i>[5](5), connections that were active when Shorewall stopped continue to work and all new connections from the firewall system itself are allowed. If this variable is not set or is given the empty value then ADMINISABSENTMINDED=No is assumed.</dl>
<p> <code>AUTO_COMMENT=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>If set, if there is not a current comment when a macro is invoked, the behavior is as if the first line of the macro file was &quot;COMMENT &lt;macro name&gt;&quot;. The AUTO_COMMENT option has a default value of &#8216;Yes&#8217;. </p>
<p> The setting of the AUTOMAKE option is ignored if the <code>start</code> or <code>restart</code> command includes a directory name (e.g.,<code> shorewall restart /etc/shorewall.new</code>).</dl>
<p> <code>AUTOMAKE=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>If set, the behavior of the &#8216;start&#8217; command is changed; if no files in /etc/shorewall have been changed since the last successful <code>start</code> or <code>restart</code> command, then the compilation step is skipped and the compiled script that executed the last <code>start</code> or <code>restart</code> command is used. The default is AUTOMAKE=No.</dl>
<p> <code>BIGDPORTLISTS=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>Setting this option to &#8216;Yes&#8217; allows you to include arbitrarily long destination port lists in all configuration files.</dl>
<p> <code>BLACKLIST_DISPOSITION=</code>[<code>DROP</code>|<code>REJECT</code>]</p>
<dl>
<dd>This parameter determines the disposition of packets from blacklisted hosts. It may have the value DROP if the packets are to be dropped or REJECT if the packets are to be replied with an ICMP port unreachable reply or a TCP RST (tcp only). If you do not assign a value or if you assign an empty value then DROP is assumed.</dl>
<p> <code>BLACKLIST_LOGLEVEL=</code>[<i>log-level</i>]</p>
<dl>
<dd>This parameter determines if packets from blacklisted hosts are logged and it determines the syslog level that they are to be logged at. Its value is a syslog level (Example: BLACKLIST_LOGLEVEL=debug). If you do not assign a value or if you assign an empty value then packets from blacklisted hosts are not logged.</dl>
<p> <code>BLACKLISTNEWONLY=</code>{<code>Yes</code>|<code>No</code>}</p>
<dl>
<dd>When set to <code>Yes</code> or <code>yes</code>, blacklists are only consulted for new connections. When set to <code>No</code> or <code>no</code>, blacklists are consulted for every packet (will slow down your firewall noticably if you have large blacklists). If the BLACKLISTNEWONLY option is not set or is set to the empty value then BLACKLISTNEWONLY=No is assumed. </p>
<p> Note BLACKLISTNEWONLY=No is incompatible with FASTACCEPT=Yes.</dl>
<p> <code>CLAMPMSS=[</code><code>Yes</code>|<code>No</code>|<i>value</i>]</p>
<dl>
<dd>This parameter enables the TCP Clamp MSS to PMTU feature of Netfilter and is usually required when your internet connection is through PPPoE or PPTP. If set to <code>Yes</code> or <code>yes</code>, the feature is enabled. If left blank or set to <code>No</code> or <code>no</code>, the feature is not enabled. </p>
<p> <code>Important</code>: This option requires CONFIG_IP_NF_TARGET_TCPMSS in your kernel. </p>
<p> You may also set CLAMPMSS to a numeric <i>value</i> (e.g., CLAMPMSS=1400). This will set the MSS field in TCP SYN packets going through the firewall to the <i>value</i> that you specify.</dl>
<p> <code>CLEAR_TC=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>If this option is set to <code>No</code> then Shorewall won&#8217;t clear the current traffic control rules during [re]start. This setting is intended for use by people who prefer to configure traffic shaping when the network interfaces come up rather than when the firewall is started. If that is what you want to do, set TC_ENABLED=Yes and CLEAR_TC=No and do not supply an /etc/shorewall/tcstart file. That way, your traffic shaping rules can still use the lqfwmarkrq classifier based on packet marking defined in <i>shorewall-tcrules</i>[6](5). If not specified, CLEAR_TC=Yes is assumed.</dl>
<p> <code>CONFIG_PATH</code>=[<i>directory</i>[:<i>directory</i>]&#8230;]</p>
<dl>
<dd>Specifies where configuration files other than shorewall.conf may be found. CONFIG_PATH is specifies as a list of directory names separated by colons (&quot;:&quot;). When looking for a configuration file other than shorewall.conf: </p>
<dl>
<dd>*If the command is &quot;try&quot; or a &quot;&lt;configuration directory&gt;&quot; was specified in the command (e.g., <code>shorewall check ./gateway</code>) then the directory given in the command is searched first.</dl>
<dl>
<dd>*Next, each directory in the CONFIG_PATH setting is searched in sequence.</dl>
<dl>
<dd>If CONFIG_PATH is not given or if it is set to the empty value then the contents of /usr/share/shorewall/configpath are used. As released from shorewall.net, that file sets the CONFIG_PATH to /etc/shorewall:/usr/share/shorewall but your particular distribution may set it differently. See the output of shorewall show config for the default on your system. </p>
<p> Note that the setting in /usr/share/shorewall/configpath is always used to locate shorewall.conf.</dl>
</dl>
<p> <code>DELETE_THEN_ADD=</code>{<code>Yes</code>|<code>No</code>}</p>
<dl>
<dd>If set to Yes (the default value), entries in the /etc/shorewall/route_stopped files cause an &#8216;ip rule del&#8217; command to be generated in addition to an &#8216;ip rule add&#8217; command. Setting this option to No, causes the &#8216;ip rule del&#8217; command to be omitted.</dl>
<p> <code>DETECT_DNAT_IPADDRS=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>If set to <code>Yes</code> or <code>yes</code>, Shorewall will detect the first IP address of the interface to the source zone and will include this address in DNAT rules as the original destination IP address. If set to <code>No</code> or <code>no</code>, Shorewall will not detect this address and any destination IP address will match the DNAT rule. If not specified or empty, lqDETECT_DNAT_IPADDRS=Yesrq is assumed.</dl>
<p> <code>DISABLE_IPV6=</code>[<code>Yes</code>|<code>No</code>]</p>
<dl>
<dd>If set to <code>Yes</code> or <code>yes</code>, IPv6 traffic to, from and through the firewall system is disabled. If set to <code>No</code> or <code>no</code>, Shorewall will take no action with respect to allowing or disallowing IPv6 traffic. If not specified or empty, lqDISABLE_IPV6=Norq is assumed.</dl>
<p> <code>DONT_LOAD=</code>[<i>module</i>[,<i>module</i>]&#8230;]</p>
<dl>
<dd>Causes Shorewall to not load the listed kernel modules.</dl>
<p> <code>DYNAMIC_BLACKLIST=</code>{<code>Yes</code>|<code>No</code>}</p>
<dl>
<dd>Added in Shorewall 4.4.7. When set to <code>No</code> or <code>no</code>, dynamic blacklisting using the <code>shorewall drop</code>, <code>shorewall reject</code>, <code>shorewall logdrop</code> and <code>shorewall logreject</code> is disabled. Default is <code>Yes</code>.</dl>
<p> <code>EXPAND_POLICIES=</code>{<code>Yes</code>|<code>No</code>}</p>
<dl>
<dd>Normally, when the SOURCE or DEST columns in <a href="/docs/linux/man/5-shorewall-policy/">shorewall-policy</a>(5) contains &#8216;all&#8217;, a single policy chain is created and the policy is enforced in that chain. For example, if the policy entry is </p>
<dl>
<dd>
<pre>#SOURCE DEST POLICY LOG
# LEVEL
net all DROP info</pre>
</dl>
<p> then the chain name is &#8216;net2all&#8217; which is also the chain named in Shorewall log messages generated as a result of the policy. If EXPAND_POLICIES=Yes, then Shorewall will create a separate chain for each pair of zones covered by the policy. This makes the resulting log messages easier to interpret since the chain in the messages will have a name of the form &#8216;a2b&#8217; where &#8216;a&#8217; is the SOURCE zone and &#8216;b&#8217; is the DEST zone.</dl>
<p> <code>EXPORTPARAMS=</code>{<code>Yes</code>|<code>No</code>}</p>
<dl>
<dd>It is quite difficult to code a &#8216;params&#8217; file that assigns other than constant values such that it works correctly with Shorewall Lite. The EXPORTPARAMS option works around this problem. When EXPORTPARAMS=No, the &#8216;params&#8217; file is not copied to the compiler output. </p>
<p> With EXPORTPARAMS=No, if you need to set environmental variables on the firewall system for use by your extension scripts, then do so in the init extension script. </p>
<p> The default is EXPORTPARAMS=Yes which is the recommended setting unless you are using Shorewall Lite.</dl>
<p> <code>FASTACCEPT=</code>{<code>Yes</code>|<code>No</code>}</p>
<dl>
<dd>Normally, Shorewall defers accepting ESTABLISHED/RELATED packets until these packets reach the chain in which the original connection was accepted. So for packets going from the &#8216;loc&#8217; zone to the &#8216;net&#8217; zone, ESTABLISHED/RELATED packets are ACCEPTED in the &#8216;loc2net&#8217; chain. </p>
<p> If you set FASTACCEPT=Yes, then ESTABLISHED/RELEATED packets are accepted early in the INPUT, FORWARD and OUTPUT chains. If you set FASTACCEPT=Yes then you may not include rules in the ESTABLISHED or RELATED sections of <i>shorewall-rules</i>[7](5). </p>
<p> Note FASTACCEPT=Yes is incompatible with BLACKLISTNEWONLY=No.</dl>
<p> <code>HIGH_ROUTE_MARKS=</code>{<code>Yes</code>|<code>No</code>}</p>
<dl>
<dd>Prior to version 3.2.0, it was not possible to use connection marking in <i>shorewall-tcrules</i>[6](5) if you had a multi-ISP configuration that uses the track option. </p>
<p> You may set HIGH_ROUTE_MARKS=Yes in to effectively divide the packet mark and connection mark into two mark fields. </p>
<p> Note From Shorewall 2.5.0 onward, this option is deprecated in favor of the PROVIDER_OFFSET option. </p>
<p> The width of the fields are determined by the setting of WIDE_TC_MARKS. If WIDE_TC_MARKS=No (the default): </p>
<dl>
<dd>1.The MARK field in the providers file must have a value that is less than 65536 and that is a multiple of 256 (using hex representation, the values are 0x0100-0xFF00 with the low-order 8 bits being zero).</dl>
<dl>
<dd>2.You may only set those mark values in the PREROUTING chain.</dl>
<dl>
<dd>3.Marks used for traffic shaping must still be in the range of 1-255 and may still not be set in the PREROUTING chain.</dl>
<dl>
<dd>When WIDE_TC_MARKS=Yes: </p>
<dl>
<dd>1.The MARK field in the providers file must have a value that is a multiple of 65536 (using hex representation, the values are 0x010000-0xFF0000 with the low-order 16 bits being zero).</dl>
<dl>
<dd>2.You may only set those mark values in the PREROUTING chain.</dl>
<dl>
<dd>3.Marks used for traffic shaping must be in the range of 1-16383 and may still not be set in the PREROUTING chain.</dl>
<dd>Regardless of the setting of WIDE_TC_MARKS, when you SAVE or RESTORE in tcrules, only the TC mark value is saved or restored. Shorewall handles saving and restoring the routing (provider) marks.</dl>
</dl>
<p> <code>IMPLICIT_CONTINUE=</code>{<code>Yes</code>|<code>No</code>}</p>
<dl>
<dd>When this option is set to <code>Yes</code>, it causes subzones to be treated differently with respect to policies. </p>
<p> Subzones are defined by following their name with &quot;:&quot; and a list of parent zones (in <i>shorewall-zones</i>[8](5)). Normally, you want to have a set of special rules for the subzone and if a connection doesn&#8217;t match any of those subzone-specific rules then you want the parent zone rules and policies to be applied; see <i>shorewall-nesting</i>[9](5). With IMPLICIT_CONTINUE=Yes, that happens automatically. </p>
<p> If IMPLICIT_CONTINUE=No or if IMPLICIT_CONTINUE is not set, then subzones are not subject to this special treatment. With IMPLICIT_CONTINUE=Yes, an implicit CONTINUE policy may be overridden by including an explicit policy (one that does not specify &quot;all&quot; in either the SOURCE or the DEST columns).</dl>
<p> <code>IP</code>=[<i>pathname</i>]</p>
<dl>
<dd>If specified, gives the pathname of the &#8216;ip&#8217; executable. If not specified, &#8216;ip&#8217; is assumed and the utility will be located using the current PATH setting.</dl>
<p> <code>IP_FORWARDING=</code>[<code>On</code>|<code>Off</code>|<code>Keep</code>]</p>
<dl>
<dd>This parameter determines whether Shorewall enables or disables IPV4 Packet Forwarding (/proc/sys/net/ipv4/ip_forward). Possible values are: </p>
<p> <code>On</code> or <code>on</code></p>
<dl>
<dd>packet forwarding will be enabled.</dl>
<p> <code>Off</code> or <code>off</code></p>
<dl>
<dd>packet forwarding will be disabled.</dl>
<p> <code>Keep</code> or <code>keep</code></p>
<dl>
<dd>Shorewall will neither enable nor disable packet forwarding.</dl>
<p> If this variable is not set or is given an empty value (IP_FORWARD=&quot;&quot;) then IP_FORWARD=On is assumed.</dl>
<p> <code>IPSET</code>=[<i>pathname</i>]</p>
<dl>
<dd>If specified, gives the pathname of the &#8216;ipset&#8217; executable. If not specified, &#8216;ipset&#8217; is assumed and the utility will be located using the current PATH setting.</dl>
<p> <code>IPTABLES=</code>[<i>pathname</i>]</p>
<dl>
<dd>This parameter names the iptables executable to be used by Shorewall. If not specified or if specified as a null value, then the iptables executable located using the PATH option is used. </p>
<p> Regardless of how the IPTABLES utility is located (specified via IPTABLES= or located via PATH), Shorewall uses the iptables-restore and iptables-save utilities from that same directory.</dl>
<p> <code>KEEP_RT_TABLES=</code>{<code>Yes</code>|<code>No</code>}</p>
<dl>
<dd>When set to <code>Yes</code>, this option prevents generated scripts from altering the /etc/iproute2/rt_tables database when there are entries in <i>/etc/shorewall/providers</i>. If you set this option to <code>Yes</code> while Shorewall (Shorewall-lite) is running, you should remove the file <i>/var/lib/shorewall/rt_tables</i> (<i>/var/lib/shorewall-lite/rt_tables</i>) before your next <code>stop</code>, <code>refresh</code>, <code>restore</code> on <code>restart</code> command. </p>
<p> The default is KEEP_RT_TABLES=No.</dl>
<p> <code>LOAD_HELPERS_ONLY=</code>{<code>Yes</code>|<code>No</code>}</p>
<dl>
<dd>Added in Shorewall 4.4.7. When set to Yes, restricts the set of modules loaded by shorewall to those listed in /var/lib/shorewall/helpers and those that are actually used. When not set, or set to the empty value, LOAD_HELPERS_ONLY=No is assumed.</dl>
<p> <code>LOG_MARTIANS=</code>[<code>Yes</code>|<code>No</code>|Keep]</p>
<dl>
<dd>If set to <code>Yes</code> or <code>yes</code>, sets <i>/proc/sys/net/ipv4/conf/*/log_martians</i> to 1 with the exception of <i>/proc/sys/net/ipv4/conf/all/log_martians which is set to 0</i>. The default value is <code>Yes</code> which sets both of the above to one. If you do not enable martian logging for all interfaces, you may still enable it for individual interfaces using the <code>logmartians</code> interface option in <i>shorewall-interfaces</i>[10](5). </p>
<p> The value <code>Keep</code> causes Shorewall to ignore the option. If the option is set to <code>Yes</code>, then martians are logged on all interfaces. If the option is set to <code>No</code>, then martian logging is disabled on all interfaces except those specified in <i>shorewall-interfaces</i>[10](5).</dl>
<p> <code>LOG_VERBOSITY=</code>[<i>number</i>]</p>
<dl>
<dd>This option controls the amount of information logged to the file specified in the STARTUP_LOG option. </p>
<p> Values are:</p>
<dl>
<dd>-1 &#8211; Logging is disabled</p>
<dd>0 &#8211; Silent. Only error messages are logged.</p>
<dd>1 &#8211; Major progress messages logged.</p>
<dd>2 &#8211; All progress messages logged If not specified, then -1 is assumed.</dl>
</dl>
<p> <code>LOGALLNEW=</code>[<i>log-level</i>]</p>
<dl>
<dd>This option is intended for use as a debugging aid. When set to a log level, this option causes Shorewall to generate a logging rule as the first rule in each builtin chain. </p>
<dl>
<dd>*The table name is used as the chain name in the log prefix.</dl>
<dl>
<dd>*The chain name is used as the target in the log prefix.</dl>
<dl>
<dd>For example, using the default LOGFORMAT, the log prefix for logging from the nat table&#8217;s PREROUTING chain is: </p>
<dl>
<dd>
<pre> Shorewall:nat:PREROUTING</pre>
</dl>
<p> Important To help insure that all packets in the NEW state are logged, rate limiting (LOGBURST and LOGRATE) should be disabled when using LOGALLNEW. Use LOGALLNEW at your own risk; it may cause high CPU and disk utilization and you may not be able to control your firewall after you enable this option. </p>
<p> Caution Do not use this option if the resulting log messages will be sent to another system.</dl>
</dl>
<p> <code>LOGFILE=</code>[<i>pathname</i>]</p>
<dl>
<dd>This parameter tells the /sbin/shorewall program where to look for Shorewall messages when processing the <code>dump</code>, <code>logwatch</code>, <code>show log</code>, and <code>hits</code> commands. If not assigned or if assigned an empty value, /var/log/messages is assumed. For further information, see <i><a rel="nofollow" href="http://www.shorewall.net/shorewall_logging.html">http://www.shorewall.net/shorewall_logging.html</a></i>.</dl>
<p> <code>LOGFORMAT=</code>[<code>&quot;</code><i>formattemplate</i><code>&quot;</code>]</p>
<dl>
<dd>The value of this variable generate the &#8211;log-prefix setting for Shorewall logging rules. It contains a lqprintfrq formatting template which accepts three arguments (the chain name, logging rule number (optional) and the disposition). To use LOGFORMAT with fireparse, set it as: </p>
<dl>
<dd>
<pre> LOGFORMAT=&quot;fp=%s:%d a=%s &quot;</pre>
</dl>
<p> If the LOGFORMAT value contains the substring lq%drq then the logging rule number is calculated and formatted in that position; if that substring is not included then the rule number is not included. If not supplied or supplied as empty (LOGFORMAT=&quot;&quot;) then lqShorewall:%s:%s:rq is assumed.</dl>

<p> <code>LOGRATE=</code>[<i>rate</i>/{<code>minute</code>|<code>second</code>}]</p>

<p> <code>WIDE_TC_MARKS=</code>{<code>Yes</code>|<code>No</code>}</p>
<dl>
<dd>When set to No (the default), traffic shaping marks are 8 bytes wide (possible values are 1-255). When WIDE_TC_MARKS=Yes, traffic shaping marks are 14 bytes wide (values 1-16383). The setting of WIDE_TC_MARKS also has an effect on the HIGH_ROUTE_MARKS option (see above). </p>
<p> Note From Shorewall 2.5.0 onware, this option is deprecated in favor of the TC_BITS option.</dl>
<p> <code>ZONE2ZONE</code>={<code>2</code>|<code>&#8211;</code>}</p>
<dl>
<dd>Added in Shorewall 4.4.4. This option determines how Shorewall constructs chain names involving zone names and/or &#8216;all&#8217;. The default is &#8216;2&#8217; (e.g., fw2net).</dl>
