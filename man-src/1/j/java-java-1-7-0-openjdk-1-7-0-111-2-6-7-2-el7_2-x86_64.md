<p>java &#8211; the Java application launcher </p>
<h2>Synopsis</h2>
<pre><code>java</code> [ <i>options</i> ] <i>class</i> [ <i>argument ...</i> ]
<code>java</code> [ <i>options</i> ] <code>-jar</code> <i>file.jar</i> [ <i>argument ...</i> ]</pre>
<dl>
<dd>
<dl>
<dt>options</p>
<dd>Command-line options. See <i>Options</i>.</p>
<dt>class</p>
<dd>The name of the class to be called.</p>
<dt>file.jar</p>
<dd>The name of the JAR file to be called. Used only with the <code>-jar</code> command.</p>
<dt>argument</p>
<dd>The arguments passed to the <code>main</code> function.</dl>
</dl>
<h2>Description</h2>
<p>The <code>java</code> command starts a Java application. It does this by starting a Java runtime environment, loading a specified class, and calling that class&#8217;s <code>main</code> method. </p>
<p> The method must be declared public and static, it must not return any value, and it must accept a String array as a parameter. The method declaration has the following form: </p>
<pre><code>public static void main(String args[])</code></pre>
<p>By default, the first argument without an option is the name of the class to be called. A fully qualified class name should be used. If the <code>-jar</code> option is specified, then the first non-option argument is the name of a JAR file containing class and resource files for the application, with the startup class indicated by the Main-Class manifest header. </p>
<p> The Java runtime searches for the startup class, and other classes used, in three sets of locations: the bootstrap class path, the installed extensions, and the user class path. </p>
<p> Non-option arguments after the class name or JAR file name are passed to the <code>main</code> function. </p>
<h2>Options</h2>
<p>The launcher has a set of standard options that are supported in the current runtime environment. </p>
<p> In addition, the current implementations of the virtual machines support a set of nonstandard options that are subject to change in future releases. See <i>Nonstandard Options</i>. </p>
<h3>Standard Options</h3>
<dl>
<dd>
<dl>
<dt>-client</p>
<dd>Selects the Java HotSpot Client VM. A 64-bit capable JDK currently ignores this option and instead uses the Java Hotspot Server VM. </p>
<p> For default Java VM selection, see <i>Server-Class Machine Detection</i> at <a rel="nofollow" href="http://docs.oracle.com/javase/7/docs/technotes/guides/vm/server-class.html">http://docs.oracle.com/javase/7/docs/technotes/guides/vm/server-class.html</a></p>
<dt>-server</p>
<dd>Selects the Java HotSpot Server VM. On a 64-bit capable JDK, only the Java Hotspot Server VM is supported so the <code>&#8211;</code><code>server</code> option is implicit. </p>
<p> For default a Java VM selection, see <i>Server-Class Machine Detection</i> at <a rel="nofollow" href="http://docs.oracle.com/javase/7/docs/technotes/guides/vm/server-class.html">http://docs.oracle.com/javase/7/docs/technotes/guides/vm/server-class.html</a></p>
<dt>-agentlib:libname[=options]</p>
<dd>Loads native agent library <i>libname</i>, for example: </p>
<pre><code>-agentlib:hprof
 
-agentlib:jdwp=help
 
-agentlib:hprof=help</code></pre>
<p>See <i>JVMTI Agent Command-Line Options</i> at <a rel="nofollow" href="http://docs.oracle.com/javase/7/docs/platform/jvmti/jvmti.html#starting">http://docs.oracle.com/javase/7/docs/platform/jvmti/jvmti.html#starting</a></p>
<dt>-agentpath:pathname[=options]</p>
<dd>Loads a native agent library by full <i>pathname</i>. See <i>JVMTI Command-Line Options</i> at <a rel="nofollow" href="http://docs.oracle.com/javase/7/docs/platform/jvmti/jvmti.html#starting">http://docs.oracle.com/javase/7/docs/platform/jvmti/jvmti.html#starting</a></p>
<dt>-classpath classpath, -cp classpath</p>
<dd>Specifies a list of directories, JAR files, and ZIP archives to search for class files. Separate class path entries with colons (:). Specifying <code>-classpath</code> or <code>-cp</code> overrides any setting of the <i>CLASSPATH</i> environment variable. </p>
<p> If <code>-classpath</code> and <code>-cp</code> are not used and <i>CLASSPATH</i> is not set, then the user class path consists of the current directory (.). </p>
<p> As a special convenience, a class path element that contains a base name of <code>*</code> is considered equivalent to specifying a list of all the files in the directory with the extension .jar or .JAR. A Java program cannot tell the difference between the two invocations. </p>
<p> For example, if directory mydir contains a.jar and b.JAR, then the class path element <code>mydir/*</code> is expanded to a A.jar:b.JAR, except that the order of jar files is unspecified. All jar files in the specified directory, even hidden ones, are included in the list. A class path entry consisting simply of <code>*</code> expands to a list of all the jar files in the current directory. The <i>CLASSPATH</i> environment variable, where defined, will be similarly expanded. Any class path wildcard expansion occurs before the Java VM is started. No Java program will ever see wild cards that are not expanded except by querying the environment. For example, by calling <code>System.getenv(&quot;CLASSPATH&quot;)</code>.</p>
<dt>-Dproperty=value</p>
<dd>Sets a system property value.</p>
<dt>-d32</p>
<dd>Run the application in a 32-bit environment. If a 32-bit environment is not installed or is not supported, an error will be reported. By default, the application is run in a 32-bit environment unless a 64-bit only system is used.</p>
<dt>-d64</p>
<dd>Run the application in a 64-bit environment. If a 64-bit environment is not installed or is not supported, an error will be reported. By default, the application is run in a 32-bit environment unless a 64-bit only system is used. </p>
<p> Currently only the Java HotSpot Server VM supports 64-bit operation, and the <code>-server</code> option is implicit with the use of <code>-d64</code>. The <code>-client</code> option is ignored with the use of <code>-d64</code>. This is subject to change in a future release.</p>
<dt>-disableassertions[:package name&quot;&#8230;&quot; | :class name ], -da[:package name&quot;&#8230;&quot; | :class name ]</p>
<dd>Disable assertions. This is the default. </p>
<p> With no arguments, <code>-disableassertions</code> or <code>-da</code> disables assertions. With one argument ending in <code>&quot;&#8230;&quot;</code>, the switch disables assertions in the specified package and any subpackages. If the argument is <code>&quot;&#8230;&quot;</code>, then the switch disables assertions in the unnamed package in the current working directory. With one argument not ending in <code>&quot;&#8230;&quot;</code>, the switch disables assertions in the specified class. </p>
<p> To run a program with assertions enabled in <code>package com.wombat.fruitbat</code> but disabled in class <code>com.wombat.fruitbat.Brickbat</code>, the following command could be used: </p>
<pre><code>java -ea:com.wombat.fruitbat... -da:com.wombat.fruitbat.Brickbat &lt;Main Class&gt;</code></pre>
<p>The <code>-disableassertions</code> and <code>-da</code> switches apply to all class loaders and to system classes (which do not have a class loader). There is one exception to this rule: in their no-argument form, the switches do not apply to system. This makes it easy to turn on asserts in all classes except for system classes. The <code>-disablesystemassertions</code> option provides a separate swith to enable assertions in all system classes.</p>
<dt>-enableassertions[:package name&quot;&#8230;&quot; | :class name ], -ea[:package name&quot;&#8230;&quot; | :class name ]</p>
<dd>Enable assertions. Assertions are disabled by default. </p>
<p> With no arguments, <code>-enableassertions</code> or <code>-ea</code> enables assertions. With one argument ending in <code>&quot;&#8230;&quot;</code>, the switch enables assertions in the specified package and any subpackages. If the argument is <code>&quot;&#8230;&quot;</code>, then the switch enables assertions in the unnamed package in the current working directory. With one argument not ending in <code>&quot;&#8230;&quot;</code>, the switch enables assertions in the specified class. </p>
<p> If a single command contains multiple instances of these switches, then they are processed in order before loading any classes. So, for example, to run a program with assertions enabled only in package com.wombat.fruitbat (and any subpackages), the following command could be used: </p>
<pre><code>java -ea:com.wombat.fruitbat... &lt;Main Class&gt;</code></pre>
<p>The <code>-enableassertions</code> and <code>-ea</code> switches apply to all class loaders and to system classes (which do not have a class loader). There is one exception to this rule: in their no-argument form, the switches do not apply to system. This makes it easy to turn on asserts in all classes except for system classes. The <code>-enablesystemassertions</code> option provides a separate switch to enable assertions in all system classes.</p>
<dt>-enablesystemassertions, -esa</p>
<dd>Enable assertions in all system classes (sets the default assertion status for system classes to true).</p>
<dt>-disablesystemassertions, -dsa</p>
<dd>Disables assertions in all system classes.</p>
<dt>-help or -?</p>
<dd>Displays usage information and exit.</p>
<dt>-jar</p>
<dd>Executes a program encapsulated in a JAR file. The first argument is the name of a JAR file instead of a startup class name. For this option to work, the manifest of the JAR file must contain a line in the form <code>Main-Class</code>: <i>classname</i>. Here, <i>classname</i> identifies the class with the <code>public static void main(String[] args)</code> method that serves as your application&#8217;s starting point. </p>
<p> When you use this option, the JAR file is the source of all user classes, and other user class path settings are ignored. </p>
<p> JAR files that can be run with the <code>java -jar</code> option can have their execute permissions set so they can be run without using <code>java -jar</code>. See <i>JAR File Overview</i> at <a rel="nofollow" href="http://docs.oracle.com/javase/7/docs/technotes/guides/jar/jarGuide.html">http://docs.oracle.com/javase/7/docs/technotes/guides/jar/jarGuide.html</a></p>
<dt>-javaagent:jarpath[=options]</p>
<dd>Loads a Java programming language agent. For more information about instrumenting Java applications, see the java.lang.instrument package description in the Java API documentation at<br />
 <i><a rel="nofollow" href="http://docs.oracle.com/javase/7/docs/api/java/lang/instrument/package-summary.html">http://docs.oracle.com/javase/7/docs/api/java/lang/instrument/package-summary.html</a></i> @ <a rel="nofollow" href="http://docs.oracle.com/javase/7/docs/api/java/lang/instrument/package-summary.html">http://docs.oracle.com/javase/7/docs/api/java/lang/instrument/package-summary.html</a></p>
<dt>-jre-restrict-search</p>
<dd>Includes user-private JREs in the version search.</p>
<dt>-no-jre-restrict-search</p>
<dd>Excludes user-private JREs in the version search.</p>
<dt>-showversion</p>
<dd>Displays version information and continues.</p>
<dt>-splash:imagepath</p>
<dd>Shows splash screen with image specified by <i>imagepath</i>.</p>
<dt>-verbose, -verbose:class</p>
<dd>Displays information about each class loaded.</p>
<dt>-verbose:gc</p>
<dd>Reports on each garbage collection event.</p>
<dt>-verbose:jni</p>
<dd>Reports information about use of native methods and other Java Native Interface activity.</p>
<dt>-version</p>
<dd>Displays version information and exits. See also the <code>-showversion</code> option.</p>
<dt>-version:release</p>
<dd>Specifies that the version specified by the release is required by the class or JAR file specified on the command line. If the version of the <code>java</code> command called does not meet this specification and an appropriate implementation is found on the system, then the appropriate implementation will be used. </p>
<p> The <code>release</code> option specifies an exact version and a list of versions called a version string. A version string is an ordered list of version ranges separated by spaces. A version range is either a <i>version-id</i>, a <i>version-id</i> followed by an asterisk (<code>*</code>), a <i>version-id</i> followed by a plus sign (<code>+</code>), or a version range that consists of two <i>version-ids</i> combined using an ampersand (<code>&amp;</code>). The asterisk means prefix match, the plus sign means this version or greater, and the ampersand means the logical <code>and</code> of the two version-ranges, for example: </p>
<pre><code>-version:&quot;1.6.0_13 1.6*&amp;1.6.0_10+&quot;</code></pre>
<p>The meaning of the previous example is that the class or JAR file requires either version 1.6.0_13, or a version with 1.6 as a <i>version-id</i> prefix and that is not less than 1.6.0_10. The exact syntax and definition of version strings can be found in Appendix A of the <i>Java Network Launching Protocol &amp; API Specification (JSR-56)</i>. </p>
<p> For JAR files, the preference is to specify version requirements in the JAR file manifest rather than on the command line. </p>
<p> See <i>Notes</i> for important policy information on the use of this option.</dl>
</dl>
<h3>Non-Standard Options</h3>
<dl>
<dd>
<dl>
<dt>-X</p>
<dd>Displays information about nonstandard options and exits.</p>
<dt>-Xint</p>
<dd>Operates in interpreted-only mode. Compilation to native code is disabled, and all bytecode is executed by the interpreter. The performance benefits offered by the Java HotSpot Client VM adaptive compiler is not present in this mode.</p>
<dt>-Xbatch</p>
<dd>Disables background compilation. Typically, the Java VM compiles the method as a background task, running the method in interpreter mode until the background compilation is finished. The -Xbatch flag disables background compilation so that compilation of all methods proceeds as a foreground task until completed.</p>
<dt>-Xbootclasspath:bootclasspath</p>
<dd>Specifies a colon-separated list of directories, JAR files, and ZIP archives to search for boot class files. These are used in place of the boot class files included in the Java platform JDK. </p>
<p> Applications that use this option for the purpose of overriding a class in rt.jar should not be deployed because doing so would contravene the Java Runtime Environment binary code license.</p>
<dt>-Xbootclasspath/a:path</p>
<dd>Specifies a colon-separated path of directories, JAR files, and ZIP archives to append to the default bootstrap class path.</p>
<dt>-Xbootclasspath/p:path</p>
<dd>Specifies a colon-separated path of directories, JAR files, and ZIP archives to add in front of the default bootstrap class path. </p>
<p> Do not deploy applications that use this option to override a class in rt.jar because this violates the Java Runtime Environment binary code license.</p>
<dt>-Xcheck:jni</p>
<dd>Performs additional checks for Java Native Interface (JNI) functions. Specifically, the Java Virtual Machine validates the parameters passed to the JNI function and the runtime environment data before processing the JNI request. Any invalid data encountered indicates a problem in the native code, and the Java Virtual Machine will terminate with a fatal error in such cases. Expect a performance degradation when this option is used.</p>
<dt>-Xfuture</p>
<dd>Performs strict class-file format checks. For backward compatibility, the default format checks performed by the Java virtual machine are no stricter than the checks performed by 1.1.x versions of the JDK software. The <code>-Xfuture</code> option turns on stricter class-file format checks that enforce closer conformance to the class-file format specification. Developers are encouraged to use this flag when developing new code because the stricter checks will become the default in future releases of the Java application launcher.</p>
<dt>-Xnoclassgc</p>
<dd>Disables class garbage collection. Use of this option preven memory recovery from loaded classes thus increasing overall memory usage. This could cause <code>OutOfMemoryError</code> to be thrown in some applications.</p>
<dt>-Xincgc</p>
<dd>Enables the incremental garbage collector. The incremental garbage collector, which is turned off by default, will reduce the occasional long garbage-collection pauses during program execution. The incremental garbage collector will at times execute concurrently with the program and during such times will reduce the processor capacity available to the program.</p>
<dt>-Xloggc:file</p>
<dd>Reports on each garbage collection event, as with <code>-verbose:gc</code>, but logs this data to a file. In addition to the information <code>-verbose:gc</code> gives, each reported event will be preceded by the time (in seconds) since the first garbage-collection event. </p>
<p> Always use a local file system for storage of this file to avoid stalling the Java VM due to network latency. The file may be truncated in the case of a full file system and logging will continue on the truncated file. This option overrides <code>-verbose:gc</code> when both are specified on the command line.</p>
<dt>-Xmnsize or -XX:NewSize</p>
<dd>Sets the size of the young generation (nursery).</p>
<dt>-Xmsn</p>
<dd>Specifies the initial size, in bytes, of the memory allocation pool. This value must be a multiple of 1024 greater than 1 MB. Append the letter <code>k</code> or <code>K</code> to indicate kilobytes, or <code>m</code> or <code>M</code> to indicate megabytes. The default value is chosen at runtime based on system configuration. See <i>Garbage Collector Ergonomics</i> at <a rel="nofollow" href="http://docs.oracle.com/javase/7/docs/technotes/guides/vm/gc-ergonomics.html">http://docs.oracle.com/javase/7/docs/technotes/guides/vm/gc-ergonomics.html</a> </p>
<p> Examples: </p>
<pre><code>-Xms6291456
-Xms6144k
-Xms6m</code></pre>
<dt>-Xmxn</p>
<dd>Specifies the maximum size, in bytes, of the memory allocation pool. This value must a multiple of 1024 greater than 2 MB. Append the letter <code>k</code> or <code>K</code> to indicate kilobytes, or <code>m</code> or <code>M</code> to indicate megabytes. The default value is chosen at runtime based on system configuration. </p>
<p> For server deployments, <code>-Xms</code> and <code>-Xmx</code> are often set to the same value. See <i>Garbage Collector Ergonomics</i> at <a rel="nofollow" href="http://docs.oracle.com/javase/7/docs/technotes/guides/vm/gc-ergonomics.html">http://docs.oracle.com/javase/7/docs/technotes/guides/vm/gc-ergonomics.html</a> </p>
<p> Examples: </p>
<pre><code>-Xmx83886080
-Xmx81920k
-Xmx80m</code></pre>
<p>On Solaris 7 and Solaris 8 SPARC platforms, the upper limit for this value is approximately 4000 m minus overhead amounts. On Solaris 2.6 and x86 platforms, the upper limit is approximately 2000 m minus overhead amounts. On Linux platforms, the upper limit is approximately 2000 m minus overhead amounts.</p>
<dt>-Xprof</p>
<dd>Profiles the running program, and sends profiling data to standard output. This option is provided as a utility that is useful in program development and is not intended to be used in production systems.</p>
<dt>-Xrs</p>
<dd>Reduces use of operating-system signals by the Java VM. </p>
<p> In an earlier release, the Shutdown Hooks facility was added to enable orderly shutdown of a Java application. The intent was to enable user cleanup code (such as closing database connections) to run at shutdown, even if the Java VM terminates abruptly. </p>
<p> The Java VM catches signals to implement shutdown hooks for unexpected Java VM termination. The Java VM uses <code>SIGHUP</code>, <code>SIGINT</code>, and <code>SIGTERM</code> to initiate the running of shutdown hooks. </p>
<p> The JVM uses a similar mechanism to implement the feature of dumping thread stacks for debugging purposes. The JVM uses <code>SIGQUIT</code> to perform thread dumps. </p>
<p> Applications embedding the Java VM frequently need to trap signals such as <code>SIGINT</code> or <code>SIGTERM</code>, which can lead to interference with the Java VM signal handlers. The <code>-Xrs</code> command-line option is available to address this issue. When <code>-Xrs</code> is used on the Java VM, the signal masks for <code>SIGINT</code>, <code>SIGTERM</code>, <code>SIGHUP</code>, and <code>SIGQUIT</code> are not changed by the Java VM, and signal handlers for these signals are not installed. </p>
<p> There are two consequences of specifying <code>-Xrs</code>:</p>
<dl>
<dd>
<dl>
<dt>o</p>
<dd><code>SIGQUIT</code> thread dumps are not available.</p>
<dt>o</p>
<dd>User code is responsible for causing shutdown hooks to run, for example by calling <code>System.exit()</code> when the Java VM is to be terminated.</dl>
</dl>
<dt>-Xssn</p>
<dd>Sets the thread stack size.</p>
<dt>-XX:AllocationPrefetchStyle=n</p>
<dd>Sets the style of prefetch used during allocation. default=2.</p>
<dt>-XX:+AggressiveOpts</p>
<dd>Enables aggressive optimization.</p>
<dt>-XX:+|-DisableAttachMechanism</p>
<dd>Specifies whether commands (such as <code>jmap</code> and <code>jconsole</code>) can attach to the Java VM. By default, this feature is disabled. That is, attaching is enabled, for example: </p>
<pre><code>java -XX:+DisableAttachMechanism</code></pre>
<dt>-XXLargePageSizeInBytes=n</p>
<dd>Specifies the maximum size for large pages.</p>
<dt>-XX:MaxGCPauseMillis=n</p>
<dd>Sets a target for the maximum GC pause time. </p>
<p> This is a soft goal, and the Java VM will make its best effort to achieve it. There is no maximum value set by default.</p>
<dt>-XX:NewSize</p>
<dd>Sets the size of the young generation (nursery). Sames as <code>-Xmnsize</code>.</p>
<dt>-XX:ParallelGCThreads=n</p>
<dd>Sets the number of GC threads in the parallel collectors.</p>
<dt>-XX:PredictedClassLoadCount=n</p>
<dd>This option requires that the <code>UnlockExperimentalVMOptions</code> flag be set first. Use the <code>PredictedClassLoadCount</code> flag if your application loads a lot of classes and especially if <code>class.forName()</code> is used heavily. The recommended value is the number of classes loaded as shown in the output from <code>-verbose:class</code>. </p>
<p> Example: </p>
<pre><code>java -XX:+UnlockExperimentalVMOptions -XX:PredictedClassLoadCount=60013</code></pre>
<dt>-XX:+PrintCompilation</p>
<dd>Prints verbose output from the Java HotSpot VM dynamic runtime compiler.</p>
<dt>-XX:+PrintGCDetails -XX:+PrintGCTimeStamps</p>
<dd>Prints garbage collection output along with time stamps.</p>
<dt>-XX:SoftRefLRUPolicyMSPerMB=0</p>
<dd>This flag enables aggressive processing of software references. Use this flag if the software reference count has an impact on the Java HotSpot VM garbage collector.</p>
<dt>-XX:TLABSize=n</p>
<dd>Thread local allocation buffers (TLAB) are enabled by default in the Java HotSpot VM. The Java HotSpot VM sizes TLABs based on allocation patterns. The <code>-XX:TLABSize</code> option enables fine-tuning the size of TLABs.</p>
<dt>-XX:+UseAltSigs</p>
<dd>The Java VM uses <code>SIGUSR1</code> and <code>SIGUSR2</code> by default, which can sometimes conflict with applications that signal-chain <code>SIGUSR1</code> and <code>SIGUSR2</code>. The <code>-XX:+UseAltSigs</code> option causes the Java VM to use signals other than <code>SIGUSR1</code> and <code>SIGUSR2</code> as the default.</p>
<dt>-XX:+|-UseCompressedOops</p>
<dd>Enables compressed references in 64-bit Java VMs. </p>
<p> This option is true by default.</p>
<dt>-XX:+UseConcMarkSweepGC or -XX:+UseG1GC</p>
<dd>Enables either the Concurrent Mark Sweep (CMS) or the G1 garbage collectors.</p>
<dt>-XX:+|-UseLargePages</p>
<dd>Enables large page support. </p>
<p> Large pages are enabled by default on Solaris.</p>
<dt>-XX:+UseParallelOldGC</p>
<dd>Enables the parallel garbage collectors, which are optimized for throughput and average response time.</dl>
</dl>
<h2>Notes</h2>
<p>The <i>-version:release</i> option places no restrictions on the complexity of the release specification. However, only a restricted subset of the possible release specifications represent sound policy and only these are fully supported. These policies are: </p>
<dl>
<dd>
<dl>
<dt>1.</p>
<dd>Any version, represented by not using this option.</p>
<dt>2.</p>
<dd>Any version greater than an arbitrarily precise <i>version-i</i>d value, for example: </p>
<pre><code>&quot;1.6.0_10+&quot;</code></pre>
<p>This would utilize any version greater than 1.6.0_10. This is useful for a case where an interface was introduced (or a bug fixed) in the release specified.</p>
<dt>3.</p>
<dd>A version greater than an arbitrarily precise version-id, bounded by the upper bound of that release family, for example: </p>
<pre><code>&quot;1.6.0_10+&amp;1.6*&quot;</code></pre>
<dt>4.</p>
<dd>An <code>or</code> expressions of items 2 or 3, for example: </p>
<pre><code>&quot;1.6.0_10+&amp;1.6* 1.7+&quot;</code></pre>
<p>Similar to item 2. This is useful when a change was introduced in a release (1.7) but also made available in updates to earlier releases.</dl>
</dl>
<h2>Performance Tuning Examples</h2>
<p>The following examples show how to use experimental tuning flags to optimize either throughput or faster response time. </p>
<h3>Example 1, Tuning for Higher Throughput</h3>
<pre><code> java -d64 -server -XX:+AggressiveOpts -XX:+UseLargePages -Xmn10g -Xms26g -Xmx26g </code></pre>
<h3>Example 2, Tuning for Lower Response Time</h3>
<pre><code> java -d64 -XX:+UseG1GC -Xms26g Xmx26g -XX:MaxGCPauseMillis=500 -XX:+PrintGCTimeStamps </code></pre>
<h2>Exit Status</h2>
<p>The following exit values are typically returned by the launcher, typically when the launcher is called with the wrong arguments, serious errors, or exceptions thrown from the Java Virtual Machine. However, a Java application may choose to return any value using the API call <code>System.exit(exitValue)</code>. </p>
<dl>
<dd>
<dl>
<dt>o</p>
<dd><code>0</code>: Successful completion</p>
<dt>o</p>
<dd><code>&gt;0</code>: An error occurred</dl>
