<h2 class="name">NAME</h2>
<p> jigdo-file &#8211; Prepare files for Jigsaw Download (distribution of huge files, e.g. CD images). </p>
<h2>SYNOPSIS</h2>
<p> <code>jigdo-file</code> <i> COMMAND</i> [ <code>&#8211;image=</code><i>cdrom.iso</i> ] [ <code>&#8211;jigdo=</code><i>cdrom.jigdo</i> ] [ <code>&#8211;template=</code><i>cdrom.template</i> ] [ <code>&#8211;force</code> ] [ <code>MORE OPTIONS</code> ] [ <i>FILES</i><i> &#8230;</i> | <code>&#8211;files-from=</code><i>f</i> ]<br />
&nbsp;<wbr><code>Common COMMANDs: make-template, make-image, verify</code> </p>
<h2>DESCRIPTION</h2>
<p> Jigsaw Download, or short jigdo, is a scheme developed primarily to make it easy to distribute huge filesystem images (e.g. CD (ISO9660) or DVD (UDF) images) over the internet, but it could also be used for other data which is awkward to handle due to its size, like audio/video files or large software packages. </p>
<p> jigdo tries to ensure that the large file (always called <i>image</i> from now on) is downloaded in small parts which can be stored on different servers. People who want to download the image do so by telling the <code><a href="/docs/linux/man/1-jigdo/">jigdo</a></code>(1) <code>(NOT IMPLEMENTED YET)</code> download tool to process one `<i>.jigdo</i>&#8216; file; using it, <code>jigdo</code> downloads the parts and reassembles the image. <code>jigdo-file</code> is used to prepare the files for download. </p>
<p> What makes jigdo special is that the parts that are used to reconstruct the image can have any size and content &#8211; they only need to be contained in a contiguous region anywhere in the image. </p>
<p> For example, if you wish to distribute an ISO9660 image which contains a snapshot of an FTP server, you can instruct <code>jigdo-file</code> to prepare the download data in such a way that when people use <code>jigdo</code> to download the image, <code>jigdo</code> actually fetches the individual files from the FTP server and assembles them into an exact copy of your image &#8211; during the download! (If the image is not a filesystem dump, you can use <code><a href="/docs/linux/man/1-split/">split</a></code>(1) to create the small parts that the image will be reassembled from.) </p>
<p> You are completely free to choose where the individual parts of the image are stored: They may be in entirely different directories on different servers (e.g. because of storage/bandwidth constraints), but this is invisible to the people downloading your image. The information about available servers only needs to be added to the `<i>.jigdo</i>&#8216; file by you before distributing it. </p>
<p> The `DETAILS&#8217; section below contains technical details on how jigdo works. The `EXAMPLES&#8217; section lists a number of common scenarios and may help you to get an idea of what jigdo is useful for.</p>
<h2>OPTIONS</h2>
<p> Many options are specific to a particular <i>COMMAND</i>; the ones below are general or used by several commands. Further options are listed below with the individual commands. All options are silently ignored if they are not applicable to the current command. For any <i>BYTES</i> parameters to options, you can append one of the letters `k&#8217;, `M&#8217; or `G&#8217; to the amount you specify, to indicate kilobytes, megabytes or gigabytes.</p>
<dl>
<dt><code>-h &#8211;help</code></p>
<dd> Output short summary of commands and options.</p>
<dt><code>-H &#8211;help-all</code></p>
<dd> Output complete summary of commands and options.</p>
<dt><code>-v &#8211;version</code></p>
<dd> Output program version.</p>
<dt><code>-i &#8211;image=</code><i>cdrom.iso</i></p>
<dd> Specify location of the file containing the image. The image is the large file that you want to distribute.</p>
<dt><code>-j &#8211;jigdo=</code><i>cdrom.jigdo</i></p>
<dd> Specify location of the Jigsaw Download description file. The jigdo file is a human-readable file generated by <code>jigdo-file</code>, to which you add information about all the servers you are going to upload the files to. <code>jigdo</code> will download this file as the first step of retrieving the image.</p>
<dt><code>-t &#8211;template=</code><i>cdrom.template</i></p>
<dd> Specify location of the image `template&#8217; file. The template file is a binary file generated by <code>jigdo-file</code>, it contains information on how to reassemble the image and also (in compressed form) all the data from the image which was not found in any of the parts. </p>
<p> Depending on the command, each of these three files is used sometimes for input, sometimes for output. If the file is to be used for output for a particular command and the output file already exists, <code>jigdo-file</code> exits with an error, unless <code>&#8211;force</code> is present. </p>
<p> In most cases, you will only need to specify one out of <code>-i</code> <code>-j</code> <code>-t</code>, because any missing filenames will be deduced from the one you specify. This is done by first stripping any extension from the supplied name and then appending nothing (if deducing <code>&#8211;image</code>), `<i>.jigdo</i>&#8216; or `<i>.template</i>&#8216;.</p>
<dt><code>-r &#8211;report=default|noprogress|quiet|grep</code></p>
<dd> Control how verbose the program is, and what format the output has: <code>noprogress</code> is the same as <code>default</code> except that no `x% done&#8217; progress messages are printed. <code>quiet</code> restricts the output to what is absolutely necessary, mostly error messages. <code>grep</code> is only different from <code>default</code> for the <code>make-template</code> command: It enables output in a simple `<i>&lt;offset&gt; &lt;file&gt;</i>&#8216; format which is useful when searching for binary files in other binary files.</p>
<dt><code>-f &#8211;force</code></p>
<dd> Overwrite existent output files without complaining.</p>
<dt><code>&#8211;no-force</code></p>
<dd> <code>This is the default.</code> Refuse to overwrite existent output files.</p>
<dt><code>-c &#8211;cache=</code><i>jigdo-cache.db</i></p>
<dd> <code>jigdo-file</code> usually needs to read the entire contents of all the <i>FILES</i> you specify. If you use it repeatedly (e.g. because you make a new CD image available daily), caching the file information will increase the program&#8217;s speed significantly. The cache file is automatically created if it is not yet present. Data is usually both read from and written to it.</p>
<dt><code>&#8211;no-cache</code></p>
<dd> <code>This is the default.</code> Do not use a cache.</p>
<dt><code>&#8211;cache-expiry=</code><i>SECONDS</i></p>
<dd> Set maximum age of cache entries. Any entries older than this will be removed from the cache. The default is 30 days. You can append one of the letters `h&#8217;, `d&#8217;, `w&#8217;, `m&#8217;, `y&#8217; to denote hours, days, weeks, months or years, respectively. A value of `0&#8242; or `off&#8217; disables expiry, so that all entries will stay in the cache forever. See the section `CACHE FILES&#8217; below for more information.</p>
<dt><code>&#8211;readbuffer=</code><i>BYTES</i></p>
<dd> Set size of internal buffers. The default is 128k &#8211; if you have a fast disc, increasing this value may make <code>jigdo-file</code> faster, but in general, changing it is not necessary.</p>
<dt><code>&#8211;md5-block-size=</code><i>BYTES</i></p>
<dd> <code>Uninteresting internal parameter.</code> Set size of blocks into which files are subdivided. The default is 128k. If you change it, any cache file will have to be regenerated. Internally, <code>jigdo-file</code> may choose to use a slightly larger or smaller value.</p>
<dt><code>-T &#8211;files-from=</code><i>file</i></p>
<dd> Read file and directory names from the specified file. If <i>file</i> is `-&#8216;, read names from standard input. Each line in the file is taken as a name, so the names may contain spaces, but not newline characters. An empty line causes <code>jigdo-file</code> to stop reading from the file. </p>
<p> <code><a href="/docs/linux/man/1-find/">find</a></code>(1) is a powerful tool for generating file lists, but make sure to use `<code>find -type f</code>&#8216; if possible &#8211; otherwise, if you instruct <code>find</code> to output both a filename and a symlink to that filename, <code>jigdo-file</code> will read the file contents twice.</p>
<dt><code>&#8211;hex</code></p>
<dd> Output checksums in hexadecimal instead of Base64-like format. This should not be used with the <code>make-template</code> command, because the resulting `<i>.jigdo</i>&#8216; file violates the `<i>.jigdo</i>&#8216; file format. Its intended use is to make <code>jigdo-file</code> more interoperable with other Unix shell utilities like <code><a href="/docs/linux/man/1-md5sum/">md5sum</a></code>(1).</p>
<dt><code>&#8211;no-hex</code></p>
<dd> <code>This is the default.</code> Use jigdo&#8217;s own Base64-like encoding of checksums.</p>
<dt><code>&#8211;debug[=help|=all|=</code><i>UNIT,~UNIT&#8230;</i><code> ]</code></p>
<dd> Switch on or off debugging output. Just `&#8211;debug&#8217; is equivalent to `&#8211;debug=all&#8217;. The argument is a comma-separated list of unit names for which debugging output is to be enabled, or disabled if the name is preceded by `~&#8217;. The special name `all&#8217; means all units. By default, debugging output is switched off except for the units `assert&#8217; and `general&#8217;. The exact list of available units for which debugging can be switched on depends on whether jigdo was compiled with debugging support &#8211; the list can be printed with `&#8211;debug=help&#8217;.</p>
<dt><i>FILES</i></p>
<dd> Names of files or directories to use as input. These are the parts that are contained in the image. In case one of the names is a directory, the program recursively scans the directory and adds all files contained in it. While doing this, it follows symbolic links, but avoids symlink loops. </p>
<p> If one of the filenames starts with the character `-&#8216;, you must precede the list of files with `&#8211;&#8216;. A value of `-&#8216; has <code>no</code> special meaning in this list, it stands for a file whose name is a single hyphen.</dl>
<h2>COMMANDS</h2>
<p> The command name is the first non-option argument passed to <code>jigdo-file</code>. Most commands have short abbreviations as well as long names. <code>The short command names should not be used in scripts &#8211; there may be incompatible changes to them in the future!</code></p>
<h3>MAKE-TEMPLATE, MT</h3>
<p> Reads <i>image</i> and <i>FILES</i>, creates `<i>.jigdo</i>&#8216; and `<i>.template</i>&#8216;. This is the main functionality of <code>jigdo-file</code>. </p>
<p> It is possible to specify both <code>&#8211;image=-</code> and <code>&#8211;files-from=-</code>. In this case, first the list of files is read from standard input until an empty line is encountered. Everything following it is assumed to be the image data. This can be useful if you use <code><a href="/docs/linux/man/1-mkisofs/">mkisofs</a></code>(1) or similar programs that can output the complete image on their standard output, because there is no need to store the image on disc temporarily. </p>
<p> If a <i>FILES</i> argument contains the characters `//&#8217; (Unix) or `\.\&#8217; (Windows), this has special meaning. In the final jigdo file that users will download, each of the parts is referenced in the `[Parts]&#8217; section with a URI of the form `Label:some/filename&#8217;. (See `FORMAT OF .JIGDO FILES&#8217; below for a detailed description.) The `[Servers]&#8217; section gives a mapping of labels to servers on the internet, with lines like `Label=<a rel="nofollow" href="http://myserver.org/jigdofiles/'.">http://myserver.org/jigdofiles/&#8217;.</a> Using this information, <code>jigdo</code> will create the final download URI for the part, `<a rel="nofollow" href="http://myserver.org/jigdofiles/some/filename'.">http://myserver.org/jigdofiles/some/filename&#8217;.</a> Specifying `//&#8217; (or `\.\&#8217;) in a file or directory name serves to `cut off&#8217; the names at the right directory level. For example, if the Unix path of one of your <i>FILES</i> is `/path/some/filename&#8217;, you can tell <code>jigdo-file</code> to cut off after the `/path&#8217; by passing it the argument `/path//some/filename&#8217;, or `/path//&#8217; if you want the whole directory scanned. The path names need not be absolute; `somedirectory//&#8217; is also possible.</p>
<dl>
<dt><code>&#8211;label </code><i>Label=/path</i></p>
<dd> Specify a name to use as the label name for a path on disc. (Influences the output jigdo file.) If you used `//&#8217; in the <i>FILES</i> arguments as described above, <code>jigdo-file</code> will by default pick label names automatically (`A&#8217;, `B&#8217; etc.). With this option, you can give labels more meaningful names. Note that the label name will only be used if one or more <i>FILES</i> begin with `/path//&#8217;. </p>
<p> Try to use label names that start with uppercase characters, to disambiguate them clearly from protocol names like `http&#8217;, `ftp&#8217;.</p>
<dt><code>&#8211;uri </code><i>Label=<a rel="nofollow" href="http://some.server.org/">http://some.server.org/</a></i></p>
<dd> By default, using <code>&#8211;label</code> as described above will cause lines of the form `Label=file:/path/&#8217; to be written to the `[Servers]&#8217; section of the output jigdo file. If you want to override the `file:&#8217; URI so that the line reads `Label=<a rel="nofollow" href="http://some.server.org/',">http://some.server.org/&#8217;,</a> you can do so by specifying <code>&#8211;uri</code> along with <code>&#8211;label</code>. Giving just <code>&#8211;uri </code><i>Label=&#8230;</i> without the corresponding <code>&#8211;label </code><i>Label=&#8230;</i> has no effect, and even if you specify both, an entry is only added to the `[Servers]&#8217; section if the label is referenced by at least one `[Parts]&#8217; entry. </p>
<p> The supplied value is not quoted by the program; if it contains characters such as space or any of the characters #&quot;&#8217;\ then you must quote it. (Under Unix, you may need to quote the value twice to also protect it from the shell, e.g. \\ or &#8216;\&#8217; to get a single backslash in the URI.) </p>
<p> The mapping specified with an <code>&#8211;uri</code> option is ignored if it is already present in the output jigdo file. </p>
<p> Users of the Windows version may notice that the `\&#8217; directory separators are converted into `/&#8217; in the `file:&#8217; URIs that are generated by default. This is done to increase cross-platform compatibility of `file:&#8217; &#8211; the <code>print-missing</code> command of the Windows version will automatically re-convert the characters when it prints the URIs. In case you supply your own `file:&#8217; URIs under Windows using <code>&#8211;uri</code>, you must also exchange `/&#8217; and `\&#8217;.</p>
<dt><code>-0 to -9</code></p>
<dd> Set amount of compression in the output template file, from <code>-0</code> (no compression) to <code>-9</code> (maximum compression). The default is <code>-9</code>, which can make the template generation quite slow. By default, the compression algorithm used is the same as for <code><a href="/docs/linux/man/1-gzip/">gzip</a></code>(1).</p>
<dt><code>&#8211;gzip and &#8211;bzip2</code></p>
<dd> Choose between the gzip and bzip2 compression algorithms. The default is gzip. Bzip2 usually gives a better compression ratio, but compression is significantly slower than with gzip.</p>
<dt><code>&#8211;min-length=</code><i>BYTES</i></p>
<dd> Set minimum length of a part for <code>jigdo-file</code> to look for it in the image. The default is 1k. Parts smaller than this will never be found in the image, so their data will be included in the template file. The search algorithm used requires such a minimum length, otherwise template generation could become extremely slow. If you know for sure that all your <i>FILES</i> are larger than a certain amount, you can increase <code>jigdo-file</code>&#8216;s speed slightly by specifying the amount with this option. There is a hard-wired absolute minimum of 256 bytes &#8211; anything lower will silently be set to 256.</p>
<dt><code>&#8211;merge=</code><i>FILE</i></p>
<dd> Include the contents of <i>FILE</i> in the output `<i>.jigdo</i>&#8216; file. The file can contain data which you want added to the output (for example, a `[Servers]&#8217; section with a list of your servers as entries), or it can be the jigdo file output by an earlier run of <code>jigdo-file</code>. </p>
<p> It is possible to specify the same file for input with <code>&#8211;merge</code> and for output with <code>&#8211;jigdo</code>. However, you will also need to use <code>&#8211;force</code> to make the program overwrite the old version of the jigdo file with the new one. <i>FILE</i> can be `-&#8216; for standard input. </p>
<p> When <code>adding</code> new information to the supplied file, <code>jigdo-file</code> will not insert new lines into the `[Parts]&#8217; section if an entry for the same MD5 checksum (but not necessarily with the same URI!) already exists, and it will not insert new lines into the `[Servers]&#8217; section if a completely identical entry already exists. </p>
<p> When <code>reading in</code> the existing <i>FILE</i>, the behaviour is slightly different: The program <code>preserves</code> entries in the `[Parts]&#8217; section with identical checksum, but different URIs. For completely identical entries (same checksum and URI), only one entry is preserved and the duplicates are removed. The `[Servers]&#8217; section is left untouched.</p>
<dt><code>&#8211;image-section</code></p>
<dd> <code>This is the default.</code> Causes <code>jigdo-file</code> to add an `[Image]&#8217; section to the `<i>.jigdo</i>&#8216; file. </p>
<p> As an exception, a new `[Image]&#8217; section is <code>not</code> added if you use <code>&#8211;merge</code> and the file to merge contains an `[Image]&#8217; section with a line which reads `Template-MD5Sum=&#8217; (end of line after the `=&#8217;). In this case, the generated template data&#8217;s MD5 checksum value is just added after the `=&#8217; of the first line of this form in the file &#8211; no whole new `[Image]&#8217; section is appended. This behaviour is useful because it allows you to pass via <code>&#8211;merge</code> an `[Image]&#8217; section with arbitrary content and then have the MD5 checksum automatically added by <code>jigdo-file</code>. The section `FORMAT OF `[Image]&#8217; section contents in greater detail.</p>
<dt><code>&#8211;no-image-section</code></p>
<dd> Do <code>not</code> include an `[Image]&#8217; section in the `<i>.jigdo</i>&#8216; file. You need to add one yourself if you use this option. However, doing that is not easy (you also need to add a `Template-MD5Sum&#8217; line with the correct checksum, or <code>jigdo</code> will complain), so use of this option is discouraged.</p>
<dt><code>&#8211;servers-section</code></p>
<dd> <code>This is the default.</code> Causes <code>jigdo-file</code> to add a `[Servers]&#8217; section to the `<i>.jigdo</i>&#8216; file. This default section uses `file:&#8217; URIs, which allows for immediate reassembly of the image from the local filesystem, and is also useful if you want to edit the file manually and replace the `file:&#8217; URIs with other URIs.</p>
<dt><code>&#8211;no-servers-section</code></p>
<dd> Do <code>not</code> add a `[Servers]&#8217; section at the end of the `<i>.jigdo</i>&#8216; file. Useful e.g. if you are going to append the section with a script.</p>
<dt><code>&#8211;match-exec=</code><i>SHELLCOMMAND</i></p>
<dd> Whenever a file is found in the image, execute the supplied command string by passing it to a shell. <code>jigdo-file</code> sets up a number of environment variables with information about the file match. For example, if the file `<i>/path//a/b/file</i>&#8216; was found in the image and `Label:a/b/file&#8217; is going to be written to the `<i>.jigdo</i>&#8216; file:</p>
<dl>
<dt>
<dd>
<dl>
<dt>*</p>
<dd> <code>LABEL</code>=&quot;Label&quot; &#8211; Name of the label for the file. The example assumes that `<code>&#8211;label</code> Label=/path&#8217; was specified by you. In the absence of such an option, <code>LABEL</code> will be set but empty.</p>
<dt>*</p>
<dd> <code>LABELPATH</code>=&quot;/path/&quot; &#8211; The path corresponding to the label, or in other words, the prefix of the matched file&#8217;s path that will <code>not</code> appear in the output `<i>.jigdo</i>&#8216; file. Is set even without any `<code>&#8211;label</code>&#8216; option present. Ends with a slash.</p>
<dt>*</p>
<dd> <code>MATCHPATH</code>=&quot;a/b/&quot; &#8211; The rest of the path, without the leafname of the matched file. Is either empty or ends with a slash.</p>
<dt>*</p>
<dd> <code>LEAF</code>=&quot;file&quot; &#8211; The leafname of the matched file.</p>
<dt>*</p>
<dd> <code>MD5SUM</code>=&quot;lNVdUSqbo2yqm33webrhnw&quot; &#8211; The md5sum of the matched file, in Base64-like format.</p>
<dt>*</p>
<dd> <code>FILE</code>=&quot;/path//a/b/file&quot; &#8211; For convenience, the complete path of the file. The variable is always set to $LABELPATH$MATCHPATH$LEAF.</dl>
</dl>
<p> Please be careful to correctly quote the string passed to this option, otherwise your supplied command will not work with filenames that contain spaces. As an example, to create a backup of hard links to the matched files, use the following option: &#8211;match-exec=&#8217;mkdir -p &quot;${LABEL:-.}/$MATCHPATH&quot; &amp;&amp; ln -f &quot;$FILE&quot; &quot;${LABEL:-.}/$MATCHPATH$LEAF&quot;&#8217; </p>
<p> By default, no command is executed. Use &#8211;match-exec=&quot;&quot; to remove a command string which was set with an earlier use of this option.</p>
<dt><code>&#8211;greedy-matching</code></p>
<dd> <code>This is the default.</code> Imagine that your image contains a <i>.tar</i> file which in turn contains another file <i>x</i>, and that you provide both the <i>.tar</i> and the files inside it on the command line. When <code>jigdo-file</code> scans the image, it encounters the beginning of the <i>.tar</i> file, and then the file <i>x</i>. </p>
<p> At this point, a decision must be made: Should the smaller file <i>x</i> be recorded as matched, or should it be ignored in favour of the larger (and thus better) match of the <i>.tar</i> file? Unfortunately, at this point it is not clear whether there will actually be a full match of the <i>.tar</i>, so by default, the program prefers the small match.</p>
<dt><code>&#8211;no-greedy-matching</code></p>
<dd> In the case where a large partial match is present and a shorter match has been confirmed, ignore the small match. (See the option above.)</dl>
<h3>MAKE-IMAGE, MI</h3>
<p> Reads `<i>.template</i>&#8216; and <i>FILES</i>, creates <i>image</i> (or `<i>imagename.tmp</i>&#8216;). Provides a rudimentary way of reassembling images &#8211; <code>jigdo</code> is usually better suited for this task. However, in contrast to <code>jigdo</code>, no `<i>.jigdo</i>&#8216; file is required. </p>
<p> If the image is to be written to a file (and not to standard output), it is possible to create the image in several steps, with several invocations of `<code>jigdo-file make-image</code>&#8216;, as follows: You first invoke <code>jigdo-file</code>, specifying as many files as are available at this time. The program scans the files, and those that are contained in the image are copied to a temporary file, whose name is formed by appending `<i>.tmp</i>&#8216; to the image filename. </p>
<p> For all further files which could be parts of the image, you repeat this process. As soon as all parts are present, the temporary file will be truncated slightly (to delete some administrative data that <code>jigdo-file</code> appends at the end) and renamed to the final image name. The possibility of reassembling the image in several steps is especially useful for gathering files from removable media, e.g. several older CDs. </p>
<p> Scripts using <code>make-image</code> can detect whether image creation is complete by checking the exit status: 0 signals successful creation, whereas 1 means that more files need to be supplied. Other errors result in an exit status of 2 (`recoverable&#8217;, e.g. file not found) or 3 (non-recoverable, e.g. write error).</p>
<dl>
<dt><code>&#8211;check-files</code></p>
<dd> <code>This is the default.</code> Whenever any part is copied to the image, re-check its checksum against the checksum stored in the template. It is recommended that you leave this switched on, even if it slows down image creation a bit.</p>
<dt><code>&#8211;no-check-files</code></p>
<dd> Do not check files&#8217; checksums when copying them to the image. This can be safely used when no cache file is used (which means that files will be written to the image immediately after being scanned) or the whole image is checked later with the <code>verify</code> command.</dl>
<h3>PRINT-MISSING, PM</h3>
<p> Reads `<i>.jigdo</i>&#8216;, `<i>.template</i>&#8216; and (if present) `<i>imagename.tmp</i>&#8216;, outputs a list of URIs still needed to completely reassemble the image. </p>
<p> Together with the <code>make-image</code> command, this provides most of the functionality of <code>jigdo</code> on the command line. </p>
<p> For each part that is not yet present in the temporary image file, the file checksum is looked up in the `[Parts]&#8217; section of the jigdo file. Any label in the corresponding entry is then expanded according to the label definitions in the `[Servers]&#8217; section and printed on standard output. <code>jigdo</code> allows you to specify several alternative locations for each label in this section, but <code>print-missing</code> will only output the first one for each missing part. </p>
<p> If the checksum cannot be found in the `[Parts]&#8217; section (this Should Not Happen unless you deleted that section), a lookup is instead made for `MD5Sum:<i>&lt;checksum&gt;</i>&#8216;, just like with <code>jigdo</code>. (Thus, if you want to get rid of the `[Parts]&#8217; section, you can do so if you rename each part to its own checksum.)</p>
<dl>
<dt><code>&#8211;uri </code><i>Label=<a rel="nofollow" href="http://some.server.org/">http://some.server.org/</a></i></p>
<dd> Override the entries in the `<i>.jigdo</i>&#8216; file for any label with a URI of your choice. With the example above, a `[Parts]&#8217; entry of `Label:some/filename&#8217; will cause the line `<a rel="nofollow" href="http://some.server.org/some/filename'">http://some.server.org/some/filename&#8217;</a> to be printed. </p>
<p> The supplied value is not quoted by the program; if it contains characters such as space or any of the characters #&quot;&#8217;\ then you must quote it. (Under Unix, you may need to quote the value twice to also protect it from the shell, e.g. \\ or &#8216;\&#8217; to get a single backslash in the URI.)</dl>
<h3>PRINT-MISSING-ALL, PMA</h3>
<p> Just like <code>print-missing</code>, this command outputs a list of URIs still needed to completely reassemble the image. However, <code>all</code> alternative download locations are printed instead of just one. In the output, the URIs for a file are separated from other files&#8217; URIs with blank lines. The <code>&#8211;uri</code> option has the same effect as for <code>print-missing</code>.</p>
<h3>VERIFY, VER</h3>
<p> Reads <i>image</i> (presumably generated with <code>make-image</code>) and `<i>.template</i>&#8216;, checks for correct checksum of image. </p>
<p> The template data does not only contain checksums of the individual parts, but also of the image as a whole. <code>make-image</code> already performs a number of internal checks, but if you like, you can additionally check the image with this command.</p>
<h3>SCAN, SC</h3>
<p> Reads all the <i>FILES</i> and enters them into the cache, unless they are already cached. The <code>&#8211;cache</code> option must be present for this command.</p>
<dl>
<dt><code>&#8211;no-scan-whole-file</code></p>
<dd> <code>This is the default.</code> This only causes the first <code>&#8211;md5-block-size</code> bytes of each file to be read. If the cache is used later by <code>jigdo-file make-image</code>, the rest of the file will be read once these first bytes are recognized in the input image.</p>
<dt><code>&#8211;scan-whole-file</code></p>
<dd> Immediately read the entire file contents and store them in the cache.</dl>
<h3>MD5SUM, MD5</h3>
<p> Reads all the <i>FILES</i> and prints out MD5 checksums of their contents. This command is quite similar to <code><a href="/docs/linux/man/1-md5sum/">md5sum</a></code>(1), except that the checksum is output in the Base64-like encoding which is also used elsewhere by <code>jigdo-file</code>. </p>
<p> The <i>FILES</i> arguments are processed in the same way as with the other commands, which means that recursion automatically takes place for any arguments that are directories, and that symbolic links are not listed except when the file(s) they point to are not reachable directly. </p>
<p> In the checksum list printed on standard output, only the part of the filename following any `//&#8217; (or `\.\&#8217; on Windows) is printed. Any <code>&#8211;cache</code> will be used for querying files&#8217; MD5 checksums and/or writing the checksums of scanned files.</p>
<h3>LIST-TEMPLATE, LS</h3>
<p> Reads a `<i>.template</i>&#8216; file and outputs low-level information about the image and all parts contained in it, including offset, length and checksum. </p>
<p> You can also use this command with temporary image files (by specifying something like <code>&#8211;template=imagename.tmp</code>) &#8211; in that case, the output also distinguishes between parts that have been written to the image and parts that haven&#8217;t. </p>
<p> The exact output format may change incompatibly between different jigdo releases. The following different types of lines can be output. `have-file&#8217; only occurs for `<i>.tmp</i>&#8216; files, indicating a file that has already been successfully written to the temporary file: </p>
<pre>
in-template <i>offset-in-image length</i>
need-file <i>offset-in-image length file-md5sum filestart-rsyncsum</i>
have-file <i>offset-in-image length file-md5sum filestart-rsyncsum</i>
image-info <i>image-length image-md5sum rsyncsum-size</i>
</pre>
<h2>DETAILS</h2>
<p> Jigsaw Download was created with the format of ISO9660 CD images in mind &#8211; however, the following also applies to many other filesystem formats, as well as to `tar&#8217; archives and uncompressed `zip&#8217; archives. A CD image contains both information for organizing the filesystem (header with disc name etc., ISO9660 directory data, data of extensions such as Joliet or RockRidge, zero padding) and the files contained on the CD. An important property that jigdo relies on is that each file is stored in one contiguous section of the image; it is not split into two or more parts. </p>
<p> When <code>jigdo-file</code> is given a number of files that might be contained in an image, it detects whether any of the files are present using a `rolling checksum&#8217; inspired by the one used by <code><a href="/docs/linux/man/1-rsync/">rsync</a></code>(1). The resulting data is written to the `<i>.template</i>&#8216; file: If a section of the image could not be matched (e.g. it was directory information), the data is compressed and written directly to the template. However, if a matching file was found, its data is omitted from the template. Instead, only a reference (an MD5 checksum of the file) is inserted in the template. </p>
<p> Note that the template data only contains binary data, it does not contain any filenames or URIs, since it cannot be easily edited in case any of these values need to be changed. All that information is stored in the `<i>.jigdo</i>&#8216; file, a text file to which you can add URLs for your server(s). The jigdo file provides a mapping for each MD5 checksum to one or more alternative download locations for the corresponding part. </p>
<p> Apart from the mapping of MD5 sums to URIs, the jigdo file also contains an URI pointing to a download location for the template file. This way, the <code>jigdo</code> download tool only needs to be given one URI (that of the `<i>.jigdo</i>&#8216; file) to be able to download and reassemble the complete image.</p>
<h2>FORMAT OF .JIGDO FILES</h2>
<p> The overall format of `<i>.jigdo</i>&#8216; files follows that of `<i>.ini</i>&#8216; files, as also used by the Gnome and KDE projects for some data. The file is organized into sections, each of which is preceded by a line reading `[Sectionname]&#8217;. Within each section, lines have the form `Label=Value&#8217;. Such lines are also called `entries&#8217; below. All `<i>.jigdo</i>&#8216; files use UTF-8 as their character encoding. </p>
<p> Comments are introduced with the `#&#8217; character and extend to the end of the line. Whitespace is ignored at line start and end as well as to the left and right of section names and the `=&#8217; in entries. Furthermore, the jigdo utilities split up the text of the entry value (i.e. the part after the `=&#8217;) into whitespace-separated words, much like the Unix shell. Single &#8221; and double &quot;&quot; quotes can be used to prevent that e.g. URIs containing whitespace are split apart. Similarly, characters with special meaning (the characters &#8216;&quot;#\ and space/tab) must be quoted with \ to appear in the value. As with the shell, there is a difference between &#8216;~&#8217; and &quot;~&quot;: Within &#8216;~&#8217;, the characters &quot;#\ and whitespace lose their special meaning and become ordinary characters, whereas within &quot;~&quot;, only the characters &#8216;# and whitespace lose their special meaning &#8211; in other words, backslash escapes still work inside &quot;~&quot;, but not &#8216;~&#8217;. </p>
<p> `<i>.jigdo</i>&#8216; files can optionally be compressed with <code><a href="/docs/linux/man/1-gzip/">gzip</a></code>(1). <code>jigdo-file</code> always outputs uncompressed files, which you can compress yourself. <code>jigdo-lite</code> supports single uncompressed and compressed files. </p>
<p> (Behaviour which may change in the future and which should not be relied upon: <code>jigdo</code> additionally supports any number of concatenated plaintext and gzipped parts in the files &#8211; for example, you can compress a `<i>.jigdo</i>&#8216; file and then add a couple of lines of uncompressed data to the end.) </p>
<p> In all cases, the `<i>.gz</i>&#8216; extension should be removed from the filename &#8211; the tools will determine automatically from the file contents whether a file is compressed or not. </p>
<p> Below is a description of the individual section names used by jigdo.</p>
<h3>JIGDO SECTION</h3>
<pre>
[Jigdo]
Version=1.1
Generator=jigdo-file/1.0.0
</pre>
<p> Information about the version of the jigdo file format used, and the program that generated it. There should be one such section per `<i>.jigdo</i>&#8216; file.</p>
<h3>IMAGE SECTION</h3>
<pre><code>
[Image] Filename = "filename for saving on user's disc" Template = "URI where to fetch template file" Template - MD5Sum = OQ8riqT1BuyzsrT9964A7g
                                                                       ShortInfo = single - line description of the image(200 characters max.)
                                                                                                Info = long description(5000 characters max.)
</code></pre>
<p> The value for the `Template&#8217; entry can be either an URL (absolute or relative to the URL of the jigdo file) or a string of the form `<i>Label</i>:<i>pathname</i>&#8216; (<code>UNIMPLEMENTED</code>), as described below. </p>
<p> The `Template-MD5Sum&#8217; entry is added by <code>jigdo-file</code> and specifies the MD5 checksum of the generated `<i>.template</i>&#8216; file. It is used by <code>jigdo</code> to detect cases where the downloaded template data is corrupted or belongs to a different image. </p>
<p> Unlike other entry values, the values of the `ShortInfo&#8217; and `Info&#8217; entries are <code>not</code> split up into words, instead all quoting is preserved. </p>
<p> The value of the `Info&#8217; entry is special in that <code><a href="/docs/linux/man/1-jigdo/">jigdo</a></code>(1) can optionally parse XML markup it contains. If the markup has errors such as unbalanced/unsupported tags, the string is displayed literally, without XML parsing. Supported tags are &lt;b&gt;&lt;/b&gt; (bold), &lt;i&gt;&lt;/i&gt; (italic), &lt;tt&gt;&lt;/tt&gt; (typewriter font), &lt;u&gt;&lt;/u&gt; (underline), &lt;big&gt;&lt;/big&gt; (larger font), &lt;small&gt;&lt;/small&gt; (smaller font) and &lt;br/&gt; (linebreak). Supported entities include &amp;lt; (`&lt;&#8216;), &amp;gt; (`&gt;&#8217;) and &amp;amp; (`&amp;&#8217;). Note that the whole `Info&#8217; entry must be on one line in the jigdo file. </p>
<p> This section may occur multiple times, but all except the first one will be ignored. This is useful e.g. when creating a `<i>.jigdo</i>&#8216; file for a DVD image when you already have `<i>.jigdo</i>&#8216; files for CDs with the same content: You can simply `[Include]&#8217; (see below) the CDs&#8217; jigdo files at the end of the DVD jigdo file, after its `[Image]&#8217; section.</p>
<h3>PARTS SECTION</h3>
<pre>
[Parts]
xJNkjrq8NYMraeGavUpllw=LabelA:part0
GoTResP2EC6Lb_2wTsqOoQ=LabelA:part1
kyfebwu6clbYqqWUdFIyaw=LabelB:some/path/part2
-J9UAimo0Bqg9c0oOXI1mQ=<a rel="nofollow" href="http://some.where.com/part3">http://some.where.com/part3</a>
</pre>
<p> All lines in the section, which provides the mapping from MD5 checksums to URIs, have the same format: On the left side of the `=&#8217; the checksum (encoded with a Base64-like encoding) is given, and on the right a string corresponding to the part with this checksum; either a complete URI or a string of the form `<i>Label</i>:<i>pathname</i>&#8216;, which is expanded into one or more URIs by looking up the definition(s) for the <i>Label</i> in the `[Servers]&#8217; section. </p>
<p> In case a particular MD5 checksum cannot be found in any `[Parts]&#8217; section by <code>jigdo</code>, the program will perform a lookup for `MD5Sum:<i>&lt;checksum&gt;</i>&#8216;, e.g. for `MD5Sum:xJNkjrq8NYMraeGavUpllw&#8217; if you deleted the line for `part0&#8242; above. </p>
<p> A checksum appearing multiple times in this section indicates alternative download locations for the part. </p>
<p> There may be any number of `[Parts]&#8217; sections in the file; they are all considered when looking up MD5 checksums. </p>
<p> <code>jigdo-file</code> always puts the `[Parts]&#8217; section at the end of the file, and it even rearranges any file specified with <code>&#8211;merge</code> to have only one such section at the end. This is done to allow <code>jigdo</code> to display the information from the `[Image]&#8217; section while the rest of that file is still being downloaded.</p>
<h3>SERVERS SECTION</h3>
<pre>
[Servers]
LabelA=<a rel="nofollow" href="http://myserver.org/">http://myserver.org/</a>
LabelA=<a href="ftp://mirror.myserver.org/">ftp://mirror.myserver.org/</a>
LabelB=LabelC:subdirectory/
LabelC=<a rel="nofollow" href="http://some.where.com/jigdo/">http://some.where.com/jigdo/</a>
</pre>
<p> All lines in the section, which provides the mapping from server labels to server locations, have the same format: On the left side of the `=&#8217; the label name is given, and on the right the value to expand the label name to. </p>
<p> A label name appearing multiple times in this section indicates alternative download locations for the parts that use the label in the `[Parts]&#8217; section. This notation makes it very easy to add mirrors to the jigdo file. </p>
<p> As shown by the example above, the label values may themselves reference other labels. In this case, the entry `LabelB:some/path/part2&#8242; in the `[Parts]&#8217; section will expand to `<a rel="nofollow" href="http://some.where.com/jigdo/subdirectory/some/path/part2'.">http://some.where.com/jigdo/subdirectory/some/path/part2&#8242;.</a> Loops in the label definitions result in undefined behaviour and must be avoided. </p>
<p> There may be any number of `[Servers]&#8217; sections in the file; they are all considered when looking up labels. Either of `[Parts]&#8217; or `[Servers]&#8217;, but not both, can be omitted from the jigdo file.</p>
<h3>COMMENT SECTION</h3>
<pre>
[Comment]
Any text, except that lines must not begin with `['.
</pre>
<p> All text following a `[Comment]&#8217; or `[comment]&#8217; line is ignored, up to the next line with a section label.</p>
<h3>INCLUDE DIRECTIVE</h3>
<pre>
[Include <a rel="nofollow" href="http://some.url/file.jigdo]">http://some.url/file.jigdo]</a>
</pre>
<p> Lines of this form cause the content of the specified jigdo file to be downloaded and parsed just like the main jigdo file. The effect will be the same as copying the included file&#8217;s contents into the file which contains the include directive. (Exception: Any relative URLs are always resolved using the URL of the `<i>.jigdo</i>&#8216; file that contains that relative URL.) </p>
<p> The URL argument can be an absolute or relative URL. Relative URLs are assumed to be relative to the URL of the jigdo file which contains the include directive. Includes can be nested, but it is an error to create a loop of include directives. It is <code>not</code> possible to use URLs of the form `<i>Label</i>:<i>pathname</i>&#8216;. </p>
<p> The URL cannot be quoted with &quot;&quot;. Any `]&#8217; characters in the argument must be escaped as `%5D&#8217;, and any spaces as `%20&#8242;. </p>
<p> Include directives are only supported by <code>jigdo</code>, they are ignored by <code>jigdo-lite</code>. </p>
<p> An include directive terminates any previous section, but it does not start a new one. In other words, a new section must always be started after the include line, <code>jigdo</code> does not allow normal entries to appear below the `[Include]&#8217;.</p>
<h2>CACHE FILES</h2>
<p> Any file specified with the <code>&#8211;cache</code> option is used to store information about the <i>FILES</i> presented to <code>jigdo-file</code>. When querying the cache, a file is considered unchanged (and the cached data is used) only if filename, file size and last modification time (mtime) match exactly. For the filename match, not the entire file name is used, but only the part following any `//&#8217;, so that any changes to the part before the `//&#8217; will not invalidate the cache. </p>
<p> Old cache entries are removed from the cache if they have not been read from or written to for the amount of time specified with <code>&#8211;cache-expiry</code>. Entries are <code>not</code> immediately removed from the cache if the file they refer to no longer exists &#8211; this makes it possible to cache information about files on removable media. </p>
<p> Cache expiry only takes place <code>after</code> <code>jigdo-file</code> has done its main work &#8211; if any old entries are accessed before expiry takes place, they will be kept. For example, if the program is run using the default expiry time of 30 days, but accesses a cache file with entries generated 2 months ago, then entries in that cache <code>will</code> be considered, and only those cache entries that were not needed during the program run will be expired. </p>
<p> Due to a peculiarity of the underlying database library (libdb3), cache files never shrink, they only grow. If a large number of entries was expired from your cache file and you want it to shrink, you can either just delete it (of course then everything will have to be regenerated) or use the utilities accompanying libdb3 to dump and restore the database, with a command like `<code>db3_dump </code><i>old-cache.db</i><code> | db3_load </code><i>new-cache.db</i>&#8216;. For Debian, these programs are supplied in the package `libdb3-util&#8217;. </p>
<p> If a different <code>&#8211;md5-block-size</code> is specified, the entire file needs to be re-read to update its cache entry. If a different <code>&#8211;min-length</code> is specified, only the first `md5-block-size&#8217; bytes of the file need to be re-read.</p>
<h2>EXAMPLES</h2>
<h3>PREPARING YOUR CD IMAGE FOR DISTRIBUTION</h3>
<p> You have created a CD image `<i>image.iso</i>&#8216; from some of the files stored in the directory `<i>/home/ftp</i>&#8216; on your harddisc, which is also available online as `<a href="ftp://mysite.org'.">ftp://mysite.org&#8217;.</a> As you don&#8217;t want to waste space by effectively hosting the same data twice (once as files on the FTP server, once inside the image), and you are fed up with users&#8217; downloads aborting after 200MB and their restarting the download dozens of times, you decide to use jigdo. How do you prepare the image for download? </p>
<p> In fact, only one command is necessary: </p>
<dl>
<dt>
<dd>
<p> <code>jigdo-file make-template &#8211;image=image.iso &#8211;jigdo=/home/ftp/image.jigdo &#8211;template=/home/ftp/image.template /home/ftp// &#8211;label Mysite=/home/ftp &#8211;uri Mysite=<a href="ftp://mysite.org/">ftp://mysite.org/</a></code></dl>
<p> People can now point <code>jigdo</code> at `<a href="ftp://mysite.org/image.jigdo'">ftp://mysite.org/image.jigdo&#8217;</a> to download your image. The template file needs to be accessible as `<a href="ftp://mysite.org/image.template'.">ftp://mysite.org/image.template&#8217;.</a> </p>
<p> Note that nothing prevents you from doing the same for an FTP server that isn&#8217;t administrated by you &#8211; in that case, you only need to host the `<i>.jigdo</i>&#8216; and `<i>.template</i>&#8216; files on your own server/homepage.</p>
<h3>PREPARING AN ARBITRARY LARGE FILE FOR DISTRIBUTION</h3>
<p> We assume that you have a large file that is not a filesystem, e.g. `<i>movie.mpeg</i>&#8216;. Because of space problems, you want to distribute the data on two servers. </p>
<p> In this case, the parts of the image need to be generated artificially with the <code>split</code> command. For example, to create chunks of 4MB each, use `<code>split -b 4m movie.mpeg part</code>&#8216;. Copy the resulting files `<i>partXX</i>&#8216; into two directories `<i>1</i>&#8216; and `<i>2</i>&#8216; that you create, according to how you want the files distributed between the servers. Next, create the jigdo and template files with `<code>jigdo-file make-template &#8211;image=movie.mpeg 1// 2//</code>&#8216;. You will need to edit the `<i>.jigdo</i>&#8216; file and provide the right URIs for the two servers that you are going to upload the `<i>partXX</i>&#8216; files to.</p>
<h3>CUSTOMIZED VERSIONS OF IMAGES</h3>
<p> Because it is possible to assign a different URI for each part of an image if necessary, jigdo is very flexible. Only one example is the possibility of customized versions of images: Suppose that someone is distributing a CD image, and that you want to make a few small changes to it and redistribute your own version. You download the `<i>official.iso</i>&#8216; CD image with <code>jigdo</code> (passing it the URL of `<i>official.jigdo</i>&#8216;), write it to CD-R, make your changes (say, adding files from the `<i>myfiles</i>&#8216; directory on your harddisc) and produce your own version, `<i>myversion.iso</i>&#8216;. Next, you instruct <code>jigdo-file</code> to create the jigdo and template files for your modified image, using the command </p>
<dl>
<dt>
<dd>
<p> <code>jigdo-file make-template &#8211;image=myversion.iso /mnt/cdrom/ myfiles// &#8211;label My=myfiles/ &#8211;uri My=<a rel="nofollow" href="http://my.homepage.net/">http://my.homepage.net/</a> &#8211;merge=official.jigdo</code></dl>
<p> while `<i>official.iso</i>&#8216; is mounted under `<i>/mnt/cdrom</i>&#8216;. By using <code>&#8211;merge</code>, you have told <code>jigdo-file</code> to take the contents of `<i>official.jigdo</i>&#8216;, add to it a new `[Image]&#8217; section for `<i>myversion.iso</i>&#8216; and write the resulting jigdo file to `<i>myversion.jigdo</i>&#8216; &#8211; so now `<i>myversion.jigdo</i>&#8216; offers two images for download, the original version and your modified version. (If you do not want it to offer the official version, edit it and remove the `[Image]&#8217; section that lists `<i>official.iso</i>&#8216;.) </p>
<p> Now you can upload the `<i>.jigdo</i>&#8216; file, the `<i>.template</i>&#8216; file and also the files in `<i>myfiles</i>&#8216; to `<a rel="nofollow" href="http://my.homepage.net/'.">http://my.homepage.net/&#8217;.</a> Thus, for people to download your modified image, you do <code>not</code> need to upload the complete image contents to your web space, but only the changes you made! </p>
<p> (In case you only made very few changes, you could also omit the `myfiles&#8217; parameter in the command above, then all your changes end up in the new template file.)</p>
<h3>COMBINING MANY JIGDO-MANAGED IMAGES INTO ONE</h3>
<p> It is also no problem to combine data from several sources that use jigdo. For example, if of five different and unrelated servers each one distributes a different CD image via jigdo, you can create a customized DVD image that contains the data from all these CDs. When people use <code>jigdo</code> to download your image, the individual files on the DVD are fetched from the same sources as the original CDs. </p>
<p> Consequently, even though you will be distributing a 3.2GB file via your web space, the actual amount of data that is stored on your server will only be in the order of several MBs.</p>
<h2>BUGS</h2>
<p> For certain contents of one of the input files, most notably a sequence of zero bytes longer than <code>&#8211;min-length</code> at the start of the file and an area of zeros preceding the file data in the image, <code>jigdo-file make-template</code> may fail to find the file in the image. Unfortunately, this restriction cannot be avoided because the program could become very slow otherwise. If you use the <code>&#8211;debug</code> option, all instances of <code>jigdo-file</code> discarding possible matches are indicated by lines containing the word `DROPPED&#8217;. </p>
<p> In fact, not only all-zeroes files trigger this behaviour, but also files which contain at their start a long sequence of short identical strings. For example, both a file containing only `a&#8217; characters and one containing `abcabcabcabc&#8230;&#8217; are problematic.</p>
