<h2 class="name">NAME</h2>
<p> glilypond &#8211; integrate lilypond parts into groff </p>
<h2>SYNOPSIS</h2>
<p> [{<code>&#8211;ly2eps</code>|<code>&#8211;pdf2eps</code>}] [<code>-e</code> <i>directory</i>] [ <code>-k</code> ] [<code>-o</code> <i>output-file</i>] [<code>-p</code> <i>filename-prefix</i>] [<code>-t</code> <i>tdir</i>] [{<code>-v</code>|<code>-V</code>}] [ <code>&#8211;</code> ] [ <code>&#8212;</code> ] [<i>filespec</i> &#8230; ] [{<code>&#8211;ly2eps</code>|<code>&#8211;pdf2eps</code>}] [<code>&#8211;eps_dir</code> <i>directory</i>] [ <code>&#8211;keep_all</code> ] [<code>&#8211;output</code> <i>output-file</i>] [<code>&#8211;prefix</code> <i>filename-prefix</i>] [<code>&#8211;temp_dir</code> <i>tdir</i>] [ <code>&#8211;verbose</code> ] [ <code>&#8211;</code> ] [ <code>&#8212;</code> ] [<i>filespec</i> &#8230; ] <code>-?</code> <code>-h</code> <code>&#8211;help</code> <code>&#8211;usage</code> <code>-l</code> <code>&#8211;license</code> <code>&#8211;version</code></p>
<h2>DESCRIPTION</h2>
<p> <code>glilypond</code> transforms sheet music written in the <i>lilypond</i> language into the <code><a href="/docs/linux/man/7-groff/">groff</a></code>(7) language using the <code>.PSPIC</code> request, such that <code><a href="/docs/linux/man/1-groff/">groff</a></code>(1) can transform it into a format that can be displayed directly. <code>.PDFPIC</code> is available, but does on yet work with lilypond. </p>
<p> Files in <i>groff</i> language and <i>standard input</i> can be provided as arguments.</p>
<h2>WORKING GLILYPOND</h2>
<p> Together with <code>.PSPIC</code>, <code>glilypond can work only for</code> <i>troff</i> devices without <i>PDF</i> and <i>X</i> devices. </p>
<p> I.e., the following <code>groff</code> devices work, <code>-Tps</code>, <code>-Tdvi</code>, <code>-Thtml</code>, and <code>-Txhtml</code>. </p>
<p> I&#8217;m not sure about the <code>ldp</code> and <code>lj4</code> devices. </p>
<p> In <code>groffer</code>, it is easier to use the following device options, either <code>&#8211;ps</code>, <code>&#8211;div</code>, <code>&#8211;html</code>, or <code>&#8211;xhtml</code>. </p>
<p> Unfortunately, the <code>groff</code> option <code>-Tpdf</code> does not work and the <code>groffer</code> default <i>PDF</i> works neither. </p>
<p> But <code>groffer</code> has an additional <i>pdf mode</i>, not available in <code>groff</code>. It is based on the <i>ps mode</i> in <code>groff</code> and is called through <code>groffer &#8211;pdf2</code> <i>roff-file-with-lilypond</i>.</p>

<h3>Options for building EPS Files</h3>
<dl>
<dt>[ <code>&#8211;ly2eps</code> ]</p>
<dd> Here the <code>lilypond</code> program creates <i>eps</i> files directly. This is the default.</p>
<dt>[ <code>&#8211;pdf2eps</code> ]</p>
<dd> The program <code>glilypond</code> generates a <i>PDF</i> file using <code>lilypond</code>. Then the <i>eps</i> file is generated by <code>pdf2ps</code> and <code>ps2eps</code>R<code>.</code></dl>
<h3>Directories and Files</h3>
<dl>
<dt><code>-e</code>|<code>&#8211;eps_dir</code><i> directory_name</i></p>
<dd> Normally all <i>EPS</i> files are sent to the temporary directory. With this option, you can generate your own directory, in which all useful <i>EPS</i> files are send. So at last, the temporary directory can be removed.</p>
<dt><code>-p</code>|<code>&#8211;prefix</code><i> begin_of_name</i></p>
<dd> Normally all temporary files get names that start with the <code>ly</code><i>&#8230; </i> prefix. With this option, you can freely change this prefix.</p>
<dt><code>-k</code>|<code>&#8211;keep_all</code></p>
<dd> Normally all temporary files without the <i>eps</i> files are deleted. With this option, all generated files either by the <code>lilypond</code> program or other format transposers are kept.</p>
<dt><code>-t</code>|<code>&#8211;temp_dir</code><i> dir</i></p>
<dd> With this option, you call a directory that is the base for the temporary directory. This directory name is used as is without any extensions. If this directory does not exist it is be created. The temporary directory is created by Perl&#8217;s security operations directly under this directory. In this temporary directory, the temporary files are stored.</dl>
<h3>Output</h3>
<dl>
<dt><code>-o</code>|<code>&#8211;output</code><i> file_name</i></p>
<dd> Normally all <i>groff</i> output of this program is sent to <code>STDOUT</code>. With this option, that can be changed, such that the output is stored into a file named in the option argument <i>file_name</i>.</p>
<dt><code>-v</code>|<code>-V</code>|<code>&#8211;verbose</code></p>
<dd> A lot more of information is sent to STDERR.</dl>
<h3>Short Option Collections</h3>
<p> The argument handling of options </p>
<p> <i>Short options</i> are arguments that start with a single dash <code>&#8211;</code>. Such an argument can consist of arbitrary many options without option argument, composed as a collection of option characters following the single dash. </p>
<p> Such a collection can be terminated by an option character that expects an option argument. If this option character is not the last character of the argument, the following final part of the argument is the option argument. If it is the last character of the argument, the next argument is taken as the option argument. </p>
<p> This is the standard for <i>POSIX</i> and <i>GNU</i> option management. </p>
<p> For example,</p>
<dl>
<dt><code>-kVe</code><i> some_dir</i></p>
<dd> is a collection of the short options <code>-k</code> and <code>-V</code> without option argument, followed by the short option <code>-e</code> with option argument that is the following part of the argument <i>some_dir</i>. So this argument could also be written as several arguments <code>-k -V -e</code> <i>some_dir</i>.</dl>
<h3>Handling of Long Options</h3>
<p> Arguments that start with a double dash <code>&#8212;</code> are so-called <i>long options R .</i> Each double dash argument can only have a single long option. </p>
<p> <i>Long options</i> have or have not an option argument. An option argument can be the next argument or can be appended with an equal sign <code>=</code> to the same argument as the long option.</p>
<dl>
<dt><code>&#8211;help</code></p>
<dd> is a long option without an option argument.</p>
<dt><code>&#8211;eps_dir</code><i> some_dir</i></p>
<dd> <code>&#8211;eps_dir=</code><i>some_dir</i> is the long option <code>&#8211;eps_dir</code> with the option argument <i>some_dir</i>.</dl>
<p> Moreover the program allows abbreviations of long options, as much as possible. </p>
<p> The <i>long option</i> <code>&#8211;keep_all</code> can be abbreviated from <code>&#8211;keep_al</code> up to <code>&#8211;k</code> because the program does not have another <i>long option</i> whose name starts with the character <code>k</code>. </p>
<p> On the other hand, the option <code>&#8211;version</code> cannot be abbreviated further than <code>&#8211;vers</code> because there is also the <i>long option</i> <code>&#8211;verbose</code> that can be abbreviated up to <code>&#8211;verb</code>. </p>
<p> An option argument can also be appended to an abbreviation. So is <code>&#8211;e=</code><i>some_dir</i> the same as <code>&#8211;eps_dir</code> <i>some_dir</i>. </p>
<p> Moreover the program allows an arbitrary usage of upper and lower case in the option name. This is <i>Perl</i> style. </p>
<p> For example, the <i>long option</i> <code>&#8211;keep_all</code> can as well be written as <code>&#8211;Keep_All</code> or even as an abbreviation like <code>&#8211;KeE</code>.</p>
<h2>FILESPEC ARGUMENTS</h2>
<p> An argument that is not an option or an option argument is called a <i>filespec</i> argument. </p>
<p> Without any <i>filespec</i> argument, <i>standard input</i> is read. </p>
<p> Each <i>filespec</i> argument must either be the name of a readable file or a dash <code>&#8211;</code> for <i>standard input</i>. Each input must be written in the <i>roff</i> or <i>groff</i> language and can include <i>lilypond</i> parts. </p>
<p> Normally arguments starting with a dash <code>&#8211;</code> are interpreted as an option. But if you use an argument that consists only of a doubled dash <code>&#8212; R ,</code> all following arguments are taken as <i>filespec</i> argument, even if such an argument starts with a dash. This is handled according to the <i>GNU</i> standard.</p>
<h2>THE LILYPOND PARTS IN ROFF INPUT</h2>
<h3>Integrated Lilypond Codes</h3>
<p> A <i>lilypond</i> part within a structure written in the <i>groff</i> language is the whole part between the marks</p>
<dl>
<dt>
<dd> <code>.lilypond start</code></dl>
<p> and</p>
<dl>
<dt>
<dd> <code>.lilypond end</code></dl>
<p> A <i>groff</i> input can have several of these <i>lilypond</i> parts. </p>
<p> When processing such a <i>lilypond</i> part between <code>.lilypond start</code> and <code>.lilypond end</code> we say that the <code>glilypond</code> program is in <i>lilypond mode</i>. </p>
<p> These <i>lilypond</i> parts are sent into temporary <i>lilypond</i> files with the file name extension <code>.ly</code>. These files are transformed later on into <i>EPS</i> files.</p>
<h3>Inclusion of ly-Files</h3>
<p> An additional command line for file inclusion of <i>lilypond</i> files is given by <code>.lilypond include</code><i> file_name</i> in <i>groff</i> input. For each such <i>include</i> command, one file of <i>lilypond</i> code can be included into the <i>groff</i> code. Arbitrarily many of these commands can be included in the <i>groff</i> input. </p>
<p> These include commands can only be used outside the <i>lilypond</i> parts. Within the <i>lilypond mode</i>, this inclusion is not possible. So <code>.lilypond include</code> may not be used in <i>lilypond mode</i>, i.e. between <code>.lilypond start</code> and <code>.lilypond end</code>. These included <i>ly</i>-files are also transformed into <i>EPS</i> files.</p>
<h2>GENERATED FILES</h2>
<p> By the transformation process of <i>lilypond</i> parts into <i>EPS</i> files, there are many files generated. By default, these files are regarded as temporary files and as such stored in a temporary directory. </p>
<p> This process can be changed by command-line options.</p>
<h3>Command Line Options for Directories</h3>
<p> The temporary directory for this program is either created automatically or can be named by the option <code>-t</code>|<code>&#8211;temp_dir</code> <i>dir</i>. </p>
<p> Moreover, the <i>EPS</i> files that are later on referred by <code>.PSPIC</code> command in the final <i>groff</i> output can be stored in a different directory that can be set by the command-line option <code>-e</code>|<code>&#8211;eps_dir</code> <i>directory_name</i>. With this option, the temporary directory can be removed completely at the end of the program. </p>
<p> The beginning of the names of the temporary files can be set by the command-line option [ <code>-p </code><i>| </i><code>&#8211;prefix</code> ] <i>begin_of_name</i>. </p>
<p> All of the temporary files except the <i>EPS</i> files are deleted finally. This can be changed by setting the command-line option [ <code>-k </code><i>| </i><code>&#8211;keep_files </code><i>.</i> ] With this, all temporary files and directories are kept, not deleted. </p>
<p> These <i>EPS</i> files are stored in a temporary or <i>EPS</i> directory. But they cannot be deleted by the transformation process because they are needed for the display which can take a long time.</p>
<h2>TRANSFORMATION PROCESSES FOR GENERATING EPS FILES</h2>
<h3>Mode pdf2eps</h3>
<p> This mode is the actual default and can also be chosen by the option <code>&#8211;pdf2eps</code>. </p>
<p> In this mode, the <code>.ly</code> files are transformed by the <code><a href="/docs/linux/man/1-lilypond/">lilypond</a></code>(1) program into <i>PDF</i> files, using</p>
<dl>
<dt>
<dd> <code>lilypond &#8211;pdf &#8211;output=</code><i>file-name</i></dl>
<p> for each <code>.ly</code> file. The <i>file-name</i> must be provided without the extension <code>.pdf</code>. By this process, a file <i>file-name</i><code>.pdf</code> is generated. </p>
<p> The next step is to transform these <i>PDF</i> files into a <i>PS</i> file. This is done by the <code><a href="/docs/linux/man/1-pdf2ps/">pdf2ps</a></code>(1) program using</p>
<dl>
<dt>
<dd> $ <code>pdf2ps</code> <i>file-name</i> <code>.pdf</code> <i>file-name</i> <code>.ps</code></dl>
<p> The next step creates an <i>EPS</i> file from the <i>PS</i> file. This is done by the <code><a href="/docs/linux/man/1-ps2eps/">ps2eps</a></code>(1) program using</p>
<dl>
<dt>
<dd> $ <code>ps2eps </code><i>file-name</i><code>.ps</code></dl>
<p> By that, a file <i>file-name</i><code>.eps</code> is created for each <i>lilypond</i> part in the <i>groff</i> file or standard input. </p>
<p> The last step to be done is replacing all <i>lilypond</i> parts by the <i>groff</i> command</p>
<dl>
<dt>
<dd> <code>.PSPIC </code><i>file-name</i><code>.eps</code></dl>
<h3>Mode ly2eps</h3>
<p> In earlier time, this mode was the default. But now it does not work any more, so accept the new default <code>pdf2eps</code>. For testing, this mode can also be chosen by the <code>glilypond</code> option <code>&#8211;ly2eps</code>. </p>
<p> In this mode, the <code>.ly</code> files are transformed by the <code>lilypond</code> program into many files of different formats, including <i>eps</i> files, using</p>
<dl>
<dt>
<dd> <code>$ lilypond &#8211;ps -dbackend=eps -dgs-load-fonts &#8211;output=</code><i>file-name</i></dl>
<p> for each <code>.ly</code> file. The output <i>file-name</i> must be provided without an extension, its directory is temporary. </p>
<p> There are many <i>EPS</i> files created. One having the complete transformed <code>ly</code> file, named <i>file-name</i><code>.eps</code><i></i>. </p>
<p> Moreover there are <i>EPS</i> files for each page, named <i>file-name</i><code>&#8211;</code><i>digit</i><code>.eps</code><i></i>. </p>
<p> The last step to be done is replacing all <i>lilypond</i> parts by the collection of the corresponding <i>EPS</i> page files. This is done by <i>groff</i> commands <code>.PSPIC </code><i>file-name</i><code>&#8211;</code><i>digit</i><code>.eps</code></p>
<h2>THE GENERATED NEW ROFF STRUCTURE</h2>
<p> The new <code><a href="/docs/linux/man/7-groff/">groff</a></code>(7) structure generated by <code>glilypond</code> is either</p>
<dl>
<dt>1)</p>
<dd> sent to standard output and can there be saved into a file or piped into <code><a href="/docs/linux/man/1-groff/">groff</a></code>(1) or <code><a href="/docs/linux/man/1-groffer/">groffer</a></code>(1) or</p>
<dt>2)</p>
<dd> stored into a file by given the option <code>-o&nbsp;~|</code>~&#8211;output <i>file_name</i></dl>
