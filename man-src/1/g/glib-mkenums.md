<h2 class="name">NAME</h2>
<p> glib-mkenums &#8211; C language enum description generation utility </p>
<h2>SYNOPSIS</h2>
<dl>
<dt> <code>glib-mkenums</code> [OPTION&#8230;] [FILE&#8230;]</dl>
<h2>DESCRIPTION</h2>
<p> <code>glib-mkenums</code></p>
<dd>is a small utility that parses C code to extract enum definitions and produces enum descriptions based on text templates specified by the user. Typically, you can use this tool to generate enumeration types for the GType type system, for GObject properties and signal marshalling; additionally, you can use it to generate enumeration values of GSettings schemas. </p>
<p> <code>glib-mkenums</code> takes a list of valid C code files as input. The options specified control the text that generated, substituting various keywords enclosed in @ characters in the templates.</p>
<h3>Production text substitutions</h3>
<p> Certain keywords enclosed in @ characters will be substituted in the emitted text. For the substitution examples of the keywords below, the following example enum definition is assumed: </p>
<dl>
<dt>
<dd>
<pre><code>
typedef enum {
    PREFIX_THE_XVALUE = 1 &lt;&lt; 3,
    PREFIX_ANOTHER_VALUE = 1 &lt;&lt; 4
} PrefixTheXEnum;
</code></pre>
</dl>
<p> @EnumName@&gt;</p>
<dl>
<dt>
<dd> The name of the enum currently being processed, enum names are assumed to be properly namespaced and to use mixed capitalization to separate words (e.g. PrefixTheXEnum).</dl>
<p> @enum_name@</p>
<dl>
<dt>
<dd> The enum name with words lowercase and word-separated by underscores (e.g. prefix_the_xenum).</dl>
<p> @ENUMNAME@</p>
<dl>
<dt>
<dd> The enum name with words uppercase and word-separated by underscores (e.g. PREFIX_THE_XENUM).</dl>
<p> @ENUMSHORT@</p>
<dl>
<dt>
<dd> The enum name with words uppercase and word-separated by underscores, prefix stripped (e.g. THE_XENUM).</dl>
<p> @ENUMPREFIX@</p>
<dl>
<dt>
<dd> The prefix of the enum name (e.g. PREFIX).</dl>
<p> @VALUENAME@</p>
<dl>
<dt>
<dd> The enum value name currently being processed with words uppercase and word-separated by underscores, this is the assumed literal notation of enum values in the C sources (e.g. PREFIX_THE_XVALUE).</dl>
<p> @valuenick@</p>
<dl>
<dt>
<dd> A nick name for the enum value currently being processed, this is usually generated by stripping common prefix words of all the enum values of the current enum, the words are lowercase and underscores are substituted by a minus (e.g. the-xvalue).</dl>
<p> @valuenum@</p>
<dl>
<dt>
<dd> The integer value for the enum value currently being processed. If the evaluation fails then <code>glib-mkenums</code> will exit with an error status, but this only happens if @valuenum@ appears in your value production template. (Since: 2.26)</dl>
<p> @type@</p>
<dl>
<dt>
<dd> This is substituted either by &quot;enum&quot; or &quot;flags&quot;, depending on whether the enum value definitions contained bit-shift operators or not (e.g. flags).</dl>
<p> @Type@</p>
<dl>
<dt>
<dd> The same as @type@ with the first letter capitalized (e.g. Flags).</dl>
<p> @TYPE@</p>
<dl>
<dt>
<dd> The same as @type@ with all letters uppercased (e.g. FLAGS).</dl>
<p> @filename@</p>
<dl>
<dt>
<dd> The full path of the input file currently being processed (e.g. /build/environment/project/src/foo.h).</dl>
<p> @basename@</p>
<dl>
<dt>
<dd> The base name of the input file currently being processed (e.g. foo.h). Typically you want to use @basename@ in place of @filename@ in your templates, to improve the reproducibility of the build. (Since: 2.22)</dl>
<h3>Trigraph extensions</h3>
<p> Some C comments are treated specially in the parsed enum definitions, such comments start out with the trigraph sequence /*&lt; and end with the trigraph sequence &gt;*/. Per enum definition, the options skip and flags can be specified, to indicate this enum definition to be skipped, or for it to be treated as a flags definition, or to specify the common prefix to be stripped from all values to generate value nicknames, respectively. The underscore_name option can be used to specify the word separation used in the <code>*_get_type()</code> function. For instance, /*&lt; underscore_name=gnome_vfs_uri_hide_options &gt;*/. </p>
<p> Per value definition, the options skip and nick are supported. The former causes the value to be skipped, and the latter can be used to specify the otherwise auto-generated nickname. Examples: </p>
<dl>
<dt>
<dd>
typedef enum /*&lt; skip &gt;*/<br />
{<br />
    PREFIX_FOO<br />
} PrefixThisEnumWillBeSkipped;<br />
typedef enum /*&lt; flags,prefix=PREFIX &gt;*/<br />
{<br />
    PREFIX_THE_ZEROTH_VALUE, /*&lt; skip &gt;*/<br />
    PREFIX_THE_FIRST_VALUE,<br />
    PREFIX_THE_SECOND_VALUE,<br />
    PREFIX_THE_THIRD_VALUE, /*&lt; nick=the-last-value &gt;*/<br />
} PrefixTheFlagsEnum;
</dl>
<h2>OPTIONS</h2>
<p> <code>&#8211;fhead</code> <i>TEXT</i></p>
<dl>
<dt>
<dd> Emits <i>TEXT</i> prior to processing input files. </p>
<p> You can specify this option multiple times, and the <i>TEXT</i> will be concatenated. </p>
<p> When used along with a template file, <i>TEXT</i> will be prepended to the template&#8217;s file-header section.</dl>
<p> <code>&#8211;fprod</code> <i>TEXT</i></p>
<dl>
<dt>
<dd> Emits <i>TEXT</i> every time a new input file is being processed. </p>
<p> You can specify this option multiple times, and the <i>TEXT</i> will be concatenated. </p>
<p> When used along with a template file, <i>TEXT</i> will be appended to the template&#8217;s file-production section.</dl>
<p> <code>&#8211;ftail</code> <i>TEXT</i></p>
<dl>
<dt>
<dd> Emits <i>TEXT</i> after all input files have been processed. </p>
<p> You can specify this option multiple times, and the <i>TEXT</i> will be concatenated. </p>
<p> When used along with a template file, <i>TEXT</i> will be appended to the template&#8217;s file-tail section.</dl>
<p> <code>&#8211;eprod</code> <i>TEXT</i></p>
<dl>
<dt>
<dd> Emits <i>TEXT</i> every time an enum is encountered in the input files.</dl>
<p> <code>&#8211;vhead</code> <i>TEXT</i></p>
<dl>
<dt>
<dd> Emits <i>TEXT</i> before iterating over the set of values of an enum. </p>
<p> You can specify this option multiple times, and the <i>TEXT</i> will be concatenated. </p>
<p> When used along with a template file, <i>TEXT</i> will be prepended to the template&#8217;s value-header section.</dl>
<p> <code>&#8211;vprod</code> <i>TEXT</i></p>
<dl>
<dt>
<dd> Emits <i>TEXT</i> for every value of an enum. </p>
<p> You can specify this option multiple times, and the <i>TEXT</i> will be concatenated. </p>
<p> When used along with a template file, <i>TEXT</i> will be appended to the template&#8217;s value-production section.</dl>
<p> <code>&#8211;vtail</code> <i>TEXT</i></p>
<dl>
<dt>
<dd> Emits <i>TEXT</i> after iterating over all values of an enum. </p>
<p> You can specify this option multiple times, and the <i>TEXT</i> will be concatenated. </p>
<p> When used along with a template file, <i>TEXT</i> will be appended to the template&#8217;s value-tail section.</dl>
<p> <code>&#8211;comments</code> <i>TEXT</i></p>
<dl>
<dt>
<dd> Template for auto-generated comments, the default (for C code generations) is &quot;/* @comment@ */&quot;.</dl>
<p> <code>&#8211;template</code> <i>FILE</i></p>
<dl>
<dt>
<dd> Read templates from the given file. The templates are enclosed in specially-formatted C comments: </p>
<dl>
<dt>
<dd>
<pre>
/*** BEGIN section ***/
/*** END section ***/
</pre>
</dl>
<p> <i>section</i> may be file-header, file-production, file-tail, enumeration-production, value-header, value-production, value-tail or comment.</dl>
<p> <code>&#8211;identifier-prefix</code> <i>PREFIX</i></p>
<dl>
<dt>
<dd> Indicates what portion of the enum name should be interpreted as the prefix (eg, the &quot;Gtk&quot; in &quot;GtkDirectionType&quot;). Normally this will be figured out automatically, but you may need to override the default if your namespace is capitalized oddly.</dl>
<p> <code>&#8211;symbol-prefix</code> <i>PREFIX</i></p>
<dl>
<dt>
<dd> Indicates what prefix should be used to correspond to the identifier prefix in related C function names (eg, the &quot;gtk&quot; in &quot;gtk_direction_type_get_type&quot;. Equivalently, this is the lowercase version of the prefix component of the enum value names (eg, the &quot;GTK&quot; in &quot;GTK_DIR_UP&quot;. The default value is the identifier prefix, converted to lowercase.</dl>
<p> <code>&#8211;help</code></p>
<dl>
<dt>
<dd> Print brief help and exit.</dl>
<p> <code>&#8211;version</code></p>
<dl>
<dt>
<dd> Print version and exit.</dl>
<p> <code>&#8211;output=FILE</code></p>
<dl>
<dt>
<dd> Write output to FILE instead of stdout.</dl>
<p> <code>@RSPFILE</code></p>
<dl>
<dt>
<dd> When passed as the sole argument, read and parse the actual arguments from RSPFILE. Useful on systems with a low command-line length limit. For example, Windows has a limit of 8191 characters.</dl>
<h2>USING TEMPLATES</h2>
<p> Instead of passing the various sections of the generated file to the command line of <code>glib-mkenums</code>, it&#8217;s strongly recommended to use a template file, especially for generating C sources. </p>
<p> A C header template file will typically look like this: </p>
<dl>
<dt>
<dd>
/*** BEGIN file-header ***/<br />
#pragma once<br />
/* Include the main project header */<br />
#include &#8220;project.h&#8221;<br />
G_BEGIN_DECLS<br />
/*** END file-header ***/<br />
/*** BEGIN file-production ***/<br />
/* enumerations from &#8220;@basename@&#8221; */<br />
/*** END file-production ***/<br />
/*** BEGIN value-header ***/<br />
GType @enum_name[at] _get_type(void) G_GNUC_CONST;<br />
#define @ENUMPREFIX[at] _TYPE_ @ENUMSHORT @(@enum_name[at] _get_type())<br />
/*** END value-header ***/<br />
/*** BEGIN file-tail ***/<br />
G_END_DECLS<br />
/*** END file-tail ***/
</dl>
<p> A C source template file will typically look like this: </p>
<dl>
<dt>
<dd>
/*** BEGIN file-header ***/<br />
#include &#8220;config.h&#8221;<br />
#include &#8220;enum-types.h&#8221;<br />
/*** END file-header ***/<br />
/*** BEGIN file-production ***/<br />
/* enumerations from &#8220;@basename@&#8221; */<br />
/*** END file-production ***/<br />
/*** BEGIN value-header ***/<br />
GType<br />
    @enum_name[at] _get_type(void)<br />
{<br />
    static volatile gsize g_[at] type @_type_id__volatile;<br />
    if (g_once_init_enter(&amp;g_define_type_id__volatile)) {<br />
        static const G @Type[at] Value values[] = {<br />
            /*** END value-header ***/<br />
            /*** BEGIN value-production ***/<br />
            {@VALUENAME @, &#8220;@VALUENAME@&#8221;, &#8220;@valuenick@&#8221;},<br />
            /*** END value-production ***/<br />
            /*** BEGIN value-tail ***/<br />
            {0, NULL, NULL}};<br />
        GType g_[at] type @_type_id =<br />
            g_[at] type @_register_static(g_intern_static_string(&#8220;@EnumName@&#8221;), values);<br />
        g_once_init_leave(&amp;g_[at] type @_type_id__volatile, g_[at] type @_type_id);<br />
    }<br />
    return g_[at] type @_type_id__volatile;<br />
}<br />
/*** END value-tail ***/
</dl>
<p> Template files are easier to modify and update, and can be used to generate various types of outputs using the same command line or tools during the build.</p>
<h2>USING GLIB-MKENUMS WITH MESON</h2>
<p> Meson supports generating enumeration types using <code>glib-mkenums</code> out of the box in its &quot;gnome&quot; module. </p>
<p> In your meson.build file you will typically call the gnome.mkenums_simple() method to generate idiomatic enumeration types from a list of headers to inspect: </p>
<dl>
<dt>
<dd>
<pre>
project_headers = [
  'project-foo.h',
  'project-bar.h',
  'project-baz.h',
]
gnome = import('gnome')
enum_files = gnome.mkenums_simple('enum-types',
  sources: project_headers,
)
</pre>
</dl>
<p> The enum_files variable will contain an array of two elements in the following order: </p>
<dl>
<dt>
<dd> &bull; a build target for the source file</dl>
<dl>
<dt>
<dd> &bull; a build target for the header file</dl>
<p> You should use the returned objects to provide a dependency on every other build target that references the source or header file; for instance, if you are using the source to build a library: </p>
<dl>
<dt>
<dd>
<pre>
mainlib = library('project',
  sources: project_sources + enum_files,
  ...
)
</pre>
</dl>
<p> Additionally, if you are including the generated header file inside a build target that depends on the library you just built, you must ensure that the internal dependency includes the generated header as a required source file: </p>
<dl>
<dt>
<dd>
<pre>
mainlib_dep = declare_dependency(sources: enum_files[1], link_with: mainlib)
</pre>
</dl>
<p> You should not include the generated source file as well, otherwise it will be built separately for every target that depends on it, causing build failures. To know more about why all this is required, please refer to the m[blue]<code>corresponding Meson FAQ entry</code>m[]<font SIZE="-2">[1]</font>. </p>
<p> If you are generating C header and source files that require special templates, you can use gnome.mkenums() to provide those headers, for instance: </p>
<dl>
<dt>
<dd>
<pre>
enum_files = gnome.mkenums('enum-types',
  sources: project_headers,
  h_template: 'enum-types.h.in',
  c_template: 'enum-types.c.in',
  install_header: true,
)
</pre>
</dl>
<p> For more information, see the m[blue]<code>Meson documentation for gnome.mkenums()</code>m[]<font SIZE="-2">[2]</font>.</p>
<h2>USING GLIB-MKENUMS WITH AUTOTOOLS</h2>
<p> In order to use <code>glib-mkenums</code> in your project when using Autotools as the build system, you will first need to modify your configure.ac file to ensure you find the appropriate command using <code>pkg-config</code>, similarly as to how you discover the compiler and linker flags for GLib. </p>
<dl>
<dt>
<dd>
PKG_PROG_PKG_CONFIG([0.28])<br />
PKG_CHECK_VAR([GLIB_MKENUMS], [glib &#8211; 2.0], [glib_mkenums])
</dl>
<p> In your Makefile.am file you will typically use rules like these: </p>
<dl>
<dt>
<dd>
<pre><code>
#A list of headers to inspect
project_headers =
    project - foo.h project - bar.h project - baz.h enum - types.h : $(project_headers) enum - types.h.in $(AM_V_GEN) $(GLIB_MKENUMS)-- template = enum - types.h.in-- output = $ @$(project_headers) enum - types.c : $(project_headers) enum - types.c.in enum - types.h $(AM_V_GEN) $(GLIB_MKENUMS)-- template = enum - types.c.in-- output = $ @$(project_headers)
#Build the enum types files before every other target
                                                                                                                                                                                                                                                                                                                        BUILT_SOURCES += enum - types.h enum - types.c CLEANFILES += enum - types.h enum - types.c EXTRA_DIST += enum - types.h.in enum - types.c.in
</code></pre>
</dl>
<p> In the example above, we have a variable called project_headers where we reference all header files we want to inspect for generating enumeration GTypes. In the enum-types.h rule we use <code>glib-mkenums</code> with a template called enum-types.h.in in order to generate the header file; similarly, in the enum-types.c rule we use a template called enum-types.c.in.</p>
