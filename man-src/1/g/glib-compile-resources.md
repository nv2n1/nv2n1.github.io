<h2 class="name">NAME</h2>
<p> glib-compile-resources &#8211; GLib resource compiler </p>
<h2>SYNOPSIS</h2>
<dl>
<dt> <code>glib-compile-resources</code> [OPTION&#8230;] {FILE}</dl>
<h2>DESCRIPTION</h2>
<p> <code>glib-compile-resources</code></p>
<dd>reads the resource description from <i>FILE</i> and the files that it references and creates a binary resource bundle that is suitable for use with the <code>GResource</code> API. The resulting bundle is then written out as-is, or as C source for linking into an application. </p>
<p> The XML resource files normally have the filename extension .gresource.xml. For a detailed description of the XML file format, see the <code>GResource</code> documentation.</p>
<h2>OPTIONS</h2>
<p> <code>-h</code>, <code>&#8211;help</code></p>
<dl>
<dt>
<dd> Print help and exit</dl>
<p> <code>&#8211;version</code></p>
<dl>
<dt>
<dd> Print program version and exit</dl>
<p> <code>&#8211;target=</code><i>TARGET</i></p>
<dl>
<dt>
<dd> Store the compiled resources in the file <i>TARGET</i>. If not specified a filename based on the <i>FILE</i> basename is used.</dl>
<p> <code>&#8211;sourcedir=</code><i>DIRECTORY</i></p>
<dl>
<dt>
<dd> The files referenced in <i>FILE</i> are loaded from this directory. If not specified, the current directory is used.</dl>
<p> <code>&#8211;generate</code></p>
<dl>
<dt>
<dd> Write the output file in the format selected for by its filename extension: </p>
<p> .c</p>
<dl>
<dt>
<dd> C source</dl>
<p> .h</p>
<dl>
<dt>
<dd> C header</dl>
<p> .gresource</p>
<dl>
<dt>
<dd> resource bundle</dl>
</dl>
<p> <code>&#8211;generate-source</code></p>
<dl>
<dt>
<dd> Instead of a writing the resource bundle in binary form create a C source file that contains the resource bundle. This can then be compiled into an application for easy access.</dl>
<p> <code>&#8211;generate-header</code></p>
<dl>
<dt>
<dd> Generate a header file for use with C code generated by <code>&#8211;generate-source</code>.</dl>
<p> <code>&#8211;generate-dependencies</code></p>
<dl>
<dt>
<dd> Prints the list of files that the resource bundle references to standard output. This can be used to track dependencies in the build system. For example, the following make rule would mark <i>test.gresource</i> as depending on all the files that <i>test.gresource.xml</i> includes, so that is is automatically rebuilt if any of them change: </p>
<dl>
<dt>
<dd>
<pre>
test.gresource: test.gresource.xml $(shell $(GLIB_COMPILE_RESOURCES) --generate-dependencies test.gresource.xml)
</pre>
</dl>
<p> Note that this may or may not be portable to non-GNU <code>make</code>. </p>
<p> Also see <code>&#8211;dependency-file</code>.</dl>
<p> <code>&#8211;c-name</code></p>
<dl>
<dt>
<dd> Specify the prefix used for the C identifiers in the code generated by <code>&#8211;generate-source</code> and <code>&#8211;generate-header</code>.</dl>
<p> <code>&#8211;manual-register</code></p>
<dl>
<dt>
<dd> By default code generated by <code>&#8211;generate-source</code> uses automatic initialization of the resource. This works on most systems by using the compiler support for constructors. However, some (uncommon) compilers may not support this, you can then specify <code>&#8211;manual-register</code>, which will generate custom register and unregister functions that your code can manually call at initialization and uninitialization time.</dl>
<p> <code>&#8211;internal</code></p>
<dl>
<dt>
<dd> By default code generated by <code>&#8211;generate-source</code> declares all initialization functions as <code>extern</code>. So they are exported unless this is prevented by a link script or other means. Since libraries usually want to use the functions only internally it can be more useful to declare them as G_GNUC_INTERNAL which is what <code>&#8211;internal</code> does.</dl>
<p> <code>&#8211;external-data</code></p>
<dl>
<dt>
<dd> By default code generated by <code>&#8211;generate-source</code> embeds the resource data as a string literal. When <code>&#8211;external-data</code> is given, the data is only declared in the generated C file, and the data has to be linked externally.</dl>
<p> <code>&#8211;dependency-file=</code><i>FILE</i></p>
<dl>
<dt>
<dd> Write dependencies in the same style as gcc -M -MF to the given file. If <code>FILE</code> is -, the dependencies are written to the standard output. Unlike <code>&#8211;generate-dependencies</code>, this option can be combined with other <code>&#8211;generate</code> options to generate dependencies as a side-effect of generating sources.</dl>
<p> <code>&#8211;generate-phony-targets</code></p>
<dl>
<dt>
<dd> When creating a dependency file with <code>&#8211;dependency-file</code> include phony targets in the same style as gcc -MP. This would typically be used with make.</dl>
<h2>ENVIRONMENT</h2>
<p> <code>XMLLINT</code></p>
<dl>
<dt>
<dd> The full path to the <code>xmllint</code> executable. This is used to preprocess resources with the xml-stripblanks preprocessing option. If this environment variable is not set, <code>xmllint</code> is searched for in the <code>PATH</code>.</dl>
<p> <code>GDK_PIXBUF_PIXDATA</code></p>
<dl>
<dt>
<dd> The full path to the <code>gdk-pixbuf-pixdata</code> executable. This is used to preprocess resources with the to-pixdata preprocessing option. If this environment variable is not set, <code>gdk-pixbuf-pixdata</code> is searched for in the <code>PATH</code>.</dl>
<p> <code>JSON_GLIB_FORMAT</code></p>
<dl>
<dt>
<dd> The full path to the <code>json-glib-format</code> executable. This is used to preprocess resources with the json-stripblanks preprocessing option. If this environment variable is not set, <code>json-glib-format</code> is searched for in the <code>PATH</code>.</dl>
