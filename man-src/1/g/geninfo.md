<h2>NAME</h2>
<p> geninfo &#8211; Generate tracefiles from .da files</p>
<h2>SYNOPSIS</h2>
<p> <code>geninfo</code> [<code>-h</code>|<code>&#8211;help</code>] [<code>-v</code>|<code>&#8211;version</code>] [<code>-q</code>|<code>&#8211;quiet</code>] </p>
<dl>
<dt>
<dd> [<code>-i</code>|<code>&#8211;initial</code>] [<code>-t</code>|<code>&#8211;test-name</code> <i>test-name</i>]<br />
 [<code>-o</code>|<code>&#8211;output-filename</code> <i>filename</i>] [<code>-f</code>|<code>&#8211;follow</code>]<br />
 [<code>-b</code>|<code>&#8211;base-directory</code> <i>directory</i>]<br />
 [<code>&#8211;checksum</code>] [<code>&#8211;no-checksum</code>]<br />
 [<code>&#8211;compat-libtool</code>] [<code>&#8211;no-compat-libtool</code>]<br />
 [<code>&#8211;gcov-tool</code> <i>tool</i>] [<code>&#8211;ignore-errors</code> <i>errors</i>]<br />
 [<code>&#8211;no-recursion</code>] <i>directory</i> [<code>&#8211;external</code>] [<code>&#8211;no-external</code>]<br />
 [<code>&#8211;config-file</code> <i>config-file</i>] [<code>&#8211;no-markers</code>]<br />
 [<code>&#8211;derive-func-data</code>] [<code>&#8211;compat</code> <i>mode</i>=on|off|auto]<br />
 [<code>&#8211;rc</code> <i>keyword</i>=<i>value</i>]</dl>
<h2>DESCRIPTION</h2>
<p> <code>geninfo </code> converts all GCOV coverage data files found in <i>directory</i> into tracefiles, which the <code>genhtml</code> tool can convert to HTML output. </p>
<p> Unless the &#8211;output-filename option is specified, <code>geninfo</code> writes its output to one file per .da file, the name of which is generated by simply appending &quot;.info&quot; to the respective .da file name. </p>
<p> Note that the current user needs write access to both <i>directory</i> as well as to the original source code location. This is necessary because some temporary files have to be created there during the conversion process. </p>
<p> Note also that <code>geninfo</code> is called from within <code>lcov</code>, so that there is usually no need to call it directly. </p>
<p> <code>Exclusion markers</code> </p>
<p> To exclude specific lines of code from a tracefile, you can add exclusion markers to the source code. Exclusion markers are keywords which can for example be added in the form of a comment. </p>
<p> The following markers are recognized by geninfo: </p>
<p> LCOV_EXCL_LINE</p>
<dl>
<dt>
<dd> Lines containing this marker will be excluded.
</dl>
<p> LCOV_EXCL_START</p>
<dl>
<dt>
<dd> Marks the beginning of an excluded section. The current line is part of this section.
</dl>
<p> LCOV_EXCL_STOP</p>
<dl>
<dt>
<dd> Marks the end of an excluded section. The current line not part of this section.</dl>
<h2>OPTIONS</h2>
<p> <code>-b</code> <i>directory</i><br />
 <code>&#8211;base-directory</code> <i>directory</i> </p>
<dl>
<dt>
<dd> Use <i>directory</i> as base directory for relative paths. </p>
<p> Use this option to specify the base directory of a build-environment when geninfo produces error messages like: </p>
<dl>
<dt>
<dd> ERROR: could not read source file /home/user/project/subdir1/subdir2/subdir1/subdir2/file.c</dl>
<p> In this example, use /home/user/project as base directory. </p>
<p> This option is required when using geninfo on projects built with libtool or similar build environments that work with a base directory, i.e. environments, where the current working directory when invoking the compiler is not the same directory in which the source code file is located. </p>
<p> Note that this option will not work in environments where multiple base directories are used. In that case use configuration file setting <code>geninfo_auto_base=1</code> (see <code><a href="/docs/linux/man/5-lcovrc/">lcovrc</a></code>(5)).</dl>
<p> <code>&#8211;checksum</code><br />
 <code>&#8211;no-checksum</code> </p>
<dl>
<dt>
<dd> Specify whether to generate checksum data when writing tracefiles. </p>
<p> Use &#8211;checksum to enable checksum generation or &#8211;no-checksum to disable it. Checksum generation is <code>disabled</code> by default. </p>
<p> When checksum generation is enabled, a checksum will be generated for each source code line and stored along with the coverage data. This checksum will be used to prevent attempts to combine coverage data from different source code versions. </p>
<p> If you don&#8217;t work with different source code versions, disable this option to speed up coverage data processing and to reduce the size of tracefiles.</dl>
<p> <code>&#8211;compat</code> <i>mode</i>=<i>value</i>[,<i>mode</i>=<i>value</i>,&#8230;] </p>
<dl>
<dt>
<dd> Set compatibility mode. </p>
<p> Use &#8211;compat to specify that geninfo should enable one or more compatibility modes when capturing coverage data. You can provide a comma-separated list of mode=value pairs to specify the values for multiple modes. </p>
<p> Valid <i>values</i> are: </p>
<p> <code>on</code></p>
<dl>
<dt>
<dd> Enable compatibility mode.</dl>
<p> <code>off</code></p>
<dl>
<dt>
<dd> Disable compatibility mode.</dl>
<p> <code>auto</code></p>
<dl>
<dt>
<dd> Apply auto-detection to determine if compatibility mode is required. Note that auto-detection is not available for all compatibility modes.</dl>
<p> If no value is specified, &#8216;on&#8217; is assumed as default value. </p>
<p> Valid <i>modes</i> are: </p>
<p> <code>libtool</code></p>
<dl>
<dt>
<dd> Enable this mode if you are capturing coverage data for a project that was built using the libtool mechanism. See also &#8211;compat-libtool. </p>
<p> The default value for this setting is &#8216;on&#8217;. </p>
</dl>
<p> <code>hammer</code></p>
<dl>
<dt>
<dd> Enable this mode if you are capturing coverage data for a project that was built using a version of GCC 3.3 that contains a modification (hammer patch) of later GCC versions. You can identify a modified GCC 3.3 by checking the build directory of your project for files ending in the extension &#8216;.bbg&#8217;. Unmodified versions of GCC 3.3 name these files &#8216;.bb&#8217;. </p>
<p> The default value for this setting is &#8216;auto&#8217;. </p>
</dl>
<p> <code>split_crc</code></p>
<dl>
<dt>
<dd> Enable this mode if you are capturing coverage data for a project that was built using a version of GCC 4.6 that contains a modification (split function checksums) of later GCC versions. Typical error messages when running geninfo on coverage data produced by such GCC versions are &#8216;out of memory&#8217; and &#8216;reached unexpected end of file&#8217;. </p>
<p> The default value for this setting is &#8216;auto&#8217;</dl>
</dl>
<p> <code>&#8211;compat-libtool</code><br />
 <code>&#8211;no-compat-libtool</code> </p>
<dl>
<dt>
<dd> Specify whether to enable libtool compatibility mode. </p>
<p> Use &#8211;compat-libtool to enable libtool compatibility mode or &#8211;no-compat-libtool to disable it. The libtool compatibility mode is <code>enabled</code> by default. </p>
<p> When libtool compatibility mode is enabled, geninfo will assume that the source code relating to a .da file located in a directory named &quot;.libs&quot; can be found in its parent directory. </p>
<p> If you have directories named &quot;.libs&quot; in your build environment but don&#8217;t use libtool, disable this option to prevent problems when capturing coverage data.</dl>
<p> <code>&#8211;config-file</code> <i>config-file</i> </p>
<dl>
<dt>
<dd> Specify a configuration file to use. </p>
<p> When this option is specified, neither the system-wide configuration file /etc/lcovrc, nor the per-user configuration file ~/.lcovrc is read. </p>
<p> This option may be useful when there is a need to run several instances of <code>geninfo</code> with different configuration file options in parallel.</dl>
<p> <code>&#8211;derive-func-data</code> </p>
<dl>
<dt>
<dd> Calculate function coverage data from line coverage data. </p>
<p> Use this option to collect function coverage data, even if the version of the gcov tool installed on the test system does not provide this data. lcov will instead derive function coverage data from line coverage data and information about which lines belong to a function.</dl>
<p> <code>&#8211;external</code><br />
 <code>&#8211;no-external</code> </p>
<dl>
<dt>
<dd> Specify whether to capture coverage data for external source files. </p>
<p> External source files are files which are not located in one of the directories specified by &#8211;directory or &#8211;base-directory. Use &#8211;external to include external source files while capturing coverage data or &#8211;no-external to ignore this data. </p>
<p> Data for external source files is <code>included</code> by default.</dl>
<p> <code>-f</code><br />
 <code>&#8211;follow</code></p>
<dl>
<dt>
<dd> Follow links when searching .da files.</dl>
<p> <code>&#8211;gcov-tool</code> <i>tool</i> </p>
<dl>
<dt>
<dd> Specify the location of the gcov tool.</dl>
<p> <code>-h</code><br />
 <code>&#8211;help</code></p>
<dl>
<dt>
<dd> Print a short help text, then exit.</dl>
<p> <code>&#8211;ignore-errors</code> <i>errors</i> </p>
<dl>
<dt>
<dd> Specify a list of errors after which to continue processing. </p>
<p> Use this option to specify a list of one or more classes of errors after which geninfo should continue processing instead of aborting. </p>
<p> <i>errors</i> can be a comma-separated list of the following keywords: </p>
<p> <code>gcov:</code> the gcov tool returned with a non-zero return code. </p>
<p> <code>source:</code> the source code file for a data set could not be found.</dl>
<p> <code>-i</code><br />
 <code>&#8211;initial</code></p>
<dl>
<dt>
<dd> Capture initial zero coverage data. </p>
<p> Run geninfo with this option on the directories containing .bb, .bbg or .gcno files before running any test case. The result is a &quot;baseline&quot; coverage data file that contains zero coverage for every instrumented line and function. Combine this data file (using lcov -a) with coverage data files captured after a test run to ensure that the percentage of total lines covered is correct even when not all object code files were loaded during the test. </p>
<p> Note: currently, the &#8211;initial option does not generate branch coverage information.</dl>
<p> <code>&#8211;no-markers</code> </p>
<dl>
<dt>
<dd> Use this option if you want to get coverage data without regard to exclusion markers in the source code file.</dl>
<p> <code>&#8211;no-recursion</code> </p>
<dl>
<dt>
<dd> Use this option if you want to get coverage data for the specified directory only without processing subdirectories.</dl>
<p> <code>-o </code><i>output-filename</i><br />
 <code>&#8211;output-filename </code><i>output-filename</i></p>
<dl>
<dt>
<dd> Write all data to <i>output-filename</i>. </p>
<p> If you want to have all data written to a single file (for easier handling), use this option to specify the respective filename. By default, one tracefile will be created for each processed .da file.</dl>
<p> <code>-q</code><br />
 <code>&#8211;quiet</code></p>
<dl>
<dt>
<dd> Do not print progress messages. </p>
<p> Suppresses all informational progress output. When this switch is enabled, only error or warning messages are printed.</dl>
<p> <code>&#8211;rc</code> <i>keyword</i>=<i>value</i> </p>
<dl>
<dt>
<dd> Override a configuration directive. </p>
<p> Use this option to specify a <i>keyword</i>=<i>value</i> statement which overrides the corresponding configuration statement in the lcovrc configuration file. You can specify this option more than once to override multiple configuration statements. See <code><a href="/docs/linux/man/5-lcovrc/">lcovrc</a></code>(5) for a list of available keywords and their meaning.</dl>
<p> <code>-t </code><i>testname</i><br />
 <code>&#8211;test-name </code><i>testname</i></p>
<dl>
<dt>
<dd> Use test case name <i>testname</i> for resulting data. Valid test case names can consist of letters, decimal digits and the underscore character (&#8216;_&#8217;). </p>
<p> This proves useful when data from several test cases is merged (i.e. by simply concatenating the respective tracefiles) in which case a test name can be used to differentiate between data from each test case.</dl>
<p> <code>-v</code><br />
 <code>&#8211;version</code></p>
<dl>
<dt>
<dd> Print version number, then exit.</dl>
<h2>FILES</h2>
<p> <i>/etc/lcovrc</i></p>
<dl>
<dt>
<dd> The system-wide configuration file.</dl>
<p> <i>~/.lcovrc</i></p>
<dl>
<dt>
<dd> The per-user configuration file.</dl>
<p> Following is a quick description of the tracefile format as used by <code>genhtml</code>, <code>geninfo</code> and <code>lcov</code>. </p>
<p> A tracefile is made up of several human-readable lines of text, divided into sections. If available, a tracefile begins with the <i>testname</i> which is stored in the following format: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>TN:&lt;test name&gt; </p>
<p> For each source file referenced in the .da file, there is a section containing filename and coverage data: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>SF:&lt;absolute path to the source file&gt; </p>
<p> Following is a list of line numbers for each function name found in the source file: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>FN:&lt;line number of function start&gt;,&lt;function name&gt; </p>
<p> Next, there is a list of execution counts for each instrumented function: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>FNDA:&lt;execution count&gt;,&lt;function name&gt; </p>
<p> This list is followed by two lines containing the number of functions found and hit: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>FNF:&lt;number of functions found&gt;<br />
&nbsp;<wbr>&nbsp;<wbr>FNH:&lt;number of function hit&gt; </p>
<p> Branch coverage information is stored which one line per branch: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>BRDA:&lt;line number&gt;,&lt;block number&gt;,&lt;branch number&gt;,&lt;taken&gt; </p>
<p> Block number and branch number are gcc internal IDs for the branch. Taken is either &#8216;-&#8216; if the basic block containing the branch was never executed or a number indicating how often that branch was taken. </p>
<p> Branch coverage summaries are stored in two lines: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>BRF:&lt;number of branches found&gt;<br />
&nbsp;<wbr>&nbsp;<wbr>BRH:&lt;number of branches hit&gt; </p>
<p> Then there is a list of execution counts for each instrumented line (i.e. a line which resulted in executable code): </p>
<p>&nbsp;<wbr>&nbsp;<wbr>DA:&lt;line number&gt;,&lt;execution count&gt;[,&lt;checksum&gt;] </p>
<p> Note that there may be an optional checksum present for each instrumented line. The current <code>geninfo</code> implementation uses an MD5 hash as checksumming algorithm. </p>
<p> At the end of a section, there is a summary about how many lines were found and how many were actually instrumented: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>LH:&lt;number of lines with a non-zero execution count&gt;<br />
&nbsp;<wbr>&nbsp;<wbr>LF:&lt;number of instrumented lines&gt; </p>
<p> Each sections ends with: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>end_of_record </p>
<p> In addition to the main source code file there are sections for all #included files which also contain executable code. </p>
<p> Note that the absolute path of a source file is generated by interpreting the contents of the respective .bb file (see <code>gcov </code>(1) for more information on this file type). Relative filenames are prefixed with the directory in which the .bb file is found. </p>
<p> Note also that symbolic links to the .bb file will be resolved so that the actual file path is used instead of the path to a link. This approach is necessary for the mechanism to work with the /proc/gcov files. </p>
