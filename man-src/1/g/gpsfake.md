<h2 class="name">NAME</h2>
<p> gpsfake &#8211; test harness for gpsd, simulating a GPS </p>
<h2>SYNOPSIS</h2>
<dl>
<dt> <code>gpsfake</code> [-1] [-h] [-b] [-f] [-c&nbsp;<wbr><i>interval</i>] [-i] [-D&nbsp;<wbr><i>debuglevel</i>] [-l] [-m&nbsp;<wbr><i>monitor</i>] [-g] [-n] [-o&nbsp;<wbr><i>options</i>] [-p] [-P&nbsp;<wbr><i>port</i>] [-r&nbsp;<wbr><i>initcmd</i>] [-s&nbsp;<wbr><i>speed</i>] [-u] [-t] [-v] [<i>logfile</i>&#8230;]</dl>
<h2>DESCRIPTION</h2>
<dd>gpsfake is a test harness for gpsd and its clients. It opens a pty (pseudo-TTY), launches a gpsd instance that thinks the slave side of the pty is its GPS device, and repeatedly feeds the contents of one or more test logfiles through the master side to the GPS. If there are multiple logfiles, sentences from them are interleaved in the order the files are specified. </p>
<p> gpsfake does not require root privileges, and can be run concurrently with a production gpsd instance without causing problems. </p>
<p> The logfiles may contain packets in any supported format, including in particular NMEA, SiRF, TSIP, or Zodiac. Leading lines beginning with # will be treated as comments and ignored, except in the following special cases: </p>
<dl>
<dt>
<dd> &bull; a comment of the form #Date: yyyy-mm-dd (ISO8601 date format) may be used to set the initial date for the log.</dl>
<dl>
<dt>
<dd> &bull; a comment of the form #Serial: [0-9]* [78][NOE][12] may be used to set serial parameters for the log &#8211; baud rate, word length, stop bits.</dl>
<dl>
<dt>
<dd> &bull; a comment of the form #Transport: UDP may be used to fake a UDP source rather than the normal pty.</dl>
<p> The gpsd instance is run in foreground. The thread sending fake GPS data to the daemon is run in background.</p>
<h2>OPTIONS</h2>
<p> With the -1 option, the logfile is interpreted once only rather than repeatedly. This option is intended to facilitate regression testing. </p>
<p> The <code>-b</code> enables a twirling-baton progress indicator on standard error. At termination, it reports elapsed time. </p>
<p> The <code>-c</code> sets the delay between sentences in seconds. Fractional values of seconds are legal. The default is zero (no delay). </p>
<p> The <code>-l</code> makes the program dump a line or packet number just before each sentence is fed to the daemon. If the sentence is textual (e.g. NMEA), the text is dumped as well. If not, the packet will be dumped in hexadecimal (except for RTCM packets, which aren&#8217;t dumped at all). This option is useful for checking that gpsfake is getting packet boundaries right. </p>
<p> The <code>-i</code> is for single-stepping through logfiles. It dumps the line or packet number (and the sentence if the protocol is textual) followed by &quot;? &quot;. Only when the user keys Enter is the line actually fed to gpsd. </p>
<p> The <code>-m</code> specifies a monitor program inside which the daemon should be run. This option is intended to be used with <code><a href="/docs/linux/man/1-valgrind/">valgrind</a></code>(1), <code><a href="/docs/linux/man/1-gdb/">gdb</a></code>(1) and similar programs. </p>
<p> The <code>-g</code> uses the monitor facility to run the gpsd instance within gpsfake under control of gdb. </p>
<p> The <code>-f</code> configures gpsd to bind to a random dynamic/private port (range 49152 &#8211; 65535). Its main use is within regression-test scripts so they won&#8217;t collide with a production instance. </p>
<p> The <code>-o</code> specifies options to pass to the daemon. The -n option passes -n to start the daemon reading the GPS without waiting for a client (equivalent to -o &quot;-n&quot;). The <code>-D</code> passes a -D option to the daemon: thus -D 4 is shorthand for -o &quot;-D 4&quot;. </p>
<p> The -p (&quot;pipe&quot;) option sets watcher mode and dumps the NMEA and GPSD notifications generated by the log to standard output. This is useful for regression-testing. </p>
<p> The -P (&quot;port&quot;) option sets the daemon&#8217;s listening port. </p>
<p> The <code>-r</code> specifies an initialization command to use in pipe mode. The default is <code>?WATCH={&quot;enable&quot;:true,&quot;json&quot;:true}</code>. </p>
<p> The <code>-s</code> sets the baud rate for the slave tty. The default is 4800. </p>
<p> The <code>-t</code> forces the test framework to use TCP rather than pty devices. Besides being a test of TCP source handling, this may be useful for testing from within chroot jails where access to pty devices is locked out. </p>
<p> The <code>-u</code> forces the test framework to use UDP rather than pty devices. Besides being a test of UDP source handling, this may be useful for testing from within chroot jails where access to pty devices is locked out. </p>
<p> The <code>-v</code> enables verbose progress reports to stderr. It is mainly useful for debugging gpsfake itself. </p>
<p> The <code>-x</code> dumps packets as gpsfake gathers them. It is mainly useful for debugging gpsfake itself. </p>
<p> The <code>-h</code> makes gpsfake print a usage message and exit. </p>
<p> The argument must be the name of a file containing the data to be cycled at the device. gpsfake will print a notification each time it cycles. </p>
<p> Normally, gpsfake creates a pty for each logfile and passes the slave side of the device to the daemon. If the header comment in the logfile contains the string &quot;UDP&quot;, packets are instead shipped via UDP port 5000 to the address 192.168.0.1.255. You can monitor them with this: <code>tcpdump -s0 -n -A -i lo udp and port 5000</code>.</p>
<h2>MAGIC COMMENTS</h2>
<p> Certain magic comments in test load headers can change the conditions of the test. These are: </p>
<p> Serial:</p>
<dl>
<dt>
<dd> May contain a serial-port setting such as 4800 7N2 &#8211; baud rate followed by 7 or 8 for byte length, N or O or E for parity and 1 or 2 for stop bits. The test is run with those settings on the slave port that the daemon sees.</dl>
<p> Transport:</p>
<dl>
<dt>
<dd> Values &#8216;TCP&#8217; and &#8216;UDP&#8217; force the use of TCP and UDP feeds respectively (the default is a pty).</dl>
<p> Delay-Cookie:</p>
<dl>
<dt>
<dd> Must be followed by two whitespace-separated fields, a delimiter character and a numeric delay in seconds. Instead of being broken up by packet boundaries, the test load is split on the delimiters. The delay is performed after each feed. Can be useful for imposing write boundaries in the middle of packets.</dl>
<h2>CUSTOM TESTS</h2>
<p> gpsfake is a trivial wrapper around a Python module, also named gpsfake, that can be used to fully script sessions involving a gpsd instance, any number of client sessions, and any number of fake GPSes feeding the daemon instance with data from specified sentence logs. </p>
<p> Source and embedded documentation for this module is shipped with the gpsd development tools. You can use it to torture-test either gpsd itself or any gpsd-aware client application. </p>
<p> Logfiles for the use with gpsfake can be retrieved using gpspipe, gpscat, or gpsmon from the gpsd distribution, or any other application which is able to create a compatible output. </p>
