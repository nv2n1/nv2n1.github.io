<h2 class="name">NAME</h2>
<p> guestfs-hacking &#8211; extending and contributing to libguestfs </p>
<h2>DESCRIPTION</h2>
<p> This manual page is for hackers who want to extend libguestfs itself.</p>
<h2>THE SOURCE CODE</h2>
<p> Libguestfs source is located in the github repository <a rel="nofollow" href="https://github.com/libguestfs/libguestfs">https://github.com/libguestfs/libguestfs</a> </p>
<p> Large amounts of boilerplate code in libguestfs (<font SIZE="-1">RPC,</font> bindings, documentation) are generated. This means that many source files will appear to be missing from a straightforward git checkout. You have to run the generator (<tt>&quot;./autogen.sh &amp;&amp; make -C generator&quot;</tt>) in order to create those files. </p>
<p> Libguestfs uses an autotools-based build system, with the main files being <i>configure.ac</i> and <i>Makefile.am</i>. See &#8220;<font SIZE="-1">THE BUILD SYSTEM&#8221;</font>. </p>
<p> The <i>generator</i> subdirectory contains the generator, plus files describing the <font SIZE="-1">API.</font> The <i>lib</i> subdirectory contains source for the library. The <i>appliance</i> and <i>daemon</i> subdirectories contain the source for the code that builds the appliance, and the code that runs in the appliance respectively. Other directories are covered in the section &#8220;<font SIZE="-1">SOURCE CODE SUBDIRECTORIES&#8221;</font> below. </p>
<p> Apart from the fact that all <font SIZE="-1">API</font> entry points go via some generated code, the library is straightforward. (In fact, even the generated code is designed to be readable, and should be read as ordinary code). Some actions run entirely in the library, and are written as C functions in files under <i>lib</i>. Others are forwarded to the daemon where (after some generated <font SIZE="-1">RPC</font> marshalling) they appear as C functions in files under <i>daemon</i>. </p>
<p> To build from source, first read the <code><a href="/docs/linux/man/1-guestfs-building/">guestfs-building</a></code>(1).</p>

<h3><font SIZE="-1">THE BUILD SYSTEM</font></h3>
<p> Libguestfs uses the <font SIZE="-1">GNU</font> autotools build system (autoconf, automake, libtool). </p>
<p> The <i>./configure</i> script is generated from <i>configure.ac</i> and <i>m4/guestfs-*.m4</i>. Most of the configure script is split over many m4 macro files by topic, for example <i>m4/guestfs-daemon.m4</i> deals with the dependencies of the daemon. </p>
<p> The job of the top level <i>Makefile.am</i> is mainly to list the subdirectories (<tt>&quot;SUBDIRS&quot;</tt>) in the order they should be compiled. </p>
<p> <i>common-rules.mk</i> is included in every <i>Makefile.am</i> (top level and subdirectories). <i>subdir-rules.mk</i> is included only in subdirectory <i>Makefile.am</i> files. </p>
<p> There are many make targets. Use this command to list them all: </p>
<pre>
 make help
</pre>
<h2>EXTENDING LIBGUESTFS</h2>
<h3><font SIZE="-1">ADDING A NEW API</font></h3>
<p> Because large amounts of boilerplate code in libguestfs are generated, this makes it easy to extend the libguestfs <font SIZE="-1">API.</font> </p>
<p> To add a new <font SIZE="-1">API</font> action there are two changes:</p>
<dl>
<dt>1.</p>
<dd> You need to add a description of the call (name, parameters, return type, tests, documentation) to <i>generator/actions_*.ml</i> and possibly <i>generator/proc_nr.ml</i>. </p>
<p> There are two sorts of <font SIZE="-1">API</font> action, depending on whether the call goes through to the daemon in the appliance, or is serviced entirely by the library (see &#8220;<font SIZE="-1">ARCHITECTURE&#8221;</font> in <code><a href="/docs/linux/man/1-guestfs-internals/">guestfs-internals</a></code>(1)). &#8220;guestfs_sync&#8221; in <code><a href="/docs/linux/man/3-guestfs/">guestfs</a></code>(3) is an example of the former, since the sync is done in the appliance. &#8220;guestfs_set_trace&#8221; in <code><a href="/docs/linux/man/3-guestfs/">guestfs</a></code>(3) is an example of the latter, since a trace flag is maintained in the handle and all tracing is done on the library side. </p>
<p> Most new actions are of the first type, and get added to the <tt>&quot;daemon_functions&quot;</tt> list. Each function has a unique procedure number used in the <font SIZE="-1">RPC</font> protocol which is assigned to that action when we publish libguestfs and cannot be reused. Take the latest procedure number and increment it. </p>
<p> For library-only actions of the second type, add to the <tt>&quot;non_daemon_functions&quot;</tt> list. Since these functions are serviced by the library and do not travel over the <font SIZE="-1">RPC</font> mechanism to the daemon, these functions do not need a procedure number, and so the procedure number is set to <tt>&quot;-1&quot;</tt>.</p>
<dt>2.</p>
<dd> Implement the action (in C): </p>
<p> For daemon actions, implement the function <tt>&quot;do_&lt;name&gt;&quot;</tt> in the <tt>&quot;daemon/&quot;</tt> directory. </p>
<p> For library actions, implement the function <tt>&quot;guestfs_impl_&lt;name&gt;&quot;</tt> in the <tt>&quot;lib/&quot;</tt> directory. </p>
<p> In either case, use another function as an example of what to do.</p>
<dt>3.</p>
<dd> As an alternative to step 2: Since libguestfs 1.38, daemon actions can be implemented in OCaml. You have to set the <tt>&quot;impl = OCaml ...&quot;</tt> flag in the generator. Take a look at <i>daemon/file.ml</i> for an example.</dl>
<p> After making these changes, use <tt>&quot;make&quot;</tt> to compile. </p>
<p> Note that you don’t need to implement the <font SIZE="-1">RPC,</font> language bindings, manual pages or anything else. It’s all automatically generated from the OCaml description. </p>
<p> <i>Adding tests for an </i><font SIZE="-1"><i>API</i></font><i></i> </p>
<p> You can supply zero or as many tests as you want per <font SIZE="-1">API</font> call. The tests can either be added as part of the <font SIZE="-1">API</font> description (<i>generator/actions_*.ml</i>), or in some rarer cases you may want to drop a script into <tt>&quot;tests/*/&quot;</tt>. Note that adding a script to <tt>&quot;tests/*/&quot;</tt> is slower, so if possible use the first method. </p>
<p> The following describes the test environment used when you add an <font SIZE="-1">API</font> test in <i>actions_*.ml</i>. </p>
<p> The test environment has 4 block devices:</p>
<dl>
<dt><i>/dev/sda</i> 2 <font SIZE="-1">GB</font></p>
<dd> General block device for testing.</p>
<dt><i>/dev/sdb</i> 2 <font SIZE="-1">GB</font></p>
<dd> <i>/dev/sdb1</i> is an ext2 filesystem used for testing filesystem write operations.</p>
<dt><i>/dev/sdc</i> 10 <font SIZE="-1">MB</font></p>
<dd> Used in a few tests where two block devices are needed.</p>
<dt><i>/dev/sdd</i></p>
<dd> <font SIZE="-1">ISO</font> with fixed content (see <i>images/test.iso</i>).</dl>
<p> To be able to run the tests in a reasonable amount of time, the libguestfs appliance and block devices are reused between tests. So don&#8217;t try testing &#8220;guestfs_kill_subprocess&#8221; in <code><a href="/docs/linux/man/3-guestfs/">guestfs</a></code>(3) :-x </p>
<p> Each test starts with an initial scenario, selected using one of the <tt>&quot;Init*&quot;</tt> expressions, described in <i>generator/types.ml</i>. These initialize the disks mentioned above in a particular way as documented in <i>types.ml</i>. You should not assume anything about the previous contents of other disks that are not initialized. </p>
<p> You can add a prerequisite clause to any individual test. This is a run-time check, which, if it fails, causes the test to be skipped. Useful if testing a command which might not work on all variations of libguestfs builds. A test that has prerequisite of <tt>&quot;Always&quot;</tt> means to run unconditionally. </p>
<p> In addition, packagers can skip individual tests by setting environment variables before running <tt>&quot;make check&quot;</tt>. </p>
<pre>
 SKIP_TEST_&lt;CMD&gt;_&lt;NUM&gt;=1
</pre>
<p> eg: <tt>&quot;SKIP_TEST_COMMAND_3=1&quot;</tt> skips test #3 of &#8220;guestfs_command&#8221; in <code><a href="/docs/linux/man/3-guestfs/">guestfs</a></code>(3). </p>
<p> or: </p>
<pre>
 SKIP_TEST_&lt;CMD&gt;=1
</pre>
<p> eg: <tt>&quot;SKIP_TEST_ZEROFREE=1&quot;</tt> skips all &#8220;guestfs_zerofree&#8221; in <code><a href="/docs/linux/man/3-guestfs/">guestfs</a></code>(3) tests. </p>
<p> Packagers can run only certain tests by setting for example: </p>
<pre>
 TEST_ONLY=&quot;vfs_type zerofree&quot;
</pre>
<p> See <i>tests/c-api/tests.c</i> for more details of how these environment variables work. </p>
<p> <i>Debugging new APIs</i> </p>
<p> Test new actions work before submitting them. </p>
<p> You can use guestfish to try out new commands. </p>
<p> Debugging the daemon is a problem because it runs inside a minimal environment. However you can fprintf messages in the daemon to stderr, and they will show up if you use <tt>&quot;guestfish -v&quot;</tt>.</p>
<h3><font SIZE="-1">ADDING A NEW LANGUAGE BINDING</font></h3>
<p> All language bindings must be generated by the generator (see the <i>generator</i> subdirectory). </p>
<p> There is no documentation for this yet. We suggest you look at an existing binding, eg. <i>generator/ocaml.ml</i> or <i>generator/perl.ml</i>. </p>
<p> <i>Adding tests for language bindings</i> </p>
<p> Language bindings should come with tests. Previously testing of language bindings was rather ad-hoc, but we have been trying to formalize the set of tests that every language binding should use. </p>
<p> Currently only the OCaml and Perl bindings actually implement the full set of tests, and the OCaml bindings are canonical, so you should emulate what the OCaml tests do. </p>
<p> This is the numbering scheme used by the tests: </p>
<pre>
 - 000+ basic tests:
 
   010  load the library
   020  create
   030  create-flags
   040  create multiple handles
   050  test setting and getting config properties
   060  explicit close
   065  implicit close (in GC'd languages)
   070  optargs
   080  version
   090  retvalues
 
 - 100  launch, create partitions and LVs and filesystems
 
 - 400+ events:
 
   410  close event
   420  log messages
   430  progress messages
 
 - 800+ regression tests (specific to the language)
 
 - 900+ any other custom tests for the language
</pre>
<p> To save time when running the tests, only 100, 430, 800+, 900+ should launch the handle.</p>
<h3><font SIZE="-1">FORMATTING CODE</font></h3>
<p> Our C source code generally adheres to some basic code-formatting conventions. The existing code base is not totally consistent on this front, but we do prefer that contributed code be formatted similarly. In short, use spaces-not-TABs for indentation, use 2 spaces for each indentation level, and other than that, follow the K&amp;R style. </p>
<p> If you use Emacs, add the following to one of your start-up files (e.g., ~/.emacs), to help ensure that you get indentation right: </p>
<pre><code>
;
;
;
In libguestfs, indent with spaces everywhere(not TABs).;
;
; Exceptions: Makefile and ChangeLog modes.
 (add-hook 'find-file-hook
     '(lambda () (if (and buffer-file-name
                          (string-match "/libguestfs\&gt;"
                              (buffer-file-name))
                          (not (string-equal mode-name "Change Log"))
                          (not (string-equal mode-name "Makefile")))
                     (setq indent-tabs-mode nil))))
 
 ;
;
; When editing C sources in libguestfs, use this style.
 (defun libguestfs-c-mode ()
   "C mode with adjusted defaults for use with libguestfs."
   (interactive)
   (c-set-style "K&amp;R")
   (setq c-indent-level 2)
   (setq c-basic-offset 2))
 (add-hook 'c-mode-hook
           '(lambda () (if (string-match "/libguestfs\&gt;"
                               (buffer-file-name))
                           (libguestfs-c-mode))))
</code></pre>
<h3><font SIZE="-1">TESTING YOUR CHANGES</font></h3>
<p> Turn warnings into errors when developing to make warnings hard to ignore: </p>
<pre>
 ./configure --enable-werror
</pre>
<p> Useful targets are:</p>
<dl>
<dt>&quot;make check&quot;</p>
<dd> Runs the regular test suite. </p>
<p> This is implemented using the regular automake <tt>&quot;TESTS&quot;</tt> target. See the automake documentation for details.</p>
<dt>&quot;make check-valgrind&quot;</p>
<dd> Runs a subset of the test suite under valgrind. </p>
<p> See &#8220;<font SIZE="-1">VALGRIND&#8221;</font> below.</p>
<dt>&quot;make check-valgrind-local-guests&quot;</p>
<dd> Runs a subset of the test suite under valgrind using locally installed libvirt guests (read-only).</p>
<dt>&quot;make check-direct&quot;</p>

<h3><font SIZE="-1">DAEMON CUSTOM PRINTF FORMATTERS</font></h3>
<p> In the daemon code we have created custom printf formatters <tt>%Q</tt> and <tt>%R</tt>, which are used to do shell quoting.</p>

<dt>%Q</p>
<dd> Simple shell quoted string. Any spaces or other shell characters are escaped for you.</p>
<dt>%R</p>

<h2>MISCELLANEOUS TOPICS</h2>
<h3><font SIZE="-1">HOW OCAML PROGRAMS ARE COMPILED AND LINKED</font></h3>
<p> Mostly this section is &#8220;how we make automake &amp; ocamlopt work together&#8221; since OCaml programs themselves are easy to compile. </p>
<p> Automake has no native support for OCaml programs, ocamlc nor ocamlopt. What we do instead is to treat OCaml programs as C programs which happen to contain these &#8220;other objects&#8221; (<tt>&quot;DEPENDENCIES&quot;</tt> in automake-speak) that happen to be the OCaml objects. This works because OCaml programs usually have C files for native bindings etc. </p>
<p> So a typical program is described as just its C sources: </p>
<pre>
 virt_v2v_SOURCES = ... utils-c.c xml-c.c
</pre>
<p> For programs that have no explicit C sources, we create an empty <i>dummy.c</i> file, and list that instead: </p>
<pre>
 virt_resize_SOURCES = dummy.c
</pre>
<p> The OCaml objects which contain most of the code are listed as automake dependencies (other dependencies may also be listed): </p>
<pre>
 virt_v2v_DEPENDENCIES = ... cmdline.cmx v2v.cmx
</pre>
<p> The only other special thing we need to do is to provide a custom link command. This is needed because automake won&#8217;t assemble the ocamlopt command, the list of objects and the <tt>&quot;-cclib&quot;</tt> libraries in the correct order otherwise. </p>
<pre>
 virt_v2v_LINK = \
     $(top_srcdir)/ocaml-link.sh -cclib '-lutils -lgnu' -- ...
</pre>
<p> The actual rules, which you can examine in <i>v2v/Makefile.am</i>, are a little bit more complicated than this because they have to handle:</p>
<dl>
<dt>&bull;</p>
<dd> Compiling for byte code or native code.</p>
<dt>&bull;</p>
<dd> The pattern rules needed to compile the OCaml sources to objects. </p>
<p> These are now kept in <i>subdir-rules.mk</i> at the top level, which is included in every subdirectory <i>Makefile.am</i>.</p>
<dt>&bull;</p>
<dd> Adding OCaml sources files to <tt>&quot;EXTRA_DIST&quot;</tt>. </p>
<p> Automake isn&#8217;t aware of the complete list of sources for a binary, so it will not add them all automatically.</dl>
<h3><font SIZE="-1">VIRT-V2V</font></h3>
<p> First a little history. Virt-v2v has been through at least two complete rewrites, so this is probably about the third version (but we don&#8217;t intend to rewrite it again). The previous version was written in Perl and can be found here: <a rel="nofollow" href="https://git.fedorahosted.org/git/virt-v2v.git">https://git.fedorahosted.org/git/virt-v2v.git</a> </p>
<p> The current version started out as almost a line-for-line rewrite of the Perl code in OCaml + C, and it still has a fairly similar structure. Therefore if there are details of this code that you don&#8217;t understand (especially in the details of guest conversion), checking the Perl code may help. </p>
<p> The files to start with when reading this code are:</p>
<dl>
<dt>&bull;</p>
<dd> <i>types.mli</i></p>
<dt>&bull;</p>
<dd> <i>v2v.ml</i></dl>
<p> <i>types.mli</i> defines all the structures used and passed around when communicating between different bits of the program. <i>v2v.ml</i> controls how the program runs in stages. </p>
<p> After studying those files, you may want to branch out into the input modules (<i>input_*</i>), the output modules (<i>output_*</i>) or the conversion modules (<i>convert_*</i>). The input and output modules define <i>-i</i> and <i>-o</i> options (see the manual). The conversion modules define what guest types we can handle and the detailed steps involved in converting them. </p>
<p> Every other file in this directory is a support module / library of some sort. Some code is written in C, especially where we want to use an external C library such as libxml2.</p>
<h3><font SIZE="-1">VIRT-P2V</font></h3>
<p> Virt-p2v is a front end on virt-v2v. ie. All it does is act as a <font SIZE="-1">GUI</font> front end, and it calls out to virt-v2v to perform the actual conversion. Therefore most of the C code in the <i>p2v/</i> subdirectory is Gtk (<font SIZE="-1">GUI</font>) code, or supporting code for talking to the remote conversion server. There is no special support for physical machines in virt-v2v. They are converted in the same way as foreign VMs. </p>
<p> <i>Running virt-p2v</i> </p>
<p> You can run the <i>p2v/virt-p2v</i> binary directly, but it will try to convert your machine’s real <i>/dev/sda</i> which is unlikely to work well. However virt-p2v also has a test mode in which you can supply a test disk: </p>
<pre>
 make -C p2v run-virt-p2v-directly
</pre>
<p> This is a wrapper around the <code><a href="/docs/linux/man/1-virt-p2v/">virt-p2v</a></code>(1) <i>&#8211;test-disk</i> option. You can control the &#8220;physical machine&#8221; disk by setting <tt>&quot;PHYSICAL_MACHINE&quot;</tt> to point to a disk image. </p>
<p> A more realistic test is to run virt-p2v inside a <font SIZE="-1">VM</font> on the local machine. To do that, do: </p>
<pre>
 make -C p2v run-virt-p2v-in-a-vm
</pre>
<p> This also runs qemu with the &#8220;physical machine&#8221; disk (which you can set by setting <tt>&quot;PHYSICAL_MACHINE&quot;</tt>), a virtual <font SIZE="-1">CD,</font> and a variety of network cards for testing. You can change the qemu binary and add extra qemu options by setting <tt>&quot;QEMU&quot;</tt> and/or <tt>&quot;QEMU_OPTIONS&quot;</tt> on the make commandline. </p>
<p> A third way to run virt-p2v simulates fairly accurately the program being downloaded over <font SIZE="-1">PXE</font> and then doing an automatic conversion of the source physical machine (the non-GUI path &#8212; see next section below): </p>
<pre>
 make -C p2v run-virt-p2v-non-gui-conversion
</pre>
<p> <i>Understanding the virt-p2v code</i> </p>
<p> <i>See also:</i> &#8220;<font SIZE="-1">HOW VIRT-P2V WORKS&#8221;</font> in <code><a href="/docs/linux/man/1-virt-p2v/">virt-p2v</a></code>(1) </p>
<p> There are two paths through the code, <font SIZE="-1">GUI</font> or non-GUI (parsing the kernel command line): </p>
<pre>
 main.c ──────┬─────&#x25b6; gui.c ──────┬─────&#x25b6; conversion.c
              │                   │
              │                   │
              └────&#x25b6; kernel.c ────┘
</pre>
<p> but both paths call back to the <i>conversion.c</i> function <tt>&quot;start_conversion&quot;</tt> to run the remote virt-v2v. </p>
<p> The main task of <i>gui.c</i>/<i>kernel.c</i> is to populate the virt-v2v configuration (<i>config.c</i>). </p>
<p> During conversion, we need to establish ssh connections, and that is done using two libraries: </p>
<pre>
 conversion.c ──────&#x25b6; ssh.c ──────&#x25b6; miniexpect.c
</pre>
<p> where <i>ssh.c</i> is responsible for managing ssh connections overall, and <i>miniexpect.c</i> implements &#8220;expect-like&#8221; functionality for talking interactively to the remote virt-v2v conversion server. </p>
<p> (Note that miniexpect is a separate library with its own upstream, so if you patch miniexpect.c, then please make sure the changes get reflected in miniexpect’s upstream too: <i><a rel="nofollow" href="http://git.annexia.org/?p=miniexpect.git;a=summary">http://git.annexia.org/?p=miniexpect.git;a=summary</a></i>)</p>

<p> Return the location of firmware needed to boot the appliance. This is aarch64 only currently, since that&#8217;s the only architecture where <font SIZE="-1">UEFI</font> is mandatory (and that only for <font SIZE="-1">RHEL</font>). </p>
<p> <tt>*code</tt> is initialized with the path to the read-only <font SIZE="-1">UEFI</font> code file. <tt>*vars</tt> is initialized with the path to a copy of the <font SIZE="-1">UEFI</font> vars file (which is cleaned up automatically on exit). </p>
<p> If <tt>*code</tt> == <tt>*vars</tt> == <tt>&quot;NULL&quot;</tt> then no <font SIZE="-1">UEFI</font> firmware is available. </p>
<p> <tt>*code</tt> and <tt>*vars</tt> should be freed by the caller. </p>
<p> If the function returns <tt>&quot;-1&quot;</tt> then there was a real error which should cause appliance building to fail (no <font SIZE="-1">UEFI</font> firmware is not an error). </p>
<p> See also <i>v2v/utils.ml</i>:find_uefi_firmware </p>

<p> Function <tt>&quot;lib/appliance.c:guestfs_int_build_appliance&quot;</tt> </p>
<p>int guestfs_int_build_appliance(guestfs_h *g,<br />
                                char **kernel_rtn,<br />
                                char **initrd_rtn,<br />
                                char **appliance_rtn)</p>
<p> Locate or build the appliance. </p>
<p> This function locates or builds the appliance as necessary, handling the supermin appliance, caching of supermin-built appliances, or using either a fixed or old-style appliance. </p>
<p> The return value is <tt>0</tt> = good, <tt>&quot;-1&quot;</tt> = error. Returned in <tt>&quot;appliance.kernel&quot;</tt> will be the name of the kernel to use, <tt>&quot;appliance.initrd&quot;</tt> the name of the initrd, <tt>&quot;appliance.image&quot;</tt> the name of the ext2 root filesystem. <tt>&quot;appliance.image&quot;</tt> can be <tt>&quot;NULL&quot;</tt>, meaning that we are using an old-style (non-ext2) appliance. All three strings must be freed by the caller. However the referenced files themselves must <i>not</i> be deleted. </p>
<p> The process is as follows:</p>
<dl>
<dt>1.</p>
<dd> Look in <tt>&quot;path&quot;</tt> which contains a supermin appliance skeleton. If no element has this, skip straight to step 3.</p>
<dt>2.</p>
<dd> Call <tt>&quot;supermin --build&quot;</tt> to build the full appliance (if it needs to be rebuilt). If this is successful, return the full appliance.</p>
<dt>3.</p>
<dd> Check <tt>&quot;path&quot;</tt>, looking for a fixed appliance. If one is found, return it.</p>
<dt>4.</p>
<dd> Check <tt>&quot;path&quot;</tt>, looking for an old-style appliance. If one is found, return it.</dl>
<p> The supermin appliance cache directory lives in <i></i>$TMPDIR<i>/.guestfs-$UID/</i> and consists of up to four files: </p>
<pre>
  $TMPDIR/.guestfs-$UID/lock            - the supermin lock file
  $TMPDIR/.guestfs-$UID/appliance.d/kernel - the kernel
  $TMPDIR/.guestfs-$UID/appliance.d/initrd - the supermin initrd
  $TMPDIR/.guestfs-$UID/appliance.d/root   - the appliance
</pre>
<p> Multiple instances of libguestfs with the same <font SIZE="-1">UID</font> may be racing to create an appliance. However (since supermin ≥ 5) supermin provides a <i>&#8211;lock</i> flag and atomic update of the <i>appliance.d</i> subdirectory. </p>

<p> <i>File lib/command.c</i> </p>
<p> A wrapper for running external commands, loosely based on libvirt&#8217;s <tt>&quot;virCommand&quot;</tt> interface. </p>
<p> In outline to use this interface you must:</p>
<dl>
<dt>1.</p>
<dd> Create a new command handle: </p>
<p>struct command *cmd;<br />
cmd = guestfs_int_new_command(g);</p>
<dt>2.</p>
<dd> <i>Either</i> add arguments: </p>
<p>guestfs_int_cmd_add_arg(cmd, &#8220;qemu-img&#8221;);<br />
guestfs_int_cmd_add_arg(cmd, &#8220;info&#8221;);<br />
guestfs_int_cmd_add_arg(cmd, filename);</p>
<p> (<font SIZE="-1"><code>NB:</code></font> You don&#8217;t need to add a <tt>&quot;NULL&quot;</tt> argument at the end.)</p>
<dt>3.</p>
<dd> <i>Or</i> construct a command using a mix of quoted and unquoted strings. (This is useful for <code><a href="/docs/linux/man/3-system/">system</a></code>(3)/<tt>&quot;popen(&quot;r&quot;)&quot;</tt>-style shell commands, with the added safety of allowing args to be quoted properly). </p>
<p>guestfs_int_cmd_add_string_unquoted(cmd, &#8220;qemu-img info &#8220;);<br />
guestfs_int_cmd_add_string_quoted(cmd, filename);</p>
<dt>4.</p>
<dd> Set various flags, such as whether you want to capture errors in the regular libguestfs error log.</p>
<dt>5.</p>
<dd> Run the command. This is what does the <code><a href="/docs/linux/man/2-fork/">fork</a></code>(2) call, optionally loops over the output, and then does a <code><a href="/docs/linux/man/3-waitpid/">waitpid</a></code>(3) and returns the exit status of the command. </p>
<p>r = guestfs_int_cmd_run(cmd);<br />
if (r == -1)<br />
// error<br />
// else test r using the WIF* functions</p>
<dt>6.</p>
<dd> Close the handle: </p>
<pre>
 guestfs_int_cmd_close (cmd);
</pre>
<p> (or use <tt>&quot;CLEANUP_CMD_CLOSE&quot;</tt>).</dl>
