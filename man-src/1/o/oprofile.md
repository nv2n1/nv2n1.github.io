<h2 class="name">NAME</h2>
<p> oprofile &#8211; a system-wide profiler </p>
<h2>SYNOPSIS</h2>
<p> <code>opcontrol</code> [ <i>options</i> ]<br />
 <code>opreport</code> [ <i>options</i> ] [ profile specification ]<br />
 <code>opannotate</code> [ <i>options</i> ] [ profile specification ]<br />
 <code>oparchive</code> [ <i>options</i> ] [ profile specification ]<br />
 <code>opgprof</code> [ <i>options</i> ] [ profile specification ] </p>
<h2>DESCRIPTION</h2>
<p> OProfile is a profiling system for systems running Linux 2.6 and greater. Profiling runs transparently in the background and profile data can be collected at any time. OProfile makes use of the hardware performance counters provided on Intel, AMD, and other processors, and uses a timer-interrupt based mechanism on CPUs without counters. OProfile can profile the whole system in high detail.<br />
 For a gentle guide to using OProfile, please read the HTML documentation listed in SEE ALSO. </p>
<h2>OPCONTROL</h2>
<p> <code>opcontrol</code> is used for starting and stopping the OProfile daemon, and providing set-up parameters.</p>
<h2>OPREPORT</h2>
<p> <code>opreport</code> gives image and symbol-based profile summaries for the whole system or a subset of binary images.</p>
<h2>OPANNOTATE</h2>
<p> <code>opannotate</code> can produce annotated source or mixed source and assembly output.</p>
<h2>OPARCHIVE</h2>
<p> <code>oparchive</code> produces oprofile archive for offline analysis</p>
<h2>OPGPROF</h2>
<p> <code>opgprof</code> can produce a gprof-format profile for a single binary. </p>
<h2>PROFILE SPECIFICATIONS</h2>
<p> All of the post-profiling tools can take profile specifications, which is some combination of the following parameters. Enclosing part of a profile specification in curly braces { } can be used for differential profiles with <code>opreport</code> ; the braces <code>must</code> be surrounded by whitespace. </p>
<dl>
<dt><code>archive:archive</code></p>
<dd> Path to the archive to inspect, as generated by <code>oparchive</code> </p>
<dt><code>session:sessionlist</code></p>
<dd> A comma-separated list of session names to resolve in. Absence of this tag, unlike all others, means &quot;the current session&quot;, equivalent to specifying &quot;session:current&quot;. </p>
<dt><code>session-exclude:sessionlist</code></p>
<dd> A comma-separated list of sessions to exclude. </p>
<dt><code>image:imagelist</code></p>
<dd> A comma-separated list of image names to resolve. Each entry may be relative path, glob-style name, or full path, e.g. opreport &#8216;image:/usr/bin/oprofiled,*op*,./oprofpp&#8217; </p>
<dt><code>image-exclude:imagelist</code></p>
<dd> Same as image:, but the matching images are excluded. </p>
<dt><code>lib-image:imagelist</code></p>
<dd> Same as image:, but only for images that are for a particular primary binary image (namely, an application). This only makes sense to use if you&#8217;re using &#8211;separate. This includes kernel modules and the kernel when using &#8211;separate=kernel. </p>
<dt><code>lib-image-exclude:imagelist</code></p>
<dd> Same as &lt;option&gt;lib-image:&lt;/option&gt;, but the matching images are excluded. </p>
<dt><code>event:eventname</code></p>
<dd> The symbolic event name to match on, e.g. event:DATA_MEM_REFS. </p>
<dt><code>count:eventcount</code></p>
<dd> The event count to match on, e.g. event:DATA_MEM_REFS count:30000. </p>
<dt><code>unit-mask:maskvalue</code></p>
<dd> The unit mask value of the event to match on, e.g. unit-mask:1. </p>
<dt><code>cpu:cpulist</code></p>
<dd> Only consider profiles for the given numbered CPU (starting from zero). This is only useful when using CPU profile separation. </p>
<dt><code>tgid:pidlist</code></p>
<dd> Only consider profiles for the given task groups. Unless some program is using threads, the task group ID of a process is the same as its process ID. This option corresponds to the POSIX notion of a thread group. This is only useful when using per-process profile separation. </p>
<dt><code>tid:tidlist</code></p>
<dd> Only consider profiles for the given threads. When using recent thread libraries, all threads in a process share the same task group ID, but have different thread IDs. You can use this option in combination with tgid: to restrict the results to particular threads within a process. This is only useful when using per-process profile separation. </p>
</dl>
<h2>ENVIRONMENT</h2>
<p> No special environment variables are recognised by oprofile. </p>
<h2>FILES</h2>
<dl>
<dt><i>$HOME/.oprofile/</i></p>
<dd> Configuration files</p>
<dt><i>/root/.oprofile/daemonrc</i></p>
<dd> Configuration file for opcontrol</p>
<dt><i>/usr/share/oprofile/</i></p>
<dd> Event description files used by OProfile.</p>
<dt><i>/var/lib/oprofile/samples/oprofiled.log</i></p>
<dd> The user-space daemon logfile.</p>
<dt><i>/dev/oprofile</i></p>
<dd> The device filesystem for communication with the Linux kernel module.</p>
<dt><i>/var/lib/oprofile/samples/</i></p>
<dd> The location of the generated sample files. </p>
</dl>
