<p>ocamlc &#8211; The OCaml bytecode compiler</p>
<h2>Synopsis</h2>
<p><code>ocamlc</code> [ <i>options</i> ] <i>filename &#8230;</i> </p>
<p> <code>ocamlc.opt</code> [ <i>options</i> ] <i>filename &#8230;</i> </p>
<h2>Description</h2>
<p>The OCaml bytecode compiler <code><a href="/docs/linux/man/1-ocamlc/">ocamlc</a></code>(1) compiles OCaml source files to bytecode object files and links these object files to produce standalone bytecode executable files. These executable files are then run by the bytecode interpreter <code><a href="/docs/linux/man/1-ocamlrun/">ocamlrun</a></code>(1). </p>
<p> The <code><a href="/docs/linux/man/1-ocamlc/">ocamlc</a></code>(1) command has a command-line interface similar to the one of most C compilers. It accepts several types of arguments and processes them sequentially: </p>
<p> Arguments ending in .mli are taken to be source files for compilation unit interfaces. Interfaces specify the names exported by compilation units: they declare value names with their types, define public data types, declare abstract data types, and so on. From the file <i>x</i>.mli, the <code><a href="/docs/linux/man/1-ocamlc/">ocamlc</a></code>(1) compiler produces a compiled interface in the file <i>x</i>.cmi. </p>
<p> Arguments ending in .ml are taken to be source files for compilation unit implementations. Implementations provide definitions for the names exported by the unit, and also contain expressions to be evaluated for their side-effects. From the file <i>x</i>.ml, the <code><a href="/docs/linux/man/1-ocamlc/">ocamlc</a></code>(1) compiler produces compiled object bytecode in the file <i>x</i>.cmo. </p>
<p> If the interface file <i>x</i>.mli exists, the implementation <i>x</i>.ml is checked against the corresponding compiled interface <i>x</i>.cmi, which is assumed to exist. If no interface <i>x</i>.mli is provided, the compilation of <i>x</i>.ml produces a compiled interface file <i>x</i>.cmi in addition to the compiled object code file <i>x</i>.cmo. The file <i>x</i>.cmi produced corresponds to an interface that exports everything that is defined in the implementation <i>x</i>.ml. </p>
<p> Arguments ending in .cmo are taken to be compiled object bytecode. These files are linked together, along with the object files obtained by compiling .ml arguments (if any), and the OCaml standard library, to produce a standalone executable program. The order in which .cmo and.ml arguments are presented on the command line is relevant: compilation units are initialized in that order at run-time, and it is a link-time error to use a component of a unit before having initialized it. Hence, a given <i>x</i>.cmo file must come before all .cmo files that refer to the unit <i>x</i>. </p>
<p> Arguments ending in .cma are taken to be libraries of object bytecode. A library of object bytecode packs in a single file a set of object bytecode files (.cmo files). Libraries are built with <code>ocamlc -a</code> (see the description of the <code>-a</code> option below). The object files contained in the library are linked as regular .cmo files (see above), in the order specified when the .cma file was built. The only difference is that if an object file contained in a library is not referenced anywhere in the program, then it is not linked in. </p>
<p> Arguments ending in .c are passed to the C compiler, which generates a .o object file. This object file is linked with the program if the <code>-custom</code> flag is set (see the description of <code>-custom</code> below). </p>
<p> Arguments ending in .o or .a are assumed to be C object files and libraries. They are passed to the C linker when linking in <code>-custom</code> mode (see the description of <code>-custom</code> below). </p>
<p> Arguments ending in .so are assumed to be C shared libraries (DLLs). During linking, they are searched for external C functions referenced from the OCaml code, and their names are written in the generated bytecode executable. The run-time system <code><a href="/docs/linux/man/1-ocamlrun/">ocamlrun</a></code>(1) then loads them dynamically at program start-up time. </p>
<p> The output of the linking phase is a file containing compiled bytecode that can be executed by the OCaml bytecode interpreter: the command <code><a href="/docs/linux/man/1-ocamlrun/">ocamlrun</a></code>(1). If <code>caml.out</code> is the name of the file produced by the linking phase, the command <code>ocamlrun caml.out</code> <i>arg1</i>&nbsp;<wbr><i>&nbsp;<wbr>arg2</i>&nbsp;<wbr>&#8230;<i>&nbsp;<wbr>argn</i> executes the compiled code contained in <code>caml.out</code>, passing it as arguments the character strings <i>arg1</i> to <i>argn</i>. (See <code><a href="/docs/linux/man/1-ocamlrun/">ocamlrun</a></code>(1) for more details.) </p>
<p> On most systems, the file produced by the linking phase can be run directly, as in: <code>./caml.out</code> <i>arg1</i>&nbsp;<wbr><i>&nbsp;<wbr>arg2</i>&nbsp;<wbr>&#8230;<i>&nbsp;<wbr>argn</i>. The produced file has the executable bit set, and it manages to launch the bytecode interpreter by itself. </p>
<p> <code>ocamlc.opt</code> is the same compiler as <code>ocamlc</code>, but compiled with the native-code compiler <code><a href="/docs/linux/man/1-ocamlopt/">ocamlopt</a></code>(1). Thus, it behaves exactly like <code>ocamlc</code>, but compiles faster. <code>ocamlc.opt</code> may not be available in all installations of OCaml. </p>
<h2>Options</h2>
<p>The following command-line options are recognized by <code><a href="/docs/linux/man/1-ocamlc/">ocamlc</a></code>(1).</p>
<dl COMPACT>
<dt><code>-a</code></p>
<dd>Build a library (.cma file) with the object files (.cmo files) given on the command line, instead of linking them into an executable file. The name of the library must be set with the <code>-o</code> option.</p>
<dd>If <code>-custom</code>,<code>&nbsp;<wbr>-cclib</code>&nbsp;<wbr>or<code>&nbsp;<wbr>-ccopt</code> options are passed on the command line, these options are stored in the resulting .cma library. Then, linking with this library automatically adds back the <code>-custom</code>,<code>&nbsp;<wbr>-cclib</code>&nbsp;<wbr>and<code>&nbsp;<wbr>-ccopt</code> options as if they had been provided on the command line, unless the <code>-noautolink</code> option is given.</p>
<dt><code>-absname</code></p>
<dd>Show absolute filenames in error messages.</p>
<dt><code>-annot</code></p>
<dd>Dump detailed information about the compilation (types, bindings, tail-calls, etc). The information for file <i>src</i>.ml is put into file <i>src</i>.annot. In case of a type error, dump all the information inferred by the type-checker before the error. The <i>src</i>.annot file can be used with the emacs commands given in <code>emacs/caml-types.el</code> to display types and other annotations interactively.</p>
<dt><code>-bin-annot</code></p>
<dd>Dump detailed information about the compilation (types, bindings, tail-calls, etc) in binary format. The information for file <i>src</i>.ml is put into file <i>src</i>.cmt. In case of a type error, dump all the information inferred by the type-checker before the error. The annotation files produced by <code>-bin-annot</code> contain more information and are much more compact than the files produced by <code>-annot</code>.</p>
<dt><code>-c</code></p>
<dd>Compile only. Suppress the linking phase of the compilation. Source code files are turned into compiled files, but no executable file is produced. This option is useful to compile modules separately.</p>
<dt><code>-cc</code><i>&nbsp;<wbr>ccomp</i></p>
<dd>Use <i>ccomp</i> as the C linker when linking in &quot;custom runtime&quot; mode (see the <code>-custom</code> option) and as the C compiler for compiling .c source files.</p>
<dt><code>-cclib -l</code><i>libname</i></p>
<dd>Pass the <code>-l</code><i>libname</i> option to the C linker when linking in &quot;custom runtime&quot; mode (see the <code>-custom</code> option). This causes the given C library to be linked with the program.</p>
<dt><code>-ccopt</code><i>&nbsp;<wbr>option</i></p>
<dd>Pass the given <i>option</i> to the C compiler and linker, when linking in &quot;custom runtime&quot; mode (see the <code>-custom</code> option). For instance, <code>-ccopt -L</code><i>dir</i> causes the C linker to search for C libraries in directory <i>dir</i>.</p>
<dt><code>-compat-32</code></p>
<dd>Check that the generated bytecode executable can run on 32-bit platforms and signal an error if it cannot. This is useful when compiling bytecode on a 64-bit machine.</p>
<dt><code>-config</code></p>
<dd>Print the version number of <code><a href="/docs/linux/man/1-ocamlc/">ocamlc</a></code>(1) and a detailed summary of its configuration, then exit.</p>
<dt><code>-custom</code></p>
<dd>Link in &quot;custom runtime&quot; mode. In the default linking mode, the linker produces bytecode that is intended to be executed with the shared runtime system, <code><a href="/docs/linux/man/1-ocamlrun/">ocamlrun</a></code>(1). In the custom runtime mode, the linker produces an output file that contains both the runtime system and the bytecode for the program. The resulting file is larger, but it can be executed directly, even if the <code><a href="/docs/linux/man/1-ocamlrun/">ocamlrun</a></code>(1) command is not installed. Moreover, the &quot;custom runtime&quot; mode enables linking OCaml code with user-defined C functions. </p>
<p> Never use the <code><a href="/docs/linux/man/1-strip/">strip</a></code>(1) command on executables produced by <code>ocamlc -custom</code>, this would remove the bytecode part of the executable.</p>
<dt><code>-dllib -l</code><i>libname</i></p>
<dd>Arrange for the C shared library <code>dll</code><i>libname</i><code>.so</code> to be loaded dynamically by the run-time system <code><a href="/docs/linux/man/1-ocamlrun/">ocamlrun</a></code>(1) at program start-up time.</p>
<dt><code>-dllpath</code><i>&nbsp;<wbr>dir</i></p>
<dd>Adds the directory <i>dir</i> to the run-time search path for shared C libraries. At link-time, shared libraries are searched in the standard search path (the one corresponding to the <code>-I</code> option). The <code>-dllpath</code> option simply stores <i>dir</i> in the produced executable file, where <code><a href="/docs/linux/man/1-ocamlrun/">ocamlrun</a></code>(1) can find it and use it.</p>
<dt><code>-for-pack</code><i>&nbsp;<wbr>ident</i></p>
<dd>This option is accepted for compatibility with <code><a href="/docs/linux/man/1-ocamlopt/">ocamlopt</a></code>(1) ; it does nothing.</p>
<dt><code>-g</code></p>
<dd>Add debugging information while compiling and linking. This option is required in order to be able to debug the program with <code><a href="/docs/linux/man/1-ocamldebug/">ocamldebug</a></code>(1) and to produce stack backtraces when the program terminates on an uncaught exception.</p>
<dt><code>-i</code></p>
<dd>Cause the compiler to print all defined names (with their inferred types or their definitions) when compiling an implementation (.ml file). No compiled files (.cmo and .cmi files) are produced. This can be useful to check the types inferred by the compiler. Also, since the output follows the syntax of interfaces, it can help in writing an explicit interface (.mli file) for a file: just redirect the standard output of the compiler to a .mli file, and edit that file to remove all declarations of unexported names.</p>
<dt><code>-I</code><i>&nbsp;<wbr>directory</i></p>
<dd>Add the given directory to the list of directories searched for compiled interface files (.cmi), compiled object code files (.cmo), libraries (.cma), and C libraries specified with <code>-cclib -l</code><i>xxx</i> . By default, the current directory is searched first, then the standard library directory. Directories added with <code>-I</code> are searched after the current directory, in the order in which they were given on the command line, but before the standard library directory. See also option <code>-nostdlib</code>. </p>
<p> If the given directory starts with <code>+</code>, it is taken relative to the standard library directory. For instance, <code>-I&nbsp;<wbr>+labltk</code> adds the subdirectory <code>labltk</code> of the standard library to the search path.</p>
<dt><code>-impl</code><i>&nbsp;<wbr>filename</i></p>
<dd>Compile the file <i>filename</i> as an implementation file, even if its extension is not .ml.</p>
<dt><code>-intf</code><i>&nbsp;<wbr>filename</i></p>
<dd>Compile the file <i>filename</i> as an interface file, even if its extension is not .mli.</p>
<dt><code>-intf-suffix</code><i>&nbsp;<wbr>string</i></p>
<dd>Recognize file names ending with <i>string</i> as interface files (instead of the default .mli).</p>
<dt><code>-labels</code></p>
<dd>Labels are not ignored in types, labels may be used in applications, and labelled parameters can be given in any order. This is the default.</p>
<dt><code>-linkall</code></p>
<dd>Force all modules contained in libraries to be linked in. If this flag is not given, unreferenced modules are not linked in. When building a library (option <code>-a</code>), setting the <code>-linkall</code> option forces all subsequent links of programs involving that library to link all the modules contained in the library.</p>
<dt><code>-make-runtime</code></p>
<dd>Build a custom runtime system (in the file specified by option <code>-o</code>) incorporating the C object files and libraries given on the command line. This custom runtime system can be used later to execute bytecode executables produced with the option <code>ocamlc -use-runtime</code> <i>runtime-name</i>.</p>
<dt><code>-no-app-funct</code></p>
<dd>Deactivates the applicative behaviour of functors. With this option, each functor application generates new types in its result and applying the same functor twice to the same argument yields two incompatible structures.</p>
<dt><code>-noassert</code></p>
<dd>Do not compile assertion checks. Note that the special form <code>assert false</code> is always compiled because it is typed specially. This flag has no effect when linking already-compiled files.</p>
<dt><code>-noautolink</code></p>
<dd>When linking .cma libraries, ignore <code>-custom</code>,<code>&nbsp;<wbr>-cclib</code>&nbsp;<wbr>and<code>&nbsp;<wbr>-ccopt</code> options potentially contained in the libraries (if these options were given when building the libraries). This can be useful if a library contains incorrect specifications of C libraries or C options; in this case, during linking, set <code>-noautolink</code> and pass the correct C libraries and options on the command line.</p>
<dt><code>-nolabels</code></p>
<dd>Ignore non-optional labels in types. Labels cannot be used in applications, and parameter order becomes strict.</p>
<dt><code>-nostdlib</code></p>
<dd>Do not automatically add the standard library directory to the list of directories searched for compiled interface files (.cmi), compiled object code files (.cmo), libraries (.cma), and C libraries specified with <code>-cclib -l</code><i>xxx</i> . See also option <code>-I</code>.</p>
<dt><code>-o</code><i>&nbsp;<wbr>exec-file</i></p>
<dd>Specify the name of the output file produced by the linker. The default output name is <code>a.out</code>, in keeping with the Unix tradition. If the <code>-a</code> option is given, specify the name of the library produced. If the <code>-pack</code> option is given, specify the name of the packed object file produced. If the <code>-output-obj</code> option is given, specify the name of the output file produced.</p>
<dt><code>-output-obj</code></p>
<dd>Cause the linker to produce a C object file instead of a bytecode executable file. This is useful to wrap OCaml code as a C library, callable from any C program. The name of the output object file must be set with the <code>-o</code> option. This option can also be used to produce a C source file (.c extension) or a compiled shared/dynamic library (.so extension).</p>
<dt><code>-pack</code></p>
<dd>Build a bytecode object file (.cmo file) and its associated compiled interface (.cmi) that combines the object files given on the command line, making them appear as sub-modules of the output .cmo file. The name of the output .cmo file must be given with the <code>-o</code> option. For instance, <code>ocamlc -pack -o p.cmo a.cmo b.cmo c.cmo</code> generates compiled files p.cmo and p.cmi describing a compilation unit having three sub-modules A, B and C, corresponding to the contents of the object files a.cmo, b.cmo and c.cmo. These contents can be referenced as P.A, P.B and P.C in the remainder of the program.</p>
<dt><code>-pp</code><i>&nbsp;<wbr>command</i></p>
<dd>Cause the compiler to call the given <i>command</i> as a preprocessor for each source file. The output of <i>command</i> is redirected to an intermediate file, which is compiled. If there are no compilation errors, the intermediate file is deleted afterwards. The name of this file is built from the basename of the source file with the extension .ppi for an interface (.mli) file and .ppo for an implementation (.ml) file.</p>
<dt><code>-ppx</code><i>&nbsp;<wbr>command</i></p>
<dd>After parsing, pipe the abstract syntax tree through the preprocessor <i>command</i>. The format of the input and ouput of the preprocessor are not yet documented.</p>
<dt><code>-principal</code></p>
<dd>Check information path during type-checking, to make sure that all types are derived in a principal way. When using labelled arguments and/or polymorphic methods, this flag is required to ensure future versions of the compiler will be able to infer types correctly, even if internal algorithms change. All programs accepted in <code>-principal</code> mode are also accepted in the default mode with equivalent types, but different binary signatures, and this may slow down type checking; yet it is a good idea to use it once before publishing source code.</p>
<dt><code>-rectypes</code></p>
<dd>Allow arbitrary recursive types during type-checking. By default, only recursive types where the recursion goes through an object type are supported. Note that once you have created an interface using this flag, you must use it again for all dependencies.</p>
<dt><code>-runtime-variant</code><i>&nbsp;<wbr>suffix</i></p>
<dd>Add <i>suffix</i> to the name of the runtime library that will be used by the program. If OCaml was configured with option <code>-with-debug-runtime</code>, then the <code>d</code> suffix is supported and gives a debug version of the runtime.</p>
<dt><code>-short-paths</code></p>
<dd>When a type is visible under several module-paths, use the shortest one when printing the type&#8217;s name in inferred interfaces and error and warning messages.</p>
<dt><code>-strict-sequence</code></p>
<dd>Force the left-hand part of each sequence to have type unit.</p>
<dt><code>-thread</code></p>
<dd>Compile or link multithreaded programs, in combination with the system &quot;threads&quot; library described in <i>The OCaml user&#8217;s manual</i>.</p>
<dt><code>-unsafe</code></p>
<dd>Turn bound checking off for array and string accesses (the <code>v.(i)</code>and<code>s.[i]</code> constructs). Programs compiled with <code>-unsafe</code> are therefore slightly faster, but unsafe: anything can happen if the program accesses an array or string outside of its bounds.</p>
<dt><code>-use-runtime</code><i>&nbsp;<wbr>runtime-name</i></p>
<dd>Generate a bytecode executable file that can be executed on the custom runtime system <i>runtime-name</i>, built earlier with <code>ocamlc -make-runtime</code> <i>runtime-name</i>.</p>
<dt><code>-v</code></p>
<dd>Print the version number of the compiler and the location of the standard library directory, then exit.</p>
<dt><code>-verbose</code></p>
<dd>Print all external commands before they are executed, in particular invocations of the C compiler and linker in <code>-custom</code> mode. Useful to debug C library problems.</p>
<dt><code>-vmthread</code></p>
<dd>Compile or link multithreaded programs, in combination with the VM-level threads library described in <i>The OCaml user&#8217;s manual</i>.</p>
<dt><code>-vnum</code>&nbsp;<wbr>or&nbsp;<wbr><code>-version</code></p>
<dd>Print the version number of the compiler in short form (e.g. &quot;3.11.0&quot;), then exit.</p>
<dt><code>-w</code><i>&nbsp;<wbr>warning-list</i></p>
<dd>Enable, disable, or mark as fatal the warnings specified by the argument <i>warning-list</i>. </p>
<p> Each warning can be <i>enabled</i>&nbsp;<wbr>or&nbsp;<wbr><i>disabled</i>, and each warning can be <i>fatal</i>or <i>non-fatal</i>. If a warning is disabled, it isn&#8217;t displayed and doesn&#8217;t affect compilation in any way (even if it is fatal). If a warning is enabled, it is displayed normally by the compiler whenever the source code triggers it. If it is enabled and fatal, the compiler will also stop with an error after displaying it. </p>
<p> The <i>warning-list</i> argument is a sequence of warning specifiers, with no separators between them. A warning specifier is one of the following: </p>
<p> <code>+</code><i>num</i> &nbsp;<wbr>&nbsp;<wbr>Enable warning number <i>num</i>. </p>
<p> <code>&#8211;</code><i>num</i> &nbsp;<wbr>&nbsp;<wbr>Disable warning number <i>num</i>. </p>
<p> <code>@</code><i>num</i> &nbsp;<wbr>&nbsp;<wbr>Enable and mark as fatal warning number <i>num</i>. </p>
<p> <code>+</code><i>num1</i><code>..</code><i>num2</i> &nbsp;<wbr>&nbsp;<wbr>Enable all warnings between <i>num1</i> and <i>num2</i> (inclusive). </p>
<p> <code>&#8211;</code><i>num1</i><code>..</code><i>num2</i> &nbsp;<wbr>&nbsp;<wbr>Disable all warnings between <i>num1</i> and <i>num2</i> (inclusive). </p>
<p> <code>@</code><i>num1</i><code>..</code><i>num2</i> &nbsp;<wbr>&nbsp;<wbr>Enable and mark as fatal all warnings between <i>num1</i> and <i>num2</i> (inclusive). </p>
<p> <code>+</code><i>letter</i> &nbsp;<wbr>&nbsp;<wbr>Enable the set of warnings corresponding to <i>letter</i>. The letter may be uppercase or lowercase. </p>
<p> <code>&#8211;</code><i>letter</i> &nbsp;<wbr>&nbsp;<wbr>Disable the set of warnings corresponding to <i>letter</i>. The letter may be uppercase or lowercase. </p>
<p> <code>@</code><i>letter</i> &nbsp;<wbr>&nbsp;<wbr>Enable and mark as fatal the set of warnings corresponding to <i>letter</i>. The letter may be uppercase or lowercase. </p>
<p> <i>uppercase-letter</i> &nbsp;<wbr>&nbsp;<wbr>Enable the set of warnings corresponding to <i>uppercase-letter</i>. </p>
<p> <i>lowercase-letter</i> &nbsp;<wbr>&nbsp;<wbr>Disable the set of warnings corresponding to <i>lowercase-letter</i>. </p>
<p> The warning numbers are as follows. </p>
<p> 1 &nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>Suspicious-looking start-of-comment mark. </p>
<p> 2 &nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>Suspicious-looking end-of-comment mark. </p>
<p> 3 &nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>Deprecated feature. </p>
<p> 4 &nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>Fragile pattern matching: matching that will remain complete even if additional constructors are added to one of the variant types matched. </p>
<p> 5 &nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>Partially applied function: expression whose result has function type and is ignored. </p>
<p> 6 &nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>Label omitted in function application. </p>
<p> 7 &nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>Method overridden without using the &quot;method!&quot; keyword </p>
<p> 8 &nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>Partial match: missing cases in pattern-matching. </p>
<p> 9 &nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>Missing fields in a record pattern. </p>
<p> 10 &nbsp;<wbr>&nbsp;<wbr>Expression on the left-hand side of a sequence that doesn&#8217;t have type <code>unit</code> (and that is not a function, see warning number 5). </p>
<p> 11 &nbsp;<wbr>&nbsp;<wbr>Redundant case in a pattern matching (unused match case). </p>
<p> 12 &nbsp;<wbr>&nbsp;<wbr>Redundant sub-pattern in a pattern-matching. </p>
<p> 13 &nbsp;<wbr>&nbsp;<wbr>Override of an instance variable. </p>
<p> 14 &nbsp;<wbr>&nbsp;<wbr>Illegal backslash escape in a string constant. </p>
<p> 15 &nbsp;<wbr>&nbsp;<wbr>Private method made public implicitly. </p>
<p> 16 &nbsp;<wbr>&nbsp;<wbr>Unerasable optional argument. </p>
<p> 17 &nbsp;<wbr>&nbsp;<wbr>Undeclared virtual method. </p>
<p> 18 &nbsp;<wbr>&nbsp;<wbr>Non-principal type. </p>
<p> 19 &nbsp;<wbr>&nbsp;<wbr>Type without principality. </p>
<p> 20 &nbsp;<wbr>&nbsp;<wbr>Unused function argument. </p>
<p> 21 &nbsp;<wbr>&nbsp;<wbr>Non-returning statement. </p>
<p> 22 &nbsp;<wbr>&nbsp;<wbr>Camlp4 warning. </p>
<p> 23 &nbsp;<wbr>&nbsp;<wbr>Useless record <code>with</code> clause. </p>
<p> 24 &nbsp;<wbr>&nbsp;<wbr>Bad module name: the source file name is not a valid OCaml module name. </p>
<p> 25 &nbsp;<wbr>&nbsp;<wbr>Pattern-matching with all clauses guarded. </p>
<p> 26 &nbsp;<wbr>&nbsp;<wbr>Suspicious unused variable: unused variable that is bound with <code>let</code>&nbsp;<wbr>or<code>&nbsp;<wbr>as</code>, and doesn&#8217;t start with an underscore (_) character. </p>
<p> 27 &nbsp;<wbr>&nbsp;<wbr>Innocuous unused variable: unused variable that is not bound with <code>let</code>&nbsp;<wbr>nor<code>&nbsp;<wbr>as</code>, and doesn&#8217;t start with an underscore (_) character. </p>
<p> 28 &nbsp;<wbr>&nbsp;<wbr>A pattern contains a constant constructor applied to the underscore (_) pattern. </p>
<p> 29 &nbsp;<wbr>&nbsp;<wbr>A non-escaped end-of-line was found in a string constant. This may cause portability problems between Unix and Windows. </p>
<p> 30 &nbsp;<wbr>&nbsp;<wbr>Two labels or constructors of the same name are defined in two mutually recursive types. </p>
<p> 31 &nbsp;<wbr>&nbsp;<wbr>A module is linked twice in the same executable. </p>
<p> 32 &nbsp;<wbr>&nbsp;<wbr>Unused value declaration. </p>
<p> 33 &nbsp;<wbr>&nbsp;<wbr>Unused open statement. </p>
<p> 34 &nbsp;<wbr>&nbsp;<wbr>Unused type declaration. </p>

<dt><code>-warn-error</code><i>&nbsp;<wbr>warning-list</i></p>
<dd>Mark as errors the warnings specified in the argument <i>warning-list</i>. The compiler will stop with an error when one of these warnings is emitted. The <i>warning-list</i> has the same meaning as for the <code>-w</code> option: a <code>+</code> sign (or an uppercase letter) marks the corresponding warnings as fatal, a <code>&#8211;</code> sign (or a lowercase letter) turns them back into non-fatal warnings, and a <code>@</code> sign both enables and marks as fatal the corresponding warnings. </p>
<p> Note: it is not recommended to use the <code>-warn-error</code> option in production code, because it will almost certainly prevent compiling your program with later versions of OCaml when they add new warnings. </p>
<p> The default setting is <code>-warn-error -a (all warnings are non-fatal).</code></p>
