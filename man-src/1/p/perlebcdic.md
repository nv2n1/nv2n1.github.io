<h2 class="name">NAME</h2>
<p> perlebcdic &#8211; Considerations for running Perl on EBCDIC platforms </p>
<h2>DESCRIPTION</h2>
<p> An exploration of some of the issues facing Perl programmers on <font SIZE="-1">EBCDIC</font> based computers. </p>
<p> Portions of this document that are still incomplete are marked with <font SIZE="-1">XXX.</font> </p>
<p> Early Perl versions worked on some <font SIZE="-1">EBCDIC</font> machines, but the last known version that ran on <font SIZE="-1">EBCDIC</font> was v5.8.7, until v5.22, when the Perl core again works on z/OS. Theoretically, it could work on <font SIZE="-1">OS/400</font> or Siemens&#8217; <font SIZE="-1">BS2000</font> (or their successors), but this is untested. In v5.22 and 5.24, not all the modules found on <font SIZE="-1">CPAN</font> but shipped with core Perl work on z/OS. </p>
<p> If you want to use Perl on a non-z/OS <font SIZE="-1">EBCDIC</font> machine, please let us know by sending mail to perlbug [at] perl.org </p>
<p> Writing Perl on an <font SIZE="-1">EBCDIC</font> platform is really no different than writing on an &#8220;<font SIZE="-1">ASCII&#8221;</font> one, but with different underlying numbers, as we&#8217;ll see shortly. You&#8217;ll have to know something about those &#8220;<font SIZE="-1">ASCII&#8221;</font> platforms because the documentation is biased and will frequently use example numbers that don&#8217;t apply to <font SIZE="-1">EBCDIC.</font> There are also very few <font SIZE="-1">CPAN</font> modules that are written for <font SIZE="-1">EBCDIC</font> and which don&#8217;t work on <font SIZE="-1">ASCII</font>; instead the vast majority of <font SIZE="-1">CPAN</font> modules are written for <font SIZE="-1">ASCII,</font> and some may happen to work on <font SIZE="-1">EBCDIC,</font> while a few have been designed to portably work on both. </p>
<p> If your code just uses the 52 letters A-Z and a-z, plus <font SIZE="-1">SPACE,</font> the digits 0-9, and the punctuation characters that Perl uses, plus a few controls that are denoted by escape sequences like <tt>&quot;
&quot;</tt> and <tt>&quot;	&quot;</tt>, then there&#8217;s nothing special about using Perl, and your code may very well work on an <font SIZE="-1">ASCII</font> machine without change. </p>
<p> But if you write code that uses <tt>&quot;&quot;</tt> to mean a <font SIZE="-1">TAB</font> or <tt>&quot;�&quot;</tt> to mean an &#8220;A&#8221;, or <tt>&quot;�&quot;</tt> to mean a &#8220;ÿ&#8221; (small <tt>&quot;y&quot;</tt> with a diaeresis), then your code may well work on your <font SIZE="-1">EBCDIC</font> platform, but not on an <font SIZE="-1">ASCII</font> one. That&#8217;s fine to do if no one will ever want to run your code on an <font SIZE="-1">ASCII</font> platform; but the bias in this document will be towards writing code portable between <font SIZE="-1">EBCDIC</font> and <font SIZE="-1">ASCII</font> systems. Again, if every character you care about is easily enterable from your keyboard, you don&#8217;t have to know anything about <font SIZE="-1">ASCII,</font> but many keyboards don&#8217;t easily allow you to directly enter, say, the character <tt>&quot;�&quot;</tt>, so you have to specify it indirectly, such as by using the <tt>&quot;�&quot;</tt> escape sequence. In those cases it&#8217;s easiest to know something about the ASCII/Unicode character sets. If you know that the small &#8220;ÿ&#8221; is <tt>&quot;U+00FF&quot;</tt>, then you can instead specify it as <tt>&quot;\N{U+FF}&quot;</tt>, and have the computer automatically translate it to <tt>&quot;�&quot;</tt> on your platform, and leave it as <tt>&quot;�&quot;</tt> on <font SIZE="-1">ASCII</font> ones. Or you could specify it by name, <tt>&quot;\N{LATIN SMALL LETTER Y WITH DIAERESIS&quot;</tt> and not have to know the numbers. Either way works, but both require familiarity with Unicode.</p>
<h2>COMMON CHARACTER CODE SETS</h2>
<h3><font SIZE="-1">ASCII</font></h3>
<p> The American Standard Code for Information Interchange (<font SIZE="-1">ASCII</font> or US-ASCII) is a set of integers running from 0 to 127 (decimal) that have standardized interpretations by the computers which use <font SIZE="-1">ASCII.</font> For example, 65 means the letter &#8220;A&#8221;. The range 0..127 can be covered by setting various bits in a 7-bit binary digit, hence the set is sometimes referred to as &#8220;7-bit <font SIZE="-1">ASCII&#8221;. ASCII</font> was described by the American National Standards Institute document <font SIZE="-1">ANSI X3.4-1986.</font> It was also described by <font SIZE="-1">ISO 646:1991</font> (with localization for currency symbols). The full <font SIZE="-1">ASCII</font> set is given in the table below as the first 128 elements. Languages that can be written adequately with the characters in <font SIZE="-1">ASCII</font> include English, Hawaiian, Indonesian, Swahili and some Native American languages. </p>
<p> Most non-EBCDIC character sets are supersets of <font SIZE="-1">ASCII.</font> That is the integers 0-127 mean what <font SIZE="-1">ASCII</font> says they mean. But integers 128 and above are specific to the character set. </p>
<p> Many of these fit entirely into 8 bits, using <font SIZE="-1">ASCII</font> as 0-127, while specifying what 128-255 mean, and not using anything above 255. Thus, these are single-byte (or octet if you prefer) character sets. One important one (since Unicode is a superset of it) is the <font SIZE="-1">ISO 8859-1</font> character set.</p>
<h3><font SIZE="-1">ISO 8859</font></h3>
<p> The <font SIZE="-1">ISO 8859-</font><i></i>$n<i></i> are a collection of character code sets from the International Organization for Standardization (<font SIZE="-1">ISO</font>), each of which adds characters to the <font SIZE="-1">ASCII</font> set that are typically found in various languages, many of which are based on the Roman, or Latin, alphabet. Most are for European languages, but there are also ones for Arabic, Greek, Hebrew, and Thai. There are good references on the web about all these.</p>
<h3>Latin 1 (<font SIZE="-1">ISO 8859-1</font>)</h3>
<p> A particular 8-bit extension to <font SIZE="-1">ASCII</font> that includes grave and acute accented Latin characters. Languages that can employ <font SIZE="-1">ISO 8859-1</font> include all the languages covered by <font SIZE="-1">ASCII</font> as well as Afrikaans, Albanian, Basque, Catalan, Danish, Faroese, Finnish, Norwegian, Portuguese, Spanish, and Swedish. Dutch is covered albeit without the ij ligature. French is covered too but without the oe ligature. German can use <font SIZE="-1">ISO 8859-1</font> but must do so without German-style quotation marks. This set is based on Western European extensions to <font SIZE="-1">ASCII</font> and is commonly encountered in world wide web work. In <font SIZE="-1">IBM</font> character code set identification terminology, <font SIZE="-1">ISO 8859-1</font> is also known as <font SIZE="-1">CCSID 819</font> (or sometimes 0819 or even 00819).</p>
<h3><font SIZE="-1">EBCDIC</font></h3>
<p> The Extended Binary Coded Decimal Interchange Code refers to a large collection of single- and multi-byte coded character sets that are quite different from <font SIZE="-1">ASCII</font> and <font SIZE="-1">ISO 8859-1,</font> and are all slightly different from each other; they typically run on host computers. The <font SIZE="-1">EBCDIC</font> encodings derive from 8-bit byte extensions of Hollerith punched card encodings, which long predate <font SIZE="-1">ASCII.</font> The layout on the cards was such that high bits were set for the upper and lower case alphabetic characters <tt>&quot;[a-z]&quot;</tt> and <tt>&quot;[A-Z]&quot;</tt>, but there were gaps within each Latin alphabet range, visible in the table below. These gaps can cause complications. </p>
<p> Some <font SIZE="-1">IBM EBCDIC</font> character sets may be known by character code set identification numbers (<font SIZE="-1">CCSID</font> numbers) or code page numbers. </p>
<p> Perl can be compiled on platforms that run any of three commonly used <font SIZE="-1">EBCDIC</font> character sets, listed below. </p>
<p> <i>The 13 variant characters</i> </p>
<p> Among <font SIZE="-1">IBM EBCDIC</font> character code sets there are 13 characters that are often mapped to different integer values. Those characters are known as the 13 &#8220;variant&#8221; characters and are: </p>
<pre><code>
\ [] {} ^ ~!# | $ @ `
</code></pre>
<p> When Perl is compiled for a platform, it looks at all of these characters to guess which <font SIZE="-1">EBCDIC</font> character set the platform uses, and adapts itself accordingly to that platform. If the platform uses a character set that is not one of the three Perl knows about, Perl will either fail to compile, or mistakenly and silently choose one of the three. </p>
<p> The Line Feed (<font SIZE="-1">LF</font>) character is actually a 14th variant character, and Perl checks for that as well. </p>
<p> <i></i><font SIZE="-1"><i>EBCDIC</i></font><i> code sets recognized by Perl</i></p>
<dl>
<dt><code>0037</code></p>
<dd> Character code set <font SIZE="-1">ID 0037</font> is a mapping of the <font SIZE="-1">ASCII</font> plus Latin-1 characters (i.e. <font SIZE="-1">ISO 8859-1</font>) to an <font SIZE="-1">EBCDIC</font> set. 0037 is used in North American English locales on the <font SIZE="-1">OS/400</font> operating system that runs on <font SIZE="-1">AS/400</font> computers. <font SIZE="-1">CCSID 0037</font> differs from <font SIZE="-1">ISO 8859-1</font> in 236 places; in other words they agree on only 20 code point values.</p>
<dt><code>1047</code></p>
<dd> Character code set <font SIZE="-1">ID 1047</font> is also a mapping of the <font SIZE="-1">ASCII</font> plus Latin-1 characters (i.e. <font SIZE="-1">ISO 8859-1</font>) to an <font SIZE="-1">EBCDIC</font> set. 1047 is used under Unix System Services for <font SIZE="-1">OS/390</font> or z/OS, and OpenEdition for <font SIZE="-1">VM/ESA.</font> <font SIZE="-1">CCSID 1047</font> differs from <font SIZE="-1">CCSID 0037</font> in eight places, and from <font SIZE="-1">ISO 8859-1</font> in 236.</p>
<dt><code>POSIX-BC</code></p>
<dd> The <font SIZE="-1">EBCDIC</font> code page in use on Siemens&#8217; <font SIZE="-1">BS2000</font> system is distinct from 1047 and 0037. It is identified below as the POSIX-BC set. Like 0037 and 1047, it is the same as <font SIZE="-1">ISO 8859-1</font> in 20 code point values.</dl>
<h3>Unicode code points versus <font SIZE="-1">EBCDIC</font> code points</h3>
<p> In Unicode terminology a <i>code point</i> is the number assigned to a character: for example, in <font SIZE="-1">EBCDIC</font> the character &#8220;A&#8221; is usually assigned the number 193. In Unicode, the character &#8220;A&#8221; is assigned the number 65. All the code points in <font SIZE="-1">ASCII</font> and Latin-1 (<font SIZE="-1">ISO 8859-1</font>) have the same meaning in Unicode. All three of the recognized <font SIZE="-1">EBCDIC</font> code sets have 256 code points, and in each code set, all 256 code points are mapped to equivalent Latin1 code points. Obviously, &#8220;A&#8221; will map to &#8220;A&#8221;, &#8220;B&#8221; =&gt; &#8220;B&#8221;, &#8220;%&#8221; =&gt; &#8220;%&#8221;, etc., for all printable characters in Latin1 and these code pages. </p>
<p> It also turns out that <font SIZE="-1">EBCDIC</font> has nearly precise equivalents for the ASCII/Latin1 C0 controls and the <font SIZE="-1">DELETE</font> control. (The C0 controls are those whose <font SIZE="-1">ASCII</font> code points are 0..0x1F; things like <font SIZE="-1">TAB, ACK, BEL,</font> etc.) A mapping is set up between these <font SIZE="-1">ASCII/EBCDIC</font> controls. There isn&#8217;t such a precise mapping between the C1 controls on <font SIZE="-1">ASCII</font> platforms and the remaining <font SIZE="-1">EBCDIC</font> controls. What has been done is to map these controls, mostly arbitrarily, to some otherwise unmatched character in the other character set. Most of these are very very rarely used nowadays in <font SIZE="-1">EBCDIC</font> anyway, and their names have been dropped, without much complaint. For example the <font SIZE="-1">EO</font> (Eight Ones) <font SIZE="-1">EBCDIC</font> control (consisting of eight one bits = 0xFF) is mapped to the C1 <font SIZE="-1">APC</font> control (0x9F), and you can&#8217;t use the name &#8220;<font SIZE="-1">EO&#8221;.</font> </p>
<p> The <font SIZE="-1">EBCDIC</font> controls provide three possible line terminator characters, <font SIZE="-1">CR</font> (0x0D), <font SIZE="-1">LF</font> (0x25), and <font SIZE="-1">NL</font> (0x15). On <font SIZE="-1">ASCII</font> platforms, the symbols &#8220;<font SIZE="-1">NL&#8221;</font> and &#8220;<font SIZE="-1">LF&#8221;</font> refer to the same character, but in strict <font SIZE="-1">EBCDIC</font> terminology they are different ones. The <font SIZE="-1">EBCDIC NL</font> is mapped to the C1 control called &#8220;<font SIZE="-1">NEL&#8221;</font> (&#8220;Next Line&#8221;; here&#8217;s a case where the mapping makes quite a bit of sense, and hence isn&#8217;t just arbitrary). On some <font SIZE="-1">EBCDIC</font> platforms, this <font SIZE="-1">NL</font> or <font SIZE="-1">NEL</font> is the typical line terminator. This is true of z/OS and <font SIZE="-1">BS2000.</font> In these platforms, the C compilers will swap the <font SIZE="-1">LF</font> and <font SIZE="-1">NEL</font> code points, so that <tt>&quot;
&quot;</tt> is 0x15, and refers to <font SIZE="-1">NL.</font> Perl does that too; you can see it in the code chart below. This makes things generally &#8220;just work&#8221; without you even having to be aware that there is a swap.</p>
<h3>Unicode and <font SIZE="-1">UTF</font></h3>
<p> <font SIZE="-1">UTF</font> stands for &#8220;Unicode Transformation Format&#8221;. <font SIZE="-1">UTF-8</font> is an encoding of Unicode into a sequence of 8-bit byte chunks, based on <font SIZE="-1">ASCII</font> and Latin-1. The length of a sequence required to represent a Unicode code point depends on the ordinal number of that code point, with larger numbers requiring more bytes. UTF-EBCDIC is like <font SIZE="-1">UTF-8,</font> but based on <font SIZE="-1">EBCDIC.</font> They are enough alike that often, casual usage will conflate the two terms, and use &#8220;<font SIZE="-1">UTF-8&#8221;</font> to mean both the <font SIZE="-1">UTF-8</font> found on <font SIZE="-1">ASCII</font> platforms, and the UTF-EBCDIC found on <font SIZE="-1">EBCDIC</font> ones. </p>
<p> You may see the term &#8220;invariant&#8221; character or code point. This simply means that the character has the same numeric value and representation when encoded in <font SIZE="-1">UTF-8</font> (or UTF-EBCDIC) as when not. (Note that this is a very different concept from &#8220;The 13 variant characters&#8221; mentioned above. Careful prose will use the term &#8220;<font SIZE="-1">UTF-8</font> invariant&#8221; instead of just &#8220;invariant&#8221;, but most often you&#8217;ll see just &#8220;invariant&#8221;.) For example, the ordinal value of &#8220;A&#8221; is 193 in most <font SIZE="-1">EBCDIC</font> code pages, and also is 193 when encoded in UTF-EBCDIC. All <font SIZE="-1">UTF-8</font> (or UTF-EBCDIC) variant code points occupy at least two bytes when encoded in <font SIZE="-1">UTF-8</font> (or UTF-EBCDIC); by definition, the <font SIZE="-1">UTF-8</font> (or UTF-EBCDIC) invariant code points are exactly one byte whether encoded in <font SIZE="-1">UTF-8</font> (or UTF-EBCDIC), or not. (By now you see why people typically just say &#8220;<font SIZE="-1">UTF-8&#8221;</font> when they also mean &#8220;UTF-EBCDIC&#8221;. For the rest of this document, we&#8217;ll mostly be casual about it too.) In <font SIZE="-1">ASCII UTF-8,</font> the code points corresponding to the lowest 128 ordinal numbers (0 &#8211; 127: the <font SIZE="-1">ASCII</font> characters) are invariant. In UTF-EBCDIC, there are 160 invariant characters. (If you care, the <font SIZE="-1">EBCDIC</font> invariants are those characters which have <font SIZE="-1">ASCII</font> equivalents, plus those that correspond to the C1 controls (128 &#8211; 159 on <font SIZE="-1">ASCII</font> platforms).) </p>
<p> A string encoded in UTF-EBCDIC may be longer (very rarely shorter) than one encoded in <font SIZE="-1">UTF-8.</font> Perl extends both <font SIZE="-1">UTF-8</font> and UTF-EBCDIC so that they can encode code points above the Unicode maximum of U+10FFFF. Both extensions are constructed to allow encoding of any code point that fits in a 64-bit word. </p>
<p> UTF-EBCDIC is defined by Unicode Technical Report #16 &lt;<a rel="nofollow" href="http://www.unicode.org/reports/tr16">http://www.unicode.org/reports/tr16</a>&gt; (often referred to as just <font SIZE="-1">TR16</font>). It is defined based on <font SIZE="-1">CCSID 1047,</font> not allowing for the differences for other code pages. This allows for easy interchange of text between computers running different code pages, but makes it unusable, without adaptation, for Perl on those other code pages. </p>
<p> The reason for this unusability is that a fundamental assumption of Perl is that the characters it cares about for parsing and lexical analysis are the same whether or not the text is in <font SIZE="-1">UTF-8.</font> For example, Perl expects the character <tt>&quot;[&quot;</tt> to have the same representation, no matter if the string containing it (or program text) is <font SIZE="-1">UTF-8</font> encoded or not. To ensure this, Perl adapts UTF-EBCDIC to the particular code page so that all characters it expects to be <font SIZE="-1">UTF-8</font> invariant are in fact <font SIZE="-1">UTF-8</font> invariant. This means that text generated on a computer running one version of Perl&#8217;s UTF-EBCDIC has to be translated to be intelligible to a computer running another. </p>
<p> <font SIZE="-1">TR16</font> implies a method to extend UTF-EBCDIC to encode points up through <tt>&quot;2 ** 31 - 1&quot;</tt>. Perl uses this method for code points up through <tt>&quot;2 ** 30 - 1&quot;</tt>, but uses an incompatible method for larger ones, to enable it to handle much larger code points than otherwise.</p>
<h3>Using Encode</h3>
<p> Starting from Perl 5.8 you can use the standard module Encode to translate from <font SIZE="-1">EBCDIC</font> to Latin-1 code points. Encode knows about more <font SIZE="-1">EBCDIC</font> character sets than Perl can currently be compiled to run on. </p>
<p>use Encode &#8216;from_to&#8217;;<br />
my % ebcdic = (176 = &gt; &#8216;cp37&#8217;, 95 = &gt; &#8216;cp1047&#8217;, 106 = &gt; &#8216;posix-bc&#8217;);<br />
#$a is in EBCDIC code points<br />
from_to($a, $ebcdic{ord &#8216;^&#8217;}, &#8216;latin1&#8217;);<br />
#$a is ISO 8859 &#8211; 1 code points</p>
<p> and from Latin-1 code points to <font SIZE="-1">EBCDIC</font> code points </p>
<p>use Encode &#8216;from_to&#8217;;<br />
my % ebcdic = (176 = &gt; &#8216;cp37&#8217;, 95 = &gt; &#8216;cp1047&#8217;, 106 = &gt; &#8216;posix-bc&#8217;);<br />
#$a is ISO 8859 &#8211; 1 code points<br />
from_to($a, &#8216;latin1&#8217;, $ebcdic{ord &#8216;^&#8217;});<br />
#$a is in EBCDIC code points</p>
<p> For doing I/O it is suggested that you use the autotranslating features of PerlIO, see perluniintro. </p>
<p> Since version 5.8 Perl uses the PerlIO I/O library. This enables you to use different encodings per <font SIZE="-1">IO</font> channel. For example you may use </p>
<p>use Encode;<br />
open($f, &#8220;&gt;:encoding(ascii)&#8221;, &#8220;test.ascii&#8221;);<br />
print $f &#8220;Hello World!
&#8221;;<br />
open($f, &#8220;&gt;:encoding(cp37)&#8221;, &#8220;test.ebcdic&#8221;);<br />
print $f &#8220;Hello World!
&#8221;;<br />
open($f, &#8220;&gt;:encoding(latin1)&#8221;, &#8220;test.latin1&#8221;);<br />
print $f &#8220;Hello World!
&#8221;;<br />
open($f, &#8220;&gt;:encoding(utf8)&#8221;, &#8220;test.utf8&#8221;);<br />
print $f &#8220;Hello World!
&#8221;;</p>
<p> to get four files containing &#8220;Hello World!
&#8221; in <font SIZE="-1">ASCII, CP 0037 EBCDIC, ISO 8859-1</font> (Latin-1) (in this example identical to <font SIZE="-1">ASCII</font> since only <font SIZE="-1">ASCII</font> characters were printed), and UTF-EBCDIC (in this example identical to normal <font SIZE="-1">EBCDIC</font> since only characters that don&#8217;t differ between <font SIZE="-1">EBCDIC</font> and UTF-EBCDIC were printed). See the documentation of Encode::PerlIO for details. </p>
<p> As the PerlIO layer uses raw <font SIZE="-1">IO</font> (bytes) internally, all this totally ignores things like the type of your filesystem (<font SIZE="-1">ASCII</font> or <font SIZE="-1">EBCDIC</font>).</p>

<h2>IDENTIFYING CHARACTER CODE SETS</h2>
<p> It is possible to determine which character set you are operating under. But first you need to be really really sure you need to do this. Your code will be simpler and probably just as portable if you don&#8217;t have to test the character set and do different things, depending. There are actually only very few circumstances where it&#8217;s not easy to write straight-line code portable to all character sets. See &#8220;Unicode and <font SIZE="-1">EBCDIC&#8221;</font> in perluniintro for how to portably specify characters. </p>
<p> But there are some cases where you may want to know which character set you are running under. One possible example is doing sorting in inner loops where performance is critical. </p>
<p> To determine if you are running under <font SIZE="-1">ASCII</font> or <font SIZE="-1">EBCDIC,</font> you can use the return value of <tt>&quot;ord()&quot;</tt> or <tt>&quot;chr()&quot;</tt> to test one or more character values. For example: </p>
<p>$is_ascii = &#8220;A&#8221; eq chr(65);<br />
$is_ebcdic = &#8220;A&#8221; eq chr(193);<br />
$is_ascii = ord(&#8220;A&#8221;) == 65;<br />
$is_ebcdic = ord(&#8220;A&#8221;) == 193;</p>
<p> There&#8217;s even less need to distinguish between <font SIZE="-1">EBCDIC</font> code pages, but to do so try looking at one or more of the characters that differ between them. </p>
<p>$is_ascii = ord(&#8216;[&#8216;) == 91;<br />
$is_ebcdic_37 = ord(&#8216;[&#8216;) == 186;<br />
$is_ebcdic_1047 = ord(&#8216;[&#8216;) == 173;<br />
$is_ebcdic_POSIX_BC = ord(&#8216;[&#8216;) == 187;</p>
<p> However, it would be unwise to write tests such as: </p>
<p>$is_ascii = &#8220;&#8221; ne chr(13);<br />
#WRONG $is_ascii = &#8220;
&#8221; ne chr(10);<br />
#ILL ADVISED</p>
<p> Obviously the first of these will fail to distinguish most <font SIZE="-1">ASCII</font> platforms from either a <font SIZE="-1">CCSID 0037,</font> a 1047, or a POSIX-BC <font SIZE="-1">EBCDIC</font> platform since <tt>&quot;&quot;&quot; eq chr(13)&quot;</tt> under all of those coded character sets. But note too that because <tt>&quot;
&quot;</tt> is <tt>&quot;chr(13)&quot;</tt> and <tt>&quot;&quot;</tt> is <tt>&quot;chr(10)&quot;</tt> on old Macintosh (which is an <font SIZE="-1">ASCII</font> platform) the second <tt>$is_ascii</tt> test will lead to trouble there. </p>
<p> To determine whether or not perl was built under an <font SIZE="-1">EBCDIC</font> code page you can use the Config module like so: </p>
<p>use Config;<br />
$is_ebcdic = $Config{&#8216;ebcdic&#8217;} eq &#8216;define&#8217;;</p>
