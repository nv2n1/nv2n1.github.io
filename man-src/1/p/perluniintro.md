<h2 class="name">NAME</h2>
<p> perluniintro &#8211; Perl Unicode introduction </p>
<h2>DESCRIPTION</h2>
<p> This document gives a general idea of Unicode and how to use Unicode in Perl. See &#8220;Further Resources&#8221; for references to more in-depth treatments of Unicode.</p>
<h3>Unicode</h3>
<p> Unicode is a character set standard which plans to codify all of the writing systems of the world, plus many other symbols. </p>
<p> Unicode and <font SIZE="-1">ISO/IEC 10646</font> are coordinated standards that unify almost all other modern character set standards, covering more than 80 writing systems and hundreds of languages, including all commercially-important modern languages. All characters in the largest Chinese, Japanese, and Korean dictionaries are also encoded. The standards will eventually cover almost all characters in more than 250 writing systems and thousands of languages. Unicode 1.0 was released in October 1991, and 6.0 in October 2010. </p>
<p> A Unicode <i>character</i> is an abstract entity. It is not bound to any particular integer width, especially not to the C language <tt>&quot;char&quot;</tt>. Unicode is language-neutral and display-neutral: it does not encode the language of the text, and it does not generally define fonts or other graphical layout details. Unicode operates on characters and on text built from those characters. </p>
<p> Unicode defines characters like <tt>&quot;LATIN CAPITAL LETTER A&quot;</tt> or <tt>&quot;GREEK SMALL LETTER ALPHA&quot;</tt> and unique numbers for the characters, in this case 0x0041 and 0x03B1, respectively. These unique numbers are called <i>code points</i>. A code point is essentially the position of the character within the set of all possible Unicode characters, and thus in Perl, the term <i>ordinal</i> is often used interchangeably with it. </p>
<p> The Unicode standard prefers using hexadecimal notation for the code points. If numbers like <tt>0x0041</tt> are unfamiliar to you, take a peek at a later section, &#8220;Hexadecimal Notation&#8221;. The Unicode standard uses the notation <tt>&quot;U+0041 LATIN CAPITAL LETTER A&quot;</tt>, to give the hexadecimal code point and the normative name of the character. </p>
<p> Unicode also defines various <i>properties</i> for the characters, like &#8220;uppercase&#8221; or &#8220;lowercase&#8221;, &#8220;decimal digit&#8221;, or &#8220;punctuation&#8221;; these properties are independent of the names of the characters. Furthermore, various operations on the characters like uppercasing, lowercasing, and collating (sorting) are defined. </p>
<p> A Unicode <i>logical</i> &#8220;character&#8221; can actually consist of more than one internal <i>actual</i> &#8220;character&#8221; or code point. For Western languages, this is adequately modelled by a <i>base character</i> (like <tt>&quot;LATIN CAPITAL LETTER A&quot;</tt>) followed by one or more <i>modifiers</i> (like <tt>&quot;COMBINING ACUTE ACCENT&quot;</tt>). This sequence of base character and modifiers is called a <i>combining character sequence</i>. Some non-western languages require more complicated models, so Unicode created the <i>grapheme cluster</i> concept, which was later further refined into the <i>extended grapheme cluster</i>. For example, a Korean Hangul syllable is considered a single logical character, but most often consists of three actual Unicode characters: a leading consonant followed by an interior vowel followed by a trailing consonant. </p>
<p> Whether to call these extended grapheme clusters &#8220;characters&#8221; depends on your point of view. If you are a programmer, you probably would tend towards seeing each element in the sequences as one unit, or &#8220;character&#8221;. However from the user&#8217;s point of view, the whole sequence could be seen as one &#8220;character&#8221; since that&#8217;s probably what it looks like in the context of the user&#8217;s language. In this document, we take the programmer&#8217;s point of view: one &#8220;character&#8221; is one Unicode code point. </p>
<p> For some combinations of base character and modifiers, there are <i>precomposed</i> characters. There is a single character equivalent, for example, for the sequence <tt>&quot;LATIN CAPITAL LETTER A&quot;</tt> followed by <tt>&quot;COMBINING ACUTE ACCENT&quot;</tt>. It is called <tt>&quot;LATIN CAPITAL LETTER A WITH ACUTE&quot;</tt>. These precomposed characters are, however, only available for some combinations, and are mainly meant to support round-trip conversions between Unicode and legacy standards (like <font SIZE="-1">ISO 8859</font>). Using sequences, as Unicode does, allows for needing fewer basic building blocks (code points) to express many more potential grapheme clusters. To support conversion between equivalent forms, various <i>normalization forms</i> are also defined. Thus, <tt>&quot;LATIN CAPITAL LETTER A WITH ACUTE&quot;</tt> is in <i>Normalization Form Composed</i>, (abbreviated <font SIZE="-1">NFC</font>), and the sequence <tt>&quot;LATIN CAPITAL LETTER A&quot;</tt> followed by <tt>&quot;COMBINING ACUTE ACCENT&quot;</tt> represents the same character in <i>Normalization Form Decomposed</i> (<font SIZE="-1">NFD</font>). </p>
<p> Because of backward compatibility with legacy encodings, the &#8220;a unique number for every character&#8221; idea breaks down a bit: instead, there is &#8220;at least one number for every character&#8221;. The same character could be represented differently in several legacy encodings. The converse is not true: some code points do not have an assigned character. Firstly, there are unallocated code points within otherwise used blocks. Secondly, there are special Unicode control characters that do not represent true characters. </p>
<p> When Unicode was first conceived, it was thought that all the world&#8217;s characters could be represented using a 16-bit word; that is a maximum of <tt>0x10000</tt> (or 65,536) characters would be needed, from <tt>0x0000</tt> to <tt>0xFFFF</tt>. This soon proved to be wrong, and since Unicode 2.0 (July 1996), Unicode has been defined all the way up to 21 bits (<tt>0x10FFFF</tt>), and Unicode 3.1 (March 2001) defined the first characters above <tt>0xFFFF</tt>. The first <tt>0x10000</tt> characters are called the <i>Plane 0</i>, or the <i>Basic Multilingual Plane</i> (<font SIZE="-1">BMP</font>). With Unicode 3.1, 17 (yes, seventeen) planes in all were defined&#8212;but they are nowhere near full of defined characters, yet. </p>
<p> When a new language is being encoded, Unicode generally will choose a <tt>&quot;block&quot;</tt> of consecutive unallocated code points for its characters. So far, the number of code points in these blocks has always been evenly divisible by 16. Extras in a block, not currently needed, are left unallocated, for future growth. But there have been occasions when a later release needed more code points than the available extras, and a new block had to allocated somewhere else, not contiguous to the initial one, to handle the overflow. Thus, it became apparent early on that &#8220;block&#8221; wasn&#8217;t an adequate organizing principle, and so the <tt>&quot;Script&quot;</tt> property was created. (Later an improved script property was added as well, the <tt>&quot;Script_Extensions&quot;</tt> property.) Those code points that are in overflow blocks can still have the same script as the original ones. The script concept fits more closely with natural language: there is <tt>&quot;Latin&quot;</tt> script, <tt>&quot;Greek&quot;</tt> script, and so on; and there are several artificial scripts, like <tt>&quot;Common&quot;</tt> for characters that are used in multiple scripts, such as mathematical symbols. Scripts usually span varied parts of several blocks. For more information about scripts, see &#8220;Scripts&#8221; in perlunicode. The division into blocks exists, but it is almost completely accidental&#8212;an artifact of how the characters have been and still are allocated. (Note that this paragraph has oversimplified things for the sake of this being an introduction. Unicode doesn&#8217;t really encode languages, but the writing systems for them&#8212;their scripts; and one script can be used by many languages. Unicode also encodes things that aren&#8217;t really about languages, such as symbols like <tt>&quot;BAGGAGE CLAIM&quot;</tt>.) </p>
<p> The Unicode code points are just abstract numbers. To input and output these abstract numbers, the numbers must be <i>encoded</i> or <i>serialised</i> somehow. Unicode defines several <i>character encoding forms</i>, of which <i></i><font SIZE="-1"><i>UTF-8</i></font><i></i> is the most popular. <font SIZE="-1">UTF-8</font> is a variable length encoding that encodes Unicode characters as 1 to 4 bytes. Other encodings include <font SIZE="-1">UTF-16</font> and <font SIZE="-1">UTF-32</font> and their big- and little-endian variants (<font SIZE="-1">UTF-8</font> is byte-order independent). The <font SIZE="-1">ISO/IEC 10646</font> defines the <font SIZE="-1">UCS-2</font> and <font SIZE="-1">UCS-4</font> encoding forms. </p>
<p> For more information about encodings&#8212;for instance, to learn what <i>surrogates</i> and <i>byte order marks</i> (BOMs) are&#8212;see perlunicode.</p>
<h3>Perl&#8217;s Unicode Support</h3>
<p> Starting from Perl v5.6.0, Perl has had the capacity to handle Unicode natively. Perl v5.8.0, however, is the first recommended release for serious Unicode work. The maintenance release 5.6.1 fixed many of the problems of the initial Unicode implementation, but for example regular expressions still do not work with Unicode in 5.6.1. Perl v5.14.0 is the first release where Unicode support is (almost) seamlessly integrable without some gotchas. (There are a few exceptions. Firstly, some differences in quotemeta were fixed starting in Perl 5.16.0. Secondly, some differences in the range operator were fixed starting in Perl 5.26.0. Thirdly, some differences in split were fixed started in Perl 5.28.0.) </p>
<p> To enable this seamless support, you should <tt>&quot;use feature 'unicode_strings'&quot;</tt> (which is automatically selected if you <tt>&quot;use 5.012&quot;</tt> or higher). See feature. (5.14 also fixes a number of bugs and departures from the Unicode standard.) </p>
<p> Before Perl v5.8.0, the use of <tt>&quot;use utf8&quot;</tt> was used to declare that operations in the current block or file would be Unicode-aware. This model was found to be wrong, or at least clumsy: the &#8220;Unicodeness&#8221; is now carried with the data, instead of being attached to the operations. Starting with Perl v5.8.0, only one case remains where an explicit <tt>&quot;use utf8&quot;</tt> is needed: if your Perl script itself is encoded in <font SIZE="-1">UTF-8,</font> you can use <font SIZE="-1">UTF-8</font> in your identifier names, and in string and regular expression literals, by saying <tt>&quot;use utf8&quot;</tt>. This is not the default because scripts with legacy 8-bit data in them would break. See utf8.</p>
<h3>Perl&#8217;s Unicode Model</h3>
<p> Perl supports both pre-5.6 strings of eight-bit native bytes, and strings of Unicode characters. The general principle is that Perl tries to keep its data as eight-bit bytes for as long as possible, but as soon as Unicodeness cannot be avoided, the data is transparently upgraded to Unicode. Prior to Perl v5.14.0, the upgrade was not completely transparent (see &#8220;The &#8221;Unicode Bug&quot;&quot; in perlunicode), and for backwards compatibility, full transparency is not gained unless <tt>&quot;use feature 'unicode_strings'&quot;</tt> (see feature) or <tt>&quot;use 5.012&quot;</tt> (or higher) is selected. </p>
<p> Internally, Perl currently uses either whatever the native eight-bit character set of the platform (for example Latin-1) is, defaulting to <font SIZE="-1">UTF-8,</font> to encode Unicode strings. Specifically, if all code points in the string are <tt>0xFF</tt> or less, Perl uses the native eight-bit character set. Otherwise, it uses <font SIZE="-1">UTF-8.</font> </p>
<p> A user of Perl does not normally need to know nor care how Perl happens to encode its internal strings, but it becomes relevant when outputting Unicode strings to a stream without a PerlIO layer (one with the &#8220;default&#8221; encoding). In such a case, the raw bytes used internally (the native character set or <font SIZE="-1">UTF-8,</font> as appropriate for each string) will be used, and a &#8220;Wide character&#8221; warning will be issued if those strings contain a character beyond 0x00FF. </p>
