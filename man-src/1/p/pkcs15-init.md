<h2 class="name">NAME</h2>
<p> pkcs15-init &#8211; smart card personalization utility </p>
<h2>DESCRIPTION</h2>
<p> The <code>pkcs15-init</code> utility can be used to create a PKCS #15 structure on a smart card, and add key or certificate objects. Details of the structure that will be created are controlled via profiles. </p>
<p> The profile used by default is <code>pkcs15</code>. Alternative profiles can be specified via the <code>-p</code> switch.</p>
<h2>PIN USAGE</h2>
<p> <code>pkcs15-init</code> can be used to create a PKCS #15 structure on your smart card, create PINs, and install keys and certificates on the card. This process is also called <i>personalization</i>. </p>
<p> An OpenSC card can have one security officer PIN, and zero or more user PINs. PIN stands for Personal Identification Number, and is a secret code you need to present to the card before being allowed to perform certain operations, such as using one of the stored RSA keys to sign a document, or modifying the card itself. </p>
<p> Usually, PINs are a sequence of decimal digits, but some cards will accept arbitrary ASCII characters. Be aware however that using characters other than digits will make the card unusable with PIN pad readers, because those usually have keys for entering digits only. </p>
<p> The security officer (SO) PIN is special; it is used to protect meta data information on the card, such as the PKCS #15 structure itself. Setting the SO PIN is optional, because the worst that can usually happen is that someone finding your card can mess it up. To extract any of your secret keys stored on the card, an attacker will still need your user PIN, at least for the default OpenSC profiles. However, it is possible to create card profiles that will allow the security officer to override user PINs. </p>
<p> For each PIN, you can specify a PUK (also called <i>unblock PIN</i>). The PUK can be used to overwrite or unlock a PIN if too many incorrect values have been entered in a row.</p>
<h2>MODES OF OPERATION</h2>
<h3>Initialization</h3>
<p> This is the first step during card personalization, and will create the basic files on the card. To create the initial PKCS #15 structure, invoke the utility as </p>
<p> <code>pkcs15-init &#8211;create-pkcs15</code> </p>
<p> You will then be asked for several the security officer PIN and PUK. Simply pressing return at the SO PIN prompt will skip installation of an SO PIN. </p>
<p> If the card supports it, you can also request that the card is erased prior to creating the PKCS #15 structure, by specifying the <code>&#8211;erase-card</code> option.</p>
<h3>User PIN Installation</h3>
<p> Before installing any user objects such as private keys, you need at least one PIN to protect these objects. you can do this using </p>
<p> <code>pkcs15-init &#8211;store-pin &#8211;id &quot; nn</code> </p>
<p> where <i>nn</i> is a PKCS #15 ID in hexadecimal notation. Common values are 01, 02, etc. </p>
<p> Entering the command above will ask you for the user&#8217;s PIN and PUK. If you do not wish to install an unblock PIN, simply press return at the PUK prompt. </p>
<p> To set a label for this PIN object (which can be used by applications to display a meaningful prompt to the user), use the <code>&#8211;label</code> command line option.</p>
<h3>Key generation</h3>
<p> <code>pkcs15-init</code> lets you generate a new key and store it on the card. You can do this using: </p>
<p> <code>pkcs15-init &#8211;generate-key &quot; keyspec &quot; &#8211;auth-id &quot; nn</code> </p>
<p> where <code>keyspec</code> describes the algorithm and length of the key to be created, such as <code>rsa/512</code>. This will create a 512 bit RSA key. Currently, only RSA key generation is supported. Note that cards usually support just a few different key lengths. Almost all cards will support 512 and 1024 bit keys, some will support 768 or 2048 as well. </p>
<p> <code>nn</code> is the ID of a user PIN installed previously, e.g. 01. </p>
<p> In addition to storing the private portion of the key on the card, <code>pkcs15-init</code> will also store the the public portion of the key as a PKCS #15 public key object. </p>
<p> By default, <code>pkcs15-init</code> will try to use the card&#8217;s on-board key generation facilities, if available. If the card does not support on-board key generation, <code>pkcs15-init</code> will fall back to software key generation.</p>
<h3>Private Key Download</h3>
<p> You can use a private key generated by other means and download it to the card. For instance, to download a private key contained in a file named <i>okir.pem</i>, which is in PEM format, you would use </p>
<p> <code>pkcs15-init &#8211;store-private-key okir.pem &#8211;id 45 &#8211;auth-id 01</code> </p>
<p> If the key is protected by a pass phrase, <code>pkcs15-init</code> will prompt you for a pass phrase to unlock the key. </p>
<p> In addition to storing the private portion of the key on the card, <code>pkcs15-init</code> will also store the the public portion of the key as a PKCS #15 public key object. </p>
<p> Note the use of the <code>&#8211;id</code> option. The current <code>pkcs15</code> profile defines two key templates, one for authentication (key ID 45), and one for non-repudiation purposes (key ID 46). Other key templates will probably be added in the future. Note that if you don&#8217;t specify a key ID, <code>pkcs15-init</code> will pick just the first key template defined by the profile. </p>
<p> In addition to the PEM key file format, <code>pkcs15-init</code> also supports DER encoded keys, and PKCS #12 files. The latter is the file format used by Netscape Navigator (among others) when exporting certificates to a file. A PKCS #12 file usually contains the X.509 certificate corresponding to the private key. If that is the case, <code>pkcs15-init</code> will store the certificate instead of the public key portion.</p>
<h3>Public Key Download</h3>
<p> You can also download individual public keys to the card using the <code>&#8211;store-public-key</code> option, which takes a filename as an argument. This file is supposed to contain the public key. If you don&#8217;t specify a key file format using the <code>&#8211;format</code> option, <code>pkcs15-init</code> will assume PEM format. The only other supported public key file format is DER. </p>
<p> Since the corresponding public keys are always downloaded automatically when generating a new key, or when downloading a private key, you will probably use this option only very rarely.</p>
<h3>Certificate Download</h3>
<p> You can download certificates to the card using the <code>&#8211;store-certificate</code> option, which takes a filename as an argument. This file is supposed to contain the DER encoded X.509 certificate.</p>
<h3>Downloading PKCS #12 bags</h3>
<p> Most browsers nowadays use PKCS #12 format files when you ask them to export your key and certificate to a file. <code>pkcs15-init</code> is capable of parsing these files, and storing their contents on the card in a single operation. This works just like storing a private key, except that you need to specify the file format: </p>
<p> <code>pkcs15-init &#8211;store-private-key okir.p12 &#8211;format pkcs12 &#8211;auth-id 01</code> </p>
<p> This will install the private key contained in the file <i>okir.p12</i>, and protect it with the PIN referenced by authentication ID <i>01</i>. It will also store any X.509 certificates contained in the file, which is usually the user certificate that goes with the key, as well as the CA certificate.</p>
<h2>OPTIONS</h2>
<p> <code>&#8211;profile</code> <i>name</i>, <code>-p</code> <i>name</i></p>
<dl>
<dt>
<dd> Tells <code>pkcs15-init</code> to load the specified general profile. Currently, the only application profile defined is <code>pkcs15</code>, but you can write your own profiles and specify them using this option. </p>
<p> The profile name can be combined with one or more <i>profile options</i>, which slightly modify the profile&#8217;s behavior. For instance, the default OpenSC profile supports the <code>openpin</code> option, which installs a single PIN during card initialization. This PIN is then used both as the SO PIN as well as the user PIN for all keys stored on the card. </p>
<p> Profile name and options are separated by a <code>+</code> character, as in <code>pkcs15+onepin</code>.</dl>
<p> <code>&#8211;card-profile</code> <i>name</i>, <code>-c</code> <i>name</i></p>
<dl>
<dt>
<dd> Tells <code>pkcs15-init</code> to load the specified card profile option. You will rarely need this option.</dl>
<p> <code>&#8211;create-pkcs15, -C</code></p>
<dl>
<dt>
<dd> This tells <code>pkcs15-init</code> to create a PKCS #15 structure on the card, and initialize any PINs.</dl>
<p> <code>&#8211;erase-card, -E</code></p>
<dl>
<dt>
<dd> This will erase the card prior to creating the PKCS #15 structure, if the card supports it. If the card does not support erasing, <code>pkcs15-init</code> will fail.</dl>
<p> <code>&#8211;generate-key</code> <i>keyspec</i>, <code>-G</code> <i>keyspec</i></p>
<dl>
<dt>
<dd> Tells the card to generate new key and store it on the card. <i>keyspec</i> consists of an algorithm name (currently, the only supported name is <code>RSA</code>), optionally followed by a slash and the length of the key in bits. It is a good idea to specify the key ID along with this command, using the <code>id</code> option.</dl>
<p> <code>&#8211;store-private-key</code> <i>filename</i>, <code>-S</code> <i>filename</i></p>
<dl>
<dt>
<dd> Tells <code>pkcs15-init</code> to download the specified private key to the card. This command will also create a public key object containing the public key portion. By default, the file is assumed to contain the key in PEM format. Alternative formats can be specified using <code>&#8211;format</code>. It is a good idea to specify the key ID along with this command, using the <code>&#8211;id</code> option.</dl>
<p> <code>&#8211;store-public-key</code> <i>filename</i>, <code>-P</code> <i>filename</i></p>
<dl>
<dt>
<dd> Tells <code>pkcs15-init</code> to download the specified public key to the card and create a public key object with the key ID specified via the <code>&#8211;id</code>. By default, the file is assumed to contain the key in PEM format. Alternative formats can be specified using <code>&#8211;format</code>.</dl>
<p> <code>&#8211;store-certificate</code> <i>filename</i>, <code>-X</code> <i>filename</i></p>
<dl>
<dt>
<dd> Tells <code>pkcs15-init</code> to store the certificate given in <code>filename</code> on the card, creating a certificate object with the ID specified via the <code>&#8211;id</code> option. The file is assumed to contain the DER encoded certificate.</dl>
<p> <code>&#8211;so-pin, &#8211;so-puk, &#8211;pin, &#8211;puk</code></p>
<dl>
<dt>
<dd> These options can be used to specify PIN/PUK values on the command line. Note that on most operation systems, any user can display the command line of any process on the system using utilities such as <code><a href="/docs/linux/man/1-ps/">ps</a>(1)</code>. Therefore, you should use these options only on a secured system, or in an options file specified with <code>&#8211;options-file</code>.</dl>
<p> <code>&#8211;passphrase</code></p>
<dl>
<dt>
<dd> When downloading a private key, this option can be used to specify the pass phrase to unlock the private key. The same caveat applies here as in the case of the <code>&#8211;pin</code> options.</dl>
<p> <code>&#8211;options-file</code> <i>filename</i></p>
<dl>
<dt>
<dd> Tells <code>pkcs15-init</code> to read additional options from <i>filename</i>. The file is supposed to contain one long option per line, without the leading dashes, for instance: </p>
<dl>
<dt>
<dd>
<pre>
        pin             frank
        puk             zappa
</pre>
</dl>
<p> You can specify <code>&#8211;options-file</code> several times.</dl>
<p> <code>&#8211;verbose, -v</code></p>
<dl>
<dt>
<dd> Causes <code>pkcs15-init</code> to be more verbose. Specify this flag several times to enable debug output in the OpenSC library.</dl>
