<h2 class="name">NAME</h2>
<p> perlbug &#8211; how to submit bug reports on Perl </p>
<h2>SYNOPSIS</h2>
<p> <code>perlbug</code> </p>
<p> <code>perlbug</code> [ <code>-v</code> ] [ <code>-a</code> <i>address</i> ] [ <code>-s</code> <i>subject</i> ] [ <code>-b</code> <i>body</i> | <code>-f</code> <i>inputfile</i> ] [ <code>-F</code> <i>outputfile</i> ] [ <code>-r</code> <i>returnaddress</i> ] [ <code>-e</code> <i>editor</i> ] [ <code>-c</code> <i>adminaddress</i> | <code>-C</code> ] [ <code>-S</code> ] [ <code>-t</code> ] [ <code>-d</code> ] [ <code>-h</code> ] [ <code>-T</code> ] </p>
<p> <code>perlbug</code> [ <code>-v</code> ] [ <code>-r</code> <i>returnaddress</i> ]<br />
&nbsp;[ <code>-ok</code> | <code>-okay</code> | <code>-nok</code> | <code>-nokay</code> ] </p>
<p> <code>perlthanks</code></p>
<h2>DESCRIPTION</h2>
<p> This program is designed to help you generate bug reports (and thank-you notes) about perl5 and the modules which ship with it. </p>
<p> In most cases, you can just run it interactively from a command line without any special arguments and follow the prompts. </p>
<p> If you have found a bug with a non-standard port (one that was not part of the <i>standard distribution</i>), a binary distribution, or a non-core module (such as Tk, <font SIZE="-1">DBI,</font> etc), then please see the documentation that came with that distribution to determine the correct place to report bugs. </p>
<p> Bug reports should be submitted to the GitHub issue tracker at &lt;<a rel="nofollow" href="https://github.com/Perl/perl5/issues">https://github.com/Perl/perl5/issues</a>&gt;. The <code>perlbug [at] perl.org</code> address no longer automatically opens tickets. You can use this tool to compose your report and save it to a file which you can then submit to the issue tracker. </p>
<p> In extreme cases, <code>perlbug</code> may not work well enough on your system to guide you through composing a bug report. In those cases, you may be able to use <code>perlbug -d</code> or <code>perl -V</code> to get system configuration information to include in your issue report. </p>
<p> When reporting a bug, please run through this checklist:</p>
<dl>
<dt>What version of Perl you are running?</p>
<dd> Type <tt>&quot;perl -v&quot;</tt> at the command line to find out.</p>
<dt>Are you running the latest released version of perl?</p>
<dd> Look at &lt;<a rel="nofollow" href="http://www.perl.org/">http://www.perl.org/</a>&gt; to find out. If you are not using the latest released version, please try to replicate your bug on the latest stable release. </p>
<p> Note that reports about bugs in old versions of Perl, especially those which indicate you haven&#8217;t also tested the current stable release of Perl, are likely to receive less attention from the volunteers who build and maintain Perl than reports about bugs in the current release.</p>
<dt>Are you sure what you have is a bug?</p>
<dd> A significant number of the bug reports we get turn out to be documented features in Perl. Make sure the issue you&#8217;ve run into isn&#8217;t intentional by glancing through the documentation that comes with the Perl distribution. </p>
<p> Given the sheer volume of Perl documentation, this isn&#8217;t a trivial undertaking, but if you can point to documentation that suggests the behaviour you&#8217;re seeing is <i>wrong</i>, your issue is likely to receive more attention. You may want to start with <code>perldoc</code> perltrap for pointers to common traps that new (and experienced) Perl programmers run into. </p>
<p> If you&#8217;re unsure of the meaning of an error message you&#8217;ve run across, <code>perldoc</code> perldiag for an explanation. If the message isn&#8217;t in perldiag, it probably isn&#8217;t generated by Perl. You may have luck consulting your operating system documentation instead. </p>
<p> If you are on a non-UNIX platform <code>perldoc</code> perlport, as some features may be unimplemented or work differently. </p>
<p> You may be able to figure out what&#8217;s going wrong using the Perl debugger. For information about how to use the debugger <code>perldoc</code> perldebug.</p>
<dt>Do you have a proper test case?</p>
<dd> The easier it is to reproduce your bug, the more likely it will be fixed &#8212; if nobody can duplicate your problem, it probably won&#8217;t be addressed. </p>
<p> A good test case has most of these attributes: short, simple code; few dependencies on external commands, modules, or libraries; no platform-dependent code (unless it&#8217;s a platform-specific bug); clear, simple documentation. </p>
<p> A good test case is almost always a good candidate to be included in Perl&#8217;s test suite. If you have the time, consider writing your test case so that it can be easily included into the standard test suite.</p>
<dt>Have you included all relevant information?</p>
<dd> Be sure to include the <code>exact</code> error messages, if any. &#8220;Perl gave an error&#8221; is not an exact error message. </p>
<p> If you get a core dump (or equivalent), you may use a debugger (<code>dbx</code>, <code>gdb</code>, etc) to produce a stack trace to include in the bug report. </p>
<p> <font SIZE="-1">NOTE:</font> unless your Perl has been compiled with debug info (often <code>-g</code>), the stack trace is likely to be somewhat hard to use because it will most probably contain only the function names and not their arguments. If possible, recompile your Perl with debug info and reproduce the crash and the stack trace.</p>
<dt>Can you describe the bug in plain English?</p>
<dd> The easier it is to understand a reproducible bug, the more likely it will be fixed. Any insight you can provide into the problem will help a great deal. In other words, try to analyze the problem (to the extent you can) and report your discoveries.</p>
<dt>Can you fix the bug yourself?</p>
<dd> If so, that&#8217;s great news; bug reports with patches are likely to receive significantly more attention and interest than those without patches. Please submit your patch via the GitHub Pull Request workflow as described in <code>perldoc</code> perlhack. You may also send patches to <code>perl5-porters [at] perl.org</code>. When sending a patch, create it using <tt>&quot;git format-patch&quot;</tt> if possible, though a unified diff created with <tt>&quot;diff -pu&quot;</tt> will do nearly as well. </p>
<p> Your patch may be returned with requests for changes, or requests for more detailed explanations about your fix. </p>
<p> Here are a few hints for creating high-quality patches: </p>
<p> Make sure the patch is not reversed (the first argument to diff is typically the original file, the second argument your changed file). Make sure you test your patch by applying it with <tt>&quot;git am&quot;</tt> or the <tt>&quot;patch&quot;</tt> program before you send it on its way. Try to follow the same style as the code you are trying to patch. Make sure your patch really does work (<tt>&quot;make test&quot;</tt>, if the thing you&#8217;re patching is covered by Perl&#8217;s test suite).</p>
<dt>Can you use &quot;perlbug&quot; to submit a thank-you note?</p>
<dd> Yes, you can do this by either using the <tt>&quot;-T&quot;</tt> option, or by invoking the program as <tt>&quot;perlthanks&quot;</tt>. Thank-you notes are good. It makes people smile.</dl>
<p> Please make your issue title informative. &#8220;a bug&#8221; is not informative. Neither is &#8220;perl crashes&#8221; nor is &#8220;<font SIZE="-1">HELP</font>!!!&#8221;. These don&#8217;t help. A compact description of what&#8217;s wrong is fine. </p>
<p> Having done your bit, please be prepared to wait, to be told the bug is in your code, or possibly to get no reply at all. The volunteers who maintain Perl are busy folks, so if your problem is an obvious bug in your own code, is difficult to understand or is a duplicate of an existing report, you may not receive a personal reply. </p>
<p> If it is important to you that your bug be fixed, do monitor the issue tracker (you will be subscribed to notifications for issues you submit or comment on) and the commit logs to development versions of Perl, and encourage the maintainers with kind words or offers of frosty beverages. (Please do be kind to the maintainers. Harassing or flaming them is likely to have the opposite effect of the one you want.) </p>
<p> Feel free to update the ticket about your bug on &lt;<a rel="nofollow" href="https://github.com/Perl/perl5/issues">https://github.com/Perl/perl5/issues</a>&gt; if a new version of Perl is released and your bug is still present.</p>
<h2>OPTIONS</h2>
<dl>
<dt><code>-a</code></p>
<dd> Address to send the report to instead of saving to a file.</p>
<dt><code>-b</code></p>
<dd> Body of the report. If not included on the command line, or in a file with <code>-f</code>, you will get a chance to edit the report.</p>
<dt><code>-C</code></p>
<dd> Don&#8217;t send copy to administrator when sending report by mail.</p>
<dt><code>-c</code></p>
<dd> Address to send copy of report to when sending report by mail. Defaults to the address of the local perl administrator (recorded when perl was built).</p>
<dt><code>-d</code></p>
<dd> Data mode (the default if you redirect or pipe output). This prints out your configuration data, without saving or mailing anything. You can use this with <code>-v</code> to get more complete data.</p>
<dt><code>-e</code></p>
<dd> Editor to use.</p>
<dt><code>-f</code></p>
<dd> File containing the body of the report. Use this to quickly send a prepared report.</p>
<dt><code>-F</code></p>
<dd> File to output the results to. Defaults to <code>perlbug.rep</code>.</p>
<dt><code>-h</code></p>
<dd> Prints a brief summary of the options.</p>
<dt><code>-ok</code></p>
<dd> Report successful build on this system to perl porters. Forces <code>-S</code> and <code>-C</code>. Forces and supplies values for <code>-s</code> and <code>-b</code>. Only prompts for a return address if it cannot guess it (for use with <code>make</code>). Honors return address specified with <code>-r</code>. You can use this with <code>-v</code> to get more complete data. Only makes a report if this system is less than 60 days old.</p>
<dt><code>-okay</code></p>
<dd> As <code>-ok</code> except it will report on older systems.</p>
<dt><code>-nok</code></p>
<dd> Report unsuccessful build on this system. Forces <code>-C</code>. Forces and supplies a value for <code>-s</code>, then requires you to edit the report and say what went wrong. Alternatively, a prepared report may be supplied using <code>-f</code>. Only prompts for a return address if it cannot guess it (for use with <code>make</code>). Honors return address specified with <code>-r</code>. You can use this with <code>-v</code> to get more complete data. Only makes a report if this system is less than 60 days old.</p>
<dt><code>-nokay</code></p>
<dd> As <code>-nok</code> except it will report on older systems.</p>
<dt><code>-p</code></p>
<dd> The names of one or more patch files or other text attachments to be included with the report. Multiple files must be separated with commas.</p>
<dt><code>-r</code></p>
<dd> Your return address. The program will ask you to confirm its default if you don&#8217;t use this option.</p>
<dt><code>-S</code></p>
<dd> Save or send the report without asking for confirmation.</p>
<dt><code>-s</code></p>
<dd> Subject to include with the report. You will be prompted if you don&#8217;t supply one on the command line.</p>
<dt><code>-t</code></p>
<dd> Test mode. Makes it possible to command perlbug from a pipe or file, for testing purposes.</p>
<dt><code>-T</code></p>
<dd> Send a thank-you note instead of a bug report.</p>
<dt><code>-v</code></p>
<dd> Include verbose configuration data in the report.</dl>
