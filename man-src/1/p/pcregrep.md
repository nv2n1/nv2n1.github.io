<h2>NAME</h2>
<p> pcregrep &#8211; a grep with Perl-compatible regular expressions.</p>
<h2>SYNOPSIS</h2>
<p> <code>pcregrep [options] [long options] [pattern] [path1 path2 &#8230;]</code></p>
<h2>DESCRIPTION</h2>
<p> <code>pcregrep</code> searches files for character patterns, in the same way as other grep commands do, but it uses the PCRE regular expression library to support patterns that are compatible with the regular expressions of Perl 5. See <code><a href="/docs/linux/man/3-pcrepattern/">pcrepattern</a></code>(3) for a full description of syntax and semantics of the regular expressions that PCRE supports. </p>
<p> Patterns, whether supplied on the command line or in a separate file, are given without delimiters. For example: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>pcregrep Thursday&nbsp;<wbr>/etc/motd </p>
<p> If you attempt to use delimiters (for example, by surrounding a pattern with slashes, as is common in Perl scripts), they are interpreted as part of the pattern. Quotes can of course be used to delimit patterns on the command line because they are interpreted by the shell, and indeed quotes are required if a pattern contains white space or shell metacharacters. </p>
<p> The first argument that follows any option settings is treated as the single pattern to be matched when neither <code>-e</code> nor <code>-f</code> is present. Conversely, when one or both of these options are used to specify patterns, all arguments are treated as path names. At least one of <code>-e</code>, <code>-f</code>, or an argument pattern must be provided. </p>
<p> If no files are specified, <code>pcregrep</code> reads the standard input. The standard input can also be referenced by a name consisting of a single hyphen. For example: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>pcregrep some-pattern&nbsp;<wbr>/file1 &#8211;&nbsp;<wbr>/file3 </p>
<p> By default, each line that matches a pattern is copied to the standard output, and if there is more than one file, the file name is output at the start of each line, followed by a colon. However, there are options that can change how <code>pcregrep</code> behaves. In particular, the <code>-M</code> option makes it possible to search for patterns that span line boundaries. What defines a line boundary is controlled by the <code>-N</code> (<code>&#8211;newline</code>) option. </p>
<p> The amount of memory used for buffering files that are being scanned is controlled by a parameter that can be set by the <code>&#8211;buffer-size</code> option. The default value for this parameter is specified when <code>pcregrep</code> is built, with the default default being 20K. A block of memory three times this size is used (to allow for buffering &quot;before&quot; and &quot;after&quot; lines). An error occurs if a line overflows the buffer. </p>
<p> Patterns can be no longer than 8K or BUFSIZ bytes, whichever is the greater. BUFSIZ is defined in <code>&lt;stdio.h&gt;</code>. When there is more than one pattern (specified by the use of <code>-e</code> and/or <code>-f</code>), each pattern is applied to each line in the order in which they are defined, except that all the <code>-e</code> patterns are tried before the <code>-f</code> patterns. </p>
<p> By default, as soon as one pattern matches a line, no further patterns are considered. However, if <code>&#8211;colour</code> (or <code>&#8211;color</code>) is used to colour the matching substrings, or if <code>&#8211;only-matching</code>, <code>&#8211;file-offsets</code>, or <code>&#8211;line-offsets</code> is used to output only the part of the line that matched (either shown literally, or as an offset), scanning resumes immediately following the match, so that further matches on the same line can be found. If there are multiple patterns, they are all tried on the remainder of the line, but patterns that follow the one that matched are not tried on the earlier part of the line. </p>
<p> This behaviour means that the order in which multiple patterns are specified can affect the output when one of the above options is used. This is no longer the same behaviour as GNU grep, which now manages to display earlier matches for later patterns (as long as there is no overlap). </p>
<p> Patterns that can match an empty string are accepted, but empty string matches are never recognized. An example is the pattern &quot;(super)?(man)?&quot;, in which all components are optional. This pattern finds all occurrences of both &quot;super&quot; and &quot;man&quot;; the output differs from matching with &quot;super|man&quot; when only the matching substrings are being shown. </p>
<p> If the <code>LC_ALL</code> or <code>LC_CTYPE</code> environment variable is set, <code>pcregrep</code> uses the value to set a locale when calling the PCRE library. The <code>&#8211;locale</code> option can be used to override this.</p>
<h2>SUPPORT FOR COMPRESSED FILES</h2>
<p> It is possible to compile <code>pcregrep</code> so that it uses <code>libz</code> or <code>libbz2</code> to read files whose names end in <code>.gz</code> or <code>.bz2</code>, respectively. You can find out whether your binary has support for one or both of these file types by running it with the <code>&#8211;help</code> option. If the appropriate support is not present, files are treated as plain text. The standard input is always so treated.</p>
<h2>BINARY FILES</h2>
<p> By default, a file that contains a binary zero byte within the first 1024 bytes is identified as a binary file, and is processed specially. (GNU grep also identifies binary files in this manner.) See the <code>&#8211;binary-files</code> option for a means of changing the way binary files are handled.</p>
<h2>OPTIONS</h2>
<p> The order in which some of the options appear can affect the output. For example, both the <code>-h</code> and <code>-l</code> options affect the printing of file names. Whichever comes later in the command line will be the one that takes effect. Similarly, except where noted below, if an option is given twice, the later setting is used. Numerical values for options may be followed by K or M, to signify multiplication by 1024 or 1024*1024 respectively.</p>
<dl>
<dt><code>&#8212;</code></p>
<dd> This terminates the list of options. It is useful if the next item on the command line starts with a hyphen but is not an option. This allows for the processing of patterns and filenames that start with hyphens.</p>
<dt><code>-A</code> <i>number</i>, <code>&#8211;after-context=</code><i>number</i></p>
<dd> Output <i>number</i> lines of context after each matching line. If filenames and/or line numbers are being output, a hyphen separator is used instead of a colon for the context lines. A line containing &quot;&#8211;&quot; is output between each group of lines, unless they are in fact contiguous in the input file. The value of <i>number</i> is expected to be relatively small. However, <code>pcregrep</code> guarantees to have up to 8K of following text available for context output.</p>
<dt><code>-a</code>, <code>&#8211;text</code></p>
<dd> Treat binary files as text. This is equivalent to <code>&#8211;binary-files</code>=<i>text</i>.</p>
<dt><code>-B</code> <i>number</i>, <code>&#8211;before-context=</code><i>number</i></p>
<dd> Output <i>number</i> lines of context before each matching line. If filenames and/or line numbers are being output, a hyphen separator is used instead of a colon for the context lines. A line containing &quot;&#8211;&quot; is output between each group of lines, unless they are in fact contiguous in the input file. The value of <i>number</i> is expected to be relatively small. However, <code>pcregrep</code> guarantees to have up to 8K of preceding text available for context output.</p>
<dt><code>&#8211;binary-files=</code><i>word</i></p>
<dd> Specify how binary files are to be processed. If the word is &quot;binary&quot; (the default), pattern matching is performed on binary files, but the only output is &quot;Binary file &lt;name&gt; matches&quot; when a match succeeds. If the word is &quot;text&quot;, which is equivalent to the <code>-a</code> or <code>&#8211;text</code> option, binary files are processed in the same way as any other file. In this case, when a match succeeds, the output may be binary garbage, which can have nasty effects if sent to a terminal. If the word is &quot;without-match&quot;, which is equivalent to the <code>-I</code> option, binary files are not processed at all; they are assumed not to be of interest.</p>
<dt><code>&#8211;buffer-size=</code><i>number</i></p>
<dd> Set the parameter that controls how much memory is used for buffering files that are being scanned.</p>
<dt><code>-C</code> <i>number</i>, <code>&#8211;context=</code><i>number</i></p>
<dd> Output <i>number</i> lines of context both before and after each matching line. This is equivalent to setting both <code>-A</code> and <code>-B</code> to the same value.</p>
<dt><code>-c</code>, <code>&#8211;count</code></p>
<dd> Do not output individual lines from the files that are being scanned; instead output the number of lines that would otherwise have been shown. If no lines are selected, the number zero is output. If several files are are being scanned, a count is output for each of them. However, if the <code>&#8211;files-with-matches</code> option is also used, only those files whose counts are greater than zero are listed. When <code>-c</code> is used, the <code>-A</code>, <code>-B</code>, and <code>-C</code> options are ignored.</p>
<dt><code>&#8211;colour</code>, <code>&#8211;color</code></p>
<dd> If this option is given without any data, it is equivalent to &quot;&#8211;colour=auto&quot;. If data is required, it must be given in the same shell item, separated by an equals sign.</p>
<dt><code>&#8211;colour=</code><i>value</i>, <code>&#8211;color=</code><i>value</i></p>
<dd> This option specifies under what circumstances the parts of a line that matched a pattern should be coloured in the output. By default, the output is not coloured. The value (which is optional, see above) may be &quot;never&quot;, &quot;always&quot;, or &quot;auto&quot;. In the latter case, colouring happens only if the standard output is connected to a terminal. More resources are used when colouring is enabled, because <code>pcregrep</code> has to search for all possible matches in a line, not just one, in order to colour them all. </p>
<p> The colour that is used can be specified by setting the environment variable PCREGREP_COLOUR or PCREGREP_COLOR. The value of this variable should be a string of two numbers, separated by a semicolon. They are copied directly into the control string for setting colour on a terminal, so it is your responsibility to ensure that they make sense. If neither of the environment variables is set, the default is &quot;1;31&quot;, which gives red.</p>
<dt><code>-D</code> <i>action</i>, <code>&#8211;devices=</code><i>action</i></p>
<dd> If an input path is not a regular file or a directory, &quot;action&quot; specifies how it is to be processed. Valid values are &quot;read&quot; (the default) or &quot;skip&quot; (silently skip the path).</p>
<dt><code>-d</code> <i>action</i>, <code>&#8211;directories=</code><i>action</i></p>
<dd> If an input path is a directory, &quot;action&quot; specifies how it is to be processed. Valid values are &quot;read&quot; (the default in non-Windows environments, for compatibility with GNU grep), &quot;recurse&quot; (equivalent to the <code>-r</code> option), or &quot;skip&quot; (silently skip the path, the default in Windows environments). In the &quot;read&quot; case, directories are read as if they were ordinary files. In some operating systems the effect of reading a directory like this is an immediate end-of-file; in others it may provoke an error.</p>
<dt><code>-e</code> <i>pattern</i>, <code>&#8211;regex=</code><i>pattern</i>, <code>&#8211;regexp=</code><i>pattern</i></p>
<dd> Specify a pattern to be matched. This option can be used multiple times in order to specify several patterns. It can also be used as a way of specifying a single pattern that starts with a hyphen. When <code>-e</code> is used, no argument pattern is taken from the command line; all arguments are treated as file names. There is no limit to the number of patterns. They are applied to each line in the order in which they are defined until one matches. </p>
<p> If <code>-f</code> is used with <code>-e</code>, the command line patterns are matched first, followed by the patterns from the file(s), independent of the order in which these options are specified. Note that multiple use of <code>-e</code> is not the same as a single pattern with alternatives. For example, X|Y finds the first character in a line that is X or Y, whereas if the two patterns are given separately, with X first, <code>pcregrep</code> finds X if it is present, even if it follows Y in the line. It finds Y only if there is no X in the line. This matters only if you are using <code>-o</code> or <code>&#8211;colo(u)r</code> to show the part(s) of the line that matched.</p>
<dt><code>&#8211;exclude</code>=<i>pattern</i></p>
<dd> Files (but not directories) whose names match the pattern are skipped without being processed. This applies to all files, whether listed on the command line, obtained from <code>&#8211;file-list</code>, or by scanning a directory. The pattern is a PCRE regular expression, and is matched against the final component of the file name, not the entire path. The <code>-F</code>, <code>-w</code>, and <code>-x</code> options do not apply to this pattern. The option may be given any number of times in order to specify multiple patterns. If a file name matches both an <code>&#8211;include</code> and an <code>&#8211;exclude</code> pattern, it is excluded. There is no short form for this option.</p>
<dt><code>&#8211;exclude-from=</code><i>filename</i></p>
<dd> Treat each non-empty line of the file as the data for an <code>&#8211;exclude</code> option. What constitutes a newline when reading the file is the operating system&#8217;s default. The <code>&#8211;newline</code> option has no effect on this option. This option may be given more than once in order to specify a number of files to read.</p>
<dt><code>&#8211;exclude-dir</code>=<i>pattern</i></p>
<dd> Directories whose names match the pattern are skipped without being processed, whatever the setting of the <code>&#8211;recursive</code> option. This applies to all directories, whether listed on the command line, obtained from <code>&#8211;file-list</code>, or by scanning a parent directory. The pattern is a PCRE regular expression, and is matched against the final component of the directory name, not the entire path. The <code>-F</code>, <code>-w</code>, and <code>-x</code> options do not apply to this pattern. The option may be given any number of times in order to specify more than one pattern. If a directory matches both <code>&#8211;include-dir</code> and <code>&#8211;exclude-dir</code>, it is excluded. There is no short form for this option.</p>
<dt><code>-F</code>, <code>&#8211;fixed-strings</code></p>
<dd> Interpret each data-matching pattern as a list of fixed strings, separated by newlines, instead of as a regular expression. What constitutes a newline for this purpose is controlled by the <code>&#8211;newline</code> option. The <code>-w</code> (match as a word) and <code>-x</code> (match whole line) options can be used with <code>-F</code>. They apply to each of the fixed strings. A line is selected if any of the fixed strings are found in it (subject to <code>-w</code> or <code>-x</code>, if present). This option applies only to the patterns that are matched against the contents of files; it does not apply to patterns specified by any of the <code>&#8211;include</code> or <code>&#8211;exclude</code> options.</p>
<dt><code>-f</code> <i>filename</i>, <code>&#8211;file=</code><i>filename</i></p>
<dd> Read patterns from the file, one per line, and match them against each line of input. What constitutes a newline when reading the file is the operating system&#8217;s default. The <code>&#8211;newline</code> option has no effect on this option. Trailing white space is removed from each line, and blank lines are ignored. An empty file contains no patterns and therefore matches nothing. See also the comments about multiple patterns versus a single pattern with alternatives in the description of <code>-e</code> above. </p>
<p> If this option is given more than once, all the specified files are read. A data line is output if any of the patterns match it. A filename can be given as &quot;-&quot; to refer to the standard input. When <code>-f</code> is used, patterns specified on the command line using <code>-e</code> may also be present; they are tested before the file&#8217;s patterns. However, no other pattern is taken from the command line; all arguments are treated as the names of paths to be searched.</p>
<dt><code>&#8211;file-list</code>=<i>filename</i></p>
<dd> Read a list of files and/or directories that are to be scanned from the given file, one per line. Trailing white space is removed from each line, and blank lines are ignored. These paths are processed before any that are listed on the command line. The filename can be given as &quot;-&quot; to refer to the standard input. If <code>&#8211;file</code> and <code>&#8211;file-list</code> are both specified as &quot;-&quot;, patterns are read first. This is useful only when the standard input is a terminal, from which further lines (the list of files) can be read after an end-of-file indication. If this option is given more than once, all the specified files are read.</p>
<dt><code>&#8211;file-offsets</code></p>
<dd> Instead of showing lines or parts of lines that match, show each match as an offset from the start of the file and a length, separated by a comma. In this mode, no context is shown. That is, the <code>-A</code>, <code>-B</code>, and <code>-C</code> options are ignored. If there is more than one match in a line, each of them is shown separately. This option is mutually exclusive with <code>&#8211;line-offsets</code> and <code>&#8211;only-matching</code>.</p>
<dt><code>-H</code>, <code>&#8211;with-filename</code></p>
<dd> Force the inclusion of the filename at the start of output lines when searching a single file. By default, the filename is not shown in this case. For matching lines, the filename is followed by a colon; for context lines, a hyphen separator is used. If a line number is also being output, it follows the file name.</p>
<dt><code>-h</code>, <code>&#8211;no-filename</code></p>
<dd> Suppress the output filenames when searching multiple files. By default, filenames are shown when multiple files are searched. For matching lines, the filename is followed by a colon; for context lines, a hyphen separator is used. If a line number is also being output, it follows the file name.</p>
<dt><code>&#8211;help</code></p>
<dd> Output a help message, giving brief details of the command options and file type support, and then exit. Anything else on the command line is ignored.</p>
<dt><code>-I</code></p>
<dd> Treat binary files as never matching. This is equivalent to <code>&#8211;binary-files</code>=<i>without-match</i>.</p>
<dt><code>-i</code>, <code>&#8211;ignore-case</code></p>
<dd> Ignore upper/lower case distinctions during comparisons.</p>
<dt><code>&#8211;include</code>=<i>pattern</i></p>
<dd> If any <code>&#8211;include</code> patterns are specified, the only files that are processed are those that match one of the patterns (and do not match an <code>&#8211;exclude</code> pattern). This option does not affect directories, but it applies to all files, whether listed on the command line, obtained from <code>&#8211;file-list</code>, or by scanning a directory. The pattern is a PCRE regular expression, and is matched against the final component of the file name, not the entire path. The <code>-F</code>, <code>-w</code>, and <code>-x</code> options do not apply to this pattern. The option may be given any number of times. If a file name matches both an <code>&#8211;include</code> and an <code>&#8211;exclude</code> pattern, it is excluded. There is no short form for this option.</p>
<dt><code>&#8211;include-from=</code><i>filename</i></p>
<dd> Treat each non-empty line of the file as the data for an <code>&#8211;include</code> option. What constitutes a newline for this purpose is the operating system&#8217;s default. The <code>&#8211;newline</code> option has no effect on this option. This option may be given any number of times; all the files are read.</p>
<dt><code>&#8211;include-dir</code>=<i>pattern</i></p>
<dd> If any <code>&#8211;include-dir</code> patterns are specified, the only directories that are processed are those that match one of the patterns (and do not match an <code>&#8211;exclude-dir</code> pattern). This applies to all directories, whether listed on the command line, obtained from <code>&#8211;file-list</code>, or by scanning a parent directory. The pattern is a PCRE regular expression, and is matched against the final component of the directory name, not the entire path. The <code>-F</code>, <code>-w</code>, and <code>-x</code> options do not apply to this pattern. The option may be given any number of times. If a directory matches both <code>&#8211;include-dir</code> and <code>&#8211;exclude-dir</code>, it is excluded. There is no short form for this option.</p>
<dt><code>-L</code>, <code>&#8211;files-without-match</code></p>
<dd> Instead of outputting lines from the files, just output the names of the files that do not contain any lines that would have been output. Each file name is output once, on a separate line.</p>
<dt><code>-l</code>, <code>&#8211;files-with-matches</code></p>
<dd> Instead of outputting lines from the files, just output the names of the files containing lines that would have been output. Each file name is output once, on a separate line. Searching normally stops as soon as a matching line is found in a file. However, if the <code>-c</code> (count) option is also used, matching continues in order to obtain the correct count, and those files that have at least one match are listed along with their counts. Using this option with <code>-c</code> is a way of suppressing the listing of files with no matches.</p>
<dt><code>&#8211;label</code>=<i>name</i></p>
<dd> This option supplies a name to be used for the standard input when file names are being output. If not supplied, &quot;(standard input)&quot; is used. There is no short form for this option.</p>
<dt><code>&#8211;line-buffered</code></p>
<dd> When this option is given, input is read and processed line by line, and the output is flushed after each write. By default, input is read in large chunks, unless <code>pcregrep</code> can determine that it is reading from a terminal (which is currently possible only in Unix-like environments). Output to terminal is normally automatically flushed by the operating system. This option can be useful when the input or output is attached to a pipe and you do not want <code>pcregrep</code> to buffer up large amounts of data. However, its use will affect performance, and the <code>-M</code> (multiline) option ceases to work.</p>
<dt><code>&#8211;line-offsets</code></p>
<dd> Instead of showing lines or parts of lines that match, show each match as a line number, the offset from the start of the line, and a length. The line number is terminated by a colon (as usual; see the <code>-n</code> option), and the offset and length are separated by a comma. In this mode, no context is shown. That is, the <code>-A</code>, <code>-B</code>, and <code>-C</code> options are ignored. If there is more than one match in a line, each of them is shown separately. This option is mutually exclusive with <code>&#8211;file-offsets</code> and <code>&#8211;only-matching</code>.</p>
<dt><code>&#8211;locale</code>=<i>locale-name</i></p>
<dd> This option specifies a locale to be used for pattern matching. It overrides the value in the <code>LC_ALL</code> or <code>LC_CTYPE</code> environment variables. If no locale is specified, the PCRE library&#8217;s default (usually the &quot;C&quot; locale) is used. There is no short form for this option.</p>
<dt><code>&#8211;match-limit</code>=<i>number</i></p>
<dd> Processing some regular expression patterns can require a very large amount of memory, leading in some cases to a program crash if not enough is available. Other patterns may take a very long time to search for all possible matching strings. The <code>pcre_exec()</code> function that is called by <code>pcregrep</code> to do the matching has two parameters that can limit the resources that it uses. </p>
<p> The <code>&#8211;match-limit</code> option provides a means of limiting resource usage when processing patterns that are not going to match, but which have a very large number of possibilities in their search trees. The classic example is a pattern that uses nested unlimited repeats. Internally, PCRE uses a function called <code>match()</code> which it calls repeatedly (sometimes recursively). The limit set by <code>&#8211;match-limit</code> is imposed on the number of times this function is called during a match, which has the effect of limiting the amount of backtracking that can take place. </p>
<p> The <code>&#8211;recursion-limit</code> option is similar to <code>&#8211;match-limit</code>, but instead of limiting the total number of times that <code>match()</code> is called, it limits the depth of recursive calls, which in turn limits the amount of memory that can be used. The recursion depth is a smaller number than the total number of calls, because not all calls to <code>match()</code> are recursive. This limit is of use only if it is set smaller than <code>&#8211;match-limit</code>. </p>
<p> There are no short forms for these options. The default settings are specified when the PCRE library is compiled, with the default default being 10 million.</p>
<dt><code>-M</code>, <code>&#8211;multiline</code></p>
<dd> Allow patterns to match more than one line. When this option is given, patterns may usefully contain literal newline characters and internal occurrences of ^ and $ characters. The output for a successful match may consist of more than one line, the last of which is the one in which the match ended. If the matched string ends with a newline sequence the output ends at the end of that line. </p>
<p> When this option is set, the PCRE library is called in &quot;multiline&quot; mode. There is a limit to the number of lines that can be matched, imposed by the way that <code>pcregrep</code> buffers the input file as it scans it. However, <code>pcregrep</code> ensures that at least 8K characters or the rest of the document (whichever is the shorter) are available for forward matching, and similarly the previous 8K characters (or all the previous characters, if fewer than 8K) are guaranteed to be available for lookbehind assertions. This option does not work when input is read line by line (see &#8211;line-buffered.)</p>
<dt><code>-N</code> <i>newline-type</i>, <code>&#8211;newline</code>=<i>newline-type</i></p>
<dd> The PCRE library supports five different conventions for indicating the ends of lines. They are the single-character sequences CR (carriage return) and LF (linefeed), the two-character sequence CRLF, an &quot;anycrlf&quot; convention, which recognizes any of the preceding three types, and an &quot;any&quot; convention, in which any Unicode line ending sequence is assumed to end a line. The Unicode sequences are the three just mentioned, plus VT (vertical tab, U+000B), FF (form feed, U+000C), NEL (next line, U+0085), LS (line separator, U+2028), and PS (paragraph separator, U+2029). </p>
<p> When the PCRE library is built, a default line-ending sequence is specified. This is normally the standard sequence for the operating system. Unless otherwise specified by this option, <code>pcregrep</code> uses the library&#8217;s default. The possible values for this option are CR, LF, CRLF, ANYCRLF, or ANY. This makes it possible to use <code>pcregrep</code> to scan files that have come from other environments without having to modify their line endings. If the data that is being scanned does not agree with the convention set by this option, <code>pcregrep</code> may behave in strange ways. Note that this option does not apply to files specified by the <code>-f</code>, <code>&#8211;exclude-from</code>, or <code>&#8211;include-from</code> options, which are expected to use the operating system&#8217;s standard newline sequence.</p>
<dt><code>-n</code>, <code>&#8211;line-number</code></p>
<dd> Precede each output line by its line number in the file, followed by a colon for matching lines or a hyphen for context lines. If the filename is also being output, it precedes the line number. This option is forced if <code>&#8211;line-offsets</code> is used.</p>
<dt><code>&#8211;no-jit</code></p>
<dd> If the PCRE library is built with support for just-in-time compiling (which speeds up matching), <code>pcregrep</code> automatically makes use of this, unless it was explicitly disabled at build time. This option can be used to disable the use of JIT at run time. It is provided for testing and working round problems. It should never be needed in normal use.</p>
<dt><code>-o</code>, <code>&#8211;only-matching</code></p>
<dd> Show only the part of the line that matched a pattern instead of the whole line. In this mode, no context is shown. That is, the <code>-A</code>, <code>-B</code>, and <code>-C</code> options are ignored. If there is more than one match in a line, each of them is shown separately. If <code>-o</code> is combined with <code>-v</code> (invert the sense of the match to find non-matching lines), no output is generated, but the return code is set appropriately. If the matched portion of the line is empty, nothing is output unless the file name or line number are being printed, in which case they are shown on an otherwise empty line. This option is mutually exclusive with <code>&#8211;file-offsets</code> and <code>&#8211;line-offsets</code>.</p>
<dt><code>-o</code><i>number</i>, <code>&#8211;only-matching</code>=<i>number</i></p>
<dd> Show only the part of the line that matched the capturing parentheses of the given number. Up to 32 capturing parentheses are supported, and -o0 is equivalent to <code>-o</code> without a number. Because these options can be given without an argument (see above), if an argument is present, it must be given in the same shell item, for example, -o3 or &#8211;only-matching=2. The comments given for the non-argument case above also apply to this case. If the specified capturing parentheses do not exist in the pattern, or were not set in the match, nothing is output unless the file name or line number are being printed. </p>
<p> If this option is given multiple times, multiple substrings are output, in the order the options are given. For example, -o3 -o1 -o3 causes the substrings matched by capturing parentheses 3 and 1 and then 3 again to be output. By default, there is no separator (but see the next option).</p>
<dt><code>&#8211;om-separator</code>=<i>text</i></p>
<dd> Specify a separating string for multiple occurrences of <code>-o</code>. The default is an empty string. Separating strings are never coloured.</p>
<dt><code>-q</code>, <code>&#8211;quiet</code></p>
<dd> Work quietly, that is, display nothing except error messages. The exit status indicates whether or not any matches were found.</p>
<dt><code>-r</code>, <code>&#8211;recursive</code></p>
<dd> If any given path is a directory, recursively scan the files it contains, taking note of any <code>&#8211;include</code> and <code>&#8211;exclude</code> settings. By default, a directory is read as a normal file; in some operating systems this gives an immediate end-of-file. This option is a shorthand for setting the <code>-d</code> option to &quot;recurse&quot;.</p>
<dt><code>&#8211;recursion-limit</code>=<i>number</i></p>
<dd> See <code>&#8211;match-limit</code> above.</p>
<dt><code>-s</code>, <code>&#8211;no-messages</code></p>
<dd> Suppress error messages about non-existent or unreadable files. Such files are quietly skipped. However, the return code is still 2, even if matches were found in other files.</p>
<dt><code>-u</code>, <code>&#8211;utf-8</code></p>
<dd> Operate in UTF-8 mode. This option is available only if PCRE has been compiled with UTF-8 support. All patterns (including those for any <code>&#8211;exclude</code> and <code>&#8211;include</code> options) and all subject lines that are scanned must be valid strings of UTF-8 characters.</p>
<dt><code>-V</code>, <code>&#8211;version</code></p>
<dd> Write the version numbers of <code>pcregrep</code> and the PCRE library to the standard output and then exit. Anything else on the command line is ignored.</p>
<dt><code>-v</code>, <code>&#8211;invert-match</code></p>
<dd> Invert the sense of the match, so that lines which do <i>not</i> match any of the patterns are the ones that are found.</p>
<dt><code>-w</code>, <code>&#8211;word-regex</code>, <code>&#8211;word-regexp</code></p>
<dd> Force the patterns to match only whole words. This is equivalent to having  at the start and end of the pattern. This option applies only to the patterns that are matched against the contents of files; it does not apply to patterns specified by any of the <code>&#8211;include</code> or <code>&#8211;exclude</code> options.</p>
<dt><code>-x</code>, <code>&#8211;line-regex</code>, <code>&#8211;line-regexp</code></p>
<dd> Force the patterns to be anchored (each must start matching at the beginning of a line) and in addition, require them to match entire lines. This is equivalent to having ^ and $ characters at the start and end of each alternative branch in every pattern. This option applies only to the patterns that are matched against the contents of files; it does not apply to patterns specified by any of the <code>&#8211;include</code> or <code>&#8211;exclude</code> options.</dl>
<h2>ENVIRONMENT VARIABLES</h2>
<p> The environment variables <code>LC_ALL</code> and <code>LC_CTYPE</code> are examined, in that order, for a locale. The first one that is set is used. This can be overridden by the <code>&#8211;locale</code> option. If no locale is set, the PCRE library&#8217;s default (usually the &quot;C&quot; locale) is used.</p>
<h2>NEWLINES</h2>
<p> The <code>-N</code> (<code>&#8211;newline</code>) option allows <code>pcregrep</code> to scan files with different newline conventions from the default. Any parts of the input files that are written to the standard output are copied identically, with whatever newline sequences they have in the input. However, the setting of this option does not affect the interpretation of files specified by the <code>-f</code>, <code>&#8211;exclude-from</code>, or <code>&#8211;include-from</code> options, which are assumed to use the operating system&#8217;s standard newline sequence, nor does it affect the way in which <code>pcregrep</code> writes informational messages to the standard error and output streams. For these it uses the string &quot;
&quot; to indicate newlines, relying on the C I/O library to convert this to an appropriate sequence.</p>
<h2>OPTIONS COMPATIBILITY</h2>
<p> Many of the short and long forms of <code>pcregrep</code>&#8216;s options are the same as in the GNU <code>grep</code> program. Any long option of the form <code>&#8211;xxx-regexp</code> (GNU terminology) is also available as <code>&#8211;xxx-regex</code> (PCRE terminology). However, the <code>&#8211;file-list</code>, <code>&#8211;file-offsets</code>, <code>&#8211;include-dir</code>, <code>&#8211;line-offsets</code>, <code>&#8211;locale</code>, <code>&#8211;match-limit</code>, <code>-M</code>, <code>&#8211;multiline</code>, <code>-N</code>, <code>&#8211;newline</code>, <code>&#8211;om-separator</code>, <code>&#8211;recursion-limit</code>, <code>-u</code>, and <code>&#8211;utf-8</code> options are specific to <code>pcregrep</code>, as is the use of the <code>&#8211;only-matching</code> option with a capturing parentheses number. </p>
<p> Although most of the common options work the same way, a few are different in <code>pcregrep</code>. For example, the <code>&#8211;include</code> option&#8217;s argument is a glob for GNU <code>grep</code>, but a regular expression for <code>pcregrep</code>. If both the <code>-c</code> and <code>-l</code> options are given, GNU grep lists only file names, without counts, but <code>pcregrep</code> gives the counts.</p>
<h2>OPTIONS WITH DATA</h2>
<p> There are four different ways in which an option with data can be specified. If a short form option is used, the data may follow immediately, or (with one exception) in the next command line item. For example: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>-f/some/file<br />
&nbsp;<wbr>&nbsp;<wbr>-f&nbsp;<wbr>/some/file </p>
<p> The exception is the <code>-o</code> option, which may appear with or without data. Because of this, if data is present, it must follow immediately in the same item, for example -o3. </p>
<p> If a long form option is used, the data may appear in the same command line item, separated by an equals character, or (with two exceptions) it may appear in the next command line item. For example: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>&#8211;file=/some/file<br />
&nbsp;<wbr>&nbsp;<wbr>&#8211;file&nbsp;<wbr>/some/file </p>
<p> Note, however, that if you want to supply a file name beginning with ~ as data in a shell command, and have the shell expand ~ to a home directory, you must separate the file name from the option, because the shell does not treat ~ specially unless it is at the start of an item. </p>
<p> The exceptions to the above are the <code>&#8211;colour</code> (or <code>&#8211;color</code>) and <code>&#8211;only-matching</code> options, for which the data is optional. If one of these options does have data, it must be given in the first form, using an equals character. Otherwise <code>pcregrep</code> will assume that it has no data.</p>
<h2>MATCHING ERRORS</h2>
<p> It is possible to supply a regular expression that takes a very long time to fail to match certain lines. Such patterns normally involve nested indefinite repeats, for example: (a+)*\d when matched against a line of a&#8217;s with no final digit. The PCRE matching function has a resource limit that causes it to abort in these circumstances. If this happens, <code>pcregrep</code> outputs an error message and the line that caused the problem to the standard error stream. If there are more than 20 such errors, <code>pcregrep</code> gives up. </p>
<p> The <code>&#8211;match-limit</code> option of <code>pcregrep</code> can be used to set the overall resource limit; there is a second option called <code>&#8211;recursion-limit</code> that sets a limit on the amount of memory (usually stack) that is used (see the discussion of these options above).</p>
<h2>DIAGNOSTICS</h2>
<p> Exit status is 0 if any matches were found, 1 if no matches were found, and 2 for syntax errors, overlong lines, non-existent or inaccessible files (even if matches were found in other files) or too many matching errors. Using the <code>-s</code> option to suppress error messages about inaccessible files does not affect the return code.</p>
