<h2 class="name">NAME</h2>
<p> nsupdate &#8211; dynamic DNS update utility </p>
<h2>SYNOPSIS</h2>
<p> <code>nsupdate</code> [<code>-d</code>] [<code>-D</code>] [<code>-i</code>] [<code>-L</code> level] [ [<code>-g</code>] | [<code>-o</code>] | [<code>-l</code>] | [<code>-y</code> [hmac:]keyname:secret] | [<code>-k</code> keyfile] ] [<code>-t</code> timeout] [<code>-u</code> udptimeout] [<code>-r</code> udpretries] [<code>-v</code>] [<code>-T</code>] [<code>-P</code>] [<code>-V</code>] [ [<code>-4</code>] | [<code>-6</code>] ] [filename]</p>
<h2>DESCRIPTION</h2>
<p> <code>nsupdate</code> is used to submit Dynamic DNS Update requests, as defined in <i>RFC 2136</i>, to a name server. This allows resource records to be added or removed from a zone without manually editing the zone file. A single update request can contain requests to add or remove more than one resource record. </p>
<p> Zones that are under dynamic control via <code>nsupdate</code> or a DHCP server should not be edited by hand. Manual edits could conflict with dynamic updates and cause data to be lost. </p>
<p> The resource records that are dynamically added or removed with <code>nsupdate</code> must be in the same zone. Requests are sent to the zone&#8217;s primary server, which is identified by the MNAME field of the zone&#8217;s SOA record. </p>
<p> Transaction signatures can be used to authenticate the Dynamic DNS updates. These use the TSIG resource record type described in <i>RFC 2845</i>, the SIG(0) record described in <i>RFC 2535</i> and <i>RFC 2931</i>, or GSS-TSIG as described in <i>RFC 3645</i>. </p>
<p> TSIG relies on a shared secret that should only be known to <code>nsupdate</code> and the name server. For instance, suitable <code>key</code> and <code>server</code> statements are added to <code>/etc/bind/named.conf</code> so that the name server can associate the appropriate secret key and algorithm with the IP address of the client application that is using TSIG authentication. <i>ddns-confgen</i> can generate suitable configuration fragments. <code>nsupdate</code> uses the <i>-y</i> or <i>-k</i> options to provide the TSIG shared secret; these options are mutually exclusive. </p>
<p> SIG(0) uses public key cryptography. To use a SIG(0) key, the public key must be stored in a KEY record in a zone served by the name server. </p>
<p> GSS-TSIG uses Kerberos credentials. Standard GSS-TSIG mode is switched on with the <i>-g</i> flag. A non-standards-compliant variant of GSS-TSIG used by Windows 2000 can be switched on with the <i>-o</i> flag.</p>
<h2>OPTIONS</h2>
<dl>
<dt><code>-4</code></p>
<dd> This option sets use of IPv4 only.</p>
<dt><code>-6</code></p>
<dd> This option sets use of IPv6 only.</p>
<dt><code>-C</code></p>
<dd> Overrides the default <i>resolv.conf</i> file. This is only intended for testing.</p>
<dt><code>-d</code></p>
<dd> This option sets debug mode, which provides tracing information about the update requests that are made and the replies received from the name server.</p>
<dt><code>-D</code></p>
<dd> This option sets extra debug mode.</p>
<dt><code>-g</code></p>
<dd> This option enables standard GSS-TSIG mode.</p>
<dt><code>-i</code></p>
<dd> This option forces interactive mode, even when standard input is not a terminal.</p>
<dt><code>-k keyfile</code></p>
<dd> This option indicates the file containing the TSIG authentication key. Keyfiles may be in two formats: a single file containing a <i>named.conf</i>-format <code>key</code> statement, which may be generated automatically by <i>ddns-confgen</i>; or a pair of files whose names are of the format <code>K{name}.+157.+{random}.key</code> and <code>K{name}.+157.+{random}.private</code>, which can be generated by <i>dnssec-keygen</i>. The <i>-k</i> option can also be used to specify a SIG(0) key used to authenticate Dynamic DNS update requests. In this case, the key specified is not an HMAC-MD5 key.</p>
<dt><code>-l</code></p>
<dd> This option sets local-host only mode, which sets the server address to localhost (disabling the <code>server</code> so that the server address cannot be overridden). Connections to the local server use a TSIG key found in <code>/run/session.key</code>, which is automatically generated by <i>named</i> if any local <code>primary</code> zone has set <code>update-policy</code> to <code>local</code>. The location of this key file can be overridden with the <i>-k</i> option.</p>
<dt><code>-L level</code></p>
<dd> This option sets the logging debug level. If zero, logging is disabled.</p>
<dt><code>-o</code></p>
<dd> This option enables a non-standards-compliant variant of GSS-TSIG used by Windows 2000.</p>
<dt><code>-p port</code></p>
<dd> This option sets the port to use for connections to a name server. The default is 53.</p>
<dt><code>-P</code></p>
<dd> This option prints the list of private BIND-specific resource record types whose format is understood by <code>nsupdate</code>. See also the <i>-T</i> option.</p>
<dt><code>-r udpretries</code></p>
<dd> This option sets the number of UDP retries. The default is 3. If zero, only one update request is made.</p>
<dt><code>-t timeout</code></p>
<dd> This option sets the maximum time an update request can take before it is aborted. The default is 300 seconds. If zero, the timeout is disabled.</p>
<dt><code>-T</code></p>
<dd> This option prints the list of IANA standard resource record types whose format is understood by <code>nsupdate</code>. <code>nsupdate</code> exits after the lists are printed. The <i>-T</i> option can be combined with the <i>-P</i> option. </p>
<p> Other types can be entered using <code>TYPEXXXXX</code> where <code>XXXXX</code> is the decimal value of the type with no leading zeros. The rdata, if present, is parsed using the UNKNOWN rdata format, (&lt;backslash&gt; &lt;hash&gt; &lt;space&gt; &lt;length&gt; &lt;space&gt; &lt;hexstring&gt;).</p>
<dt><code>-u udptimeout</code></p>
<dd> This option sets the UDP retry interval. The default is 3 seconds. If zero, the interval is computed from the timeout interval and number of UDP retries.</p>
<dt><code>-v</code></p>
<dd> This option specifies that TCP should be used even for small update requests. By default, <code>nsupdate</code> uses UDP to send update requests to the name server unless they are too large to fit in a UDP request, in which case TCP is used. TCP may be preferable when a batch of update requests is made.</p>
<dt><code>-V</code></p>
<dd> This option prints the version number and exits.</p>
<dt><code>-y [hmac:]keyname:secret</code></p>
<dd> This option sets the literal TSIG authentication key. <code>keyname</code> is the name of the key, and <code>secret</code> is the base64 encoded shared secret. <code>hmac</code> is the name of the key algorithm; valid choices are <code>hmac-md5</code>, <code>hmac-sha1</code>, <code>hmac-sha224</code>, <code>hmac-sha256</code>, <code>hmac-sha384</code>, or <code>hmac-sha512</code>. If <code>hmac</code> is not specified, the default is <code>hmac-md5</code>, or if MD5 was disabled, <code>hmac-sha256</code>. </p>
<p> NOTE: Use of the <i>-y</i> option is discouraged because the shared secret is supplied as a command-line argument in clear text. This may be visible in the output from ps1 or in a history file maintained by the user&#8217;s shell.</dl>
<h2>INPUT FORMAT</h2>
<p> <code>nsupdate</code> reads input from <code>filename</code> or standard input. Each command is supplied on exactly one line of input. Some commands are for administrative purposes; others are either update instructions or prerequisite checks on the contents of the zone. These checks set conditions that some name or set of resource records (RRset) either exists or is absent from the zone. These conditions must be met if the entire update request is to succeed. Updates are rejected if the tests for the prerequisite conditions fail. </p>
<p> Every update request consists of zero or more prerequisites and zero or more updates. This allows a suitably authenticated update request to proceed if some specified resource records are either present or missing from the zone. A blank input line (or the <code>send</code> command) causes the accumulated commands to be sent as one Dynamic DNS update request to the name server. </p>
<p> The command formats and their meanings are as follows:</p>
<dl>
<dt><code>server servername port</code></p>
<dd> This command sends all dynamic update requests to the name server <code>servername</code>. When no server statement is provided, <code>nsupdate</code> sends updates to the primary server of the correct zone. The MNAME field of that zone&#8217;s SOA record identify the primary server for that zone. <code>port</code> is the port number on <code>servername</code> where the dynamic update requests are sent. If no port number is specified, the default DNS port number of 53 is used. </p>
<p> <code>NOTE:</code> This command has no effect when GSS-TSIG is in use.</p>
<dt><code>local address port</code></p>
<dd> This command sends all dynamic update requests using the local <code>address</code>. When no local statement is provided, <code>nsupdate</code> sends updates using an address and port chosen by the system. <code>port</code> can also be used to force requests to come from a specific port. If no port number is specified, the system assigns one.</p>
<dt><code>zone zonename</code></p>
<dd> This command specifies that all updates are to be made to the zone <code>zonename</code>. If no <code>zone</code> statement is provided, <code>nsupdate</code> attempts to determine the correct zone to update based on the rest of the input.</p>
<dt><code>class classname</code></p>
<dd> This command specifies the default class. If no <code>class</code> is specified, the default class is <code>IN</code>.</p>
<dt><code>ttl seconds</code></p>
<dd> This command specifies the default time-to-live, in seconds, for records to be added. The value <code>none</code> clears the default TTL.</p>
<dt><code>key hmac:keyname secret</code></p>
<dd> This command specifies that all updates are to be TSIG-signed using the <code>keyname</code>&#8211;<code>secret</code> pair. If <code>hmac</code> is specified, it sets the signing algorithm in use. The default is <code>hmac-md5</code>; if MD5 was disabled, the default is <code>hmac-sha256</code>. The <code>key</code> command overrides any key specified on the command line via <i>-y</i> or <i>-k</i>.</p>
<dt><code>gsstsig</code></p>
<dd> This command uses GSS-TSIG to sign the updates. This is equivalent to specifying <i>-g</i> on the command line.</p>
<dt><code>oldgsstsig</code></p>
<dd> This command uses the Windows 2000 version of GSS-TSIG to sign the updates. This is equivalent to specifying <i>-o</i> on the command line.</p>
<dt><code>realm [realm_name]</code></p>
<dd> When using GSS-TSIG, this command specifies the use of <code>realm_name</code> rather than the default realm in <code>krb5.conf</code>. If no realm is specified, the saved realm is cleared.</p>
<dt><code>check-names [boolean]</code></p>
<dd> This command turns on or off check-names processing on records to be added. Check-names has no effect on prerequisites or records to be deleted. By default check-names processing is on. If check-names processing fails, the record is not added to the UPDATE message.</p>
<dt><code>prereq nxdomain domain-name</code></p>
<dd> This command requires that no resource record of any type exist with the name <code>domain-name</code>.</p>
<dt><code>prereq yxdomain domain-name</code></p>
<dd> This command requires that <code>domain-name</code> exist (as at least one resource record, of any type).</p>
<dt><code>prereq nxrrset domain-name class type</code></p>
<dd> This command requires that no resource record exist of the specified <code>type</code>, <code>class</code>, and <code>domain-name</code>. If <code>class</code> is omitted, IN (Internet) is assumed.</p>
<dt><code>prereq yxrrset domain-name class type</code></p>
<dd> This command requires that a resource record of the specified <code>type</code>, <code>class</code> and <code>domain-name</code> exist. If <code>class</code> is omitted, IN (internet) is assumed.</p>
<dt><code>prereq yxrrset domain-name class type data</code></p>
<dd> With this command, the <code>data</code> from each set of prerequisites of this form sharing a common <code>type</code>, <code>class</code>, and <code>domain-name</code> are combined to form a set of RRs. This set of RRs must exactly match the set of RRs existing in the zone at the given <code>type</code>, <code>class</code>, and <code>domain-name</code>. The <code>data</code> are written in the standard text representation of the resource record&#8217;s RDATA.</p>
<dt><code>update delete domain-name ttl class type data</code></p>
<dd> This command deletes any resource records named <code>domain-name</code>. If <code>type</code> and <code>data</code> are provided, only matching resource records are removed. The Internet class is assumed if <code>class</code> is not supplied. The <code>ttl</code> is ignored, and is only allowed for compatibility.</p>
<dt><code>update add domain-name ttl class type data</code></p>
<dd> This command adds a new resource record with the specified <code>ttl</code>, <code>class</code>, and <code>data</code>.</p>
<dt><code>show</code></p>
<dd> This command displays the current message, containing all of the prerequisites and updates specified since the last send.</p>
<dt><code>send</code></p>
<dd> This command sends the current message. This is equivalent to entering a blank line.</p>
<dt><code>answer</code></p>
<dd> This command displays the answer.</p>
<dt><code>debug</code></p>
<dd> This command turns on debugging.</p>
<dt><code>version</code></p>
<dd> This command prints the version number.</p>
<dt><code>help</code></p>
<dd> This command prints a list of commands. </p>
<p> Lines beginning with a semicolon (;) are comments and are ignored.</dl>
<h2>EXAMPLES</h2>
<p> The examples below show how <code>nsupdate</code> can be used to insert and delete resource records from the <code>example.com</code> zone. Notice that the input in each example contains a trailing blank line, so that a group of commands is sent as one dynamic update request to the primary name server for <code>example.com</code>. </p>
<pre>
# nsupdate
&gt; update delete oldhost.example.com A
&gt; update add newhost.example.com 86400 A 172.16.1.1
&gt; send
</pre>
<p> Any A records for <code>oldhost.example.com</code> are deleted, and an A record for <code>newhost.example.com</code> with IP address 172.16.1.1 is added. The newly added record has a TTL of 1 day (86400 seconds). </p>
<pre>
# nsupdate
&gt; prereq nxdomain nickname.example.com
&gt; update add nickname.example.com 86400 CNAME somehost.example.com
&gt; send
</pre>
<p> The prerequisite condition tells the name server to verify that there are no resource records of any type for <code>nickname.example.com</code>. If there are, the update request fails. If this name does not exist, a CNAME for it is added. This ensures that when the CNAME is added, it cannot conflict with the long-standing rule in <i>RFC 1034</i> that a name must not exist as any other record type if it exists as a CNAME. (The rule has been updated for DNSSEC in <i>RFC 2535</i> to allow CNAMEs to have RRSIG, DNSKEY, and NSEC records.)</p>

<h2>BUGS</h2>
<p> The TSIG key is redundantly stored in two separate files. This is a consequence of <code>nsupdate</code> using the DST library for its cryptographic operations, and may change in future releases.</p>
