<h2 class="name">NAME</h2>
<p> nytprofhtml &#8211; Generate reports from Devel::NYTProf data </p>
<h2>SYNOPSIS</h2>
<p> Typical usage: </p>
<pre>
 $ perl -d:NYTProf some_perl_app.pl
 $ nytprofhtml --open
</pre>
<p> Options synopsis: </p>
<pre><code>
$ nytprofhtml[-h][-d][-m][-o&lt;output directory&gt;][-f&lt;input file&gt;][--open]
</code></pre>
<h2>DESCRIPTION</h2>
<p> Devel::NYTProf is a powerful feature-rich Perl source code profiler. See Devel::NYTProf for details. </p>
<p> <tt>&quot;nytprofhtml&quot;</tt> generates a set of html reports from a single data file generated by Devel::NYTProf. (If your process forks you&#8217;ll probably have multiple files. See Devel::NYTProf and nytprofmerge.) </p>
<p> The reports include dynamic runtime analysis wherein each line and each file is analyzed based on the performance of the other lines and files. As a result, you can quickly find the slowest module and the slowest line in a module. Slowness is measured in three ways: total calls, total time, and average time per call. </p>
<p> Coloring is based on absolute deviations from the median. See &lt;<a rel="nofollow" href="http://en.wikipedia.org/wiki/Median_absolute_deviation">http://en.wikipedia.org/wiki/Median_absolute_deviation</a>&gt; for more details. </p>
<p> That might sound complicated, but in reality you can just run the command and enjoy your report!</p>
<h2>COMMAND-LINE OPTIONS</h2>
<dl>
<dt>-f, &#8211;file &lt;filename&gt;</p>
<dd> Specifies the location of the file generated by Devel::NYTProf. Default: ./nytprof.out</p>
<dt>-o, &#8211;out &lt;dir&gt;</p>
<dd> The directory in which to place the generated report files. Default: ./nytprof/</p>
<dt>-d, &#8211;delete</p>
<dd> Purge any existing contents of the report output directory.</p>
<dt>-l, &#8211;lib &lt;dir&gt;</p>
<dd> Add a path to the beginning of <tt>@INC</tt> to help nytprofhtml find the source files used by the code. Should not be needed in practice.</p>
<dt>&#8211;open</p>
<dd> Make your web browser visit the report after it has been generated. </p>
<p> If this doesn&#8217;t work well for you, try installing the Browser::Open module.</p>
<dt>-m, &#8211;minimal</p>
<dd> Don&#8217;t generate graphviz .dot files or block/sub-level reports.</p>
<dt>&#8211;no-flame</p>
<dd> Disable generation of the flamegraph on the index page. Also disables calculation of distinct call stacks that are used to produce the flamegraph.</p>
<dt>-h, &#8211;help</p>
<dd> Print the help message.</dl>

<h2>DIAGNOSTICS</h2>
<h3>Unable to open &#8216;&#8230; (autosplit into &#8230;)&#8217;</h3>
<p> The profiled application executed code in a module that used AutoLoader to load the code from a separate .al file. NYTProf automatically recognises this situation and tries to determine the &#8216;parent&#8217; module file so it can associate the profile data with it. In order to do that the parent module file must already be &#8216;known&#8217; to NYTProf, typically by already having some code profiled. </p>
<p> You&#8217;re only likely to see this warning if you&#8217;re using the <tt>&quot;start&quot;</tt> option to start profiling after compile-time. The effect is that times spent in autoloaded subs won&#8217;t be associated with the parent module file and you won&#8217;t get annotated reports for them. </p>
<p> You can avoid this by using the default <tt>&quot;start=begin&quot;</tt> option, or by ensuring you execute some non-autoloaded code in the parent module, while the profiler is running, before an autoloaded sub is called.</p>
<h3>Background</h3>
<p> Subroutine-level profilers: </p>
<pre>
  Devel::DProf        | 1995-10-31 | ILYAZ
  Devel::AutoProfiler | 2002-04-07 | GSLONDON
  Devel::Profiler     | 2002-05-20 | SAMTREGAR
  Devel::Profile      | 2003-04-13 | JAW
  Devel::DProfLB      | 2006-05-11 | JAW
  Devel::WxProf       | 2008-04-14 | MKUTTER
</pre>
<p> Statement-level profilers: </p>
<pre>
  Devel::SmallProf    | 1997-07-30 | ASHTED
  Devel::FastProf     | 2005-09-20 | SALVA
  Devel::NYTProf      | 2008-03-04 | AKAPLAN
  Devel::Profit       | 2008-05-19 | LBROCARD
</pre>
<p> Devel::NYTProf is a (now distant) fork of Devel::FastProf, which was itself an evolution of Devel::SmallProf. </p>
<p> Adam Kaplan took Devel::FastProf and added html report generation (based on Devel::Cover) and a test suite &#8211; a tricky thing to do for a profiler. Meanwhile Tim Bunce had been extending Devel::FastProf to add novel per-sub and per-block timing, plus subroutine caller tracking. </p>
<p> When Devel::NYTProf was released Tim switched to working on Devel::NYTProf because the html report would be a good way to show the extra profile data, and the test suite made development much easier and safer. </p>
<p> Then he went a little crazy and added a slew of new features, in addition to per-sub and per-block timing and subroutine caller tracking. These included the &#8216;opcode interception&#8217; method of profiling, ultra-fast and robust inclusive subroutine timing, doubling performance, plus major changes to html reporting to display all the extra profile call and timing data in richly annotated and cross-linked reports. </p>
<p> Steve Peters came on board along the way with patches for portability and to keep NYTProf working with the latest development Perl versions. </p>
