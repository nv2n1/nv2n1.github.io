<h2 class="name">NAME</h2>
<p> llvm-ld &#8211; LLVM linker </p>
<h2>SYNOPSIS</h2>
<p> <code>llvm-ld</code> &lt;options&gt; &lt;files&gt;</p>
<h2>DESCRIPTION</h2>
<p> The <code>llvm-ld</code> tool takes a set of <font SIZE="-1">LLVM</font> bitcode files and links them together into a single <font SIZE="-1">LLVM</font> bitcode file. The output bitcode file can be another bitcode file or an executable bitcode program. Using additional options, <code>llvm-ld</code> is able to produce native code executables. </p>
<p> The <code>llvm-ld</code> tool is the main linker for <font SIZE="-1">LLVM</font>. It is used to link together the output of <font SIZE="-1">LLVM</font> front-end compilers and run &#8220;link time&#8221; optimizations (mostly the inter-procedural kind). </p>
<p> The <code>llvm-ld</code> tools attempts to mimic the interface provided by the default system linker so that it can act as a <i>drop-in</i> replacement.</p>
<h2>Search Order</h2>
<p> When looking for objects specified on the command line, <code>llvm-ld</code> will search for the object first in the current directory and then in the directory specified by the <font SIZE="-1"><code>LLVM_LIB_SEARCH_PATH</code></font> environment variable. If it cannot find the object, it fails. </p>
<p> When looking for a library specified with the <code>-l</code> option, <code>llvm-ld</code> first attempts to load a file with that name from the current directory. If that fails, it looks for lib<i>library</i>.bc, lib<i>library</i>.a, or lib<i>library</i>.<i>shared library extension</i>, in that order, in each directory added to the library search path with the <code>-L</code> option. These directories are searched in the order they are specified. If the library cannot be located, then <code>llvm-ld</code> looks in the directory specified by the <font SIZE="-1"><code>LLVM_LIB_SEARCH_PATH</code></font> environment variable. If it does not find a library there, it fails. </p>
<p> The <i>shared library extension</i> may be <i>.so</i>, <i>.dyld</i>, <i>.dll</i>, or something different, depending upon the system. </p>
<p> The <code>-L</code> option is global. It does not matter where it is specified in the list of command line arguments; the directory is simply added to the search path and is applied to all libraries, preceding or succeeding, in the command line.</p>
<h2>Link order</h2>
<p> All object and bitcode files are linked first in the order they were specified on the command line. All library files are linked next. Some libraries may not be linked into the object program; see below.</p>
<h2>Library Linkage</h2>
<p> Object files and static bitcode objects are always linked into the output file. Library archives (.a files) load only the objects within the archive that define symbols needed by the output file. Hence, libraries should be listed after the object files and libraries which need them; otherwise, the library may not be linked in, and the dependent library will not have its undefined symbols defined.</p>
<h2>Native code generation</h2>
<p> The <code>llvm-ld</code> program has limited support for native code generation, when using the <code>-native</code> or <code>-native-cbe</code> options. Native code generation is performed by converting the linked bitcode into native assembly (.s) or C code and running the system compiler (typically gcc) on the result.</p>
<h2>OPTIONS</h2>
<h2>General Options</h2>
<dl>
<dt><code>-help</code></p>
<dd> Print a summary of command line options.</p>
<dt><code>-v</code></p>
<dd> Specifies verbose mode. In this mode the linker will print additional information about the actions it takes, programs it executes, etc.</p>
<dt><code>-stats</code></p>
<dd> Print statistics.</p>
<dt><code>-time-passes</code></p>
<dd> Record the amount of time needed for each pass and print it to standard error.</dl>
<h2>Input/Output Options</h2>
<dl>
<dt><code>-o</code> <i>filename</i></p>
<dd> This overrides the default output file and specifies the name of the file that should be generated by the linker. By default, <code>llvm-ld</code> generates a file named <i>a.out</i> for compatibility with <code>ld</code>. The output will be written to <i>filename</i>.</p>
<dt><code>-b</code> <i>filename</i></p>
<dd> This option can be used to override the output bitcode file name. By default, the name of the bitcode output file is one more &#8220;.bc&#8221; suffix added to the name specified by <code>-o filename</code> option.</p>
<dt><code>-l</code><i>name</i></p>
<dd> This option specifies the <i>name</i> of a library to search when resolving symbols for the program. Only the base name should be specified as <i>name</i>, without a <i>lib</i> prefix or any suffix.</p>
<dt><code>-L</code><i>Path</i></p>
<dd> This option tells <code>llvm-ld</code> to look in <i>Path</i> to find any library subsequently specified with the <code>-l</code> option. The paths will be searched in the order in which they are specified on the command line. If the library is still not found, a small set of system specific directories will also be searched. Note that libraries specified with the <code>-l</code> option that occur <i>before</i> any <code>-L</code> options will not search the paths given by the <code>-L</code> options following it.</p>
<dt><code>-link-as-library</code></p>
<dd> Link the bitcode files together as a library, not an executable. In this mode, undefined symbols will be permitted.</p>
<dt><code>-r</code></p>
<dd> An alias for -link-as-library.</p>
<dt><code>-native</code></p>
<dd> Generate a native machine code executable. </p>
<p> When generating native executables, <code>llvm-ld</code> first checks for a bitcode version of the library and links it in, if necessary. If the library is missing, <code>llvm-ld</code> skips it. Then, <code>llvm-ld</code> links in the same libraries as native code. </p>
<p> In this way, <code>llvm-ld</code> should be able to link in optimized bitcode subsets of common libraries and then link in any part of the library that hasn&#8217;t been converted to bitcode.</p>
<dt><code>-native-cbe</code></p>
<dd> Generate a native machine code executable with the <font SIZE="-1">LLVM</font> C backend. </p>
<p> This option is identical to the <code>-native</code> option, but uses the C backend to generate code for the program instead of an <font SIZE="-1">LLVM</font> native code generator.</dl>
<h2>Optimization Options</h2>
<dl>
<dt><code>-disable-inlining</code></p>
<dd> Do not run the inlining pass. Functions will not be inlined into other functions.</p>
<dt><code>-disable-opt</code></p>
<dd> Completely disable optimization.</p>
<dt><code>-disable-internalize</code></p>
<dd> Do not mark all symbols as internal.</p>
<dt><code>-verify-each</code></p>
<dd> Run the verification pass after each of the passes to verify intermediate results.</p>
<dt><code>-strip-all</code></p>
<dd> Strip all debug and symbol information from the executable to make it smaller.</p>
<dt><code>-strip-debug</code></p>
<dd> Strip all debug information from the executable to make it smaller.</p>
<dt><code>-s</code></p>
<dd> An alias for <code>-strip-all</code>.</p>
<dt><code>-S</code></p>
<dd> An alias for <code>-strip-debug</code>.</p>
<dt><code>-export-dynamic</code></p>
<dd> An alias for <code>-disable-internalize</code></p>
<dt><code>-post-link-opt</code><i>Path</i></p>
<dd> Run post-link optimization program. After linking is completed a bitcode file will be generated. It will be passed to the program specified by <i>Path</i> as the first argument. The second argument to the program will be the name of a temporary file into which the program should place its optimized output. For example, the &#8220;no-op optimization&#8221; would be a simple shell script: </p>
<pre>
    #!/bin/bash
    cp $1 $2
</pre>
</dl>
<h2>EXIT STATUS</h2>
<p> If <code>llvm-ld</code> succeeds, it will exit with 0 return code. If an error occurs, it will exit with a non-zero return code.</p>
<h2>ENVIRONMENT</h2>
<p> The <tt>&quot;LLVM_LIB_SEARCH_PATH&quot;</tt> environment variable is used to find bitcode libraries. Any paths specified in this variable will be searched after the <tt>&quot;-L&quot;</tt> options.</p>
