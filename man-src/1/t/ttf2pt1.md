<h2 class="name">NAME</h2>
<p> TTF2PT1 &#8211; A True Type to PostScript Type 1 Font Converter </p>
<h2>SYNOPSIS</h2>
<p> <tt>&quot;ttf2pt1 </tt>[-options] ttffont.ttf [Fontname]<tt>&quot;</tt> </p>
<p> or </p>
<p> <tt>&quot;ttf2pt1 </tt>[-options] ttffont.ttf &#8211;<tt>&quot;</tt></p>
<h2>DESCRIPTION</h2>
<p> Ttf2pt1 is a font converter from the True Type format (and some other formats supported by the FreeType library as well) to the Adobe Type1 format. </p>
<p> The versions 3.0 and later got rather extensive post-processing algorithm that brings the converted fonts to the requirements of the Type1 standard, tries to correct the rounding errors introduced during conversions and some simple kinds of bugs that are typical for the public domain <font SIZE="-1">TTF</font> fonts. It also generates the hints that enable much better rendering of fonts in small sizes that are typical for the computer displays. But everything has its price, and some of the optimizations may not work well for certain fonts. That&#8217;s why the options were added to the converter, to control the performed optimizations.</p>
<h2>OPTIONS</h2>
<p> The first variant creates the file <tt>&quot;Fontname.pfa&quot;</tt> (or <tt>&quot;Fontname.pfb&quot;</tt> if the option &#8216;<code>-b</code>&#8216; was used) with the converted font and <tt>&quot;Fontname.afm&quot;</tt> with the font metrics, the second one prints the font or another file (if the option &#8216;<code>-G</code>&#8216; was used) on the standard output from where it can be immediately piped through some filter. If no <tt>&quot;Fontname&quot;</tt> is specified for the first variant, the name is generated from <tt>&quot;ttffont&quot;</tt> by replacing the <tt>&quot;.ttf&quot;</tt> filename suffix. </p>
<p> Most of the time no options are neccessary (with a possible exception of &#8216;<code>-e</code>&#8216;). But if there are some troubles with the resulting font, they may be used to control the conversion. The <code>options</code> are:</p>
<dl>
<dt>&bull;</p>
<dd> <tt>&quot;</tt>-a<tt>&quot;</tt> &#8211; Include all the glyphs from the source file into the converted file. If this option is not specified then only the glyphs that have been assigned some encoding are included, because the rest of glyphs would be inaccessible anyway and would only consume the disk space. But some applications are clever enough to change the encoding on the fly and thus use the other glyphs, in this case they could benefit from using this option. But there is a catch: the X11 library has rather low limit for the font size. Including more glyphs increases the file size and thus increases the chance of hitting this limit.</p>
<dt>&bull;</p>
<dd> <tt>&quot;</tt>-b<tt>&quot;</tt> &#8211; Encode the resulting font to produce a ready <tt>&quot;.pfb&quot;</tt> file.</p>
<dt>&bull;</p>
<dd> <tt>&quot;</tt>-d suboptions<tt>&quot;</tt> &#8211; Debugging options. The suboptions are: </p>
<p> <tt>&quot;</tt>a<tt>&quot;</tt> &#8211; Print out the absolute coordinates of dots in outlines. Such a font can not be used by any program (that&#8217;s why this option is incompatible with &#8216;<code>-e</code>&#8216;) but it has proven to be a valuable debuging information. </p>
<p> <tt>&quot;</tt>r<tt>&quot;</tt> &#8211; Do not reverse the direction of outlines. The <font SIZE="-1">TTF</font> fonts have the standard direction of outlines opposite to the Type1 fonts. So they should be reversed during proper conversion. This option may be used for debugging or to handle a <font SIZE="-1">TTF</font> font with wrong direction of outlines (possibly, converted in a broken way from a Type1 font). The first signs of the wrong direction are the letters like &#8220;P&#8221; or &#8220;B&#8221; without the unpainted &#8220;holes&#8221; inside.</p>
<dt>&bull;</p>
<dd> <tt>&quot;</tt>-e<tt>&quot;</tt> &#8211; Assemble the resulting font to produce a ready <tt>&quot;.pfa&quot;</tt> file. </p>
<p> [ S.B.: Personally I don&#8217;t think that this option is particularly useful. The same result may be achieved by piping the unassembled data through t1asm, the Type 1 assembler. And, anyways, it&#8217;s good to have the t1utils package handy. But Mark and many users think that this functionality is good and it took not much time to add this option. ]</p>
<dt>&bull;</p>
<dd> <tt>&quot;</tt>-F<tt>&quot;</tt> &#8211; Force the Unicode encoding: any type of <font SIZE="-1">MS</font> encoding specified in the font is ignored and the font is treated like it has Unicode encoding. <font SIZE="-1"><code>WARNING:</code></font> this option is intended for buggy fonts which actually are in Unicode but are marked as something else. The effect on the other fonts is unpredictable.</p>
<dt>&bull;</p>
<dd> <tt>&quot;</tt>-G suboptions<tt>&quot;</tt> &#8211; File generation options. The suboptions may be lowercase or uppercase, the lowercase ones disable the generation of particular files, the corresponding uppercase suboptions enable the generation of the same kind of files. If the result of ttf2pt1 is requested to be printed on the standard output, the last enabling suboption of <code>-G</code> determines which file will be written to the standard output and the rest of files will be discarded. For example, <code>-G A</code> will request the <font SIZE="-1">AFM</font> file. The suboptions to disable/enable the generation of the files are: </p>
<p> <tt>&quot;</tt>f/F<tt>&quot;</tt> &#8211; The font file. Depending on the other options this file will have one of the suffixes <tt>&quot;.t1a&quot;</tt>, <tt>&quot;.pfa&quot;</tt> or <tt>&quot;.pfb&quot;</tt>. If the conversion result is requested on the standard output (&#8216;<tt>&quot;-&quot;</tt>&#8216; is used as the output file name) then the font file will also be written there by default, if not overwritten by another suboption of <code>-G</code>. <code>Default: enabled</code> </p>
<p> <tt>&quot;</tt>a/A<tt>&quot;</tt> &#8211; The Adobe font metrics file (<tt>&quot;.afm&quot;</tt>). <code>Default: enabled</code> </p>
<p> <tt>&quot;</tt>e/E<tt>&quot;</tt> &#8211; The dvips encoding file (<tt>&quot;.enc&quot;</tt>). <code>Default: disabled</code></p>
<dt>&bull;</p>
<dd> <tt>&quot;</tt>-l language[+argument]<tt>&quot;</tt> &#8211; Extract the fonts for the specified language from a multi-language Unicode font. If this option is not used the converter tries to guess the language by the values of the shell variable <font SIZE="-1">LANG.</font> If it is not able to guess the language by <font SIZE="-1">LANG</font> it tries all the languages in the order they are listed. </p>
<p> After the plus sign an optional argument for the language extractor may be specified. The format of the argument is absolutely up to the particular language converter. The primary purpose of the argument is to support selection of planes for the multi-plane Eastern encodings but it can also be used in any other way. The language extractor may decide to add the plane name in some form to the name of the resulting font. None of the currently supported languages make any use of the argument yet. </p>
<p> As of now the following languages are supported: </p>
<p> &nbsp;<wbr>&nbsp;<wbr><tt>&quot;latin1&quot;</tt> &#8211; for all the languages using the Latin-1 encoding </p>
<p> &nbsp;<wbr>&nbsp;<wbr><tt>&quot;latin2&quot;</tt> &#8211; for the Central European languages </p>
<p> &nbsp;<wbr>&nbsp;<wbr><tt>&quot;latin4&quot;</tt> &#8211; for the Baltic languages </p>
<p> &nbsp;<wbr>&nbsp;<wbr><tt>&quot;latin5&quot;</tt> &#8211; for the Turkish language </p>
<p> &nbsp;<wbr>&nbsp;<wbr><tt>&quot;cyrillic&quot;</tt> &#8211; for the languages with Cyrillic alphabet </p>
<p> &nbsp;<wbr>&nbsp;<wbr><tt>&quot;russian&quot;</tt> &#8211; historic synonym for cyrillic </p>
<p> &nbsp;<wbr>&nbsp;<wbr><tt>&quot;bulgarian&quot;</tt> &#8211; historic synonym for cyrillic </p>
<p> &nbsp;<wbr>&nbsp;<wbr><tt>&quot;adobestd&quot;</tt> &#8211; for the AdobeStandard encoding used by TeX </p>
<p> &nbsp;<wbr>&nbsp;<wbr><tt>&quot;plane+</tt>argument<tt>&quot;</tt> &#8211; to select one plane from a multi-byte encoding </p>
<p> The argument of the &quot;<tt>&quot;plane&quot;</tt>&quot; language may be in one of three forms: </p>
<p> &nbsp;<wbr>&nbsp;<wbr><tt>&quot;plane+</tt>pid=<tt></tt>&lt;pid&gt;<tt></tt>,eid=<tt></tt>&lt;eid&gt;<tt>&quot;</tt> </p>
<p> &nbsp;<wbr>&nbsp;<wbr><tt>&quot;plane+</tt>pid=<tt></tt>&lt;pid&gt;<tt></tt>,eid=<tt></tt>&lt;eid&gt;<tt></tt>,<tt></tt>&lt;plane_number&gt;<tt>&quot;</tt> </p>
<p> &nbsp;<wbr>&nbsp;<wbr><tt>&quot;plane+</tt>&lt;plane_number&gt;<tt>&quot;</tt> </p>
<p> Pid (<font SIZE="-1">TTF</font> platform id) and eid (<font SIZE="-1">TTF</font> encoding id) select a particular <font SIZE="-1">TTF</font> encoding table in the original font. They are specified as decimal numbers. If this particular encoding table is not present in the font file then the conversion fails. The native (&#8220;ttf&#8221;) front-end parser supports only pid=3 (Windows platform), the FreeType-based (&#8220;ft&#8221;) front-end supports any platform. If pid/eid is not specified then the <font SIZE="-1">TTF</font> encoding table is determined as usual: Unicode encoding if it&#8217;s first or an 8-bit encoding if not (and for an 8-bit encoding the plane number is silently ignored). To prevent the converter from falling back to an 8-bit encoding, specify the Unicode pid/eid value explicitly. </p>
<p> Plane_number is a hexadecimal (if starts with &quot;<code>0x</code>&#8220;) or decimal number. It gives the values of upper bytes for which 256 characters will be selected. If not specified, defaults to 0. It is also used as a font name suffix (the leading &#8221;0x&quot; is not included into the suffix). </p>
<p> <font SIZE="-1"><code>NOTE:</code></font> You may notice that the language names are not uniform: some are the names of particular languages and some are names of encodings. This is because of the different approaches. The original idea was to implement a conversion from Unicode to the appropriate Windows encoding for a given language. And then use the translation tables to generate the fonts in whatever final encodings are needed. This would allow to pile together the Unicode fonts and the non-Unicode Windows fonts for that language and let the program to sort them out automatically. And then generate fonts in all the possible encodings for that language. An example of this approach is the Russian language support. But if there is no multiplicity of encodings used for some languages and if the non-Unicode fonts are not considered important by the users, another way would be simpler to implement: just provide only one table for extraction of the target encoding from Unicode and don&#8217;t bother with the translation tables. The latin* &#8220;languages&#8221; are examples of this approach. If somebody feels that he needs the Type1 fonts both in Latin-* and Windows encodings he or she is absolutely welcome to submit the code to implement it. </p>
<p> <font SIZE="-1"><code>WARNING:</code></font> Some of the glyphs included into the AdobeStandard encoding are not included into the Unicode standard. The most typical examples of such glyphs are ligatures like &#8216;fi&#8217;, &#8216;fl&#8217; etc. Because of this the font designers may place them at various places. The converter tries to do its best, if the glyphs have honest Adobe names and/or are placed at the same codes as in the Microsoft fonts they will be picked up. Otherwise a possible solution is to use the option &#8216;<code>-L</code>&#8216; with an external map.</p>
<dt>&bull;</p>
<dd> <tt>&quot;</tt>-L file[+[pid=&lt;pid&gt;,eid=&lt;eid&gt;,][plane]]<tt>&quot;</tt> &#8211; Extract the fonts for the specified language from a multi-language font using the map from this file. This is rather like the option &#8216;<code>-l</code>&#8216; but the encoding map is not compiled into the program, it&#8217;s taken from that file, so it&#8217;s easy to edit. Examples of such files are provided in <tt>&quot;maps/adobe-standard-encoding.map&quot;</tt>, <tt>&quot;CP1250.map&quot;</tt>. (<font SIZE="-1"><code>NOTE:</code></font> the &#8216;standard encoding&#8217; map does not include all the glyphs of the AdobeStandard encoding, it&#8217;s provided only as an example.) The description of the supported map formats is in the file <tt>&quot;maps/unicode-sample.map&quot;</tt>. </p>
<p> Likewise to &#8216;<code>-l</code>&#8216;, an argument may be specified after the map file name. But in this case the argument has fixed meaning: it selects the original <font SIZE="-1">TTF</font> encoding table (the syntax is the same as in &#8216;<code>-l plane</code>&#8216;) and/or a plane of the map file. The plane name also gets added after dash to the font name. The plane is a concept used in the Eastern fonts with big number of glyphs: one <font SIZE="-1">TTF</font> font gets divided into multiple Type1 fonts, each containing one plane of up to 256 glyphs. But with a little creativity this concept may be used for other purposes of combining multiple translation maps into one file. To extract multiple planes from a <font SIZE="-1">TTF</font> font <tt>&quot;ttf2pt1&quot;</tt> must be run multiple times, each time with a different plane name specified. </p>
<p> The default original <font SIZE="-1">TTF</font> encoding table used for the option &#8216;<code>-L</code>&#8216; is Unicode. The map files may include directives to specify different original <font SIZE="-1">TTF</font> encodings. However if the pid/eid pair is specified with it overrides any original encoding specified in the map file.</p>
<dt>&bull;</p>
<dd> <tt>&quot;</tt>-m type=value<tt>&quot;</tt> &#8211; Set maximal or minimal limits of resources. These limits control the the font generation by limiting the resources that the font is permitted to require from the PostScript interpreter. The currently supported types of limits are: </p>
<p> <tt>&quot;</tt>h<tt>&quot;</tt> &#8211; the maximal hint stack depth for the substituted hints. The default value is 128, according to the limitation in X11. This seems to be the lowest (and thus the safest) widespread value. To display the hint stack depth required by each glyph in a <tt>&quot;.t1a&quot;</tt> file use the script <tt>&quot;ttf2pt1_cntstems&quot;</tt>.</p>
<dt>&bull;</p>
<dd> <tt>&quot;</tt>-O suboptions<tt>&quot;</tt> &#8211; Outline processing options. The suboptions may be lowercase or uppercase, the lowercase ones disable the features, the corresponding uppercase suboptions enable the same features. The suboptions to disable/enable features are: </p>
<p> <tt>&quot;</tt>b/B<tt>&quot;</tt> &#8211; Guessing of the ForceBold parameter. This parameter helps the Type1 engine to rasterize the bold fonts properly at small sizes. But the algorithm used to guess the proper value of this flag makes that guess based solely on the font name. In rare cases that may cause errors, in these cases you may want to disable this guessing. <code>Default: enabled</code> </p>
<p> <tt>&quot;</tt>h/H<tt>&quot;</tt> &#8211; Autogeneration of hints. The really complex outlines may confuse the algorithm, so theoretically it may be useful sometimes to disable them. Although up to now it seems that even bad hints are better than no hints at all. <code>Default: enabled</code> </p>
<p> <tt>&quot;</tt>u/U<tt>&quot;</tt> &#8211; Hint substitution. Hint substitution is a technique permitting generation of more detailed hints for the rasterizer. It allows to use different sets of hints for different parts of a glyph and change these sets as neccessary during rasterization (that&#8217;s why &#8220;substituted&#8221;). So it should improve the quality of the fonts rendered at small sizes. But there are two catches: First, the X11 library has rather low limit for the font size. More detailed hints increase the file size and thus increase the chance of hitting this limit (that does not mean that you shall hit it but you may if your fonts are particularly big). This is especially probable for Unicode fonts converted with option &#8216;<code>-a</code>&#8216;, so you may want to use &#8216;<code>-a</code>&#8216; together with &#8216;<code>-Ou</code>&#8216;. Second, some rasterizers (again, X11 is the typical example) have a limitation for total number of hints used when drawing a glyph (also known as the hint stack depth). If that stack overflows the glyph is ignored. Starting from version 3.22 <tt>&quot;ttf2pt1&quot;</tt> uses algorithms to minimizing this depth, with the trade-off of slightly bigger font files. The glyphs which still exceed the limit set by option &#8216;<code>-mh</code>&#8216; have all the substituted hints removed and only base hints left. The algorithms seem to have been refined far enough to make the fonts with substituted hints look better than the fonts without them or at least the same. Still if the original fonts are not well-designed the detailed hinting may emphasize the defects of the design, such as non-even thickness of lines. So provided that you are not afraid of the X11 bug the best idea would be to generate a font with this feature and without it, then compare the results using the program <tt>&quot;ttf2pt1_cmpf&quot;</tt> (see the description in <tt>&quot;other/README&quot;</tt>) and decide which one looks better. <code>Default: enabled</code> </p>
<p> <tt>&quot;</tt>o/O<tt>&quot;</tt> &#8211; Space optimization of the outlines&#8217; code. This kind of optimization never hurts, and the only reason to disable this feature is for comparison of the generated fonts with the fonts generated by the previous versions of converter. Well, it _almost_ never hurts. As it turned out there exist some brain-damaged printers which don&#8217;t understand it. Actually this feature does not change the outlines at all. The Type 1 font manual provides a set of redundant operators that make font description shorter, such as &#8217;10 hlineto&#8217; instead of &#8216;0 10 rlineto&#8217; to describe a horizontal line. This feature enables use of these operators. <code>Default: enabled</code> </p>
<p> <tt>&quot;</tt>s/S<tt>&quot;</tt> &#8211; Smoothing of outlines. If the font is broken in some way (even the ones that are not easily noticeable), such smoothing may break it further. So disabling this feature is the first thing to be tried if some font looks odd. But with smoothing off the hint generation algorithms may not work properly too. <code>Default: enabled</code> </p>
<p> <tt>&quot;</tt>t/T<tt>&quot;</tt> &#8211; Auto-scaling to the 1000&#215;1000 Type1 standard matrix. The <font SIZE="-1">TTF</font> fonts are described in terms of an arbitrary matrix up to 4000&#215;4000. The converted fonts must be scaled to conform to the Type1 standard. But the scaling introduces additional rounding errors, so it may be curious sometimes to look at the font in its original scale. <code>Default: enabled</code> </p>
<p> <tt>&quot;</tt>v/V<tt>&quot;</tt> &#8211; Do vectorization on the bitmap fonts. Functionally &#8220;vectorization&#8221; is the same thing as &#8220;autotracing&#8221;, a different word is used purely to differentiate it from the Autotrace library. It tries to produce nice smooth outlines from bitmaps. This feature is still a work in progress though the results are already mostly decent. <code>Default: disabled</code> </p>
<p> <tt>&quot;</tt>w/W<tt>&quot;</tt> &#8211; Glyphs&#8217; width corection. This option is designed to be used on broken fonts which specify too narrow widths for the letters. You can tell that a font can benefit from this option if you see that the characters are smashed together without any whitespace between them. This option causes the converter to set the character widths to the actual width of this character plus the width of a typical vertical stem. But on the other hand the well-designed fonts may have characters that look better if their widths are set slightly narrower. Such well-designed fonts will benefit from disabling this feature. You may want to convert a font with and without this feature, compare the results and select the better one. This feature may be used only on proportional fonts, it has no effect on the fixed-width fonts. <code>Default: disabled</code> </p>
<p> <tt>&quot;</tt>z/Z<tt>&quot;</tt> &#8211; Use the Autotrace library on the bitmap fonts. The results are horrible and <code>the use of this option is not recommended</code>. This option is present for experimental purposes. It may change or be removed in the future. The working tracing can be achieved with option <tt>&quot;</tt>-OV<tt>&quot;</tt>. <code>Default: disabled</code></p>
<dt>&bull;</p>
<dd> <tt>&quot;</tt>-p parser_name<tt>&quot;</tt> &#8211; Use the specified front-end parser to read the font file. If this option is not used, ttf2pt1 selects the parser automatically based on the suffix of the font file name, it uses the first parser in its list that supports this font type. Now two parsers are supported: </p>
<p> &nbsp;<wbr>&nbsp;<wbr><tt>&quot;ttf&quot;</tt> &#8211; built-in parser for the ttf files (suffix <tt>&quot;.ttf&quot;</tt>) </p>
<p> &nbsp;<wbr>&nbsp;<wbr><tt>&quot;bdf&quot;</tt> &#8211; built-in parser for the <font SIZE="-1">BDF</font> files (suffix <tt>&quot;.bdf&quot;</tt>) </p>
<p> &nbsp;<wbr>&nbsp;<wbr><tt>&quot;ft&quot;</tt> &#8211; parser based on the FreeType-2 library (suffixes <tt>&quot;.ttf&quot;</tt>, <tt>&quot;.otf&quot;</tt>, <tt>&quot;.pfa&quot;</tt>, <tt>&quot;.pfb&quot;</tt>) </p>
<p> The parser <tt>&quot;ft&quot;</tt> is <font SIZE="-1"><code>NOT</code></font> linked in by default. See <tt>&quot;Makefile&quot;</tt> for instructions how to enable it. We do no support this parser on Windows: probably it will work but nobody tried and nobody knows how to build it. </p>
<p> The conversion of the bitmap fonts (such as <font SIZE="-1">BDF</font>) is simplistic yet, producing jagged outlines. When converting such fonts, it might be a good idea to turn off the hint substitution (using option <code>-Ou</code>) because the hints produced will be huge but not adding much to the quality of the fonts.</p>
<dt>&bull;</p>
<dd> <tt>&quot;</tt>-u number<tt>&quot;</tt> &#8211; Mark the font with this value as its UniqueID. The UniqueID is used by the printers with the hard disks to cache the rasterized characters and thus significantly speed-up the printing. Some of those printers just can&#8217;t store the fonts without UniqueID on their disk.The problem is that the <font SIZE="-1">ID</font> is supposed to be unique, as it name says. And there is no easy way to create a guaranteed unique <font SIZE="-1">ID.</font> Adobe specifies the range 4000000-4999999 for private IDs but still it&#8217;s difficult to guarantee the uniqueness within it. So if you don&#8217;t really need the UniqueID don&#8217;t use it, it&#8217;s optional. Luckily there are a few millions of possible IDs, so the chances of collision are rather low. If instead of the number a special value &#8216;<tt>&quot;</tt>A<tt>&quot;</tt>&#8216; is given then the converter generates the value of UniqueID automatically, as a hash of the font name. (<font SIZE="-1"><code>NOTE:</code></font> in the version 3.22 the algorithm for autogeneration of UniqueID was changed to fit the values into the Adobe-spacified range. This means that if UniqueIDs were used then the printer&#8217;s cache may need to be flushed before replacing the fonts converted by an old version with fonts converted by a newer version). A simple way to find if any of the fonts in a given directory have duplicated UniqueIDs is to use the command: </p>
<p> <tt>&quot;&nbsp;<wbr>&nbsp;<wbr>cat *.pf[ab] | grep UniqueID | sort | uniq -c | grep -v ' 1 '&quot;</tt> </p>
<p> Or if you use <tt>&quot;ttf2pt1_convert&quot;</tt> it will do that for you automatically plus it will also give the exact list of files with duplicate UIDs.</p>
<dt>&bull;</p>
<dd> <tt>&quot;</tt>-v size<tt>&quot;</tt> &#8211; Re-scale the font to get the size of a typical uppercase letter somewhere around the specified size. Actually, it re-scales the whole font to get the size of one language-dependent letter to be at least of the specified size. Now this letter is &#8220;A&#8221; in all the supported languages. The size is specified in the points of the Type 1 coordinate grids, the maximal value is 1000. This is an experimental option and should be used with caution. It tries to increase the visible font size for a given point size and thus make the font more readable. But if overused it may cause the fonts to look out of scale. As of now the interesting values of size for this option seem to be located mostly between 600 and 850. This re-scaling may be quite useful but needs more experience to understand the balance of its effects.</p>
<dt>&bull;</p>
<dd> <tt>&quot;</tt>-W level<tt>&quot;</tt> &#8211; Select the verbosity level of the warnings. Currently the levels from 0 to 4 are supported. Level 0 means no warnings at all, level 4 means all the possible warnings. The default level is 3. Other levels may be added in the future, so using the level number 99 is recommended to get all the possible warnings. Going below level 2 is not generally recommended because you may miss valuable information about the problems with the fonts being converted.</p>
<dt>&bull;</p>
<dd> <code>Obsolete option:</code> <tt>&quot;</tt>-A<tt>&quot;</tt> &#8211; Print the font metrics (.afm file) instead of the font on <font SIZE="-1">STDOUT.</font> Use <code>-GA</code> instead.</p>
<dt>&bull;</p>
<dd> <code>Very obsolete option:</code> </p>
<p> The algorithm that implemented the forced fixed width had major flaws, so it was disabled. The code is still in the program and some day it will be refined and returned back. Meanwhile the option name &#8216;<code>-f</code>&#8216; was reused for another option. The old version was: </p>
<p> <tt>&quot;</tt>-f<tt>&quot;</tt> &#8211; Don&#8217;t try to force the fixed width of font. Normally the converter considers the fonts in which the glyph width deviates by not more than 5% as buggy fixed width fonts and forces them to have really fixed width. If this is undesirable, it can be disabled by this option.</dl>
<p> The <tt>&quot;.pfa&quot;</tt> font format supposes that the description of the characters is binary encoded and encrypted. This converter does not encode or encrypt the data by default, you have to specify the option &#8216;<code>-e</code>&#8216; or use the <tt>&quot;t1asm&quot;</tt> program to assemble (that means, encode and encrypt) the font program. The <tt>&quot;t1asm&quot;</tt> program that is included with the converter is actually a part of the <tt>&quot;t1utils&quot;</tt> package, rather old version of which may be obtained from </p>
<p> <a rel="nofollow" href="http://ttf2pt1.sourceforge.net/t1utils.tar.gz">http://ttf2pt1.sourceforge.net/t1utils.tar.gz</a> </p>
<p> Note that <tt>&quot;t1asm&quot;</tt> from the old version of that package won&#8217;t work properly with the files generated by <tt>&quot;ttf2pt1&quot;</tt> version 3.20 and later. Please use <tt>&quot;t1asm&quot;</tt> packaged with <tt>&quot;ttf2pt1&quot;</tt> or from the new version <tt>&quot;t1utils&quot;</tt> instead. For a newer version of <tt>&quot;t1utils&quot;</tt> please look at </p>
<p> <a rel="nofollow" href="http://www.lcdf.org/~eddietwo/type/">http://www.lcdf.org/~eddietwo/type/</a></p>
<h2>EXAMPLES</h2>
<p> So, the following command lines: </p>
<p> <tt>&quot;ttf2pt1 -e ttffont.ttf t1font&quot;</tt> </p>
<p> <tt>&quot;ttf2pt1 ttffont.ttf - | t1asm &gt;t1font.pfa&quot;</tt> </p>
<p> represent two ways to get a working font. The benefit of the second form is that other filters may be applied to the font between the converter and assembler.</p>

<h2>BUGS</h2>
<p> It seems that many Eastern fonts use features of the <font SIZE="-1">TTF</font> format that are not supported by the ttf2pt1&#8217;s built-in front-end parser. Because of this for now we recommend using the FreeType-based parser (option &#8216;<code>-p ft</code>&#8216;) with the &quot;<tt>&quot;plane&quot;</tt>&quot; language.</p>
<h3>Troubleshooting and bug reports</h3>
<p> Have problems with conversion of some font ? The converter dumps core ? Or your printer refuses to understand the converted fonts ? Or some characters are missing ? Or some characters look strange ? </p>
<p> Send the bug reports to the ttf2pt1 development mailing list at ttf2pt1-devel [at] lists.sourceforge.net. </p>
<p> Try to collect more information about the problem and include it into the bug report. (Of course, even better if you would provide a ready fix, but just a detailed bug report is also good). Provide detailed information about your problem, this will speed up the response greatly. Don&#8217;t just write &#8220;this font looks strange after conversion&#8221; but describe what&#8217;s exactly wrong with it: for example, what characters look wrong and what exactly is wrong about their look. Providing a link to the original font file would be also a good idea. Try to do a little troublehooting and report its result. This not only would help with the fix but may also give you a temporary work-around for the bug. </p>
<p> First, enable full warnings with option &#8216;<code>-W99</code>&#8216;, save them to a file and read carefully. Sometimes the prolem is with a not implemented feature which is reported in the warnings. Still, reporting about such problems may be a good idea: some features were missed to cut corners, in hope that no real font is using them. So a report about a font using such a feature may motivate someone to implement it. Of course, you may be the most motivated person: after all, you are the one wishing to convert that font. ;-) Seriously, the philosophy &#8220;scrath your own itch&#8221; seems to be the strongest moving force behind the Open Source software. </p>
<p> The next step is playing with the options. This serves a dual purpose: on one hand, it helps to localize the bug, on the other hand you may be able to get a working version of the font for the meantime while the bug is being fixed. The typical options to try out are: first &#8216;<code>-Ou</code>&#8216;, if it does not help then &#8216;<code>-Os</code>&#8216;, then &#8216;<code>-Oh</code>&#8216;, then &#8216;<code>-Oo</code>&#8216;. They are described in a bit more detail above. Try them one by one and in combinations. See if with them the resulting fonts look better. </p>
<p> On some fonts ttf2pt1 just crashes. Commonly that happens because the font being converted is highly defective (although sometimes the bug is in ttf2pt1 itself). In any case it should not crash, so the reports about such cases will help to handle these defects properly in future. </p>
<p> We try to respond to the bug reports in a timely fashion but alas, this may not always be possible, especially if the problem is complex. This is a volunteer project and its resources are limited. Because of this we would appreciate bug reports as detailed as possible, and we would appreciate the ready fixes and contributions even more.</p>
