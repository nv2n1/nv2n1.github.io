<h2 class="name">NAME</h2>
<p> vncviewer &#8211; an X viewer client for VNC </p>
<h2>SYNOPSIS</h2>
<p> <code>vncviewer</code> [<i>options</i>] [<i>host</i>][<i>:display</i>]<br />
 <code>vncviewer</code> [<i>options</i>] [<i>host</i>][<i>::port</i>]<br />
 <code>vncviewer</code> [<i>options</i>] <i>-listen</i> [<i>display</i>]<br />
 <code>vncviewer</code> <i>-help</i> </p>
<h2>DESCRIPTION</h2>
<p> <code>vncviewer</code> is an Xt-based client application for the VNC (Virtual Network Computing) system. It can connect to any VNC-compatible server such as <code>Xvnc</code> or WinVNC, allowing you to control desktop environment of a different machine. </p>
<p> You can use F8 to display a pop-up utility menu. Press F8 twice to pass single F8 to the remote side.</p>
<h2>OPTIONS</h2>
<dl>
<dt><code>-help</code></p>
<dd> Prints a short usage notice to stderr.</p>
<dt><code>-listen</code></p>
<dd> Make the viewer listen on port 5500+<i>display</i> for reverse connections from a server. WinVNC supports reverse connections using the &quot;Add New Client&quot; menu option, or the -connect command line option. <code>Xvnc</code> requires the use of the helper program <code>vncconnect</code>.</p>
<dt><code>-via</code> <i>gateway</i></p>
<dd> Automatically create encrypted TCP tunnel to the <i>gateway</i> machine before connection, connect to the <i>host</i> through that tunnel (TightVNC-specific). By default, this option invokes SSH local port forwarding, assuming that SSH client binary can be accessed as /usr/bin/ssh. Note that when using the <code>-via</code> option, the host machine name should be specified as known to the gateway machine, e.g. &quot;localhost&quot; denotes the <i>gateway</i>, not the machine where vncviewer was launched. See the ENVIRONMENT section below for the information on configuring the <code>-via</code> option.</p>
<dt><code>-shared</code></p>
<dd> When connecting, specify that a shared connection is requested. In TightVNC, this is the default mode, allowing you to share the desktop with other clients already using it.</p>
<dt><code>-noshared</code></p>
<dd> When connecting, specify that the session may not be shared. This would either disconnect other connected clients or refuse your connection, depending on the server configuration.</p>
<dt><code>-viewonly</code></p>
<dd> Disable transfer of mouse and keyboard events from the client to the server.</p>
<dt><code>-fullscreen</code></p>
<dd> Start in full-screen mode. Please be aware that operating in full-screen mode may confuse X window managers. Typically, such conflicts cause incorrect handling of input focus or make the viewer window disappear mysteriously. See the grabKeyboard setting in the RESOURCES section below for a method to solve input focus problem.</p>
<dt><code>-noraiseonbeep</code></p>
<dd> By default, the viewer shows and raises its window on remote beep (bell) event. This option disables such behaviour (TightVNC-specific).</p>
<dt><code>-user</code> <i>username</i></p>
<dd> User name for Unix login authentication. Default is to use current Unix user name. If this option was given, the viewer will prefer Unix login authentication over the standard VNC authentication.</p>
<dt><code>-passwd</code> <i>passwd-file</i></p>
<dd> File from which to get the password (as generated by the <code><a href="/docs/linux/man/1-vncpasswd/">vncpasswd</a></code>(1) program). This option affects only the standard VNC authentication.</p>
<dt><code>-encodings</code> <i>encoding-list</i></p>
<dd> TightVNC supports several different compression methods to encode screen updates; this option specifies a set of them to use in order of preference. Encodings are specified separated with spaces, and must thus be enclosed in quotes if more than one is specified. Available encodings, in default order for a remote connection, are &quot;copyrect tight hextile zlib corre rre raw&quot;. For a local connection (to the same machine), the default order to try is &quot;raw copyrect tight hextile zlib corre rre&quot;. Raw encoding is always assumed as a last option if no other encoding can be used for some reason. For more information on encodings, see the section ENCODINGS below.</p>
<dt><code>-bgr233</code></p>
<dd> Always use the BGR233 format to encode pixel data. This reduces network traffic, but colors may be represented inaccurately. The bgr233 format is an 8-bit &quot;true color&quot; format, with 2 bits blue, 3 bits green, and 3 bits red.</p>
<dt><code>-owncmap</code></p>
<dd> Try to use a PseudoColor visual and a private colormap. This allows the VNC server to control the colormap.</p>
<dt><code>-truecolour</code>, <code>-truecolor</code></p>
<dd> Try to use a TrueColor visual.</p>
<dt><code>-depth</code> <i>depth</i></p>
<dd> On an X server which supports multiple TrueColor visuals of different depths, attempt to use the specified one (in bits per pixel); if successful, this depth will be requested from the VNC server.</p>
<dt><code>-compresslevel </code><i>level</i></p>
<dd> Use specified compression <i>level</i> (0..9) for &quot;tight&quot; and &quot;zlib&quot; encodings (TightVNC-specific). Level 1 uses minimum of CPU time and achieves weak compression ratios, while level 9 offers best compression but is slow in terms of CPU time consumption on the server side. Use high levels with very slow network connections, and low levels when working over high-speed LANs. It&#8217;s not recommended to use compression level 0, reasonable choices start from the level 1.</p>
<dt><code>-quality </code><i>level</i></p>
<dd> Use the specified JPEG quality <i>level</i> (0..9) for the &quot;tight&quot; encoding (TightVNC-specific). Quality level 0 denotes bad image quality but very impressive compression ratios, while level 9 offers very good image quality at lower compression ratios. Note that the &quot;tight&quot; encoder uses JPEG to encode only those screen areas that look suitable for lossy compression, so quality level 0 does not always mean unacceptable image quality.</p>
<dt><code>-nojpeg</code></p>
<dd> Disable lossy JPEG compression in Tight encoding (TightVNC-specific). Disabling JPEG compression is not a good idea in typical cases, as that makes the Tight encoder less efficient. You might want to use this option if it&#8217;s absolutely necessary to achieve perfect image quality (see also the <code>-quality</code> option).</p>
<dt><code>-nocursorshape</code></p>
<dd> Disable cursor shape updates, protocol extensions used to handle remote cursor movements locally on the client side (TightVNC-specific). Using cursor shape updates decreases delays with remote cursor movements, and can improve bandwidth usage dramatically.</p>
<dt><code>-x11cursor</code></p>
<dd> Use a real X11 cursor with X-style cursor shape updates, instead of drawing the remote cursor on the framebuffer. This option also disables the dot cursor, and disables cursor position updates in non-fullscreen mode.</p>
<dt><code>-autopass</code></p>
<dd> Read a plain-text password from stdin. This option affects only the standard VNC authentication.</dl>
<h2>ENCODINGS</h2>
<p> The server supplies information in whatever format is desired by the client, in order to make the client as easy as possible to implement. If the client represents itself as able to use multiple formats, the server will choose one. </p>
<p> <i>Pixel format</i> refers to the representation of an individual pixel. The most common formats are 24 and 16 bit &quot;true-color&quot; values, and 8-bit &quot;color map&quot; representations, where an arbitrary map converts the color number to RGB values. </p>
<p> <i>Encoding</i> refers to how a rectangle of pixels are sent (all pixel information in VNC is sent as rectangles). All rectangles come with a header giving the location and size of the rectangle and an encoding type used by the data which follows. These types are listed below.</p>
<dl>
<dt><code>Raw</code></p>
<dd> The raw encoding simply sends width*height pixel values. All clients are required to support this encoding type. Raw is also the fastest when the server and viewer are on the same machine, as the connection speed is essentially infinite and raw encoding minimizes processing time.</p>
<dt><code>CopyRect</code></p>
<dd> The Copy Rectangle encoding is efficient when something is being moved; the only data sent is the location of a rectangle from which data should be copied to the current location. Copyrect could also be used to efficiently transmit a repeated pattern.</p>
<dt><code>RRE</code></p>
<dd> The Rise-and-Run-length-Encoding is basically a 2D version of run-length encoding (RLE). In this encoding, a sequence of identical pixels are compressed to a single value and repeat count. In VNC, this is implemented with a background color, and then specifications of an arbitrary number of subrectangles and color for each. This is an efficient encoding for large blocks of constant color.</p>
<dt><code>CoRRE</code></p>
<dd> This is a minor variation on RRE, using a maximum of 255&#215;255 pixel rectangles. This allows for single-byte values to be used, reducing packet size. This is in general more efficient, because the savings from sending 1-byte values generally outweighs the losses from the (relatively rare) cases where very large regions are painted the same color.</p>
<dt><code>Hextile</code></p>
<dd> Here, rectangles are split up in to 16&#215;16 tiles, which are sent in a predetermined order. The data within the tiles is sent either raw or as a variant on RRE. Hextile encoding is usually the best choice for using in high-speed network environments (e.g. Ethernet local-area networks).</p>
<dt><code>Zlib</code></p>
<dd> Zlib is a very simple encoding that uses zlib library to compress raw pixel data. This encoding achieves good compression, but consumes a lot of CPU time. Support for this encoding is provided for compatibility with VNC servers that might not understand Tight encoding which is more efficient than Zlib in nearly all real-life situations.</p>
<dt><code>Tight</code></p>
<dd> Like Zlib encoding, Tight encoding uses zlib library to compress the pixel data, but it pre-processes data to maximize compression ratios, and to minimize CPU usage on compression. Also, JPEG compression may be used to encode color-rich screen areas (see the description of -quality and -nojpeg options above). Tight encoding is usually the best choice for low-bandwidth network environments (e.g. slow modem connections).</dl>
<h2>RESOURCES</h2>
<p> X resources that <code>vncviewer</code> knows about, aside from the normal Xt resources, are as follows:</p>
<dl>
<dt><code>shareDesktop</code></p>
<dd> Equivalent of <code>-shared</code>/<code>-noshared</code> options. Default true.</p>
<dt><code>viewOnly</code></p>
<dd> Equivalent of <code>-viewonly</code> option. Default false.</p>
<dt><code>fullScreen</code></p>
<dd> Equivalent of <code>-fullscreen</code> option. Default false.</p>
<dt><code>grabKeyboard</code></p>
<dd> Grab keyboard in full-screen mode. This can help to solve problems with losing keyboard focus. Default false.</p>
<dt><code>raiseOnBeep</code></p>
<dd> Equivalent of <code>-noraiseonbeep</code> option, when set to false. Default true.</p>
<dt><code>passwordFile</code></p>
<dd> Equivalent of <code>-passwd</code> option.</p>
<dt><code>userLogin</code></p>
<dd> Equivalent of <code>-user</code> option.</p>
<dt><code>passwordDialog</code></p>
<dd> Whether to use a dialog box to get the password (true) or get it from the tty (false). Irrelevant if <code>passwordFile</code> is set. Default false.</p>
<dt><code>encodings</code></p>
<dd> Equivalent of <code>-encodings</code> option.</p>
<dt><code>compressLevel</code></p>
<dd> Equivalent of <code>-compresslevel</code> option (TightVNC-specific).</p>
<dt><code>qualityLevel</code></p>
<dd> Equivalent of <code>-quality</code> option (TightVNC-specific).</p>
<dt><code>enableJPEG</code></p>
<dd> Equivalent of <code>-nojpeg</code> option, when set to false. Default true.</p>
<dt><code>useRemoteCursor</code></p>
<dd> Equivalent of <code>-nocursorshape</code> option, when set to false (TightVNC-specific). Default true.</p>
<dt><code>useBGR233</code></p>
<dd> Equivalent of <code>-bgr233</code> option. Default false.</p>
<dt><code>nColours</code></p>
<dd> When using BGR233, try to allocate this many &quot;exact&quot; colors from the BGR233 color cube. When using a shared colormap, setting this resource lower leaves more colors for other X clients. Irrelevant when using truecolor. Default is 256 (i.e. all of them).</p>
<dt><code>useSharedColours</code></p>
<dd> If the number of &quot;exact&quot; BGR233 colors successfully allocated is less than 256 then the rest are filled in using the &quot;nearest&quot; colors available. This resource says whether to only use the &quot;exact&quot; BGR233 colors for this purpose, or whether to use other clients&#8217; &quot;shared&quot; colors as well. Default true (i.e. use other clients&#8217; colors).</p>
<dt><code>forceOwnCmap</code></p>
<dd> Equivalent of <code>-owncmap</code> option. Default false.</p>
<dt><code>forceTrueColour</code></p>
<dd> Equivalent of <code>-truecolour</code> option. Default false.</p>
<dt><code>requestedDepth</code></p>
<dd> Equivalent of <code>-depth</code> option.</p>
<dt><code>useSharedMemory</code></p>
<dd> Use MIT shared memory extension if on the same machine as the X server. Default true.</p>
<dt><code>wmDecorationWidth, wmDecorationHeight</code></p>
<dd> The total width and height taken up by window manager decorations. This is used to calculate the maximum size of the VNC viewer window. Default is width 4, height 24.</p>
<dt><code>bumpScrollTime, bumpScrollPixels</code></p>
<dd> When in full screen mode and the VNC desktop is bigger than the X display, scrolling happens whenever the mouse hits the edge of the screen. The maximum speed of scrolling is bumpScrollPixels pixels every bumpScrollTime milliseconds. The actual speed of scrolling will be slower than this, of course, depending on how fast your machine is. Default 20 pixels every 25 milliseconds.</p>
<dt><code>popupButtonCount</code></p>
<dd> The number of buttons in the popup window. See the README file for more information on how to customize the buttons.</p>
<dt><code>debug</code></p>
<dd> For debugging. Default false.</p>
<dt><code>rawDelay, copyRectDelay</code></p>
<dd> For debugging, see the README file for details. Default 0 (off).</dl>
<h2>ENVIRONMENT</h2>
<p> When started with the <code>-via</code> option, vncviewer reads the <code>VNC_VIA_CMD</code> environment variable, expands patterns beginning with the &quot;%&quot; character, and executes result as a command assuming that it would create TCP tunnel that should be used for VNC connection. If not set, this environment variable defaults to &quot;/usr/bin/ssh -f -L %L:%H:%R %G sleep 20&quot;. </p>
<p> The following patterns are recognized in the <code>VNC_VIA_CMD</code> (note that all the patterns %G, %H, %L and %R must be present in the command template):</p>
<dl>
<dt><code>%%</code></p>
<dd> A literal &quot;%&quot;;</p>
<dt><code>%G</code></p>
<dd> gateway host name;</p>
<dt><code>%H</code></p>
<dd> remote VNC host name, as known to the gateway;</p>
<dt><code>%L</code></p>
<dd> local TCP port number;</p>
<dt><code>%R</code></p>
<dd> remote TCP port number.</dl>
