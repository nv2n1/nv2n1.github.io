<p>Xnest &#8211; a nested X server</p>
<h2>Synopsis</h2>
<p><code>Xnest</code> [ <i>options</i> ]</p>
<h2>Description</h2>
<p><code>Xnest</code> is both an X client and an X server. <code>Xnest</code> is a client of the real server which manages windows and graphics requests on its behalf. <code>Xnest</code> is a server to its own clients. <code>Xnest</code> manages windows and graphics requests on their behalf. To these clients, <code>Xnest</code> appears to be a conventional server.</p>
<h2>Options</h2>
<p><code>Xnest</code> supports all standard options of the sample server implementation. For more details, please see <code><a href="/docs/linux/man/1-xserver/">Xserver</a></code>(1). The following additional arguments are supported as well.</p>
<dl>
<dt><code>-display </code><i>string</i></p>
<dd>This option specifies the display name of the real server that <code>Xnest</code> should try to connect to. If it is not provided on the command line, <code>Xnest</code> will read the <i>DISPLAY</i> environment variable in order to find out this information.</p>
<dt><code>-sync</code></p>
<dd>This option tells <code>Xnest</code> to synchronize its window and graphics operations with the real server. This is a useful option for debugging, but it will slow down <code>Xnest</code>&#8216;s performance considerably. It should not be used unless absolutely necessary.</p>
<dt><code>-full</code></p>
<dd>This option tells <code>Xnest</code> to utilize full regeneration of real server objects and reopen a new connection to the real server each time the nested server regenerates. The sample server implementation regenerates all objects in the server when the last client of this server terminates. When this happens, <code>Xnest</code> by default maintains the same top-level window and the same real server connection in each new generation. If the user selects full regeneration, even the top-level window and the connection to the real server will be regenerated for each server generation.</p>
<dt><code>-class </code><i>string</i></p>
<dd>This option specifies the default visual class of the nested server. It is similar to the <code>-cc</code> option from the set of standard options except that it will accept a string rather than a number for the visual class specification. The <i>string</i> must be one of the following six values: <code>StaticGray</code>, <code>GrayScale</code>, <code>StaticColor</code>, <code>PseudoColor</code>, <code>TrueColor</code>, or <code>DirectColor</code>. If both the <code>-class</code> and <code>-cc</code> options are specified, the last instance of either option takes precedence. The class of the default visual of the nested server need not be the same as the class of the default visual of the real server, but it must be supported by the real server. Use <code><a href="/docs/linux/man/1-xdpyinfo/">xdpyinfo</a></code>(1) to obtain a list of supported visual classes on the real server before starting <code>Xnest</code>. If the user chooses a static class, all the colors in the default color map will be preallocated. If the user chooses a dynamic class, colors in the default color map will be available to individual clients for allocation.</p>
<dt><code>-depth </code><i>int</i></p>
<dd>This option specifies the default visual depth of the nested server. The depth of the default visual of the nested server need not be the same as the depth of the default visual of the real server, but it must be supported by the real server. Use <code><a href="/docs/linux/man/1-xdpyinfo/">xdpyinfo</a></code>(1) to obtain a list of supported visual depths on the real server before starting <code>Xnest</code>.</p>
<dt><code>-sss</code></p>
<dd>This option tells <code>Xnest</code> to use the software screen saver. By default, <code>Xnest</code> will use the screen saver that corresponds to the hardware screen saver in the real server. Of course, even this screen saver is software-generated since <code>Xnest</code> does not control any actual hardware. However, it is treated as a hardware screen saver within the sample server code.</p>
<dt><code>-geometry </code><i>W</i><code>x</code><i>H</i><code>+</code><i>X</i><code>+</code><i>Y</i></p>
<dd>This option specifies the geometry parameters for the top-level <code>Xnest</code> window. See &#8220;GEOMETRY SPECIFICATIONS&#8221; in <code><a href="/docs/linux/man/7-x/">X</a></code>(7) for a discusson of this option&#8217;s syntax. This window corresponds to the root window of the nested server. The width <i>W</i> and height <i>H</i> specified with this option will be the maximum width and height of each top-level <code>Xnest</code> window. <code>Xnest</code> will allow the user to make any top-level window smaller, but it will not actually change the size of the nested server root window. <code>Xnest</code> does not yet support the RANDR extension for resizing, rotation, and reflection of the root window. If this option is not specified, <code>Xnest</code> will choose <i>W</i> and <i>H</i> to be 3/4ths the dimensions of the root window of the real server.</p>
<dt><code>-bw </code><i>int</i></p>
<dd>This option specifies the border width of the top-level <code>Xnest</code> window. The integer parameter <i>int</i> must be positive. The default border width is 1.</p>
<dt><code>-name </code><i>string</i></p>
<dd>This option specifies the name of the top-level <code>Xnest</code> window as <i>string</i>. The default value is the program name.</p>
<dt><code>-scrns </code><i>int</i></p>
<dd>This option specifies the number of screens to create in the nested server. For each screen, <code>Xnest</code> will create a separate top-level window. Each screen is referenced by the number after the dot in the client display name specification. For example, <code>xterm -display :1.1</code> will open an <code><a href="/docs/linux/man/1-xterm/">xterm</a></code>(1) client in the nested server with the display number <code>:1</code> on the second screen. The number of screens is limited by the hard-coded constant in the server sample code, which is usually 3.</p>
<dt><code>-install</code></p>
<dd>This option tells <code>Xnest</code> to do its own color map installation by bypassing the real window manager. For it to work properly, the user will probably have to temporarily quit the real window manager. By default, <code>Xnest</code> will keep the nested client window whose color map should be installed in the real server in the <i>WM_COLORMAP_WINDOWS</i> property of the top-level <code>Xnest</code> window. If this color map is of the same visual type as the root window of the nested server, <code>Xnest</code> will associate this color map with the top-level <code>Xnest</code> window as well. Since this does not have to be the case, window managers should look primarily at the <i>WM_COLORMAP_WINDOWS</i> property rather than the color map associated with the top-level <code>Xnest</code> window. Unfortunately, window managers are not very good at doing that yet so this option might come in handy.</p>
<dt><code>-parent </code><i>window_id</i></p>
<dd>This option tells <code>Xnest</code> to use <i>window_id</i> as the root window instead of creating a window.</dl>
<h2>Extended Description</h2>
<p>Starting up <code>Xnest</code> is just as simple as starting up <code><a href="/docs/linux/man/1-xclock/">xclock</a></code>(1) from a terminal emulator. If a user wishes to run <code>Xnest</code> on the same workstation as the real server, it is important that the nested server is given its own listening socket address. Therefore, if there is a server already running on the user&#8217;s workstation, <code>Xnest</code> will have to be started up with a new display number. Since there is usually no more than one server running on a workstation, specifying &#8216;<code>Xnest :1</code>&#8216; on the command line will be sufficient for most users. For each server running on the workstation, the display number needs to be incremented by one. Thus, if you wish to start another <code>Xnest</code>, you will need to type &#8216;<code>Xnest :2</code>&#8216; on the command line. </p>
<p> To run clients in the nested server, each client needs to be given the same display number as the nested server. For example, &#8216;<code>xterm -display :1</code>&#8216; will start up an <code>xterm</code> process in the first nested server and &#8216;<code>xterm -display :2</code>&#8216; will start an <code>xterm</code> in the second nested server from the example above. Additional clients can be started from these <code>xterm</code>s in each nested server.</p>
<h3>Xnest as a client</h3>
<p><code>Xnest</code> behaves and looks to the real server and other real clients as another real client. It is a rather demanding client, however, since almost any window or graphics request from a nested client will result in a window or graphics request from <code>Xnest</code> to the real server. Therefore, it is desirable that <code>Xnest</code> and the real server are on a local network, or even better, on the same machine. <code>Xnest</code> assumes that the real server supports the SHAPE extension. There is no way to turn off this assumption dynamically. <code>Xnest</code> can be compiled without the SHAPE extension built in, in which case the real server need not support it. Dynamic SHAPE extension selection support may be considered in further development of <code>Xnest</code>. </p>
<p> Since <code>Xnest</code> need not use the same default visual as the the real server, the top-level window of the <code>Xnest</code> client always has its own color map. This implies that other windows&#8217; colors will not be displayed properly while the keyboard or pointer focus is in the <code>Xnest</code> window, unless the real server has support for more than one installed color map at any time. The color map associated with the top window of the <code>Xnest</code> client need not be the appropriate color map that the nested server wants installed in the real server. In the case that a nested client attempts to install a color map of a different visual from the default visual of the nested server, <code>Xnest</code> will put the top window of this nested client and all other top windows of the nested clients that use the same color map into the <i>WM_COLORMAP_WINDOWS</i> property of the top-level <code>Xnest</code> window on the real server. Thus, it is important that the real window manager that manages the <code>Xnest</code> top-level window looks at the <i>WM_COLORMAP_WINDOWS</i> property rather than the color map associated with the top-level <code>Xnest</code> window. Since most window managers don&#8217;t yet appear to implement this convention properly, <code>Xnest</code> can optionally do direct installation of color maps into the real server bypassing the real window manager. If the user chooses this option, it is usually necessary to temporarily disable the real window manager since it will interfere with the <code>Xnest</code> scheme of color map installation. </p>
<p> Keyboard and pointer control procedures of the nested server change the keyboard and pointer control parameters of the real server. Therefore, after <code>Xnest</code> is started up, it will change the keyboard and pointer controls of the real server to its own internal defaults.</p>
<h3>Xnest as a server</h3>
<p><code>Xnest</code> as a server looks exactly like a real server to its own clients. For the clients, there is no way of telling if they are running on a real or a nested server. </p>
<p> As already mentioned, <code>Xnest</code> is a very user-friendly server when it comes to customization. <code>Xnest</code> will pick up a number of command-line arguments that can configure its default visual class and depth, number of screens, etc. </p>
<p> The only apparent intricacy from the users&#8217; perspective about using <code>Xnest</code> as a server is the selection of fonts. <code>Xnest</code> manages fonts by loading them locally and then passing the font name to the real server and asking it to load that font remotely. This approach avoids the overload of sending the glyph bits across the network for every text operation, although it is really a bug. The consequence of this approach is that the user will have to worry about two different font paths &#8212; a local one for the nested server and a remote one for the real server &#8212; since <code>Xnest</code> does not propagate its font path to the real server. The reason for this is because real and nested servers need not run on the same file system which makes the two font paths mutually incompatible. Thus, if there is a font in the local font path of the nested server, there is no guarantee that this font exists in the remote font path of the real server. The <code><a href="/docs/linux/man/1-xlsfonts/">xlsfonts</a></code>(1) client, if run on the nested server, will list fonts in the local font path and, if run on the real server, will list fonts in the remote font path. Before a font can be successfully opened by the nested server, it has to exist in local and remote font paths. It is the users&#8217; responsibility to make sure that this is the case.</p>
<h2>Future Directions</h2>
<p>Make dynamic the requirement for the SHAPE extension in the real server, rather than having to recompile <code>Xnest</code> to turn this requirement on and off. </p>
<p> Perhaps there should be a command-line option to tell <code>Xnest</code> to inherit the keyboard and pointer control parameters from the real server rather than imposing its own. </p>
<p> <code>Xnest</code> should read a customization input file to provide even greater freedom and simplicity in selecting the desired layout. </p>
<p> There is no support for backing store and save unders, but this should also be considered. </p>
<p> The proper implementation of fonts should be moved into the <i>os</i> layer.</p>
