<h2 class="name">NAME</h2>
<p> dvisvgm &#8211; converts DVI and EPS files to the XML-based SVG format </p>
<h2>SYNOPSIS</h2>
<p> <code>dvisvgm</code> [<i>options</i>] <i>file</i>[.dvi] </p>
<p> <code>dvisvgm</code> &#8211;eps [<i>options</i>] <i>file1</i>[.eps] <i>file2</i>[.eps] &#8230; </p>
<p> <code>dvisvgm</code> &#8211;pdf [<i>options</i>] <i>file</i>[.pdf]</p>
<h2>DESCRIPTION</h2>
<p> The command-line utility <code>dvisvgm</code> converts DVI files, as generated by TeX/LaTeX, to the XML-based scalable vector graphics format SVG. It supports the classic DVI version 2 as well as version 3 (created by pTeX in vertical mode), and the XeTeX versions 5 to 7 which are also known as XDV. Besides the basic DVI commands, dvisvgm also evaluates many so-called <i>specials</i> which heavily extend the capabilities of the plain DVI format. For a more detailed overview, see section <code>Supported Specials</code> below. </p>
<p> Since the current SVG standard 1.1 doesn&#8217;t specify multi-page graphics, dvisvgm creates separate SVG files for each DVI page. Because of compatibility reasons, only the first page is converted by default. In order to select a different page or arbitrary page sequences, use option <code>-p</code> which is described below. </p>
<p> SVG is a vector-based graphics format and therefore dvisvgm tries to convert the glyph outlines of all fonts referenced in a DVI page section to scalable path descriptions. The fastest way to achieve this is to extract the path information from vector-based font files available in PFB, TTF, or OTF format. If dvisvgm is able to find such a file, it extracts all necessary outline information about the glyphs from it. </p>
<p> However, TeX&#8217;s main source for font descriptions is Metafont, which produces bitmap output (GF files). That&#8217;s why not all obtainable TeX fonts are available in a scalable format. In these cases, dvisvgm tries to vectorize Metafont&#8217;s output by tracing the glyph bitmaps. The results are not as perfect as most (manually optimized) PFB or OTF counterparts, but are nonetheless really nice in most cases. </p>
<p> When running dvisvgm without option <code>&#8211;no-fonts</code>, it creates <i>font</i> elements (<code>&lt;font&gt;</code>&#8230;<code>&lt;/font&gt;</code>) to embed the font data into the SVG files. Unfortunately, only few SVG renderers support these elements yet. Most web browsers and vector graphics applications don&#8217;t evaluate them properly so that the text components of the resulting graphics might look strange. In order to create more compatible SVG files, command-line option <code>&#8211;no-fonts</code> can be given to replace the font elements by plain graphics paths. Most web browsers (but only few external SVG renderers) also support WOFF and WOFF2 fonts that can be used instead of the default SVG fonts. Option <code>&#8211;font-format</code> offers the functionality to change the format applied to the fonts being embedded. This, however, only works when converting DVI files. Text present in PDF and PostScript files is always converted to path elements.</p>
<h2>OPTIONS</h2>
<p> dvisvgm provides a POSIX-compliant command-line interface with short and long option names. They may be given before and/or after the name of the file to be converted. Also, the order of specifying the options is not significant, i.e. you can add them in any order without changing dvisvgm&#8217;s behavior. Certain options accept or require additional parameters which are directly appended to or separated by whitespace from a short option (e.g. <code>-v0</code> or <code>-v 0</code>). Long options require an additional equals sign (<code>=</code>) between option name and argument but without any surrounding whitespace (e.g. <code>&#8211;verbosity=0</code>). Multiple short options that don&#8217;t expect a further parameter can be combined after a single dash (e.g. <code>-ejs</code> rather than <code>-e -j -s</code>). </p>
<p> Long option names may also be shortened by omitting trailing characters. As long as the shortened name is unambiguous, it&#8217;s recognized and applied. For example, option <code>&#8211;exact-bbox</code> can be shortened to <code>&#8211;exact</code>, <code>&#8211;exa</code>, or <code>&#8211;ex</code>. In case of an ambiguous abbreviation, dvisvgm prints an error message together with all matching option names. </p>
<p> <code>-b, &#8211;bbox</code>=<i>fmt</i></p>
<dl>
<dt>
<dd> Sets the bounding box of the generated SVG graphic to the specified format. This option only affects the conversion of DVI files. SVG documents generated from PDF and PostScript always inherit the bounding boxes of the input files. </p>
<p> Parameter <i>fmt</i> takes either one of the format specifiers listed below, or a sequence of four comma- or whitespace-separated length values <i>x1</i>, <i>y1</i>, <i>x2</i> and <i>y2</i>. The latter define the absolute coordinates of two diagonal corners of the bounding box. Each length value consists of a floating point number and an optional length unit (pt, bp, cm, mm, in, pc, dd, cc, or sp). If the unit is omitted, TeX points (pt) are assumed. </p>
<p> It&#8217;s also possible to give only one length value <i>l</i>. In this case, the minimal bounding box is computed and enlarged by adding (-<i>l</i>,-<i>l</i>) to the upper left and (<i>l</i>,<i>l</i>) to the lower right corner. </p>
<p> Additionally, dvisvgm also supports the following format specifiers: </p>

<p> <code>Page orientation</code></p>
<dl>
<dt>
<dd> The default page orientation for DIN/ISO and American paper sizes is <i>portrait</i>, i.e. <i>width</i> &lt; <i>height</i>. Appending <code>-landscape</code> or simply <code>-l</code> to the format string switches to <i>landscape</i> mode (<i>width</i> &gt; <i>height</i>). For symmetry reasons you can also explicitly add <code>-portrait</code> or <code>-p</code> to indicate the default portrait format. Note that these suffixes are part of the size string and not separate options. Thus, they must directly follow the size specifier without additional blanks. Furthermore, the orientation suffixes can&#8217;t be used with <code>dvi</code>, <code>min</code>, and <code>none</code>. </p>
<dl>
<dt>
<dd>

 Option <code>-b, &#8211;bbox</code> only affects the bounding box and does not transform the page content. Hence, if you choose a landscape format, the page won&#8217;t be rotated. </p>

To select the alternative lossless PNG format, <code>&#8211;bitmap-format=png</code> can be used. There are some more format variants dvisvgm currently supports even though <code>jpeg</code> and <code>png</code> should be sufficient in most cases. The following list gives an overview of the known format names which correspond to names of Ghostscript output devices. </p>

<p> Since the collection of supported output devices can vary among local Ghostscript installations, not all formats may be available in some environments. dvisvgm quits with a PostScript error message if the selected output format requires a locally unsupported output device. </p>
<p> The two JPEG format specifiers accept an optional parameter to set the IJG quality level which must directly follow the format specifier separated by a colon, e.g. <code>&#8211;bitmap-format=jpeg:50</code>. The quality value is an integer between 0 and 100. Higher values result in better image quality but lower compression rates and therefore larger files. The default quality level is 75 which is applied if no quality parameter is given or if it&#8217;s set to 0.</dl>
<p> <code>-C, &#8211;cache</code>[=<i>dir</i>]</p>
<dl>
<dt>
<dd> To speed up the conversion process of bitmap fonts, dvisvgm saves intermediate conversion information in cache files. By default, these files are stored in <code>$XDG_CACHE_HOME/dvisvgm/</code> or <code>$HOME/.cache/dvisvgm</code> if <code>XDG_CACHE_HOME</code> is not set. If you prefer a different location, use option <code>&#8211;cache</code> to overwrite the default. Furthermore, it is also possible to disable the font caching mechanism completely with option <code>&#8211;cache=none</code>. If argument <i>dir</i> is omitted, dvisvgm prints the path of the default cache directory together with further information about the stored fonts. Additionally, outdated and corrupted cache files are removed.</dl>
<p> <code>-j, &#8211;clipjoin</code></p>
<dl>
<dt>
<dd> This option tells dvisvgm to compute all intersections of clipping paths itself rather than delegating this task to the SVG renderer. The resulting SVG files are more portable because some SVG viewers don&#8217;t support intersecting clipping paths which are defined by <i>clipPath</i> elements containing a <i>clip-path</i> attribute.</dl>
<p> <code>&#8211;color</code></p>
<dl>
<dt>
<dd> Enables colorization of messages printed during the conversion process. The colors can be customized via environment variable <code>DVISVGM_COLORS</code>. See the Environment section below for further information.</dl>
<p> <code>&#8211;colornames</code></p>
<dl>
<dt>
<dd> By default, dvisvgm exclusively uses RGB values of the form <i>#RRGGBB</i> or <i>#RGB</i> to represent colors in the SVG file. The latter is a short form for colors whose RGB components each consist of two identical hex digits, e.g. <code>#123</code> equals <code>#112233</code>. According to the SVG standard, it&#8217;s also possible to use color names (like <code>black</code> and <code>darkblue</code>) for a limited number of predefined colors (m[blue]<a rel="nofollow" href="https://www.w3.org/TR/SVG11/types.html#ColorKeywordsm[]">https://www.w3.org/TR/SVG11/types.html#ColorKeywordsm[]</a>). In order to apply these color names rather than their RGB values, call dvisvgm with option <code>&#8211;colornames</code>. All colors without an SVG color name will still be represented by RGB values.</dl>
<p> <code>&#8211;comments</code></p>
<dl>
<dt>
<dd> Adds comments with further information about selected data to the SVG file. Currently, only font elements and font CSS rules related to native fonts are annotated.</dl>
<p> <code>-E, &#8211;eps</code></p>
<dl>
<dt>
<dd> If this option is given, dvisvgm does not expect a DVI but a single or multiple EPS input files, and tries to convert them to SVG. In order to do so, a single <i>psfile</i> special command is created and forwarded to the PostScript special handler. This option is only available if dvisvgm was built with PostScript support enabled, and requires Ghostscript to be available. See option <code>&#8211;libgs</code> for further information.</dl>
<p> <code>-e, &#8211;exact-bbox</code></p>
<dl>
<dt>
<dd> This option tells dvisvgm to compute the precise bounding box of each character. By default, the values stored in a font&#8217;s TFM file are used to determine a glyph&#8217;s extent. As these values are intended to implement optimal character placements and are not designed to represent the exact dimensions, they don&#8217;t necessarily correspond with the bounds of the visual glyphs. Thus, width and/or height of some glyphs may be larger (or smaller) than the respective TFM values. As a result, this can lead to clipped characters at the bounds of the SVG graphics. With option <code>&#8211;exact-bbox</code> given, dvisvgm analyzes the actual shape of each character and derives a usually tight bounding box.</dl>
<p> <code>-f, &#8211;font-format</code>=<i>format</i></p>
<dl>
<dt>
<dd> Selects the file format used to embed font data into the generated SVG output when converting DVI files. It has no effect when converting PDF or PostScript files. Text fragments present in these files are always converted to path elements. </p>
<p> Following formats are supported: <code>SVG</code> (that&#8217;s the default), <code>TTF</code> (TrueType), <code>WOFF</code>, and <code>WOFF2</code> (Web Open Font Format version 1 and 2). By default, dvisvgm creates unhinted fonts that might look bad on low-resolution devices. In order to improve the display quality, the generated TrueType, WOFF, or WOFF2 fonts can be autohinted. The autohinter is enabled by appending <code>,autohint</code> or <code>,ah</code> to the font format, e.g. <code>&#8211;font-format=woff,autohint</code> or <code>&#8211;fwoff,ah</code>. </p>
<p> Option <code>&#8211;font-format</code> is only available if dvisvgm was built with WOFF support enabled.</dl>
<p> <code>-m, &#8211;fontmap</code>=<i>filenames</i></p>
<dl>
<dt>
<dd> Loads and evaluates a single font map file or a sequence of font map files. These files are required to resolve font file names and encodings. dvisvgm does not provide its own map files but tries to read available ones coming with dvips or dvipdfm. If option <code>&#8211;fontmap</code> is omitted, dvisvgm looks for the default map files <i>ps2pk.map</i>, <i>pdftex.map</i>, <i>dvipdfm.map</i>, and <i>psfonts.map</i> (in this order). Otherwise, the files given as option arguments are evaluated in the given order. Multiple filenames must be separated by commas without leading and/or trailing whitespace. </p>
<p> By default, redefined mappings do not replace previous ones. However, each filename can be preceded by an optional mode specifier (<code>+</code>, <code>&#8211;</code>, or <code>=</code>) to change this behavior: </p>
<p> +mapfile</p>
<dl>
<dt>
<dd> Only those entries in the given map file that don&#8217;t redefine a font mapping are applied, i.e. fonts already mapped keep untouched. That&#8217;s also the default mode if no mode specifier is given.</dl>
<p> -mapfile</p>
<dl>
<dt>
<dd> Ensures that none of the font mappings defined in the given map file are used, i.e. previously defined mappings for the specified fonts are removed.</dl>
<p> =mapfile</p>
<dl>
<dt>
<dd> All mappings defined in the map file are applied. Previously defined settings for the same fonts are replaced. </p>
<p> If the first filename in the filename sequence is preceded by a mode specifier, dvisvgm loads the default font map (see above) and applies the other map files afterwards. Otherwise, none of default map files will be loaded automatically. </p>
<p> Examples: <code>&#8211;fontmap=myfile1.map,+myfile2.map</code> loads <i>myfile1.map</i> followed by <i>myfile2.map</i> where all redefinitions of <code>myfile2.map</code> are ignored. <code>&#8211;fontmap==myfile1.map,-myfile2.map</code> loads the default map file followed by <i>myfile1.map</i> and <i>myfile2.map</i> where all redefinitions of <i>myfile1.map</i> replace previous entries. Afterwards, all definitions for the fonts given in <i>myfile2.map</i> are removed from the font map tree. </p>
<p> For further information about the map file formats and the mode specifiers, see the manuals of dvips (m[blue]<a rel="nofollow" href="https://tug.org/texinfohtml/dvips.htmlm[])">https://tug.org/texinfohtml/dvips.htmlm[])</a> and dvipdfm (m[blue]<a rel="nofollow" href="https://ctan.org/tex-archive/dviware/dvipdfmm[]">https://ctan.org/tex-archive/dviware/dvipdfmm[]</a>).</dl>
</dl>
<p> <code>&#8211;grad-overlap</code></p>
<dl>
<dt>
<dd> Tells dvisvgm to create overlapping grid segments when approximating color gradient fills (also see option <code>&#8211;grad-segments</code> below). By default, adjacent segments don&#8217;t overlap but only touch each other like separate tiles. However, this alignment can lead to visible gaps between the segments because the background color usually influences the color at the boundary of the segments if the SVG renderer uses anti-aliasing to create smooth contours. One way to avoid this and to create seamlessly touching color regions is to enlarge the segments so that they extend into the area of their right and bottom neighbors. Since the latter are drawn on top of the overlapping parts, the visible size of all segments keeps unchanged. Just the former gaps disappear as the background is now completely covered by the correct colors. Currently, dvisvgm computes the overlapping segments separately for each patch of the mesh (a patch mesh may consist of multiple patches of the same type). Therefore, there still might be visible gaps at the seam of two adjacent patches.</dl>
<p> <code>&#8211;grad-segments</code>=<i>number</i></p>
<dl>
<dt>
<dd> Determines the maximal number of segments per column and row used to approximate gradient color fills. Since SVG 1.1 only supports a small subset of the shading algorithms available in PostScript, dvisvgm approximates some of them by subdividing the area to be filled into smaller, monochromatic segments. Each of these segments gets the average color of the region it covers. Thus, increasing the number of segments leads to smaller monochromatic areas and therefore a better approximation of the actual color gradient. As a drawback, more segments imply bigger SVG files because every segment is represented by a separate path element. </p>
<p> Currently, dvisvgm supports free- and lattice-form triangular patch meshes as well as Coons and tensor-product patch meshes. They are approximated by subdividing the area of each patch into a <i>n</i>&#215;<i>n</i> grid of smaller segments. The maximal number of segments per column and row can be changed with option <code>&#8211;grad-segments</code>.</dl>
<p> <code>&#8211;grad-simplify</code>=<i>delta</i></p>
<dl>
<dt>
<dd> If the size of the segments created to approximate gradient color fills falls below the given delta value, dvisvgm reduces their level of detail. For example, B&eacute;zier curves are replaced by straight lines, and triangular segments are combined to tetragons. For a small <i>delta</i>, these simplifications are usually not noticeable but reduce the size of the generated SVG files significantly.</dl>
<p> <code>-h, &#8211;help</code>[=<i>mode</i>]</p>
<dl>
<dt>
<dd> Prints a short summary of all available command-line options. The optional <i>mode</i> parameter is an integer value between 0 and 2. It selects the display variant of the help text. Mode 0 lists all options divided into categories with section headers. This is also the default if dvisvgm is called without parameters. Mode 1 lists all options ordered by the short option names, while mode 2 sorts the lines by the long option names. </p>
<p> A values in brackets after the description text indicate the default parameter of the option. They are applied if an option with a mandatory parameter is not used or if an optional parameter is omitted. For example, option <code>&#8211;bbox</code> requires a size parameter which defaults to <code>min</code> if <code>&#8211;bbox</code> is not used. Option <code>&#8211;zip</code>, which isn&#8217;t applied by default, accepts an optional compression level parameter. If it&#8217;s omitted, the stated default value 9 is used.</dl>
<p> <code>&#8211;keep</code></p>
<dl>
<dt>
<dd> Disables the removal of temporary files as created by Metafont (usually .gf, .tfm, and .log files) or the TrueType/WOFF module.</dl>
<p> <code>&#8211;libgs</code>=<i>path</i></p>
<dl>
<dt>
<dd> This option is only available if the Ghostscript library is not directly linked to dvisvgm and if PostScript support was not completely disabled during compilation. In this case, dvisvgm tries to load the shared GS library dynamically during runtime. By default, it expects the library&#8217;s name to be <code>libgs.so.X</code> (on Unix-like systems, where <code>X</code> is the ABI version of the library) or <code>gsdll32.dll</code>/<code>gsdll64.dll</code> (Windows). If dvisvgm doesn&#8217;t find the library, option <code>&#8211;libgs</code> can be used to specify the correct path and filename, e.g. <code>&#8211;libgs=/usr/local/lib/libgs.so.9</code> or <code>&#8211;libgs=\gs\gs9.25in\gsdll64.dll</code>. </p>
<p> Alternatively, it&#8217;s also possible to assign the path to environment variable <code>LIBGS</code>, e.g. <code>export LIBGS=/usr/local/lib/libgs.so.9</code> or <code>set LIBGS=\gs\gs9.25in\gsdll63.dll</code>. <code>LIBGS</code> has less precedence than the command-line option, i.e. dvisvgm ignores variable <code>LIBGS</code> if <code>&#8211;libgs</code> is given.</dl>
<p> <code>-L, &#8211;linkmark</code>=<i>style</i></p>
<dl>
<dt>
<dd> Selects the method how to mark hyperlinked areas. The <i>style</i> argument can take one of the values <i>none</i>, <i>box</i>, and <i>line</i>, where <i>box</i> is the default, i.e. a rectangle is drawn around the linked region if option <code>&#8211;linkmark</code> is omitted. Style argument <i>line</i> just draws the lower edge of the bounding rectangle, and <i>none</i> tells dvisvgm not to add any visible objects to hyperlinks. The lines and boxes get the current text color selected. In order to apply a different, constant color, a colon followed by a color specifier can be appended to the style string. A <i>color specifier</i> is either a hexadecimal RGB value of the form <i>#RRGGBB</i>, or a dvips color name (m[blue]<a rel="nofollow" href="https://en.wikibooks.org/wiki/LaTeX/Colors#The_68_standard_colors_known_to_dvipsm[]">https://en.wikibooks.org/wiki/LaTeX/Colors#The_68_standard_colors_known_to_dvipsm[]</a>). </p>
<p> Moreover, argument <i>style</i> can take a single color specifier to highlight the linked region by a frameless box filled with that color. An optional second color specifier separated by a colon selects the frame color. </p>
<p> Examples: <code>box:red</code> or <code>box:#ff0000</code> draws red boxes around the linked areas. <code>yellow:blue</code> creates yellow filled rectangles with blue frames.</dl>
<p> <code>-l, &#8211;list-specials</code></p>
<dl>
<dt>
<dd> Prints a list of registered special handlers and exits. Each handler processes a set of special statements belonging to the same category. In most cases, these categories are identified by the prefix of the special statements which is usually a leading string followed by a colon or a blank, e.g. <i>color</i> or <i>ps</i>. The listed handler names, however, don&#8217;t need to match these prefixes, e.g. if there is no common prefix or if functionality is split into separate handlers in order to allow them to be disabled separately using option <code>&#8211;no-specials</code>. All special statements not covered by one of the special handlers are silently ignored.</dl>
<p> <code>-M, &#8211;mag</code>=<i>factor</i></p>
<dl>
<dt>
<dd> Sets the magnification factor applied in conjunction with Metafont calls prior tracing the glyphs. The larger this value, the better the tracing results. Nevertheless, large magnification values can cause Metafont arithmetic errors due to number overflows. So, use this option with care. The default setting usually produces nice results.</dl>
<p> <code>&#8211;no-merge</code></p>
<dl>
<dt>
<dd> Puts every single character in a separate <i>text</i> element with corresponding <i>x</i> and <i>y</i> attributes. By default, new <i>text</i> or <i>tspan</i> elements are only created if a string starts at a location that differs from the regular position defined by the characters&#8217; advance values.</dl>
<p> <code>&#8211;no-mktexmf</code></p>
<dl>
<dt>
<dd> Suppresses the generation of missing font files. If dvisvgm can&#8217;t find a font file through the kpathsea lookup mechanism, it calls the external tools <i>mktextfm</i> or <i>mktexmf</i>. This option disables these calls.</dl>
<p> <code>-n, &#8211;no-fonts</code>[=<i>variant</i>]</p>
<dl>
<dt>
<dd> If this option is given, dvisvgm doesn&#8217;t create SVG <i>font</i> elements but uses <i>paths</i> instead. The resulting SVG files tend to be larger but are concurrently more compatible with most applications that don&#8217;t support SVG fonts. The optional argument <i>variant</i> selects the method how to substitute fonts by paths. Variant 0 creates <i>path</i> and <i>use</i> elements in order to avoid lengthy duplicates. Variant 1 creates <i>path</i> elements only. Option <code>&#8211;no-fonts</code> implies <code>&#8211;no-styles</code>.</dl>
<p> <code>-c, &#8211;scale</code>=<i>sx</i>[,<i>sy</i>]</p>
<dl>
<dt>
<dd> Scales the page content horizontally by <i>sx</i> and vertically by <i>sy</i>. This option is equivalent to <code>-TS</code><i>sx</i>,<i>sy</i>.</dl>
<p> <code>-S, &#8211;no-specials</code>[=<i>names</i>]</p>
<dl>
<dt>
<dd> Disable processing of special commands embedded in the DVI file. If no further parameter is given, all specials are ignored. To disable a selected set of specials, an optional comma-separated list of names can be appended to this option. A <i>name</i> is the unique identifier referencing the intended special handler as listed by option <code>&#8211;list-specials</code>.</dl>
<p> <code>&#8211;no-styles</code></p>
<dl>
<dt>
<dd> By default, dvisvgm creates CSS styles and class attributes to reference fonts. This variant is more compact than adding the complete font information to each text element over and over again. However, if you prefer direct font references, the default behavior can be disabled with option <code>&#8211;no-styles</code>.</dl>
<p> <code>-O, &#8211;optimize</code>[=<i>modules</i>]</p>
<dl>
<dt>
<dd> Applies several optimizations on the generated SVG tree to reduce the file size. The optimizations are performed by running separate optimizer modules specified by optional argument <i>modules</i>. It may consist of a single module name or a comma-separated list of several module names. The corresponding modules are executed one by one in the given order and thus transform the XML tree gradually. </p>
<p> The following list describes the currently available optimizer modules. </p>
<p> <code>list</code></p>
<dl>
<dt>
<dd> Lists all available optimizer modules and exits.</dl>
<p> <code>none</code></p>
<dl>
<dt>
<dd> If this argument is given, dvisvgm doesn&#8217;t apply any optimization. <code>none</code> can&#8217;t be combined with other module names.</dl>
<p> <code>all</code></p>
<dl>
<dt>
<dd> Performs all optimizations listed below. This is also the default if option <code>&#8211;optimize</code> is used without argument. The modules are executed in a predefined order that usually leads to the best results. <code>all</code> can&#8217;t be combined with other module names.</dl>
<p> <code>collapse-groups</code></p>
<dl>
<dt>
<dd> Combines nested group elements (<code>&lt;g&gt;</code>&#8230;<code>&lt;/g&gt;</code>) that contain only a single group each. If possible, the group attributes are moved to the outermost element of the processed subtree. This module also unwraps group elements that have no attributes at all.</dl>
<p> <code>group-attributes</code></p>
<dl>
<dt>
<dd> Creates groups (<code>&lt;g&gt;</code>&#8230;<code>&lt;/g&gt;</code>) for common attributes around adjacent elements. Each attribute is moved to a separate group so that multiple common attributes lead to nested groups. They can be combined by applying optimizer module <i>collapse-groups</i> afterwards. The algorithm only takes inheritable properties, such as <code>fill</code> or <code>stroke-width</code>, into account and only removes them from an element if none of the other attributes, like <code>id</code>, prevents this.</dl>
<p> <code>remove-clippath</code></p>
<dl>
<dt>
<dd> Removes all redundant <i>clipPath</i> elements. This optimization was already present in former versions of dvisvgm and was always applied by default. This behavior is retained, i.e. dvisvgm executes this module even if option <code>&#8211;optimize</code> is not given. You can use argument <i>none</i> to prevent that.</dl>
<p> <code>simplify-text</code></p>
<dl>
<dt>
<dd> If a <code>text</code> element only contains whitespace nodes and <code>tspan</code> elements, all common inheritable attributes of the latter are moved to the enclosing text element. All <code>tspan</code> elements without further attributes are unwrapped.</dl>
<p> <code>simplify-transform</code></p>
<dl>
<dt>
<dd> Tries to shorten all <i>transform</i> attributes. This module combines the transformation commands of each attribute and decomposes the resulting transformation matrix into a sequence of basic transformations, i.e. translation, scaling, rotation, and skewing. If this sequence is shorter than the equivalent <i>matrix</i> expression, it&#8217;s assigned to the attribute. Otherwise, the matrix expression is used.</dl>
</dl>
<p> <code>-o, &#8211;output</code>=<i>pattern</i></p>
<dl>
<dt>
<dd> Sets the pattern that determines the names of the generated SVG files. The required parameter <i>pattern</i> may consist of an arbitrary sequence of characters which make up the filenames. With the exception of the following mentioned variables and expressions, all characters are treated as static parts of the filenames and are therefore identical for all pages processed during a run of dvisvgm. The strings <code>%f</code>, <code>%p</code>, <code>%P</code>, <code>%n</code>, <code>%N</code>, <code>%hd</code>, <code>%ho</code>, and <code>%hc</code> are variables that can be used as part of the pattern. <code>%f</code> expands to the base name of the DVI file, i.e. the filename without suffix, <code>%p</code> is the current page number, and <code>%P</code> the total number of pages in the DVI file. The variables <code>%n</code> and <code>%N</code> expand to the number of the current file being converted (starting at 1) and the total number of files given, respectively. </p>
<p> An optional number (0-9) specified directly after the percent sign of a variable holding a numeric value denotes the minimal number of digits to be created. If a particular value consists of less digits, the number is padded with leading zeros. Example: <code>%3p</code> enforces 3 digits for the current page number (001, 002, etc.). Without an explicit width specifier, <code>%p</code> gets the same number of digits as <code>%P</code>. </p>
<p> If you need more control over the numbering, you can use arithmetic expressions as part of a pattern. The syntax is <code>%(</code><i>expr</i><code>)</code> where <i>expr</i> may contain additions, subtractions, multiplications, and integer divisions with common precedence. The variables <code>p</code> and <code>P</code> contain the current page number and the total number of pages, respectively. For example, <code>&#8211;output=&quot;%f-%(p-1)&quot;</code> creates filenames where the numbering starts with 0 rather than 1. </p>
<p> The variables <code>%hX</code> contain different hash values computed from the DVI page data and the options given on the command-line. <code>%hd</code> and <code>%hc</code> are only set if option <code>&#8211;page-hashes</code> is present. Otherwise, they are empty. For further information, see the description of option <code>&#8211;page-hashes</code> below. </p>
<p> The default pattern is <code>%f-%p.svg</code> if the DVI file consists of more than one page, and <code>%f.svg</code> otherwise. That means, a DVI file <i>foo.dvi</i> is converted to <i>foo.svg</i> if <i>foo.dvi</i> is a single-page document. Otherwise, multiple SVG files <i>foo-01.svg</i>, <i>foo-02.svg</i>, etc. are produced. In Windows environments, the percent sign indicates dereferenced environment variables, and must therefore be protected by a second percent sign, e.g. <code>&#8211;output=%%f-%%p</code>.</dl>
<p> <code>-p, &#8211;page</code>=<i>ranges</i></p>
<dl>
<dt>
<dd> This option selects the pages to be processed. Parameter <i>ranges</i> consists of a comma-separated list of single page numbers and/or page ranges. A page range is a pair of numbers separated by a hyphen, e.g. 5-12. Thus, a page sequence might look like this: 2-4,6,9-12,15. It doesn&#8217;t matter if a page is given more than once or if page ranges overlap. dvisvgm always extracts the page numbers in ascending order and converts them only once. In order to stay compatible with previous versions, the default page sequence is 1. dvisvgm therefore converts only the first page and not the whole document if option <code>&#8211;page</code> is omitted. Usually, page ranges consist of two numbers denoting the first and last page to be converted. If the conversion should start at page 1, or if it should continue up to the last DVI page, the first or second range number can be omitted, respectively. Example: <code>&#8211;page=-10</code> converts all pages up to page 10, <code>&#8211;page=10-</code> converts all pages starting with page 10. Please consider that the page values don&#8217;t refer to the page numbers printed on the corresponding page. Instead, the physical page count is expected, where the first page always gets number 1.</dl>
<p> <code>-H, &#8211;page-hashes</code>[=<i>params</i>]</p>
<dl>
<dt>
<dd> If this option is given, dvisvgm computes hash values of all pages to be processed. As long as the page contents don&#8217;t change, the hash value of that page stays the same. This property can be used to determine whether a DVI page must be converted again or can be skipped in consecutive runs of dvisvgm. This is done by propagating the hash value to variable <code>%hd</code> which can be accessed in the output pattern (see option <code>&#8211;output</code>). By default, dvisvgm changes the output pattern to <code>%f-%hd</code> if option <code>&#8211;page-hashes</code> is given. As a result, all SVG file names contain the hash value instead of the page number. When calling dvisvgm again with option <code>&#8211;page-hashes</code> with the same output pattern, it checks the existence of the SVG file to be created and skips the conversion if it&#8217;s already present. This also applies for consecutive calls of dvisvgm with different command-line parameters. If you want to force another conversion of a DVI file that hasn&#8217;t changed, you must remove the corresponding SVG files beforehand or add the parameter <code>replace</code> (see below). If you manually set the output pattern to not contain a hash value, the conversion won&#8217;t be skipped. </p>
<p> Alternatively, the output pattern may contain the variables <code>%ho</code> and <code>%hc</code>. <code>%ho</code> expands to a 32-bit hash representing the given command-line options that affect the generated SVG output, like <code>&#8211;no-fonts</code> and <code>&#8211;precision</code>. Different combinations of options and parameters lead to different hashes. Thus pattern <code>%f-%hd-%ho</code> creates filenames that change depending on the DVI data and the given command-line options. Variable <code>%hc</code> provides a combined hash computed from the DVI data and the command-line options. It has the same length as <code>%hd</code>. </p>
<p> Since the page number isn&#8217;t part of the file name by default, different DVI pages with identical contents get the same file name. Therefore, only the first one is converted while the others are skipped. To create separate files for each page, you can add the page number to the output pattern, e.g. <code>&#8211;output=&quot;%f-%p-%hc&quot;</code>. </p>
<p> By default, dvisvgm uses the fast XXH64 hash algorithm to compute the values provided through <code>%hd</code> and <code>%hc</code>. 64-bit hashes should be sufficient for most documents with an average size of pages. Alternatively, XXH32 and MD5 can be used as well. The desired algorithm is specified by argument <i>params</i> of option <code>&#8211;page-hashes</code>. It takes one of the strings <code>MD5</code>, <code>XXH32</code>, and <code>XXH64</code>, where the names can be given in lower case too, like <code>&#8211;page-hashes=md5</code>. Since version 0.7.1, xxHash provides an experimental 128-bit hash function whose algorithm has been stabilized as of version 0.8. When using a version prior to 0.8, the 128-bit hash values can vary depending on the used xxHash version. If the corresponding API is available, dvisvgm supports the new hash function, and option <code>&#8211;page-hashes</code> additionally accepts the algorithm specifier <code>XXH128</code>. </p>
<p> Finally, option <code>&#8211;page-hashes</code> can take a second argument that must be separated by a comma. Currently, only the two parameters <i>list</i> and <i>replace</i> are evaluated, e.g. <code>&#8211;page-hashes=md5,list</code> or <code>&#8211;page-hashes=replace</code>. When <i>list</i> is present, dvisvgm doesn&#8217;t perform any conversion but just lists the hash values <code>%hd</code> and <code>%hc</code> of the pages specified by option <code>&#8211;page</code>. Parameter <i>replace</i> forces dvisvgm to convert a DVI page even if a file with the target name already exists.</dl>
<p> <code>-P, &#8211;pdf</code></p>
<dl>
<dt>
<dd> If this option is given, dvisvgm does not expect a DVI but a PDF input file, and tries to convert it to SVG. Similar to the conversion of DVI files, only the first page is processed by default. Option <code>&#8211;page</code> can be used to select different pages, page ranges, and/or page sequences. The conversion is realized by creating a single <i>pdffile</i> special command which is forwarded to the PostScript special handler. Therefore, this option is only available if dvisvgm was built with PostScript support enabled, and requires Ghostscript to be accessible. See option <code>&#8211;libgs</code> for further information.</dl>
<p> <code>-d, &#8211;precision</code>=<i>digits</i></p>
<dl>
<dt>
<dd> Specifies the maximal number of decimal places applied to floating-point attribute values. All attribute values written to the generated SVG file(s) are rounded accordingly. The parameter <i>digits</i> accepts integer values from 0 to 6, where 0 enables the automatic selection of significant decimal places. This is also the default value if dvisvgm is called without option <code>&#8211;precision</code>.</dl>
<p> <code>&#8211;progress</code>[=<i>delay</i>]</p>
<dl>
<dt>
<dd> Enables a simple progress indicator shown when time-consuming operations like PostScript specials are processed. The indicator doesn&#8217;t appear before the given delay (in seconds) has elapsed. The default delay value is 0.5 seconds.</dl>
<p> <code>-r, &#8211;rotate</code>=<i>angle</i></p>
<dl>
<dt>
<dd> Rotates the page content clockwise by <i>angle</i> degrees around the page center. This option is equivalent to <code>-TR</code><i>angle</i>.</dl>
<p> <code>-R, &#8211;relative</code></p>
<dl>
<dt>
<dd> SVG allows you to define graphics paths by a sequence of absolute and/or relative path commands, i.e. each command expects either absolute coordinates or coordinates relative to the current drawing position. By default, dvisvgm creates paths made up of absolute commands. If option <code>&#8211;relative</code> is given, relative commands are created instead. This slightly reduces the size of the SVG files in most cases.</dl>
<p> <code>&#8211;stdin</code></p>
<dl>
<dt>
<dd> Tells dvisvgm to read the DVI or EPS input data from <code>stdin</code> instead from a file. Alternatively to option <code>&#8211;stdin</code>, a single dash (-) can be given. The default name of the generated SVG file is <i>stdin.svg</i> which can be changed with option <code>&#8211;output</code>.</dl>
<p> <code>-s, &#8211;stdout</code></p>
<dl>
<dt>
<dd> Don&#8217;t write the SVG output to a file but redirect it to <code>stdout</code>.</dl>
<p> <code>&#8211;tmpdir</code>[=<i>path</i>]</p>
<dl>
<dt>
<dd> In some cases, dvisvgm needs to create temporary files to work properly. These files go to the system&#8217;s temporary folder by default, e.g. <code>/tmp</code> on Linux systems. Option <code>&#8211;tmpdir</code> can be used to specify a different location. Please note that dvisvgm does not create this folder if it doesn&#8217;t exist. Therefore, you must ensure that it&#8217;s actually present before running dvisvgm. </p>

<p> <code>-a, &#8211;trace-all</code>=[<i>retrace</i>]</p>
<dl>
<dt>
<dd> This option forces dvisvgm to vectorize not only the glyphs actually required to render the SVG file correctly &#8211; which is the default -, but processes all glyphs of all fonts referenced in the DVI file. Because dvisvgm stores the tracing results in a font cache, all following conversions of these fonts will speed up significantly. The boolean option <i>retrace</i> determines how to handle glyphs already stored in the cache. By default, these glyphs are skipped. Setting argument <i>retrace</i> to <i>yes</i> or <i>true</i> forces dvisvgm to retrace the corresponding bitmaps again. </p>
<dl>
<dt>
<dd>
 <font SIZE="+1"> <code>Note</code> </font><br />

<h2>SUPPORTED SPECIALS</h2>
<p> dvisvgm supports several <i>special commands</i> that enrich the DVI command set with additional instructions for features, like color, graphics, and hyperlinks. The term <i>special command</i>, or just <i>special</i>, originates from the TeX command <code>\special{&#8230;}</code> which does almost nothing. TeX only forwards the whole command to the DVI file and delegates its execution to the DVI driver. The DVI driver can then decide to either process or ignore it, depending on the supported statements. The parameter of TeX&#8217;s <code>\special</code> command is given in curly braces and may consist of an arbitrary character sequence representing the actual instruction, for example <code>color Red</code>. </p>
<p> + dvisvgm delegates the evaluation of special commands to dedicated handlers. Each handler is responsible for all special statements of the same command set, i.e. commands usually &#8211; but not necessarily &#8211; beginning with a common prefix. For example, all PDF specials start with the prefix <code>pdf:</code>, while the TPIC special set consists of 13 different commands without common identifier. The PDF specials are processed by dvisvgm&#8217;s <i>pdf</i> handler, the TPIC ones by the <i>tpic</i> handler. To get a list of the actually provided special handlers, use option <code>&#8211;list-specials</code> (see above). The following list gives an overview of the special sets currently supported. The names of the handlers can also be used to disable the processing of individual sets of specials. For further information on this, see option <code>&#8211;no-specials</code>. </p>
<p> <code>bgcolor</code></p>
<dl>
<dt>
<dd> Special statements for changing the background/page color. Currently, dvisvgm only supports the <code>background</code> statement as specified in the dvips manual (m[blue]<a rel="nofollow" href="https://tug.org/texinfohtml/dvips.html#Color-specificationsm[]">https://tug.org/texinfohtml/dvips.html#Color-specificationsm[]</a>). Since SVG 1.1 doesn&#8217;t support background colors, dvisvgm inserts a rectangle of the chosen color into the generated SVG document. This rectangle always gets the same size as the selected or computed bounding box. This background color command is part of the color special set but is handled separately in order to let the user turn it off.</dl>
<p> <code>color</code></p>
<dl>
<dt>
<dd> Statements of this command set provide instructions to change the text/paint color. For an overview of the exact syntax, see the documentation of dvips, for instance.</dl>
<p> <code>dvisvgm</code></p>
<dl>
<dt>
<dd> dvisvgm offers its own small set of specials. The following list gives a brief overview. </p>
<p> <code>dvisvgm:raw</code> <i>text</i></p>
<dl>
<dt>
<dd> Adds an arbitrary sequence of XML nodes to the page section of the SVG document. dvisvgm checks syntax and proper nesting of the inserted elements but does not perform any validation, thus the user has to ensure that the resulting SVG is still valid. Opening and closing tags may be distributed among different <i>raw</i> specials. The tags themselves can also be split but must be continued with the immediately following <i>raw</i> special. Both syntactically incorrect and wrongly nested tags lead to error messages. Parameter <i>text</i> may also contain the expressions <code>{?x}</code>, <code>{?y}</code>, <code>{?color}</code>, and <code>{?matrix}</code> that expand to the current <i>x</i> or <i>y</i> coordinate, the current color, and current transformation matrix, respectively. Character sequence <code>{?nl}</code> expands to a newline character. Finally, constructions of the form <code>{?(</code><i>expr</i><code>)}</code> enable the evaluation of mathematical expressions which may consist of basic arithmetic operations including modulo. Like above, the variables <i>x</i> and <i>y</i> represent the current coordinates. Example: <code>{?(-10*(x+2y)-5)}</code>.</dl>
<p> <code>dvisvgm:rawdef</code> <i>text</i></p>
<dl>
<dt>
<dd> This command is similar to <code>dvisvgm:raw</code>, but puts the XML nodes into the &lt;defs&gt; section of the SVG document currently being generated.</dl>
<p> <code>dvisvgm:rawset</code> <i>name</i> &#8230; <code>dvisvgm:endrawset</code></p>
<dl>
<dt>
<dd> This pair of specials marks the begin and end of a definition of a named raw SVG fragment. All <code>dvisvgm:raw</code> and <code>dvisvgm:rawdef</code> specials enclosed by <code>dvisvgm:rawset</code> and <code>dvisvgm:endrawset</code> are not evaluated immediately but stored together under the given <i>name</i> for later use. Once defined, the named fragment can be referenced throughout the DVI file by <code>dvisvgm:rawput</code> (see below). The two commands <code>dvisvgm:rawset</code> and <code>dvisvgm:endrawset</code> must not be nested, i.e. each call of <code>dvisvgm:rawset</code> has to be followed by a corresponding call of <code>dvisvgm:endrawset</code> before another <code>dvisvgm:rawset</code> may occur. Also, the identifier <i>name</i> must be unique throughout the DVI file. Using <code>dvisvgm:rawset</code> multiple times together with the same <i>name</i> leads to warning messages.</dl>
<p> <code>dvisvgm:rawput</code> <i>name</i></p>
<dl>
<dt>
<dd> Inserts raw SVG fragments previously stored under the given <i>name</i>. dvisvgm distinguishes between fragments that were specified with <code>dvisvgm:raw</code> or <code>dvisvgm:rawdef</code>, and handles them differently: It inserts all <code>dvisvgm:raw</code> parts every time <code>dvisvgm:rawput</code> is called, whereas the <code>dvisvgm:rawdef</code> portions go to the &lt;defs&gt; section of the current SVG document only once.</dl>
<p> <code>dvisvgm:img</code> <i>width</i> <i>height</i> <i>file</i></p>
<dl>
<dt>
<dd> Creates an image element at the current graphic position referencing the given file. JPEG, PNG, and SVG images can be used here. However, dvisvgm does not check the file format or the file name suffix. The lengths <i>width</i> and <i>height</i> can be given together with a unit specifier (see option <code>&#8211;bbox</code>) or as plain floating point numbers. In the latter case, TeX point units are assumed (1in = 72.27pt).</dl>
<p> <code>dvisvgm:bbox</code> lock</p>
<dl>
<dt>
<dd> Locks the bounding box of the current page and prevents it from further updating, i.e. graphics elements added after calling this special are not taken into account in determining the extent of the bounding box.</dl>
<p> <code>dvisvgm:bbox</code> unlock</p>
<dl>
<dt>
<dd> Unlocks the previously locked bounding box of the current page so that it gets updated again when adding graphics elements to the page.</dl>
<p> <code>dvisvgm:bbox</code> n[ew] <i>name</i></p>
<dl>
<dt>
<dd> Defines or resets a local bounding box called <i>name</i>. The name may consist of letters and digits. While processing a DVI page, dvisvgm continuously updates the (global) bounding box of the current page in order to determine the minimal rectangle containing all visible page components (characters, images, drawing elements etc.) Additionally to the global bounding box, the user can request an arbitrary number of named local bounding boxes. Once defined, these boxes are updated together with the global bounding box starting with the first character that follows the definition. Thus, the local boxes can be used to compute the extent of parts of the page. This is useful for scenarios where the generated SVG file is post-processed. In conjunction with special <code>dvisvgm:raw</code>, the macro <code>{?bbox </code><i>name</i><code>}</code> expands to the four values <i>x</i>, <i>y</i>, <i>w</i>, and <i>h</i> (separated by spaces) specifying the coordinates of the upper left corner, width, and height of the local box <i>name</i>. If box <i>name</i> wasn&#8217;t previously defined, all four values equal to zero.</dl>
<p> <code>dvisvgm:bbox</code> <i>width</i> <i>height</i> [<i>depth</i>] [<code>transform</code>]</p>
<dl>
<dt>
<dd> Updates the bounding box of the current page by embedding a virtual rectangle (<i>x</i>, <i>y</i>, <i>width</i>, <i>height</i>) where the lower left corner is located at the current DVI drawing position (<i>x</i>,<i>y</i>). If the optional parameter <i>depth</i> is specified, dvisvgm embeds a second rectangle (<i>x</i>, <i>y</i>, <i>width</i>, &#8211;<i>depth</i>). The lengths <i>width</i>, <i>height</i>, and <i>depth</i> can be given together with a unit specifier (see option <code>&#8211;bbox</code>) or as plain floating point numbers. In the latter case, TeX point units are assumed (1in = 72.27pt). Depending on size and position of the virtual rectangle, this command either enlarges the overall bounding box or leaves it as is. It&#8217;s not possible to reduce its extent. This special should be used together with <code>dvisvgm:raw</code> in order to update the viewport of the page properly. By default, the box extents are assigned unchanged and, in particular, are not altered by transformation commands. In order to apply the current transformation matrix, the optional modifier <code>transform</code> can be added at the end of the special statement.</dl>
<p> <code>dvisvgm:bbox</code> a[bs] <i>x1</i> <i>y1</i> <i>x2</i> <i>y2</i> [<code>transform</code>]</p>
<dl>
<dt>
<dd> This variant of the bbox special updates the bounding box by embedding a virtual rectangle (<i>x1</i>,<i>y1</i>,<i>x2</i>,<i>y2</i>). The points (<i>x1</i>,<i>y1</i>) and (<i>x2</i>,<i>y2</i>) denote the absolute coordinates of two diagonal corners of the rectangle. As with the relative special variant described above, the optional modifier <code>transform</code> allows for applying the current transformation matrix to the bounding box.</dl>
<p> <code>dvisvgm:bbox</code> f[ix] <i>x1</i> <i>y1</i> <i>x2</i> <i>y2</i> [<code>transform</code>]</p>
<dl>
<dt>
<dd> This variant of the bbox special assigns an absolute (final) bounding box to the resulting SVG. After executing this command, dvisvgm doesn&#8217;t further alter the bounding box coordinates, except this special is called again later. The points (<i>x1</i>,<i>y1</i>) and (<i>x2</i>,<i>y2</i>) denote the absolute coordinates of two diagonal corners of the rectangle. As with the relative special variant described above, the optional modifier <code>transform</code> allows for applying the current transformation matrix to the bounding box. </p>
<p> The following TeX snippet adds two raw SVG elements to the output and updates the bounding box accordingly: </p>
<dl>
<dt>
<dd>
<pre><code>
\special{dvisvgm : raw&lt;circle cx = '{?x}' cy = '{?y}' r = '10' stroke = 'black' fill = 'red' /&gt;} %
\special{dvisvgm : bbox 10bp 10bp 10bp transform} %
\special
{
dvisvgm:
    bbox - 10bp 10bp 10bp transform
}
\special{dvisvgm : raw&lt;path d = 'M50 200 L10 250 H100 Z' stroke = 'black' fill = 'blue' /&gt;} %
\special
{
dvisvgm:
    bbox abs 10bp 200bp 100bp 250bp transform
}
</code></pre>
</dl>
</dl>
</dl>
<p> <code>em</code></p>
<dl>
<dt>
<dd> These specials were introduced with the <i>emTeX</i> distribution by Eberhard Mattes. They provide line drawing statements, instructions for embedding MSP, PCX, and BMP image files, as well as two PCL commands. dvisvgm supports only the line drawing statements and ignores all other em specials silently. A description of the command syntax can be found in the DVI driver documentation coming with emTeX (m[blue]<a rel="nofollow" href="https://ctan.org/pkg/emtexm[]">https://ctan.org/pkg/emtexm[]</a>).</dl>
<p> <code>html</code></p>
<dl>
<dt>
<dd> The hyperref specification defines several variants on how to mark hyperlinked areas in a DVI file. dvisvgm supports the plain HyperTeX special constructs as created with hyperref package option <i>hypertex</i>. By default, all linked areas of the document are marked by a rectangle. Option <code>&#8211;linkmark</code> allows you to change this behavior. See above for further details. Information on syntax and semantics of the HyperTeX specials can be found in the hyperref manual (m[blue]<a rel="nofollow" href="https://ctan.org/pkg/hyperrefm[]">https://ctan.org/pkg/hyperrefm[]</a>).</dl>
<p> <code>papersize</code></p>
<dl>
<dt>
<dd> The <i>papersize</i> special, which is an extension introduced by dvips, can be used to specify the widths and heights of the pages in the DVI file. It affects the page it appears on as well as all following pages until another papersize special is found. If there is more than one papersize special present on a page, dvisvgm applies the last one. However, in order to stay compatible with previous versions of dvisvgm that did not evaluate these specials, their processing must be explicitly enabled by adding option <code>&#8211;bbox=papersize</code> on the command-line. Otherwise, dvisvgm ignores them and computes tight bounding boxes.</dl>
<p> <code>pdf</code></p>
<dl>
<dt>
<dd> pdfTeX and dvipdfmx introduced several special commands related to the generation of PDF files. Currently, only <i>pdf:mapfile</i>, <i>pdf:mapline</i>, <i>pdf:pagesize</i>, and PDF hyperlink specials are supported by dvisvgm. The latter are the PDF pendants to the HTML HyperTeX specials generated by the hyperref package in PDF mode. </p>
<p> <i>pdf:pagesize</i> is similar to the <i>papersize</i> special (see above) which specifies the size of the current and all following pages. In order to actually apply the extents to the generated SVG files, option <code>&#8211;bbox=papersize</code> must be given. </p>
<p> <i>pdf:mapfile</i> and <i>pdf:mapline</i> allow for modifying the font map tree while processing the DVI file. They are used by CTeX, for example. dvisvgm supports both, the dvips and dvipdfm font map format. For further information on the command syntax and semantics, see the documentation of <code>\pdfmapfile</code> in the pdfTeX user manual (m[blue]<a rel="nofollow" href="https://ctan.org/pkg/pdftexm[]">https://ctan.org/pkg/pdftexm[]</a>).</dl>
<p> <code>ps</code></p>
<dl>
<dt>
<dd> The famous DVI driver <i>dvips</i> (m[blue]<a rel="nofollow" href="https://www.tug.org/texinfohtml/dvips.htmlm[])">https://www.tug.org/texinfohtml/dvips.htmlm[])</a> introduced its own set of specials in order to embed PostScript code into DVI files, which greatly improves the capabilities of DVI documents. One aim of dvisvgm is to completely evaluate all PostScript fragments and to convert as many of them as possible to SVG. In contrast to dvips, dvisvgm uses floating point arithmetics to compute the precise position of each graphic element, i.e. it doesn&#8217;t round the coordinates. Therefore, the relative locations of the graphic elements may slightly differ from those computed by dvips. </p>
<p> Since PostScript is a rather complex language, dvisvgm does not implement its own PostScript interpreter but relies on Ghostscript (m[blue]<a rel="nofollow" href="https://ghostscript.comm[])">https://ghostscript.comm[])</a> instead. If the Ghostscript library was not linked to the dvisvgm binary, it is looked up and loaded dynamically during runtime. In this case, dvisvgm looks for <i>libgs.so.X</i> on Unix-like systems (supported ABI versions: 7,8,9), for <i>libgs.X.dylib</i> on macOS, and for <i>gsdll32.dll</i> or <i>gsdll64.dll</i> on Windows. You can override the default file names with environment variable <code>LIBGS</code> or the command-line option <code>&#8211;libgs</code>. The library must be reachable through the ld search path (*nix) or the PATH environment variable (Windows). Alternatively, the absolute file path can be specified. If the library cannot be found, dvisvgm disables the processing of PostScript specials and prints a warning message. Use option <code>&#8211;list-specials</code> to check whether PostScript support is available, i.e. entry <i>ps</i> is present. </p>
<p> The PostScript handler also recognizes and evaluates bounding box data generated by the preview package (m[blue]<a rel="nofollow" href="https://ctan.org/pkg/previewm[])">https://ctan.org/pkg/previewm[])</a> with option <i>tightpage</i>. If such data is present in the DVI file and if dvisvgm is called with option <code>&#8211;bbox=preview</code>, dvisvgm sets the width and total height of the SVG file to the values derived from the preview data. Additionally, it prints a message showing the width, height, and depth of the box in TeX point units to the console. Especially, the depth value can be read by a post-processor to vertically align the SVG graphics with the baseline of surrounding text in HTML or XSL-FO documents, for example. Please note that SVG bounding boxes are defined by a width and (total) height. In contrast to TeX, SVG provides no means to differentiate between height and depth, i.e. the vertical extents above and below the baseline, respectively. Therefore, it is generally not possible to retrieve the depth value from the SVG file itself. </p>
<p> If you call dvisvgm with option <code>&#8211;bbox=min</code> (the default) and preview data is present in the DVI file, dvisvgm doesn&#8217;t apply the preview extents but computes a bounding box that tightly encloses the page contents. The height, depth and width values written to console are adapted accordingly.</dl>
<p> <code>tpic</code></p>
<dl>
<dt>
<dd> The TPIC special set defines instructions for drawing simple geometric objects. Some LaTeX packages, like eepic and tplot, use these specials to describe graphics.</dl>

<h2>ENVIRONMENT</h2>
<p> dvisvgm uses the <code>kpathsea</code> library for locating the files that it opens. Hence, the environment variables described in the library&#8217;s documentation influence the converter. </p>
<p> If dvisvgm was linked without the Ghostscript library, and if PostScript support has not been disabled, the shared Ghostscript library is looked up during runtime via dlopen(). The environment variable <code>LIBGS</code> can be used to specify path and file name of the library. </p>
<p> The pre-compiled Windows versions of dvisvgm require a working installation of MiKTeX 2.9 or above. dvisvgm does not work together with the portable edition of MiKTeX because it relies on MiKTeX&#8217;s COM interface that is only accessible in a local installation. To enable the evaluation of PostScript specials, the original Ghostscript DLL <i>gsdll32.dll</i> must be present and reachable through the search path. 64-bit Windows builds require the 64-bit Ghostscript DLL <i>gsdll64.dll</i>. Both DLLs come with the corresponding Ghostscript installers available from m[blue]<code><a rel="nofollow" href="https://ghostscript.com">https://ghostscript.com</a></code>m[]. </p>
<p> The environment variable <code>DVISVGM_COLORS</code> specifies the colors used to highlight various parts of dvisvgm&#8217;s message output. It is only evaluated if option <code>&#8211;color</code> is given. The value of <code>DVISVGM_COLORS</code> is a list of colon-separated entries of the form <i>gg</i>=<i>BF</i>, where <i>gg</i> denotes one of the color group indicators listed below, and <i>BF</i> are two hexadecimal digits specifying the background (first digit) and foreground/text color (second digit). The color values are defined as follows: 0=black, 1=red, 2=green, 3=yellow, 4=blue, 5=magenta, 6=cyan, 7=gray, 8=bright red, 9=bright green, A=bright yellow, B=bright blue, C=bright magenta, D=bright cyan, E=bright gray, F=white. Depending on the terminal, the colors may differ. Rather than changing both the text and background color, it&#8217;s also possible to change only one of them: An asterisk (*) in place of a hexadecimal digit indicates the default text or background color of the terminal. </p>
<p> All malformed entries in the list are silently ignored. </p>
