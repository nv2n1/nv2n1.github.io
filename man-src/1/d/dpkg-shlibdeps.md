<h2 class="name">NAME</h2>
<p> dpkg-shlibdeps &#8211; generate shared library substvar dependencies </p>
<h2>SYNOPSIS</h2>
<p> <code>dpkg-shlibdeps</code> [<i>option</i>&#8230;] [<code>-e</code>] <i>executable</i> [<i>option</i>&#8230;]</p>
<h2>DESCRIPTION</h2>
<p> <code>dpkg-shlibdeps</code> calculates shared library dependencies for executables named in its arguments. The dependencies are added to the substitution variables file <code>debian/substvars</code> as variable names <code>shlibs:</code><i>dependency-field</i> where <i>dependency-field</i> is a dependency field name. Any other variables starting with <code>shlibs:</code> are removed from the file. </p>
<p> <code>dpkg-shlibdeps</code> has two possible sources of information to generate dependency information. Either <i>symbols</i> files or <i>shlibs</i> files. For each binary that <code>dpkg-shlibdeps</code> analyzes, it finds out the list of libraries that it&#8217;s linked with. Then, for each library, it looks up either the <i>symbols</i> file, or the <i>shlibs</i> file (if the former doesn&#8217;t exist or if debian/shlibs.local contains the relevant dependency). Both files are supposed to be provided by the library package and should thus be available as /var/lib/dpkg/info/<i>package</i>.<i>symbols</i> or /var/lib/dpkg/info/<i>package</i>.<i>shlibs</i>. The package name is identified in two steps: find the library file on the system (looking in the same directories that <code>ld.so</code> would use), then use <code>dpkg -S</code> <i>library-file</i> to lookup the package providing the library.</p>
<h3>Symbols files</h3>
<p> Symbols files contain finer-grained dependency information by providing the minimum dependency for each symbol that the library exports. The script tries to find a symbols file associated to a library package in the following places (first match is used):</p>
<dl>
<dt>debian/*/DEBIAN/symbols</p>
<dd> Shared library information generated by the current build process that also invoked <code>dpkg-shlibdeps</code>. They are generated by <code><a href="/docs/linux/man/1-dpkg-gensymbols/">dpkg-gensymbols</a></code>(1). They are only used if the library is found in a package&#8217;s build tree. The symbols file in that build tree takes precedence over symbols files from other binary packages.</p>
<dt>/etc/dpkg/symbols/<i>package</i>.symbols.<i>arch</i></p>
<dd>
<dt>/etc/dpkg/symbols/<i>package</i>.symbols</p>
<dd> Per-system overriding shared library dependency information. <i>arch</i> is the architecture of the current system (obtained by <code>dpkg-architecture -qDEB_HOST_ARCH</code>).</p>
<dt>Output from &#8220;<code>dpkg-query &#8211;control-path</code> <i>package</i> symbols&#8221;</p>
<dd> Package-provided shared library dependency information. Unless overridden by <code>&#8211;admindir</code>, those files are located in /var/lib/dpkg.</dl>
<p> While scanning the symbols used by all binaries, <code>dpkg-shlibdeps</code> remembers the (biggest) minimal version needed for each library. At the end of the process, it is able to write out the minimal dependency for every library used (provided that the information of the <i>symbols</i> files are accurate). </p>
<p> As a safe-guard measure, a symbols file can provide a <code>Build-Depends-Package</code> meta-information field and <code>dpkg-shlibdeps</code> will extract the minimal version required by the corresponding package in the <code>Build-Depends</code> field and use this version if it&#8217;s higher than the minimal version computed by scanning symbols.</p>
<h3>Shlibs files</h3>
<p> Shlibs files associate directly a library to a dependency (without looking at the symbols). It&#8217;s thus often stronger than really needed but very safe and easy to handle. </p>
<p> The dependencies for a library are looked up in several places. The first file providing information for the library of interest is used:</p>
<dl>
<dt>debian/shlibs.local</p>
<dd> Package-local overriding shared library dependency information.</p>
<dt>/etc/dpkg/shlibs.override</p>
<dd> Per-system overriding shared library dependency information.</p>
<dt>debian/*/DEBIAN/shlibs</p>
<dd> Shared library information generated by the current build process that also invoked <code>dpkg-shlibdeps</code>. They are only used if the library is found in a package&#8217;s build tree. The shlibs file in that build tree takes precedence over shlibs files from other binary packages.</p>
<dt>Output from &#8220;<code>dpkg-query &#8211;control-path</code> <i>package</i> shlibs&#8221;</p>
<dd> Package-provided shared library dependency information. Unless overridden by <code>&#8211;admindir</code>, those files are located in /var/lib/dpkg.</p>
<dt>/etc/dpkg/shlibs.default</p>
<dd> Per-system default shared library dependency information.</dl>
<p> The extracted dependencies are then directly used (except if they are filtered out because they have been identified as duplicate, or as weaker than another dependency).</p>
<h2>OPTIONS</h2>
<p> <code>dpkg-shlibdeps</code> interprets non-option arguments as executable names, just as if they&#8217;d been supplied as <code>-e</code><i>executable</i>.</p>
<dl>
<dt><code>-e</code><i>executable</i></p>
<dd> Include dependencies appropriate for the shared libraries required by <i>executable</i>. This option can be used multiple times.</p>
<dt><code>-l</code><i>directory</i></p>
<dd> Prepend <i>directory</i> to the list of directories to search for private shared libraries (since dpkg 1.17.0). This option can be used multiple times. </p>
<p> <code>Note:</code> Use this option instead of setting <font SIZE="-1"><code>LD_LIBRARY_PATH</code></font>, as that environment variable is used to control the run-time linker and abusing it to set the shared library paths at build-time can be problematic when cross-compiling for example.</p>
<dt><code>-d</code><i>dependency-field</i></p>
<dd> Add dependencies to be added to the control file dependency field <i>dependency-field</i>. (The dependencies for this field are placed in the variable <code>shlibs:</code><i>dependency-field</i>.) </p>
<p> The <code>-d</code><i>dependency-field</i> option takes effect for all executables after the option, until the next <code>-d</code><i>dependency-field</i>. The default <i>dependency-field</i> is <code>Depends</code>. </p>
<p> If the same dependency entry (or set of alternatives) appears in more than one of the recognized dependency field names <code>Pre-Depends</code>, <code>Depends</code>, <code>Recommends</code>, <code>Enhances</code> or <code>Suggests</code> then <code>dpkg-shlibdeps</code> will automatically remove the dependency from all fields except the one representing the most important dependencies.</p>
<dt><code>-p</code><i>varname-prefix</i></p>
<dd> Start substitution variables with <i>varname-prefix</i><code>:</code> instead of <code>shlibs:</code>. Likewise, any existing substitution variables starting with <i>varname-prefix</i><code>:</code> (rather than <code>shlibs:</code>) are removed from the substitution variables file.</p>
<dt><code>-O</code>[<i>filename</i>]</p>
<dd> Print substitution variable settings to standard output (or <i>filename</i> if specified, since dpkg 1.17.2), rather than being added to the substitution variables file (<code>debian/substvars</code> by default).</p>
<dt><code>-t</code><i>type</i></p>
<dd> Prefer shared library dependency information tagged for the given package type. If no tagged information is available, falls back to untagged information. The default package type is <code>deb</code>. Shared library dependency information is tagged for a given type by prefixing it with the name of the type, a colon, and whitespace.</p>
<dt><code>-L</code><i>local-shlibs-file</i></p>
<dd> Read overriding shared library dependency information from <i>local-shlibs-file</i> instead of <code>debian/shlibs.local</code>.</p>
<dt><code>-T</code><i>substvars-file</i></p>
<dd> Write substitution variables in <i>substvars-file</i>; the default is <code>debian/substvars</code>.</p>
<dt><code>-v</code></p>
<dd> Enable verbose mode (since dpkg 1.14.8). Numerous messages are displayed to explain what <code>dpkg-shlibdeps</code> does.</p>
<dt><code>-x</code><i>package</i></p>
<dd> Exclude the package from the generated dependencies (since dpkg 1.14.8). This is useful to avoid self-dependencies for packages which provide <font SIZE="-1">ELF</font> binaries (executables or library plugins) using a library contained in the same package. This option can be used multiple times to exclude several packages.</p>
<dt><code>-S</code><i>package-build-dir</i></p>
<dd> Look into <i>package-build-dir</i> first when trying to find a library (since dpkg 1.14.15). This is useful when the source package builds multiple flavors of the same library and you want to ensure that you get the dependency from a given binary package. You can use this option multiple times: directories will be tried in the same order before directories of other binary packages.</p>
<dt><code>-I</code><i>package-build-dir</i></p>
<dd> Ignore <i>package-build-dir</i> when looking for shlibs, symbols, and shared library files (since dpkg 1.18.5). You can use this option multiple times.</p>
<dt><code>&#8211;ignore-missing-info</code></p>
<dd> Do not fail if dependency information can&#8217;t be found for a shared library (since dpkg 1.14.8). Usage of this option is discouraged, all libraries should provide dependency information (either with shlibs files, or with symbols files) even if they are not yet used by other packages.</p>
<dt><code>&#8211;warnings=</code><i>value</i></p>
<dd> <i>value</i> is a bit field defining the set of warnings that can be emitted by <code>dpkg-shlibdeps</code> (since dpkg 1.14.17). Bit 0 (value=1) enables the warning &#8220;symbol <i>sym</i> used by <i>binary</i> found in none of the libraries&#8221;, bit 1 (value=2) enables the warning &#8220;package could avoid a useless dependency&#8221; and bit 2 (value=4) enables the warning &#8220;<i>binary</i> should not be linked against <i>library</i>&#8220;. The default <i>value</i> is 3: the first two warnings are active by default, the last one is not. Set <i>value</i> to 7 if you want all warnings to be active.</p>
<dt><code>&#8211;admindir=</code><i>dir</i></p>
<dd> Change the location of the <code>dpkg</code> database (since dpkg 1.14.0). The default location is <i>/var/lib/dpkg</i>.</p>
<dt><code>-?</code>, <code>&#8211;help</code></p>
<dd> Show the usage message and exit.</p>
<dt><code>&#8211;version</code></p>
<dd> Show the version and exit.</dl>
<h2>ENVIRONMENT</h2>
<dl>
<dt><font SIZE="-1"><code>DPKG_COLORS</code></font></p>
<dd> Sets the color mode (since dpkg 1.18.5). The currently accepted values are: <code>auto</code> (default), <code>always</code> and <code>never</code>.</p>
<dt><font SIZE="-1"><code>DPKG_NLS</code></font></p>
<dd> If set, it will be used to decide whether to activate Native Language Support, also known as internationalization (or i18n) support (since dpkg 1.19.0). The accepted values are: <code>0</code> and <code>1</code> (default).</dl>
<h2>DIAGNOSTICS</h2>
<h3>Warnings</h3>
<p> Since <code>dpkg-shlibdeps</code> analyzes the set of symbols used by each binary of the generated package, it is able to emit warnings in several cases. They inform you of things that can be improved in the package. In most cases, those improvements concern the upstream sources directly. By order of decreasing importance, here are the various warnings that you can encounter:</p>
<dl>
<dt><code>symbol</code> <i>sym</i> <code>used by</code> <i>binary</i> <code>found in none of the libraries.</code></p>
<dd> The indicated symbol has not been found in the libraries linked with the binary. The <i>binary</i> is most likely a library and it needs to be linked with an additional library during the build process (option <code>-l</code><i>library</i> of the linker).</p>
<dt><i>binary</i> <code>contains an unresolvable reference to symbol</code> <i>sym</i><code>: it&#8217;s probably a plugin</code></p>
<dd> The indicated symbol has not been found in the libraries linked with the binary. The <i>binary</i> is most likely a plugin and the symbol is probably provided by the program that loads this plugin. In theory a plugin doesn&#8217;t have any <font SIZE="-1">SONAME</font> but this binary does have one and as such it could not be clearly identified as such. However the fact that the binary is stored in a non-public directory is a strong indication that&#8217;s it&#8217;s not a normal shared library. If the binary is really a plugin, then disregard this warning. But there&#8217;s always the possibility that it&#8217;s a real library and that programs linking to it are using an <font SIZE="-1">RPATH</font> so that the dynamic loader finds it. In that case, the library is broken and needs to be fixed.</p>
<dt><code>package could avoid a useless dependency if</code> <i>binary</i> <code>was not linked against</code> <i>library</i> <code>(it uses none of the library&#8217;s symbols)</code></p>
<dd> None of the <i>binaries</i> that are linked with <i>library</i> use any of the symbols provided by the library. By fixing all the binaries, you would avoid the dependency associated to this library (unless the same dependency is also generated by another library that is really used).</p>
<dt><code>package could avoid a useless dependency if</code> <i>binaries</i> <code>were not linked against</code> <i>library</i> <code>(they use none of the library&#8217;s symbols)</code></p>
<dd> Exactly the same as the above warning, but for multiple binaries.</p>
<dt><i>binary</i> <code>should not be linked against</code> <i>library</i> <code>(it uses none of the library&#8217;s symbols)</code></p>
<dd> The <i>binary</i> is linked to a library that it doesn&#8217;t need. It&#8217;s not a problem but some small performance improvements in binary load time can be obtained by not linking this library to this binary. This warning checks the same information as the previous one but does it for each binary instead of doing the check globally on all binaries analyzed.</dl>
<h3>Errors</h3>
<p> <code>dpkg-shlibdeps</code> will fail if it can&#8217;t find a public library used by a binary or if this library has no associated dependency information (either shlibs file or symbols file). A public library has a <font SIZE="-1">SONAME</font> and is versioned (libsomething.so.<i>X</i>). A private library (like a plugin) should not have a <font SIZE="-1">SONAME</font> and doesn&#8217;t need to be versioned.</p>
<dl>
<dt><code>couldn&#8217;t find library</code> <i>library-soname</i> <code>needed by</code> <i>binary</i> <code>(its </code><font SIZE="-1"><code>RPATH</code></font><code> is &#8216;</code><i>rpath</i><code>&#8216;)</code></p>
<dd> The <i>binary</i> uses a library called <i>library-soname</i> but <code>dpkg-shlibdeps</code> has been unable to find the library. <code>dpkg-shlibdeps</code> creates a list of directories to check as following: directories listed in the <font SIZE="-1">RPATH</font> of the binary, directories added by the <code>-l</code> option, directories listed in the <font SIZE="-1"><code>LD_LIBRARY_PATH</code></font> environment variable, cross multiarch directories (ex. /lib/arm64-linux-gnu, /usr/lib/arm64-linux-gnu), standard public directories (/lib, /usr/lib), directories listed in /etc/ld.so.conf, and obsolete multilib directories (/lib32, /usr/lib32, /lib64, /usr/lib64). Then it checks those directories in the package&#8217;s build tree of the binary being analyzed, in the packages&#8217; build trees indicated with the <code>-S</code> command-line option, in other packages&#8217; build trees that contains a DEBIAN/shlibs or DEBIAN/symbols file and finally in the root directory. If the library is not found in any of those directories, then you get this error. </p>
<p> If the library not found is in a private directory of the same package, then you want to add the directory with <code>-l</code>. If it&#8217;s in another binary package being built, you want to make sure that the shlibs/symbols file of this package is already created and that <code>-l</code> contains the appropriate directory if it also is in a private directory.</p>
<dt><code>no dependency information found for</code> <i>library-file</i> <code>(used by</code> <i>binary</i><code>).</code></p>
<dd> The library needed by <i>binary</i> has been found by <code>dpkg-shlibdeps</code> in <i>library-file</i> but <code>dpkg-shlibdeps</code> has been unable to find any dependency information for that library. To find out the dependency, it has tried to map the library to a Debian package with the help of <code>dpkg -S</code> <i>library-file</i>. Then it checked the corresponding shlibs and symbols files in /var/lib/dpkg/info/, and in the various package&#8217;s build trees (debian/*/DEBIAN/). </p>
<p> This failure can be caused by a bad or missing shlibs or symbols file in the package of the library. It might also happen if the library is built within the same source package and if the shlibs files has not yet been created (in which case you must fix debian/rules to create the shlibs before calling <code>dpkg-shlibdeps</code>). Bad <font SIZE="-1">RPATH</font> can also lead to the library being found under a non-canonical name (example: /usr/lib/openoffice.org/../lib/libssl.so.0.9.8 instead of /usr/lib/libssl.so.0.9.8) that&#8217;s not associated to any package, <code>dpkg-shlibdeps</code> tries to work around this by trying to fallback on a canonical name (using <code><a href="/docs/linux/man/3-realpath/">realpath</a></code>(3)) but it might not always work. It&#8217;s always best to clean up the <font SIZE="-1">RPATH</font> of the binary to avoid problems. </p>
<p> Calling <code>dpkg-shlibdeps</code> in verbose mode (<code>-v</code>) will provide much more information about where it tried to find the dependency information. This might be useful if you don&#8217;t understand why it&#8217;s giving you this error.</dl>
