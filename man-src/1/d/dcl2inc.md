<h2 class="name">NAME</h2>
<p> dcl2inc &#8211; postprocess ftnchek .dcl files to create separate INCLUDE files </p>
<h2>SYNOPSIS</h2>
<p> <code>dcl2inc</code> <i>*.dcl</i></p>
<h2>DESCRIPTION</h2>
<p> <code>dcl2inc</code> postprocessing declaration files output by <code><a href="/docs/linux/man/1-ftnchek/">ftnchek</a></code>(1), replacing unique COMMON block definitions by Fortran <i>INCLUDE</i> statements. For each input <i>.dcl</i> file, a modified output <i>.dcn</i> file is produced, together with include files named by the COMMON block name, with filename extension <i>.inc</i>. </p>
<p> In addition, <code>dcl2inc</code> produces on <i>stdout</i> a list of <i>Makefile</i> dependencies for the UNIX <code><a href="/docs/linux/man/1-make/">make</a></code>(1) utility. These can be appended to the project <i>Makefile</i> to ensure that any subsequent changes to <i>.inc</i> files provoke recompilation of source files that include them. </p>
<p> <code>dcl2inc</code> warns about COMMONs which differ from their first occurrence, and simply copies them to the output <i>.dcn</i> file, instead of replacing them with an INCLUDE statement. Thus, any COMMON statements that are found in the output <i>.dcn</i> files should be examined carefully to determine why they differ: they may well be in error. </p>
<p> Replication of identical data, and bugs arising from subsequent modification of only part of it, is a significant reason why Fortran programming projects should <i>require</i> that COMMON declarations occur in separate include files, so that there is only a <i>single</i> point of definition of any global object. </p>
<p> Even though the Fortran <i>INCLUDE</i> statement was tragically omitted from the 1977 Standard, it has long been implemented by virtually all compiler vendors, and is part of the 1990 Standard. In practice, there is therefore no portability problem associated with use of INCLUDE statements, <i>provided</i> that one avoids nonportable file names. As long as the code obeys Fortran&#8217;s limit of six-character alphanumeric names, the filenames generated by <code>dcl2inc</code> will be acceptable on all current popular operating systems. </p>
<p> Fortran&#8217;s default, or IMPLICIT, variable typing is deprecated in modern programming languages, because it encourages sloppy documentation, and worse, bugs due to misspelled variables, or variables that have been truncated because they extend past column 72. If all variables used are explicitly typed, and a compiler option is used to reject all program units with untyped variables, variable spelling and truncation errors can be eliminated. </p>
<p> Variable declarations that have been produced automatically by a tool like <code><a href="/docs/linux/man/1-ftnchek/">ftnchek</a></code>(1) or <code><a href="/docs/linux/man/1-pfort/">pfort</a></code>(1) have a consistent format that facilitates application of stream editors (e.g. to change array dimensions or rename variables), and simple floating-point precision conversion tools like <code><a href="/docs/linux/man/1-d2s/">d2s</a></code>(1), <code><a href="/docs/linux/man/1-dtoq/">dtoq</a></code>(1), <code><a href="/docs/linux/man/1-dtos/">dtos</a></code>(1), <code><a href="/docs/linux/man/1-qtod/">qtod</a></code>(1), <code><a href="/docs/linux/man/1-s2d/">s2d</a></code>(1), and <code><a href="/docs/linux/man/1-stod/">stod</a></code>(1).</p>
<h2>CAVEAT</h2>
<p> The current version (2.9) of <code><a href="/docs/linux/man/1-ftnchek/">ftnchek</a></code>(1) does not produce Fortran EQUIVALENCE statements in <i>.dcl</i> files, so you must be careful to preserve them when replacing original declarations with new ones from <i>.dcl</i> or <i>.dcn</i> files.</p>
