<h2 class="name">NAME</h2>
<p> burst &#8211; explode digests into messages </p>
<h2>SYNOPSIS</h2>
<dl>
<dt> <code>burst</code> [<i>+folder</i>] [<i>msgs</i>] [<code>-inplace</code> | <code>-noinplace</code>] [<code>-mime</code> | <code>-nomime</code>] [<code>-automime</code>] [<code>-quiet</code> | <code>-noquiet</code>] [<code>-verbose</code> | <code>-noverbose</code>] [<code>-version</code>] [<code>-help</code>]</dl>
<h2>DESCRIPTION</h2>
<p> <code>Burst</code></p>
<dd>considers the specified messages in the named folder to be Internet digests, and explodes them in that folder. </p>
<p> If <code>-inplace</code> is given, each digest is replaced by the &#8220;table of contents&#8221; for the digest (the original digest is removed). <code>Burst</code> then renumbers all of the messages following the digest in the folder to make room for each of the messages contained within the digest. These messages are placed immediately after the digest. </p>
<p> If <code>-noinplace</code> is given, each digest is preserved, no table of contents is produced, and the messages contained within the digest are placed at the end of the folder. Other messages are not tampered with in any way. </p>
<p> If <code>-automime</code> is given, <code>burst</code> will try to determine if the message is formatted with MIME and contains MIME parts of type &#8220;message/rfc822&#8221;. If it does, it will burst the message using MIME formatting rules. The <code>-mime</code> switch can be used to enforce the use of MIME formatting. The <code>-nomime</code> switch will force <code>burst</code> to use RFC 934 rules. </p>
<p> The <code>-quiet</code> switch directs <code>burst</code> to be silent about reporting messages that are not in digest format. </p>
<p> The <code>-verbose</code> switch directs <code>burst</code> to tell the user the general actions that it is taking to explode the digest. </p>
<p> It turns out that <code>burst</code> works equally well on forwarded messages and blind-carbon-copies as on Internet digests, provided that the former two were generated by <code>forw</code> or <code>send</code>.</p>

<h2>CONTEXT</h2>
<p> If a folder is given, it will become the current folder. If <code>-inplace</code> is given, then the first message burst becomes the current message. This leaves the context ready for a <code>show</code> of the table of contents of the digest, and a <code>next</code> to see the first message of the digest. If <code>-noinplace</code> is given, then the first message extracted from the first digest burst becomes the current message. This leaves the context in a similar, but not identical, state to the context achieved when using <code>-inplace</code>.</p>
<h2>BUGS</h2>
<p> The <code>burst</code> program enforces a limit on the number of messages which may be <code>burst</code> from a single message. This number is on the order of 1000 messages. There is usually no limit on the number of messages which may reside in the folder after the <code>burst</code>ing. </p>
<p> Although <code>burst</code> uses a sophisticated algorithm to determine where one encapsulated message ends and another begins, not all digestifying programs use an encapsulation algorithm. In degenerate cases, this usually results in <code>burst</code> finding an encapsulation boundary prematurely and splitting a single encapsulated message into two or more messages. These erroneous digestifying programs should be fixed. </p>
<p> Furthermore, any text which appears after the last encapsulated message is not placed in a separate message by <code>burst</code>. In the case of digestified messages, this text is usually an &#8220;End of digest&#8221; string. As a result of this possibly un-friendly behavior on the part of <code>burst</code>, note that when the <code>-inplace</code> option is used, this trailing information is lost. In practice, this is not a problem since correspondents usually place remarks in text prior to the first encapsulated message, and this information is not lost. </p>
