<h2 class="name">NAME</h2>
<p> bootctl &#8211; Control EFI firmware boot settings and manage boot loader </p>
<h2>SYNOPSIS</h2>
<dl>
<dt> <code>bootctl</code> [OPTIONS&#8230;] {COMMAND}</dl>
<h2>DESCRIPTION</h2>
<p> <code>bootctl</code></p>
<dd>can check the EFI firmware and boot loader status, list and manage available boot loaders and boot loader entries, and install, update, or remove the <code><a href="/docs/linux/man/7-systemd-boot/">systemd-boot</a></code>(7) boot loader on the current system.</p>
<h2>GENERIC EFI FIRMWARE/BOOT LOADER COMMANDS</h2>
<p> These commands are available on any EFI system, regardless of the boot loader used. </p>
<p> <code>status</code></p>
<dl>
<dt>
<dd> Shows brief information about the system firmware, the boot loader that was used to boot the system, the boot loaders currently available in the ESP, the boot loaders listed in the firmware&#8217;s list of boot loaders and the current default boot loader entry. If no command is specified, this is the implied default.</dl>
<p> <code>reboot-to-firmware</code> [<i>BOOL</i>]</p>
<dl>
<dt>
<dd> Query or set the &quot;Reboot-Into-Firmware-Setup&quot; flag of the EFI firmware. Takes a boolean argument which controls whether to show the firmware setup on next system reboot. If the argument is omitted shows the current status of the flag, or whether the flag is supported. This controls the same flag as <code>systemctl reboot &#8211;firmware-setup</code>, but is more low-level and allows setting the flag independently from actually requesting a reboot.</dl>
<p> <code>systemd-efi-options</code> [<i>STRING</i>]</p>
<dl>
<dt>
<dd> When called without the optional argument, prints the current value of the &quot;SystemdOptions&quot; EFI variable. When called with an argument, sets the variable to that value. See <code><a href="/docs/linux/man/1-systemd/">systemd</a></code>(1) for the meaning of that variable.</dl>
<h2>BOOT LOADER SPECIFICATION COMMANDS</h2>
<p> These commands are available for all boot loaders that implement the m[blue]<code>Boot Loader Specification</code>m[]<font SIZE="-2">[1]</font> and/or the m[blue]<code>Boot Loader Interface</code>m[]<font SIZE="-2">[2]</font>, such as <code>systemd-boot</code>. </p>
<p> <code>list</code></p>
<dl>
<dt>
<dd> Shows all available boot loader entries implementing the m[blue]<code>Boot Loader Specification</code>m[]<font SIZE="-2">[1]</font>, as well as any other entries discovered or automatically generated by a boot loader implementing the m[blue]<code>Boot Loader Interface</code>m[]<font SIZE="-2">[2]</font>.</dl>
<p> <code>set-default</code> <i>ID</i>, <code>set-oneshot</code> <i>ID</i></p>
<dl>
<dt>
<dd> Sets the default boot loader entry. Takes a single boot loader entry ID string as argument. The <code>set-oneshot</code> command will set the default entry only for the next boot, the <code>set-default</code> will set it persistently for all future boots. Optionally, the boot loader entry ID may be specified as one of: <code>@default</code>, <code>@oneshot</code> or <code>@current</code>, which correspond to the current default boot loader entry for all future boots, the current default boot loader entry for the next boot, and the currently booted boot loader entry. These special IDs are resolved to the current values of the EFI variables <i>LoaderEntryDefault</i>, <i>LoaderEntryOneShot</i> and <i>LoaderEntrySelected</i>, see m[blue]<code>Boot Loader Specification</code>m[]<font SIZE="-2">[1]</font> for details. These special IDs are primarily useful as a quick way to persistently make the currently booted boot loader entry the default choice, or to upgrade the default boot loader entry for the next boot to the default boot loader entry for all future boots, but may be used for other operations too. When an empty string (&quot;&quot;) is specified as an ID, then the corresponding EFI variable will be unset.</dl>
<h2>SYSTEMD-BOOT COMMANDS</h2>
<p> These commands manage the <code>systemd-boot</code> EFI boot loader, and do not work in conjunction with other boot loaders. </p>
<p> <code>install</code></p>
<dl>
<dt>
<dd> Installs <code>systemd-boot</code> into the EFI system partition. A copy of <code>systemd-boot</code> will be stored as the EFI default/fallback loader at <i>ESP</i>/EFI/BOOT/BOOT*.EFI. The boot loader is then added to the top of the firmware&#8217;s boot loader list.</dl>
<p> <code>update</code></p>
<dl>
<dt>
<dd> Updates all installed versions of <code><a href="/docs/linux/man/7-systemd-boot/">systemd-boot</a></code>(7), if the available version is newer than the version installed in the EFI system partition. This also includes the EFI default/fallback loader at <i>ESP</i>/EFI/BOOT/BOOT*.EFI. The boot loader is then added to end of the firmware&#8217;s boot loader list if missing.</dl>
<p> <code>remove</code></p>
<dl>
<dt>
<dd> Removes all installed versions of <code>systemd-boot</code> from the EFI system partition and the firmware&#8217;s boot loader list.</dl>
<p> <code>is-installed</code></p>
<dl>
<dt>
<dd> Checks whether <code>systemd-boot</code> is installed in the ESP. Note that a single ESP might host multiple boot loaders; this hence checks whether <code>systemd-boot</code> is one (of possibly many) installed boot loaders &#8212; and neither whether it is the default nor whether it is registered in any EFI variables.</dl>
<p> <code>random-seed</code></p>
<dl>
<dt>
<dd> Generates a random seed and stores it in the EFI System Partition, for use by the <code>systemd-boot</code> boot loader. Also, generates a random &#8216;system token&#8217; and stores it persistently as an EFI variable, if one has not been set before. If the boot loader finds the random seed in the ESP and the system token in the EFI variable it will derive a random seed to pass to the OS and a new seed to store in the ESP from the combination of both. The random seed passed to the OS is credited to the kernel&#8217;s entropy pool by the system manager during early boot, and permits userspace to boot up with an entropy pool fully initialized very early on. Also see <code><a href="/docs/linux/man/8-systemd-boot-system-token-service/">systemd-boot-system-token.service</a></code>(8). </p>
<p> See m[blue]<code>Random Seeds</code>m[]<font SIZE="-2">[3]</font> for further information.</dl>
<h2>OPTIONS</h2>
<p> The following options are understood: </p>
<p> <code>&#8211;esp-path=</code></p>
<dl>
<dt>
<dd> Path to the EFI System Partition (ESP). If not specified, /efi/, /boot/, and /boot/efi/ are checked in turn. It is recommended to mount the ESP to /efi/, if possible.</dl>
<p> <code>&#8211;boot-path=</code></p>
<dl>
<dt>
<dd> Path to the Extended Boot Loader partition, as defined in the m[blue]<code>Boot Loader Specification</code>m[]<font SIZE="-2">[1]</font>. If not specified, /boot/ is checked. It is recommended to mount the Extended Boot Loader partition to /boot/, if possible.</dl>
<p> <code>-p</code>, <code>&#8211;print-esp-path</code></p>
<dl>
<dt>
<dd> This option modifies the behaviour of <code>status</code>. Only prints the path to the EFI System Partition (ESP) to standard output and exits.</dl>
<p> <code>-x</code>, <code>&#8211;print-boot-path</code></p>
<dl>
<dt>
<dd> This option modifies the behaviour of <code>status</code>. Only prints the path to the Extended Boot Loader partition if it exists, and the path to the ESP otherwise to standard output and exit. This command is useful to determine where to place boot loader entries, as they are preferably placed in the Extended Boot Loader partition if it exists and in the ESP otherwise. </p>
<p> Boot Loader Specification Type #1 entries should generally be placed in the directory &quot;$(bootctl -x)/loader/entries/&quot;. Existence of that directory may also be used as indication that boot loader entry support is available on the system. Similarly, Boot Loader Specification Type #2 entries should be placed in the directory &quot;$(bootctl -x)/EFI/Linux/&quot;. </p>
<p> Note that this option (similar to the <code>&#8211;print-booth-path</code> option mentioned above), is available independently from the boot loader used, i.e. also without <code>systemd-boot</code> being installed.</dl>
<p> <code>&#8211;no-variables</code></p>
<dl>
<dt>
<dd> Do not touch the firmware&#8217;s boot loader list stored in EFI variables.</dl>
<p> <code>&#8211;graceful</code></p>
<dl>
<dt>
<dd> Ignore failure when the EFI System Partition cannot be found, or when EFI variables cannot be written. Currently only applies to random seed operations.</dl>
<p> <code>&#8211;make-machine-id-directory=yes|no|auto</code></p>
<dl>
<dt>
<dd> Control creation and deletion of the top-level machine ID directory on the file system containing boot loader entries (i.e. beneath the file system returned by the <code>&#8211;print-boot-path</code> option, see above) during <code>install</code> and <code>remove</code>, respectively. &quot;auto&quot; is equivalent to &quot;yes&quot; if /etc/machine-id resides on a filesystem other than tmpfs and &quot;no&quot; otherwise (in the latter case the machine ID is likely transient and hence should not be used persistently in the ESP). Defaults to &quot;auto&quot;. See <code><a href="/docs/linux/man/5-machine-id/">machine-id</a></code>(5) for details about the machine ID concept and file. </p>
<p> Overriding this may be desirable to hide the machine ID from the (unencrypted) ESP, configure a <code><a href="/docs/linux/man/8-kernel-install/">kernel-install</a></code>(8) script, or, conversely, commit a transient machine ID. </p>
<p> The top-level machine ID directory is useful to allow smooth multi-boot installations: each installed OS instance will have a different machine ID and thus a separate directory to place its boot-time resources in. If this feature is turned off with this option, care needs to be taken that multiple OS instances do not place conflicting files on the shared ESP and Extended Boot Loader Partitions, or that multiple OS instances are not possible.</dl>
<p> <code>&#8211;no-pager</code></p>
<dl>
<dt>
<dd> Do not pipe output into a pager.</dl>
<p> <code>-h</code>, <code>&#8211;help</code></p>
<dl>
<dt>
<dd> Print a short help text and exit.</dl>
<p> <code>&#8211;version</code></p>
<dl>
<dt>
<dd> Print a short version string and exit.</dl>
<h2>EXIT STATUS</h2>
<p> On success, 0 is returned, a non-zero failure code otherwise.</p>
<h2>ENVIRONMENT</h2>
<p> If <i>$SYSTEMD_RELAX_ESP_CHECKS=1</i> is set the validation checks for the ESP are relaxed, and the path specified with <code>&#8211;esp-path=</code> may refer to any kind of file system on any kind of partition. </p>
<p> Similarly, <i>$SYSTEMD_RELAX_XBOOTLDR_CHECKS=1</i> turns off some validation checks for the Extended Boot Loader partition.</p>
