<h2>NAME</h2>
<p> salt-call &#8211; salt-call Documentation</p>
<h2>SYNOPSIS</h2>
<pre>
salt-call [options]
</pre>
<h2>DESCRIPTION</h2>
<p> The salt-call command is used to run module functions locally on a minion instead of executing them from the master. Salt-call is used to run a Standalone Minion, and was originally created for troubleshooting. </p>
<p> The Salt Master is contacted to retrieve state files and other resources during execution unless the <code>&#8211;local</code> option is specified. </p>
<p> <code>NOTE:</code> <code>salt-call</code> commands execute from the current user&#8217;s shell context, while <code>salt</code> commands execute from the system&#8217;s default context.</p>
<h2>OPTIONS</h2>
<dl>
<dt><code>&#8211;version</code></p>
<dd> Print the version of Salt that is running.</p>
<dt><code>&#8211;versions-report</code></p>
<dd> Show program&#8217;s dependencies and version number, and then exit</p>
<dt><code>-h, &#8211;help</code></p>
<dd> Show the help message and exit</p>
<dt><code>-c CONFIG_DIR, &#8211;config-dir=CONFIG_dir</code></p>
<dd> The location of the Salt configuration directory. This directory contains the configuration files for Salt master and minions. The default location on most systems is <code>/etc/salt</code>.</p>
<dt><code>&#8211;hard-crash</code></p>
<dd> Raise any original exception rather than exiting gracefully Default: False</p>
<dt><code>-g, &#8211;grains</code></p>
<dd> Return the information generated by the Salt grains</p>
<dt><code>-m MODULE_DIRS, &#8211;module-dirs=MODULE_DIRS</code></p>
<dd> Specify an additional directory to pull modules from. Multiple directories can be provided by passing -m /&#8211;module-dirs multiple times.</p>
<dt><code>-d, &#8211;doc, &#8211;documentation</code></p>
<dd> Return the documentation for the specified module or for all modules if none are specified</p>
<dt><code>&#8211;master=MASTER</code></p>
<dd> Specify the master to use. The minion must be authenticated with the master. If this option is omitted, the master options from the minion config will be used. If multi masters are set up the first listed master that responds will be used.</p>
<dt><code>&#8211;return RETURNER</code></p>
<dd> Set salt-call to pass the return data to one or many returner interfaces. To use many returner interfaces specify a comma delimited list of returners.</p>
<dt><code>&#8211;local</code></p>
<dd> Run salt-call locally, as if there was no master running.</p>
<dt><code>&#8211;file-root=FILE_ROOT</code></p>
<dd> Set this directory as the base file root.</p>
<dt><code>&#8211;pillar-root=PILLAR_ROOT</code></p>
<dd> Set this directory as the base pillar root.</p>
<dt><code>&#8211;retcode-passthrough</code></p>
<dd> Exit with the salt call retcode and not the salt binary retcode</p>
<dt><code>&#8211;metadata</code></p>
<dd> Print out the execution metadata as well as the return. This will print out the outputter data, the return code, etc.</p>
<dt><code>&#8211;id=ID</code></p>
<dd> Specify the minion id to use. If this option is omitted, the id option from the minion config will be used.</p>
<dt><code>&#8211;skip-grains</code></p>
<dd> Do not load grains.</p>
<dt><code>&#8211;refresh-grains-cache</code></p>
<dd> Force a refresh of the grains cache</dl>
<h3>Logging Options</h3>
<p> Logging options which override any settings defined on the configuration files.</p>
<dl>
<dt><code>-l LOG_LEVEL, &#8211;log-level=LOG_LEVEL</code></p>
<dd> Console logging log level. One of <code>all</code>, <code>garbage</code>, <code>trace</code>, <code>debug</code>, <code>info</code>, <code>warning</code>, <code>error</code>, <code>quiet</code>. Default: <code>info</code>.</p>
<dt><code>&#8211;log-file=LOG_FILE</code></p>
<dd> Log file path. Default: /var/log/salt/minion.</p>
<dt><code>&#8211;log-file-level=LOG_LEVEL_LOGFILE</code></p>
<dd> Logfile logging log level. One of <code>all</code>, <code>garbage</code>, <code>trace</code>, <code>debug</code>, <code>info</code>, <code>warning</code>, <code>error</code>, <code>quiet</code>. Default: <code>info</code>.</dl>
<h3>Output Options</h3>
<dl>
<dt><code>&#8211;out</code></p>
<dd> Pass in an alternative outputter to display the return of data. This outputter can be any of the available outputters: <code>grains</code>, <code>highstate</code>, <code>json</code>, <code>key</code>, <code>overstatestage</code>, <code>pprint</code>, <code>raw</code>, <code>txt</code>, <code>yaml</code> </p>
<p> Some outputters are formatted only for data returned from specific functions; for instance, the <code>grains</code> outputter will not work for non-grains data. </p>
<p> If an outputter is used that does not support the data passed into it, then Salt will fall back on the <code>pprint</code> outputter and display the return data using the Python <code>pprint</code> standard library module. </p>
<p> <code>NOTE:</code> If using <code>&#8211;out=json</code>, you will probably want <code>&#8211;static</code> as well. Without the static option, you will get a separate JSON string per minion which makes JSON output invalid as a whole. This is due to using an iterative outputter. So if you want to feed it to a JSON parser, use <code>&#8211;static</code> as well.</p>
<dt><code>&#8211;out-indent OUTPUT_INDENT, &#8211;output-indent OUTPUT_INDENT</code></p>
<dd> Print the output indented by the provided value in spaces. Negative values disable indentation. Only applicable in outputters that support indentation.</p>
<dt><code>&#8211;out-file=OUTPUT_FILE, &#8211;output-file=OUTPUT_FILE</code></p>
<dd> Write the output to the specified file.</p>
<dt><code>&#8211;no-color</code></p>
<dd> Disable all colored output</p>
<dt><code>&#8211;force-color</code></p>
<dd> Force colored output </p>
<p> <code>NOTE:</code> When using colored output the color codes are as follows: </p>
<p> <code>green</code> denotes success, <code>red</code> denotes failure, <code>blue</code> denotes changes and success and <code>yellow</code> denotes a expected future change in configuration.</dl>
