<p> S-nail provides a simple and friendly environment for sending and receiving mail. It is intended to provide the functionality of the POSIX <a href="/docs/linux/man/1-mailx/">mailx</a>(1) command, but is MIME capable and optionally offers extensions for line editing, S/MIME, SMTP and POP3, among others. S-nail divides incoming mail into its constituent messages and allows the user to deal with them in any order. It offers many Sx COMMANDS and Sx INTERNAL VARIABLES for manipulating messages and sending mail. It provides the user simple editing capabilities to ease the composition of outgoing messages, and increasingly powerful and reliable non-interactive scripting capabilities.</p>

<h3>A starter</h3>
<p> S-nail is a direct descendant of BSD Mail, itself a successor to the Research UNIX mail which &#8220;was there from the start&#8221; according to Sx HISTORY . It thus represents the user side of the UNIX mail system, whereas the system side (Mail-Transfer-Agent, MTA) was traditionally taken by <a href="/docs/linux/man/8-sendmail/">sendmail</a>(8) (and most MTAs provide a binary of this name for compatibility reasons). If the [Option]al SMTP <i>mta</i> is included in the <i>features</i> of S-nail then the system side is not a mandatory precondition for mail delivery. </p>
<p> S-nail strives for compliance with the POSIX <a href="/docs/linux/man/1-mailx/">mailx</a>(1) standard, but <i>posix</i> one of the Sx INTERNAL VARIABLES , or its Sx ENVIRONMENT Ns al equivalent <code>POSIXLY_CORRECT</code> needs to be set to adjust behaviour to be almost on par. Almost, because there is one important difference: POSIX Sx Shell-style argument quoting is ([v15 behaviour may differ] increasingly) used instead of the Sx Old-style argument quoting that the standard documents, which is believed to be a feature. The builtin as well as the (default) global s-nail.rc Sx Resource files already bend the standard imposed settings a bit. </p>
<p> For example, <i>hold</i> and <i>keepsave</i> are <code>set</code> in order to suppress the automatic moving of messages to the Sx secondary mailbox <code>MBOX</code> that would otherwise occur (see Sx Message states ) , and <i>keep</i> to not remove empty system MBOX mailbox files (or all empty such files in <i>posix</i> mode) to avoid mangling of file permissions when files eventually get recreated. </p>
<p> To enter interactive mode even if the initial mailbox is empty <i>emptystart</i> is set, <i>editheaders</i> to allow editing of headers as well as <i>fullnames</i> to not strip down addresses in Sx Compose mode , and <i>quote</i> to include the message that is being responded to when <code>reply ing, which is indented by an</code> <i>indentprefix</i> that also deviates from standard imposed settings. <i>mime-counter-evidence</i> is fully enabled, too. It sets <i>followup-to-honour</i> and <i>reply-to-honour</i> to comply with reply address desires. </p>
<p> Credentials and other settings are easily addressable by grouping them via <code>account</code> The file mode creation mask can be managed with <i>umask</i> Files and shell pipe output can be <code>source d for</code> <code>eval uation, also during startup from within the</code> Sx Resource files . Informational context can be available by <code>set ting</code> <i>verbose</i> or <i>debug</i> (as via &#8211;<code>v , d )</code></p>
<h3>On sending mail, and non-interactive mode</h3>
<p> To send a message to one or more people, using a local or built-in <i>mta</i> (Mail-Transfer-Agent) transport to actually deliver the generated mail message, S-nail can be invoked with arguments which are the names of people to whom the mail will be sent, and the command line options &#8211;<code>b</code> and &#8211;<code>c</code> can be used to add (blind) carbon copy receivers: </p>
<blockquote><p>

#Via sendmail(1) MTA<br />
                                                        $ &lt;<br />
                                             / dev / null s &#8211; nail &#8211; : x &#8211; s test $LOGNAME<br />

<p> Email addresses and plain user names are subject to <code>alternates</code> filtering, names only are first expanded through <code>alias</code> and <i>mta-aliases</i> An address in angle brackets consisting only of a valid local user `&lt;name&gt;&#8217; will be converted to a fully qualified address if either <i>hostname</i> is not set, or set to a non-empty value; if set to the empty value the conversion is left up to the <i>mta</i> By setting <i>expandaddr</i> fine-grained control of recipient address types other than user names and network addresses is possible. Recipients are classified as follows: any name that starts with a vertical bar `|&#8217; character specifies a command pipe &#8211; the command string following the `|&#8217; is executed and the message is sent to its standard input; likewise, any name that consists only of hyphen-minus `-&#8216; or starts with the character solidus `/&#8217; or the character sequence dot solidus `./&#8217; is treated as a file, regardless of the remaining content. Any other name which contains a commercial at `@&#8217; character is a network address; Any other name which starts with a plus sign `+&#8217; character is a mailbox name; Any other name which contains a solidus `/&#8217; character but no exclamation mark `!&#8217; or percent sign `%&#8217; character before is also a mailbox name; What remains is treated as a network address. <h3>Compose mode</h3>
<p> If standard input is a terminal rather than the message to be sent, the user is expected to type in the message contents. In compose mode lines beginning with the character `~&#8217; (in fact the value of <i>escape</i> are special &#8211; these are so-called Sx COMMAND ESCAPES which can be used to read in files, process shell commands, add and edit attachments and more. For example <code>~v</code> or <code>~e</code> will start the <code>VISUAL</code> text <code>EDITOR</code> respectively, to revise the message in its current state, <code>~h</code> allows editing of the most important message headers, with the potent <code>~^</code> custom headers can be created, for example (more specifically than with &#8211;<code>C</code> and <i>customhdr )</i> [Option]ally <code>~?</code> gives an overview of most other available command escapes. </p>
<p> To create file-carbon-copies the special recipient header `Fcc:&#8217; may be used as often as desired, for example via <code>~^</code> Its entire value (or body in standard terms) is interpreted as a <code>folder</code> target, after having been subject to Sx Filename transformations : this is the only way to create a file-carbon-copy without introducing an ambiguity regarding the interpretation of the address, file names with leading vertical bars or commercial ats can be used. Like all other recipients `Fcc:&#8217; is subject to the checks of <i>expandaddr</i> Any local file and pipe command addressee honours the setting of <i>mbox-fcc-and-pcc</i> </p>
<p> Once finished with editing the command escape <code>~.</code> (see there) will call hooks, insert automatic injections and receivers, leave compose mode and send the message once it is completed. Aborting letter composition is possible with either of <code>~x</code> or <code>~q</code> the latter of which will save the message in the file denoted by <code>DEAD</code> unless no <i>save</i> is set. And unless <i>ignoreeof</i> is set the effect of <code>~.</code> can also be achieved by typing end-of-transmission (EOT) via `control-D&#8217; ( `^D&#8217; at the beginning of an empty line, and <code>~q</code> is always reachable by typing end-of-text (ETX) twice via `control-C&#8217; ( `^C&#8217; ). </p>
<p> The compose mode hooks <i>on-compose-enter , on-compose-splice , on-compose-leave</i> and <i>on-compose-cleanup</i> may be set to <code>define d macros and provide reliable and increasingly powerful mechanisms to</code> perform automated message adjustments dependent on message context, for example addition of message signatures ( <i>message-inject-head , message-inject-tail</i> or creation of additional receiver lists (also by setting <i>autocc , autobcc )</i> To achieve that the command <code>digmsg</code> may be used in order to query and adjust status of message(s). The splice hook can also make use of Sx COMMAND ESCAPES . ([v15 behaviour may differ] The compose mode hooks work for <code>forward , mail , reply</code> and variants; <code>resend</code> and <code>Resend</code> only provide the hooks <i>on-resend-enter</i> and <i>on-resend-cleanup</i> which are pretty restricted due to the nature of the operation.)</p>
<h3>On reading mail, and more on interactive mode</h3>
<p> When invoked without addressees S-nail enters interactive mode in which mails may be read. When used like that the user&#8217;s system <i>inbox</i> (for more on mailbox types please see the command <code>folder</code> is read in and a one line header of each message therein is displayed if the variable <i>header</i> is set. The visual style of this summary of <code>headers</code> can be adjusted through the variable <i>headline</i> and the possible sorting criterion via <i>autosort</i> Scrolling through <i>screen </i><code>fuls of</code> <code>headers</code> can be performed with the command <code>z</code> If the initially opened mailbox is empty S-nail will instead exit immediately (after displaying a message) unless the variable <i>emptystart</i> is set. </p>
<p> At the <i>prompt</i> the command <code>list</code> will give a listing of all available commands and <code>help</code> will [Option]ally give a summary of some common ones. If the [Option]al documentation strings are available (see <i>features</i> one can type `help&#8217; X (or `?X&#8217; and see the actual expansion of `X&#8217; and what its purpose is, i.e., commands can be abbreviated (note that POSIX defines some abbreviations, so that the alphabetical order of commands does not necessarily relate to the abbreviations; it is however possible to define overwrites with <code>commandalias )</code> These commands can also produce a more <i>verbose</i> output. </p>
<p> Messages are given numbers (starting at 1) which uniquely identify messages; the current message &#8211; the &#8220;dot&#8221; &#8211; will either be the first new message, or the first unread message, or the first message of the mailbox; the internal variable <i>showlast</i> will instead cause usage of the last message for this purpose. The command <code>headers</code> will display a <i>screen </i><code>ful of header summaries containing the</code> &#8220;dot&#8221; whereas <code>from</code> will display only the summaries of the given messages, defaulting to the &#8220;dot&#8221; </p>
<p> Message content can be displayed with the command <code>type</code> ( `t&#8217; alias <code>print )</code> Here the variable <i>crt</i> controls whether and when S-nail will use the configured <code>PAGER</code> for display instead of directly writing to the user terminal <i>screen</i> the sole difference to the command <code>more</code> which will always use the <code>PAGER</code> The command <code>top</code> will instead only show the first <i>toplines</i> of a message (maybe even compressed if <i>topsqueeze</i> is set). Message display experience may improve by setting and adjusting <i>mime-counter-evidence</i> and also see Sx HTML mail and MIME attachments . </p>
<p> By default the current message ( &#8220;dot&#8221; is displayed, but like with many other commands it is possible to give a fancy message specification (see Sx Specifying messages ) , for example `t:u&#8217; will display all unread messages, `t.&#8217; will display the &#8220;dot&#8221; `t&#8217; 1 5 will type the messages 1 and 5, `t&#8217; 1-5 will type the messages 1 through 5, and `t-&#8216; and `t+&#8217; will display the previous and the next message, respectively. The command <code>search</code> (a more substantial alias for <code>from</code> will display a header summary of the given message specification list instead of their content; the following will search for subjects: </p>
<blockquote><p><tt>? from &quot;'@Some subject to search for'&quot;</tt></p></blockquote>
<p> In the default setup all header fields of a message will be <code>type d, but fields can be white- or blacklisted for a variety of</code> applications by using the command <code>headerpick</code> e.g., to restrict their display to a very restricted set for <code>type</code> `<code>headerpick</code> &#8216; Cd type retain Ar from to cc subject . In order to display all header fields of a message regardless of currently active ignore or retain lists, use the commands <code>Type</code> and <code>Top</code> <code>Show</code> will show the raw message content. Note that historically the global s-nail.rc not only adjusts the list of displayed headers, but also sets <i>crt</i> ([v15 behaviour may differ] A yet somewhat restricted) Reliable scriptable message inspection is available via <code>digmsg</code> </p>
<p> Dependent upon the configuration a line editor (see the section Sx On terminal control and line editor ) aims at making the user experience with the many Sx COMMANDS a bit nicer. When reading the system <i>inbox</i> or when &#8211;<code>f</code> (or <code>folder</code> specified a mailbox explicitly prefixed with the special `%:&#8217; modifier (to propagate it to a Sx primary system mailbox ) , then messages which have been read (see&nbsp; Sx Message states will be automatically moved to a Sx secondary mailbox , the user&#8217;s <code>MBOX</code> file, when the mailbox is left, either by changing the active mailbox or by quitting S-nail &#8211; this automatic moving from a system- or primary- to the secondary mailbox is not performed when the variable <i>hold</i> is set. Messages can also be explicitly <code>move d to other mailboxes, whereas</code> <code>copy</code> keeps the original message. <code>write</code> can be used to write out data content of specific parts of messages. </p>
<p> After examining a message the user can <code>reply `r&#8217; </code> to the sender and all recipients (which will also be placed in `To:&#8217; unless <i>recipients-in-cc</i> is set), or <code>Reply `R&#8217; </code> exclusively to the sender(s). To comply with with the receivers desired reply address the Sx quadoption Ns s <i>followup-to-honour</i> and <i>reply-to-honour</i> should usually be set. The commands <code>Lreply</code> and <code>Lfollowup</code> know how to apply a special addressee massage, see Sx Mailing lists . Dependent on the presence and value of <i>quote</i> the message being replied to will be included in a quoted form. <code>forward ing a message will allow editing the new message: the original message</code> will be contained in the message body, adjusted according to <code>headerpick</code> It is possible to <code>resend</code> or <code>Resend</code> messages: the former will add a series of `Resent-&#8216; headers, whereas the latter will not; different to newly created messages editing is not possible and no copy will be saved even with <i>record</i> unless the additional variable <i>record-resent</i> is set. When sending, replying or forwarding messages comments and full names will be stripped from recipient addresses unless the internal variable <i>fullnames</i> is set. </p>
<p> Of course messages can be <code>delete `d&#8217; </code> and they can spring into existence again via <code>undelete</code> or when the S-nail session is ended via the <code>exit</code> or <code>xit</code> commands to perform a quick program termation. To end a mail processing session regularly and perform a full program exit one may issue the command <code>quit</code> It will, among others, move read messages to the Sx secondary mailbox <code>MBOX</code> as necessary, discard deleted messages in the current mailbox, and update the [Option]al (see <i>features</i> line editor <i>history-file</i> By the way, whenever the main event loop is about to look out for the next input line it will trigger the hook <i>on-main-loop-tick</i></p>
<h3>HTML mail and MIME attachments</h3>
<p> HTML-only messages become more and more common, and many messages come bundled with a bouquet of MIME (Multipurpose Internet Mail Extensions) parts and attachments. To get a notion of MIME types there is a built-in default set, onto which the content of Sx The mime.types files will be added (as configured and allowed by <i>mimetypes-load-control )</i> Types can also become registered and listed with the command <code>mimetype</code> To improve interaction with the faulty MIME part declarations of real life <i>mime-counter-evidence</i> will allow verification of the given assertion, and the possible provision of an alternative, better MIME type. Note plain text parts will always be preferred in `multipart/alternative&#8217; MIME messages unless <i>mime-alternative-favour-rich</i> is set. </p>
<p> Whereas a simple HTML-to-text filter for displaying HTML messages is [Option]ally supported (indicated by `,+filter-html-tagsoup,&#8217; in <i>features )</i> MIME types other than plain text cannot be handled directly. To deal with specific non-text MIME types or file extensions programs need to be registered which either prepare (re-)integrable plain text versions of their input (a mode which is called <code>copiousoutput )</code> or display the content externally, for example in a graphical window: the latter type is only considered by and for the command <code>mimeview</code> </p>
<p> To install a handler program for a MIME type an according <i>pipe-TYPE/SUBTYPE</i> variable needs to be set; to define a handler for a file extension <i>pipe-EXTENSION</i> can be used &#8211; these handlers take precedence. [Option]ally mail user agent configuration is supported (see Sx The Mailcap files ) , and will be queried for display or quote handlers after the former ones. Type-markers registered via <code>mimetype</code> are the last possible source for information how to handle a MIME type. </p>
<p> For example, to display HTML messages integrated via the text browsers <a href="/docs/linux/man/1-lynx/">lynx</a>(1) or <a href="/docs/linux/man/1-elinks/">elinks</a>(1), register a MathML MIME type and enable its plain text display, and to open PDF attachments in an external PDF viewer, asynchronously and with some other magic attached: </p>
