<h2>NAME</h2>
<p> smidump &#8211; dump SMI or SPPI modules in various formats</p>
<h2>SYNOPSIS</h2>
<p> <code>smidump</code> [ <code>-Vhqusmk</code> ] [ <code>-c </code><i>file</i> ] [ <code>-o </code><i>name</i> ] [ <code>-p </code><i>module</i> ] [ <code>-l </code><i>level</i> ] [ <code>-f </code><i>format</i> ] <i>module(s)</i></p>
<h2>DESCRIPTION</h2>
<p> The <code>smidump</code> program is used to dump the contents of a single MIB or PIB module or a collection of modules to stdout in a selectable output format. This format may be a simple tree of nodes, types or imported modules, but also a format fully compliant to SMIv1, SMIv2, SPPI or SMIng or CORBA IDL or C source code. Smidump can thus be used to convert modules from SMIv2 to SMIng and from SMIng to SMIv2, or to develop template based agent code.</p>
<h2>OPTIONS</h2>
<dl>
<dt><code>-V, &#8211;version</code></p>
<dd> Show the smidump version and exit.</p>
<dt><code>-h, &#8211;help</code></p>
<dd> Show a help text and exit. The help text contains a list of all supported output formats.</p>
<dt><code>-c </code><i>file</i><code>, &#8211;config=</code><i>file</i></p>
<dd> Read <i>file</i> instead of any other (global and user) configuration file.</p>
<dt><code>-f </code><i>format</i><code>, &#8211;format=</code><i>format</i></p>
<dd> Use <i>format</i> when dumping a module. Supported output formats are described below. The default output format is SMIng. The <i>format</i> argument is case insensitive.</p>
<dt><code>-l </code><i>level</i><code>, &#8211;level=</code><i>level</i></p>
<dd> Report errors and warnings up to the given severity <i>level</i>. See the <a href="/docs/linux/man/1-smilint/">smilint</a>(1) manual page for a description of the error levels. The default error level is 3.</p>
<dt><code>-s, &#8211;severity</code></p>
<dd> Show the error severity in brackets before error messages.</p>
<dt><code>-m, &#8211;error-names</code></p>
<dd> Show the error names in braces before error messages.</p>
<dt><code>-o </code><i>name</i><code>, &#8211;output=</code><i>name</i><code></p>
<dd> Write the output in one or multiple files instead of stdout. The file name(s) are derived from the </code><i>name</i> argument. Not all format support this option.</p>
<dt><code>-p </code><i>module</i><code>, &#8211;preload=</code><i>module</i></p>
<dd> Preload the module <i>module</i> before reading the main module(s). This may be helpful if an incomplete main module misses to import some definitions.</p>
<dt><code>-q, &#8211;quiet</code></p>
<dd> Suppress comments from dumped modules. What kind of information gets suppressed depends on the output format.</p>
<dt><code>-u, &#8211;unified</code></p>
<dd> Dump a unified output in case of multiple <i>module(s)</i> instead of multiple concatenated output sections. This is not supported for all output formats.</p>
<dt><code>-k, &#8211;keep-going</code></p>
<dd> Continue as much as possible after serious parse errors. Note that the output generated after serious parse errors may be incomplete and should be used with care.</p>
<dt><i>module(s)</i></p>
<dd> These are the module(s) to be dumped. If a module argument represents a path name (identified by containing at least one dot or slash character), this is assumed to be the exact file to read. Otherwise, if a module is identified by its plain module name, it is searched according to libsmi internal rules. See <code><a href="/docs/linux/man/3-smi_config/">smi_config</a>(3)</code> for more details.</dl>
<h2>OUTPUT FORMATS</h2>
<p> The <code>smidump</code> program supports the following output formats:</p>
<dl>
<dt>sming</p>
<dd> SMIng compliant format as defined in the SMIng Internet-Draft.</p>
<dt>smiv2</p>
<dd> SMIv2 compliant format as defined in RFC 2578, RFC 2579, RFC 2580.</p>
<dt>smiv1</p>
<dd> SMIv2 compliant format as defined in RFC 1155, RFC 1212, RFC 1215.</p>
<dt>sppi</p>
<dd> SPPI compliant format as defined in RFC 3159. If the underlying module is not SPPI, there might be some mandatory information missing.</p>
<dt>mosy</p>
<dd> Format generated by the mosy compiler.</p>
<dt>imports</p>
<dd> Import hierarchy of a module.</p>
<dt>types</p>
<dd> Types defined in a module.</p>
<dt>tree</p>
<dd> OID registration tree structure of a module.</p>
<dt>metrics</p>
<dd> Metrics derived from a module (experimental).</p>
<dt>identifiers</p>
<dd> List of identifiers defined in a module.</p>
<dt>compliances</p>
<dd> Compliance definitions with all included objects and notifications.</p>
<dt>corba</p>
<dd> CORBA IDL and OID definitions following the JIDM specification translation rules.</p>
<dt>netsnmp</p>
<dd> C source code files for usage within the net-snmp package (experimental).</p>
<dt>scli</p>
<dd> ANSI C manager stubs for usage within the scli package (experimental).</p>
<dt>cm</p>
<dd> Reverse engineered conceptual model in DIA XML file format (experimental).</p>
<dt>svg</p>
<dd> SVG diagram of a module (experimental). Use with <code>-u</code> when dumping multiple <i>modules</i>.</p>
<dt>jax</p>
<dd> Java AgentX sub-agent classes in separate files (experimental).</p>
<dt>perl</p>
<dd> Perl represention of the MIB module (contributed by Martin Schulz &lt;schulz [at] videotron.ca&gt;).</p>
<dt>python</p>
<dd> Python dictionaries represention of the MIB module (contributed by Pat Knight &lt;pat [at] ktgroup.co.uk&gt;).</p>
<dt>xml</p>
<dd> SMI in XML format (experimental).</p>
<dt>xsd</p>
<dd> SMI in XML schema format (experimental).</p>
<dt>sizes</p>
<dd> SNMP best case / worst case RFC 3416 PDU sizes for typical PDUs excluding SNMP message and transport headers (experimental). </p>
</dl>
<h2>EXAMPLE</h2>
<p> This example converts the SMIv2 module IF-MIB in the current directory to IF-MIB.sming in SMIng format. Note that the ./ prefix is used to ensure reading the module from the current directory and not from a place that libsmi guesses on its own. </p>
<pre>
  $ smidump -f sming ./IF-MIB &gt; IF-MIB.sming
</pre>
