<p>rmid &#8211; The Java RMI Activation System Daemon </p>
<p> <code>rmid</code> starts the activation system daemon that allows objects to be registered and activated in a virtual machine (VM). </p>
<h2>Synopsis</h2>
<pre><code>rmid [options]</code></pre>
<h2>Description</h2>
<p>The <code>rmid</code> tool starts the activation system daemon. The activation system daemon must be started before activatable objects can be either registered with the activation system or activated in a VM. See the <i>Java RMI Specification</i> @ <a rel="nofollow" href="http://docs.oracle.com/javase/7/docs/platform/rmi/spec/rmiTOC.html">http://docs.oracle.com/javase/7/docs/platform/rmi/spec/rmiTOC.html</a> and <i>Activation tutorials</i> @ <a rel="nofollow" href="http://docs.oracle.com/javase/7/docs/technotes/guides/rmi/activation/overview.html">http://docs.oracle.com/javase/7/docs/technotes/guides/rmi/activation/overview.html</a> for details on how to write programs that use activatable remote objects. </p>
<p> The daemon can be started by executing the <i>rmid</i> command, and specifying a security policy file, as follows: </p>
<pre><code> rmid -J-Djava.security.policy=rmid.policy</code></pre>
<p><code>Note:</code> When running Sun&#8217;s implementation of <i>rmid</i>, by default you will need to specify a security policy file so that <i>rmid</i> can verify whether or not the information in each <i>ActivationGroupDesc</i> is allowed to be used to launch a VM for an activation group. Specifically, the command and options specified by the <i>CommandEnvironment</i> and any <i>Properties</i> passed to an <i>ActivationGroupDesc</i>&#8216;s constructor must now be explicitly allowed in the security policy file for <i>rmid</i>. The value of the <i>sun.rmi.activation.execPolicy</i> property dictates the policy that <i>rmid</i> uses to determine whether or not the information in an <i>ActivationGroupDesc</i> may be used to launch a VM for an activation group. </p>
<p> Executing <i>rmid</i> by default </p>
<dl COMPACT>
<dd>
<dl COMPACT>
<dt>o</p>
<dd>starts the Activator and an internal registry on the default port, 1098, and</p>
<dt>o</p>
<dd>binds an <i>ActivationSystem</i> to the name <i>java.rmi.activation.ActivationSystem</i> in this internal registry.</dl>
</dl>
<p> To specify an alternate port for the registry, you must specify the <i>-port</i> option when starting up <i>rmid</i>. For example, </p>
<pre><code> rmid -J-Djava.security.policy=rmid.policy -port 1099</code></pre>
<p>starts the activation system daemon and a registry on the registry&#8217;s default port, 1099. </p>
<h3>Starting rmid from inetd/xinetd</h3>
<p>An alternative to starting <i>rmid</i> from the command line is to configure <i>inetd</i> (Solaris) or <i>xinetd</i> (Linux) to start <i>rmid</i> on demand. </p>
<p> When <i>rmid</i> starts up, it attempts to obtain an inherited channel (inherited from <i>inetd</i>/<i>xinetd</i>) by invoking the <i>System.inheritedChannel</i> method. If the inherited channel is <i>null</i> or not an instance of <i>java.nio.channels.ServerSocketChannel</i>, then <i>rmid</i> assumes that it was not started by <i>inetd</i>/<i>xinetd</i>, and it starts up as described above. </p>
<p> If the inherited channel is a <i>ServerSocketChannel</i> instance, then <i>rmid</i> uses the <i>java.net.ServerSocket</i> obtained from the <i>ServerSocketChannel</i> as the server socket that accepts requests for the remote objects it exports, namely the registry in which the <i>java.rmi.activation.ActivationSystem</i> is bound and the <i>java.rmi.activation.Activator</i> remote object. In this mode, <i>rmid</i> behaves the same as when it is started from the command line, <i>except</i>: </p>
<dl COMPACT>
<dd>
<dl COMPACT>
<dt>o</p>
<dd>Output printed to <i>System.err</i> is redirected to a file. This file is located in the directory specified by the <i>java.io.tmpdir</i> system property (typically <i>/var/tmp</i> or <i>/tmp</i>) with the prefix <i>&quot;rmid-err&quot;</i> and the suffix <i>&quot;tmp&quot;</i>.</p>
<dt>o</p>
<dd>The <i>-port</i> option is disallowed. If this option is specified, <i>rmid</i> will exit with an error message.</p>
<dt>o</p>
<dd>The <i>-log</i> option is required. If this option is not specified, <i>rmid</i> will exit with an error message.</dl>
</dl>
<p> See the man pages for <i>inetd</i> (Solaris) or <i>xinetd</i> (Linux) for details on how to configure services to be started on demand. </p>
<h2>Options</h2>
<dl COMPACT>
<dd>
<dl COMPACT>
<dt>-C&lt;someCommandLineOption&gt;</p>
<dd>Specifies an option that is passed as a command-line argument to each child process (activation group) of <i>rmid</i> when that process is created. For example, you could pass a property to each virtual machine spawned by the activation system daemon: </p>
<pre><code> rmid -C-Dsome.property=value</code></pre>
<p>This ability to pass command-line arguments to child processes can be useful for debugging. For example, the following command: </p>
<pre><code> rmid -C-Djava.rmi.server.logCalls=true</code></pre>
<p>will enable server-call logging in all child VMs.</dl>
<dl COMPACT>
<dt>-J&lt;someCommandLineOption&gt;</p>
<dd>Specifies an option that is passed to the <i>java</i> interpreter running <i>rmid</i>. For example, to specify that <i>rmid</i> use a policy file named <i>rmid.policy</i>, the <i>-J</i> option can be used to define the <i>java.security.policy</i> property on <i>rmid</i>&#8216;s command line, for example: </p>
<pre><code> rmid -J-Djava.security.policy=rmid.policy</code></pre>
<dt>-J-Dsun.rmi.activation.execPolicy=&lt;policy&gt;</p>
<dd>Specifies the policy that <i>rmid</i> employs to check commands and command-line options used to launch the VM in which an activation group runs. Please note that this option exists only in Sun&#8217;s implementation of the Java RMI activation daemon. If this property is not specified on the command line, the result is the same as if <i>-J-Dsun.rmi.activation.execPolicy=default</i> were specified. The possible values of <i>&lt;policy&gt;</i> can be <i>default</i>, <i>&lt;policyClassName&gt;</i>, or <i>none</i>:</p>
<dl COMPACT>
<dd>
<dl COMPACT>
<dt>o</p>
<dd><code>default (or if this property is </code><tt>unspecified</tt><code>)</code></dl>
<p> The default <i>execPolicy</i> allows <i>rmid</i> to execute commands with specific command-line options only if <i>rmid</i> has been granted permission to execute those commands and options in the security policy file that <i>rmid</i> uses. Only the default activation group implementation can be used with the <i>default</i> execution policy. </p>
<p> <i>rmid</i> launches a VM for an activation group using the information in the group&#8217;s registered activation group descriptor, an <i>ActivationGroupDesc</i>. The group descriptor specifies an optional <i>ActivationGroupDesc.CommandEnvironment</i> which includes the <i>command</i> to execute to start the activation group as well as any command line <i>options</i> to be added to the command line. By default, <i>rmid</i> uses the <i>java</i> command found in <i>java.home</i>. The group descriptor also contains <i>properties</i> overrides that are added to the command line as options defined as: </p>
<pre><code> -D</code><tt>&lt;property&gt;</tt><code>=</code><tt>&lt;value&gt;</tt></pre>
<p>The permission <i>com.sun.rmi.rmid.ExecPermission</i> is used to grant <i>rmid</i> permission to execute a command, specified in the group descriptor&#8217;s <i>CommandEnvironment</i> to launch an activation group. The permission <i>com.sun.rmi.rmid.ExecOptionPermission</i> is used to allow <i>rmid</i> to use command-line options, specified as properties overrides in the group descriptor or as options in the <i>CommandEnvironment</i>, when launching the activation group. </p>
<p> When granting <i>rmid</i> permission to execute various commands and options, the permissions <i>ExecPermission</i> and <i>ExecOptionPermission</i> need to be granted universally (i.e., granted to all code sources).</p>
<dl COMPACT>
<dd>
<dl COMPACT>
<dt>ExecPermission</p>
<dd>The <i>ExecPermission</i> class represents permission for <i>rmid</i> to execute a specific <i>command</i> to launch an activation group.</dl>
<p> <code>Syntax</code><br />
 The <i>name</i> of an <i>ExecPermission</i> is the path name of a command to grant <i>rmid</i> permission to execute. A path name that ends in &quot;/*&quot; indicates all the files contained in that directory (where &quot;/&quot; is the file-separator character, <i>File.separatorChar</i>). A path name that ends with &quot;/-&quot; indicates all files and subdirectories contained in that directory (recursively). A path name consisting of the special token &quot;&lt;&lt;ALL FILES&gt;&gt;&quot; matches <code>any</code> file. </p>
<p> <code>Note:</code> A path name consisting of a single &quot;*&quot; indicates all the files in the current directory, while a path name consisting of a single &quot;-&quot; indicates all the files in the current directory and (recursively) all files and subdirectories contained in the current directory.</p>
<dl COMPACT>
<dt>ExecOptionPermission</p>
<dd>The <i>ExecOptionPermission</i> class represents permission for <i>rmid</i> to use a specific command-line <i>option</i> when launching an activation group. The <i>name</i> of an <i>ExecOptionPermission</i> is the value of a command line option.</dl>
<p> <code>Syntax</code><br />
 Options support a limited wildcard scheme. An asterisk signifies a wildcard match, and it may appear as the option name itself (i.e., it matches any option), or an asterisk may appear at the end of the option name only if the asterisk follows either a &quot;.&quot; or &quot;=&quot;. </p>
<p> For example: &quot;*&quot; or &quot;-Dfoo.*&quot; or &quot;-Da.b.c=*&quot; is valid, &quot;*foo&quot; or &quot;-Da*b&quot; or &quot;ab*&quot; is not.</p>
<dl COMPACT>
<dt>Policy file for rmid</p>
<dd>When granting <i>rmid</i> permission to execute various commands and options, the permissions <i>ExecPermission</i> and <i>ExecOptionPermission</i> need to be granted universally (i.e., granted to all code sources). It is safe to grant these permissions universally because only <i>rmid</i> checks these permissions.</dl>
<p> An example policy file that grants various execute permissions to <i>rmid</i> is: </p>
<pre><code>grant {
 permission com.sun.rmi.rmid.ExecPermission
 &quot;/files/apps/java/jdk1.7.0/solaris/bin/java&quot;;
 permission com.sun.rmi.rmid.ExecPermission
 &quot;/files/apps/rmidcmds/*&quot;;
 permission com.sun.rmi.rmid.ExecOptionPermission
 &quot;-Djava.security.policy=/files/policies/group.policy&quot;;
 permission com.sun.rmi.rmid.ExecOptionPermission
 &quot;-Djava.security.debug=*&quot;;
 permission com.sun.rmi.rmid.ExecOptionPermission
 &quot;-Dsun.rmi.*&quot;;
};</code></pre>
<p>The first permission granted allow <i>rmid</i> to execute the 1.7.0 version of the <i>java</i> command, specified by its explicit path name. Note that by default, the version of the <i>java</i> command found in <i>java.home</i> is used (the same one that <i>rmid</i> uses), and does not need to be specified in the policy file. The second permission allows <i>rmid</i> to execute any command in the directory <i>/files/apps/rmidcmds</i>. </p>
<p> The third permission granted, an <i>ExecOptionPermission</i>, allows <i>rmid</i> to launch an activation group that defines the security policy file to be <i>/files/policies/group.policy</i>. The next permission allows the <i>java.security.debug</i> property to be used by an activation group. The last permission allows any property in the <i>sun.rmi</i> property name hierarchy to be used by activation groups. </p>
<p> To start <i>rmid</i> with a policy file, the <i>java.security.policy</i> property needs to be specified on <i>rmid</i>&#8216;s command line, for example: </p>
<p> <i>rmid -J-Djava.security.policy=rmid.policy</i></dl>
<dl COMPACT>
<dt>o</p>
<dd><tt>&lt;policyClassName&gt;</tt></dl>
<p> If the default behavior is not flexible enough, an administrator can provide, when starting <i>rmid</i>, the name of a class whose <i>checkExecCommand</i> method is executed in order to check commands to be executed by rmid. </p>
<p> The <i>policyClassName</i> specifies a public class with a public, no-argument constructor and an implementation of the following <i>checkExecCommand</i> method: </p>
<pre><code> public void checkExecCommand(ActivationGroupDesc desc,
 String[] command)
 throws SecurityException;</code></pre>
<p>Before launching an activation group, <i>rmid</i> calls the policy&#8217;s <i>checkExecCommand</i> method, passing it the activation group descriptor and an array containing the complete command to launch the activation group. If the <i>checkExecCommand</i> throws a <i>SecurityException</i>, <i>rmid</i> will not launch the activation group and an <i>ActivationException</i> will be thrown to the caller attempting to activate the object.</p>
<dl COMPACT>
<dt>o</p>
<dd><code>none</code></dl>
<p> If the <i>sun.rmi.activation.execPolicy</i> property value is &quot;none&quot;, then <i>rmid</i> will not perform any validation of commands to launch activation groups.</dl>
</dl>
<dl COMPACT>
<dt>-log dir</p>
<dd>Specifies the name of the directory the activation system daemon uses to write its database and associated information. The log directory defaults to creating a directory, <i>log</i>, in the directory in which the <i>rmid</i> command was executed.</dl>
<dl COMPACT>
<dt>-port port</p>
<dd>Specifies the port <i>rmid</i>&#8216;s registry uses. The activation system daemon binds the <i>ActivationSystem</i>, with the name <i>java.rmi.activation.ActivationSystem</i>, in this registry. Thus, the <i>ActivationSystem</i> on the local machine can be obtained using the following <i>Naming.lookup</i> method call: </p>
<pre><code> import java.rmi.*; 
 import java.rmi.activation.*;
 ActivationSystem system; system = (ActivationSystem)
 Naming.lookup(&quot;//:</code><tt>port</tt>/java.rmi.activation.ActivationSystem&quot;);</pre>
<dt>-stop</p>
<dd>Stops the current invocation of <i>rmid</i>, for a port specified by the <i>-port</i> option. If no port is specified, it will stop the <i>rmid</i> running on port 1098.</dl>
</dl>
