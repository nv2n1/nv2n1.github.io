<h2>NAME</h2>
<p> reprepro - produce, manage and sync a local repository of Debian packages  </p>
<h2>SYNOPSIS</h2>
<p> <code>reprepro --help</code> </p>
<p> <code>reprepro</code> [ <i>options</i> ] <i>command</i> [ <i>per-command-arguments</i> ]  </p>
<h2>DESCRIPTION</h2>
<p> reprepro is a tool to manage a repository of Debian packages (.deb, .udeb, .dsc, ...). It stores files either being injected manually or downloaded from some other repository (partially) mirrored into a pool/ hierarchy. Managed packages and checksums of files are stored in a Berkeley DB database file, so no database server is needed. Checking signatures of mirrored repositories and creating signatures of the generated Package indices is supported. </p>
<p> Former working title of this program was mirrorer.  </p>
<h2>GLOBAL OPTIONS</h2>
<p> Options can be specified before the command. Each affects a different subset of commands and is ignored by other commands. </p>
<dl>
<dt><code>-h --help</code></dt>
<dd> <p> Displays a short list of options and commands with description. </p>
 </dd>
<dt><code>-v, -V, --verbose</code></dt>
<dd> <p> Be more verbose. Can be applied multiple times. One uppercase <code>-V</code> counts as five lowercase <code>-v.</code> </p>
 </dd>
<dt><code>--silent</code></dt>
<dd> <p> Be less verbose. Can be applied multiple times. One <code>-v</code> and one <code>-s</code> cancel each other out. </p>
 </dd>
<dt><code>-f, --force</code></dt>
<dd> <p> This option is ignored, as it no longer exists. </p>
 </dd>
<dt><code>-b, --basedir </code><i>basedir</i></dt>
<dd> <p> Sets the base-dir all other default directories are relative to. If none is supplied and the <code>REPREPRO_BASE_DIR</code> environment variable is not set either, the current directory will be used. </p>
 </dd>
<dt><code>--outdir </code><i>outdir</i></dt>
<dd> <p> Sets the base-dir of the repository to manage, i.e. where the <code>pool/</code> subdirectory resides. And in which the <code>dists/</code> directory is placed by default. If this starts with &#8216;<code>+b/</code>&#8216;, it is relative to basedir. </p>
<p> The default for this is <i>basedir</i>. </p>
 </dd>
<dt><code>--confdir </code><i>confdir</i></dt>
<dd> <p> Sets the directory where the configuration is searched in. </p>
<p> If this starts with &#8216;<code>+b/</code>&#8216;, it is relative to basedir. </p>
<p> If none is given, <code>+b/conf</code> (i.e. <i>basedir</i><code>/conf</code>) will be used. </p>
 </dd>
<dt><code>--distdir </code><i>distdir</i></dt>
<dd> <p> Sets the directory to generate index files relatively to. (i.e. things like Packages.gz, Sources.gz and Release.gpg) </p>
<p> If this starts with &#8216;<code>+b/</code>&#8216;, it is relative to basedir, if starting with &#8216;<code>+o/</code>&#8216; relative to outdir. </p>
<p> If none is given, <code>+o/dists</code> (i.e. <i>outdir</i><code>/dists</code>) is used. </p>
<p> <code>Note:</code> apt has <code>dists</code> hard-coded in it, so this is mostly only useful for testing or when your webserver pretends another directory structure than your physical layout. </p>
<p> <code>Warning:</code> Beware when changing this forth and back between two values not ending in the same directory. Reprepro only looks if files it wants are there. If nothing of the content changed and there is a file it will not touch it, assuming it is the one it wrote last time, assuming any different <code>--distdir</code> ended in the same directory. So either clean a directory before setting <code>--distdir</code> to it or do an <code>export</code> with the new one first to have a consistent state. </p>
 </dd>
<dt><code>--logdir </code><i>logdir</i></dt>
<dd> <p> The directory where files generated by the <code>Log:</code> directive are stored if they have no absolute path. </p>
<p> If this starts with &#8216;<code>+b/</code>&#8216;, it is relative to basedir, if starting with &#8216;<code>+o/</code>&#8216; relative to outdir, with &#8216;<code>+c/</code>&#8216; relative to confdir. </p>
<p> If none is given, <code>+b/logs</code> (i.e. <i>basedir</i><code>/logs</code>) is used. </p>
 </dd>
<dt><code>--dbdir </code><i>dbdir</i></dt>
<dd> <p> Sets the directory where reprepro keeps its databases. </p>
<p> If this starts with &#8216;<code>+b/</code>&#8216;, it is relative to basedir, if starting with &#8216;<code>+o/</code>&#8216; relative to outdir, with &#8216;<code>+c/</code>&#8216; relative to confdir. </p>
<p> If none is given, <code>+b/db</code> (i.e. <i>basedir</i><code>/db</code>) is used. </p>
<p> <code>Note:</code> This is permanent data, no cache. One has almost to regenerate the whole repository when this is lost. </p>
 </dd>
<dt><code>--listdir </code><i>listdir</i></dt>
<dd> <p> Sets the directory where downloads it downloads indices to when importing from other repositories. This is temporary data and can be safely deleted when not in an update run. </p>
<p> If this starts with &#8216;<code>+b/</code>&#8216;, it is relative to basedir, if starting with &#8216;<code>+o/</code>&#8216; relative to outdir, with &#8216;<code>+c/</code>&#8216; relative to confdir. </p>
<p> If none is given, <code>+b/lists</code> (i.e. <i>basedir</i><code>/lists</code>) is used. </p>
 </dd>
<dt><code>--morguedir </code><i>morguedir</i></dt>
<dd> <p> Files deleted from the pool are stored into <i>morguedir</i>. </p>
<p> If this starts with &#8216;<code>+b/</code>&#8216;, it is relative to basedir, if starting with &#8216;<code>+o/</code>&#8216; relative to outdir, with &#8216;<code>+c/</code>&#8216; relative to confdir. </p>
<p> If none is given, deleted files are just deleted. </p>
 </dd>
<dt><code>--methoddir </code><i>methoddir</i></dt>
<dd> <p> Look in <i>methoddir</i> instead of <code>/usr/lib/apt/methods</code> for methods to call when importing from other repositories. </p>
 </dd>
<dt><code>-C, --component </code><i>components</i></dt>
<dd> <p> Limit the specified command to this components only. This will force added packages to this components, limit removing packages from this components, only list packages in this components, and/or otherwise only look at packages in this components, depending on the command in question. </p>
<p> Multiple components are specified by separating them with <code>|</code>, as in <code>-C &#8216;main|contrib&#8217;</code>. </p>
 </dd>
<dt><code>-A, --architecture </code><i>architectures</i></dt>
<dd> <p> Limit the specified command to this architectures only. (i.e. only list such packages, only remove packages from the specified architectures, or otherwise only look at/act on this architectures depending on the specific command). </p>
<p> Multiple architectures are specified by separating them with <code>|</code>, as in <code>-A &#8216;sparc|i386&#8217;</code>. </p>
<p> Note that architecture <code>all</code> packages can be included to each architecture but are then handled separately. Thus by using <code>-A</code> in a specific way one can have different versions of an architecture <code>all</code> package in different architectures of the same distribution. </p>
 </dd>
<dt><code>-T, --type </code>dsc|deb|udeb </dt>
<dd> <p> Limit the specified command to this packagetypes only. (i.e. only list such packages, only remove such packages, only include such packages, ...) </p>
 </dd>
<dt><code>-S, --section </code><i>section</i></dt>
<dd> <p> Overrides the section of inclusions. (Also override possible override files) </p>
 </dd>
<dt><code>-P, --priority </code><i>priority</i></dt>
<dd> <p> Overrides the priority of inclusions. (Also override possible override files) </p>
 </dd>
<dt><code>--export=</code>(<code>never</code>|<code>changed</code>|<code>lookedat</code>|<code>force</code>) </dt>
<dd> <p> This option specify whether and how the high level actions (e.g. install, update, pull, delete) should export the index files of the distributions they work with. </p>
 </dd>
<dt><code>--export=lookedat</code></dt>
<dd> <p> In this mode every distribution the action handled will be exported, unless there was an error possibly corrupting it. <br />
 <i>Note</i> that only missing files and files whose intended content changed between before and after the action will be written. To get a guaranteed current export, use the <code>export</code> action. <br />
 For backwards compatibility, <code>lookedat</code> is also available under the old name <code>normal</code>. The name <code>normal</code> is deprecated and will be removed in future versions. </p>
 </dd>
<dt><code>--export=changed</code></dt>
<dd> <p> In this mode every distribution actually changed will be exported, unless there was an error possibly corrupting it. (i.e. if nothing changed, not even missing files will be created.) <br />
 <i>Note</i> that only missing files and files whose intended content changed between before and after the action will be written. To get a guaranteed current export, use the <code>export</code> action. </p>
 </dd>
<dt><code>--export=force</code></dt>
<dd> <p> Always export all distributions looked at, even if there was some error possibly bringing it into a inconsistent state. </p>
 </dd>
<dt><code>--export=never</code></dt>
<dd> <p> No index files are exported. You will have to call <code>export</code> later. <br />
 <i>Note</i> that you most likely additionally need the <code>--keepunreferencedfiles</code> option, if you do not want some of the files pointed to by the untouched index files to vanish. </p>
 </dd>
<dt><code>--ignore=</code><i>what</i></dt>
<dd> <p> Ignore errors of type <i>what</i>. See the section <code>ERROR IGNORING</code> for possible values. </p>
 </dd>
<dt><code>--nolistsdownload</code></dt>
<dd> <p> When running <code>update</code>, <code>checkupdate</code> or <code>predelete</code> do not download any Release or index files. This is hardly useful except when you just run one of those command for the same distributions. And even then reprepro is usually good in not downloading except <code>Release</code> and <code>Release.gpg</code> files again. </p>
 </dd>
<dt><code>--nothingiserror</code></dt>
<dd> <p> If nothing was done, return with exitcode 1 instead of the usual 0. </p>
<p> Note that &quot;nothing was done&quot; means the primary purpose of the action in question. Auxillary actions (opening and closeing the database, exporting missing files with --export=lookedat, ...) usually do not count. Also note that this is not very well tested. If you find an action that claims to have done something in some cases where you think it should not, please let me know. </p>
 </dd>
<dt><code>--keeptemporaries</code></dt>
<dd> <p> Do not delete temporary <code>.new</code> files when exporting a distribution fails. (reprepro first create <code>.new</code> files in the <code>dists</code> directory and only if everything is generated, all files are put into their final place at once. If this option is not specified and something fails, all are deleted to keep <code>dists</code> clean). </p>
 </dd>
<dt><code>--keepunreferencedfiles</code></dt>
<dd> <p> Do not delete files that are no longer used because the package they are from is deleted/replaced with a newer version from the last distribution it was in. </p>
 </dd>
<dt><code>--keepunusednewfiles</code></dt>
<dd> <p> The include, includedsc, includedeb and processincoming by default delete any file they added to the pool that is not marked used at the end of the operation. While this keeps the pool clean and allows changing before trying to add again, this needs copying and checksum calculation every time one tries to add a file. </p>
 </dd>
<dt><code>--keepdirectories</code></dt>
<dd> <p> Do not try to rmdir parent directories after files or directories have been removed from them. (Do this if your directories have special permissions you want keep, do not want to be pestered with warnings about errors to remove them, or have a buggy rmdir call deleting non-empty directories.) </p>
 </dd>
<dt><code>--ask-passphrase</code></dt>
<dd> <p> Ask for passphrases when signing things and one is needed. This is a quick and dirty implementation using the obsolete <code><a href="/docs/linux/man/3-getpass/">getpass</a>(3)</code> function with the description gpgme is supplying. So the prompt will look quite funny and support for passphrases with more than 8 characters depend on your libc. I suggest using gpg-agent or something like that instead. </p>
 </dd>
<dt><code>--noskipold</code></dt>
<dd> <p> When updating do not skip targets where no new index files and no files marked as already processed are available. </p>
<p> If you changed a script to preprocess downloaded index files or changed a Listfilter, you most likely want to call reprepro with --noskipold. </p>
 </dd>
<dt><code>--waitforlock </code><i>count</i></dt>
<dd> <p> If there is a lockfile indicating another instance of reprepro is currently using the database, retry <i>count</i> times after waiting for 10 seconds each time. The default is 0 and means to error out instantly. </p>
 </dd>
<dt><code>--spacecheck full</code>|none </dt>
<dd> <p> The default is <code>full</code>: <br />
 In the update commands, check for every to be downloaded file which filesystem it is on and how much space is left. <br />
 To disable this behaviour, use <code>none</code>. </p>
 </dd>
<dt><code>--dbsafetymargin</code><i> bytes-count</i></dt>
<dd> <p> If checking for free space, reserve <i>byte-count</i> bytes on the filesystem containing the <code>db/</code> directory. The default is 104857600 (i.e. 100MB), which is quite large. But as there is no way to know in advance how large the databases will grow and libdb is extremely touchy in that regard, lower only when you know what you do. </p>
 </dd>
<dt><code>--safetymargin</code><i> bytes-count</i></dt>
<dd> <p> If checking for free space, reserve <i>byte-count</i> bytes on filesystems not containing the <code>db/</code> directory. The default is 1048576 (i.e. 1MB). </p>
 </dd>
<dt><code>--noguessgpgtty</code></dt>
<dd> <p> Don&#8217;t set the environment variable <code>GPG_TTY</code>, even when it is not set, stdin is terminal and <code>/proc/self/fd/0</code> is a readable symbolic link. </p>
 </dd>
<dt><code>--gnupghome</code></dt>
<dd> <p> Set the <code>GNUPGHOME</code> evnironment variable to the given directory as argument to this option. And your gpg will most likely use the content of this variable instead of &quot;~/.gnupg&quot;. Take a look at <code><a href="/docs/linux/man/1-gpg/">gpg</a></code>(1) to be sure. This option in the command line is usually not very useful, as it is possible to set the environment variable directly. Its main reason for existance is that it can be used in <i>conf</i><code>/options</code>. </p>
 </dd>
<dt><code>--gunzip</code><i> gz-uncompressor</i></dt>
<dd> <p> While reprepro links against <code>libz</code>, it will look for the program given with this option (or <code>gunzip</code> if not given) and use that when uncompressing index files while downloading from remote repositories. (So that downloading and uncompression can happen at the same time). If the program is not found or is <code>NONE</code> (all-uppercase) then uncompressing will always be done using the built in uncompression method. The program has to accept the compressed file as stdin and write the uncompressed file into stdout. </p>
 </dd>
<dt><code>--bunzip2</code><i> bz2-uncompressor</i></dt>
<dd> <p> When uncompressing downloaded index files or when not linked against <code>libbz2</code> reprepro will use this program to uncompress <code>.bz2</code> files. The default value is <code>bunzip2</code>. If the program is not found or is <code>NONE</code> (all-uppercase) then uncompressing will always be done using the built in uncompression method or not be possible when not linked against <code>libbz2</code>. The program has to accept the compressed file as stdin and write the uncompressed file into stdout. </p>
 </dd>
<dt><code>--unlzma</code><i> lzma-uncompressor</i></dt>
<dd> <p> When trying to uncompress or read lzma compressed files, this program will be used. The default value is <code>unlzma</code>. If the program is not found or is <code>NONE</code> (all-uppercase) then uncompressing lzma files will not be possible. The program has to accept the compressed file as stdin and write the uncompressed file into stdout. </p>
 </dd>
<dt><code>--unxz</code><i> xz-uncompressor</i></dt>
<dd> <p> When trying to uncompress or read xz compressed files, this program will be used. The default value is <code>unxz</code>. If the program is not found or is <code>NONE</code> (all-uppercase) then uncompressing xz files will not be possible. The program has to accept the compressed file as stdin and write the uncompressed file into stdout. </p>
 </dd>
<dt><code>--lunzip</code><i> lzip-uncompressor</i></dt>
<dd> <p> When trying to uncompress or read lzip compressed files, this program will be used. The default value is <code>lunzip</code>. If the program is not found or is <code>NONE</code> (all-uppercase) then uncompressing lz files will not be possible. The program has to accept the compressed file as stdin and write the uncompressed file into stdout. </p>
 </dd>
<dt><code>--list-max</code><i> count</i></dt>
<dd> <p> Limits the output of <code>list</code>, <code>listmatched</code> and <code>listfilter</code> to the first <i>count</i> results. The default is 0, which means unlimited. </p>
 </dd>
<dt><code>--list-skip</code><i> count</i></dt>
<dd> <p> Omitts the first <i>count</i> results from the output of <code>list</code>, <code>listmatched</code> and <code>listfilter</code>. </p>
 </dd>
<dt><code>--list-format</code><i> format</i></dt>
<dd> <p> Set the output format of <code>list</code>, <code>listmatched</code> and <code>listfilter</code> commands. The format is similar to dpkg-query&#8217;s <code>--showformat</code>: fields are specified as <code>${</code><i>fieldname</i><code>}</code> or <code>${</code><i>fieldname</i><code>;</code><i>length</i><code>}</code>. Zero length or no length means unlimited. Positive numbers mean fill with spaces right, negative fill with spaces left. </p>
<p> <code>\n</code>, <code>\r</code>, <code>\t</code>, <code>\0</code> are new-line, carriage-return, tabulator and zero-byte. Backslash (<code>\</code>) can be used to escape every non-letter-or-digit. </p>
<p> The special field names <code>$identifier</code>, <code>$architecture</code>, <code>$component</code>, <code>$type</code>, <code>$codename</code> denote where the package was found. </p>
<p> The special field names <code>$source</code> and <code>$sourceversion</code> denote the source and source version a package belongs to. (i.e. <code>${$source}</code> will either be the same as <code>${source}</code> (without a possible version in parentheses at the end) or the same as <code>${package}</code>. </p>
<p> The special field names <code>$basename</code>, <code>$filekey</code> and <code>$fullfilename</code> denote the first package file part of this entry (i.e. usually the .deb, .udeb or .dsc file) as basename, as filekey (filename relative to the outdir) and the full filename with outdir prepended (i.e. as relative or absolute as your outdir (or basedir if you did not set outdir) is). </p>
<p> When <code>--list-format</code> is not given or <code>NONE</code>, then the default is equivalent to <br />
 <code>${$identifier} ${package} ${version}\n</code>. </p>
<p> Escaping digits or letters not in above list, using dollars not escaped outside specified constructs, or any field names not listed as special and not consisting entirely out of letters, digits and minus signs have undefined behaviour and might change meaning without any further notice. </p>
<p> If you give this option on the command line, don&#8217;t forget that $ is also interpreted by your shell. So you have to properly escape it. For example by putting the whole argument to --list-format in single quotes. </p>
 </dd>
<dt><code>--show-percent</code></dt>
<dd> <p> When downloading packages, show each completed percent of completed package downloads together with the size of completely downloaded packages. (Repeating this option increases the frequency of this output). </p>
 </dd>
<dt><code>--onlysmalldeletes</code></dt>
<dd> <p> The pull and update commands will skip every distribution in which one target loses more than 20% of its packages (and at least 10). </p>
<p> Using this option (or putting it in the options config file) can avoid removing large quantities of data but means you might often give <code>--noonlysmalldeletes</code> to override it. </p>
 </dd>
<dt><code>--restrict </code><i>src</i>[=<i>version</i>|:<i>type</i>] </dt>
<dd> <p> Restrict a <code>pull</code> or <code>update</code> to only act on packages belonging to source-package <i>src</i>. Any other package will not be updated (unless it matches a <code>--restrict-bin</code>). Only packages that would otherwise be updated or are at least marked with <code>hold</code> in a <code>FilterList</code> or <code>FilerSrcList</code> will be updated. </p>
<p> The action can be restricted to a source version using a equal sign or changed to another type (see FilterList) using a colon. </p>
<p> This option can be given multiple times to list multiple packages, but each package may only be named once (even when there are different versions or types). </p>
 </dd>
<dt><code>--restrict-binary </code><i>name</i>[=<i>version</i>|:<i>type</i>] </dt>
<dd> <p> Like <code>--restrict</code> but restrict to binary packages (<code>.deb</code> and <code>.udeb</code>). Source packages are not upgraded unless they appear in a <code>--restrict</code>. </p>
 </dd>
<dt><code>--restrict-file </code><i>filename</i></dt>
<dd> <p> Like <code>--restrict</code> but read a whole file in the <code>FilterSrcList</code> format. </p>
 </dd>
<dt><code>--restrict-file-bin </code><i>filename</i></dt>
<dd> <p> Like <code>--restrict-bin</code> but read a whole file in the <code>FilterList</code> format. </p>
 </dd>
<dt><code>--endhook </code><i>hookscript</i></dt>
<dd> <p> Run the specified <i>hookscript</i> once reprepro exits. It will get the usual <code>REPREPRO_</code>* environment variables set (or unset) and additionally a variable <code>REPREPRO_EXIT_CODE</code> that is the exit code with which reprepro would have exited (the hook is always called once the initial parsing of global options and the command name is done, no matter if reprepro did anything or not). Reprepro will return to the calling process with the exitcode of this script. Reprepro has closed all its databases and removed all its locks, so you can run reprepro again in this script (unless someone else did so in the same repository before, of course). </p>
<p> The only advantage over running that command always directly after reprepro is that you can some environment variables set and cannot so easily forget it if this option is in conf/options. </p>
<p> The script is supposed to be located relative to <i>confdir</i>, unless its name starts with <code>/</code>, <code>./</code>, <code>+b/</code>, <code>+o/</code>, or <code>+c/</code> and the name may not start (except in the cases given before) with a <code>+</code>. </p>
<p> An example script looks like: <code> <br />
&nbsp;<wbr>#!/bin/sh <br />
&nbsp;<wbr> <br />
&nbsp;<wbr>if&nbsp;<wbr>[&nbsp;<wbr>&quot;$REPREPRO_EXIT_CODE&quot;&nbsp;<wbr>-ne 0&nbsp;<wbr>]&nbsp;<wbr>;&nbsp;<wbr>then <br />
&nbsp;<wbr><code>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr></code>exit&nbsp;<wbr>&quot;$REPREPRO_EXIT_CODE&quot;<br />
 <br />
&nbsp;<wbr>fi <br />
&nbsp;<wbr> <br />
&nbsp;<wbr>echo&nbsp;<wbr>&quot;congratulations, reprepro with arguments:&nbsp;<wbr>$*&quot; <br />
&nbsp;<wbr>echo&nbsp;<wbr>&quot;seems to have run successfully. REPREPRO_&nbsp;<wbr>part of the environment is:&quot; <br />
&nbsp;<wbr>set | grep&nbsp;<wbr>^REPREPRO_ <br />
&nbsp;<wbr> <br />
&nbsp;<wbr>exit 0 <br />
&nbsp;<wbr></code> </p>
 </dd>
<dt><code>--outhook </code><i>hookscript</i></dt>
<dd> <p> <i>hookscript</i> is called with a <code>.outlog</code> file as argument (located in <i>logdir</i>) containing a description of all changes made to <i>outdir</i>. </p>
<p> The script is supposed to be located relative to <i>confdir</i>, unless its name starts with <code>/</code>, <code>./</code>, <code>+b/</code>, <code>+o/</code>, or <code>+c/</code> and the name may not start (except in the cases given before) with a <code>+</code>. </p>
<p> For a format of the <code>.outlog</code> files generated for this script see the <code>manual.html</code> shiped with reprepro. </p>
 </dd></dl>
<h2>COMMANDS</h2>
<dl>
<dt><code>export</code> [ <i>codenames</i> ] </dt>
<dd> <p> Generate all index files for the specified distributions. </p>
<p> This regenerates all files unconditionally. It is only useful if you want to be sure <code>dists</code> is up to date, you called some other actions with <code>--export=never</code> before or you want to create an initial empty but fully equipped <code>dists/</code><i>codename</i> directory. </p>
 </dd>
<dt> [ <code>--delete</code> ] <code>createsymlinks</code> [ <i>codenames</i> ] </dt>

<dt><code>listfilter </code><i>codename</i><i>condition</i></dt>
<dd> <p> as list, but does not list a single package, but all packages matching the given condition. </p>
<p> The format of the formulas is those of the dependency lines in Debian packages&#8217; control files with some extras. That means a formula consists of names of fields with a possible condition for its content in parentheses. These atoms can be combined with an exclamation mark &#8216;!&#8216; (meaning not), a pipe symbol &#8216;|&#8216; (meaning or) and a comma &#8216;,&#8216; (meaning and). Additionally parentheses can be used to change binding (otherwise &#8216;!&#8216; binds more than &#8216;|&#8216; than &#8216;,&#8216;). </p>
<p> The values given in the search expression are directly alphabetically compared to the headers in the respective index file. That means that each part <i>Fieldname</i><code> (</code><i>cmp</i><i>value</i><code>)</code> of the formula will be true for exactly those package that have in the <code>Package</code> or <code>Sources</code> file a line starting with <i>fieldname</i> and a value is alphabetically <i>cmp</i> to <i>value</i>. </p>
<p> Additionally since reprepro 3.11.0, &#8216;<code>%</code>&#8216; can be used as comparison operator, denoting matching a name with shell like wildcard (with &#8216;<code>*</code>&#8216;, &#8216;<code>?</code>&#8216; and &#8216;<code>[</code>..<code>]</code>&#8216;). </p>
<p> The special field names starting with &#8216;<code>$</code>&#8216; have special meaning (available since 3.11.1): </p>
<p> <code>$Version</code> </p>
<p> The version of the package, comparison is not alphabetically, but as Debian version strings. </p>
<p> <code>$Source</code> </p>
<p> The source name of the package. </p>
<p> <code>$SourceVersion</code> </p>
<p> The source version of the package. </p>
<p> <code>$Architecture</code> </p>
<p> The architecture the package is in (listfilter) or to be put into. </p>
<p> <code>$Component</code> </p>
<p> The component the package is in (listfilter) or to be put into. </p>
<p> <code>$Packagetype</code> </p>
<p> The packagetype of the package. </p>
<p> Examples: </p>
<p> <code>reprepro -b . listfilter test2 &#8216;Section (== admin)&#8216;</code> will list all packages in distribution test2 with a Section field and the value of that field being <code>admin</code>. </p>
<p> <code>reprepro -b . -T deb listfilter test2 &#8216;Source (== </code><i>blub</i>) | ( !Source , Package (== <i>blub</i>) )&#8216; will find all .deb Packages with either a Source field blub or no Source field and a Package field blub. (That means all package generated by a source package <i>blub</i>, except those also specifying a version number with its Source). </p>
<p> <code>reprepro -b . -T deb listfilter test2 &#8216;$Source (==</code><i>blub</i>) is the better way to do this (but only available since 3.11.1). </p>
<p> <code>reprepro -b . listfilter test2 &#8216;$PackageType (==deb), $Source (==</code><i>blub</i>) is another (less efficient) way. </p>
<p> <code>reprepro -b . listfilter test2 &#8216;Package (% linux-*-2.6*)&#8216;</code> lists all packages with names starting with <code>linux-</code> and later having an <code>-2.6</code>. </p>
 </dd>

<h2>CONFIG FILES</h2>
<p> <code>reprepo</code> uses three config files, which are searched in the directory specified with <code>--confdir</code> or in the <code>conf/</code> subdirectory of the <i>basedir</i>. </p>
<p> If a file <code>options</code> exists, it is parsed line by line. Each line can be the long name of a command line option (without the --) plus an argument, where possible. Those are handled as if they were command line options given before (and thus lower priority than) any other command line option. (and also lower priority than any environment variable). </p>
<p> To allow command line options to override options file options, most boolean options also have a corresponding form starting with <code>--no</code>. </p>
<p> (The only exception is when the path to look for config files changes, the options file will only opened once and of course before any options within the options file are parsed.) </p>
<p> The file <code>distributions</code> is always needed and describes what distributions to manage, while <code>updates</code> is only needed when syncing with external repositories and <code>pulls</code> is only needed when syncing with repositories in the same reprepro database. </p>
<p> The last three are in the format control files in Debian are in, i.e. paragraphs separated by empty lines consisting of fields. Each field consists of a fieldname, followed by a colon, possible whitespace and the data. A field ends with a newline not followed by a space or tab. </p>
<p> Lines starting with # as first character are ignored, while in other lines the # character and everything after it till the newline character are ignored. </p>
<p> A paragraph can also consist of only a single field &quot;<code>!include:</code>&quot; which causes the named file (relative to confdir unless starting with <code>~/</code>, <code>+b/</code>, <code>+c/</code> or <code>/</code> ) to be read as if it was found at this place. </p>
<p> Each of the three files or a file included as described above can also be a directory, in which case all files it contains with a filename ending in <code>.conf</code> and not starting with <code>.</code> are read.  </p>
<h3>conf/distributions</h3>
<dl>
<dt><code>Codename</code></dt>
<dd> <p> This required field is the unique identifier of a distribution and used as directory name within <code>dists/</code> It is also copied into the Release files. </p>
<p> Note that this name is not supposed to change. You most likely <code>never ever</code> want a name like <code>testing</code> or <code>stable</code> here (those are suite names and supposed to point to another distribution later). </p>
 </dd>
<dt><code>Suite</code></dt>
<dd> <p> This optional field is simply copied into the Release files. In Debian it contains names like stable, testing or unstable. To create symlinks from the Suite to the Codename, use the <code>createsymlinks</code> command of reprepro. </p>
 </dd>
<dt><code>FakeComponentPrefix</code></dt>
<dd> <p> If this field is present, its argument is added - separated by a slash - before every Component written to the main Release file (unless the component already starts with it), and removed from the end of the Codename and Suite fields in that file. Also if a component starts with it, its directory in the dists dir is shortened by this. <br />
 So <code> <br />
&nbsp;<wbr>Codename: bla/updates <br />
&nbsp;<wbr>Suite: foo/updates <br />
&nbsp;<wbr>FakeComponentPrefix: updates <br />
&nbsp;<wbr>Components: main bad </code> will create a Release file with <code> <br />
&nbsp;<wbr>Codename: bla <br />
&nbsp;<wbr>Suite: foo <br />
&nbsp;<wbr>Components: updates/main updates/bad </code> in it, but otherwise nothing is changed, while <code> <br />
&nbsp;<wbr>Codename: bla/updates <br />
&nbsp;<wbr>Suite: foo/updates <br />
&nbsp;<wbr>FakeComponentPrefix: updates <br />
&nbsp;<wbr>Components: updates/main updates/bad </code> will also create a Release file with <code> <br />
&nbsp;<wbr>Codename: bla <br />
&nbsp;<wbr>Suite: foo <br />
&nbsp;<wbr>Components: updates/main updates/bad </code> but the packages will actually be in the components <code>updates/main</code> and <code>updates/bad</code>, most likely causing the same file using duplicate storage space. </p>
<p> This makes the distribution look more like Debian&#8217;s security archive, thus work around problems with apt&#8217;s workarounds for that. </p>
 </dd>
<dt><code>AlsoAcceptFor</code></dt>
<dd> <p> A list of distribution names. When a <code>.changes</code> file is told to be included into this distribution with the <code>include</code> command and the distribution header of that file is neither the codename, nor the suite name, nor any name from the list, a <code>wrongdistribution</code> error is generated. The <code>process_incoming</code> command will also use this field, see the description of <code>Allow</code> and <code>Default</code> from the <code>conf/incoming</code> file for more information. </p>
 </dd>
<dt><code>Version</code></dt>
<dd> <p> This optional field is simply copied into the Release files. </p>
 </dd>
<dt><code>Origin</code></dt>
<dd> <p> This optional field is simply copied into the Release files. </p>
 </dd>
<dt><code>Label</code></dt>
<dd> <p> This optional field is simply copied into the Release files. </p>
 </dd>
<dt><code>NotAutomatic</code></dt>
<dd> <p> This optional field is simply copied into the Release files. (The value is handled as an arbitrary string, though anything but <code>yes</code> does not make much sense right now.) </p>
 </dd>
<dt><code>ButAutomaticUpgrades</code></dt>
<dd> <p> This optional field is simply copied into the Release files. (The value is handled as an arbitrary string, though anything but <code>yes</code> does not make much sense right now.) </p>
 </dd>
<dt><code>Description</code></dt>
<dd> <p> This optional field is simply copied into the Release files. </p>
 </dd>
<dt><code>Architectures</code></dt>
<dd> <p> This required field lists the binary architectures within this distribution and if it contains <code>source</code> (i.e. if there is an item <code>source</code> in this line this Distribution has source. All other items specify things to be put after &quot;binary-&quot; to form directory names and be checked against &quot;Architecture:&quot; fields.) </p>
<p> This will also be copied into the Release files. (With exception of the <code>source</code> item, which will not occur in the topmost Release file whether it is present here or not) </p>
 </dd>
<dt><code>Components</code></dt>
<dd> <p> This required field lists the component of a distribution. See <code>GUESSING</code> for rules which component packages are included into by default. This will also be copied into the Release files. </p>
 </dd>
<dt><code>UDebComponents</code></dt>
<dd> <p> Components with a debian-installer subhierarchy containing .udebs. (E.g. simply &quot;main&quot;) </p>
 </dd>
<dt><code>Update</code></dt>
<dd> <p> When this field is present, it describes which update rules are used for this distribution. There also can be a magic rule minus (&quot;-&quot;), see below. </p>
 </dd>
<dt><code>Pull</code></dt>
<dd> <p> When this field is present, it describes which pull rules are used for this distribution. Pull rules are like Update rules, but get their stuff from other distributions and not from external sources. See the description for <code>conf/pulls</code>. </p>
 </dd>
<dt><code>SignWith</code></dt>
<dd> <p> When this field is present, a Release.gpg file will be generated. If the value is &quot;yes&quot; or &quot;default&quot;, the default key of gpg is used. If the field starts with an exlamation mark (&quot;!&quot;), the given script is executed to do the signing. Otherwise the value will be given to libgpgme to determine to key to use. </p>
<p> If there are problems with signing, you can try <br />
 <code>gpg --list-secret-keys </code><i>value</i> <br />
 to see how gpg could interprete the value. If that command does not list any keys or multiple ones, try to find some other value (like the keyid), that gpg can more easily associate with a unique key. </p>
<p> If this key has a passphrase, you need to use gpg-agent or the insecure option <code>--ask-passphrase</code>. </p>
<p> A &#8216;<code>!</code>&#8216; hook script is looked for in the confdir, unless it starts with <code>~/</code>, <code>./</code>, <code>+b/</code>, <code>+o/</code>, <code>+c/</code> or <code>/</code> . Is gets three command line arguments: The filename to sign, an empty argument or the filename to create with an inline signature (i.e. InRelease) and an empty argument or the filename to create an detached signature (i.e. Release.gpg). The script may generate no Release.gpg file if it choses to (then the repository will look like unsigned for older clients), but generating empty files is not allowed. Reprepro waits for the script to finish and will abort the exporting of the distribution this signing is part of unless the scripts returns normally with exit code 0. Using a space after ! is recommended to avoid incompatibilities with possible future extensions. </p>
 </dd>
<dt><code>DebOverride</code></dt>
<dd> <p> When this field is present, it describes the override file used when including .deb files. </p>
 </dd>
<dt><code>UDebOverride</code></dt>
<dd> <p> When this field is present, it describes the override file used when including .udeb files. </p>
 </dd>
<dt><code>DscOverride</code></dt>
<dd> <p> When this field is present, it describes the override file used when including .dsc files. </p>
 </dd>
<dt><code>DebIndices</code>, <code>UDebIndices</code>, <code>DscIndices</code></dt>
<dd> <p> Choose what kind of Index files to export. The first part describes what the Index file shall be called. The second argument determines the name of a Release file to generate or not to generate if missing. Then at least one of &quot;<code>.</code>&quot;, &quot;<code>.gz</code>&quot;, &quot;<code>.xz</code>&quot; or &quot;<code>.bz2</code>&quot; specifying whether to generate uncompressed output, gzipped output, bzip2ed output or any combination. (bzip2 is only available when compiled with bzip2 support, so it might not be available when you compiled it on your own, same for xz and liblzma). If an argument not starting with dot follows, it will be executed after all index files are generated. (See the examples for what argument this gets). The default is: <br />
 DebIndices: Packages Release . .gz <br />
 UDebIndices: Packages . .gz <br />
 DscIndices: Sources Release .gz </p>
 </dd>
<dt><code>ExportOptions</code></dt>
<dd> <p> Options to modify how and if exporting is done: <br />
 <code>noexport</code> Never export this distribution. That means there will be no directory below <code>dists/</code> generated and the distribution is only useful to copy packages to other distributions. <br />
 <code>keepunknown</code> Ignore unknown files and directories in the exported directory. This is currently the only available option and the default, but might change in the future, so it can already be requested explicitely. </p>
 </dd>
<dt><code>Contents</code></dt>
<dd> <p> Enable the creation of Contents files listing all the files within the binary packages of a distribution. (Which is quite slow, you have been warned). </p>
<p> In earlier versions, the first argument was a rate at which to extract file lists. As this did not work and was no longer easily possible after some factorisation, this is no longer supported. </p>
<p> The arguments of this field is a space separated list of options. If there is a <code>udebs</code> keyword, <code>.udeb</code>s are also listed (in a file called <code>uContents-</code><i>architecture</i>.) If there is a <code>nodebs</code> keyword, <code>.deb</code>s are not listed. (Only useful together with <code>udebs</code>) If there is at least one of the keywords <code>.</code>, <code>.gz</code>, <code>.xz</code> and/or <code>.bz2</code>, the Contents files are written uncompressed, gzipped and/or bzip2ed instead of only gzipped. </p>
<p> If there is a <code>percomponent</code> then one Contents-<i>arch</i> file per component is created. If there is a <code>allcomponents</code> then one global Contents-<i>arch</i> file is generated. If both are given, both are created. If none of both is specified then <code>percomponent</code> is taken as default (earlier versions had other defaults). </p>
<p> The switches <code>compatsymlink</code> or <code>nocompatsymlink</code> (only possible if <code>allcomponents</code> was not specified explicitly) control whether a compatibility symlink is created so old versions of apt-file looking for the component independent filenames at least see the contents of the first component. </p>
<p> Unless <code>allcomponents</code> is given, <code>compatsymlinks</code> currently is the default, but that will change in some future (current estimate: after wheezy was released) </p>
 </dd>
<dt><code>ContentsArchitectures</code></dt>
<dd> <p> Limit generation of Contents files to the architectures given. If this field is not there, all architectures are processed. An empty field means no architectures are processed, thus not very useful. </p>
 </dd>
<dt><code>ContentsComponents</code></dt>
<dd> <p> Limit what components are processed for the <code>Contents-</code><i>arch</i> files to the components given. If this field is not there, all components are processed. An empty field is equivalent to specify <code>nodebs</code> in the <code>Contents</code> field, while a non-empty field overrides a <code>nodebs</code> there. </p>
 </dd>
<dt><code>ContentsUComponents</code></dt>
<dd> <p> Limit what components are processed for the uContents files to the components given. If this field is not there and there is the <code>udebs</code> keyword in the Contents field, all .udebs of all components are put in the <code>uContents.</code><i>arch</i> files. If this field is not there and there is no <code>udebs</code> keyword in the Contents field, no <code>uContents-</code><i>arch</i> files are generated at all. A non-empty fields implies generation of <code>uContents-</code><i>arch</i> files (just like the <code>udebs</code> keyword in the Contents field), while an empty one causes no <code>uContents-</code><i>arch</i> files to be generated. </p>
 </dd>
<dt><code>Uploaders</code></dt>
<dd> <p> Specifies a file (relative to confdir if not starting with <code>~/</code>, <code>+b/</code>, <code>+c/</code> or <code>/</code> ) to specify who is allowed to upload packages. Without this there are no limits, and this file can be ignored via <code>--ignore=uploaders</code>. See the section <code>UPLOADERS FILES</code> below. </p>
 </dd>
<dt><code>Tracking</code></dt>
<dd> <p> Enable the (experimental) tracking of source packages. The argument list needs to contain exactly one of the following: <br />
 <code>keep</code> Keeps all files of a given source package, until that is deleted explicitly via <code>removetrack</code>. This is currently the only possibility to keep older packages around when all indices contain newer files. <br />
 <code>all</code> Keep all files belonging to a given source package until the last file of it is no longer used within that distribution. <br />
 <code>minimal</code> Remove files no longer included in the tracked distribution. (Remove changes, logs and includebyhand files once no file is in any part of the distribution). <br />
 And any number of the following (or none): <br />
 <code>includechanges</code> Add the .changes file to the tracked files of a source package. Thus it is also put into the pool. <br />
 <code>includebyhand</code> Add <code>byhand</code> and <code>raw-</code><i>*</i> files to the tracked files and thus in the pool. <br />
 <code>includelogs</code> Add log files to the tracked files and thus in the pool. (Not that putting log files in changes files is a reprepro extension not found in normal changes files) <br />
 <code>embargoalls</code> Not yet implemented. <br />
 <code>keepsources</code> Even when using minimal mode, do not remove source files until no file is needed any more. <br />
 <code>needsources</code> Not yet implemented. </p>
 </dd>
<dt><code>Log</code></dt>
<dd> <p> Specify a file to log additions and removals of this distribution into and/or external scripts to call when something is added or removed. The rest of the <code>Log:</code> line is the filename, every following line (as usual, have to begin with a single space) the name of a script to call. The name of the script may be preceded with options of the form <code>--type=</code>(<code>dsc</code>|<code>deb</code>|<code>udeb</code>), <code>--architecture=</code><i>name</i> or <code>--component=</code><i>name</i> to only call the script for some parts of the distribution. An script with argument <code>--changes</code> is called when a <code>.changes</code> file was accepted by <code>include</code> or <code>processincoming</code> (and with other arguments). Both type of scripts can have a <code>--via=</code><i>command</i> specified, in which case it is only called when caused by reprepro command <i>command</i>. </p>
<p> For information how it is called and some examples take a look at manual.html in reprepro&#8217;s source or <code>/usr/share/doc/reprepro/</code> </p>
<p> If the filename for the log files does not start with a slash, it is relative to the directory specified with <code>--logdir</code>, the scripts are relative to <code>--confdir</code> unless starting with <code>~/</code>, <code>+b/</code>, <code>+c/</code> or <code>/</code>. </p>
 </dd>
<dt><code>ValidFor</code></dt>
<dd> <p> If this field exists, an Valid-Until field is put into generated <code>Release</code> files for this distribution with an date as much in the future as the argument specifies. </p>
<p> The argument has to be an number followed by one of the units <code>d</code>, <code>m</code> or <code>y</code>, where <code>d</code> means days, <code>m</code> means 31 days and <code>y</code> means 365 days. So <code>ValidFor: 1m 11 d</code> causes the generation of a <code>Valid-Until:</code> header in Release files that points 42 days into the future. </p>
 </dd>
<dt><code>ReadOnly</code></dt>
<dd> <p> Disallow all modifications of this distribution or its directory in <code>dists/</code><i>codename</i> (with the exception of snapshot subdirectories). </p>
 </dd>
<dt><code>ByHandHooks</code></dt>
<dd> <p> This species hooks to call for handling byhand/raw files by processincoming (and in future versions perhaps by include). </p>
<p> Each line consists out of 4 arguments: A glob pattern for the section (clasically <code>byhand</code>, though Ubuntu uses <code>raw-</code>*), a glob pattern for the priority (not usually used), and a glob pattern for the filename. </p>
<p> The 4th argument is the script to be called when all of the above match. It gets 5 arguments: the codename of the distribution, the section (usually <code>byhand</code>), the priority (usually only <code>-</code>), the filename in the changes file and the full filename (with processincoming in the secure TempDir). </p>
 </dd></dl>
<h3>conf/updates</h3>
<dl>
<dt><code>Name</code></dt>
<dd> <p> The name of this update-upstream as it can be used in the <code>Update</code> field in conf/distributions. </p>
 </dd>
<dt><code>Method</code></dt>
<dd> <p> An URI as one could also give it apt, e.g. <i><a rel="nofollow" href="http://ftp.debian.de/debian">http://ftp.debian.de/debian</a></i> which is simply given to the corresponding <code>apt-get</code> method. (So either <code>apt-get has to be installed, or you have to point with</code> <code>--methoddir</code> to a place where such methods are found. </p>
 </dd>
<dt><code>Fallback</code></dt>
<dd> <p> (Still experimental:) A fallback URI, where all files are tried that failed the first one. They are given to the same method as the previous URI (e.g. both <a rel="nofollow" href="http://">http://</a>), and the fallback-server must have everything at the same place. No recalculation is done, but single files are just retried from this location. </p>
 </dd>
<dt><code>Config</code></dt>
<dd> <p> This can contain any number of lines, each in the format <code>apt-get --option</code> would expect. (Multiple lines - as always - marked with leading spaces). </p>
 </dd></dl>
<p> For example: Config: Acquire::Http::Proxy=<a rel="nofollow" href="http://proxy.yours.org:8080">http://proxy.yours.org:8080</a> </p>
<dl>
<dt><code>From</code></dt>
<dd> <p> The name of another update rule this rules derives from. The rule containing the <code>From</code> may not contain <code>Method</code>, <code>Fallback</code> or <code>Config</code>. All other fields are used from the rule referenced in <code>From</code>, unless found in this containing the <code>From</code>. The rule referenced in <code>From</code> may itself contain a <code>From</code>. Reprepro will only assume two remote index files are the same, if both get their <code>Method</code> information from the same rule. </p>
 </dd>
<dt><code>Suite</code></dt>
<dd> <p> The suite to update from. If this is not present, the codename of the distribution using this one is used. Also &quot;*/whatever&quot; is replaced by &quot;&lt;codename&gt;/whatever&quot; </p>
 </dd>
<dt><code>Components</code></dt>
<dd> <p> The components to update. Each item can be either the name of a component or a pair of a upstream component and a local component separated with &quot;&gt;&quot;. (e.g. &quot;main&gt;all contrib&gt;all non-free&gt;notall&quot;) </p>
<p> If this field is not there, all components from the distribution to update are tried. </p>
<p> An empty field means no source or .deb packages are updated by this rule, but only .udeb packages, if there are any. </p>
<p> A rule might list components not available in all distributions using this rule. In this case unknown components are silently ignored. (Unless you start reprepro with the <code>--fast</code> option, it will warn about components unusable in all distributions using that rule. As exceptions, unusable components called <code>none</code> are never warned about, for compatibility with versions prior to 3.0.0 where and empty field had a different meaning.) </p>
 </dd>
<dt><code>Architectures</code></dt>
<dd> <p> The architectures to update. If omitted all from the distribution to update from. (As with components, you can use &quot;&gt;&quot; to download from one architecture and add into another one. (This only determine in which Package list they land, it neither overwrites the Architecture line in its description, nor the one in the filename determined from this one. In other words, it is no really useful without additional filtering)) </p>
 </dd>
<dt><code>UDebComponents</code></dt>
<dd> <p> Like <code>Components</code> but for the udebs. </p>
 </dd>
<dt><code>VerifyRelease</code></dt>
<dd> <p> Download the <code>Release.gpg</code> file and check if it is a signature of the <code>Releasefile</code> with the key given here. (In the Format as &quot;gpg --with-colons --list-key&quot; prints it, i.e. the last 16 hex digits of the fingerprint) Multiple keys can be specified by separating them with a &quot;<code>|</code>&quot; sign. Then finding a signature from one of the will suffice. To allow revoked or expired keys, add a &quot;<code>!</code>&quot; behind a key. (but to accept such signatures, the appropriate <code>--ignore</code> is also needed). To also allow subkeys of a specified key, add a &quot;<code>+</code>&quot; behind a key. </p>
 </dd>
<dt><code>IgnoreRelease: yes</code></dt>
<dd> <p> If this is present, no <code>InRelease</code> or <code>Release</code> file will be downloaded and thus the md5sums of the other index files will not be checked. </p>
 </dd>
<dt><code>GetInRelease: no</code></dt>
<dd> <p> IF this is present, no <code>InRelease</code> file is downloaded but only <code>Release</code> (and <code>Release.gpg</code> ) are tried. </p>
 </dd>
<dt><code>Flat</code></dt>
<dd> <p> If this field is in an update rule, it is supposed to be a flat repository, i.e. a repository without a <code>dists</code> dir and no subdirectories for the index files. (If the corresponding <code>sources.list</code> line has the suite end with a slash, then you might need this one.) The argument for the <code>Flat:</code> field is the Component to put those packages into. No <code>Components</code> or <code>UDebComponents</code> fields are allowed in a flat update rule. If the <code>Architecture</code> field has any <code>&gt;</code> items, the part left of the &quot;<code>&gt;</code>&quot; is ignored. <br />
 For example the <code>sources.list</code> line <br />
&nbsp;<wbr>deb&nbsp;<wbr><a rel="nofollow" href="http://cran.r-project.org/bin/linux/debian">http://cran.r-project.org/bin/linux/debian</a>&nbsp;<wbr>etch-cran/ <br />
 would translate to <br />
 <br />
&nbsp;<wbr>Name: R <br />
&nbsp;<wbr>Method:&nbsp;<wbr><a rel="nofollow" href="http://cran.r-project.org/bin/linux/debian">http://cran.r-project.org/bin/linux/debian</a> <br />
&nbsp;<wbr>Suite: etch-cran <br />
&nbsp;<wbr>Flat: whatevercomponentyoudlikethepackagesin </p>
 </dd>
<dt><code>IgnoreHashes</code></dt>
<dd> <p> This directive tells reprepro to not check the listed hashes in the downloaded Release file (and only in the Release file). Possible values are currently <code>md5</code>, <code>sha1</code> and <code>sha256</code>. </p>
<p> Note that this does not speed anything up in any measurable way. The only reason to specify this if the Release file of the distribution you want to mirror from uses a faulty algorithm implementation. Otherwise you will gain nothing and only lose security. </p>
 </dd>
<dt><code>FilterFormula</code></dt>
<dd> <p> This can be a formula to specify which packages to accept from this source. The format is misusing the parser intended for Dependency lines. To get only architecture all packages use &quot;architecture (== all)&quot;, to get only at least important packages use &quot;priority (==required) | priority (==important)&quot;. </p>
<p> See the description of the listfilter command for the semantics of formulas. </p>
 </dd>
<dt><code>FilterList</code>, FilterSrcList </dt>
<dd> <p> These take at least two arguments: The first one is the default action when something is not found in the list, then a list of filenames (relative to <code>--confdir</code>, if not starting with <code>~/</code>, <code>+b/</code>, <code>+c/</code> or <code>/</code> ) in the format of dpkg --get-selections and only packages listed in there as <code>install</code> or that are already there and are listed with <code>upgradeonly</code> will be installed. Things listed as <code>deinstall</code> or <code>purge</code> will be ignored. Packages having <code>supersede</code> will not be installed but instead cause the removal of packages with strictly smaller version (i.e. if a package would be replaced by this package if this was <code>install</code>, it will be removed instead and no new package being installed). Things listed with <code>warning</code> are also ignored, but a warning message is printed to stderr. A package being <code>hold</code> will not be upgraded but also not downgraded or removed by previous delete rules. To abort the whole upgrade/pull if a package is available, use <code>error</code>. Instead of a keyword you can also use &quot;<code>= </code><i>version</i>&quot; which is treated like <code>install</code> if the version matches and like no entry if it does not match. Only one such entry per package is currently supported and the version is currently compared as string. </p>
<p> If there is both <code>FilterList</code> and <code>FilterSrcList</code> then the first is used for <code>.deb</code> and <code>.udeb</code> and the second for <code>.dsc</code> packages. If there is only <code>FilterList</code> that is applied to everything. If there is only <code>FilterSrcList</code> that is applied to everything, too, but the source package name (and source version) is used to do the lookup. </p>
 </dd>
<dt><code>OmitExtraSourceOnly</code></dt>
<dd> <p> This field controls whether source packages with Extra-Source-Only set are ignore when getting source packages. Withouth this option or if it is true, those source packages are ignored, while if set to no or false, those source packages are also condidates if no other filter excludes them. (The default of true will likely change once reprepro supports multiple versions of a package or has other means to keep the source packages around). </p>
 </dd>
<dt><code>ListHook</code></dt>
<dd> <p> If this is given, it is executed for all downloaded index files with the downloaded list as first and a filename that will be used instead of this. (e.g. &quot;ListHook: /bin/cp&quot; works but does nothing.) </p>
<p> If a file will be read multiple times, it is processed multiple times, with the environment variables <code>REPREPRO_FILTER_CODENAME</code>, <code>REPREPRO_FILTER_PACKAGETYPE</code>, <code>REPREPRO_FILTER_COMPONENT</code> and <code>REPREPRO_FILTER_ARCHITECTURE</code> set to the where this file will be added and <code>REPREPRO_FILTER_PATTERN</code> to the name of the update rule causing it. </p>
 </dd>
<dt><code>ListShellHook</code></dt>
<dd> <p> This is like ListHook, but the whole argument is given to the shell as argument, and the input and output file are stdin and stdout. </p>
<p> i.e.: <br />
 ListShellHook: cat <br />
 works but does nothing but useless use of a shell and cat, while <br />
 ListShellHook: grep-dctrl -X -S apt -o -X -S dpkg || [ $? -eq 1 ] <br />
 will limit the update rule to packages from the specified source packages. </p>
 </dd>
<dt><code>DownloadListsAs</code></dt>
<dd> <p> The arguments of this field specify which index files reprepro will download. </p>
<p> Allowed values are <code>.</code>, <code>.gz</code>, <code>.bz2</code>, <code>.lzma</code>, <code>.xz</code>, <code>.lz</code>, <code>.diff</code>, <code>force.gz</code>, <code>force.bz2</code>, <code>force.lzma</code>, <code>force.xz</code>, <code>force.lz</code>, and <code>force.diff</code>. </p>
<p> Reprepro will try the first supported variant in the list given: Only compressions compiled in or for which an uncompressor was found are used. Unless the value starts with <code>force.</code>, it is only tried if if is found in the Release or InRelease file. </p>
<p> The default value is <code>.diff .xz .lzma .bz2 .gz .</code>, i.e. download Packages.diff if listed in the Release file, otherwise or if not usable download .xz if listed in the Release file and there is a way to uncompress it, then .lzma if usable, then .bz2 if usable, then .gz and then uncompressed). </p>
<p> Note there is no way to see if an uncompressed variant of the file is available (as the Release file always lists their checksums, even if not there), so putting &#8216;<code>.</code>&#8216; anywhere but as the last argument can mean trying to download a file that does not exist. </p>
<p> Together with <code>IgnoreRelease</code> reprepro will download the first in this list that could be unpacked (i.e. <code>force</code> is always assumed) and the default value is <code>.gz .bzip2 . .lzma .xz</code>. </p>
 </dd></dl>
<h3>conf/pulls</h3>
<p> This file contains the rules for pulling packages from one distribution to another. While this can also be done with update rules using the file or copy method and using the exported indices of that other distribution, this way is faster. It also ensures the current files are used and no copies are made. (This also leads to the limitation that pulling from one component to another is not possible.) </p>
<p> Each rule consists out of the following fields: </p>
<dl>
<dt><code>Name</code></dt>
<dd> <p> The name of this pull rule as it can be used in the <code>Pull</code> field in conf/distributions. </p>
 </dd>
<dt><code>From</code></dt>

 </dd>
<dt><code>Components</code></dt>

<p> A rule might list components not available in all distributions using this rule. In this case unknown components are silently ignored. (Unless you start reprepro with the --fast option, it will warn about components unusable in all distributions using that rule. As exception, unusable components called <code>none</code> are never warned about, for compatibility with versions prior to 3.0.0 where and empty field had a different meaning.) </p>
 </dd>
<dt><code>Architectures</code></dt>

As in <code>conf/updates</code>, you can use &quot;&gt;&quot; to download from one architecture and add into another one. (And again, only useful with filtering to avoid packages not architecture <code>all</code> to migrate). </p>
 </dd>
<dt><code>UDebComponents</code></dt>
<dd> <p> Like <code>Components</code> but for the udebs. </p>
 </dd>
<dt><code>FilterFormula</code></dt>
<dd>  </dd>

<h2>OVERRIDE FILES</h2>
<p> The format of override files used by reprepro should resemble the extended ftp-archive format, to be specific it is: </p>
<p> <i>packagename</i> <i>field name</i> <i>new value</i> </p>
<p> For example: <br />
 <code>kernel-image-2.4.31-yourorga Section protected/base</code> <br />
 <code>kernel-image-2.4.31-yourorga Priority standard</code> <br />
 <code>kernel-image-2.4.31-yourorga Maintainer That&#8217;s me &lt;me [at] localhost&gt;</code> <br />
 <code>reprepro Priority required</code> </p>
<p> All fields of a given package will be replaced by the new value specified in the override file with the exception of special fields starting with a dollar sign ($). While the field name is compared case-insensitive, it is copied in exactly the form in the override file there. (Thus I suggest to keep to the exact case it is normally found in index files in case some other tool confuses them.) More than copied is the Section header (unless <code>-S</code> is supplied), which is also used to guess the component (unless <code>-C</code> is there). </p>
<p> Some values like <code>Package</code>, <code>Filename</code>, <code>Size</code> or <code>MD5sum</code> are forbidden, as their usage would severly confuse reprepro. </p>
<p> As an extension reprepro also supports patterns instead of packagenames. If the package name contains &#8216;*&#8216;, &#8216;[&#8216; or &#8216;?&#8216;, it is considered a pattern and applied to each package that is not matched by any non-pattern override nor by any previous pattern. </p>
<p> Fieldnames starting with a dollar ($) are not be placed in the exported control data but have special meaning. Unknown ones are loudly ignored. Special fields are: </p>
<p> <br />
&nbsp;<wbr><code>$Component</code>: includedeb, includedsc, include and processincoming will put the package in the component given as value (unless itself overridden with <code>-C</code>). Note that the proper way to specify the component is by setting the section field and using this extension will most likely confuse people and/or tools. </p>
<p> <br />
&nbsp;<wbr><code>$Delete</code>: the value is treated a fieldname and fields of that name are removed. (This way one can remove fields previously added without removing and readding the package. And fields already included in the package can be removed, too). </p>
<h3>conf/incoming</h3>
<p> Every chunk is a rule set for the <code>process_incoming</code> command. Possible fields are: </p>
<dl>
<dt><code>Name</code></dt>
<dd> <p> The name of the rule-set, used as argument to the scan command to specify to use this rule. </p>
 </dd>
<dt><code>IncomingDir</code></dt>
<dd> <p> The Name of the directory to scan for <code>.changes</code> files. </p>
 </dd>
<dt><code>TempDir</code></dt>
<dd> <p> A directory where the files listed in the processed .changes files are copied into before they are read. You can avoid some copy operatations by placing this directory within the same moint point the pool hierarchy is (at least partially) in. </p>
 </dd>
<dt><code>LogDir</code></dt>
<dd> <p> A directory where .changes files, .log files and otherwise unused .byhand files are stored upon procession. </p>
 </dd>
<dt><code>Allow</code></dt>
<dd> <p> Each argument is either a pair <i>name1</i><code>&gt;</code><i>name2</i> or simply <i>name</i> which is short for <i>name</i><code>&gt;</code><i>name</i>. Each <i>name2</i> must identify a distribution, either by being Codename, a unique Suite, or a unique AlsoAcceptFor from <code>conf/distributions</code>. Each upload has each item in its <code>Distribution:</code> header compared first to last with each <i>name1</i> in the rules and is put in the first one accepting this package. e.g.: <br />
 Allow: local unstable&gt;sid <br />
 or <br />
 Allow: stable&gt;security-updates stable&gt;proposed-updates <br />
 (Note that this makes only sense if Multiple is set to true or if there are people only allowed to upload to proposed-updates but not to security-updates). </p>
 </dd>
<dt><code>Default </code><i>distribution</i></dt>
<dd> <p> Every upload not put into any other distribution because of an Allow argument is put into <i>distribution</i> if that accepts it. </p>
 </dd>
<dt><code>Multiple</code></dt>
<dd> <p> Old form of Options: multiple_distributions. </p>
 </dd>
<dt><code>Options</code></dt>
<dd> <p> A list of options <br />
 <code>multiple_distributions</code> <br />
 Allow including a upload in multiple distributions. </p>
<p> If a .changes file lists multiple distributions, then reprepro will start with the first name given, check all Accept and Default options till it finds a distribution this upload can go into. </p>
<p> If this found no distribution or if this option was given, reprepro will then do the same with the second distribution name given in the .changes file and so on. <br />
 <code>limit_arch_all</code> <br />
 If an upload contains binaries from some architecture and architecture all packages, the architecture all packages are only put into the architectures within this upload. Useful to combine with the <code>flood</code> command. </p>
 </dd>
<dt><code>Permit</code></dt>
<dd> <p> A list of options to allow things otherwise causing errors: <br />
 <code>unused_files</code> <br />
 Do not stop with error if there are files listed in the <code>.changes</code> file if it lists files not belonging to any package in it. <br />
 <code>older_version</code> <br />
 Ignore a package not added because there already is a strictly newer version available instead of treating this as an error. <br />
 <code>unlisted_binaries</code> <br />
 Do not abort with an error if a .changes file contains .deb files that are not listed in the Binaries header. </p>
 </dd>
<dt><code>Cleanup </code><i>options</i></dt>
<dd> <p> A list of options to cause more files in the incoming directory to be deleted: <br />
 <code>unused_files</code> <br />
 If there is <code>unused_files</code> in <code>Permit</code> then also delete those files when the package is deleted after successful processing. <br />
 <code>on_deny</code> <br />
 If a <code>.changes</code> file is denied processing because of missing signatures or allowed distributions to be put in, delete it and all the files it references. <br />
 <code>on_error</code> <br />
 If a <code>.changes</code> file causes errors while processing, delete it and the files it references. </p>
<p> Note that allowing cleanup in publically accessible incoming queues allows a denial of service by sending in .changes files deleting other peoples files before they are completed. Especially when .changes files are handled directly (e.g. by inoticoming). </p>
 </dd>
<dt><code>MorgueDir</code></dt>
<dd> <p> If files are to be deleted by Cleanup, they are instead moved to a subdirectory of the directory given as value to this field. This directory has to be on the same partition as the incoming directory and files are moved (i.e. owner and permission stay the same) and never copied. </p>
 </dd></dl>
<h2>UPLOADERS FILES</h2>
<p> These files specified by the <code>Uploaders</code> header in the distribution definition as explained above describe what key a <code>.changes</code> file as to be signed with to be included in that distribution. </p>
<p> Empty lines and lines starting with a hash are ignored, every other line must be of one of the following nine forms or an include directive: </p>
<dl>
<dt><code>allow </code><i>condition</i> by anybody </dt>
<dd> <p> which allows everyone to upload packages matching <i>condition</i>, </p>
 </dd>
<dt><code>allow </code><i>condition</i> by unsigned </dt>
<dd> <p> which allows everything matching that has no pgp/gpg header, </p>
 </dd>
<dt><code>allow </code><i>condition</i> by any key </dt>
<dd> <p> which allows everything matching with any valid signature in or </p>
 </dd>
<dt><code>allow </code><i>condition</i> by key <i>key-id</i></dt>
<dd> <p> which allows everything matching signed by this <i>key-id</i> (to be specified without any spaces). If the <i>key-id</i> ends with a <code>+</code> (plus), a signature with a subkey of this primary key also suffices. </p>
<p> <i>key-id</i> must be a suffix of the id libgpgme uses to identify this key, i.e. a number of hexdigits from the end of the fingerprint of the key, but no more than what libgpgme uses. (The maximal number should be what gpg --list-key --with-colons prints, as of the time of this writing that is at most 16 hex-digits). </p>
 </dd>
<dt><code>allow </code><i>condition</i> by group <i>groupname</i></dt>
<dd> <p> which allows every member of group <i>groupname</i>. Groups can be manipulated by </p>
 </dd>
<dt><code>group </code><i>groupname</i> add <i>key-id</i></dt>
<dd> <p> to add a <i>key-id</i> (see above for details) to this group, or </p>
 </dd>
<dt><code>group </code><i>groupname</i> contains <i>groupname</i></dt>
<dd> <p> to add a whole group to a group. </p>
<p> To avoid warnings in incomplete config files there is also </p>
 </dd>
<dt><code>group </code><i>groupname</i> empty </dt>
<dd> <p> to declare a group has no members (avoids warnings that it is used without those) and </p>
 </dd>
<dt><code>group </code><i>groupname</i> unused </dt>
<dd> <p> to declare that a group is not yet used (avoid warnings that it is not used). </p>
 </dd></dl>
<p> A line starting with <code>include</code> causes the rest of the line to be interpreted as filename, which is opened and processed before the rest of the file is processed. </p>
<p> The only conditions currently supported are: </p>
<dl>
<dt><code>*</code></dt>
<dd> <p> which means any package, </p>
 </dd>
<dt><code>source &#8216;</code><i>name</i><code>&#8216;</code></dt>
<dd> <p> which means any package with source <i>name</i>. (&#8216;<code>*</code>&#8216;, &#8216;<code>?</code>&#8216; and &#8216;<code>[</code>..<code>]</code>&#8216; are treated as in shell wildcards). </p>
 </dd>
<dt><code>sections &#8216;</code><i>name</i>&#8216;(|&#8216;<i>name</i>&#8216;)* </dt>
<dd> <p> matches an upload in which each section matches one of the names given. As upload conditions are checked very early, this is the section listed in the .changes file, not the one from the override file. (But this might change in the future, if you have the need for the one or the other behavior, let me know). </p>
 </dd>
<dt><code>sections contain &#8216;</code><i>name</i>&#8216;(|&#8216;<i>name</i>&#8216;)* </dt>
<dd> <p> The same, but not all sections must be from the given set, but at least one source or binary package needs to have one of those given. </p>
 </dd>
<dt><code>binaries &#8216;</code><i>name</i>&#8216;(|&#8216;<i>name</i>&#8216;)* </dt>
<dd> <p> matches an upload in which each binary (type deb or udeb) matches one of the names given. </p>
 </dd>
<dt><code>binaries contain &#8216;</code><i>name</i>&#8216;(|&#8216;<i>name</i>&#8216;)* </dt>
<dd> <p> again only at least one instead of all is required. </p>
 </dd>
<dt><code>architectures &#8216;</code><i>architecture</i>&#8216;(|&#8216;<i>name</i>&#8216;)* </dt>
<dd> <p> matches an upload in which each package has only architectures from the given set. <code>source</code> and <code>all</code> are treated as unique architectures. Wildcards are not allowed. </p>
 </dd>
<dt><code>architectures contain &#8216;</code><i>architecture</i>&#8216;(|&#8216;<i>architecture</i>&#8216;)* </dt>
<dd> <p> again only at least one instead of all is required. </p>
 </dd>
<dt><code>byhand</code></dt>
<dd> <p> matches an upload with at least one byhand file (i.e. a file with section <code>byhand</code> or <code>raw-</code><i>something</i>). </p>
 </dd>
<dt><code>byhand &#8216;</code><i>section</i>&#8216;(|&#8216;<i>section</i>&#8216;)* </dt>
<dd> <p> matches an upload with at least one byhand file and all byhand files having a section listed in the list of given section. (i.e. <code>byhand &#8216;byhand&#8217;|&#8216;raw-*&#8216;</code> is currently is the same as <code>byhand</code>). </p>
 </dd>
<dt><code>distribution &#8216;</code><i>codename</i><code>&#8216;</code></dt>
<dd> <p> which means any package when it is to be included in <i>codename</i>. As the uploaders file is given by distribution, this is only useful to reuse a complex uploaders file for multiple distributions. </p>
 </dd></dl>
<p> Putting <code>not</code> in front of a condition, inverses it&#8217;s meaning. For example <br />
 <code>allow not source &#8216;r*&#8216; by anybody</code> <br />
 means anybody may upload packages which source name does not start with an &#8216;r&#8217;. </p>
<p> Multiple conditions can be connected with <code>and</code> and <code>or</code>, with <code>or</code> binding stronger (but both weaker than <code>not</code>). That means <br />
 <code>allow source &#8216;r*&#8216; and source &#8216;*xxx&#8217; or source &#8216;*o&#8217; by anybody</code> <br />
 is equivalent to <br />
 <code>allow source &#8216;r*xxx&#8217; by anybody</code> <br />
 <code>allow source &#8216;r*o&#8217; by anybody</code> </p>
<p> (Other conditions will follow once somebody tells me what restrictions are useful. Currently planned is only something for architectures).  </p>
<h2>ERROR IGNORING</h2>
<p> With <code>--ignore</code> on the command line or an <i>ignore</i> line in the options file, the following type of errors can be ignored: </p>
<dl>
<dt><code>brokenold </code>(hopefully never seen) </dt>
<dd> <p> If there are errors parsing an installed version of package, do not error out, but assume it is older than anything else, has not files or no source name. </p>
 </dd>
<dt><code>brokensignatures</code></dt>
<dd> <p> If a .changes or .dsc file contains at least one invalid signature and no valid signature (not even expired or from an expired or revoked key), reprepro assumes the file got corrupted and refuses to use it unless this ignore directive is given. </p>
 </dd>
<dt><code>brokenversioncmp </code>(hopefully never seen) </dt>
<dd> <p> If comparing old and new version fails, assume the new one is newer. </p>
 </dd>
<dt><code>dscinbinnmu</code></dt>
<dd> <p> If a .changes file has an explicit Source version that is different the to the version header of the file, than reprepro assumes it is binary non maintainer upload (NMU). In that case, source files are not permitted in .changes files processed by <code>include</code> or <code>processincoming</code>. Adding <code>--ignore=dscinbinnmu</code> allows it for the <code>include</code> command. </p>
 </dd>
<dt><code>emptyfilenamepart </code>(insecure) </dt>
<dd> <p> Allow strings to be empty that are used to construct filenames. (like versions, architectures, ...) </p>
 </dd>
<dt><code>extension</code></dt>
<dd> <p> Allow to <code>includedeb</code> files that do not end with <code>.deb</code>, to <code>includedsc</code> files not ending in <code>.dsc</code> and to <code>include</code> files not ending in <code>.changes</code>. </p>
 </dd>
<dt><code>forbiddenchar </code>(insecure) </dt>
<dd> <p> Do not insist on Debian policy for package and source names and versions. Thus allowing all 7-bit characters but slashes (as they would break the file storage) and things syntactically active (spaces, underscores in filenames in .changes files, opening parentheses in source names of binary packages). To allow some 8-bit chars additionally, use <code>8bit</code> additionally. </p>
 </dd>
<dt><code>8bit </code>(more insecure) </dt>
<dd> <p> Allow 8-bit characters not looking like overlong UTF-8 sequences in filenames and things used as parts of filenames. Though it hopefully rejects overlong UTF-8 sequences, there might be other characters your filesystem confuses with special characters, thus creating filenames possibly equivalent to <code>/mirror/pool/main/../../../etc/shadow</code> (Which should be safe, as you do not run reprepro as root, do you?) or simply overwriting your conf/distributions file adding some commands in there. So do not use this if you are paranoid, unless you are paranoid enough to have checked the code of your libs, kernel and filesystems. </p>
 </dd>
<dt><code>ignore </code>(for forward compatibility) </dt>
<dd> <p> Ignore unknown ignore types given to <i>--ignore</i>. </p>
 </dd>
<dt><code>flatandnonflat </code>(only supresses a warning) </dt>
<dd> <p> Do not warn about a flat and a non-flat distribution from the same source with the same name when updating. (Hopefully never ever needed.) </p>
 </dd>
<dt><code>malformedchunk </code>(I hope you know what you do) </dt>
<dd> <p> Do not stop when finding a line not starting with a space but no colon(:) in it. These are otherwise rejected as they have no defined meaning. </p>
 </dd>
<dt><code>missingfield </code>(safe to ignore) </dt>
<dd> <p> Ignore missing fields in a .changes file that are only checked but not processed. Those include: Format, Date, Urgency, Maintainer, Description, Changes </p>
 </dd>
<dt><code>missingfile </code>(might be insecure) </dt>
<dd> <p> When including a .dsc file from a .changes file, try to get files needed but not listed in the .changes file (e.g. when someone forgot to specify -sa to dpkg-buildpackage) from the directory the .changes file is in instead of erroring out. (<code>--delete</code> will not work with those files, though.) </p>
 </dd>
<dt><code>spaceonlyline </code>(I hope you know what you do) </dt>
<dd> <p> Allow lines containing only (but non-zero) spaces. As these do not separate chunks as thus will cause reprepro to behave unexpected, they cause error messages by default. </p>
 </dd>
<dt><code>surprisingarch</code></dt>
<dd> <p> Do not reject a .changes file containing files for a architecture not listed in the Architecture-header within it. </p>
 </dd>
<dt><code>surprisingbinary</code></dt>
<dd> <p> Do not reject a .changes file containing .deb files containing packages whose name is not listed in the &quot;Binary:&quot; header of that changes file. </p>
 </dd>
<dt><code>undefinedtarget </code>(hope you are not using the wrong db directory) </dt>
<dd> <p> Do not stop when the packages.db file contains databases for codename/packagetype/component/architectures combinations that are not listed in your distributions file. </p>
<p> This allows you to temporarily remove some distribution from the config files, without having to remove the packages in it with the <code>clearvanished</code> command. You might even temporarily remove single architectures or components, though that might cause inconsistencies in some situations. </p>
 </dd>
<dt><code>undefinedtracking </code>(hope you are not using the wrong db directory) </dt>

<h2>GUESSING</h2>
<p> When including a binary or source package without explicitly declaring a component with <code>-C</code> it will take the first component with the name of the section, being prefix to the section, being suffix to the section or having the section as prefix or any. (In this order) </p>
<p> Thus having specified the components: &quot;main non-free contrib non-US/main non-US/non-free non-US/contrib&quot; should map e.g. &quot;non-US&quot; to &quot;non-US/main&quot; and &quot;contrib/editors&quot; to &quot;contrib&quot;, while having only &quot;main non-free and contrib&quot; as components should map &quot;non-US/contrib&quot; to &quot;contrib&quot; and &quot;non-US&quot; to &quot;main&quot;. </p>
<p> <code>NOTE:</code> Always specify main as the first component, if you want things to end up there. </p>
<p> <code>NOTE:</code> unlike in dak, non-US and non-us are different things...  </p>

<h2>Some note on updates</h2>
<h3>A version is not overwritten with the same version.</h3>
<p> <code>reprepro</code> will never update a package with a version it already has. This would be equivalent to rebuilding the whole database with every single upgrade. To force the new same version in, remove it and then update. (If files of the packages changed without changing their name, make sure the file is no longer remembered by reprepro. Without <code>--keepunreferencedfiled</code> and without errors while deleting it should already be forgotten, otherwise a <code>deleteunreferenced</code> or even some <code>__forget</code> might help.)  </p>
<h3>The magic delete rule (-).</h3>
<p> A minus as a single word in the <code>Update:</code> line of a distribution marks everything to be deleted. The mark causes later rules to get packages even if they have (strict) lower versions. The mark will get removed if a later rule sets the package on hold (hold is not yet implemented, in case you might wonder) or would get a package with the same version (Which it will not, see above). If the mark is still there at the end of the processing, the package will get removed. </p>
<p> Thus the line &quot;Update: - <i>rules</i> &quot; will cause all packages to be exactly the highest Version found in <i>rules.</i> The line &quot;Update: <i>near</i> - <i>rules</i> &quot; will do the same, except if it needs to download packages, it might download it from <i>near</i> except when too confused. (It will get too confused e.g. when <i>near</i> or <i>rules</i> have multiple versions of the package and the highest in <i>near</i> is not the first one in <i>rules,</i> as it never remember more than one possible spring for a package. </p>
<p> Warning: This rule applies to all type/component/architecture triplets of a distribution, not only those some other update rule applies to. (That means it will delete everything in those!)  </p>

<dd> <p> When there is a gpg-agent running that does not have the passphrase cached yet, gpg will most likely try to start some pinentry program to get it. <h2>BUGS</h2>
<p> Increased verbosity always shows those things one does not want to know. (Though this might be inevitable and a corollary to Murphy) </p>
<p> Reprepro uses berkeley db, which was a big mistake. The most annoying problem not yet worked around is database corruption when the disk runs out of space. (Luckily if it happens while downloading packages while updating, only the files database is affected, which is easy (though time consuming) to rebuild, see <code>recovery</code> file in the documentation). Ideally put the database on another partition to avoid that. </p>
<p> While the source part is mostly considered as the architecture <code>source</code> some parts may still not use this notation.  </p>
<h2>WORK-AROUNDS TO COMMON PROBLEMS</h2>
<dl>
<dt><code>gpgme returned an impossible condition</code></dt>
<dd> <p> With the woody version this normally meant that there was no .gnupg directory in $HOME, but it created one and reprepro succeeds when called again with the same command. Since sarge the problem sometimes shows up, too. But it is no longer reproducible and it does not fix itself, neither. Try running <code>gpg --verify </code><i>file-you-had-problems-with</i> manually as the user reprepro is running and with the same $HOME. This alone might fix the problem. It should not print any messages except perhaps <br />
 gpg: no valid OpenPGP data found. <br />
 gpg: the signature could not be verified. <br />
 if it was an unsigned file. </p>
 </dd>
<dt><code>not including .orig.tar.gz when a .changes file&#8217;s version does not end in -0 or -1</code></dt>
<dd> <p> If dpkg-buildpackage is run without the <code>-sa</code> option to build a version with a Debian revision not being -0 or -1, it does not list the <code>.orig.tar.gz</code> file in the <code>.changes</code> file. If you want to <code>include</code> such a file with reprepro when the .orig.tar.gz file does not already exist in the pool, reprepro will report an error. This can be worked around by: <br />
 call <code>dpkg-buildpackage</code> with <code>-sa</code> (recommended) <br />
 copy the .orig.tar.gz file to the proper place in the pool before <br />
 call reprepro with --ignore=missingfile (discouraged) </p>
 </dd>
<dt><code>leftover files in the pool directory.</code></dt>
<dd> <p> reprepro is sometimes a bit too timid of deleting stuff. When things go wrong and there have been errors it sometimes just leaves everything where it is. To see what files reprepro remembers to be in your pool directory but does not know anything needing them right know, you can use <br />
 <code>reprepro dumpunreferenced</code> <br />
 To delete them: <br />
 <code>reprepro deleteunreferenced</code> </p>
 </dd></dl>
<h2>INTERRUPTING</h2>
<p> Interrupting reprepro has its problems. Some things (like speaking with apt methods, database stuff) can cause problems when interrupted at the wrong time. Then there are design problems of the code making it hard to distinguish if the current state is dangerous or non-dangerous to interrupt. Thus if reprepro receives a signal normally sent to tell a process to terminate itself softly, it continues its operation, but does not start any new operations. (I.e. it will not tell the apt-methods any new file to download, it will not replace a package in a target, unless it already had started with it, it will not delete any files gotten dereferenced, and so on). </p>
<p> <code>It only catches the first signal of each type. The second signal of a given type will terminate reprepro. You will risk database corruption and have to remove the lockfile manually.</code> </p>
<p> Also note that even normal interruption leads to code-paths mostly untested and thus expose a multitude of bugs including those leading to data corruption. Better think a second more before issuing a command than risking the need for interruption.  </p>
