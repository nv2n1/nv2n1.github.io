<h2>NAME</h2>
<p> rx, rb, rz &#8211; XMODEM, YMODEM, ZMODEM (Batch) file receive</p>
<h2>SYNOPSIS</h2>
<p> <code>rz</code> [-<code>&nbsp;<wbr>+8abeOpqRtTuUvy</code>]<br />
 <code>rb</code> [-<code>&nbsp;<wbr>+abqRtuUvy</code>]<br />
 <code>rx</code> [-<code>&nbsp;<wbr>abceqRtuUv</code>] <i>file</i><br />
 [<code>&#8211;</code>][<code>v</code>]<code>rzCOMMAND</code></p>
<h2>DESCRIPTION</h2>
<p> This program uses error correcting protocols to receive files over a dial-in serial port from a variety of programs running under PC-DOS, CP/M, <font SIZE="-1">Unix,</font> and other operating systems. It is invoked from a shell prompt manually, or automatically as a result of an &quot;sz file &#8230;&quot; command given to the calling program. </p>
<p> While <i>rz</i> is smart enough to be called from <i><a href="/docs/linux/man/1-cu/">cu</a>(1),</i> very few versions of <i><a href="/docs/linux/man/1-cu/">cu</a>(1)</i> are smart enough to allow <i>rz</i> to work properly. Unix flavors of Professional-YAM are available for such dial-out application. </p>
<p> <code>Rz</code> (Receive ZMODEM) receives files with the ZMODEM batch protocol. Pathnames are supplied by the sending program, and directories are made if necessary (and possible). Normally, the &quot;rz&quot; command is automatically issued by the calling ZMODEM program, but some defective ZMODEM implementations may require starting <i>rz</i> the old fashioned way. </p>
<p> <code>Rb</code> receives file(s) with YMODEM, accepting either standard 128 byte sectors or 1024 byte sectors (YAM sb <code>-k</code> option). The user should determine when the 1024 byte block length actually improves throughput without causing lost data or even system crashes. </p>
<p> If True YMODEM (Omen Technology trademark) file information (file length, etc.) is received, the file length controls the number of bytes written to the output dataset, and the modify time and file mode (iff non zero) are set accordingly. </p>
<p> If no True YMODEM file information is received, slashes in the pathname are changed to underscore, and any trailing period in the pathname is eliminated. This conversion is useful for files received from CP/M systems. With YMODEM, each file name is converted to lower case unless it contains one or more lower case letters. </p>
<p> <code>Rx</code> receives a single <i>file</i> with XMODEM or XMODEM-1k protocol. The user should determine when the 1024 byte block length actually improves throughput without causing problems. The user must supply the file name to both sending and receiving programs. Up to 1023 garbage characters may be added to the received file. </p>
<p> <code>Rz</code> may be invoked as <code>rzCOMMAND</code> (with an optional leading &#8211; as generated by <a href="/docs/linux/man/1-login/">login</a>(1)). For each received file, <i>rz</i> will pipe the file to &#8220;COMMAND filename&#8221; where filename is the name of the transmitted file with the file contents as standard input. </p>
<p> Each file transfer is acknowledged when COMMAND exits with 0 status. A non zero exit status terminates transfers. </p>
<p> A typical use for this form is <i>rzrmail</i> which calls <a href="/docs/linux/man/1-rmail/">rmail</a>(1) to post mail to the user specified by the transmitted file name. For example, sending the file &quot;caf&quot; from a PC-DOS system to <i>rzrmail</i> on a <font SIZE="-1">Unix</font> system would result in the contents of the DOS file &quot;caf&quot; being mailed to user &quot;caf&quot;. </p>
<p> On some <font SIZE="-1">Unix</font> systems, the login directory must contain a link to COMMAND as login sets SHELL=rsh which disallows absolute pathnames. If invoked with a leading &#8220;v&#8221;, <i>rz</i> will be verbose (see <code>v</code> option). The following entry works for <font SIZE="-1">Unix</font> SYS III/V: <center> rzrmail::5:1::/bin:/usr/local/rzrmail<br />
 </center> If the SHELL environment variable includes <i>rsh</i> , <i>rbash</i> or <i>rksh</i> (restricted shell), <i>rz</i> will not accept absolute pathnames or references to a parent directory, will not modify an existing file, and removes any files received in error. </p>
<p> If <code>rz</code> is invoked with stdout and stderr to different datasets, Verbose is set to 2, causing frame by frame progress reports to stderr. This may be disabled with the <code>q</code> option. </p>
<h2>OPTIONS</h2>
<p> The meanings of the available options are: </p>
<dl>
<dt><code>-+, &#8211;append</code></p>
<dd> append received data to an existing file (ZMODEM, ASCII only).</p>
<dt><code>-a, &#8211;ascii</code></p>
<dd> Convert files to <font SIZE="-1">Unix</font> conventions by stripping carriage returns and all characters beginning with the first Control Z (CP/M end of file).</p>
<dt><code>-b, &#8211;binary</code></p>
<dd> Binary (tell it like it is) file transfer override.</p>
<dt><code>-B NUMBER, &#8211;bufsize NUMBER</code></p>
<dd> Buffer <code>NUMBER</code> bytes before writing to disk. Default ist 32768, which should be enough for most situations. If you have a slow machine or a bad disk interface or suffer from other hardware problems you might want to increase the buffersize. <code>-1</code> or <code>auto</code> use a buffer large enough to buffer the whole file. Be careful with this options &#8211; things normally get worse, not better, if the machine starts to swap.</p>
<dt><code>-c, &#8211;with-crc</code></p>
<dd> XMODEM only. Use 16 bit CRC (normally a one byte checksum is used).</p>
<dt><code>-C, &#8211;allow-remote-commands</code></p>
<dd> allow remote command execution ( <code>insecure</code> ). This allows the sender to execute an arbitrary command through <code>system</code> () or <code>execl</code> (). Default is to disable this feature (?). This option is ignored if running in restricted mode.</p>
<dt><code>-D, &#8211;null</code></p>
<dd> Output file data to /dev/null; for testing. (Unix only)</p>
<dt><code>&#8211;delay-startup N</code></p>
<dd> Wait <code>N</code> seconds before doing anything.</p>
<dt><code>-e, &#8211;escape</code></p>
<dd> Force sender to escape all control characters; normally XON, XOFF, DLE, CR-@-CR, and Ctrl-X are escaped.</p>
<dt><code>-E, &#8211;rename</code></p>
<dd> Rename incoming file if target filename already exists. The new file name will have a dot and a number (0..999) appended.</p>
<dt><code>-h, &#8211;help</code></p>
<dd> give help screen.</p>
<dt><code>-m N, &#8211;min-bps N</code></p>
<dd> Stop transmission if BPS-Rate (Bytes Per Second) falls below N for a certain time (see &#8211;min-bps-time option).</p>
<dt><code>-M N, &#8211;min-bps-time</code></p>
<dd> Used together with &#8211;min-bps. Default is 120 (seconds).</p>
<dt><code>-O, &#8211;disable-timeouts</code></p>
<dd> Disable read timeout handling code. This makes lrz hang if the sender does not send any more, but increases performance (a bit) and decreases system load (through reducing the number of system calls by about 50 percent). </p>
<p> Use this option with care.</p>
<dt><code>&#8211;o-sync</code></p>
<dd> Open output files in synchronous write mode. This may be useful if you experience errors due to lost interrupts if update (or bdflush or whoever this daemon is called on your system) writes the buffers to the disk. </p>
<p> This option is ignored and a warning is printed if your systems doesn&#8217;t support O_SYNC.</p>
<dt><code>-p, &#8211;protect</code></p>
<dd> (ZMODEM) Protect: skip file if destination file exists.</p>
<dt><code>-q, &#8211;quiet</code></p>
<dd> Quiet suppresses verbosity.</p>
<dt><code>-r, &#8211;resume</code></p>
<dd> Crash recovery mode. lrz tries to resume interrupted file transfers.</p>
<dt><code>-R, &#8211;restricted</code></p>
<dd> Enter more restricted mode. lrz will not create directories or files with a leading dot if this option is given twice. </p>
<p> See <code>SECURITY</code> for mode information about restricted mode.</p>
<dt><code>-s HH:MM, &#8211;stop-at HH:MM</code></p>
<dd> Stop transmission at <code>HH</code> hours, <code>MM</code> minutes. Another variant, using <code>+N</code> instead of <code>HH:MM,</code> stops transmission in <code>N</code> seconds.</p>
<dt><code>-S, &#8211;timesync</code></p>
<dd> Request timesync packet from the sender. The sender sends its system time, causing lrz to complain about more then 60 seconds difference. </p>
<p> Lrz tries to set the local system time to the remote time if this option is given twice (this fails if lrz is not run by root). </p>
<p> This option makes lrz incompatible with certain other ZModems. Don&#8217;t use it unless you know what you are doing.</p>
<dt><code>&#8211;syslog[=off]</code></p>
<dd> turn syslogging on or off. the default is set at configure time. This option is ignored if no syslog support is compiled in.</p>
<dt><code>-t TIM, &#8211;timeout TIM</code></p>
<dd> Change timeout to <i>TIM</i> tenths of seconds. This is ignored if timeout handling is turned of through the <code>O </code> option.</p>
<dt><code>&#8211;tcp-client ADDRESS:PORT</code></p>
<dd> Act as a tcp/ip client: Connect to the given port. </p>
<p> See <code>&#8211;tcp-server</code> for more information. </p>
<dt><code>&#8211;tcp-server</code></p>
<dd> Act as a server: Open a socket, print out what to do, wait for connection. </p>
<p> You will normally not want to use this option as lrzsz is the only zmodem which understands what to do (private extension). You might want to use this if you have to use zmodem (for which reason whatever), and cannot use the <code>&#8211;tcp</code> option of <i>lsz</i> (perhaps because your telnet doesn&#8217;t allow to spawn a local program with stdin/stdout connected to the remote side). </p>
<p> If you use this option you have to start <i>lsz </i> with the <code>&#8211;tcp-client ADDRESS:PORT</code> option. <i>lrz will print the address and port on startup.</i> </p>
<p> Use of this option imposes a security risk, somebody else could connect to the port in between. See <code>SECURITY </code> for details.</p>
<dt><code>-U, &#8211;unrestrict</code></p>
<dd> turn off restricted mode (this is not possible if running under a restricted shell).</p>
<dt><code>&#8211;version</code></p>
<dd> prints out version number.</p>
<dt><code>-v, &#8211;verbose</code></p>
<dd> Verbose causes a list of file names to be appended to stderr. More v&#8217;s generate more output.</p>
<dt><code>-wN, &#8211;windowsize N</code></p>
<dd> Set window size to N.</p>
<dt><code>-X, &#8211;xmodem</code></p>
<dd> use XMODEM protocol.</p>
<dt><code>-y, &#8211;overwrite</code></p>
<dd> Yes, clobber any existing files with the same name.</p>
<dt><code>&#8211;ymodem</code></p>
<dd> use YMODEM protocol.</p>
<dt><code>-Z, &#8211;zmodem</code></p>
<dd> use ZMODEM protocol.</dl>
<h2>SECURITY</h2>
<p> Contrary to the original ZMODEM lrz defaults to restricted mode. In restricted mode lrz will not accept absolute pathnames or references to a parent directory, will not modify an existing file, and removes any files received in error. Remote command execution is disabled. </p>
<p> To use a more restricted mode set the environment variable <code>ZMODEM_RESTRICTED </code> or give the <code>R</code> option. This disables creation of subdirectories and invisible files. </p>
<p> Restricted mode may be turned off with the <code>U </code> option, unless lrz runs under a restricted shell. </p>
<dl>
<dt>Use of the</p>
<dd> <code>&#8211;tcp-client </code> or <code>&#8211;tcp-server </code> options imposes a security risk, as somebody else could connect to the port before you do it, and grab your data. If there&#8217;s strong demand for a more secure mode i might introduce some sort of password challenge. </p>
</dl>

<h2>NOTES</h2>
<p> Sending serial data to timesharing minicomputers at sustained high speeds has been known to cause lockups, system halts, kernel panics, and occasional antisocial behaviour. When experimenting with high speed input to a system, consider rebooting the system if the file transfers are not successful, especially if the personality of the system appears altered. </p>
<p> The Unix &quot;ulimit&quot; parameter must be set high enough to permit large file transfers. </p>
<p> The TTY input buffering on some systems may not allow long blocks or streaming input at high speed. You should suspect this problem when you can&#8217;t send data to the Unix system at high speeds using ZMODEM, YMODEM-1k or XMODEM-1k, when YMODEM with 128 byte blocks works properly. If the system&#8217;s tty line handling is really broken, the serial port or the entire system may not survive the onslaught of long bursts of high speed data. </p>
<p> The DSZ or Pro-YAM <code>zmodem l</code> numeric parameter may be set to a value between 64 and 1024 to limit the burst length (&quot;zmodem pl128&quot;). </p>

<h2>BUGS</h2>
<p> Calling <i>rz</i> from most versions of <a href="/docs/linux/man/1-cu/">cu</a>(1) doesn&#8217;t work because cu&#8217;s receive process fights <i>rz</i> for characters from the modem. </p>
<p> Programs that do not properly implement the specified file transfer protocol may cause <i>sz</i> to &quot;hang&quot; the port for a minute or two. Every reported instance of this problem has been corrected by using ZCOMM, Pro-YAM, or other program with a correct implementation of the specified protocol. </p>
<p> Many programs claiming to support YMODEM only support XMODEM with 1k blocks, and they often don&#8217;t get that quite right. </p>
<p> Pathnames are restricted to 127 characters. In XMODEM single file mode, the pathname given on the command line is still processed as described above. The ASCII option&#8217;s CR/LF to NL translation merely deletes CR&#8217;s; undos(omen) performs a more intelligent translation.</p>
<h2>VMS VERSION</h2>
<p> The VMS version does not set the file time. </p>
<p> VMS C Standard I/O and RMS may interact to modify file contents unexpectedly. </p>
<p> The VMS version does not support invocation as <code>rzCOMMAND .</code> The current VMS version does not support XMODEM, XMODEM-1k, or YMODEM. </p>
<p> According to the VMS documentation, the buffered input routine used on the VMS version of <i>rz</i> introduces a delay of up to one second for each protocol transaction. This delay may be significant for very short files. Removing the &quot;#define BUFREAD&quot; line from rz.c will eliminate this delay at the expense of increased CPU utilization. </p>
<p> The VMS version causes DCL to generate a random off the wall error message under some error conditions; this is a result of the incompatibility of the VMS &quot;exit&quot; function with the Unix/MSDOS standard.</p>
<h2>ZMODEM CAPABILITIES</h2>
<p> <i>Rz</i> supports incoming ZMODEM binary (-b), ASCII (-a), protect (-p), clobber (-y), and append (-+) requests. The default is protect (-p) and binary (-b). </p>
<p> The Unix versions support ZMODEM command execution.</p>
