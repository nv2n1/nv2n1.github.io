<h2>Description</h2>
<p><code>s3</code> is an Xorg driver for S3 based video cards. The driver provides full accelerated support for the following colour depths: 8, 15, 16 and 24. The overlay video (Xv) is supported in depths 16 and 24 for the Trio64V+, Trio64UV+, Trio64V2/DX and Trio64V2/GX chips. </p>
<h2>Configuration Details</h2>
<p>Please refer to <a href="/docs/linux/man/5-xorg-conf/">xorg.conf</a>(5) for general configuration details. This section only covers configuration details specific to this driver. All options names are case and white space insensitive when parsed by the server, for example, &quot;trio 32/64&quot; and &quot;Trio32/64&quot; are equivalent.</p>

<dl>
<dd>

<dt>&quot;968&quot;</p>
<dd>86C968</p>
<dt>&quot;Trio32/64&quot;</p>

<dt>&quot;Aurora64V+&quot;</p>
<dd>86CM65</p>
<dt>&quot;Trio64UV+&quot;</p>

<p> The 86C765 (Trio64V+) is <code>Chipset</code> &quot;Trio32/64&quot; with <code>ChipRev</code> greater or equal 0x40. </p>
<p> An overriding of RAMDAC auto-detection currently is not implemented.</p>
<h3>Colour depth</h3>
<p>For every supported colour depth the X server automatically selects an appropriate number of bits per pixel (bpp) for framebuffer. The depth 8 is represented by 8 bpp framebuffer (1 byte/pixel), the depths 15 and 16 (respectively 5.5.5 and 5.6.5 pixel formats) are represented by the 16 bpp framebuffer (2 bytes/pixel). Whenever the depth 24 is configured, the X server by default uses the 32 bpp framebuffer (4 bytes/pixel), and the hardware is adjusted accordingly to the X.8.8.8 pixel format, where X is the ignored upper byte. </p>
<p> As the second option for the depth 24, the X server can be configured to use 24 bpp framebuffer with the 8.8.8 pixel format (3 bytes/pixel), which is supported by Trio64V+, Trio64UV+, Trio64V2/DX and Trio64V2/GX. If the video board has limited video RAM the 24 bpp framebuffer has an advantage over 32 bpp framebuffer as it requires less memory to store screen, and, therefore, more space will be available for a video frame (see &quot;Overlay video&quot; section). The 24 bpp framebuffer can be selected by X server&#8217;s option <code>-fbbpp 24</code> or by specifying <code>DefaultFbBpp</code> option in <a href="/docs/linux/man/5-xorg-conf/">xorg.conf</a>(5): </p>
<dl>
<dd><code>Section &#34;Screen&#34;</code></p>
<dl>
<dd><code>DefaultFbBpp 24</code><br />
 <code>DefaultDepth 24</code><br />
 <code>&#8230;</code></dl>
<p> <code>EndSection</code></dl>
<p> However, the 24 bpp framebuffer mode has the hardware limitations: (i) the 2D acceleration doesn&#8217;t work with this mode (use the <code>&#34;shadowFB&#34;</code> option to speed up drawing routines in this case); (ii) 24 bpp framebuffer cannot be used with either interlaced or doublescan graphics modes.</p>
<h3>Overlay video</h3>
<p>If your video board has limited RAM it would be useful to estimate how large video frame might be placed in offscreen video memory. Suppose that the video board has 2 MB of RAM, and X server is configured to display 800&#215;600 with the depth 24. By default the 32 bpp framebuffer will be chosen for this depth, so 800 x 600 x 4 = 1875 kB will be reserved for screen, and 2 MB &#8211; 1875 kB = 173 kB will remain for the offscreen area. This is sufficient space, for example, for the VCD NTSC 352&#215;240 frame. If you need to upscale video with a bigger frame, but it doesn&#8217;t fit the offscreen area, the only way to do this is to lower either the resolution or framebuffer&#8217;s depth or both before the viewing, otherwise, you will get the allocation error and will not see the video. For example, with 24 bpp framebuffer and the same resolution 800&#215;600 the offscreen area will be about 640 kB &#8211; it&#8217;s enough for the 640&#215;480 frame. 800&#215;600 with the 16 bpp framebuffer gives about 1110 kB of offscreen area &#8211; this allows to upscale up to 768&#215;576 movies. Note, that all movie resolutions in examples above are provided as a reference; the movies can have the different aspect ratios and non-standard dimensions. A total pixel amount is the main consideration not the certain width and height. </p>
<p> Due to hardware limitation the overlay video will not work with the interlaced/doublescan modes. Downscaling is not implemented in hardware.</p>
<h3>Configuration options</h3>
<p>The following display <code>Options</code> are supported:</p>
<dl>
<dt><code>Option &#34;HWCursor&#34; &#34;</code><i>boolean</i><code>&#34;</code></p>
<dd>Enable or disable the hardware cursor. Currently, hardware cursor is not implemented, so the option will be ignored. Default: off (software cursor).</p>
<dt><code>Option &#34;NoAccel&#34; &#34;</code><i>boolean</i><code>&#34;</code></p>
<dd>Disable acceleration. Very useful for determining if the driver has problems with drawing and acceleration routines. This is the first option to try if your server runs but you see graphic corruption on the screen. Using it decreases performance, as it uses software emulation for drawing operations the video driver can accelerate with hardware. Default: off (acceleration is enabled).</p>
<dt><code>Option &#34;ShadowFB&#34; &#34;</code><i>boolean</i><code>&#34;</code></p>
<dd>Use shadow framebuffer. Disables hardware acceleration. Use this option when the hardware acceleration is not available or undesirable. Default: off.</p>
<dt><code>Option &#34;XVideo&#34; &#34;</code><i>boolean</i><code>&#34;</code></p>
<dd>Enable or disable Xv support. Default: on. </p>
</dl>
<p> The following video memory <code>Options</code> are supported:</p>
<dl>
<dt><code>Option &#34;slow_dram_refresh&#34; &#34;</code><i>boolean</i><code>&#34;</code></p>
<dd>Enable three refresh cycles per scanline. Default: off (one refresh cycle).</p>
<dt><code>Option &#34;slow_edodram&#34; &#34;</code><i>boolean</i><code>&#34;</code></p>
<dd>Switch to 2-cycle EDO mode. Try this if you encounter pixel corruption. Using this option will cause a decrease in performance. Default: off (BIOS defaults).</p>
<dt><code>Option &#34;slow_dram&#34; &#34;</code><i>boolean</i><code>&#34;</code></p>
<dd>For Trio and Aurora64V+ chips: increase -RAS Precharge Timing to 3.5 MCLK. Try this option if you encounter pixel errors. Default: off (BIOS defaults).</p>
<dt><code>Option &#34;slow_vram&#34; &#34;</code><i>boolean</i><code>&#34;</code></p>
<dd>For Vision964, Vision968 chips: increase -RAS Low Timing to 4.5 MCLK. Default: off (BIOS defaults). </p>
</dl>
