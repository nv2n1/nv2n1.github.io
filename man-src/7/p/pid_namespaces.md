<p>pid_namespaces &#8211; overview of Linux PID namespaces</p>
<h2>Description</h2>
<p>For an overview of namespaces, see <code><a href="/docs/linux/man/7-namespaces/">namespaces</a></code>(7). </p>
<p> PID namespaces isolate the process ID number space, meaning that processes in different PID namespaces can have the same PID. PID namespaces allow containers to provide functionality such as suspending/resuming the set of processes in the container and migrating the container to a new host while the processes inside the container maintain the same PIDs. </p>
<p> PIDs in a new PID namespace start at 1, somewhat like a standalone system, and calls to <code><a href="/docs/linux/man/2-fork/">fork</a></code>(2), <code><a href="/docs/linux/man/2-vfork/">vfork</a></code>(2), or <code><a href="/docs/linux/man/2-clone/">clone</a></code>(2) will produce processes with PIDs that are unique within the namespace. </p>
<p> Use of PID namespaces requires a kernel that is configured with the <code>CONFIG_PID_NS</code> option.</p>
<h3>The namespace init process</h3>
<p>The first process created in a new namespace (i.e., the process created using <code><a href="/docs/linux/man/2-clone/">clone</a></code>(2) with the <code>CLONE_NEWPID</code> flag, or the first child created by a process after a call to <code><a href="/docs/linux/man/2-unshare/">unshare</a></code>(2) using the <code>CLONE_NEWPID</code> flag) has the PID 1, and is the &quot;init&quot; process for the namespace (see <code><a href="/docs/linux/man/1-init/">init</a></code>(1)). This process becomes the parent of any child processes that are orphaned because a process that resides in this PID namespace terminated (see below for further details). </p>
<p> If the &quot;init&quot; process of a PID namespace terminates, the kernel terminates all of the processes in the namespace via a <code>SIGKILL</code> signal. This behavior reflects the fact that the &quot;init&quot; process is essential for the correct operation of a PID namespace. In this case, a subsequent <code><a href="/docs/linux/man/2-fork/">fork</a></code>(2) into this PID namespace fail with the error <code>ENOMEM</code>; it is not possible to create a new process in a PID namespace whose &quot;init&quot; process has terminated. Such scenarios can occur when, for example, a process uses an open file descriptor for a <i>/proc/[pid]/ns/pid</i> file corresponding to a process that was in a namespace to <code><a href="/docs/linux/man/2-setns/">setns</a></code>(2) into that namespace after the &quot;init&quot; process has terminated. Another possible scenario can occur after a call to <code><a href="/docs/linux/man/2-unshare/">unshare</a></code>(2): if the first child subsequently created by a <code><a href="/docs/linux/man/2-fork/">fork</a></code>(2) terminates, then subsequent calls to <code><a href="/docs/linux/man/2-fork/">fork</a></code>(2) fail with <code>ENOMEM</code>. </p>
<p> Only signals for which the &quot;init&quot; process has established a signal handler can be sent to the &quot;init&quot; process by other members of the PID namespace. This restriction applies even to privileged processes, and prevents other members of the PID namespace from accidentally killing the &quot;init&quot; process. </p>
<p> Likewise, a process in an ancestor namespace can&#8212;subject to the usual permission checks described in <code><a href="/docs/linux/man/2-kill/">kill</a></code>(2)&#8212;send signals to the &quot;init&quot; process of a child PID namespace only if the &quot;init&quot; process has established a handler for that signal. (Within the handler, the <i>siginfo_t</i> <i>si_pid</i> field described in <code><a href="/docs/linux/man/2-sigaction/">sigaction</a></code>(2) will be zero.) <code>SIGKILL</code> or <code>SIGSTOP</code> are treated exceptionally: these signals are forcibly delivered when sent from an ancestor PID namespace. Neither of these signals can be caught by the &quot;init&quot; process, and so will result in the usual actions associated with those signals (respectively, terminating and stopping the process). </p>
<p> Starting with Linux 3.4, the <code><a href="/docs/linux/man/2-reboot/">reboot</a></code>(2) system call causes a signal to be sent to the namespace &quot;init&quot; process. See <code><a href="/docs/linux/man/2-reboot/">reboot</a></code>(2) for more details.</p>
<h3>Nesting PID namespaces</h3>
<p>PID namespaces can be nested: each PID namespace has a parent, except for the initial (&quot;root&quot;) PID namespace. The parent of a PID namespace is the PID namespace of the process that created the namespace using <code><a href="/docs/linux/man/2-clone/">clone</a></code>(2) or <code><a href="/docs/linux/man/2-unshare/">unshare</a></code>(2). PID namespaces thus form a tree, with all namespaces ultimately tracing their ancestry to the root namespace. Since Linux 3.7, the kernel limits the maximum nesting depth for PID namespaces to 32. </p>
<p> A process is visible to other processes in its PID namespace, and to the processes in each direct ancestor PID namespace going back to the root PID namespace. In this context, &quot;visible&quot; means that one process can be the target of operations by another process using system calls that specify a process ID. Conversely, the processes in a child PID namespace can&#8217;t see processes in the parent and further removed ancestor namespaces. More succinctly: a process can see (e.g., send signals with <code><a href="/docs/linux/man/2-kill/">kill</a></code>(2), set nice values with <code><a href="/docs/linux/man/2-setpriority/">setpriority</a></code>(2), etc.) only processes contained in its own PID namespace and in descendants of that namespace. </p>
<p> A process has one process ID in each of the layers of the PID namespace hierarchy in which is visible, and walking back though each direct ancestor namespace through to the root PID namespace. System calls that operate on process IDs always operate using the process ID that is visible in the PID namespace of the caller. A call to <code><a href="/docs/linux/man/2-getpid/">getpid</a></code>(2) always returns the PID associated with the namespace in which the process was created. </p>
<p> Some processes in a PID namespace may have parents that are outside of the namespace. For example, the parent of the initial process in the namespace (i.e., the <code><a href="/docs/linux/man/1-init/">init</a></code>(1) process with PID 1) is necessarily in another namespace. Likewise, the direct children of a process that uses <code><a href="/docs/linux/man/2-setns/">setns</a></code>(2) to cause its children to join a PID namespace are in a different PID namespace from the caller of <code><a href="/docs/linux/man/2-setns/">setns</a></code>(2). Calls to <code><a href="/docs/linux/man/2-getppid/">getppid</a></code>(2) for such processes return 0. </p>
<p> While processes may freely descend into child PID namespaces (e.g., using <code><a href="/docs/linux/man/2-setns/">setns</a></code>(2) with a PID namespace file descriptor), they may not move in the other direction. That is to say, processes may not enter any ancestor namespaces (parent, grandparent, etc.). Changing PID namespaces is a one-way operation. </p>
<p> The <code>NS_GET_PARENT</code> <code><a href="/docs/linux/man/2-ioctl/">ioctl</a></code>(2) operation can be used to discover the parental relationship between PID namespaces; see <code><a href="/docs/linux/man/2-ioctl_ns/">ioctl_ns</a></code>(2).</p>
<h3><a href="/docs/linux/man/2-setns/">setns</a>(2) and <a href="/docs/linux/man/2-unshare/">unshare</a>(2) semantics</h3>
<p>Calls to <code><a href="/docs/linux/man/2-setns/">setns</a></code>(2) that specify a PID namespace file descriptor and calls to <code><a href="/docs/linux/man/2-unshare/">unshare</a></code>(2) with the <code>CLONE_NEWPID</code> flag cause children subsequently created by the caller to be placed in a different PID namespace from the caller. (Since Linux 4.12, that PID namespace is shown via the <i>/proc/[pid]/ns/pid_for_children</i> file, as described in <code><a href="/docs/linux/man/7-namespaces/">namespaces</a></code>(7).) These calls do not, however, change the PID namespace of the calling process, because doing so would change the caller&#8217;s idea of its own PID (as reported by <code>getpid</code>()), which would break many applications and libraries. </p>
<p> To put things another way: a process&#8217;s PID namespace membership is determined when the process is created and cannot be changed thereafter. Among other things, this means that the parental relationship between processes mirrors the parental relationship between PID namespaces: the parent of a process is either in the same namespace or resides in the immediate parent PID namespace. </p>
<p> A process may call <code><a href="/docs/linux/man/2-unshare/">unshare</a></code>(2) with the <code>CLONE_NEWPID</code> flag only once. After it has performed this operation, its <i>/proc/PID/ns/pid_for_children</i> symbolic link will be empty until the first child is created in the namespace.</p>
<h3>Adoption of orphaned children</h3>
<p>When a child process becomes orphaned, it is reparented to the &quot;init&quot; process in the PID namespace of its parent (unless one of the nearer ancestors of the parent employed the <code><a href="/docs/linux/man/2-prctl/">prctl</a></code>(2) <code>PR_SET_CHILD_SUBREAPER</code> command to mark itself as the reaper of orphaned descendant processes). Note that because of the <code><a href="/docs/linux/man/2-setns/">setns</a></code>(2) and <code><a href="/docs/linux/man/2-unshare/">unshare</a></code>(2) semantics described above, this may be the &quot;init&quot; process in the PID namespace that is the <i>parent</i> of the child&#8217;s PID namespace, rather than the &quot;init&quot; process in the child&#8217;s own PID namespace.</p>
<h3>Compatibility of CLONE_NEWPID with other CLONE_* flags</h3>
<p>In current versions of Linux, <code>CLONE_NEWPID</code> can&#8217;t be combined with <code>CLONE_THREAD</code>. Threads are required to be in the same PID namespace such that the threads in a process can send signals to each other. Similarly, it must be possible to see all of the threads of a processes in the <code><a href="/docs/linux/man/5-proc/">proc</a></code>(5) filesystem. Additionally, if two threads were in different PID namespaces, the process ID of the process sending a signal could not be meaningfully encoded when a signal is sent (see the description of the <i>siginfo_t</i> type in <code><a href="/docs/linux/man/2-sigaction/">sigaction</a></code>(2)). Since this is computed when a signal is enqueued, a signal queue shared by processes in multiple PID namespaces would defeat that. </p>
<p> In earlier versions of Linux, <code>CLONE_NEWPID</code> was additionally disallowed (failing with the error <code>EINVAL</code>) in combination with <code>CLONE_SIGHAND</code> (before Linux 4.3) as well as <code>CLONE_VM</code> (before Linux 3.12). The changes that lifted these restrictions have also been ported to earlier stable kernels.</p>
<h3>/proc and PID namespaces</h3>
<p>A <i>/proc</i> filesystem shows (in the <i>/proc/[pid]</i> directories) only processes visible in the PID namespace of the process that performed the mount, even if the <i>/proc</i> filesystem is viewed from processes in other namespaces. </p>
<p> After creating a new PID namespace, it is useful for the child to change its root directory and mount a new procfs instance at <i>/proc</i> so that tools such as <code><a href="/docs/linux/man/1-ps/">ps</a></code>(1) work correctly. If a new mount namespace is simultaneously created by including <code>CLONE_NEWNS</code> in the <i>flags</i> argument of <code><a href="/docs/linux/man/2-clone/">clone</a></code>(2) or <code><a href="/docs/linux/man/2-unshare/">unshare</a></code>(2), then it isn&#8217;t necessary to change the root directory: a new procfs instance can be mounted directly over <i>/proc</i>. </p>
<p> From a shell, the command to mount <i>/proc</i> is: </p>
<p> $ mount -t proc proc /proc </p>
<p> Calling <code><a href="/docs/linux/man/2-readlink/">readlink</a></code>(2) on the path <i>/proc/self</i> yields the process ID of the caller in the PID namespace of the procfs mount (i.e., the PID namespace of the process that mounted the procfs). This can be useful for introspection purposes, when a process wants to discover its PID in other namespaces.</p>
<h3>/proc files</h3>
<dl>
<dt><code>/proc/sys/kernel/ns_last_pid</code> (since Linux 3.3)</p>
<dd>This file (which is virtualized per PID namespace) displays the last PID that was allocated in this PID namespace. When the next PID is allocated, the kernel will search for the lowest unallocated PID that is greater than this value, and when this file is subsequently read it will show that PID.</p>
<dd>This file is writable by a process that has the <code>CAP_SYS_ADMIN</code> or (since Linux 5.9) <code>CAP_CHECKPOINT_RESTORE</code> capability inside the user namespace that owns the PID namespace. This makes it possible to determine the PID that is allocated to the next process that is created inside this PID namespace.</dl>
<h3>Miscellaneous</h3>
<p>When a process ID is passed over a UNIX domain socket to a process in a different PID namespace (see the description of <code>SCM_CREDENTIALS</code> in <code><a href="/docs/linux/man/7-unix/">unix</a></code>(7)), it is translated into the corresponding PID value in the receiving process&#8217;s PID namespace.</p>
