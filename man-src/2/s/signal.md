<h2 class="name">NAME</h2>
<p> signal &#8211; ANSI C signal handling </p>
<h2>SYNOPSIS</h2>
<p> <code>#include &lt;signal.h&gt;</code> </p>
<p> <code>typedef void (*sighandler_t)(int);</code> </p>
<p> <code>sighandler_t signal(int </code><i>signum</i><code>, sighandler_t </code><i>handler</i><code>);</code></p>
<h2>DESCRIPTION</h2>
<p> <code>WARNING</code>:<br />
&nbsp;the behavior of <code>signal</code>() varies across UNIX versions, and has also varied historically across different versions of Linux. <code>Avoid its use</code>: use <code><a href="/docs/linux/man/2-sigaction/">sigaction</a></code>(2) instead. See <i>Portability</i> below. </p>
<p> <code>signal</code>() sets the disposition of the signal <i>signum</i> to <i>handler</i>, which is either <code>SIG_IGN</code>, <code>SIG_DFL</code>, or the address of a programmer-defined function (a &quot;signal handler&quot;). </p>
<p> If the signal <i>signum</i> is delivered to the process, then one of the following happens:</p>
<dl>
<dt>*</p>
<dd> If the disposition is set to <code>SIG_IGN</code>, then the signal is ignored.</p>
<dt>*</p>
<dd> If the disposition is set to <code>SIG_DFL</code>, then the default action associated with the signal (see <code><a href="/docs/linux/man/7-signal/">signal</a></code>(7)) occurs.</p>
<dt>*</p>
<dd> If the disposition is set to a function, then first either the disposition is reset to <code>SIG_DFL</code>, or the signal is blocked (see <i>Portability</i> below), and then <i>handler</i> is called with argument <i>signum</i>. If invocation of the handler caused the signal to be blocked, then the signal is unblocked upon return from the handler.</dl>
<p> The signals <code>SIGKILL</code> and <code>SIGSTOP</code> cannot be caught or ignored.</p>
<h2>RETURN VALUE</h2>
<p> <code>signal</code>() returns the previous value of the signal handler, or <code>SIG_ERR</code> on error. In the event of an error, <i>errno</i> is set to indicate the cause.</p>
<h2>ERRORS</h2>
<dl>
<dt><code>EINVAL</code></p>
<dd> <i>signum</i> is invalid.</dl>
<h2>CONFORMING TO</h2>
<p> POSIX.1-2001, POSIX.1-2008, C89, C99.</p>
<h2>NOTES</h2>
<p> The effects of <code>signal</code>() in a multithreaded process are unspecified. </p>
<p> According to POSIX, the behavior of a process is undefined after it ignores a <code>SIGFPE</code>, <code>SIGILL</code>, or <code>SIGSEGV</code> signal that was not generated by <code><a href="/docs/linux/man/2-kill/">kill</a></code>(2) or <code><a href="/docs/linux/man/3-raise/">raise</a></code>(3). Integer division by zero has undefined result. On some architectures it will generate a <code>SIGFPE</code> signal. (Also dividing the most negative integer by -1 may generate <code>SIGFPE</code>.) Ignoring this signal might lead to an endless loop. </p>
<p> See <code><a href="/docs/linux/man/2-sigaction/">sigaction</a></code>(2) for details on what happens when the disposition <code>SIGCHLD</code> is set to <code>SIG_IGN</code>. </p>
<p> See <code><a href="/docs/linux/man/7-signal-safety/">signal-safety</a></code>(7) for a list of the async-signal-safe functions that can be safely called from inside a signal handler. </p>
<p> The use of <i>sighandler_t</i> is a GNU extension, exposed if <code>_GNU_SOURCE</code> is defined; glibc also defines (the BSD-derived) <i>sig_t</i> if <code>_BSD_SOURCE</code> (glibc 2.19 and earlier) or <code>_DEFAULT_SOURCE</code> (glibc 2.19 and later) is defined. Without use of such a type, the declaration of <code>signal</code>() is the somewhat harder to read: </p>
<p> <code>void ( *</code><i>signal</i><code>(int </code><i>signum</i><code>, void (*</code><i>handler</i><code>)(int)) ) (int);</code></p>
<h3>Portability</h3>
<p> The only portable use of <code>signal</code>() is to set a signal&#8217;s disposition to <code>SIG_DFL</code> or <code>SIG_IGN</code>. The semantics when using <code>signal</code>() to establish a signal handler vary across systems (and POSIX.1 explicitly permits this variation); <code>do not use it for this purpose.</code> </p>
<p> POSIX.1 solved the portability mess by specifying <code><a href="/docs/linux/man/2-sigaction/">sigaction</a></code>(2), which provides explicit control of the semantics when a signal handler is invoked; use that interface instead of <code>signal</code>(). </p>
<p> In the original UNIX systems, when a handler that was established using <code>signal</code>() was invoked by the delivery of a signal, the disposition of the signal would be reset to <code>SIG_DFL</code>, and the system did not block delivery of further instances of the signal. This is equivalent to calling <code><a href="/docs/linux/man/2-sigaction/">sigaction</a></code>(2) with the following flags: </p>
<p> sa.sa_flags = SA_RESETHAND | SA_NODEFER; </p>
<p> System V also provides these semantics for <code>signal</code>(). This was bad because the signal might be delivered again before the handler had a chance to reestablish itself. Furthermore, rapid deliveries of the same signal could result in recursive invocations of the handler. </p>
<p> BSD improved on this situation, but unfortunately also changed the semantics of the existing <code>signal</code>() interface while doing so. On BSD, when a signal handler is invoked, the signal disposition is not reset, and further instances of the signal are blocked from being delivered while the handler is executing. Furthermore, certain blocking system calls are automatically restarted if interrupted by a signal handler (see <code><a href="/docs/linux/man/7-signal/">signal</a></code>(7)). The BSD semantics are equivalent to calling <code><a href="/docs/linux/man/2-sigaction/">sigaction</a></code>(2) with the following flags: </p>
<p> sa.sa_flags = SA_RESTART; </p>
<p> The situation on Linux is as follows:</p>
<dl>
<dt>*</p>
<dd> The kernel&#8217;s <code>signal</code>() system call provides System V semantics.</p>
<dt>*</p>
<dd> By default, in glibc 2 and later, the <code>signal</code>() wrapper function does not invoke the kernel system call. Instead, it calls <code><a href="/docs/linux/man/2-sigaction/">sigaction</a></code>(2) using flags that supply BSD semantics. This default behavior is provided as long as a suitable feature test macro is defined: <code>_BSD_SOURCE</code> on glibc 2.19 and earlier or <code>_DEFAULT_SOURCE</code> in glibc 2.19 and later. (By default, these macros are defined; see <code><a href="/docs/linux/man/7-feature_test_macros/">feature_test_macros</a></code>(7) for details.) If such a feature test macro is not defined, then <code>signal</code>() provides System V semantics.</dl>
