<p>ovs-pki &#8211; OpenFlow public key infrastructure management utility</p>
<h2>Synopsis</h2>
<p>Each command takes the form: <code>ovs-pki</code> [<i>options</i>] <i>command</i> [<i>args</i>] The implemented commands and their arguments are:<br />
 <code>ovs-pki</code> <code>init</code><br />
 <code>ovs-pki</code> <code>req</code> <i>name</i><br />
 <code>ovs-pki</code> <code>sign</code> <i>name</i> [<i>type</i>]<br />
 <code>ovs-pki</code> <code>req+sign</code> <i>name</i> [<i>type</i>]<br />
 <code>ovs-pki</code> <code>verify</code> <i>name</i> [<i>type</i>]<br />
 <code>ovs-pki</code> <code>fingerprint</code> <i>file</i><br />
 <code>ovs-pki</code> <code>self-sign</code> <i>name</i> Each <i>type</i> above is a certificate type, either <code>switch</code> (default) or <code>controller</code>. The available options are:<br />
 [<code>-k</code> <i>type</i> | <code>&#8211;key=</code><i>type</i>]<br />
 [<code>-B</code> <i>nbits</i> | <code>&#8211;bits=</code><i>nbits</i>]<br />
 [<code>-D</code> <i>file</i> | <code>&#8211;dsaparam=</code><i>file</i>]<br />
 [<code>-b</code> | <code>&#8211;batch</code>]<br />
 [<code>-f</code> | <code>&#8211;force</code>]<br />
 [<code>-d</code> <i>dir</i> | <code>&#8211;dir=</code><i>dir</i>]<br />
 [<code>-l</code> <i>file</i> | <code>&#8211;log=</code><i>file</i>]<br />
 [<code>-h</code> | <code>&#8211;help</code>] Some options do not apply to every command. </p>
<h2>Description</h2>
<p>The <code>ovs-pki</code> program sets up and manages a public key infrastructure for use with OpenFlow. It is intended to be a simple interface for organizations that do not have an established public key infrastructure. Other PKI tools can substitute for or supplement the use of <code>ovs-pki</code>. <code>ovs-pki</code> uses <code><a href="/docs/linux/man/1-openssl/">openssl</a></code>(1) for certificate management and key generation. </p>
<h2>Offline Commands</h2>
<p>The following <code>ovs-pki</code> commands support manual PKI administration: </p>
<dl>
<dt><code>init</code></p>
<dd>Initializes a new PKI (by default in directory <code>/var/lib/openvswitch/pki</code>) and populates it with a pair of certificate authorities for controllers and switches. </p>
<p> This command should ideally be run on a high-security machine separate from any OpenFlow controller or switch, called the CA machine. The files <code>pki/controllerca/cacert.pem</code> and <code>pki/switchca/cacert.pem</code> that it produces will need to be copied over to the OpenFlow switches and controllers, respectively. Their contents may safely be made public. </p>
<p> By default, <code>ovs-pki</code> generates 2048-bit RSA keys. The <code>-B</code> or <code>&#8211;bits</code> option (see below) may be used to override the key length. The <code>-k dsa</code> or <code>&#8211;key=dsa</code> option may be used to use DSA in place of RSA. If DSA is selected, the <code>dsaparam.pem</code> file generated in the new PKI hierarchy must be copied to any machine on which the <code>req</code> command (see below) will be executed. Its contents may safely be made public. </p>
<p> Other files generated by <code>init</code> may remain on the CA machine. The files <code>pki/controllerca/private/cakey.pem</code> and <code>pki/switchca/private/cakey.pem</code> have particularly sensitive contents that should not be exposed. </p>
<dt><code>req</code> <i>name</i></p>
<dd>Generates a new private key named <i>name</i><code>-privkey.pem</code> and corresponding certificate request named <i>name</i><code>-req.pem</code>. The private key can be intended for use by a switch or a controller. </p>
<p> This command should ideally be run on the switch or controller that will use the private key to identify itself. The file <i>name</i><code>-req.pem</code> must be copied to the CA machine for signing with the <code>sign</code> command (below). </p>
<p> This command will output a fingerprint to stdout as its final step. Write down the fingerprint and take it to the CA machine before continuing with the <code>sign</code> step. </p>
<p> When RSA keys are in use (as is the default), <code>req</code>, unlike the rest of <code>ovs-pki</code>&#8216;s commands, does not need access to a PKI hierarchy created by <code>ovs-pki init</code>. The <code>-B</code> or <code>&#8211;bits</code> option (see below) may be used to specify the number of bits in the generated RSA key. </p>
<p> When DSA keys are used (as specified with <code>&#8211;key=dsa</code>), <code>req</code> needs access to the <code>dsaparam.pem</code> file created as part of the PKI hierarchy (but not to other files in that tree). By default, <code>ovs-pki</code> looks for this file in <code>/var/lib/openvswitch/pki/dsaparam.pem</code>, but the <code>-D</code> or <code>&#8211;dsaparam</code> option (see below) may be used to specify an alternate location. </p>
<p> <i>name</i><code>-privkey.pem</code> has sensitive contents that should not be exposed. <i>name</i><code>-req.pem</code> may be safely made public. </p>
<dt><code>sign</code> <i>name</i> [<i>type</i>]</p>
<dd>Signs the certificate request named <i>name</i><code>-req.pem</code> that was produced in the previous step, producing a certificate named <i>name</i><code>-cert.pem</code>. <i>type</i>, either <code>switch</code> (default) or <code>controller</code>, indicates the use for which the key is being certified. </p>
<p> This command must be run on the CA machine. </p>
<p> The command will output a fingerprint to stdout and request that you verify that it is the same fingerprint output by the <code>req</code> command. This ensures that the request being signed is the same one produced by <code>req</code>. (The <code>-b</code> or <code>&#8211;batch</code> option suppresses the verification step.) </p>
<p> The file <i>name</i><code>-cert.pem</code> will need to be copied back to the switch or controller for which it is intended. Its contents may safely be made public. </p>
<dt><code>req+sign</code> <i>name</i> [<i>type</i>]</p>
<dd>Combines the <code>req</code> and <code>sign</code> commands into a single step, outputting all the files produced by each. The <i>name</i><code>-privkey.pem</code> and <i>name</i><code>-cert.pem</code> files must be copied securely to the switch or controller. <i>name</i><code>-privkey.pem</code> has sensitive contents and must not be exposed in transit. Afterward, it should be deleted from the CA machine. </p>
<p> This combined method is, theoretically, less secure than the individual steps performed separately on two different machines, because there is additional potential for exposure of the private key. However, it is also more convenient. </p>
<dt><code>verify</code> <i>name</i> [<i>type</i>]</p>
<dd>Verifies that <i>name</i><code>-cert.pem</code> is a valid certificate for the given <i>type</i> of use, either <code>switch</code> (default) or <code>controller</code>. If the certificate is valid for this use, it prints the message &#8220;<i>name</i><code>-cert.pem</code>: OK&#8221;; otherwise, it prints an error message. </p>
<dt><code>fingerprint</code> <i>file</i></p>
<dd>Prints the fingerprint for <i>file</i>. If <i>file</i> is a certificate, then this is the SHA-1 digest of the DER encoded version of the certificate; otherwise, it is the SHA-1 digest of the entire file. </p>
<dt><code>self-sign</code> <i>name</i></p>
<dd>Signs the certificate request named <i>name</i><code>-req.pem</code> using the private key <i>name</i><code>-privkey.pem</code>, producing a self-signed certificate named <i>name</i><code>-cert.pem</code>. The input files should have been produced with <code>ovs-pki req</code>. </p>
<p> Some controllers accept such self-signed certificates. </p>
</dl>
<h2>Options</h2>
<dl>
<dt><code>-k</code> <i>type</i></p>
<dd>
<dt><code>&#8211;key=</code><i>type</i></p>
<dd>For the <code>init</code> command, sets the public key algorithm to use for the new PKI hierarchy. For the <code>req</code> and <code>req+sign</code> commands, sets the public key algorithm to use for the key to be generated, which must match the value specified on <code>init</code>. With other commands, the value has no effect. </p>
<p> The <i>type</i> may be <code>rsa</code> (the default) or <code>dsa</code>. </p>
<dt><code>-B</code> <i>nbits</i></p>
<dd>
<dt><code>&#8211;bits=</code><i>nbits</i></p>
<dd>Sets the number of bits in the key to be generated. When RSA keys are in use, this option affects only the <code>init</code>, <code>req</code>, and <code>req+sign</code> commands, and the same value should be given each time. With DSA keys are in use, this option affects only the <code>init</code> command. </p>
<p> The value must be at least 1024. The default is 2048. </p>
<dt><code>-D</code> <i>file</i></p>
<dd>
<dt><code>&#8211;dsaparam=</code><i>file</i></p>
<dd>Specifies an alternate location for the <code>dsaparam.pem</code> file required by the <code>req</code> and <code>req+sign</code> commands. This option affects only these commands, and only when DSA keys are used. </p>
<p> The default is <code>dsaparam.pem</code> under the PKI hierarchy. </p>
<dt><code>-b</code></p>
<dd>
<dt><code>&#8211;batch</code></p>
<dd>Suppresses the interactive verification of fingerprints that the <code>sign</code> command by default requires. </p>
<dt><code>-d</code> <i>dir</i></p>
<dd>
<dt><code>&#8211;dir=</code><i>dir</i></p>
<dd>Specifies the location of the PKI hierarchy to be used or created by the command (default: <code>/var/lib/openvswitch/pki</code>). All commands, except <code>req</code>, need access to a PKI hierarchy. </p>
<dt><code>-f</code></p>
<dd>
<dt><code>&#8211;force</code></p>
<dd>By default, <code>ovs-pki</code> will not overwrite existing files or directories. This option overrides this behavior. </p>
<dt><code>-l</code> <i>file</i></p>
<dd>
<dt><code>&#8211;log=</code><i>file</i></p>
<dd>Sets the log file to <i>file</i>. Default: <code>/var/log/openvswitch/ovs-pki.log</code>. </p>
<dt><code>-h</code></p>
<dd>
<dt><code>&#8211;help</code></p>
<dd>Prints a help usage message and exits. </p>
</dl>
