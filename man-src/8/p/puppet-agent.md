<p><code>puppet-agent</code> &#8211; The puppet agent daemon</p>
<h2>Synopsis</h2>
<p>Retrieves the client configuration from the puppet master and applies it to the local host. </p>
<p> This service may be run as a daemon, run periodically using cron (or something similar), or run interactively for testing purposes.</p>
<h2>Usage</h2>
<p>puppet agent [&#8211;certname <i>name</i>] [-D|&#8211;daemonize|&#8211;no-daemonize] [-d|&#8211;debug] [&#8211;detailed-exitcodes] [&#8211;digest <i>digest</i>] [&#8211;disable [message]] [&#8211;enable] [&#8211;fingerprint] [-h|&#8211;help] [-l|&#8211;logdest syslog|<i>file</i>|console] [&#8211;no-client] [&#8211;noop] [-o|&#8211;onetime] [-t|&#8211;test] [-v|&#8211;verbose] [-V|&#8211;version] [-w|&#8211;waitforcert <i>seconds</i>]</p>
<h2>Description</h2>
<p>This is the main puppet client. Its job is to retrieve the local machine&#8217;s configuration from a remote server and apply it. In order to successfully communicate with the remote server, the client must have a certificate signed by a certificate authority that the server trusts; the recommended method for this, at the moment, is to run a certificate authority as part of the puppet server (which is the default). The client will connect and request a signed certificate, and will continue connecting until it receives one. </p>
<p> Once the client has a signed certificate, it will retrieve its configuration and apply it.</p>
<h2>Usage Notes</h2>
<p>&#8216;puppet agent&#8217; does its best to find a compromise between interactive use and daemon use. Run with no arguments and no configuration, it will go into the background, attempt to get a signed certificate, and retrieve and apply its configuration every 30 minutes. </p>
<p> Some flags are meant specifically for interactive use &#8212; in particular, &#8216;test&#8217;, &#8216;tags&#8217; or &#8216;fingerprint&#8217; are useful. &#8216;test&#8217; enables verbose logging, causes the daemon to stay in the foreground, exits if the server&#8217;s configuration is invalid (this happens if, for instance, you&#8217;ve left a syntax error on the server), and exits after running the configuration once (rather than hanging around as a long-running process). </p>
<p> &#8216;tags&#8217; allows you to specify what portions of a configuration you want to apply. Puppet elements are tagged with all of the class or definition names that contain them, and you can use the &#8216;tags&#8217; flag to specify one of these names, causing only configuration elements contained within that class or definition to be applied. This is very useful when you are testing new configurations &#8212; for instance, if you are just starting to manage &#8216;ntpd&#8217;, you would put all of the new elements into an &#8216;ntpd&#8217; class, and call puppet with &#8216;&#8211;tags ntpd&#8217;, which would only apply that small portion of the configuration during your testing, rather than applying the whole thing. </p>
<p> &#8216;fingerprint&#8217; is a one-time flag. In this mode &#8216;puppet agent&#8217; will run once and display on the console (and in the log) the current certificate (or certificate request) fingerprint. Providing the &#8216;&#8211;digest&#8217; option allows to use a different digest algorithm to generate the fingerprint. The main use is to verify that before signing a certificate request on the master, the certificate request the master received is the same as the one the client sent (to prevent against man-in-the-middle attacks when signing certificates).</p>
<h2>Options</h2>
<p>Note that any configuration parameter that&#8217;s valid in the configuration file is also a valid long argument. For example, &#8216;server&#8217; is a valid configuration parameter, so you can specify &#8216;&#8211;server <i>servername</i>&#8216; as an argument. </p>
<p> See the configuration file documentation at <a rel="nofollow" href="http://docs.puppetlabs.com/references/stable/configuration.html">http://docs.puppetlabs.com/references/stable/configuration.html</a> for the full list of acceptable parameters. A commented list of all configuration options can also be generated by running puppet agent with &#8216;&#8211;genconfig&#8217;.</p>
<dl>
<dt>&#8211;certname</p>
<dd>Set the certname (unique ID) of the client. The master reads this unique identifying string, which is usually set to the node&#8217;s fully-qualified domain name, to determine which configurations the node will receive. Use this option to debug setup problems or implement unusual node identification schemes.</p>
<dt>&#8211;daemonize</p>
<dd>Send the process into the background. This is the default.</p>
<dt>&#8211;no-daemonize</p>
<dd>Do not send the process into the background.</p>
<dt>&#8211;debug</p>
<dd>Enable full debugging.</p>
<dt>&#8211;detailed-exitcodes</p>
<dd>Provide transaction information via exit codes. If this is enabled, an exit code of &#8216;2&#8217; means there were changes, an exit code of &#8216;4&#8217; means there were failures during the transaction, and an exit code of &#8216;6&#8217; means there were both changes and failures.</p>
<dt>&#8211;digest</p>
<dd>Change the certificate fingerprinting digest algorithm. The default is SHA256. Valid values depends on the version of OpenSSL installed, but will likely contain MD5, MD2, SHA1 and SHA256.</p>
<dt>&#8211;disable</p>
<dd>Disable working on the local system. This puts a lock file in place, causing &#8216;puppet agent&#8217; not to work on the system until the lock file is removed. This is useful if you are testing a configuration and do not want the central configuration to override the local state until everything is tested and committed.</p>
<dd>Disable can also take an optional message that will be reported by the &#8216;puppet agent&#8217; at the next disabled run.</p>
<dd>&#8216;puppet agent&#8217; uses the same lock file while it is running, so no more than one &#8216;puppet agent&#8217; process is working at a time.</p>
<dd>&#8216;puppet agent&#8217; exits after executing this.</p>
<dt>&#8211;enable</p>
<dd>Enable working on the local system. This removes any lock file, causing &#8216;puppet agent&#8217; to start managing the local system again (although it will continue to use its normal scheduling, so it might not start for another half hour).</p>
<dd>&#8216;puppet agent&#8217; exits after executing this.</p>
<dt>&#8211;fingerprint</p>
<dd>Display the current certificate or certificate signing request fingerprint and then exit. Use the &#8216;&#8211;digest&#8217; option to change the digest algorithm used.</p>
<dt>&#8211;help</p>
<dd>Print this help message</p>
<dt>&#8211;logdest</p>
<dd>Where to send messages. Choose between syslog, the console, and a log file. Defaults to sending messages to syslog, or the console if debugging or verbosity is enabled.</p>
<dt>&#8211;no-client</p>
<dd>Do not create a config client. This will cause the daemon to start but not check configuration unless it is triggered with <code>puppet kick</code>. This only makes sense when puppet agent is being run with listen = true in puppet.conf or was started with the <code>&#8211;listen</code> option.</p>
<dt>&#8211;noop</p>
<dd>Use &#8216;noop&#8217; mode where the daemon runs in a no-op or dry-run mode. This is useful for seeing what changes Puppet will make without actually executing the changes.</p>
<dt>&#8211;onetime</p>
<dd>Run the configuration once. Runs a single (normally daemonized) Puppet run. Useful for interactively running puppet agent when used in conjunction with the &#8211;no-daemonize option.</p>
<dt>&#8211;test</p>
<dd>Enable the most common options used for testing. These are &#8216;onetime&#8217;, &#8216;verbose&#8217;, &#8216;ignorecache&#8217;, &#8216;no-daemonize&#8217;, &#8216;no-usecacheonfailure&#8217;, &#8216;detailed-exit-codes&#8217;, &#8216;no-splay&#8217;, and &#8216;show_diff&#8217;.</p>
<dt>&#8211;verbose</p>
<dd>Turn on verbose reporting.</p>
<dt>&#8211;version</p>
<dd>Print the puppet version number and exit.</p>
<dt>&#8211;waitforcert</p>
<dd>This option only matters for daemons that do not yet have certificates and it is enabled by default, with a value of 120 (seconds). This causes &#8216;puppet agent&#8217; to connect to the server every 2 minutes and ask it to sign a certificate request. This is useful for the initial setup of a puppet client. You can turn off waiting for certificates by specifying a time of 0.</dl>
<h2>Example</h2>
<pre>$ puppet agent --server puppet.domain.com</pre>
<h2>Diagnostics</h2>
<p>Puppet agent accepts the following signals:</p>
<dl>
<dt>SIGHUP</p>
<dd>Restart the puppet agent daemon.</p>
<dt>SIGINT and SIGTERM</p>
<dd>Shut down the puppet agent daemon.</p>
<dt>SIGUSR1</p>
<dd>Immediately retrieve and apply configurations from the puppet master.</p>
<dt>SIGUSR2</p>
<dd>Close file descriptors for log files and reopen them. Used with logrotate.</dl>
