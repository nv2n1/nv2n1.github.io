<p>ndbmtd &#8211; the MySQL Cluster data node daemon (multi-threaded version)</p>
<h2>Synopsis</h2>
<dl>
<dt> <code>ndbmtd </code><i>options</i></dl>
<h2>Description</h2>
<p><code>ndbmtd</code></p>
<dd>is a multi-threaded version of <code>ndbd</code>, the process that is used to handle all the data in tables using the NDBCLUSTER storage engine. <code>ndbmtd</code> is intended for use on host computers having multiple CPU cores. Except where otherwise noted, <code>ndbmtd</code> functions in the same way as <code>ndbd</code>; therefore, in this section, we concentrate on the ways in which <code>ndbmtd</code> differs from <code>ndbd</code>, and you should consult <code><a href="/docs/linux/man/8-ndbd/">ndbd</a></code>(8), for additional information about running MySQL Cluster data nodes that apply to both the single-threaded and multi-threaded versions of the data node process. Command-line options and configuration parameters used with <code>ndbd</code> also apply to <code>ndbmtd</code>. For more information about these options and parameters, see <code><a href="/docs/linux/man/8-ndbd/">ndbd</a></code>(8), and Section 17.3.2.6, lqDefining MySQL Cluster Data Nodesrq, respectively. <code>ndbmtd</code> is also file system-compatible with <code>ndbd</code>. In other words, a data node running <code>ndbd</code> can be stopped, the binary replaced with <code>ndbmtd</code>, and then restarted without any loss of data. (However, when doing this, you must make sure that MaxNoOfExecutionThreads is set to an apppriate value before restarting the node if you wish for <code>ndbmtd</code> to run in multi-threaded fashion.) Similarly, an <code>ndbmtd</code> binary can be replaced with <code>ndbd</code> simply by stopping the node and then starting <code>ndbd</code> in place of the multi-threaded binary. It is not necessary when switching between the two to start the data node binary using <code>&#8211;initial</code>. Prior to MySQL Cluster NDB 7.0.6, there were known issues when using <code>ndbmtd</code> with MySQL Cluster Disk Data tables. If you wish to use multi-threaded data nodes with disk-based NDB tables, you should ensure that you are running MySQL Cluster NDB 7.0.6 or later. (m[blue]<code>Bug#41915</code>m[]<font SIZE="-2">[1]</font>, m[blue]<code>Bug#44915</code>m[]<font SIZE="-2">[2]</font>) Using <code>ndbmtd</code> differs from using <code>ndbd</code> in two key respects:</p>
<dl>
<dd>1. You must set an appropriate value for the MaxNoOfExecutionThreads configuration parameter in the config.ini file. If you do not do so, <code>ndbmtd</code> runs in single-threaded mode &#8212; that is, it behaves like <code>ndbd</code>.</dl>
<dl>
<dd>2. Trace files are generated by critical errors in <code>ndbmtd</code> processes in a somewhat different fashion from how these are generated by <code>ndbd</code> failures.</dl>
<p> These differences are discussed in more detail in the next few paragraphs. <code>Number of execution threads</code>. The MaxNoOfExecutionThreads configuration parameter is used to determine the number of local query handler (LQH) threads spawned by <code>ndbmtd</code>. Although this parameter is set in [ndbd] or [ndbd default] sections of the config.ini file, it is exclusive to <code>ndbmtd</code> and does not apply to <code>ndbd</code>. This parameter takes an integer value from 2 to 8 inclusive. Generally, you should set this parameter equal to the number of CPU cores on the data node host, as shown in the following table: </p>

<dl>
<dd><font SIZE="+1"> <code>Note</code> </font><br />
 In MySQL Cluster NDB 6.4.0, it is not possible to set MaxNoOfExecutionThreads to 2. You can safely use the value 3 instead (it is treated as 2 internally). This issue is resolved in MySQL Cluster NDB 6.4.1.  In MySQL Cluster NDB 6.4.0 through 6.4.3, the default value for this parameter was undefined, although the default behavior for <code>ndbmtd</code> was to use 1 LQH thread, as though MaxNoOfExecutionThreads had been set to 2. Beginning with MySQL Cluster NDB 7.0.4, this parameter has an explcit default value of 2, thus guaranteeing this default behavior. In MySQL Cluster NDB 7.0, it is not possible to cause <code>ndbmtd</code> to use more than 1 TC thread, although we plan to introduce this capability in a future MySQL Cluster release series. Like <code>ndbd</code>, <code>ndbmtd</code> generates a set of log files which are placed in the directory specified by DataDir in the config.ini configuration file. Except for trace files, these are generated in the same way and have the same names as those generated by <code>ndbd</code>. In the event of a critical error, <code>ndbmtd</code> generates trace files describing what happened just prior to the error&#8217; occurrence. These files, which can be found in the data node&#8217;s DataDir, are useful for analysis of problems by the MySQL Cluster Development and Support teams. One trace file is generated for each <code>ndbmtd</code> thread. The names of these files follow the pattern ndb_<i>node_id</i>_trace.log.<i>trace_id</i>_t<i>thread_id</i>, where <i>node_id</i> is the data node&#8217;s unique node ID in the cluster, <i>trace_id</i> is a trace sequence number, and <i>thread_id</i> is the thread ID. For example, in the event of the failure of an <code>ndbmtd</code> process running as a MySQL Cluster data node having the node ID 3 and with MaxNoOfExecutionThreads equal to 4, four trace files are generated in the data node&#8217;s data directory; if the is the first time this node has failed, then these files are named ndb_3_trace.log.1_t1, ndb_3_trace.log.1_t2, ndb_3_trace.log.1_t3, and ndb_3_trace.log.1_t4. Internally, these trace files follow the same format as <code>ndbd</code> trace files. The <code>ndbd</code> exit codes and messages that are generated when a data node process shuts down prematurely are also used by <code>ndbmtd</code>. See m[blue]<code>ndbd Error Messages</code>m[]<font SIZE="-2">[3]</font>, for a listing of these.</p>
<dl>
<dd><font SIZE="+1"> <code>Note</code> </font><br />
 It is possible to use <code>ndbd</code> and <code>ndbmtd</code> concurrently on different data nodes in the same MySQL Cluster. However, such configurations have not been tested extensively; thus, we cannot not recommend doing so in a production setting at this time. </p>
