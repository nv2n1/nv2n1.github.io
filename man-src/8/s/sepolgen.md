<p>sepolicy-generate &#8211; Generate an initial SELinux policy module template. </p>
<h2>Synopsis</h2>
<p>Common options <code>sepolicy generate [-h ] [-p PATH]</code>  Confined Applications<br />
 <code>sepolicy generate &#8211;application [-n NAME] [-u USER ]command [-w WRITE_PATH ]</code><br />
 <code>sepolicy generate &#8211;cgi [-n NAME] command [-w WRITE_PATH ]</code><br />
 <code>sepolicy generate &#8211;dbus [-n NAME] command [-w WRITE_PATH ]</code><br />
 <code>sepolicy generate &#8211;inetd [-n NAME] command [-w WRITE_PATH ]</code><br />
 <code>sepolicy generate &#8211;init [-n NAME] command [-w WRITE_PATH ]</code> Confined Users<br />
 <code>sepolicy generate &#8211;admin_user [-r TRANSITION_ROLE] -n NAME</code><br />
 <code>sepolicy generate &#8211;confined_admin -n NAME [-a ADMIN_DOMAIN] [-u USER] [-n NAME] [-w WRITE_PATH]</code><br />
 <code>sepolicy generate &#8211;desktop_user -n NAME [-w WRITE_PATH]</code><br />
 <code>sepolicy generate &#8211;term_user -n NAME [-w WRITE_PATH]</code><br />
 <code>sepolicy generate &#8211;x_user -n NAME [-w WRITE_PATH]</code><br />
 Miscellaneous Policy<br />
 <code>sepolicy generate &#8211;customize -d DOMAIN -n NAME [-a ADMIN_DOMAIN]</code><br />
 <code>sepolicy generate &#8211;newtype -t type -n NAME</code><br />
 <code>sepolicy generate &#8211;sandbox -n NAME</code> </p>
<h2>Description</h2>
<p>Use <code>sepolicy generate</code> to generate an SELinux policy Module.<br />
 <code>sepolicy generate</code> will create 5 files. When specifying a <code>confined application</code> you must specify a path. <code>sepolicy generate</code> will use the rpm payload of the application along with <code>nm -D APPLICATION</code> to help it generate types and policy rules for your policy files. <code>Type Enforcing File NAME.te</code><br />
 This file can be used to define all the types rules for a particular domain. <i>Note:</i> Policy generated by <code>sepolicy generate</code> will automatically add a permissive DOMAIN to your te file. When you are satisfied that your policy works, you need to remove the permissive line from the te file to run your domain in enforcing mode. <code>Interface File NAME.if</code><br />
 This file defines the interfaces for the types generated in the te file, which can be used by other policy domains. <code>File Context NAME.fc</code><br />
 This file defines the default file context for the system, it takes the file types created in the te file and associates file paths to the types. Tools like restorecon and RPM will use these paths to put down labels. <code>RPM Spec File NAME_selinux.spec</code><br />
 This file is an RPM SPEC file that can be used to install the SELinux policy on to machines and setup the labeling. The spec file also installs the interface file and a man page describing the policy. You can use <code>sepolicy manpage -d NAME</code> to generate the man page. <code>Shell File NAME.sh</code><br />
 This is a helper shell script to compile, install and fix the labeling on your test system. It will also generate a man page based on the installed policy, and compile and build an RPM suitable to be installed on other machines If a generate is possible, this tool will print out all generate paths from the source domain to the target domain </p>
<h2>Options</h2>
<dl>
<dt><i>-h, &#8211;help</i></p>
<dd>Display help message</p>
<dt><i>-d, &#8211;domain</i></p>
<dd>Enter domain type(s) which you will be extending</p>
<dt><i>-n, &#8211;name</i></p>
<dd>Specify alternate name of policy. The policy will default to the executable or name specified</p>
<dt><i>-p, &#8211;path</i></p>
<dd>Specify the directory to store the created policy files. (Default to current working directory ) optional arguments:</p>
<dt><i>-r, &#8211;role</i></p>
<dd>Enter role(s) to which this admin user will transition.</p>
<dt><i>-t, &#8211;type</i></p>
<dd>Enter type(s) for which you will generate new definition and rule(s)</p>
<dt><i>-u, &#8211;user</i></p>
<dd>SELinux user(s) which will transition to this domain</p>
<dt><i>-w, &#8211;writepath</i></p>
<dd>Path(s) which the confined processes need to write</p>
<dt><i>-a, &#8211;admin</i></p>
<dd>Domain(s) which the confined admin will administrate</p>
<dt><i>&#8211;admin_user </i></p>
<dd>Generate Policy for Administrator Login User Role</p>
<dt><i>&#8211;application</i></p>
<dd>Generate Policy for User Application</p>
<dt><i>&#8211;cgi</i></p>
<dd>Generate Policy for Web Application/Script (CGI)</p>
<dt><i>&#8211;confined_admin</i></p>
<dd>Generate Policy for Confined Root Administrator Role</p>
<dt><i>&#8211;customize</i></p>
<dd>Generate Policy for Existing Domain Type</p>
<dt><i>&#8211;dbus</i></p>
<dd>Generate Policy for DBUS System Daemon</p>
<dt><i>&#8211;desktop_user</i></p>
<dd>Generate Policy for Desktop Login User Role</p>
<dt><i>&#8211;inetd</i></p>
<dd>Generate Policy for Internet Services Daemon</p>
<dt><i>&#8211;init</i></p>
<dd>Generate Policy for Standard Init Daemon (Default)</p>
<dt><i>&#8211;newtype</i></p>
<dd>Generate new policy for new types to add to an existing policy.</p>
<dt><i>&#8211;sandbox</i></p>
<dd>Generate Policy for Sandbox</p>
<dt><i>&#8211;term_user</i></p>
<dd>Generate Policy for Minimal Terminal Login User Role</p>
<dt><i>&#8211;x_user</i></p>
<dd>Generate Policy for Minimal X Windows Login User Role </p>
</dl>
<h2>Example</h2>
<p><code>&gt; sepolicy generate &#8211;init /usr/sbin/rwhod</code><br />
 Generating Policy for /usr/sbin/rwhod named rwhod<br />
 Created the following files:<br />
 rwhod.te # Type Enforcement file<br />
 rwhod.if # Interface file<br />
 rwhod.fc # File Contexts file<br />
 rwhod_selinux.spec # Spec file<br />
 rwhod.sh # Setup Script </p>
