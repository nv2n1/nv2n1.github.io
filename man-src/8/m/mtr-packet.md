<h2>Name</h2>
<dd>mtr-packet &#8211; send and receive network probes</p>
<h2>Description</h2>
<p><code>mtr-packet</code> is a tool for sending network probes to measure network connectivity and performance. Many network probes can be sent simultaneously by a single process instance of <code>mtr-packet</code> and additional probes can be generated by an instance of <code>mtr-packet</code> which already has network probes in flight. It is intended to be used by programs which invoke it with Unix pipes attached to its standard input and output streams. </p>
<p> <code>mtr-packet</code> reads command requests from <i>stdin</i>, each separated by a newline character, and responds with command replies to <i>stdout</i>, also each separated by a newline character. The syntactic structure of requests and replies are the same. The following format is used: </p>
<dl>
<dd><i>TOKEN</i> <i>COMMAND</i> [<i>ARGUMENT-NAME</i> <i>ARGUMENT-VALUE</i> &#8230;]</dl>
<p> <i>TOKEN</i> is a unique integer value. The same value will be used as the <i>TOKEN</i> for the response. This is necessary for associating replies with requests, as commands may be completed in a different order than they are requested. The invoker of <code>mtr-packet</code> should always use the <i>TOKEN</i> value to determine which command request has completed. </p>
<p> <i>COMMAND</i> is a string identifying the command request type. A common command is <code>send-probe</code>, which will transmit one network probe. </p>
<p> <i>ARGUMENT-NAME</i> strings and <i>ARGUMENT-VALUE</i> strings always come in pairs. It is a syntactic error to provide an <i>ARGUMENT-NAME</i> without a corresponding <i>ARGUMENT-VALUE</i>. Valid <i>ARGUMENT-NAME</i> strings depend on the <i>COMMAND</i> being used.</p>
<h2>Requests</h2>
<dl>
<dt><code>send-probe</code></p>
<dd>Send a network probe to a particular IP address. Either an <code>ip-4</code> or <code>ip-6</code> argument must be provided. A valid <code>send-probe</code> command will reply with <code>reply</code>, <code>no-reply</code>, or <code>ttl-expired</code>.</p>
<dd>The following arguments may be used:</p>
<dd><code>ip-4</code> <i>IP-ADDRESS</i></p>
<dt>
<dd>
<dd>The Internet Protocol version 4 address to probe.</p>
<dt>
<dd><code>ip-6</code> <i>IP-ADDRESS</i></p>
<dt>
<dd>
<dd>The Internet Protocol version 6 address to probe.</p>
<dt>
<dd><code>protocol</code> <i>PROTOCOL</i></p>
<dt>
<dd>
<dd>The protocol to use for the network probe. <code>icmp</code>, <code>sctp</code>, <code>tcp</code>, and <code>udp</code> may be used. The default protocol is <code>icmp.</code></p>
<dt>
<dd><code>port</code> <i>PORT-NUMBER</i></p>
<dt>
<dd>
<dd>The destination port to use for <code>sctp</code>, <code>tcp</code>, or <code>udp</code> probes.</p>
<dt>
<dd><code>local-ip-4</code> <i>IP-ADDRESS</i></p>
<dt>
<dd>
<dd>The local Internet Protocol version 4 address to use when sending probes.</p>
<dt>
<dd><code>local-ip-6</code> <i>IP-ADDRESS</i></p>
<dt>
<dd>
<dd>The local Internet Protocol version 6 address to use when sending probes.</p>
<dt>
<dd><code>local-port</code> <i>PORT-NUMBER</i></p>
<dt>
<dd>
<dd>For <code>udp</code> probes, the local port number from which to send probes.</p>
<dt>
<dd><code>timeout</code> <i>TIMEOUT-SECONDS</i></p>
<dt>
<dd>
<dd>The number of seconds to wait for a response to the probe before discarding the probe as lost, and generating a <code>no-reply</code> command reply.</p>
<dt>
<dd><code>ttl</code> <i>TIME-TO-LIVE</i></p>
<dt>
<dd>
<dd>The time-to-live value for the Internet Protocol packet header used in constructing the probe. This value determines the number of network hops through which the probe will travel before a response is generated by an intermediate network host.</p>
<dt>
<dd><code>size</code> <i>PACKET-SIZE</i></p>
<dt>
<dd>
<dd>The size of the packet used to send the probe, in bytes, including the Internet Protocol header and transport protocol header.</p>
<dt>
<dd><code>bit-pattern</code> <i>PATTERN-VALUE</i></p>
<dt>
<dd>
<dd>The packet payload is filled with bytes of the value specified. Valid pattern values are in the range 0 through 255.</p>
<dt>
<dd>
<dd><code>tos</code> <i>TYPE-OF-SERVICE</i></p>
<dt>
<dd>
<dd>In the case of IPv4, the &quot;type of service&quot; field in the IP header is set to this value. In the case of IPv6, the &quot;traffic class&quot; field is set.</p>
<dt>
<dd><code>mark</code> <i>ROUTING-MARK</i></p>
<dt>
<dd>
<dd>The packet mark value to be used by mark-based routing. (Available only on Linux.)</p>
<dt>
<dt><code>check-support</code></p>
<dd>
<dd>Check for support for a particular feature in this version of <code>mtr-packet</code> and in this particular operating environment. <code>check-support</code> will reply with <code>feature-supported</code>. A <code>feature</code> argument is required.</p>
<dt>
<dd><code>feature</code> <i>FEATURE-NAME</i></p>
<dt>
<dd>
<dd>The name of a feature requested.</p>
<dt>
<dd>
<dd>Some features which can be checked are <code>send-probe</code>, <code>ip-4</code>, <code>ip-6</code>, <code>icmp</code>, <code>sctp</code>, <code>tcp</code>, <code>udp</code>, and <code>mark</code>. The feature <code>version</code> can be checked to retrieve the version of <code>mtr-packet</code>.</dl>
<h2>Replies</h2>
<dl>
<dt><code>reply</code></p>
<dd>The destination host received the <code>send-probe</code> probe and replied. Arguments of <code>reply</code> are:</p>
<dt>
<dd><code>ip-4</code> <i>IP-ADDRESS</i></p>
<dt>
<dd>
<dd>The Internet Protocol version 4 address of the host which replied to the probe.</p>
<dt>
<dd><code>ip-6</code> <i>IP-ADDRESS</i></p>
<dt>
<dd>
<dd>The Internet Protocol version 6 address of the host which replied to the probe.</p>
<dt>
<dd><code>round-trip-time</code> <i>TIME</i></p>
<dt>
<dd>
<dd>The time which passed between the transmission of the probe and its response. The time is provided as a integral number of microseconds elapsed.</p>
<dt>
<dt><code>no-reply</code></p>
<dd>
<dd>No response to the probe request was received before the timeout expired.</p>
<dt><code>ttl-expired</code></p>
<dd>The time-to-live value of the transmitted probe expired before the probe arrived at its intended destination. Arguments of <code>ttl-expired</code> are:</p>
<dt>
<dd><code>ip-4</code> <i>IP-ADDRESS</i></p>
<dt>
<dd>
<dd>The Internet Protocol version 4 address of the host at which the time-to-live value expired.</p>
<dt>
<dd><code>ip-6</code> <i>IP-ADDRESS</i></p>
<dt>
<dd>
<dd>The Internet Protocol version 6 address of the host at which the time-to-live value expired.</p>
<dt>
<dd><code>round-trip-time</code> <i>TIME</i></p>
<dt>
<dd>
<dd>The time which passed between the transmission of the probe and its response. The time is provided as a integral number of microseconds elapsed.</p>
<dt>
<dd><code>mpls</code> <i>MPLS-LABEL-LIST</i></p>
<dt>
<dd>
<dd>A list of Multiprotocol Label Switching values returned with the probe response. If the <code>mpls</code> argument is present, one or more MPLS labels will be represented by a comma separated list of values. The values are provided in groups of four. The first four values in the list correspond to the first MPLS label, the next four values correspond to the second MPLS label, and so on. The values are provided in this order: <i>label</i>, <i>traffic-class</i>, <i>bottom-of-stack</i>, <i>ttl</i>.</p>
<dt>
<dt><code>no-route</code></p>
<dd>
<dd>There was no route to the host used in a <code>send-probe</code> request.</p>
<dt><code>network-down</code></p>
<dd>A probe could not be sent because the network is down.</p>
<dt><code>probes-exhausted</code></p>
<dd>A probe could not be sent because there are already too many unresolved probes in flight.</p>
<dt><code>permission-denied</code></p>
<dd>The operating system denied permission to send the probe with the specified options.</p>
<dt><code>invalid-argument</code></p>
<dd>The command request contained arguments which are invalid.</p>
<dt><code>feature-support</code></p>
<dd>A reply to provided to <code>check-support</code> indicating the availability of a particular feature. The argument provided is:</p>
<dt>
<dd><code>support</code> <i>PRESENT</i></p>
<dt>
<dd>
<dd>In most cases, the <i>PRESENT</i> value will be either <code>ok</code>, indicating the feature is supported, or <code>no</code>, indicating no support for the feature.</p>
<dd>In the case that <code>version</code> is the requested <i>FEATURE-NAME</i>, the version of <code>mtr-packet</code> is provided as the <i>PRESENT</i> value.</p>
<dt>
<dd></dl>
<h2>Examples</h2>
<dd>A controlling program may start <code>mtr-packet</code> as a child process and issue the following command on <i>stdin</i>: </p>
<dl>
<dd>42 send-probe ip-4 127.0.0.1</dl>
<p> This will send a network probe to the loopback interface. When the probe completes, <code>mtr-packet</code> will provide a response on <i>stdout</i> such as the following: </p>
<dl>
<dd>42 reply ip-4 127.0.0.1 round-trip-time 126</dl>
<p> This indicates that the loopback address replied to the probe, and the round-trip time of the probe was 126 microseconds. </p>
<p> In order to trace the route to a remote host, multiple <code>send-probe</code> commands, each with a different <code>ttl</code> value, are used. </p>
<dl>
<dd>11 send-probe ip-4 8.8.8.8 ttl 1</p>
<dl>
<dd>12 send-probe ip-4 8.8.8.8 ttl 2</p>
<dl>
<dd>13 send-probe ip-4 8.8.8.8 ttl 3</p>
<dl>
<dd>&#8230;</dl>
<p> Each intermediate host would respond with a <code>ttl-expired</code> message, and the destination host would respond with a <code>reply</code>: </p>
<dl>
<dd>11 ttl-expired ip-4 192.168.254.254 round-trip-time 1634</p>
<dl>
<dd>12 ttl-expired ip-4 184.19.243.240 round-trip-time 7609</p>
<dl>
<dd>13 ttl-expired ip-4 172.76.20.169 round-trip-time 8643</p>
<dl>
<dd>14 ttl-expired ip-4 74.40.1.101 round-trip-time 9755</p>
<dl>
<dd>15 ttl-expired ip-4 74.40.5.126 round-trip-time 10695</p>
<dl>
<dd>17 ttl-expired ip-4 108.170.245.97 round-trip-time 14077</p>
<dl>
<dd>16 ttl-expired ip-4 74.40.26.131 round-trip-time 15253</p>
<dl>
<dd>18 ttl-expired ip-4 209.85.245.101 round-trip-time 17080</p>
<dl>
<dd>19 reply ip-4 8.8.8.8 round-trip-time 17039</dl>
<p> Note that the replies in this example are printed out of order. (The reply to probe 17 arrives prior to the reply to probe 16.) This is the reason that it is important to send commands with unique token values, and to use those token values to match replies with their originating commands.</dl>
