<p>iptables-extensions &#8212; list of extensions in the standard iptables distribution</p>
<h2>Synopsis</h2>
<p><code>ip6tables</code> [<code>-m</code> <i>name</i> [<i>module-options</i>&#8230;]] [<code>-j</code> <i>target-name</i> [<i>target-options</i>&#8230;] </p>
<p> <code>iptables</code> [<code>-m</code> <i>name</i> [<i>module-options</i>&#8230;]] [<code>-j</code> <i>target-name</i> [<i>target-options</i>&#8230;]</p>
<h2>Match Extensions</h2>
<p>iptables can use extended packet matching modules with the <code>-m</code> or <code>&#8211;match</code> options, followed by the matching module name; after these, various extra command line options become available, depending on the specific module. You can specify multiple extended match modules in one line, and you can use the <code>-h</code> or <code>&#8211;help</code> options after the module has been specified to receive help specific to that module. The extended match modules are evaluated in the order they are specified in the rule. </p>
<p> If the <code>-p</code> or <code>&#8211;protocol</code> was specified and if and only if an unknown option is encountered, iptables will try load a match module of the same name as the protocol, to try making the option available.</p>
<h3>addrtype</h3>
<p>This module matches packets based on their <code>address type.</code> Address types are used within the kernel networking stack and categorize addresses into various groups. The exact definition of that group depends on the specific layer three protocol. </p>
<p> The following address types are possible:</p>
<dl>
<dt><code>UNSPEC</code></p>
<dd>an unspecified address (i.e. 0.0.0.0)</p>
<dt><code>UNICAST</code></p>
<dd>an unicast address</p>
<dt><code>LOCAL</code></p>
<dd>a local address</p>
<dt><code>BROADCAST</code></p>
<dd>a broadcast address</p>
<dt><code>ANYCAST</code></p>
<dd>an anycast packet</p>
<dt><code>MULTICAST</code></p>
<dd>a multicast address</p>
<dt><code>BLACKHOLE</code></p>
<dd>a blackhole address</p>
<dt><code>UNREACHABLE</code></p>
<dd>an unreachable address</p>
<dt><code>PROHIBIT</code></p>
<dd>a prohibited address</p>
<dt><code>THROW</code></p>
<dd>FIXME</p>
<dt><code>NAT</code></p>
<dd>FIXME</p>
<dt><code>XRESOLVE</code></p>
<dd>
<dt>[<code>!</code>] <code>&#8211;src-type</code> <i>type</i></p>
<dd>Matches if the source address is of given type</p>
<dt>[<code>!</code>] <code>&#8211;dst-type</code> <i>type</i></p>
<dd>Matches if the destination address is of given type</p>
<dt><code>&#8211;limit-iface-in</code></p>
<dd>The address type checking can be limited to the interface the packet is coming in. This option is only valid in the <code>PREROUTING</code>, <code>INPUT</code> and <code>FORWARD</code> chains. It cannot be specified with the <code>&#8211;limit-iface-out</code> option.</p>
<dt><code>&#8211;limit-iface-out</code></p>
<dd>The address type checking can be limited to the interface the packet is going out. This option is only valid in the <code>POSTROUTING</code>, <code>OUTPUT</code> and <code>FORWARD</code> chains. It cannot be specified with the <code>&#8211;limit-iface-in</code> option.</dl>

<h3>bpf</h3>
<p>Match using Linux Socket Filter. Expects a path to an eBPF object or a cBPF program in decimal format.</p>
<dl>
<dt><code>&#8211;object-pinned</code> <i>path</i></p>
<dd>Pass a path to a pinned eBPF object.</dl>
<p> Applications load eBPF programs into the kernel with the bpf() system call and BPF_PROG_LOAD command and can pin them in a virtual filesystem with BPF_OBJ_PIN. To use a pinned object in iptables, mount the bpf filesystem using</p>
<dl>
<dd>mount -t bpf bpf ${BPF_MOUNT}</dl>
<p> then insert the filter in iptables by path:</p>
<dl>
<dd>iptables -A OUTPUT -m bpf &#8211;object-pinned ${BPF_MOUNT}/{PINNED_PATH} -j ACCEPT</p>
<dt><code>&#8211;bytecode</code> <i>code</i></p>
<dd>Pass the BPF byte code format as generated by the <code>nfbpf_compile</code> utility.</dl>
<p> The code format is similar to the output of the tcpdump -ddd command: one line that stores the number of instructions, followed by one line for each instruction. Instruction lines follow the pattern &#8216;u16 u8 u8 u32&#8217; in decimal notation. Fields encode the operation, jump offset if true, jump offset if false and generic multiuse field &#8216;K&#8217;. Comments are not supported. </p>
<p> For example, to read only packets matching &#8216;ip proto 6&#8217;, insert the following, without the comments or trailing whitespace:</p>
<dl>
<dd>4 # number of instructions<br />
 48 0 0 9 # load byte ip-&gt;proto<br />
 21 0 1 6 # jump equal IPPROTO_TCP<br />
 6 0 0 1 # return pass (non-zero)<br />
 6 0 0 0 # return fail (zero)</dl>
<p> You can pass this filter to the bpf match with the following command:</p>
<dl>
<dd>iptables -A OUTPUT -m bpf &#8211;bytecode &#8216;4,48 0 0 9,21 0 1 6,6 0 0 1,6 0 0 0&#8217; -j ACCEPT</dl>
<p> Or instead, you can invoke the nfbpf_compile utility.</p>
<dl>
<dd>iptables -A OUTPUT -m bpf &#8211;bytecode &quot;`nfbpf_compile RAW &#8216;ip proto 6&#8217;`&quot; -j ACCEPT</dl>
<p> Or use tcpdump -ddd. In that case, generate BPF targeting a device with the same data link type as the xtables match. Iptables passes packets from the network layer up, without mac layer. Select a device with data link type RAW, such as a tun device:</p>
<dl>
<dd>ip tuntap add tun0 mode tun<br />
 ip link set tun0 up<br />
 tcpdump -ddd -i tun0 ip proto 6</dl>
<p> See tcpdump -L -i $dev for a list of known data link types for a given device. </p>
<p> You may want to learn more about BPF from FreeBSD&#8217;s <a href="/docs/linux/man/4-bpf/">bpf</a>(4) manpage.</p>
<h3>cgroup</h3>
<dl>
<dt>[<code>!</code>] <code>&#8211;path</code> <i>path</i></p>
<dd>Match cgroup2 membership. </p>
<p> Each socket is associated with the v2 cgroup of the creating process. This matches packets coming from or going to all sockets in the sub-hierarchy of the specified path. The path should be relative to the root of the cgroup2 hierarchy.</p>
<dt>[<code>!</code>] <code>&#8211;cgroup</code> <i>classid</i></p>
<dd>Match cgroup net_cls classid. </p>
<p> classid is the marker set through the cgroup net_cls controller. This option and &#8211;path can&#8217;t be used together.</dl>
<p> Example:</p>
<dl>
<dd>iptables -A OUTPUT -p tcp &#8211;sport 80 -m cgroup ! &#8211;path service/http-server -j DROP</p>
<dd>iptables -A OUTPUT -p tcp &#8211;sport 80 -m cgroup ! &#8211;cgroup 1 -j DROP</dl>
<p> <code>IMPORTANT</code>: when being used in the INPUT chain, the cgroup matcher is currently only of limited functionality, meaning it will only match on packets that are processed for local sockets through early socket demuxing. Therefore, general usage on the INPUT chain is not advised unless the implications are well understood. </p>
<p> Available since Linux 3.14.</p>
<h3>cluster</h3>
<p>Allows you to deploy gateway and back-end load-sharing clusters without the need of load-balancers. </p>
<p> This match requires that all the nodes see the same packets. Thus, the cluster match decides if this node has to handle a packet given the following options:</p>
<dl>
<dt><code>&#8211;cluster-total-nodes</code> <i>num</i></p>
<dd>Set number of total nodes in cluster.</p>
<dt>[<code>!</code>] <code>&#8211;cluster-local-node</code> <i>num</i></p>
<dd>Set the local node number ID.</p>
<dt>[<code>!</code>] <code>&#8211;cluster-local-nodemask</code> <i>mask</i></p>
<dd>Set the local node number ID mask. You can use this option instead of <code>&#8211;cluster-local-node</code>.</p>
<dt><code>&#8211;cluster-hash-seed</code> <i>value</i></p>
<dd>Set seed value of the Jenkins hash.</dl>
<p> Example:</p>
<dl>
<dd>iptables -A PREROUTING -t mangle -i eth1 -m cluster &#8211;cluster-total-nodes 2 &#8211;cluster-local-node 1 &#8211;cluster-hash-seed 0xdeadbeef -j MARK &#8211;set-mark 0xffff</p>
<dd>iptables -A PREROUTING -t mangle -i eth2 -m cluster &#8211;cluster-total-nodes 2 &#8211;cluster-local-node 1 &#8211;cluster-hash-seed 0xdeadbeef -j MARK &#8211;set-mark 0xffff</p>
<dd>iptables -A PREROUTING -t mangle -i eth1 -m mark ! &#8211;mark 0xffff -j DROP</p>
<dd>iptables -A PREROUTING -t mangle -i eth2 -m mark ! &#8211;mark 0xffff -j DROP</dl>
<p> And the following commands to make all nodes see the same packets:</p>
<dl>
<dd>ip maddr add 01:00:5e:00:01:01 dev eth1</p>
<dd>ip maddr add 01:00:5e:00:01:02 dev eth2</p>
<dd>arptables -A OUTPUT -o eth1 &#8211;h-length 6 -j mangle &#8211;mangle-mac-s 01:00:5e:00:01:01</p>
<dd>arptables -A INPUT -i eth1 &#8211;h-length 6 &#8211;destination-mac 01:00:5e:00:01:01 -j mangle &#8211;mangle-mac-d 00:zz:yy:xx:5a:27</p>
<dd>arptables -A OUTPUT -o eth2 &#8211;h-length 6 -j mangle &#8211;mangle-mac-s 01:00:5e:00:01:02</p>
<dd>arptables -A INPUT -i eth2 &#8211;h-length 6 &#8211;destination-mac 01:00:5e:00:01:02 -j mangle &#8211;mangle-mac-d 00:zz:yy:xx:5a:27</dl>
<p> <code>NOTE</code>: the arptables commands above use mainstream syntax. If you are using arptables-jf included in some RedHat, CentOS and Fedora versions, you will hit syntax errors. Therefore, you&#8217;ll have to adapt these to the arptables-jf syntax to get them working. </p>
<p> In the case of TCP connections, pickup facility has to be disabled to avoid marking TCP ACK packets coming in the reply direction as valid.</p>
<dl>
<dd>echo 0 &gt; /proc/sys/net/netfilter/nf_conntrack_tcp_loose</dl>

<h3>connbytes</h3>
<p>Match by how many bytes or packets a connection (or one of the two flows constituting the connection) has transferred so far, or by average bytes per packet. </p>
<p> The counters are 64-bit and are thus not expected to overflow ;) </p>
<p> The primary use is to detect long-lived downloads and mark them to be scheduled using a lower priority band in traffic control. </p>
<p> The transferred bytes per connection can also be viewed through `conntrack -L` and accessed via ctnetlink. </p>
<p> NOTE that for connections which have no accounting information, the match will always return false. The &quot;net.netfilter.nf_conntrack_acct&quot; sysctl flag controls whether <code>new</code> connections will be byte/packet counted. Existing connection flows will not be gaining/losing a/the accounting structure when be sysctl flag is flipped.</p>
<dl>
<dt>[<code>!</code>] <code>&#8211;connbytes</code> <i>from</i>[<code>:</code><i>to</i>]</p>
<dd>match packets from a connection whose packets/bytes/average packet size is more than FROM and less than TO bytes/packets. if TO is omitted only FROM check is done. &quot;!&quot; is used to match packets not falling in the range.</p>
<dt><code>&#8211;connbytes-dir</code> {<code>original</code>|<code>reply</code>|<code>both</code>}</p>
<dd>which packets to consider</p>
<dt><code>&#8211;connbytes-mode</code> {<code>packets</code>|<code>bytes</code>|<code>avgpkt</code>}</p>
<dd>whether to check the amount of packets, number of bytes transferred or the average size (in bytes) of all packets received so far. Note that when &quot;both&quot; is used together with &quot;avgpkt&quot;, and data is going (mainly) only in one direction (for example HTTP), the average packet size will be about half of the actual data packets.</p>
<dt>Example:</p>
<dd>iptables .. -m connbytes &#8211;connbytes 10000:100000 &#8211;connbytes-dir both &#8211;connbytes-mode bytes &#8230;</dl>
<h3>connlabel</h3>
<p>Module matches or adds connlabels to a connection. connlabels are similar to connmarks, except labels are bit-based; i.e. all labels may be attached to a flow at the same time. Up to 128 unique labels are currently supported.</p>
<dl>
<dt>[<code>!</code>] <code>&#8211;label</code> <code>name</code></p>
<dd>matches if label <code>name</code> has been set on a connection. Instead of a name (which will be translated to a number, see EXAMPLE below), a number may be used instead. Using a number always overrides connlabel.conf.</p>
<dt><code>&#8211;set</code></p>
<dd>if the label has not been set on the connection, set it. Note that setting a label can fail. This is because the kernel allocates the conntrack label storage area when the connection is created, and it only reserves the amount of memory required by the ruleset that exists at the time the connection is created. In this case, the match will fail (or succeed, in case <code>&#8211;label</code> option was negated).</dl>
<p> This match depends on libnetfilter_conntrack 1.0.4 or later. Label translation is done via the <code>/etc/xtables/connlabel.conf</code> configuration file. </p>
<p> Example:</p>
<dl>
<dd>
<pre>0 eth0-in
1 eth0-out
2 ppp-in
3 ppp-out
4 bulk-traffic
5 interactive</pre>
</dl>
<h3>connlimit</h3>
<p>Allows you to restrict the number of parallel connections to a server per client IP address (or client address block).</p>
<dl>
<dt><code>&#8211;connlimit-upto</code> <i>n</i></p>
<dd>Match if the number of existing connections is below or equal <i>n</i>.</p>
<dt><code>&#8211;connlimit-above</code> <i>n</i></p>
<dd>Match if the number of existing connections is above <i>n</i>.</p>
<dt><code>&#8211;connlimit-mask</code> <i>prefix_length</i></p>
<dd>Group hosts using the prefix length. For IPv4, this must be a number between (including) 0 and 32. For IPv6, between 0 and 128. If not specified, the maximum prefix length for the applicable protocol is used.</p>
<dt><code>&#8211;connlimit-saddr</code></p>
<dd>Apply the limit onto the source group. This is the default if &#8211;connlimit-daddr is not specified.</p>
<dt><code>&#8211;connlimit-daddr</code></p>
<dd>Apply the limit onto the destination group.</dl>
<p> Examples:</p>
<dl>
<dt># allow 2 telnet connections per client host</p>
<dd>iptables -A INPUT -p tcp &#8211;syn &#8211;dport 23 -m connlimit &#8211;connlimit-above 2 -j REJECT</p>
<dt># you can also match the other way around:</p>
<dd>iptables -A INPUT -p tcp &#8211;syn &#8211;dport 23 -m connlimit &#8211;connlimit-upto 2 -j ACCEPT</p>
<dt># limit the number of parallel HTTP requests to 16 per class C sized source network (24 bit netmask)</p>
<dd>iptables -p tcp &#8211;syn &#8211;dport 80 -m connlimit &#8211;connlimit-above 16 &#8211;connlimit-mask 24 -j REJECT</p>
<dt># limit the number of parallel HTTP requests to 16 for the link local network</p>
<dd>(ipv6) ip6tables -p tcp &#8211;syn &#8211;dport 80 -s fe80::/64 -m connlimit &#8211;connlimit-above 16 &#8211;connlimit-mask 64 -j REJECT</p>
<dt># Limit the number of connections to a particular host:</p>
<dd>ip6tables -p tcp &#8211;syn &#8211;dport 49152:65535 -d 2001:db8::1 -m connlimit &#8211;connlimit-above 100 -j REJECT</dl>

<h3>conntrack</h3>
<p>This module, when combined with connection tracking, allows access to the connection tracking state for this packet/connection.</p>
<dl>
<dt>[<code>!</code>] <code>&#8211;ctstate</code> <i>statelist</i></p>
<dd><i>statelist</i> is a comma separated list of the connection states to match. Possible states are listed below.</p>
<dt>[<code>!</code>] <code>&#8211;ctproto</code> <i>l4proto</i></p>
<dd>Layer-4 protocol to match (by number or name)</p>
<dt>[<code>!</code>] <code>&#8211;ctorigsrc</code> <i>address</i>[<code>/</code><i>mask</i>]</p>
<dd>
<dt>[<code>!</code>] <code>&#8211;ctorigdst</code> <i>address</i>[<code>/</code><i>mask</i>]</p>
<dd>
<dt>[<code>!</code>] <code>&#8211;ctreplsrc</code> <i>address</i>[<code>/</code><i>mask</i>]</p>
<dd>
<dt>[<code>!</code>] <code>&#8211;ctrepldst</code> <i>address</i>[<code>/</code><i>mask</i>]</p>
<dd>Match against original/reply source/destination address</p>
<dt>[<code>!</code>] <code>&#8211;ctorigsrcport</code> <i>port</i>[<code>:</code><i>port</i>]</p>
<dd>
<dt>[<code>!</code>] <code>&#8211;ctorigdstport</code> <i>port</i>[<code>:</code><i>port</i>]</p>
<dd>
<dt>[<code>!</code>] <code>&#8211;ctreplsrcport</code> <i>port</i>[<code>:</code><i>port</i>]</p>
<dd>
<dt>[<code>!</code>] <code>&#8211;ctrepldstport</code> <i>port</i>[<code>:</code><i>port</i>]</p>
<dd>Match against original/reply source/destination port (TCP/UDP/etc.) or GRE key. Matching against port ranges is only supported in kernel versions above 2.6.38.</p>
<dt>[<code>!</code>] <code>&#8211;ctstatus</code> <i>statelist</i></p>
<dd><i>statuslist</i> is a comma separated list of the connection statuses to match. Possible statuses are listed below.</p>
<dt>[<code>!</code>] <code>&#8211;ctexpire</code> <i>time</i>[<code>:</code><i>time</i>]</p>
<dd>Match remaining lifetime in seconds against given value or range of values (inclusive)</p>
<dt><code>&#8211;ctdir</code> {<code>ORIGINAL</code>|<code>REPLY</code>}</p>
<dd>Match packets that are flowing in the specified direction. If this flag is not specified at all, matches packets in both directions.</dl>
<p> States for <code>&#8211;ctstate</code>:</p>
<dl>
<dt><code>INVALID</code></p>
<dd>The packet is associated with no known connection.</p>
<dt><code>NEW</code></p>
<dd>The packet has started a new connection or otherwise associated with a connection which has not seen packets in both directions.</p>
<dt><code>ESTABLISHED</code></p>
<dd>The packet is associated with a connection which has seen packets in both directions.</p>
<dt><code>RELATED</code></p>
<dd>The packet is starting a new connection, but is associated with an existing connection, such as an FTP data transfer or an ICMP error.</p>
<dt><code>UNTRACKED</code></p>
<dd>The packet is not tracked at all, which happens if you explicitly untrack it by using -j CT &#8211;notrack in the raw table.</p>
<dt><code>SNAT</code></p>
<dd>A virtual state, matching if the original source address differs from the reply destination.</p>
<dt><code>DNAT</code></p>
<dd>A virtual state, matching if the original destination differs from the reply source.</dl>
<p> Statuses for <code>&#8211;ctstatus</code>:</p>
<dl>
<dt><code>NONE</code></p>
<dd>None of the below.</p>
<dt><code>EXPECTED</code></p>
<dd>This is an expected connection (i.e. a conntrack helper set it up).</p>
<dt><code>SEEN_REPLY</code></p>
<dd>Conntrack has seen packets in both directions.</p>
<dt><code>ASSURED</code></p>
<dd>Conntrack entry should never be early-expired.</p>
<dt><code>CONFIRMED</code></p>
<dd>Connection is confirmed: originating packet has left box.</dl>

<h3>hashlimit</h3>
<p><code>hashlimit</code> uses hash buckets to express a rate limiting match (like the <code>limit</code> match) for a group of connections using a <code>single</code> iptables rule. Grouping can be done per-hostgroup (source and/or destination address) and/or per-port. It gives you the ability to express &quot;<i>N</i> packets per time quantum per group&quot; or &quot;<i>N</i> bytes per seconds&quot; (see below for some examples). </p>
<p> A hash limit option (<code>&#8211;hashlimit-upto</code>, <code>&#8211;hashlimit-above</code>) and <code>&#8211;hashlimit-name</code> are required.</p>
<dl>
<dt><code>&#8211;hashlimit-upto</code> <i>amount</i>[<code>/second</code>|<code>/minute</code>|<code>/hour</code>|<code>/day</code>]</p>
<dd>Match if the rate is below or equal to <i>amount</i>/quantum. It is specified either as a number, with an optional time quantum suffix (the default is 3/hour), or as <i>amount</i>b/second (number of bytes per second).</p>
<dt><code>&#8211;hashlimit-above</code> <i>amount</i>[<code>/second</code>|<code>/minute</code>|<code>/hour</code>|<code>/day</code>]</p>
<dd>Match if the rate is above <i>amount</i>/quantum.</p>
<dt><code>&#8211;hashlimit-burst</code> <i>amount</i></p>
<dd>Maximum initial number of packets to match: this number gets recharged by one every time the limit specified above is not reached, up to this number; the default is 5. When byte-based rate matching is requested, this option specifies the amount of bytes that can exceed the given rate. This option should be used with caution &#8212; if the entry expires, the burst value is reset too.</p>
<dt><code>&#8211;hashlimit-mode</code> {<code>srcip</code>|<code>srcport</code>|<code>dstip</code>|<code>dstport</code>}<code>,</code>&#8230;</p>
<dd>A comma-separated list of objects to take into consideration. If no &#8211;hashlimit-mode option is given, hashlimit acts like limit, but at the expensive of doing the hash housekeeping.</p>
<dt><code>&#8211;hashlimit-srcmask</code> <i>prefix</i></p>
<dd>When &#8211;hashlimit-mode srcip is used, all source addresses encountered will be grouped according to the given prefix length and the so-created subnet will be subject to hashlimit. <i>prefix</i> must be between (inclusive) 0 and 32. Note that &#8211;hashlimit-srcmask 0 is basically doing the same thing as not specifying srcip for &#8211;hashlimit-mode, but is technically more expensive.</p>
<dt><code>&#8211;hashlimit-dstmask</code> <i>prefix</i></p>
<dd>Like &#8211;hashlimit-srcmask, but for destination addresses.</p>
<dt><code>&#8211;hashlimit-name</code> <i>foo</i></p>
<dd>The name for the /proc/net/ipt_hashlimit/foo entry.</p>
<dt><code>&#8211;hashlimit-htable-size</code> <i>buckets</i></p>
<dd>The number of buckets of the hash table</p>
<dt><code>&#8211;hashlimit-htable-max</code> <i>entries</i></p>
<dd>Maximum entries in the hash.</p>
<dt><code>&#8211;hashlimit-htable-expire</code> <i>msec</i></p>
<dd>After how many milliseconds do hash entries expire.</p>
<dt><code>&#8211;hashlimit-htable-gcinterval</code> <i>msec</i></p>
<dd>How many milliseconds between garbage collection intervals.</p>
<dt><code>&#8211;hashlimit-rate-match</code></p>
<dd>Classify the flow instead of rate-limiting it. This acts like a true/false match on whether the rate is above/below a certain number</p>
<dt><code>&#8211;hashlimit-rate-interval</code> <i>sec</i></p>
<dd>Can be used with &#8211;hashlimit-rate-match to specify the interval at which the rate should be sampled</dl>
<p> Examples:</p>
<dl>
<dt>matching on source host</p>
<dd>&quot;1000 packets per second for every host in 192.168.0.0/16&quot; =&gt; -s 192.168.0.0/16 &#8211;hashlimit-mode srcip &#8211;hashlimit-upto 1000/sec</p>
<dt>matching on source port</p>
<dd>&quot;100 packets per second for every service of 192.168.1.1&quot; =&gt; -s 192.168.1.1 &#8211;hashlimit-mode srcport &#8211;hashlimit-upto 100/sec</p>
<dt>matching on subnet</p>
<dd>&quot;10000 packets per minute for every /28 subnet (groups of 8 addresses) in 10.0.0.0/8&quot; =&gt; -s 10.0.0.0/8 &#8211;hashlimit-mask 28 &#8211;hashlimit-upto 10000/min</p>
<dt>matching bytes per second</p>
<dd>&quot;flows exceeding 512kbyte/s&quot; =&gt; &#8211;hashlimit-mode srcip,dstip,srcport,dstport &#8211;hashlimit-above 512kb/s</p>
<dt>matching bytes per second</p>
<dd>&quot;hosts that exceed 512kbyte/s, but permit up to 1Megabytes without matching&quot; &#8211;hashlimit-mode dstip &#8211;hashlimit-above 512kb/s &#8211;hashlimit-burst 1mb</dl>

<dd>Used to select whether to match the policy used for decapsulation or the policy that will be used for encapsulation. <code>in</code> is valid in the <code>PREROUTING, INPUT and FORWARD</code> chains, <code>out</code> is valid in the <code>POSTROUTING, OUTPUT and FORWARD</code> chains.</p>
<dt><code>&#8211;pol</code> {<code>none</code>|<code>ipsec</code>}</p>
<dd>Matches if the packet is subject to IPsec processing. <code>&#8211;pol none</code> cannot be combined with <code>&#8211;strict</code>.</p>
<dt><code>&#8211;strict</code></p>
<dd>Selects whether to match the exact policy or match if any rule of the policy matches the given policy.</dl>
<p> For each policy element that is to be described, one can use one or more of the following options. When <code>&#8211;strict</code> is in effect, at least one must be used per element.</p>
<dl>
<dt>[<code>!</code>] <code>&#8211;reqid</code> <i>id</i></p>
<dd>Matches the reqid of the policy rule. The reqid can be specified with <code><a href="/docs/linux/man/8-setkey/">setkey</a>(8)</code> using <code>unique:id</code> as level.</p>
<dt>[<code>!</code>] <code>&#8211;spi</code> <i>spi</i></p>
<dd>Matches the SPI of the SA.</p>
<dt>[<code>!</code>] <code>&#8211;proto</code> {<code>ah</code>|<code>esp</code>|<code>ipcomp</code>}</p>
<dd>Matches the encapsulation protocol.</p>
<dt>[<code>!</code>] <code>&#8211;mode</code> {<code>tunnel</code>|<code>transport</code>}</p>
<dd>Matches the encapsulation mode.</p>
<dt>[<code>!</code>] <code>&#8211;tunnel-src</code> <i>addr</i>[<code>/</code><i>mask</i>]</p>
<dd>Matches the source end-point address of a tunnel mode SA. Only valid with <code>&#8211;mode tunnel</code>.</p>
<dt>[<code>!</code>] <code>&#8211;tunnel-dst</code> <i>addr</i>[<code>/</code><i>mask</i>]</p>
<dd>Matches the destination end-point address of a tunnel mode SA. Only valid with <code>&#8211;mode tunnel</code>.</p>
<dt><code>&#8211;next</code></p>
<dd>Start the next element in the policy specification. Can only be used with <code>&#8211;strict</code>.</dl>
<h3>quota</h3>
<p>Implements network quotas by decrementing a byte counter with each packet. The condition matches until the byte counter reaches zero. Behavior is reversed with negation (i.e. the condition does not match until the byte counter reaches zero).</p>
<dl>
<dt>[<code>!</code>] <code>&#8211;quota</code> <i>bytes</i></p>
<dd>The quota in bytes.</dl>
<h3>rateest</h3>
<p>The rate estimator can match on estimated rates as collected by the RATEEST target. It supports matching on absolute bps/pps values, comparing two rate estimators and matching on the difference between two rate estimators. </p>
<p> For a better understanding of the available options, these are all possible combinations:</p>
<dl>
<dt>&bull;</p>
<dd><code>rateest</code> <i>operator</i> <code>rateest-bps</code></p>
<dt>&bull;</p>
<dd><code>rateest</code> <i>operator</i> <code>rateest-pps</code></p>
<dt>&bull;</p>
<dd>(<code>rateest</code> minus <code>rateest-bps1</code>) <i>operator</i> <code>rateest-bps2</code></p>
<dt>&bull;</p>
<dd>(<code>rateest</code> minus <code>rateest-pps1</code>) <i>operator</i> <code>rateest-pps2</code></p>
<dt>&bull;</p>
<dd><code>rateest1</code> <i>operator</i> <code>rateest2</code> <code>rateest-bps</code>(without rate!)</p>
<dt>&bull;</p>
<dd><code>rateest1</code> <i>operator</i> <code>rateest2</code> <code>rateest-pps</code>(without rate!)</p>
<dt>&bull;</p>
<dd>(<code>rateest1</code> minus <code>rateest-bps1</code>) <i>operator</i> (<code>rateest2</code> minus <code>rateest-bps2</code>)</p>
<dt>&bull;</p>
<dd>(<code>rateest1</code> minus <code>rateest-pps1</code>) <i>operator</i> (<code>rateest2</code> minus <code>rateest-pps2</code>)</p>
<dt><code>&#8211;rateest-delta</code></p>
<dd>For each estimator (either absolute or relative mode), calculate the difference between the estimator-determined flow rate and the static value chosen with the BPS/PPS options. If the flow rate is higher than the specified BPS/PPS, 0 will be used instead of a negative value. In other words, &quot;max(0, rateest#_rate &#8211; rateest#_bps)&quot; is used.</p>
<dt>[<code>!</code>] <code>&#8211;rateest-lt</code></p>
<dd>Match if rate is less than given rate/estimator.</p>
<dt>[<code>!</code>] <code>&#8211;rateest-gt</code></p>
<dd>Match if rate is greater than given rate/estimator.</p>
<dt>[<code>!</code>] <code>&#8211;rateest-eq</code></p>
<dd>Match if rate is equal to given rate/estimator.</dl>
<p> In the so-called &quot;absolute mode&quot;, only one rate estimator is used and compared against a static value, while in &quot;relative mode&quot;, two rate estimators are compared against another.</p>
<dl>
<dt><code>&#8211;rateest</code> <i>name</i></p>
<dd>Name of the one rate estimator for absolute mode.</p>
<dt><code>&#8211;rateest1</code> <i>name</i></p>
<dd>
<dt><code>&#8211;rateest2</code> <i>name</i></p>
<dd>The names of the two rate estimators for relative mode.</p>
<dt><code>&#8211;rateest-bps</code> [<i>value</i>]</p>
<dd>
<dt><code>&#8211;rateest-pps</code> [<i>value</i>]</p>
<dd>
<dt><code>&#8211;rateest-bps1</code> [<i>value</i>]</p>
<dd>
<dt><code>&#8211;rateest-bps2</code> [<i>value</i>]</p>
<dd>
<dt><code>&#8211;rateest-pps1</code> [<i>value</i>]</p>
<dd>
<dt><code>&#8211;rateest-pps2</code> [<i>value</i>]</p>
<dd>Compare the estimator(s) by bytes or packets per second, and compare against the chosen value. See the above bullet list for which option is to be used in which case. A unit suffix may be used &#8211; available ones are: bit, [kmgt]bit, [KMGT]ibit, Bps, [KMGT]Bps, [KMGT]iBps.</dl>
<p> Example: This is what can be used to route outgoing data connections from an FTP server over two lines based on the available bandwidth at the time the data connection was started: </p>
<p> # Estimate outgoing rates </p>
<p> iptables -t mangle -A POSTROUTING -o eth0 -j RATEEST &#8211;rateest-name eth0 &#8211;rateest-interval 250ms &#8211;rateest-ewma 0.5s </p>
<p> iptables -t mangle -A POSTROUTING -o ppp0 -j RATEEST &#8211;rateest-name ppp0 &#8211;rateest-interval 250ms &#8211;rateest-ewma 0.5s </p>
<p> # Mark based on available bandwidth </p>
<p> iptables -t mangle -A balance -m conntrack &#8211;ctstate NEW -m helper &#8211;helper ftp -m rateest &#8211;rateest-delta &#8211;rateest1 eth0 &#8211;rateest-bps1 2.5mbit &#8211;rateest-gt &#8211;rateest2 ppp0 &#8211;rateest-bps2 2mbit -j CONNMARK &#8211;set-mark 1 </p>
<p> iptables -t mangle -A balance -m conntrack &#8211;ctstate NEW -m helper &#8211;helper ftp -m rateest &#8211;rateest-delta &#8211;rateest1 ppp0 &#8211;rateest-bps1 2mbit &#8211;rateest-gt &#8211;rateest2 eth0 &#8211;rateest-bps2 2.5mbit -j CONNMARK &#8211;set-mark 2 </p>
<p> iptables -t mangle -A balance -j CONNMARK &#8211;restore-mark</p>
<h3>realm (IPv4-specific)</h3>
<p>This matches the routing realm. Routing realms are used in complex routing setups involving dynamic routing protocols like BGP.</p>
<dl>
<dt>[<code>!</code>] <code>&#8211;realm</code> <i>value</i>[<code>/</code><i>mask</i>]</p>
<dd>Matches a given realm number (and optionally mask). If not a number, value can be a named realm from /etc/iproute2/rt_realms (mask can not be used in that case). Both value and mask are four byte unsigned integers and may be specified in decimal, hex (by prefixing with &quot;0x&quot;) or octal (if a leading zero is given).</dl>
<h3>recent</h3>
<p>Allows you to dynamically create a list of IP addresses and then match against that list in a few different ways. </p>
<p> For example, you can create a &quot;badguy&quot; list out of people attempting to connect to port 139 on your firewall and then DROP all future packets from them without considering them. </p>
<p> <code>&#8211;set</code>, <code>&#8211;rcheck</code>, <code>&#8211;update</code> and <code>&#8211;remove</code> are mutually exclusive.</p>
<dl>
<dt><code>&#8211;name</code> <i>name</i></p>
<dd>Specify the list to use for the commands. If no name is given then <code>DEFAULT</code> will be used.</p>
<dt>[<code>!</code>] <code>&#8211;set</code></p>
<dd>This will add the source address of the packet to the list. If the source address is already in the list, this will update the existing entry. This will always return success (or failure if <code>!</code> is passed in).</p>
<dt><code>&#8211;rsource</code></p>
<dd>Match/save the source address of each packet in the recent list table. This is the default.</p>
<dt><code>&#8211;rdest</code></p>
<dd>Match/save the destination address of each packet in the recent list table.</p>
<dt><code>&#8211;mask</code> <i>netmask</i></p>
<dd>Netmask that will be applied to this recent list.</p>
<dt>[<code>!</code>] <code>&#8211;rcheck</code></p>
<dd>Check if the source address of the packet is currently in the list.</p>
<dt>[<code>!</code>] <code>&#8211;update</code></p>
<dd>Like <code>&#8211;rcheck</code>, except it will update the &quot;last seen&quot; timestamp if it matches.</p>
<dt>[<code>!</code>] <code>&#8211;remove</code></p>
<dd>Check if the source address of the packet is currently in the list and if so that address will be removed from the list and the rule will return true. If the address is not found, false is returned.</p>
<dt><code>&#8211;seconds</code> <i>seconds</i></p>
<dd>This option must be used in conjunction with one of <code>&#8211;rcheck</code> or <code>&#8211;update</code>. When used, this will narrow the match to only happen when the address is in the list and was seen within the last given number of seconds.</p>
<dt><code>&#8211;reap</code></p>
<dd>This option can only be used in conjunction with <code>&#8211;seconds</code>. When used, this will cause entries older than the last given number of seconds to be purged.</p>
<dt><code>&#8211;hitcount</code> <i>hits</i></p>
<dd>This option must be used in conjunction with one of <code>&#8211;rcheck</code> or <code>&#8211;update</code>. When used, this will narrow the match to only happen when the address is in the list and packets had been received greater than or equal to the given value. This option may be used along with <code>&#8211;seconds</code> to create an even narrower match requiring a certain number of hits within a specific time frame. The maximum value for the hitcount parameter is given by the &quot;ip_pkt_list_tot&quot; parameter of the xt_recent kernel module. Exceeding this value on the command line will cause the rule to be rejected.</p>
<dt><code>&#8211;rttl</code></p>
<dd>This option may only be used in conjunction with one of <code>&#8211;rcheck</code> or <code>&#8211;update</code>. When used, this will narrow the match to only happen when the address is in the list and the TTL of the current packet matches that of the packet which hit the <code>&#8211;set</code> rule. This may be useful if you have problems with people faking their source address in order to DoS you via this module by disallowing others access to your site by sending bogus packets to you.</dl>
<p> Examples:</p>
<dl>
<dd>iptables -A FORWARD -m recent &#8211;name badguy &#8211;rcheck &#8211;seconds 60 -j DROP</p>
<dd>iptables -A FORWARD -p tcp -i eth0 &#8211;dport 139 -m recent &#8211;name badguy &#8211;set -j DROP</dl>
<p> <code>/proc/net/xt_recent/*</code> are the current lists of addresses and information about each entry of each list. </p>
<p> Each file in <code>/proc/net/xt_recent/</code> can be read from to see the current list or written two using the following commands to modify the list:</p>
<dl>
<dt><code>echo +</code><i>addr</i><code> &gt;/proc/net/xt_recent/DEFAULT</code></p>
<dd>to add <i>addr</i> to the DEFAULT list</p>
<dt><code>echo &#8211;</code><i>addr</i><code> &gt;/proc/net/xt_recent/DEFAULT</code></p>
<dd>to remove <i>addr</i> from the DEFAULT list</p>
<dt><code>echo / &gt;/proc/net/xt_recent/DEFAULT</code></p>
<dd>to flush the DEFAULT list (remove all entries).</dl>
<p> The module itself accepts parameters, defaults shown:</p>
<dl>
<dt><code>ip_list_tot</code>=<i>100</i></p>
<dd>Number of addresses remembered per table.</p>
<dt><code>ip_pkt_list_tot</code>=<i>20</i></p>
<dd>Number of packets per address remembered.</p>
<dt><code>ip_list_hash_size</code>=<i>0</i></p>
<dd>Hash table size. 0 means to calculate it based on ip_list_tot, default: 512.</p>
<dt><code>ip_list_perms</code>=<i>0644</i></p>
<dd>Permissions for /proc/net/xt_recent/* files.</p>
<dt><code>ip_list_uid</code>=<i>0</i></p>
<dd>Numerical UID for ownership of /proc/net/xt_recent/* files.</p>
<dt><code>ip_list_gid</code>=<i>0</i></p>
<dd>Numerical GID for ownership of /proc/net/xt_recent/* files.</dl>
<h3>rpfilter</h3>
<p>Performs a reverse path filter test on a packet. If a reply to the packet would be sent via the same interface that the packet arrived on, the packet will match. Note that, unlike the in-kernel rp_filter, packets protected by IPSec are not treated specially. Combine this match with the policy match if you want this. Also, packets arriving via the loopback interface are always permitted. This match can only be used in the PREROUTING chain of the raw or mangle table.</p>
<dl>
<dt><code>&#8211;loose</code></p>
<dd>Used to specify that the reverse path filter test should match even if the selected output device is not the expected one.</p>
<dt><code>&#8211;validmark</code></p>
<dd>Also use the packets&#8217; nfmark value when performing the reverse path route lookup.</p>
<dt><code>&#8211;accept-local</code></p>
<dd>This will permit packets arriving from the network with a source address that is also assigned to the local machine.</p>
<dt><code>&#8211;invert</code></p>
<dd>This will invert the sense of the match. Instead of matching packets that passed the reverse path filter test, match those that have failed it.</dl>
<p> Example to log and drop packets failing the reverse path filter test: </p>
<p> iptables -t raw -N RPFILTER </p>
<p> iptables -t raw -A RPFILTER -m rpfilter -j RETURN </p>
<p> iptables -t raw -A RPFILTER -m limit &#8211;limit 10/minute -j NFLOG &#8211;nflog-prefix &quot;rpfilter drop&quot; </p>
<p> iptables -t raw -A RPFILTER -j DROP </p>
<p> iptables -t raw -A PREROUTING -j RPFILTER </p>
<p> Example to drop failed packets, without logging: </p>
<p> iptables -t raw -A RPFILTER -m rpfilter &#8211;invert -j DROP</p>

<dt>[<code>!</code>] <code>&#8211;rt-segsleft</code> <i>num</i>[<code>:</code><i>num</i>]</p>
<dd>Match the `segments left&#8217; field (range).</p>
<dt>[<code>!</code>] <code>&#8211;rt-len</code> <i>length</i></p>
<dd>Match the length of this header.</p>
<dt><code>&#8211;rt-0-res</code></p>
<dd>Match the reserved field, too (type=0)</p>
<dt><code>&#8211;rt-0-addrs</code> <i>addr</i>[<code>,</code><i>addr</i>&#8230;]</p>
<dd>Match type=0 addresses (list).</p>
<dt><code>&#8211;rt-0-not-strict</code></p>

<h3>sctp</h3>

<dl>
<dt>[<code>!</code>] <code>&#8211;source-port</code>,<code>&#8211;sport</code> <i>port</i>[<code>:</code><i>port</i>]</p>
<dd>
<dt>[<code>!</code>] <code>&#8211;destination-port</code>,<code>&#8211;dport</code> <i>port</i>[<code>:</code><i>port</i>]</p>
<dd>
<dt>[<code>!</code>] <code>&#8211;chunk-types</code> {<code>all</code>|<code>any</code>|<code>only</code>} <i>chunktype</i>[<code>:</code><i>flags</i>] [&#8230;]</p>

<h3>set</h3>
<p>This module matches IP sets which can be defined by <a href="/docs/linux/man/8-ipset/">ipset</a>(8).</p>
<dl>
<dt>[<code>!</code>] <code>&#8211;match-set</code> <i>setname</i> <i>flag</i>[<code>,</code><i>flag</i>]&#8230;</p>
<dd>where flags are the comma separated list of <code>src</code> and/or <code>dst</code> specifications and there can be no more than six of them. Hence the command</p>
<dd>&nbsp;iptables -A FORWARD -m set &#8211;match-set test src,dst</p>
<dd>will match packets, for which (if the set type is ipportmap) the source address and destination port pair can be found in the specified set. If the set type of the specified set is single dimension (for example ipmap), then the command will match packets for which the source address can be found in the specified set.</p>
<dt><code>&#8211;return-nomatch</code></p>
<dd>If the <code>&#8211;return-nomatch</code> option is specified and the set type supports the <code>nomatch</code> flag, then the matching is reversed: a match with an element flagged with <code>nomatch</code> returns <code>true</code>, while a match with a plain element returns <code>false</code>.</p>
<dt><code>!</code> <code>&#8211;update-counters</code></p>
<dd>If the <code>&#8211;update-counters</code> flag is negated, then the packet and byte counters of the matching element in the set won&#8217;t be updated. Default the packet and byte counters are updated.</p>
<dt><code>!</code> <code>&#8211;update-subcounters</code></p>
<dd>If the <code>&#8211;update-subcounters</code> flag is negated, then the packet and byte counters of the matching element in the member set of a list type of set won&#8217;t be updated. Default the packet and byte counters are updated.</p>
<dt>[<code>!</code>] <code>&#8211;packets-eq</code> <i>value</i></p>
<dd>If the packet is matched an element in the set, match only if the packet counter of the element matches the given value too.</p>
<dt><code>&#8211;packets-lt</code> <i>value</i></p>
<dd>If the packet is matched an element in the set, match only if the packet counter of the element is less than the given value as well.</p>
<dt><code>&#8211;packets-gt</code> <i>value</i></p>
<dd>If the packet is matched an element in the set, match only if the packet counter of the element is greater than the given value as well.</p>
<dt>[<code>!</code>] <code>&#8211;bytes-eq</code> <i>value</i></p>
<dd>If the packet is matched an element in the set, match only if the byte counter of the element matches the given value too.</p>
<dt><code>&#8211;bytes-lt</code> <i>value</i></p>
<dd>If the packet is matched an element in the set, match only if the byte counter of the element is less than the given value as well.</p>
<dt><code>&#8211;bytes-gt</code> <i>value</i></p>
<dd>If the packet is matched an element in the set, match only if the byte counter of the element is greater than the given value as well.</dl>
<p> The packet and byte counters related options and flags are ignored when the set was defined without counter support. </p>
<p> The option <code>&#8211;match-set</code> can be replaced by <code>&#8211;set</code> if that does not clash with an option of other extensions. </p>
<p> Use of -m set requires that ipset kernel support is provided, which, for standard kernels, is the case since Linux 2.6.39.</p>
<h3>socket</h3>
<p>This matches if an open TCP/UDP socket can be found by doing a socket lookup on the packet. It matches if there is an established or non-zero bound listening socket (possibly with a non-local address). The lookup is performed using the <code>packet</code> tuple of TCP/UDP packets, or the original TCP/UDP header <code>embedded</code> in an ICMP/ICPMv6 error packet.</p>
<dl>
<dt><code>&#8211;transparent</code></p>
<dd>Ignore non-transparent sockets.</p>
<dt><code>&#8211;nowildcard</code></p>
<dd>Do not ignore sockets bound to &#8216;any&#8217; address. The socket match won&#8217;t accept zero-bound listeners by default, since then local services could intercept traffic that would otherwise be forwarded. This option therefore has security implications when used to match traffic being forwarded to redirect such packets to local machine with policy routing. When using the socket match to implement fully transparent proxies bound to non-local addresses it is recommended to use the &#8211;transparent option instead.</dl>
<p> Example (assuming packets with mark 1 are delivered locally):</p>
<dl>
<dd>-t mangle -A PREROUTING -m socket &#8211;transparent -j MARK &#8211;set-mark 1</p>
<dt><code>&#8211;restore-skmark</code></p>
<dd>Set the packet mark to the matching socket&#8217;s mark. Can be combined with the <code>&#8211;transparent</code> and <code>&#8211;nowildcard</code> options to restrict the sockets to be matched when restoring the packet mark.</dl>
<p> Example: An application opens 2 transparent (<code>IP_TRANSPARENT</code>) sockets and sets a mark on them with <code>SO_MARK</code> socket option. We can filter matching packets:</p>
<dl>
<dd>-t mangle -I PREROUTING -m socket &#8211;transparent &#8211;restore-skmark -j action</p>
<dd>-t mangle -A action -m mark &#8211;mark 10 -j action2</p>
<dd>-t mangle -A action -m mark &#8211;mark 11 -j action3</dl>
<h3>state</h3>
<p>The &quot;state&quot; extension is a subset of the &quot;conntrack&quot; module. &quot;state&quot; allows access to the connection tracking state for this packet.</p>
<dl>
<dt>[<code>!</code>] <code>&#8211;state</code> <i>state</i></p>
<dd>Where state is a comma separated list of the connection states to match. Only a subset of the states unterstood by &quot;conntrack&quot; are recognized: <code>INVALID</code>, <code>ESTABLISHED</code>, <code>NEW</code>, <code>RELATED</code> or <code>UNTRACKED</code>. For their description, see the &quot;conntrack&quot; heading in this manpage.</dl>
<h3>statistic</h3>
<p>This module matches packets based on some statistic condition. It supports two distinct modes settable with the <code>&#8211;mode</code> option. </p>
<p> Supported options:</p>
<dl>
<dt><code>&#8211;mode</code> <i>mode</i></p>
<dd>Set the matching mode of the matching rule, supported modes are <code>random</code> and <code>nth. </code></p>
<dt>[<code>!</code>] <code>&#8211;probability</code> <i>p</i></p>
<dd>Set the probability for a packet to be randomly matched. It only works with the <code>random</code> mode. <i>p</i> must be within 0.0 and 1.0. The supported granularity is in 1/2147483648th increments.</p>
<dt>[<code>!</code>] <code>&#8211;every</code> <i>n</i></p>
<dd>Match one packet every nth packet. It works only with the <code>nth</code> mode (see also the <code>&#8211;packet</code> option).</p>
<dt><code>&#8211;packet</code> <i>p</i></p>
<dd>Set the initial counter value (0 &lt;= p &lt;= n-1, default 0) for the <code>nth </code> mode.</dl>
<h3>string</h3>
<p>This module matches a given string by using some pattern matching strategy. It requires a linux kernel &gt;= 2.6.14.</p>
<dl>
<dt><code>&#8211;algo</code> {<code>bm</code>|<code>kmp</code>}</p>
<dd>Select the pattern matching strategy. (bm = Boyer-Moore, kmp = Knuth-Pratt-Morris)</p>
<dt><code>&#8211;from</code> <i>offset</i></p>
<dd>Set the offset from which it starts looking for any matching. If not passed, default is 0.</p>
<dt><code>&#8211;to</code> <i>offset</i></p>
<dd>Set the offset up to which should be scanned. That is, byte <i>offset</i>-1 (counting from 0) is the last one that is scanned. If not passed, default is the packet size.</p>
<dt>[<code>!</code>] <code>&#8211;string</code> <i>pattern</i></p>
<dd>Matches the given pattern.</p>
<dt>[<code>!</code>] <code>&#8211;hex-string</code> <i>pattern</i></p>
<dd>Matches the given pattern in hex notation.</p>
<dt><code>&#8211;icase</code></p>
<dd>Ignore case when searching.</p>
<dt>Examples:</p>
<dd>
<dd># The string pattern can be used for simple text characters.<br />
 iptables -A INPUT -p tcp &#8211;dport 80 -m string &#8211;algo bm &#8211;string &#8216;GET /index.html&#8217; -j LOG</p>
<dd># The hex string pattern can be used for non-printable characters, like |0D 0A| or |0D0A|.<br />
 iptables -p udp &#8211;dport 53 -m string &#8211;algo bm &#8211;from 40 &#8211;to 57 &#8211;hex-string &#8216;|03|www|09|netfilter|03|org|00|&#8217;</dl>
<h3>tcp</h3>
<p>These extensions can be used if `&#8211;protocol tcp&#8217; is specified. It provides the following options:</p>
<dl>
<dt>[<code>!</code>] <code>&#8211;source-port</code>,<code>&#8211;sport</code> <i>port</i>[<code>:</code><i>port</i>]</p>
<dd>Source port or port range specification. This can either be a service name or a port number. An inclusive range can also be specified, using the format <i>first</i><code>:</code><i>last</i>. If the first port is omitted, &quot;0&quot; is assumed; if the last is omitted, &quot;65535&quot; is assumed. The flag <code>&#8211;sport</code> is a convenient alias for this option.</p>
<dt>[<code>!</code>] <code>&#8211;destination-port</code>,<code>&#8211;dport</code> <i>port</i>[<code>:</code><i>port</i>]</p>
<dd>Destination port or port range specification. The flag <code>&#8211;dport</code> is a convenient alias for this option.</p>
<dt>[<code>!</code>] <code>&#8211;tcp-flags</code> <i>mask</i> <i>comp</i></p>
<dd>Match when the TCP flags are as specified. The first argument <i>mask</i> is the flags which we should examine, written as a comma-separated list, and the second argument <i>comp</i> is a comma-separated list of flags which must be set. Flags are: <code>SYN ACK FIN RST URG PSH ALL NONE</code>. Hence the command </p>
<pre> iptables -A FORWARD -p tcp --tcp-flags SYN,ACK,FIN,RST SYN</pre>
<p>will only match packets with the SYN flag set, and the ACK, FIN and RST flags unset.</p>
<dt>[<code>!</code>] <code>&#8211;syn</code></p>
<dd>Only match TCP packets with the SYN bit set and the ACK,RST and FIN bits cleared. Such packets are used to request TCP connection initiation; for example, blocking such packets coming in an interface will prevent incoming TCP connections, but outgoing TCP connections will be unaffected. It is equivalent to <code>&#8211;tcp-flags SYN,RST,ACK,FIN SYN</code>. If the &quot;!&quot; flag precedes the &quot;&#8211;syn&quot;, the sense of the option is inverted.</p>
<dt>[<code>!</code>] <code>&#8211;tcp-option</code> <i>number</i></p>
<dd>Match if TCP option set.</dl>
<h3>tcpmss</h3>
<p>This matches the TCP MSS (maximum segment size) field of the TCP header. You can only use this on TCP SYN or SYN/ACK packets, since the MSS is only negotiated during the TCP handshake at connection startup time.</p>
<dl>
<dt>[<code>!</code>] <code>&#8211;mss</code> <i>value</i>[<code>:</code><i>value</i>]</p>
<dd>Match a given TCP MSS value or range. If a range is given, the second <i>value</i> must be greater than or equal to the first <i>value</i>.</dl>
<h3>time</h3>
<p>This matches if the packet arrival time/date is within a given range. All options are optional, but are ANDed when specified. All times are interpreted as UTC by default.</p>
<dl>
<dt><code>&#8211;datestart</code> <i>YYYY</i>[<code>&#8211;</code><i>MM</i>[<code>&#8211;</code><i>DD</i>[<code>T</code><i>hh</i>[<code>:</code><i>mm</i>[<code>:</code><i>ss</i>]]]]]</p>
<dd>
<dt><code>&#8211;datestop</code> <i>YYYY</i>[<code>&#8211;</code><i>MM</i>[<code>&#8211;</code><i>DD</i>[<code>T</code><i>hh</i>[<code>:</code><i>mm</i>[<code>:</code><i>ss</i>]]]]]</p>
<dd>Only match during the given time, which must be in ISO 8601 &quot;T&quot; notation. The possible time range is 1970-01-01T00:00:00 to 2038-01-19T04:17:07.</p>
<dd>If &#8211;datestart or &#8211;datestop are not specified, it will default to 1970-01-01 and 2038-01-19, respectively.</p>
<dt><code>&#8211;timestart</code> <i>hh</i><code>:</code><i>mm</i>[<code>:</code><i>ss</i>]</p>
<dd>
<dt><code>&#8211;timestop</code> <i>hh</i><code>:</code><i>mm</i>[<code>:</code><i>ss</i>]</p>
<dd>Only match during the given daytime. The possible time range is 00:00:00 to 23:59:59. Leading zeroes are allowed (e.g. &quot;06:03&quot;) and correctly interpreted as base-10.</p>
<dt>[<code>!</code>] <code>&#8211;monthdays</code> <i>day</i>[<code>,</code><i>day</i>&#8230;]</p>
<dd>Only match on the given days of the month. Possible values are <code>1</code> to <code>31</code>. Note that specifying <code>31</code> will of course not match on months which do not have a 31st day; the same goes for 28- or 29-day February.</p>
<dt>[<code>!</code>] <code>&#8211;weekdays</code> <i>day</i>[<code>,</code><i>day</i>&#8230;]</p>
<dd>Only match on the given weekdays. Possible values are <code>Mon</code>, <code>Tue</code>, <code>Wed</code>, <code>Thu</code>, <code>Fri</code>, <code>Sat</code>, <code>Sun</code>, or values from <code>1</code> to <code>7</code>, respectively. You may also use two-character variants (<code>Mo</code>, <code>Tu</code>, etc.).</p>
<dt><code>&#8211;contiguous</code></p>
<dd>When <code>&#8211;timestop</code> is smaller than <code>&#8211;timestart</code> value, match this as a single time period instead distinct intervals. See EXAMPLES.</p>
<dt><code>&#8211;kerneltz</code></p>
<dd>Use the kernel timezone instead of UTC to determine whether a packet meets the time regulations.</dl>
<p> About kernel timezones: Linux keeps the system time in UTC, and always does so. On boot, system time is initialized from a referential time source. Where this time source has no timezone information, such as the x86 CMOS RTC, UTC will be assumed. If the time source is however not in UTC, userspace should provide the correct system time and timezone to the kernel once it has the information. </p>
<p> Local time is a feature on top of the (timezone independent) system time. Each process has its own idea of local time, specified via the TZ environment variable. The kernel also has its own timezone offset variable. The TZ userspace environment variable specifies how the UTC-based system time is displayed, e.g. when you run <a href="/docs/linux/man/1-date/">date</a>(1), or what you see on your desktop clock. The TZ string may resolve to different offsets at different dates, which is what enables the automatic time-jumping in userspace. when DST changes. The kernel&#8217;s timezone offset variable is used when it has to convert between non-UTC sources, such as FAT filesystems, to UTC (since the latter is what the rest of the system uses). </p>
<p> The caveat with the kernel timezone is that Linux distributions may ignore to set the kernel timezone, and instead only set the system time. Even if a particular distribution does set the timezone at boot, it is usually does not keep the kernel timezone offset &#8211; which is what changes on DST &#8211; up to date. ntpd will not touch the kernel timezone, so running it will not resolve the issue. As such, one may encounter a timezone that is always +0000, or one that is wrong half of the time of the year. As such, <code>using &#8211;kerneltz is highly discouraged.</code> </p>
<p> EXAMPLES. To match on weekends, use:</p>
<dl>
<dd>-m time &#8211;weekdays Sa,Su</dl>
<p> Or, to match (once) on a national holiday block:</p>
<dl>
<dd>-m time &#8211;datestart 2007-12-24 &#8211;datestop 2007-12-27</dl>
<p> Since the stop time is actually inclusive, you would need the following stop time to not match the first second of the new day:</p>
<dl>
<dd>-m time &#8211;datestart 2007-01-01T17:00 &#8211;datestop 2007-01-01T23:59:59</dl>
<p> During lunch hour:</p>
<dl>
<dd>-m time &#8211;timestart 12:30 &#8211;timestop 13:30</dl>
<p> The fourth Friday in the month:</p>
<dl>
<dd>-m time &#8211;weekdays Fr &#8211;monthdays 22,23,24,25,26,27,28</dl>
<p> (Note that this exploits a certain mathematical property. It is not possible to say &quot;fourth Thursday OR fourth Friday&quot; in one rule. It is possible with multiple rules, though.) </p>
<p> Matching across days might not do what is expected. For instance,</p>
<dl>
<dd>-m time &#8211;weekdays Mo &#8211;timestart 23:00 &#8211;timestop 01:00 Will match Monday, for one hour from midnight to 1 a.m., and then again for another hour from 23:00 onwards. If this is unwanted, e.g. if you would like &#8216;match for two hours from Montay 23:00 onwards&#8217; you need to also specify the &#8211;contiguous option in the example above.</dl>

<h3>u32</h3>
<p>U32 tests whether quantities of up to 4 bytes extracted from a packet have specified values. The specification of what to extract is general enough to find data at given offsets from tcp headers or payloads.</p>
<dl>
<dt>[<code>!</code>] <code>&#8211;u32</code> <i>tests</i></p>
<dd>The argument amounts to a program in a small language described below.</p>
<dd>tests := location &quot;=&quot; value | tests &quot;&amp;&amp;&quot; location &quot;=&quot; value</p>
<dd>value := range | value &quot;,&quot; range</p>
<dd>range := number | number &quot;:&quot; number</dl>
<p> a single number, <i>n</i>, is interpreted the same as <i>n:n</i>. <i>n:m</i> is interpreted as the range of numbers <code>&gt;=n</code> and <code>&lt;=m</code>.</p>
<dl>
<dd>location := number | location operator number</p>
<dd>operator := &quot;&amp;&quot; | &quot;&lt;&lt;&quot; | &quot;&gt;&gt;&quot; | &quot;@&quot;</dl>
<p> The operators <code>&amp;</code>, <code>&lt;&lt;</code>, <code>&gt;&gt;</code> and <code>&amp;&amp;</code> mean the same as in C. The <code>=</code> is really a set membership operator and the value syntax describes a set. The <code>@</code> operator is what allows moving to the next header and is described further below. </p>
<p> There are currently some artificial implementation limits on the size of the tests:</p>
<dl>
<dt> *</p>
<dd>no more than 10 of &quot;<code>=</code>&quot; (and 9 &quot;<code>&amp;&amp;</code>&quot;s) in the u32 argument</p>
<dt> *</p>
<dd>no more than 10 ranges (and 9 commas) per value</p>
<dt> *</p>
<dd>no more than 10 numbers (and 9 operators) per location</dl>
<p> To describe the meaning of location, imagine the following machine that interprets it. There are three registers:</p>
<dl>
<dd>A is of type <code>char *</code>, initially the address of the IP header</p>
<dd>B and C are unsigned 32 bit integers, initially zero</dl>
<p> The instructions are:</p>
<dl>
<dt><code>number</code></p>
<dd>B = number;</p>
<dd>C = (*(A+B)&lt;&lt;24) + (*(A+B+1)&lt;&lt;16) + (*(A+B+2)&lt;&lt;8) + *(A+B+3)</p>
<dt><code>&amp;number</code></p>
<dd>C = C &amp; number</p>
<dt><code>&lt;&lt; number</code></p>
<dd>C = C &lt;&lt; number</p>
<dt><code>&gt;&gt; number</code></p>
<dd>C = C &gt;&gt; number</p>
<dt><code>@number</code></p>
<dd>A = A + C; then do the instruction number</dl>
<p> Any access of memory outside [skb-&gt;data,skb-&gt;end] causes the match to fail. Otherwise the result of the computation is the final value of C. </p>
<p> Whitespace is allowed but not required in the tests. However, the characters that do occur there are likely to require shell quoting, so it is a good idea to enclose the arguments in quotes. </p>
<p> Example:</p>
<dl>
<dd>match IP packets with total length &gt;= 256</p>
<dd>The IP header contains a total length field in bytes 2-3.</p>
<dd>&#8211;u32 &quot;<code>0 &amp; 0xFFFF = 0x100:0xFFFF</code>&quot;</p>
<dd>read bytes 0-3</p>
<dd>AND that with 0xFFFF (giving bytes 2-3), and test whether that is in the range [0x100:0xFFFF]</dl>
<p> Example: (more realistic, hence more complicated)</p>
<dl>
<dd>match ICMP packets with icmp type 0</p>
<dd>First test that it is an ICMP packet, true iff byte 9 (protocol) = 1</p>
<dd>&#8211;u32 &quot;<code>6 &amp; 0xFF = 1 &amp;&amp;</code> &#8230;</p>
<dd>read bytes 6-9, use <code>&amp;</code> to throw away bytes 6-8 and compare the result to 1. Next test that it is not a fragment. (If so, it might be part of such a packet but we cannot always tell.) N.B.: This test is generally needed if you want to match anything beyond the IP header. The last 6 bits of byte 6 and all of byte 7 are 0 iff this is a complete packet (not a fragment). Alternatively, you can allow first fragments by only testing the last 5 bits of byte 6.</p>
<dd>&nbsp;&#8230;&nbsp;<code>4&nbsp;&amp;&nbsp;0x3FFF&nbsp;=&nbsp;0&nbsp;&amp;&amp;</code>&nbsp;&#8230;</p>
<dd>Last test: the first byte past the IP header (the type) is 0. This is where we have to use the @syntax. The length of the IP header (IHL) in 32 bit words is stored in the right half of byte 0 of the IP header itself.</p>
<dd>&nbsp;&#8230;&nbsp;<code>0&nbsp;&gt;&gt;&nbsp;22&nbsp;&amp;&nbsp;0x3C&nbsp;@&nbsp;0&nbsp;&gt;&gt;&nbsp;24&nbsp;=&nbsp;0</code>&quot;</p>
<dd>The first 0 means read bytes 0-3, <code>&gt;&gt;22</code> means shift that 22 bits to the right. Shifting 24 bits would give the first byte, so only 22 bits is four times that plus a few more bits. <code>&amp;3C</code> then eliminates the two extra bits on the right and the first four bits of the first byte. For instance, if IHL=5, then the IP header is 20 (4 x 5) bytes long. In this case, bytes 0-1 are (in binary) xxxx0101 yyzzzzzz, <code>&gt;&gt;22</code> gives the 10 bit value xxxx0101yy and <code>&amp;3C</code> gives 010100. <code>@</code> means to use this number as a new offset into the packet, and read four bytes starting from there. This is the first 4 bytes of the ICMP payload, of which byte 0 is the ICMP type. Therefore, we simply shift the value 24 to the right to throw out all but the first byte and compare the result with 0.</dl>
<p> Example:</p>
<dl>
<dd>TCP payload bytes 8-12 is any of 1, 2, 5 or 8</p>
<dd>First we test that the packet is a tcp packet (similar to ICMP).</p>
<dd>&#8211;u32 &quot;<code>6 &amp; 0xFF = 6 &amp;&amp;</code> &#8230;</p>
<dd>Next, test that it is not a fragment (same as above).</p>
<dd>&nbsp;&#8230;&nbsp;<code>0&nbsp;&gt;&gt;&nbsp;22&nbsp;&amp;&nbsp;0x3C&nbsp;@&nbsp;12&nbsp;&gt;&gt;&nbsp;26&nbsp;&amp;&nbsp;0x3C&nbsp;@&nbsp;8&nbsp;=&nbsp;1,2,5,8</code>&quot;</p>
<dd><code>0&gt;&gt;22&amp;3C</code> as above computes the number of bytes in the IP header. <code>@</code> makes this the new offset into the packet, which is the start of the TCP header. The length of the TCP header (again in 32 bit words) is the left half of byte 12 of the TCP header. The <code>12&gt;&gt;26&amp;3C</code> computes this length in bytes (similar to the IP header before). &quot;@&quot; makes this the new offset, which is the start of the TCP payload. Finally, 8 reads bytes 8-12 of the payload and <code>=</code> checks whether the result is any of 1, 2, 5 or 8.</dl>

<h3>Connmark</h3>
<p>This module sets the netfilter mark value associated with a connection. The mark is 32 bits wide.</p>
<dl>
<dt><code>&#8211;set-xmark</code> <i>value</i>[<code>/</code><i>mask</i>]</p>
<dd>Zero out the bits given by <i>mask</i> and XOR <i>value</i> into the ctmark.</p>
<dt><code>&#8211;save-mark</code> [<code>&#8211;nfmask</code> <i>nfmask</i>] [<code>&#8211;ctmask</code> <i>ctmask</i>]</p>
<dd>Copy the packet mark (nfmark) to the connection mark (ctmark) using the given masks. The new nfmark value is determined as follows:</p>
<dd>ctmark = (ctmark &amp; ~ctmask) ^ (nfmark &amp; nfmask)</p>
<dd>i.e. <i>ctmask</i> defines what bits to clear and <i>nfmask</i> what bits of the nfmark to XOR into the ctmark. <i>ctmask</i> and <i>nfmask</i> default to 0xFFFFFFFF.</p>
<dt><code>&#8211;restore-mark</code> [<code>&#8211;nfmask</code> <i>nfmask</i>] [<code>&#8211;ctmask</code> <i>ctmask</i>]</p>
<dd>Copy the connection mark (ctmark) to the packet mark (nfmark) using the given masks. The new ctmark value is determined as follows:</p>
<dd>nfmark = (nfmark &amp; ~<i>nfmask</i>) ^ (ctmark &amp; <i>ctmask</i>);</p>
<dd>i.e. <i>nfmask</i> defines what bits to clear and <i>ctmask</i> what bits of the ctmark to XOR into the nfmark. <i>ctmask</i> and <i>nfmask</i> default to 0xFFFFFFFF.</p>
<dd><code>&#8211;restore-mark</code> is only valid in the <code>mangle</code> table.</dl>
<p> The following mnemonics are available for <code>&#8211;set-xmark</code>:</p>
<dl>
<dt><code>&#8211;and-mark</code> <i>bits</i></p>
<dd>Binary AND the ctmark with <i>bits</i>. (Mnemonic for <code>&#8211;set-xmark 0/</code><i>invbits</i>, where <i>invbits</i> is the binary negation of <i>bits</i>.)</p>
<dt><code>&#8211;or-mark</code> <i>bits</i></p>
<dd>Binary OR the ctmark with <i>bits</i>. (Mnemonic for <code>&#8211;set-xmark</code> <i>bits</i><code>/</code><i>bits</i>.)</p>
<dt><code>&#8211;xor-mark</code> <i>bits</i></p>
<dd>Binary XOR the ctmark with <i>bits</i>. (Mnemonic for <code>&#8211;set-xmark</code> <i>bits</i><code>/0</code>.)</p>
<dt><code>&#8211;set-mark</code> <i>value</i>[<code>/</code><i>mask</i>]</p>
<dd>Set the connection mark. If a mask is specified then only those bits set in the mask are modified.</p>
<dt><code>&#8211;save-mark</code> [<code>&#8211;mask</code> <i>mask</i>]</p>
<dd>Copy the nfmark to the ctmark. If a mask is specified, only those bits are copied.</p>
<dt><code>&#8211;restore-mark</code> [<code>&#8211;mask</code> <i>mask</i>]</p>
<dd>Copy the ctmark to the nfmark. If a mask is specified, only those bits are copied. This is only valid in the <code>mangle</code> table.</dl>
<h3>Connsecmark</h3>
<p>This module copies security markings from packets to connections (if unlabeled), and from connections back to packets (also only if unlabeled). Typically used in conjunction with SECMARK, it is valid in the <code>security</code> table (for backwards compatibility with older kernels, it is also valid in the <code>mangle</code> table).</p>
<dl>
<dt><code>&#8211;save</code></p>
<dd>If the packet has a security marking, copy it to the connection if the connection is not marked.</p>
<dt><code>&#8211;restore</code></p>
<dd>If the packet does not have a security marking, and the connection does, copy the security marking from the connection to the packet. </p>
</dl>
<h3>Ct</h3>
<p>The CT target sets parameters for a packet or its associated connection. The target attaches a &quot;template&quot; connection tracking entry to the packet, which is then used by the conntrack core when initializing a new ct entry. This target is thus only valid in the &quot;raw&quot; table.</p>
<dl>
<dt><code>&#8211;notrack</code></p>
<dd>Disables connection tracking for this packet.</p>
<dt><code>&#8211;helper</code> <i>name</i></p>
<dd>Use the helper identified by <i>name</i> for the connection. This is more flexible than loading the conntrack helper modules with preset ports.</p>
<dt><code>&#8211;ctevents</code> <i>event</i>[<code>,</code>&#8230;]</p>
<dd>Only generate the specified conntrack events for this connection. Possible event types are: <code>new</code>, <code>related</code>, <code>destroy</code>, <code>reply</code>, <code>assured</code>, <code>protoinfo</code>, <code>helper</code>, <code>mark</code> (this refers to the ctmark, not nfmark), <code>natseqinfo</code>, <code>secmark</code> (ctsecmark).</p>
<dt><code>&#8211;expevents</code> <i>event</i>[<code>,</code>&#8230;]</p>
<dd>Only generate the specified expectation events for this connection. Possible event types are: <code>new</code>.</p>
<dt><code>&#8211;zone-orig</code> {<i>id</i>|<code>mark</code>}</p>
<dd>For traffic coming from ORIGINAL direction, assign this packet to zone <i>id</i> and only have lookups done in that zone. If <code>mark</code> is used instead of <i>id</i>, the zone is derived from the packet nfmark.</p>
<dt><code>&#8211;zone-reply</code> {<i>id</i>|<code>mark</code>}</p>
<dd>For traffic coming from REPLY direction, assign this packet to zone <i>id</i> and only have lookups done in that zone. If <code>mark</code> is used instead of <i>id</i>, the zone is derived from the packet nfmark.</p>
<dt><code>&#8211;zone</code> {<i>id</i>|<code>mark</code>}</p>
<dd>Assign this packet to zone <i>id</i> and only have lookups done in that zone. If <code>mark</code> is used instead of <i>id</i>, the zone is derived from the packet nfmark. By default, packets have zone 0. This option applies to both directions.</p>
<dt><code>&#8211;timeout</code> <i>name</i></p>
<dd>Use the timeout policy identified by <i>name</i> for the connection. This is provides more flexible timeout policy definition than global timeout values available at /proc/sys/net/netfilter/nf_conntrack_*_timeout_*.</dl>
<h3>Dnat</h3>
<p>This target is only valid in the <code>nat</code> table, in the <code>PREROUTING</code> and <code>OUTPUT</code> chains, and user-defined chains which are only called from those chains. It specifies that the destination address of the packet should be modified (and all future packets in this connection will also be mangled), and rules should cease being examined. It takes the following options:</p>
<dl>
<dt><code>&#8211;to-destination</code> [<i>ipaddr</i>[<code>&#8211;</code><i>ipaddr</i>]][<code>:</code><i>port</i>[<code>&#8211;</code><i>port</i>]]</p>
<dd>which can specify a single new destination IP address, an inclusive range of IP addresses. Optionally a port range, if the rule also specifies one of the following protocols: <code>tcp</code>, <code>udp</code>, <code>dccp</code> or <code>sctp</code>. If no port range is specified, then the destination port will never be modified. If no IP address is specified then only the destination port will be modified. In Kernels up to 2.6.10 you can add several &#8211;to-destination options. For those kernels, if you specify more than one destination address, either via an address range or multiple &#8211;to-destination options, a simple round-robin (one after another in cycle) load balancing takes place between these addresses. Later Kernels (&gt;= 2.6.11-rc1) don&#8217;t have the ability to NAT to multiple ranges anymore.</p>
<dt><code>&#8211;random</code></p>
<dd>If option <code>&#8211;random</code> is used then port mapping will be randomized (kernel &gt;= 2.6.22).</p>
<dt><code>&#8211;persistent</code></p>
<dd>Gives a client the same source-/destination-address for each connection. This supersedes the SAME target. Support for persistent mappings is available from 2.6.29-rc2.</p>
<dt>IPv6 support available since Linux kernels &gt;= 3.7.</p>
<dd></dl>
<h3>DNPT (IPv6-specific)</h3>
<p>Provides stateless destination IPv6-to-IPv6 Network Prefix Translation (as described by RFC 6296). </p>
<p> You have to use this target in the <code>mangle</code> table, not in the <code>nat</code> table. It takes the following options:</p>
<dl>
<dt><code>&#8211;src-pfx</code> [<i>prefix/</i><i>length]</p>
<dd>Set source prefix that you want to translate and length</p>
<dt></i><code>&#8211;dst-pfx</code> [<i>prefix/</i><i>length]</p>
<dd>Set destination prefix that you want to use in the translation and length</dl>
<p> You have to use the SNPT target to undo the translation. Example:</p>
<dl>
<dd>ip6tables -t mangle -I POSTROUTING -s fd00::/64 -o vboxnet0 -j SNPT &#8211;src-pfx fd00::/64 &#8211;dst-pfx 2001:e20:2000:40f::/64</p>
<dd>ip6tables -t mangle -I PREROUTING -i wlan0 -d 2001:e20:2000:40f::/64 -j DNPT &#8211;src-pfx 2001:e20:2000:40f::/64 &#8211;dst-pfx fd00::/64</dl>
<p> You may need to enable IPv6 neighbor proxy:</p>
<dl>
<dd>sysctl -w net.ipv6.conf.all.proxy_ndp=1</dl>
<p> You also have to use the </i><code>NOTRACK</code> target to disable connection tracking for translated flows.</p>
<h3>Dscp</h3>
<p>This target alters the value of the DSCP bits within the TOS header of the IPv4 packet. As this manipulates a packet, it can only be used in the mangle table.</p>
<dl>
<dt><code>&#8211;set-dscp</code> <i>value</i></p>
<dd>Set the DSCP field to a numerical value (can be decimal or hex)</p>
<dt><code>&#8211;set-dscp-class</code> <i>class</i></p>
<dd>Set the DSCP field to a DiffServ class.</dl>
<h3>ECN (IPv4-specific)</h3>
<p>This target selectively works around known ECN blackholes. It can only be used in the mangle table.</p>
<dl>
<dt><code>&#8211;ecn-tcp-remove</code></p>
<dd>Remove all ECN bits from the TCP header. Of course, it can only be used in conjunction with <code>-p tcp</code>.</dl>
<h3>HL (IPv6-specific)</h3>
<p>This is used to modify the Hop Limit field in IPv6 header. The Hop Limit field is similar to what is known as TTL value in IPv4. Setting or incrementing the Hop Limit field can potentially be very dangerous, so it should be avoided at any cost. This target is only valid in <code>mangle</code> table. </p>
<p> <code>Don&#8217;t ever set or increment the value on packets that leave your local network!</code></p>
<dl>
<dt><code>&#8211;hl-set</code> <i>value</i></p>
<dd>Set the Hop Limit to `value&#8217;.</p>
<dt><code>&#8211;hl-dec</code> <i>value</i></p>
<dd>Decrement the Hop Limit `value&#8217; times.</p>
<dt><code>&#8211;hl-inc</code> <i>value</i></p>
<dd>Increment the Hop Limit `value&#8217; times.</dl>
<h3>Hmark</h3>
<p>Like MARK, i.e. set the fwmark, but the mark is calculated from hashing packet selector at choice. You have also to specify the mark range and, optionally, the offset to start from. ICMP error messages are inspected and used to calculate the hashing. </p>
<p> Existing options are:</p>
<dl>
<dt><code>&#8211;hmark-tuple</code> tuple<i></i></p>
<dd>Possible tuple members are: <code>src</code> meaning source address (IPv4, IPv6 address), <code>dst</code> meaning destination address (IPv4, IPv6 address), <code>sport</code> meaning source port (TCP, UDP, UDPlite, SCTP, DCCP), <code>dport</code> meaning destination port (TCP, UDP, UDPlite, SCTP, DCCP), <code>spi</code> meaning Security Parameter Index (AH, ESP), and <code>ct</code> meaning the usage of the conntrack tuple instead of the packet selectors.</p>
<dt><code>&#8211;hmark-mod</code> <i>value (must be &gt; 0)</i></p>
<dd>Modulus for hash calculation (to limit the range of possible marks)</p>
<dt><code>&#8211;hmark-offset</code> <i>value</i></p>
<dd>Offset to start marks from.</p>
<dt>For advanced usage, instead of using &#8211;hmark-tuple, you can specify custom</p>
<dd>prefixes and masks:</p>
<dt><code>&#8211;hmark-src-prefix</code> <i>cidr</i></p>
<dd>The source address mask in CIDR notation.</p>
<dt><code>&#8211;hmark-dst-prefix</code> <i>cidr</i></p>
<dd>The destination address mask in CIDR notation.</p>
<dt><code>&#8211;hmark-sport-mask</code> <i>value</i></p>
<dd>A 16 bit source port mask in hexadecimal.</p>
<dt><code>&#8211;hmark-dport-mask</code> <i>value</i></p>
<dd>A 16 bit destination port mask in hexadecimal.</p>
<dt><code>&#8211;hmark-spi-mask</code> <i>value</i></p>
<dd>A 32 bit field with spi mask.</p>
<dt><code>&#8211;hmark-proto-mask</code> <i>value</i></p>
<dd>An 8 bit field with layer 4 protocol number.</p>
<dt><code>&#8211;hmark-rnd</code> <i>value</i></p>
<dd>A 32 bit random custom value to feed hash calculation.</dl>
<p> <i>Examples:</i> </p>
<p> iptables -t mangle -A PREROUTING -m conntrack &#8211;ctstate NEW<br />
&nbsp;-j HMARK &#8211;hmark-tuple ct,src,dst,proto &#8211;hmark-offset 10000 &#8211;hmark-mod 10 &#8211;hmark-rnd 0xfeedcafe </p>
<p> iptables -t mangle -A PREROUTING -j HMARK &#8211;hmark-offset 10000 &#8211;hmark-tuple src,dst,proto &#8211;hmark-mod 10 &#8211;hmark-rnd 0xdeafbeef</p>
<h3>Idletimer</h3>
<p>This target can be used to identify when interfaces have been idle for a certain period of time. Timers are identified by labels and are created when a rule is set with a new label. The rules also take a timeout value (in seconds) as an option. If more than one rule uses the same timer label, the timer will be restarted whenever any of the rules get a hit. One entry for each timer is created in sysfs. This attribute contains the timer remaining for the timer to expire. The attributes are located under the xt_idletimer class: </p>
<p> /sys/class/xt_idletimer/timers/&lt;label&gt; </p>
<p> When the timer expires, the target module sends a sysfs notification to the userspace, which can then decide what to do (eg. disconnect to save power).</p>
<dl>
<dt><code>&#8211;timeout</code> <i>amount</i></p>
<dd>This is the time in seconds that will trigger the notification.</p>
<dt><code>&#8211;label</code> <i>string</i></p>
<dd>This is a unique identifier for the timer. The maximum length for the label string is 27 characters.</dl>
<h3>Led</h3>
<p>This creates an LED-trigger that can then be attached to system indicator lights, to blink or illuminate them when certain packets pass through the system. One example might be to light up an LED for a few minutes every time an SSH connection is made to the local machine. The following options control the trigger behavior:</p>
<dl>
<dt><code>&#8211;led-trigger-id</code> <i>name</i></p>
<dd>This is the name given to the LED trigger. The actual name of the trigger will be prefixed with &quot;netfilter-&quot;.</p>
<dt><code>&#8211;led-delay</code> <i>ms</i></p>
<dd>This indicates how long (in milliseconds) the LED should be left illuminated when a packet arrives before being switched off again. The default is 0 (blink as fast as possible.) The special value <i>inf</i> can be given to leave the LED on permanently once activated. (In this case the trigger will need to be manually detached and reattached to the LED device to switch it off again.)</p>
<dt><code>&#8211;led-always-blink</code></p>
<dd>Always make the LED blink on packet arrival, even if the LED is already on. This allows notification of new packets even with long delay values (which otherwise would result in a silent prolonging of the delay time.)</p>
<dt>Example:</p>
<dd>
<dt>Create an LED trigger for incoming SSH traffic:</p>
<dd>iptables -A INPUT -p tcp &#8211;dport 22 -j LED &#8211;led-trigger-id ssh</p>
<dt>Then attach the new trigger to an LED:</p>
<dd>echo netfilter-ssh &gt;/sys/class/leds/<i>ledname</i>/trigger</dl>
<h3>Log</h3>
<p>Turn on kernel logging of matching packets. When this option is set for a rule, the Linux kernel will print some information on all matching packets (like most IP/IPv6 header fields) via the kernel log (where it can be read with <i><a href="/docs/linux/man/1-dmesg/">dmesg</a>(1)</i> or read in the syslog). </p>
<p> This is a &quot;non-terminating target&quot;, i.e. rule traversal continues at the next rule. So if you want to LOG the packets you refuse, use two separate rules with the same matching criteria, first using target LOG then DROP (or REJECT).</p>
<dl>
<dt><code>&#8211;log-level</code> <i>level</i></p>
<dd>Level of logging, which can be (system-specific) numeric or a mnemonic. Possible values are (in decreasing order of priority): <code>emerg</code>, <code>alert</code>, <code>crit</code>, <code>error</code>, <code>warning</code>, <code>notice</code>, <code>info</code> or <code>debug</code>.</p>
<dt><code>&#8211;log-prefix</code> <i>prefix</i></p>
<dd>Prefix log messages with the specified prefix; up to 29 letters long, and useful for distinguishing messages in the logs.</p>
<dt><code>&#8211;log-tcp-sequence</code></p>
<dd>Log TCP sequence numbers. This is a security risk if the log is readable by users.</p>
<dt><code>&#8211;log-tcp-options</code></p>
<dd>Log options from the TCP packet header.</p>
<dt><code>&#8211;log-ip-options</code></p>
<dd>Log options from the IP/IPv6 packet header.</p>
<dt><code>&#8211;log-uid</code></p>
<dd>Log the userid of the process which generated the packet.</dl>
<h3>Mark</h3>
<p>This target is used to set the Netfilter mark value associated with the packet. It can, for example, be used in conjunction with routing based on fwmark (needs iproute2). If you plan on doing so, note that the mark needs to be set in either the PREROUTING or the OUTPUT chain of the mangle table to affect routing. The mark field is 32 bits wide.</p>
<dl>
<dt><code>&#8211;set-xmark</code> <i>value</i>[<code>/</code><i>mask</i>]</p>
<dd>Zeroes out the bits given by <i>mask</i> and XORs <i>value</i> into the packet mark (&quot;nfmark&quot;). If <i>mask</i> is omitted, 0xFFFFFFFF is assumed.</p>
<dt><code>&#8211;set-mark</code> <i>value</i>[<code>/</code><i>mask</i>]</p>
<dd>Zeroes out the bits given by <i>mask</i> and ORs <i>value</i> into the packet mark. If <i>mask</i> is omitted, 0xFFFFFFFF is assumed.</dl>
<p> The following mnemonics are available:</p>
<dl>
<dt><code>&#8211;and-mark</code> <i>bits</i></p>
<dd>Binary AND the nfmark with <i>bits</i>. (Mnemonic for <code>&#8211;set-xmark 0/</code><i>invbits</i>, where <i>invbits</i> is the binary negation of <i>bits</i>.)</p>
<dt><code>&#8211;or-mark</code> <i>bits</i></p>
<dd>Binary OR the nfmark with <i>bits</i>. (Mnemonic for <code>&#8211;set-xmark</code> <i>bits</i><code>/</code><i>bits</i>.)</p>
<dt><code>&#8211;xor-mark</code> <i>bits</i></p>
<dd>Binary XOR the nfmark with <i>bits</i>. (Mnemonic for <code>&#8211;set-xmark</code> <i>bits</i><code>/0</code>.)</dl>
<h3>Masquerade</h3>
<p>This target is only valid in the <code>nat</code> table, in the <code>POSTROUTING</code> chain. It should only be used with dynamically assigned IP (dialup) connections: if you have a static IP address, you should use the SNAT target. Masquerading is equivalent to specifying a mapping to the IP address of the interface the packet is going out, but also has the effect that connections are <i>forgotten</i> when the interface goes down. This is the correct behavior when the next dialup is unlikely to have the same interface address (and hence any established connections are lost anyway).</p>
<dl>
<dt><code>&#8211;to-ports</code> <i>port</i>[<code>&#8211;</code><i>port</i>]</p>
<dd>This specifies a range of source ports to use, overriding the default <code>SNAT</code> source port-selection heuristics (see above). This is only valid if the rule also specifies one of the following protocols: <code>tcp</code>, <code>udp</code>, <code>dccp</code> or <code>sctp</code>.</p>
<dt><code>&#8211;random</code></p>
<dd>Randomize source port mapping If option <code>&#8211;random</code> is used then port mapping will be randomized (kernel &gt;= 2.6.21). Since kernel 5.0, <code>&#8211;random</code> is identical to <code>&#8211;random-fully</code>.</p>
<dt><code>&#8211;random-fully</code></p>
<dd>Full randomize source port mapping If option <code>&#8211;random-fully</code> is used then port mapping will be fully randomized (kernel &gt;= 3.13).</p>
<dt>IPv6 support available since Linux kernels &gt;= 3.7.</p>
<dd></dl>
<h3>Netmap</h3>
<p>This target allows you to statically map a whole network of addresses onto another network of addresses. It can only be used from rules in the <code>nat</code> table.</p>
<dl>
<dt><code>&#8211;to</code> <i>address</i>[<code>/</code><i>mask</i>]</p>
<dd>Network address to map to. The resulting address will be constructed in the following way: All &#8216;one&#8217; bits in the mask are filled in from the new `address&#8217;. All bits that are zero in the mask are filled in from the original address.</p>
<dt>IPv6 support available since Linux kernels &gt;= 3.7.</p>
<dd></dl>
<h3>Nflog</h3>
<p>This target provides logging of matching packets. When this target is set for a rule, the Linux kernel will pass the packet to the loaded logging backend to log the packet. This is usually used in combination with nfnetlink_log as logging backend, which will multicast the packet through a <i>netlink</i> socket to the specified multicast group. One or more userspace processes may subscribe to the group to receive the packets. Like LOG, this is a non-terminating target, i.e. rule traversal continues at the next rule.</p>
<dl>
<dt><code>&#8211;nflog-group</code> <i>nlgroup</i></p>
<dd>The netlink group (0 &#8211; 2^16-1) to which packets are (only applicable for nfnetlink_log). The default value is 0.</p>
<dt><code>&#8211;nflog-prefix</code> <i>prefix</i></p>
<dd>A prefix string to include in the log message, up to 64 characters long, useful for distinguishing messages in the logs.</p>
<dt><code>&#8211;nflog-range</code> <i>size</i></p>
<dd>This option has never worked, use &#8211;nflog-size instead</p>
<dt><code>&#8211;nflog-size</code> <i>size</i></p>
<dd>The number of bytes to be copied to userspace (only applicable for nfnetlink_log). nfnetlink_log instances may specify their own range, this option overrides it.</p>
<dt><code>&#8211;nflog-threshold</code> <i>size</i></p>
<dd>Number of packets to queue inside the kernel before sending them to userspace (only applicable for nfnetlink_log). Higher values result in less overhead per packet, but increase delay until the packets reach userspace. The default value is 1.</dl>
<h3>Nfqueue</h3>
<p>This target passes the packet to userspace using the <code>nfnetlink_queue</code> handler. The packet is put into the queue identified by its 16-bit queue number. Userspace can inspect and modify the packet if desired. Userspace must then drop or reinject the packet into the kernel. Please see libnetfilter_queue for details. <code>nfnetlink_queue</code> was added in Linux 2.6.14. The <code>queue-balance</code> option was added in Linux 2.6.31, <code>queue-bypass</code> in 2.6.39.</p>
<dl>
<dt><code>&#8211;queue-num</code> <i>value</i></p>
<dd>This specifies the QUEUE number to use. Valid queue numbers are 0 to 65535. The default value is 0.</dl>
<dl>
<dt><code>&#8211;queue-balance</code> <i>value</i><code>:</code><i>value</i></p>
<dd>This specifies a range of queues to use. Packets are then balanced across the given queues. This is useful for multicore systems: start multiple instances of the userspace program on queues x, x+1, .. x+n and use &quot;&#8211;queue-balance <i>x</i><code>:</code><i>x+n</i>&quot;. Packets belonging to the same connection are put into the same nfqueue.</dl>
<dl>
<dt><code>&#8211;queue-bypass</code></p>
<dd>By default, if no userspace program is listening on an NFQUEUE, then all packets that are to be queued are dropped. When this option is used, the NFQUEUE rule behaves like ACCEPT instead, and the packet will move on to the next table.</dl>
<dl>
<dt><code>&#8211;queue-cpu-fanout</code></p>
<dd>Available starting Linux kernel 3.10. When used together with <code>&#8211;queue-balance</code> this will use the CPU ID as an index to map packets to the queues. The idea is that you can improve performance if there&#8217;s a queue per CPU. This requires <code>&#8211;queue-balance</code> to be specified.</dl>
<h3>Notrack</h3>
<p>This extension disables connection tracking for all packets matching that rule. It is equivalent with -j CT &#8211;notrack. Like CT, NOTRACK can only be used in the <code>raw</code> table.</p>

<dl>

<dd>Count matched packets into the pool referred to by <i>name</i>, which is freely choosable.</p>
<dt><code>&#8211;rateest-interval</code> <i>amount</i>{<code>s</code>|<code>ms</code>|<code>us</code>}</p>
<dd>Rate measurement interval, in seconds, milliseconds or microseconds.</p>
<dt><code>&#8211;rateest-ewmalog</code> <i>value</i></p>
<dd>Rate measurement averaging time constant.</dl>
<h3>Redirect</h3>
<p>This target is only valid in the <code>nat</code> table, in the <code>PREROUTING</code> and <code>OUTPUT</code> chains, and user-defined chains which are only called from those chains. It redirects the packet to the machine itself by changing the destination IP to the primary address of the incoming interface (locally-generated packets are mapped to the localhost address, 127.0.0.1 for IPv4 and ::1 for IPv6, and packets arriving on interfaces that don&#8217;t have an IP address configured are dropped).</p>
<dl>
<dt><code>&#8211;to-ports</code> <i>port</i>[<code>&#8211;</code><i>port</i>]</p>
<dd>This specifies a destination port or range of ports to use: without this, the destination port is never altered. This is only valid if the rule also specifies one of the following protocols: <code>tcp</code>, <code>udp</code>, <code>dccp</code> or <code>sctp</code>.</p>
<dt><code>&#8211;random</code></p>
<dd>If option <code>&#8211;random</code> is used then port mapping will be randomized (kernel &gt;= 2.6.22).</p>
<dt>IPv6 support available starting Linux kernels &gt;= 3.7.</p>
<dd></dl>
<h3>REJECT (IPv6-specific)</h3>
<p>This is used to send back an error packet in response to the matched packet: otherwise it is equivalent to <code>DROP</code> so it is a terminating TARGET, ending rule traversal. This target is only valid in the <code>INPUT</code>, <code>FORWARD</code> and <code>OUTPUT</code> chains, and user-defined chains which are only called from those chains. The following option controls the nature of the error packet returned:</p>
<dl>
<dt><code>&#8211;reject-with</code> <i>type</i></p>
<dd>The type given can be <code>icmp6-no-route</code>, <code>no-route</code>, <code>icmp6-adm-prohibited</code>, <code>adm-prohibited</code>, <code>icmp6-addr-unreachable</code>, <code>addr-unreach</code>, or <code>icmp6-port-unreachable</code>, which return the appropriate ICMPv6 error message (<code>icmp6-port-unreachable</code> is the default). Finally, the option <code>tcp-reset</code> can be used on rules which only match the TCP protocol: this causes a TCP RST packet to be sent back. This is mainly useful for blocking <i>ident</i> (113/tcp) probes which frequently occur when sending mail to broken mail hosts (which won&#8217;t accept your mail otherwise). <code>tcp-reset</code> can only be used with kernel versions 2.6.14 or later.</dl>
<p> <i>Warning:</i> You should not indiscriminately apply the REJECT target to packets whose connection state is classified as INVALID; instead, you should only DROP these. </p>
<p> Consider a source host transmitting a packet P, with P experiencing so much delay along its path that the source host issues a retransmission, P_2, with P_2 being successful in reaching its destination and advancing the connection state normally. It is conceivable that the late-arriving P may be considered not to be associated with any connection tracking entry. Generating a reject response for a packet so classed would then terminate the healthy connection. </p>
<p> So, instead of: </p>
<p> -A INPUT &#8230; -j REJECT </p>
<p> do consider using: </p>
<p> -A INPUT &#8230; -m conntrack &#8211;ctstate INVALID -j DROP -A INPUT &#8230; -j REJECT</p>

<dl>
<dt><code>&#8211;add-set</code> <i>setname</i> <i>flag</i>[<code>,</code><i>flag</i>&#8230;]</p>

<dd>where <i>flag</i>(s) are <code>src</code> and/or <code>dst</code> specifications and there can be no more than six of them.</p>
<dt><code>&#8211;timeout</code> <i>value</i></p>
<dd>when adding an entry, the timeout value to use instead of the default one from the set definition</p>

<dd>the set-name should be created with &#8211;skbinfo option <code>&#8211;map-mark</code> map firewall mark to packet by lookup of value in the set <code>&#8211;map-prio</code> map traffic control priority to packet by lookup of value in the set <code>&#8211;map-queue</code> map hardware NIC queue to packet by lookup of value in the set</p>
<dd>The <code>&#8211;map-set</code> option can be used from the mangle table only. The <code>&#8211;map-prio</code> and <code>&#8211;map-queue</code> flags can be used in the OUTPUT, FORWARD and POSTROUTING chains.</dl>
<p> Use of -j SET requires that ipset kernel support is provided, which, for standard kernels, is the case since Linux 2.6.39.</p>
<h3>Snat</h3>
<p>This target is only valid in the <code>nat</code> table, in the <code>POSTROUTING</code> and <code>INPUT</code> chains, and user-defined chains which are only called from those chains. It specifies that the source address of the packet should be modified (and all future packets in this connection will also be mangled), and rules should cease being examined. It takes the following options:</p>
<dl>
<dt><code>&#8211;to-source</code> [<i>ipaddr</i>[<code>&#8211;</code><i>ipaddr</i>]][<code>:</code><i>port</i>[<code>&#8211;</code><i>port</i>]]</p>
<dd>which can specify a single new source IP address, an inclusive range of IP addresses. Optionally a port range, if the rule also specifies one of the following protocols: <code>tcp</code>, <code>udp</code>, <code>dccp</code> or <code>sctp</code>. If no port range is specified, then source ports below 512 will be mapped to other ports below 512: those between 512 and 1023 inclusive will be mapped to ports below 1024, and other ports will be mapped to 1024 or above. Where possible, no port alteration will occur. In Kernels up to 2.6.10, you can add several &#8211;to-source options. For those kernels, if you specify more than one source address, either via an address range or multiple &#8211;to-source options, a simple round-robin (one after another in cycle) takes place between these addresses. Later Kernels (&gt;= 2.6.11-rc1) don&#8217;t have the ability to NAT to multiple ranges anymore.</p>
<dt><code>&#8211;random</code></p>
<dd>If option <code>&#8211;random</code> is used then port mapping will be randomized through a hash-based algorithm (kernel &gt;= 2.6.21).</p>
<dt><code>&#8211;random-fully</code></p>
<dd>If option <code>&#8211;random-fully</code> is used then port mapping will be fully randomized through a PRNG (kernel &gt;= 3.14).</p>
<dt><code>&#8211;persistent</code></p>
<dd>Gives a client the same source-/destination-address for each connection. This supersedes the SAME target. Support for persistent mappings is available from 2.6.29-rc2.</dl>
<p> Kernels prior to 2.6.36-rc1 don&#8217;t have the ability to <code>SNAT</code> in the <code>INPUT</code> chain.</p>
<dl>
<dt>IPv6 support available since Linux kernels &gt;= 3.7.</p>
<dd></dl>
<h3>SNPT (IPv6-specific)</h3>
<p>Provides stateless source IPv6-to-IPv6 Network Prefix Translation (as described by RFC 6296). </p>
<p> You have to use this target in the <code>mangle</code> table, not in the <code>nat</code> table. It takes the following options:</p>
<dl>
<dt><code>&#8211;src-pfx</code> [<i>prefix/</i><i>length]</p>
<dd>Set source prefix that you want to translate and length</p>
<dt></i><code>&#8211;dst-pfx</code> [<i>prefix/</i><i>length]</p>
<dd>Set destination prefix that you want to use in the translation and length</dl>
<p> You have to use the DNPT target to undo the translation. Example:</p>
<dl>
<dd>ip6tables -t mangle -I POSTROUTING -s fd00::/64 -o vboxnet0 -j SNPT &#8211;src-pfx fd00::/64 &#8211;dst-pfx 2001:e20:2000:40f::/64</p>
<dd>ip6tables -t mangle -I PREROUTING -i wlan0 -d 2001:e20:2000:40f::/64 -j DNPT &#8211;src-pfx 2001:e20:2000:40f::/64 &#8211;dst-pfx fd00::/64</dl>
<p> You may need to enable IPv6 neighbor proxy:</p>
<dl>
<dd>sysctl -w net.ipv6.conf.all.proxy_ndp=1</dl>
<p> You also have to use the </i><code>NOTRACK</code> target to disable connection tracking for translated flows.</p>
<h3>Synproxy</h3>
<p>This target will process TCP three-way-handshake parallel in netfilter context to protect either local or backend system. This target requires connection tracking because sequence numbers need to be translated. The kernels ability to absorb SYNFLOOD was greatly improved starting with Linux 4.4, so this target should not be needed anymore to protect Linux servers.</p>
<dl>
<dt><code>&#8211;mss</code> <i>maximum segment size</i></p>
<dd>Maximum segment size announced to clients. This must match the backend.</p>
<dt><code>&#8211;wscale</code> <i>window scale</i></p>
<dd>Window scale announced to clients. This must match the backend.</p>
<dt><code>&#8211;sack-perm</code></p>
<dd>Pass client selective acknowledgement option to backend (will be disabled if not present).</p>
<dt><code>&#8211;timestamps</code></p>
<dd>Pass client timestamp option to backend (will be disabled if not present, also needed for selective acknowledgement and window scaling).</dl>
<p> Example: </p>
<p> Determine tcp options used by backend, from an external system</p>
<dl>
<dd>tcpdump -pni eth0 -c 1 &#8216;tcp[tcpflags] == (tcp-syn|tcp-ack)&#8217; </p>
<p>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;port 80&nbsp;&amp;<br />
 telnet 192.0.2.42 80<br />
 18:57:24.693307 IP 192.0.2.42.80 &gt; 192.0.2.43.48757: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;Flags&nbsp;[S.], seq 360414582, ack 788841994, win 14480, </p>
<p>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;options&nbsp;[mss 1460,sackOK, </p>
<p>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;TS val 1409056151 ecr 9690221, </p>
<p>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;nop,wscale 9], </p>
<p>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;length 0</dl>
<p> Switch tcp_loose mode off, so conntrack will mark out-of-flow packets as state INVALID.</p>
<dl>
<dd>echo 0 &gt; /proc/sys/net/netfilter/nf_conntrack_tcp_loose</dl>
<p> Make SYN packets untracked</p>
<dl>
<dd>iptables -t raw -A PREROUTING -i eth0 -p tcp &#8211;dport 80<br />
&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;&#8211;syn -j CT &#8211;notrack</dl>
<p> Catch UNTRACKED (SYN packets) and INVALID (3WHS ACK packets) states and send them to SYNPROXY. This rule will respond to SYN packets with SYN+ACK syncookies, create ESTABLISHED for valid client response (3WHS ACK packets) and drop incorrect cookies. Flags combinations not expected during 3WHS will not match and continue (e.g. SYN+FIN, SYN+ACK).</p>
<dl>
<dd>iptables -A INPUT -i eth0 -p tcp &#8211;dport 80<br />
&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;-m state &#8211;state UNTRACKED,INVALID -j SYNPROXY<br />
&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;&#8211;sack-perm &#8211;timestamp &#8211;mss 1460 &#8211;wscale 9</dl>
<p> Drop invalid packets, this will be out-of-flow packets that were not matched by SYNPROXY.</p>
<dl>
<dd>iptables -A INPUT -i eth0 -p tcp &#8211;dport 80 -m state &#8211;state INVALID -j DROP</dl>
<h3>Tcpmss</h3>
<p>This target alters the MSS value of TCP SYN packets, to control the maximum size for that connection (usually limiting it to your outgoing interface&#8217;s MTU minus 40 for IPv4 or 60 for IPv6, respectively). Of course, it can only be used in conjunction with <code>-p tcp</code>. </p>
<p> This target is used to overcome criminally braindead ISPs or servers which block &quot;ICMP Fragmentation Needed&quot; or &quot;ICMPv6 Packet Too Big&quot; packets. The symptoms of this problem are that everything works fine from your Linux firewall/router, but machines behind it can never exchange large packets:</p>
<dl>
<dt>1.</p>
<dd>Web browsers connect, then hang with no data received.</p>
<dt>2.</p>
<dd>Small mail works fine, but large emails hang.</p>
<dt>3.</p>
<dd>ssh works fine, but scp hangs after initial handshaking.</dl>
<p> Workaround: activate this option and add a rule to your firewall configuration like:</p>
<dl>
<dd>&nbsp;iptables -t mangle -A FORWARD -p tcp &#8211;tcp-flags SYN,RST SYN<br />
&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;-j TCPMSS &#8211;clamp-mss-to-pmtu</p>
<dt><code>&#8211;set-mss</code> <i>value</i></p>
<dd>Explicitly sets MSS option to specified value. If the MSS of the packet is already lower than <i>value</i>, it will <code>not</code> be increased (from Linux 2.6.25 onwards) to avoid more problems with hosts relying on a proper MSS.</p>
<dt><code>&#8211;clamp-mss-to-pmtu</code></p>
<dd>Automatically clamp MSS value to (path_MTU &#8211; 40 for IPv4; -60 for IPv6). This may not function as desired where asymmetric routes with differing path MTU exist &#8212; the kernel uses the path MTU which it would use to send packets from itself to the source and destination IP addresses. Prior to Linux 2.6.25, only the path MTU to the destination IP address was considered by this option; subsequent kernels also consider the path MTU to the source IP address.</dl>
<p> These options are mutually exclusive.</p>

<h3>Tos</h3>
<p>This module sets the Type of Service field in the IPv4 header (including the &quot;precedence&quot; bits) or the Priority field in the IPv6 header. Note that TOS shares the same bits as DSCP and ECN. The TOS target is only valid in the <code>mangle</code> table.</p>
<dl>
<dt><code>&#8211;set-tos</code> <i>value</i>[<code>/</code><i>mask</i>]</p>
<dd>Zeroes out the bits given by <i>mask</i> (see NOTE below) and XORs <i>value</i> into the TOS/Priority field. If <i>mask</i> is omitted, 0xFF is assumed.</p>
<dt><code>&#8211;set-tos</code> <i>symbol</i></p>
<dd>You can specify a symbolic name when using the TOS target for IPv4. It implies a mask of 0xFF (see NOTE below). The list of recognized TOS names can be obtained by calling iptables with <code>-j TOS -h</code>.</dl>
<p> The following mnemonics are available:</p>
<dl>
<dt><code>&#8211;and-tos</code> <i>bits</i></p>
<dd>Binary AND the TOS value with <i>bits</i>. (Mnemonic for <code>&#8211;set-tos 0/</code><i>invbits</i>, where <i>invbits</i> is the binary negation of <i>bits</i>. See NOTE below.)</p>
<dt><code>&#8211;or-tos</code> <i>bits</i></p>
<dd>Binary OR the TOS value with <i>bits</i>. (Mnemonic for <code>&#8211;set-tos</code> <i>bits</i><code>/</code><i>bits</i>. See NOTE below.)</p>
<dt><code>&#8211;xor-tos</code> <i>bits</i></p>
<dd>Binary XOR the TOS value with <i>bits</i>. (Mnemonic for <code>&#8211;set-tos</code> <i>bits</i><code>/0</code>. See NOTE below.)</dl>
<p> NOTE: In Linux kernels up to and including 2.6.38, with the exception of longterm releases 2.6.32 (&gt;=.42), 2.6.33 (&gt;=.15), and 2.6.35 (&gt;=.14), there is a bug whereby IPv6 TOS mangling does not behave as documented and differs from the IPv4 version. The TOS mask indicates the bits one wants to zero out, so it needs to be inverted before applying it to the original TOS field. However, the aformentioned kernels forgo the inversion which breaks &#8211;set-tos and its mnemonics.</p>
<h3>Tproxy</h3>
<p>This target is only valid in the <code>mangle</code> table, in the <code>PREROUTING</code> chain and user-defined chains which are only called from this chain. It redirects the packet to a local socket without changing the packet header in any way. It can also change the mark value which can then be used in advanced routing rules. It takes three options:</p>
<dl>
<dt><code>&#8211;on-port</code> <i>port</i></p>
<dd>This specifies a destination port to use. It is a required option, 0 means the new destination port is the same as the original. This is only valid if the rule also specifies <code>-p tcp</code> or <code>-p udp</code>.</p>
<dt><code>&#8211;on-ip</code> <i>address</i></p>
<dd>This specifies a destination address to use. By default the address is the IP address of the incoming interface. This is only valid if the rule also specifies <code>-p tcp</code> or <code>-p udp</code>.</p>
<dt><code>&#8211;tproxy-mark</code> <i>value</i>[<code>/</code><i>mask</i>]</p>
<dd>Marks packets with the given value/mask. The fwmark value set here can be used by advanced routing. (Required for transparent proxying to work: otherwise these packets will get forwarded, which is probably not what you want.)</dl>
<h3>Trace</h3>
<p>This target marks packets so that the kernel will log every rule which match the packets as those traverse the tables, chains, rules. It can only be used in the <code>raw</code> table. </p>
<p> With iptables-legacy, a logging backend, such as <a href="/docs/linux/man/6-ip/">ip</a>(6)t_LOG or nfnetlink_log, must be loaded for this to be visible. The packets are logged with the string prefix: &quot;TRACE: tablename:chainname:type:rulenum &quot; where type can be &quot;rule&quot; for plain rule, &quot;return&quot; for implicit rule at the end of a user defined chain and &quot;policy&quot; for the policy of the built in chains. </p>
<p> With iptables-nft, the target is translated into nftables&#8217; <code>meta nftrace</code> expression. Hence the kernel sends trace events via netlink to userspace where they may be displayed using <code>xtables-monitor &#8211;trace</code> command. For details, refer to <code><a href="/docs/linux/man/8-xtables-monitor/">xtables-monitor</a></code>(8).</p>
<h3>TTL (IPv4-specific)</h3>
<p>This is used to modify the IPv4 TTL header field. The TTL field determines how many hops (routers) a packet can traverse until it&#8217;s time to live is exceeded. </p>
<p> Setting or incrementing the TTL field can potentially be very dangerous, so it should be avoided at any cost. This target is only valid in <code>mangle</code> table. </p>
<p> <code>Don&#8217;t ever set or increment the value on packets that leave your local network!</code></p>
<dl>
<dt><code>&#8211;ttl-set</code> <i>value</i></p>
<dd>Set the TTL value to `value&#8217;.</p>
<dt><code>&#8211;ttl-dec</code> <i>value</i></p>
<dd>Decrement the TTL value `value&#8217; times.</p>
<dt><code>&#8211;ttl-inc</code> <i>value</i></p>
<dd>Increment the TTL value `value&#8217; times.</dl>
<h3>ULOG (IPv4-specific)</h3>
<p>This is the deprecated ipv4-only predecessor of the NFLOG target. It provides userspace logging of matching packets. When this target is set for a rule, the Linux kernel will multicast this packet through a <i>netlink</i> socket. One or more userspace processes may then subscribe to various multicast groups and receive the packets. Like LOG, this is a &quot;non-terminating target&quot;, i.e. rule traversal continues at the next rule.</p>
<dl>
<dt><code>&#8211;ulog-nlgroup</code> <i>nlgroup</i></p>
<dd>This specifies the netlink group (1-32) to which the packet is sent. Default value is 1.</p>
<dt><code>&#8211;ulog-prefix</code> <i>prefix</i></p>
<dd>Prefix log messages with the specified prefix; up to 32 characters long, and useful for distinguishing messages in the logs.</p>
<dt><code>&#8211;ulog-cprange</code> <i>size</i></p>
<dd>Number of bytes to be copied to userspace. A value of 0 always copies the entire packet, regardless of its size. Default is 0.</p>
<dt><code>&#8211;ulog-qthreshold</code> <i>size</i></p>
<dd>Number of packet to queue inside kernel. Setting this value to, e.g. 10 accumulates ten packets inside the kernel and transmits them as one netlink multipart message to userspace. Default is 1 (for backwards compatibility). </p>
</dl>
