<p>iwevent &#8211; Display Wireless Events generated by drivers and setting changes</p>
<h2>Synopsis</h2>
<p><code>iwevent </code></p>
<h2>Description</h2>
<p><code>iwevent</code> displays Wireless Events received through the RTNetlink socket. Each line displays the specific Wireless Event which describes what has happened on the specified wireless interface.<br />
 This command doesn&#8217;t take any arguments.</p>
<h2>Display</h2>
<p>There are two classes of Wireless Events. </p>
<p> The first class is events related to a change of wireless settings on the interface (typically done through <code>iwconfig</code> or a script calling <code>iwconfig</code>). Only settings that could result in a disruption of connectivity are reported. The events currently reported are changing one of the following setting :<br />
 <i><tt>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;</tt>Network ID</i><br />
 <i><tt>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;</tt>ESSID</i><br />
 <i><tt>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;</tt>Frequency</i><br />
 <i><tt>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;</tt>Mode</i><br />
 <i><tt>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;</tt>Encryption</i><br />
 All those events will be generated on all wireless interfaces by the<br />
 kernel wireless subsystem (but only if the driver has been converted to the new driver API). </p>
<p> The second class of events are events generated by the hardware, when something happens or a task has been finished. Those events include :</p>
<dl>
<dt><code>New Access Point/Cell address</code></p>
<dd>The interface has joined a new Access Point or Ad-Hoc Cell, or lost its association with it. This is the same address that is reported by <code>iwconfig</code>.</p>
<dt><code>Scan request completed</code></p>
<dd>A scanning request has been completed, results of the scan are available (see <code>iwlist</code>).</p>
<dt><code>Tx packet dropped</code></p>
<dd>A packet directed at this address has been dropped because the interface believes this node doesn&#8217;t answer anymore (usually maximum of MAC level retry exceeded). This is usually an early indication that the node may have left the cell or gone out of range, but it may be due to fading or excessive contention.</p>
<dt><code>Custom driver event</code></p>
<dd>Event specific to the driver. Please check the driver documentation.</p>
<dt><code>Registered node</code></p>
<dd>The interface has successfully registered a new wireless client/peer. Will be generated mostly when the interface acts as an Access Point (mode Master).</p>
<dt><code>Expired node</code></p>
<dd>The registration of the client/peer on this interface has expired. Will be generated mostly when the interface acts as an Access Point (mode Master).</p>
<dt><code>Spy threshold crossed</code></p>
<dd>The signal strength for one of the addresses in the spy list went under the low threshold or went above the high threshold.</dl>
<p> Most wireless drivers generate only a subset of those events, not all of them, the exact list depends on the specific hardware/driver combination. Please refer to driver documentation for details on when they are generated, and use <i><a href="/docs/linux/man/8-iwlist/">iwlist</a></i>(8) to check what the driver supports.</p>
