<p>tcpslice &#8211; extract pieces of and/or merge together tcpdump files</p>
<h2>Synopsis</h2>
<p><code>tcpslice</code> [ <code>-DdlRrt</code> ] [ <code>-w</code> <i>file</i> ] </p>
<p> &nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr> [ <i>start-time</i> [ <i>end-time</i> ] ] <i>file &#8230;</i></p>
<h2>Description</h2>
<p><i>Tcpslice</i> is a program for extracting portions of packet-trace files generated using <i><a href="/docs/linux/man/l-tcpdump/">tcpdump</a>(l)</i>&#8216;s <code>-w</code> flag. It can also be used to merge together several such files, as discussed below. </p>
<p> The basic operation of <i>tcpslice</i> is to copy to <i>stdout</i> all packets from its input file(s) whose timestamps fall within a given range. The starting and ending times of the range may be specified on the command line. All ranges are inclusive. The starting time defaults to the earliest time of the first packet in any of the input files; we call this the <i>first time.</i> The ending time defaults to ten years after the starting time. Thus, the command <i>tcpslice trace-file</i> simply copies <i>trace-file</i> to <i>stdout</i> (assuming the file does not include more than ten years&#8217; worth of data). </p>
<p> There are a number of ways to specify times. The first is using Unix timestamps of the form <i>sssssssss.uuuuuu</i> (this is the format specified by <i>tcpdump</i>&#8216;s <code>-tt</code> flag). For example, <code>654321098.7654</code> specifies 38 seconds and 765,400 microseconds after 8:51PM PDT, Sept. 25, 1990. </p>
<p> All examples in this manual are given for PDT times, but when displaying times and interpreting times symbolically as discussed below, <i>tcpslice</i> uses the local timezone, regardless of the timezone in which the <i>tcpdump</i> file was generated. The daylight-savings setting used is that which is appropriate for the local timezone at the date in question. For example, times associated with summer months will usually include daylight-savings effects, and those with winter months will not. </p>
<p> Times may also be specified relative to either the <i>first time</i> (when specifying a starting time) or the starting time (when specifying an ending time) by preceding a numeric value in seconds with a `+&#8217;. For example, a starting time of <code>+200</code> indicates 200 seconds after the <i>first time,</i> and the two arguments <code>+200 +300</code> indicate from 200 seconds after the <i>first time</i> through 500 seconds after the <i>first time.</i> </p>
<p> Times may also be specified in terms of years (y), months (m), days (d), hours (h), minutes (m), seconds (s), and microseconds(u). For example, the Unix timestamp 654321098.7654 discussed above could also be expressed as <code>1990y9m25d20h51m38s765400u.</code> 2 or 4 digit years may be used; 2 digits can specify years from 1970 to 2069. </p>
<p> When specifying times using this style, fields that are omitted default as follows. If the omitted field is a unit <i>greater</i> than that of the first specified field, then its value defaults to the corresponding value taken from either <i>first time</i> (if the starting time is being specified) or the starting time (if the ending time is being specified). If the omitted field is a unit <i>less</i> than that of the first specified field, then it defaults to zero. For example, suppose that the input file has a <i>first time</i> of the Unix timestamp mentioned above, i.e., 38 seconds and 765,400 microseconds after 8:51PM PDT, Sept. 25, 1990. To specify 9:36PM PDT (exactly) on the same date we could use <code>21h36m.</code> To specify a range from 9:36PM PDT through 1:54AM PDT the next day we could use <code>21h36m 26d1h54m.</code> </p>
<p> Relative times can also be specified when using the <i>ymdhmsu</i> format. Omitted fields then default to 0 if the unit of the field is <i>greater</i> than that of the first specified field, and to the corresponding value taken from either the <i>first time</i> or the starting time if the omitted field&#8217;s unit is <i>less</i> than that of the first specified field. Given a <i>first time</i> of the Unix timestamp mentioned above, <code>22h +1h10m</code> specifies a range from 10:00PM PDT on that date through 11:10PM PDT, and <code>+1h +1h10m</code> specifies a range from 38.7654 seconds after 9:51PM PDT through 38.7654 seconds after 11:01PM PDT. The first hour of the file could be extracted using <code>+0 +1h.</code> </p>
<p> Note that with the <i>ymdhmsu</i> format there is an ambiguity between using <i>m</i> for `month&#8217; or for `minute&#8217;. The ambiguity is resolved as follows: if an <i>m</i> field is followed by a <i>d</i> field then it is interpreted as specifying months; otherwise it specifies minutes. </p>
<p> If more than one input file is specified then <i>tcpslice</i> merges the packets from the various input files into the single output file. Normally, this merge is done based on the value of the timestamps in the packets in the individual files. (Tcpslice assumes that <i>within</i> each input file, packets are in timestamp order.) If the <code>-l</code> option is used, the value used for ordering is the timestamp of a given packet minus the timestamp of the first packet in the input file in which the given packet occurs. </p>
<p> When merging files, by default <i>tcpslice</i> will discard any <i>duplicate</i> packet it finds in more than one file. A duplicate is a packet that has an identical timestamp (either relative or absolute) and identical packet contents (for as much as was captured) as another packet previously seen in a different file. Note that it is possible for the network to generate true replicates of packets, and for systems that can return the same timestamp for multiple packets, these can be mistaken for duplicates and discarded. Accordingly, <i>tcpslice</i> will not discard duplicates in the same trace file. In addition, you can use the <code>-D</code> option to suppress any discarding of duplicates. </p>
<p> A different issue arises if a file contains timestamps that skip backwards. <i>tcpslice</i> will include these in the output, even if they precede the minimum time requested. There should probably be an option to suppress these. </p>
<p> Another problem relating to backwards timestamps is that <i>tcpslice</i> uses random access to seek through a file looking for packets corresponding to the desired range of time. While doing so leads to a major performance benefit for very large trace files, it also means that in the presence of backwards timestamps <i>tcpslice</i> can fail to find the true earliest occurrence of a packet matching the time interval criteria. There should probably be an option to specify not to use random access but just read the file linearly.</p>
<h2>Options</h2>
<p>If any of <code>-R,</code> <code>-r</code> or <code>-t</code> are specified then <i>tcpslice</i> reports the timestamps of the first and last packets in each input file and exits. Only one of these three options may be specified.</p>
<dl>
<dt><code>-D</code></p>
<dd>Do not discard duplicate packets seen when merging multiple trace files.</p>
<dt><code>-d</code></p>
<dd>Dump the start and end times specified by the given range and exit. This option is useful for checking that the given range actually specifies the times you think it does. If one of <code>-R,</code> <code>-r</code> or <code>-t</code> has been specified then the times are dumped in the corresponding format; otherwise, raw format (<code> -R</code>) is used.</p>
<dt><code>-l</code></p>
<dd>When merging more than one file, merge on the basis of relative time, rather than absolute time. Normally, when merging files is done, packets are merged based on absolute timestamps. With <code>-l</code> packets are merged based on the relative time between the start of the file in which the packet is found and the timestamp of the packet itself. The timestamp of packets in the output file is calculated as the relative time for the packet within its file plus <i>first time.</i></p>
<dt><code>-R</code></p>
<dd>Dump the timestamps of the first and last packets in each input file as raw timestamps (i.e., in the form <i> sssssssss.uuuuuu</i>).</p>
<dt><code>-r</code></p>
<dd>Same as <code>-R</code> except the timestamps are dumped in human-readable format, similar to that used by <i> <a href="/docs/linux/man/1-date/">date</a>(1)</i>.</p>
<dt><code>-t</code></p>
<dd>Same as <code>-R</code> except the timestamps are dumped in <i>tcpslice</i> format, i.e., in the <i>ymdhmsu</i> format discussed above.</p>
<dt><code>-w</code></p>
<dd>Direct the output to <i>file</i> rather than <i>stdout</i>.</dl>

<h2>Bugs</h2>
<p>Please send bug reports to tcpslice [at] ee.lbl.gov. An input filename that beings with a digit or a `+&#8217; can be confused with a start/end time. Such filenames can be specified with a leading `./&#8217;; for example, specify the file `04Jul76.trace&#8217; as `./04Jul76.trace&#8217;. <i>tcpslice</i> cannot read its input from <i>stdin</i>, since it uses random-access to rummage through its input files. <i>tcpslice</i> refuses to write to its output if it is a terminal (as indicated by <i><a href="/docs/linux/man/3-isatty/">isatty</a>(3)</i>). This is not a bug but a feature, to prevent it from spraying binary data to the user&#8217;s terminal. Note that this means you must either redirect <i>stdout</i> or specify an output file via <code>-w</code>. <i>tcpslice</i> will not work properly on <i>tcpdump</i> files spanning more than one year; with files containing portions of packets whose original length was more than 65,535 bytes; nor with files containing fewer than two packets. Such files result in the error message: `couldn&#8217;t find final packet in file&#8217;. These problems are due to the interpolation scheme used by <i>tcpslice</i> to greatly speed up its processing when dealing with large trace files. Note that <i>tcpslice</i> can efficiently extract slices from the middle of trace files of any size, and can also work with truncated trace files (i.e., the final packet in the file is only partially present, typically due to <i>tcpdump</i> being ungracefully killed). Adding <code>-l</code> has broken some compatibility with older versions, since <i>tcpslice</i> now merges its input files, rather than (approximately) concatenating them together as it did previously. It would sometimes be convenient if you could specify a clock offset to use with the <code>-l</code> option. It would be nice if <i>tcpslice</i> supported more general editing of trace files. </p>
