<p>ddptctl &#8211; helper/auxiliary utility for ddpt</p>
<h2>Synopsis</h2>
<p><code>ddptctl</code> [<i>&#8211;abort</i>] [<i>&#8211;all_toks</i>] [<i>&#8211;block</i>] [<i>&#8211;del_tkn</i>] [<i>&#8211;help</i>] [<i>&#8211;immed</i>] [<i>&#8211;info</i>] [<i>&#8211;list_id=LID</i>] [<i>&#8211;oir=OIR</i>] [<i>&#8211;poll</i>] [<i>&#8211;pt=GL</i>] [<i>&#8211;receive</i>] [<i>&#8211;rtf=RTF</i>] [<i>&#8211;rtype=RTYPE</i>] [<i>&#8211;size</i>] [<i>&#8211;timeout=ITO[,CMD]</i>] [<i>&#8211;verbose</i>] [<i>&#8211;version</i>] [<i>&#8211;wut=SL</i>] [<i>DEVICE</i>]</p>
<h2>Description</h2>
<p>This utility is a helper/auxiliary for the ddpt utility which copies data between or within SCSI devices (logical units). While ddpt&#8217;s command line syntax is modelled on that of the POSIX dd command, this utility has a more standard Unix command line syntax with both short and long variants of each option. </p>
<p> The T10 committee defines a family of SCSI commands for offloaded copy. The central (but not the only) command is EXTENDED COPY often shortened to XCOPY or xcopy. There are now two generations of xcopy, the older one is given the suffix &quot;LID1&quot; and the newer one: &quot;LID4&quot;. There is a subset of XCOPY(LID4) that supports disk to disk copies and is based on the SBC-3 commands: POPULATE TOKEN (PT) and WRITE USING TOKEN (WUT). ODX is a market name that has become associated with this subset. This utility can issue PT, WUT and related commands, read the Third Party Copy VPD page and perform several other housekeeping tasks. </p>
<p> The xcopy family of commands are described in the SPC-4 and SBC-3 documents found at <a rel="nofollow" href="http://www.t10.org">http://www.t10.org</a> .</p>
<h2>Options</h2>
<p>Arguments to long options are mandatory for short options as well.</p>
<dl>
<dt><code>-A</code>, <code>&#8211;abort</code></p>
<dd>this option will issue the COPY OPERATION ABORT command with the <i>LID</i> given in the <i>&#8211;list_id=LID</i> option. If the <i>&#8211;list_id=LID</i> option is not given then its default <i>LID</i> (257) is used. If there is an xcopy operation ongoing on this I-T nexus (i.e. issued by this machine to any LU sharing the same target) using that <i>LID</i> then the copy is aborted. Note there is a sense key (COPY ABORTED) indicating some but not all data has been copied due to this action.</p>
<dt><code>-a</code>, <code>&#8211;all_toks</code></p>
<dd>send the REPORT ALL ROD TOKENS SCSI command to <i>DEVICE</i> and decode the response. An ODX implementation is not required to support this command.</p>
<dt><code>-B</code>, <code>&#8211;block</code></p>
<dd>treat <i>DEVICE</i> as a block device when checking its <i>&#8211;size</i>. The default action of this utility is to treat <i>DEVICE</i> as a SCSI pass-through device.</p>
<dt><code>-D</code>, <code>&#8211;del_tkn</code></p>
<dd>set the DEL_TKN bit in a WUT command (default: clear the DEL_TKN bit). Since an ODX copy manager deletes the ROD Token after is has been fully copied from (once), this option is typically not needed. It may be useful for long-lived ROD Tokens that have only been partially written from (or not used at all) and are no longer needed.<br />
 To delete an unused ROD Token a degenerate scatter list seems to be acceptable (e.g. &#8216;&#8211;wut=0,0 &#8211;del_tkn&#8217;).</p>
<dt><code>-h</code>, <code>&#8211;help</code></p>
<dd>outputs the usage message summarizing command line options then exits.</p>
<dt><code>-I</code>, <code>&#8211;immed</code></p>
<dd>set the IMMED bit in the PT or WUT command. When given the PT and WUT commands return promptly before the data transfer is complete; then this utility exits. The user should then invoke the utility again with the <i>&#8211;poll</i> option and the same <i>LID</i> and <i>DEVICE</i> to await completion and receive the final transfer count. The default action of PT and WUT (i.e. without this option) is to wait for completion (i.e. all data transferred or an error occurs) before exiting this utility.</p>
<dt><code>-i</code>, <code>&#8211;info</code></p>
<dd>when the <i>DEVICE</i> argument is given then check its Third Party Copy VPD page and print out anything found. Also check if the 3PC bit is set in the standard INQUIRY response.<br />
 If the <i>DEVICE</i> argument is not given and the <i>&#8211;rtf=RTF</i> option is given then decode part of the ROD Token held in the <i>&#8211;RTF</i> file. SPC-4 defines some parts of a ROD Token that can be decoded but does not require the copy manager to set these fields; so many fields may appear as zeros. A <i>&#8211;RTF</i> file that has been generated by the ddpt utility may contain multiple ROD Tokens, each optionally followed by an 8 byte &quot;number of bytes represented&quot; integer. They are all decoded, based on <i>&#8211;RTF</i> file length which should either be a multiple of 512 or 520 bytes.</p>
<dt><code>-l</code>, <code>&#8211;list_id</code>=<i>LID</i></p>
<dd><i>LID</i> is a list identifier which is used to associate an originating xcopy command (e.g. PT or WUT) with a follow-up command that retrieves information or aborts the operation. T10 requires active <i>LID</i>s to be unique on a given I-T nexus. An I-T nexus is the current machine (more precisely a HBA if a machine has two or more) and a specific target which will contain one or more logical units (LUs) of which <i>DEVICE</i> is one. If the <i>DEVICE</i>&#8216;s copy manager feels that rather complex condition has not been met then an error is generated with sense data that decodes to &quot;operation in progress&quot;. Rather than try to work out who is doing what elsewhere, try another <i>LID</i> value.<br />
 The default value for <i>LID</i> is 257.</p>
<dt><code>-O</code>, <code>&#8211;oir</code>=<i>OIR</i></p>
<dd><i>OIR</i> is the Offset In ROD, a field in the WUT command. It may be be used together with the <i>&#8211;wut=SL</i> option. Its default value is 0 and its units are the logical block size of <i>DEVICE</i>.</p>
<dt><code>-p</code>, <code>&#8211;poll</code></p>
<dd>send RECEIVE ROD TOKEN INFORMATION SCSI commands (RRTIs) to the <i>DEVICE</i> using the <i>LID</i> (i.e. from the <i>&#8211;list_id=LID</i> option). If a copy status is received indicating the operation is ongoing, then this SCSI command is sent periodically (as suggested by the previous RRTI command or 500 milliseconds) until some other copy status is detected. If the <i>&#8211;list_id=LID</i> option is not given then a <i>LID</i> of 257 is assumed.<br />
 If the originating xcopy command was POPULATE TOKEN and the RRTI command indicates that it has completed successfully then the associated ROD Token (returned in the RRTI response) is written to the <i>RTF</i> file. If the <i>&#8211;rtf=RTF</i> option is not given then the ROD token is written to a file called ddptctl_rod_tok.bin in the current directory.</p>
<dt><code>-P</code>, <code>&#8211;pt</code>=<i>GL</i></p>
<dd>send a POPULATE TOKEN (PT) command with the given gather list. The format of <i>GL</i> is given in the NOTES section. If used without the <i>&#8211;immed</i> option then this utility, after the PT command finishes successfully, will call the RRTI command. When the RRTI command finishes, potentially with a new ROD Token, this utility will exit. Prior to that exit, if a new ROD Token is available and the <i>&#8211;rtf=RTF</i> option is given then that ROD Token is written to the <i>RTF</i> file. If the <i>&#8211;rtf=RTF</i> option is not given then the ROD token is written to a file called ddptctl_rod_tok.bin in the current directory.<br />
 If the <i>&#8211;immed</i> option is given this utility will exit after the PT command finishes. To complete the operation this utility should be invoked again with the <i>&#8211;poll</i> option and the same <i>DEVICE</i>.</p>
<dt><code>-R</code>, <code>&#8211;receive</code></p>
<dd>send the RECEIVE ROD TOKEN INFORMATION SCSI command (RRTI) to the <i>DEVICE</i> using the <i>LID</i> (i.e. from the <i>&#8211;list_id=LID</i> option). If the <i>&#8211;list_id=LID</i> option is not given then a <i>LID</i> of 257 is assumed.<br />
 If the originating xcopy command was POPULATE TOKEN and the RRTI command indicates that it has completed successfully then the associated ROD Token (returned in the RRTI response) is written to the <i>RTF</i> file. If the <i>&#8211;rtf=RTF</i> option is not given then the ROD token is written to a file called ddptctl_rod_tok.bin in the current directory.</p>
<dt><code>-r</code>, <code>&#8211;rtf</code>=<i>RTF</i></p>
<dd>when <i>RTF</i> is a file containing an ODX ROD Token or the name of a file the ROD Token is to be written to. A ROD Token used by ODX is 512 bytes long. If the <i>RTF</i> file was produced by the ddpt utility then it might contain multiple ROD Tokens, each optionally followed by an 8 byte integer containing the &quot;number of bytes represented&quot; by the preceding ROD Token.<br />
 If an <i>RTF</i> file with multiple ROD Tokens is given to this utility with <i>&#8211;wut=SL</i> then only the first ROD Token is used. If an <i>RTF</i> file is being decoded (i.e. no <i>DEVICE</i> argument given) then all ROD Tokens are decoded.</p>
<dt><code>-t</code>, <code>&#8211;rtype</code>=<i>RTYPE</i></p>
<dd>where <i>RTYPE</i> is the ROD Type, a field in the PT command (apart from &quot;zero&quot;). The default value (0) indicates that the copy manager (in the <i>DEVICE</i>) decides. <i>RTYPE</i> can be a decimal number, a hex number (prefixed by 0x or with a &quot;h&quot; appended) or one of &quot;pit-def&quot;, &quot;pit-vuln&quot;, &quot;pit-pers&quot;, &quot;pit-any&quot; or &quot;zero&quot;. The final truncated word can be spelt out (e.g. &quot;pit-vulnerable&quot;). The &quot;pit-&quot; lead-in stands for &quot;point in time&quot; copy.<br />
 The &quot;zero&quot; is a special case and is not given to a PT command. Instead it causes a special Block Device Zero Token to be created that can be used with the <i>&#8211;wut=SL</i> option to write blocks of zeros to the given <i>DEVICE</i>.</p>
<dt><code>-s</code>, <code>&#8211;size</code></p>
<dd>prints the number of blocks and the size of each block for the given <i>DEVICE</i>. Protection information is printed if available. By default uses the pass-through interface and the READ CAPACITY command to obtain this information. If the <i>&#8211;block</i> option is given then the block layer in the OS is query for size information (and protection information is not reported).</p>
<dt><code>-T</code>, <code>&#8211;timeout</code>=<i>ITO[,CMD]</i></p>
<dd>where <i>ITO</i> is the inactivity timeout (units: seconds) given to the PT command. The default is 0 in which case the copy manager uses its own default which is shown in the Third party Copy VPD page.<br />
 <i>CMD</i> is the SCSI command timeout (units: seconds) applied to SCSI commands issued by this utility; default is 0 which is translated to 600 seconds for originating xcopy commands (e.g. PT and WUT) and 60 seconds for other commands. Best not to trigger command timeouts.</p>
<dt><code>-v</code>, <code>&#8211;verbose</code></p>
<dd>increase the level of verbosity, (i.e. debug output).</p>
<dt><code>-V</code>, <code>&#8211;version</code></p>
<dd>print the version string and then exit.</p>
<dt><code>-w</code>, <code>&#8211;wut</code>=<i>SL</i></p>
<dd>send a WRITE USING TOKEN (WUT) command with the given scatter list. The format of <i>SL</i> is given in the NOTES section. This option requires the <i>&#8211;rtf=RTF</i> option to supply the ROD Token. If used without the <i>&#8211;immed</i> option then after the WUT command finishes successfully this utility will call the RRTI command. When the RRTI command finishes this utility will exit.<br />
 If the <i>&#8211;immed</i> option is given this utility will exit after the WUT command finishes. To complete the operation this utility should be invoked again with the <i>&#8211;poll</i> option and the same <i>DEVICE</i>.</dl>
<h2>Notes</h2>
<p>The scatter gather list given to the <i>&#8211;pt=GL</i> and <i>&#8211;wut=SL</i> options in the simplest case contains a pair a numbers, separated by a comma. The first number is the starting LBA and the second number is the number of blocks (no bigger than 32 bits) to read to or write from that starting LBA. Another pair of numbers can appear after that forming the second element of a scatter gather list. Starting LBAs can be in any order but T10 prohibits any logical block appearing more than once in a scatter gather list. </p>
<p> Scatter gather lists can be placed in a file or read from stdin. A file name referring to a file containing a scatter gather list must follow the &quot;@&quot; character (e.g. &#8211;pt=@my_sgl.txt&quot;). Reading a list from stdin is indicated by &quot;@-&quot; or &quot;-&quot; (e.g. &quot;&#8211;pt=-&quot;). Scatter gather lists in a file have a looser format and can take spaces and tabs as well as a comma as separators. Anything from and including a &quot;#&quot; on a line is ignored. </p>
<p> Both the PT and WUT commands are issued &quot;as is&quot; without checking the Third Party Copy VPD page. The copy manager may well reject these commands (with exit status 51: invalid field in parameter list) if the maximum range descriptors field or the maximum token transfer size field are exceeded. </p>
<p> There is a web page discussing ddptctl and ddpt, XCOPY and ODX at <a rel="nofollow" href="http://sg.danny.cz/sg/ddpt_xcopy_odx.html">http://sg.danny.cz/sg/ddpt_xcopy_odx.html</a></p>
<h2>Exit Status</h2>
<p>The exit status of ddptctl is 0 when it is successful. Otherwise the exit status for this utility is the same as that for ddpt. See the EXIT STATUS section in the ddpt man page.</p>
<h2>Examples</h2>
<p>First issue a PT command without the <i>&#8211;immed</i> option so RRTI is called to complete the operation: </p>
<pre><code># ddptctl --pt=0x0,10k,20k,5k --rtf=aa.rt /dev/sdb

PT completes with a transfer count of 15360 [0x3c00]</code></pre>
<p> The transfer count (10k + 5k == 15360) indicates the operation was successful and the ROD Token is in the aa.rt file. Now use that ROD Token to write to the same locations on /dev/sdc: # ddptctl &#8211;rtf=aa.rt &#8211;wut=0x0,10k,20k,5k /dev/sdc</p>
<p>WUT completes with a transfer count of 15360 [0x3c00] So the copy was successful. Now taking a closer look at the ROD token: #ddptctl&#8211; info&#8211; rtf = aa.rt</p>
<p>Decoding information from ROD Token:</p>
<p> ROD type: point in time copy &#8211; default [0x800000]</p>
<p> Copy manager ROD Token identifier: 0x520000710000000c</p>
<p> Creator Logical Unit descriptor:</p>
<p>Peripheral Device type: 0x0</p>
<p>Relative initiator port identifier: 0x0</p>
<p>designator_type: NAA,  code_set: Binary</p>
<p>associated with the addressed logical unit</p>
<p>0x60002ac0000000000000000c00009502</p>
<p> Number of bytes represented: 0 [0x0]</p>
<p> Device type specific data (for disk) has block size of 0;<br />
unlikely so skip</p>
<p>    Target device descriptor : unexpected designator type[0x0] T10 does not require implementations to supply much of the above (only the ROD type and the token length) so expect to see some empty fields. To see information about /dev/sdb relevant to ODX, try: # ddptctl &#8211;info /dev/sdb</p>
<p>/dev/sdb [readcap]: num_blks=209715200 [0xc800000], blk_size=512, 107 GB</p>
<p>3PC (third party copy) bit set in standard INQUIRY response</p>
<p>Third Party Copy VPD page:</p>
<p>Block Device ROD Token Limits:</p>
<p>Maximum Range Descriptors: 8</p>
<p>Maximum Inactivity Timeout: 60 seconds</p>
<p>Default Inactivity Timeout: 30 seconds</p>
<p>Maximum Token Transfer Size: 524288</p>
<p>Optimal Transfer Count: 524288 That maximum token transfer size [524288 blocks each 512 bytes gives 256 MB] is the largest size a ROD Token created by /dev/sdb can hold. Use that and show the <i>&#8211;immed</i> option on the destination: </p>
<pre><code># ddptctl --pt=0x0,0x80000 --rtf=aa.rt /dev/sdb

PT completes with a transfer count of 524288 [0x80000]
# ddptctl --rtf=aa.rt --wut=0x0,0x80000 --immed /dev/sdc

Started ODX Write Using Token command in immediate mode.

User may need --list_id=257 on following invocation with --receive or

--poll for completion
# ddptctl --poll --rtf=aa.rt /dev/sdc

RRTI for Write using token: Operation completed without errors


transfer count of 524288 [0x80000]</code></pre>
<p> To copy larger amounts and/or with a larger number of scatter gather elements (than 8 &quot;range descriptors&quot;) use one of the four ODX variants in the ddpt utility.</p>
