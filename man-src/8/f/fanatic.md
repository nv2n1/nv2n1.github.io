<p>fanatic &#8211; fan bridge configuration and test wizard</p>
<h2>Synopsis</h2>
<p><code>fanatic [&lt;cmd&gt; [&lt;arg&gt; &#8230;]]</code><br />
 <code>fanatic configure</code><br />
 <code>fanatic deconfigure</code><br />
 <code>fanatic test</code></p>
<h2>Description</h2>
<p><code>fanatic</code> is the configuration and test wizard for Fan networking. It is designed to simplify the process of configuring persistent Fan bridges. It will also configure both LXD and Docker to use those bridges as required. </p>
<p> It also can be used to configure Fan networking without any user interaction (see NON-INTERACTIVE USAGE below). </p>
<p> A Fan network is a mechanism for expanding the range of IP addresses available to a system. It is most useful for containers systems such as Docker and LXC/LXD, but it can be used in other contexts as well.</p>
<h2>Terminology</h2>
<p>The Fan mapping is defined by a combination of an <code>underlay</code> and an <code>overlay</code> address. Each of these is defined in CIDR network address form. The overlay prefix defines the overall network prefix for the overlay slice. The underlay prefix defines the prefix bits to strip to obtain the slice identifier. This is concatenated with the overlay prefix to calculate the <code>overlay slice</code> which is the range of the Fan network that is assigned to a specific single address within the underlay network. This way each address within a 192.168.0.0/16 underlay, mapped to a 250.0.0.0/8 overlay would cover the range: </p>
<pre><dl><dt><dd>250.x.y.0/(8 + (32-16) = 24)
</dl></pre>
<p>Thus 8 (32-24) address bits will equate to 254 additional addresses for each address mapped from the underlay network (you cannot use the first and last address within an IPv4 subnet). </p>
<p> The following diagram shows a more advanced example with three hosts which will be joined in a single Fan network. Two of the hosts are in the same subnet (192.168.12.0/24) and the other in a separate subnet (192.168.13.0/24). Since all three will share the same overlay network (250.0.0.0/8) we would use an underlay of 192.168.0.0/16. The choice of the underlay prefix depends on the network layout which is mapped into an overlay network (which overlay prefix is used does not matter). So, if we really only were interested in joining 192.168.12/13.0/24, we could use an underlay of 192.168.12.0/23 which would maximize the number of addresses per slice but the CIDR network addresses of the slices would be less obvious to read. </p>
<pre><dl><dt><dd>+-------------+
 ... ----+ Router +---------------------+
 +------+------+ |
 | |
 +------+------+ |
 | | |
+-------------+----+ +----+-------------+ +----+-------------+
| 192.168.12.13/24 | | 192.168.12.14/24 | | 192.168.13.13/24 |
+------------------+ +------------------+ +------------------+
 . . .
 . . .
 +----------------+ +----------------+ +----------------+
 | 250.12.13.1/24 | | 250.12.14.1/24 | | 250.13.13.1/24 |
 +----------------+ +----------------+ +----------------+
 | 250.0.0.0/8 |
 +------------------------------------------------------+
</dl></pre>
<p>For the example above, a /16 over /8 layout was chosen because that moves numbers in the dotted decimal notation in a way that is simpler to read. </p>
<p> The overlay prefix is 8 bits. The underlay prefix takes the lower 16 bits of each host’s physical interface and shifts those left until hitting the least significant bit of the overlay (32-16-8=8). The result is, each interface of the host that is part of the Fan overlay gets a /24 (=8+16) slice of the Fan network. The 250.x.y.1 address is assigned to the fan-250 bridge on each host and would act as the <code>gateway</code> address of any container that runs within the overlay slice.</p>
<h2>Command Syntax</h2>
<p>Running <code>fanatic</code> with no arguments is equivalent to running <code>fanatic configure</code>.</p>
<dl>
<dt><code>fanatic [configure]</code></p>
<dd>Interactively configure the local system for Fan. This action will identify the interface to be used and offer to configure an appropriate Fan over the addresses on that interface. It will further offer to configure LXD and/or Docker to use this interface. Finally, it will offer to test the configuration as applied both locally and with an optional remote host.</p>
<dt><code>fanatic deconfigure</code></p>
<dd>Reverses the interactive configuration above. It will deconfigure both LXD and Docker (if configured) and then deconfigure the Fan. These steps are only performed if the configuration was generated by <code>fanatic</code>.</p>
<dt><code>fanatic test</code></p>
<dd>Runs the testing phase of the interactive setup. This action enables retesting of a previously configured system. Only those pieces configured will be tested.</p>
<dt><code>fanatic help</code></p>
<dd>Shows basic help including usage information and pointers to further help on use of <code>fanatic</code>.</dl>
<h2>Non-Interactive Usage</h2>
<p>It is possible to run any sub-phase of the configure, deconfigure or test phases, which are done by <code>fanatic</code> in interactive mode, individually and without user interaction:</p>
<dl>
<dt><code>fanatic enable-fan -u &lt;underlay&gt; -o &lt;overlay&gt;</code></p>
<dd>Configure a Fan over the specified interface.</p>
<dt><code>fanatic disable-fan -u &lt;underlay&gt; -o &lt;overlay&gt; </code></p>
<dd>Deconfigure a Fan over the specified interface.</p>
<dt><code>fanatic enable-lxd -u &lt;underlay&gt; -o &lt;overlay&gt; </code></p>
<dd>Configure LXD for use on the Fan over the specified interface.</p>
<dt><code>fanatic disable-lxd -u &lt;underlay&gt; -o &lt;overlay&gt; </code></p>
<dd>Deconfigure LXD for use on the Fan over the specified interface.</p>
<dt><code>fanatic enable-docker -u &lt;underlay&gt; -o &lt;overlay&gt; </code></p>
<dd>Configure docker for use on the Fan over the specified interface.</p>
<dt><code>fanatic disable-docker -u &lt;underlay&gt; -o &lt;overlay&gt; </code></p>
<dd>Deconfigure docker for use on the Fan over the specified interface.</p>
<dt><code>test-host -u &lt;underlay&gt; -o &lt;overlay&gt; -r &lt;remote host IP&gt;</code></p>
<dd>Test host-to-host Fan functionality. This requires you to be running the same test script on both hosts in the test.</p>
<dt><code>test-local-lxd -u &lt;underlay&gt; -o &lt;overlay&gt; </code></p>
<dd>Test the local LXD configuration by creating a container and running host-to-host testing against that container.</p>
<dt><code>test-local-docker -u &lt;underlay&gt; -o &lt;overlay&gt; </code></p>
<dd>Test the local Docker configuration by creating a container and running host-to-host testing against that container.</dl>
<h2>Use With Lxc/Lxd</h2>
<p>Once the Fan bridges are configured (and LXD is installed), LXC/LXD can be configured to use a specific Fan bridge for the network device of containers. This can be done by either modifying the default template or by creating a separate template which can be used when creating containers. The latter is what <code>fanatic enable-lxd</code> does internally. The same could be done manually by setting link and MTU as shown below: </p>
<pre><dl><dt><dd>lxc.network.link = &lt;Fan bridge name&gt;
lxc.network.mtu = 1450
</dl></pre>
<p>.&quot;</p>
<h2>Use With Docker</h2>
<p>Once the Fan bridges are configured (and docker installed), a docker network must be configured (similar to the LXD template). New containers can then be configured to use the Fan network. This is how the <code>fanatic enable-docker</code> call internally works. The new network will be a bridge network type named after the name of the Fan bridge which is to be used. If this were done manually, the docker command would look like: </p>
<pre><dl><dt><dd># sudo docker network create --driver bridge \
 -o &quot;com.docker.network.bridge.name=&lt;bridge name&gt;&quot; \
 -o &quot;com.docker.network.driver.mtu=1450&quot; \
 --subnet &lt;overlay&gt; --ip-range &lt;slice subnet&gt; \
 --gateway &lt;slice host&gt; \
 --aux-address &quot;reserved0=&lt;slice host&gt;&quot; \
 &lt;bridge name&gt;
</dl></pre>
<p>This defines the complete Fan overlay network to be accessed through the Fan bridge given and limits the scope of addresses used for containers to a given <code>slice subnet</code> (which is the CIDR notation of the Fan overlay slice that is assigned to the given Fan bridge). All addresses, within that range, which are not to be used need to be declared individually. Usually this is the <code>slice host</code> which is the address of the host within the overlay slice (and assigned to the Fan bridge). For example, if the overlay network were a 250.0.0.0/8 and the address of the host in the underlay address space were u.u.x.y/16 the Fan bridge would be called fan-250 and have a 250.x.y.1/24 assigned to it which would be declared as the gateway for the 250.x.y.0/24 overlay slice.</p>
<h2>Limitations</h2>
<p>Since docker (at the time of writing) does not support to allow an external DHCP service to be used, there is no way to safely mix docker and LXD containers in the same Fan overlay slice. Both types of containers can be mixed though in the same Fan overlay, as long as they use their individual slice.</p>
<h2>Examples</h2>
<p>Assuming that a Fan network should be attached to the primary interface of the host without any user interaction, the first step is to figure out which is the default interface: </p>
<pre><dl><dt><dd># ip route show | awk '$1 == &quot;default&quot;{print $NF}'
ens3
</dl></pre>
<p>Next we need to find out what IPv4 address this interface is configured to: </p>
<pre><dl><dt><dd># ip address show ens3 | awk '$1 == &quot;inet&quot;{print $2}'
192.168.2.120/24
</dl></pre>
<p>If all hosts which participate in the Fan network are located in 192.168.2.0/24, then we can use a /24 underlay address and get 65535 addresses per slice instead of the 254 if we had to include hosts from the 192.168.0.0/16 range. </p>
<p> For all of the following commands of this example we use the address of the interface with a prefix of 20 which assumes we only care for hosts in 192.168.[0-15].0/24 and results in 4095 addresses per slice. Using the interface address tells fanatic to only configure this single interface. </p>
