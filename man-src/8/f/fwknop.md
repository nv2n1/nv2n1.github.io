<p>fwknop &#8211; Firewall Knock Operator</p>
<h2>Synopsis</h2>
<p><code>fwknop</code> <code>-A</code> &lt;&#8216;proto/ports&#8217;&gt; <code>-R</code>|<code>-a</code>|<code>-s -D</code> &lt;&#8216;host&#8217;&gt; [<i>options</i>]</p>
<h2>Description</h2>
<p><code>fwknop</code> implements an authorization scheme known as Single Packet Authorization (SPA) for strong service concealment. SPA requires only a single packet which is encrypted, non-replayable, and authenticated via an HMAC in order to communicate desired access to a service that is hidden behind a firewall in a default-drop filtering stance. The main application of SPA is to use a firewall to drop all attempts to connect to services such as <i>SSH</i> in order to make the exploitation of vulnerabilities (both 0-day and unpatched code) more difficult. Any service that is concealed by SPA naturally cannot be scanned for with <i>Nmap</i>. The fwknop project supports three different firewalls: <i>iptables</i> on Linux systems, <i>pf</i> on OpenBSD, and <i>ipfw</i> on FreeBSD and Mac OS X. </p>
<p> SPA is essentially next generation Port Knocking (PK), but solves many of the limitations exhibited by PK while retaining its core benefits. PK limitations include a general difficulty in protecting against replay attacks, asymmetric ciphers and HMAC schemes are not usually possible to reliably support, and it is trivially easy to mount a DoS attack against a PK server just by spoofing an additional packet into a PK sequence as it traverses the network (thereby convincing the PK server that the client doesn&#8217;t know the proper sequence). All of these limitation are solved by SPA. At the same time, SPA hides services behind a default-drop firewall policy, acquires SPA data passively (usually via libpcap or other means), and implements standard cryptographic operations for SPA packet authentication and encryption/decryption. </p>
<p> This is the manual page for the <code>fwknop</code> client which is responsible for constructing SPA packets and sending them over the network. The server side is implemented by the <code>fwknopd</code> daemon which sniffs the network for SPA packets and interacts with the local firewall to allow SPA authenticated connections. It is recommended to read the <i><a href="/docs/linux/man/8-fwknopd/">fwknopd</a>(8)</i> manual page as well. </p>
<p> SPA packets generated by <code>fwknop</code> leverage HMAC for authenticated encryption in the encrypt-then-authenticate model. Although the usage of an HMAC is currently optional (enabled via the <code>&#8211;use-hmac</code> command line switch), it is highly recommended for three reasons: <i>1)</i> without an HMAC, cryptographically strong authentication is not possible with <code>fwknop</code> unless GnuPG is used, but even then an HMAC should still be applied, <i>2)</i> an HMAC applied after encryption protects against cryptanalytic CBC-mode padding oracle attacks such as the Vaudenay attack and related trickery (like the more recent &quot;Lucky 13&quot; attack against SSL), and <i>3)</i> the code required by the <code>fwknopd</code> daemon to verify an HMAC is much more simplistic than the code required to decrypt an SPA packet, so an SPA packet without a proper HMAC isn&#8217;t even sent through the decryption routines. Reason <i>3)</i> is why an HMAC should still be used even when SPA packets are encrypted with GnuPG due to the fact that SPA data is not sent through <code>libgpgme</code> functions unless the HMAC checks out first. GnuPG and libgpgme are relatively complex bodies of code, and therefore limiting the ability of a potential attacker to interact with this code through an HMAC operation helps to maintain a stronger security stance. Generating an HMAC for SPA communications requires a dedicated key in addition to the normal encryption key, and both can be generated with the <code>&#8211;key-gen</code> option. </p>
<p> <code>fwknop</code> encrypts SPA packets either with the <i>Rijndael</i> block cipher or via <i>GnuPG</i> and associated asymmetric cipher. If the symmetric encryption method is chosen, then as usual the encryption key is shared between the client and server (see the <code>fwknopd</code> <i>/etc/fwknop/access.conf</i> file for details). The actual encryption key used for Rijndael encryption is generated via the standard PBKDF1 key derivation algorithm, and CBC mode is set. If the GnuPG method is chosen, then the encryption keys are derived from GnuPG key rings. SPA packets generated by fwknop running as a client adhere to the following format (before encryption and the HMAC is applied): </p>
<dl>
<dd>
<pre> random data (16 digits)
 username
 timestamp
 software version
 mode (command mode (0) or access mode (1))
 if command mode =&gt; command to execute
 else access mode =&gt; IP,proto,port
 message digest (SHA512 / SHA384 / SHA256 / SHA1 / MD5)</pre>
</dl>
<p> Each of the above fields are separated by a &quot;:&quot; character due to the variable length of several of the fields, and those that might contain &quot;:&quot; characters are base64 encoded. The message digest (<code>SHA256</code> by default) is part of the data to be encrypted and is independent of the HMAC which is appended to the SPA packet data after encryption. The 16 digits of random data (about 53 bits) ensures that no two SPA packets are identical, and this is in addition to and independent of using PBKDF1 for key derivation for Rijndael in CBC mode (which uses an 8-byte random &quot;salt&quot; value). Because <code>fwknopd</code> tracks the SHA256 digest of all incoming valid SPA packets and throws out duplicates, replay attacks are not feasible against <code>fwknop</code>. Syslog alerts are generated if a replay is detected. </p>
<p> By default, the <code>fwknop</code> client sends authorization packets over UDP port 62201, but this can be altered with the <code>&#8211;server-port</code> argument (this requires <code>fwknopd</code> to be configured to acquire SPA data over the selected port). Also, <code>fwknop</code> can send the SPA packet over a random port via the <code>&#8211;rand-port</code> argument. See <i><a href="/docs/linux/man/8-fwknopd/">fwknopd</a>(8)</i> for further details. See the <code>EXAMPLES</code> section for example invocations of the <code>fwknop</code> client. </p>
<p> The <code>fwknop</code> client is quite portable, and is known to run on various Linux distributions (all major distros and embedded ones such as OpenWRT as well), FreeBSD, OpenBSD, and Cygwin on Windows. There is also a library <code>libfko</code> that both <code>fwknop</code> and <code>fwknopd</code> use for SPA packet encryption/decryption and HMAC authentication operations. This library can be used to allow third party applications to use SPA subject to the terms of the GNU Public License (GPL).</p>
<h2>Required Arguments</h2>
<p>These required arguments can be specified via command-line or from within the <i>~/.fwknoprc</i> file (see <i>-n, &#8211;named-config</i> option and the FWKNOPRC FILE section below). </p>
<p> <code>-A, &#8211;access</code>=<i>&lt;port list&gt;</i></p>
<dl>
<dd>Provide a list of ports and protocols to access on a remote computer running <code>fwknopd</code>. The format of this list is &#8220;+&lt;proto&gt;/&lt;port&gt;&#8230;&lt;proto&gt;/&lt;port&gt;+&#8221;, e.g. &#8220;tcp/22,udp/53&#8221;. <code>NOTE:</code> The vast majority of usages for <code>fwknop</code> require the <code>-A</code> argument, but sending full commands with the <code>&#8211;server-cmd</code> argument via an SPA packet to be executed by <code>fwknopd</code> does not require this argument.</dl>
<p> <code>-D, &#8211;destination</code>=<i>&lt;hostname/IP-address&gt;</i></p>
<dl>
<dd>Direct the <code>fwknop</code> client to authenticate with the <code>fwknopd</code> daemon/service at the specified destination hostname or IP address. The connection mode is discovered by the <code>fwknopd</code> daemon/service when it decrypts and parses the authentication packet.</dl>
<p> <code>-R|-a|-s</code></p>
<dl>
<dd>One of these options (see below) is required to tell the remote <code>fwknopd</code> daemon what IP should be allowed through the firewall. It is recommend to use the <code>-R</code> or <code>-a</code> options instead of <code>-s</code> in order to harden SPA communications against possible <i>Man-In-The-Middle</i> (MITM) attacks, and on the server side set <i>REQUIRE_SOURCE_ADDRESS</i> variable in the <i>/etc/fwknop/access.conf</i> file. Note that the most secure option is <code>-a</code> so that <code>fwknop</code> does not have to issue any HTTPS request to <i><a rel="nofollow" href="https://www.cipherdyne.org/cgi-bin/myip">https://www.cipherdyne.org/cgi-bin/myip</a></i> in order to resolve the externally routable IP address. Using <code>-a</code> requires that the user already knows what the external IP is for the network where fwknop is running.</dl>
<h2>General Options</h2>
<p><code>-h, &#8211;help</code></p>
<dl>
<dd>Print a usage summary message and exit.</dl>
<p> <code>-G, &#8211;get-key</code>=<i>&lt;file&gt;</i></p>
<dl>
<dd>Load an encryption key/password from the specified file. The key file contains a line for each destination hostname or IP address, a colon (&quot;:&quot;), optional space and the password, followed by a newline. Note that the last line has to have a terminating newline character. Also note: though this is a convenience, having a file on your system with clear text passwords is not a good idea and is not recommended. Having the <code>fwknop</code> client prompt you for the key is generally more secure. Note also that if a key is stored on disk, the <code>fwknop</code> rc file is a more powerful mechanism for specifying not only the key but other options as well.</dl>
<p> <code>&#8211;stdin</code></p>
<dl>
<dd>Read the encryption key/password from stdin. This can be used to send the data via a pipe for example. This command is similar to &#8211;fd 0.</dl>
<p> <code>&#8211;fd</code>=<i>&lt;number&gt;</i></p>
<dl>
<dd>Specify the file descriptor number to read the key/password from. This command avoids the user being prompted for a password if none has been found in the user specific stanza, or none has been supplied on the command line. A file descriptor set to 0 is similar to the stdin command.</dl>
<p> <code>&#8211;get-hmac-key</code>=<i>&lt;file&gt;</i></p>
<dl>
<dd>Load an HMAC key/password from the specified file. Similarly to the format for the <code>&#8211;get-key</code> option, the HMAC key file contains a line for each destination hostname or IP address, a colon (&quot;:&quot;), optional space and the password, followed by a newline. Note that the last line has to have a terminating newline character. Also note: though this is a convenience, having a file on your system with clear text passwords is not a good idea and is not recommended. Having the <code>fwknop</code> client prompt you for the HMAC key is generally more secure. Note also that if a key is stored on disk, the <code>fwknop</code> rc file is a more powerful mechanism for specifying not only the HMAC key but other options as well.</dl>
<p> <code>&#8211;key-gen</code></p>
<dl>
<dd>Have <code>fwknop</code> generate both Rijndael and HMAC keys that can be used for SPA packet encryption and authentication. These keys are derived from /dev/urandom and then base64 encoded before being printed to stdout, and are meant to be included within the &#8220;$HOME/.fwknoprc&#8221; file (or the file referenced by <code>&#8211;get-key</code>). Such keys are generally more secure than passphrases that are typed in from the command line.</dl>
<p> <code>&#8211;key-gen-file</code>=<i>&lt;file&gt;</i></p>
<dl>
<dd>Write generated keys to the specified file. Note that the file is overwritten if it already exists. If this option is not given, then <code>&#8211;key-gen</code> writes the keys to stdout.</dl>
<p> <code>&#8211;key-len</code>=<i>&lt;length&gt;</i></p>
<dl>
<dd>Specify the number of bytes for a generated Rijndael key. The maximum size is currently 128 bytes.</dl>
<p> <code>&#8211;hmac-key-len</code>=<i>&lt;length&gt;</i></p>
<dl>
<dd>Specify the number of bytes for a generated HMAC key. The maximum size is currently 128 bytes.</dl>
<p> <code>-l, &#8211;last-cmd</code></p>
<dl>
<dd>Execute <code>fwknop</code> with the command-line arguments from the previous invocation (if any). The previous arguments are parsed out of the <i>~/.fwknop.run</i> file.</dl>
<p> <code>-n, &#8211;named-config</code>=<i>&lt;stanza name&gt;</i></p>
<dl>
<dd>Specify the name of the configuration stanza in the &#8220;$HOME/.fwknoprc&#8221; file to pull configuration and command directives. These named stanzas alleviate the need for remembering the various command-line arguments for frequently used invocations of <code>fwknop</code>. See the section labeled, FWKNOPRC FILE below for a list of the valid configuration directives in the <i>.fwknoprc</i> file.</dl>
<p> <code>&#8211;key-rijndael</code>=<i>&lt;key&gt;</i></p>
<dl>
<dd>Specify the Rijndael key on the command line. Since the key may be visible to utilities such as <i>ps</i> under Unix, this form should only be used where security is not critical. Having the <code>fwknop</code> client either prompt you for the key or acquire via the &#8220;$HOME/.fwknoprc&#8221; file is generally more secure.</dl>
<p> <code>&#8211;key-base64-rijndael</code>=<i>&lt;key&gt;</i></p>
<dl>
<dd>Specify the base64 encoded Rijndael key. Since the key may be visible to utilities such as <i>ps</i> under Unix, this form should only be used where security is not critical. Having the <code>fwknop</code> client either prompt you for the key or acquire via the &#8220;$HOME/.fwknoprc&#8221; file is generally more secure.</dl>
<p> <code>&#8211;key-base64-hmac</code>=<i>&lt;key&gt;</i></p>
<dl>
<dd>Specify the base64 encoded HMAC key. Since the key may be visible to utilities such as <i>ps</i> under Unix, this form should only be used where security is not critical. Having the <code>fwknop</code> client either prompt you for the key or acquire via the &#8220;$HOME/.fwknoprc&#8221; file is generally more secure.</dl>
<p> <code>&#8211;key-hmac</code>=<i>&lt;key&gt;</i></p>
<dl>
<dd>Specify the raw HMAC key (not base64 encoded). Since the key may be visible to utilities such as <i>ps</i> under Unix, this form should only be used where security is not critical. Having the <code>fwknop</code> client either prompt you for the key or acquire via the &#8220;$HOME/.fwknoprc&#8221; file is generally more secure.</dl>
<p> <code>&#8211;rc-file</code>=<i>&lt;file&gt;</i></p>
<dl>
<dd>Specify path to the fwknop rc file (default is $HOME/.fwknoprc).</dl>
<p> <code>&#8211;save-rc-stanza</code>=<i>&lt;stanza name&gt;</i></p>
<dl>
<dd>Save command line arguments to the $HOME/.fwknoprc stanza specified with the <code>-n</code> option. If the <code>-n</code> option is omitted, then the stanza name will default to the destination server value (hostname or IP) given with the <code>-D</code> argument.</dl>
<p> <code>&#8211;force-stanza</code></p>
<dl>
<dd>Used with <code>&#8211;save-rc-stanza</code> to overwrite all of the variables for the specified stanza</dl>
<p> <code>&#8211;stanza-list</code></p>
<dl>
<dd>Dump a list of the stanzas found in &#8220;$HOME/.fwknoprc&#8221;.</dl>
<p> <code>&#8211;show-last</code></p>
<dl>
<dd>Display the last command-line arguments used by <code>fwknop</code>.</dl>
<p> <code>-E, &#8211;save-args-file</code>=<i>&lt;file&gt;</i></p>
<dl>
<dd>Save command line arguments to a specified file path. Without this option, and when <code>&#8211;no-save-args</code> is not also specified, then the default save args path is <i>~/.fwknop.run</i>.</dl>
<p> <code>&#8211;no-save-args</code></p>
<dl>
<dd>Do not save the command line arguments given when <code>fwknop</code> is executed.</dl>
<p> <code>-T, &#8211;test</code></p>
<dl>
<dd>Test mode. Generate the SPA packet data, but do not send it. Instead, print a break-down of the SPA data fields, then run the data through the decryption and decoding process and print the break-down again. This is primarily a debugging feature.</dl>
<p> <code>-B, &#8211;save-packet</code>=<i>&lt;file&gt;</i></p>
<dl>
<dd>Instruct the <code>fwknop</code> client to write a newly created SPA packet out to the specified file so that it can be examined off-line.</dl>
<p> <code>-b, &#8211;save-packet-append</code></p>
<dl>
<dd>Append the generated packet data to the file specified with the <code>-B</code> option.</dl>
<p> <code>&#8211;fault-injection-tag</code>=<i>&lt;tag&gt;</i></p>
<dl>
<dd>This option is only used for fault injection testing when <code>fwknop</code> is compiled to support the libfiu library (see: <i><a rel="nofollow" href="http://blitiri.com.ar/p/libfiu/">http://blitiri.com.ar/p/libfiu/</a></i>). Under normal circumstances this option is not used, and any packaged version of fwknop will not have code compiled in so this capability is not enabled at run time. It is documented here for completeness.</dl>
<p> <code>-v, &#8211;verbose</code></p>
<dl>
<dd>Run the <code>fwknop</code> client in verbose mode. This causes <code>fwknop</code> to print some extra information about the current command and the resulting SPA data.</dl>
<p> <code>-V, &#8211;version</code></p>
<dl>
<dd>Display version information and exit.</dl>
<h2>Spa Options</h2>
<p><code>&#8211;use-hmac</code></p>
<dl>
<dd>Set HMAC mode for authenticated encryption of SPA communications. As of <code>fwknop</code> 2.5, this is an optional feature, but this will become the default in a future release.</dl>
<p> <code>-a, &#8211;allow-ip</code>=<i>&lt;IP-address&gt;</i></p>
<dl>
<dd>Specify IP address that should be permitted through the destination <code>fwknopd</code> server firewall (this IP is encrypted within the SPA packet itself). This is useful to prevent a MITM attack where a SPA packet can be intercepted en-route and sent from a different IP than the original. Hence, if the <code>fwknopd</code> server trusts the source address on the SPA packet IP header then the attacker gains access. The <code>-a</code> option puts the source address within the encrypted SPA packet, and so thwarts this attack. The <code>-a</code> option is also useful to specify the IP that will be granted access when the SPA packet itself is spoofed with the <code>&#8211;spoof-src</code> option. Another related option is <code>-R</code> (see below) which instructs the <code>fwknop</code> client to automatically resolve the externally routable IP address the local system is connected to by querying <i><a rel="nofollow" href="https://www.cipherdyne.org/cgi-bin/myip">https://www.cipherdyne.org/cgi-bin/myip</a></i>. This returns the actual IP address it sees from the calling system.</dl>
<p> <code>-g, &#8211;gpg-encryption</code></p>
<dl>
<dd>Use GPG encryption on the SPA packet (default if not specified is Rijndael). <code>Note:</code> Use of this option will also require a GPG recipient (see <code>&#8211;gpg-recipient</code> along with other GPG-related options below).</dl>
<p> <code>&#8211;hmac-digest-type</code>=<i>&lt;digest&gt;</i></p>
<dl>
<dd>Set the HMAC digest algorithm for authenticated encryption of SPA packets. Choices are: <code>MD5</code>, <code>SHA1</code>, <code>SHA256</code> (the default), <code>SHA384</code>, and <code>SHA512</code>.</dl>
<p> <code>-N, &#8211;nat-access</code>=<i>&lt;internalIP:forwardPort&gt;</i></p>
<dl>
<dd>The <code>fwknopd</code> server offers the ability to provide SPA access through an iptables firewall to an internal service by interfacing with the iptables NAT capabilities. So, if the <code>fwknopd</code> server is protecting an internal network on an RFC-1918 address space, an external <code>fwknop</code> client can request that the server port forward an external port to an internal IP, i.e. &#8220;+&#8211;NAT-access 192.168.10.2,55000+&#8221;. In this case, access will be granted to 192.168.10.2 via port 55000 to whatever service is requested via the <code>&#8211;access</code> argument (usually tcp/22). Hence, after sending such an SPA packet, one would then do &#8220;ssh -p 55000 user [at] host&#8221; and the connection would be forwarded on through to the internal 192.168.10.2 system automatically. Note that the port &#8220;55000&#8221; can be randomly generated via the <code>&#8211;nat-rand-port</code> argument (described later).</dl>
<p> <code>&#8211;nat-local</code></p>
<dl>
<dd>On the <code>fwknopd</code> server, a NAT operation can apply to the local system instead of being forwarded through the system. That is, for iptables firewalls, a connection to, say, port 55,000 can be translated to port 22 on the local system. By making use of the <code>&#8211;nat-local</code> argument, the <code>fwknop</code> client can be made to request such access. This means that any external attacker would only see a connection over port 55,000 instead of the expected port 22 after the SPA packet is sent.</dl>
<p> <code>&#8211;nat-port</code></p>
<dl>
<dd>Usually <code>fwknop</code> is used to request access to a specific port such as tcp/22 on a system running <code>fwknopd</code>. However, by using the <code>&#8211;nat-port</code> argument, it is possible to request access to a (again, such as tcp/22), but have this access granted via the specified port (so, the <code>-p</code> argument would then be used on the <i>SSH</i> client command line). See the <code>&#8211;nat-local</code> and <code>&#8211;nat-access</code> command line arguments to <code>fwknop</code> for additional details on gaining access to services via a NAT operation.</dl>
<p> <code>&#8211;nat-rand-port</code></p>
<dl>
<dd>Usually <code>fwknop</code> is used to request access to a specific port such as tcp/22 on a system running <code>fwknopd</code>. However, by using the <code>&#8211;nat-rand-port</code> argument, it is possible to request access to a particular service (again, such as tcp/22), but have this access granted via a random translated port. That is, once the <code>fwknop</code> client has been executed in this mode and the random port selected by <code>fwknop</code> is displayed, the destination port used by the follow-on client must be changed to match this random port. For <i>SSH</i>, this is accomplished via the <code>-p</code> argument. See the <code>&#8211;nat-local</code> and <code>&#8211;nat-access</code> command line arguments to <code>fwknop</code> for additional details on gaining access to services via a NAT operation.</dl>
<p> <code>-p, &#8211;server-port</code>=<i>&lt;port&gt;</i></p>
<dl>
<dd>Specify the port number where <code>fwknopd</code> accepts packets via libpcap or ulogd pcap writer. By default <code>fwknopd</code> looks for authorization packets over UDP port 62201.</dl>
<p> <code>-P, &#8211;server-proto</code>=<i>&lt;protocol&gt;</i></p>
<dl>
<dd>Set the protocol (udp, tcp, http, udpraw, tcpraw, or icmp) for the outgoing SPA packet. Note: The <code>udpraw</code>, <code>tcpraw</code>, and <code>icmp</code> modes use raw sockets and thus require root access to run. Also note: The <code>tcp</code> mode expects to establish a TCP connection to the server before sending the SPA packet. This is not normally done, but is useful for compatibility with the Tor for strong anonymity; see <i><a rel="nofollow" href="http://tor.eff.org/">http://tor.eff.org/</a></i>. In this case, the <code>fwknopd</code> server will need to be configured to listen on the target TCP port (which is 62201 by default).</dl>
<p> <code>-Q, &#8211;spoof-src</code>=<i>&lt;IP&gt;</i></p>
<dl>
<dd>Spoof the source address from which the <code>fwknop</code> client sends SPA packets. This requires root on the client side access since a raw socket is required to accomplish this. Note that the <code>&#8211;spoof-user</code> argument can be given in this mode in order to pass any <code>REQUIRE_USERNAME</code> keyword that might be specified in <i>/etc/fwknop/access.conf</i>.</dl>
<p> <code>-r, &#8211;rand-port</code></p>
<dl>
<dd>Instruct the <code>fwknop</code> client to send an SPA packet over a random destination port between 10,000 and 65535. The <code>fwknopd</code> server must use a <code>PCAP_FILTER</code> variable that is configured to accept such packets. For example, the <code>PCAP_FILTER</code> variable could be set to: &#8220;+udp dst portrange 10000-65535+&#8221;.</dl>
<p> <code>-R, &#8211;resolve-ip-https</code></p>
<dl>
<dd>This is an important option, and instructs the <code>fwknop</code> client to issue an HTTPS request to a script running on <i>cipherdyne.org</i> that returns the client&#8217;s IP address (as seen by the web server). In some cases, this is needed to determine the IP address that should be allowed through the firewall policy at the remote <code>fwknopd</code> server side. This option is useful if the <code>fwknop</code> client is being used on a system that is behind an obscure NAT address, and the external Internet facing IP is not known to the user. The full resolution URL is: <i><a rel="nofollow" href="https://www.cipherdyne.org/cgi-bin/myip">https://www.cipherdyne.org/cgi-bin/myip</a></i>, and is accessed by <code>fwknop</code> via <i>wget</i> in <code>&#8211;secure-protocol</code> mode. Note that it is generally more secure to use the <code>-a</code> option if the externally routable IP address for the client is already known to the user since this elminates the need for <code>fwknop</code> to issue any sort of HTTPS request.</dl>
<p> <code>&#8211;resolve-url</code> <i>&lt;url&gt;</i></p>
<dl>
<dd>Override the default URL used for resolving the source IP address. For best results, the URL specified here should point to a web service that provides just an IP address in the body of the HTTP response.</dl>
<p> <code>&#8211;resolve-http-only</code></p>
<dl>
<dd>This option forces the <code>fwknop</code> client to resolve the external IP via HTTP instead of HTTPS. There are some circumstances where this might be necessary such as when <i>wget</i> is not available (or hasn&#8217;t been compiled with SSL support), but generally this is not recommeded since it opens the possibility of a MITM attack through manipulation of the IP resolution HTTP response. Either specify the IP manually with <code>-a</code>, or use <code>-R</code> and omit this option.</dl>
<p> <code>-w, &#8211;wget-cmd</code>=<i>&lt;wget full path&gt;</i></p>
<dl>
<dd>Manually set the full path to the <i>wget</i> command. Normally the <i>configure</i> script finds the <i>wget</i> command, but this option can be used to specify the path if it is located in a non-standard place.</dl>
<p> <code>-s, &#8211;source-ip</code></p>
<dl>
<dd>Instruct the <code>fwknop</code> client to form an SPA packet that contains the special-case IP address &#8220;+0.0.0.0+&#8221; which will inform the destination <code>fwknopd</code> SPA server to use the source IP address from which the SPA packet originates as the IP that will be allowed through upon modification of the firewall ruleset. This option is useful if the <code>fwknop</code> client is deployed on a machine that is behind a NAT device and the external IP is not known. However, usage of this option is not recommended, and either the <code>-a</code> or <code>-R</code> options should be used instead. The permit-address options <code>-s</code>, <code>-R</code> and <code>-a</code> are mutually exclusive.</dl>
<p> <code>-S, &#8211;source-port</code>=<i>&lt;port&gt;</i></p>
<dl>
<dd>Set the source port for outgoing SPA packet.</dl>
<p> <code>-f, &#8211;fw-timeout</code>=<i>&lt;seconds&gt;</i></p>
<dl>
<dd>Specify the length of time (seconds) that the remote firewall rule that grants access to a service is to remain active. The default maintained by <code>fwknopd</code> is 30 seconds, but any established connection can be kept open after the initial accept rule is deleted through the use of a connection tracking mechanism that may be offered by the firewall.</dl>
<p> <code>-C, &#8211;server-cmd</code>=<i>&lt;command to execute&gt;</i></p>
<dl>
<dd>Instead of requesting access to a service with an SPA packet, the <code>&#8211;server-cmd</code> argument specifies a command that will be executed by the <code>fwknopd</code> server. The command is encrypted within the SPA packet and sniffed off the wire (as usual) by the <code>fwknopd</code> server.</dl>
<p> <code>-H, &#8211;http-proxy</code>=<i>&lt;proxy-host&gt;[:port]</i></p>
<dl>
<dd>Specify an HTTP proxy that the <code>fwknop</code> client will use to send the SPA packet through. Using this option will automatically set the SPA packet transmission mode (usually set via the <code>&#8211;server-proto</code> argument) to &quot;http&quot;. You can also specify the proxy port by adding &quot;:&lt;port&gt;&quot; to the proxy host name or ip.</dl>
<p> <code>-m, &#8211;digest-type</code>=<i>&lt;digest&gt;</i></p>
<dl>
<dd>Specify the message digest algorithm to use in the SPA data. Choices are: <code>MD5</code>, <code>SHA1</code>, <code>SHA256</code> (the default), <code>SHA384</code>, and <code>SHA512</code>.</dl>
<p> <code>-M, &#8211;encryption-mode</code>=<i>&lt;mode&gt;</i></p>
<dl>
<dd>Specify the encryption mode when AES is used for encrypting SPA packets. The default is CBC mode, but others can be chosen such as CFB or OFB as long as this is also specified in the <i>/etc/fwknop/access.conf</i> file on the server side via the ENCRYPTION_MODE variable. In general, it is recommended to not include this argument and let the default (CBC) apply. Note that the string &#8220;legacy&#8221; can be specified in order to generate SPA packets with the old initialization vector strategy used by versions of <code>fwknop</code> prior to 2.5. With the 2.5 release, <code>fwknop</code> generates initialization vectors in a manner that is compatible with OpenSSL via the PBKDF1 algorithm.</dl>
<p> <code>&#8211;time-offset-plus</code>=<i>&lt;time&gt;</i></p>
<dl>
<dd>By default, the <code>fwknopd</code> daemon on the server side enforces time synchronization between the clocks running on client and server systems. The <code>fwknop</code> client places the local time within each SPA packet as a time stamp to be validated by the fwknopd server after decryption. However, in some circumstances, if the clocks are out of sync and the user on the client system does not have the required access to change the local clock setting, it can be difficult to construct and SPA packet with a time stamp the server will accept. In this situation, the <code>&#8211;time-offset-plus</code> option can allow the user to specify an offset (e.g. &#8220;60sec&#8221; &#8220;60min&#8221; &#8220;2days&#8221; etc.) that is added to the local time.</dl>
<p> <code>&#8211;time-offset-minus</code>=<i>&lt;time&gt;</i></p>
<dl>
<dd>This is similar to the <code>&#8211;time-offset-plus</code> option (see above), but subtracts the specified time offset instead of adding it to the local time stamp.</dl>
<p> <code>-u, &#8211;user-agent</code>=<i>&lt;user-agent-string&gt;</i></p>
<dl>
<dd>Set the HTTP User-Agent for resolving the external IP via <code>-R</code>, or for sending SPA packets over HTTP.</dl>
<p> <code>&#8211;use-wget-user-agent</code></p>
<dl>
<dd>By default when the <code>fwknop</code> client resolves the external IP with <code>wget</code> via SSL, it sets the User-Agent to &#8220;Fwknop/&lt;version&gt;&#8221; unless it was already manually specified with the <code>&#8211;user-agent</code> option mentioned above. However, the <code>&#8211;user-wget-user-agent</code> option lets the default <code>wget</code> User-Agent string apply without influence from <code>fwknop</code>.</dl>
<p> <code>-U, &#8211;spoof-user</code>=<i>&lt;user&gt;</i></p>
<dl>
<dd>Specify the username that is included within SPA packet. This allows the <code>fwknop</code> client to satisfy any non-root <code>REQUIRE_USERNAME</code> keyword on the fwknopd server (<code>&#8211;spoof-src</code> mode requires that the <code>fwknop</code> client is executed as root).</dl>
<p> <code>&#8211;icmp-type</code>=<i>&lt;type&gt;</i></p>
<dl>
<dd>In <code>-P icmp</code> mode, specify the ICMP type value that will be set in the SPA packet ICMP header. The default is echo reply.</dl>
<p> <code>&#8211;icmp-code</code>=<i>&lt;code&gt;</i></p>
<dl>
<dd>In <code>-P icmp</code> mode, specify the ICMP code value that will be set in the SPA packet ICMP header. The default is zero.</dl>
<h2>Gpg Options</h2>
<p>Note that the usage of GPG for SPA encryption/decryption can and should involve GPG keys that are signed by each side (client and server). The basic procedure for this involves the following steps after the client key has been transferred to the server and vice-versa: </p>
<dl>
<dd>
<pre> [spaserver]# gpg --import client.asc
 [spaserver]# gpg --edit-key 1234ABCD
 Command&gt; sign
 [spaclient]$ gpg --import server.asc
 [spaclient]$ gpg --edit-key ABCD1234
 Command&gt; sign</pre>
</dl>
<p> More comprehensive information on this can be found here: <i><a rel="nofollow" href="http://www.cipherdyne.org/fwknop/docs/gpghowto.html">http://www.cipherdyne.org/fwknop/docs/gpghowto.html</a></i>. </p>
<p> <code>&#8211;gpg-agent</code></p>
<dl>
<dd>Instruct <code>fwknop</code> to acquire GnuPG key password from a running gpg-agent instance (if available).</dl>
<p> <code>&#8211;gpg-home-dir</code>=<i>&lt;dir&gt;</i></p>
<dl>
<dd>Specify the path to the GnuPG directory; normally this path is derived from the home directory of the user that is running the <code>fwknop</code> client (so the default is <i>~/.gnupg</i>). This is useful when a &#8220;root&#8221; user wishes to log into a remote machine whose sshd daemon/service does not permit root login.</dl>
<p> <code>&#8211;gpg-recipient</code>=<i>&lt;key ID or Name&gt;</i></p>
<dl>
<dd>Specify the GnuPG key ID, e.g. &#8220;+1234ABCD+&#8221; (see the output of &quot;gpg&#8212;list-keys&quot;) or the key name (associated email address) of the recipient of the Single Packet Authorization message. This key is imported by the <code>fwknopd</code> server and the associated private key is used to decrypt the SPA packet. The recipient&#8217;s key must first be imported into the client GnuPG key ring.</dl>
<p> <code>&#8211;gpg-signer-key</code>=<i>&lt;key ID or Name&gt;</i></p>
<dl>
<dd>Specify the GnuPG key ID, e.g. &#8220;+ABCD1234+&#8221; (see the output of &quot;gpg &#8211;list-keys&quot;) or the key name to use when signing the SPA message. The user is prompted for the associated GnuPG password to create the signature. This adds a cryptographically strong mechanism to allow the <code>fwknopd</code> daemon on the remote server to authenticate who created the SPA message.</dl>
<p> <code>&#8211;gpg-no-signing-pw</code></p>
<dl>
<dd>Instruct <code>fwknop</code> to not acquire a passphrase for usage of GnuPG signing key. This option is provided to make SPA packet construction easier for client-side operations in automated environments where the passphrase for the signing key has been removed from the GnuPG key ring. However, it is usually better to leverage <i>gpg-agent</i> instead of using this option.</dl>
<h2>Fwknoprc File</h2>
<p>The <i>.fwknoprc</i> file is used to set various parameters to override default program parameters at runtime. It also allows for additional named configuration <i>stanzas</i> for setting program parameters for a particular invocation. </p>
<p> The <code>fwknop</code> client will create this file if it does not exist in the user&#8217;s home directory. This initial version has some sample directives that are commented out. It is up to the user to edit this file to meet their needs. </p>
<p> The <i>.fwknoprc</i> file contains a default configuration area or stanza which holds global configuration directives that override the program defaults. You can edit this file and create additional <i>named stanzas</i> that can be specified with the <code>-n</code> or <code>&#8211;named-config</code> option. Parameters defined in the named stanzas will override any matching <i>default</i> stanza directives. Note that command-line options will still override any corresponding <i>.fwknoprc</i> directives. </p>
<p> There are directives to match most of the command-line parameters <code>fwknop</code> supports. Here is the current list of each directive along with a brief description and its matching command-line option(s): </p>
<p> <code>SPA_SERVER</code> <i>&lt;hostname/IP-address&gt;</i></p>
<dl>
<dd>Specify the hostname or IP of the destination (<code>fwknopd</code>) server (<i>-D, &#8211;destination</i>).</dl>
<p> <code>ALLOW_IP</code> <i>&lt;IP-address&gt;</i></p>
<dl>
<dd>Specify the address to allow within the SPA data. Note: This parameter covers the <code>-a</code>, <code>-s</code>, and <code>-R</code> command-line options. You can specify a hostname or IP address (the <code>-a</code> option), specify the word &quot;source&quot; to tell the <code>fwknopd</code> server to accept the source IP of the packet as the IP to allow (the <code>-s</code> option), or use the word &quot;resolve&quot; to have <code>fwknop</code> resolve the external network IP via HTTP request (the <code>-R</code> option).</dl>
<p> <code>ACCESS</code> <i>&lt;port list&gt;</i></p>
<dl>
<dd>Set the one or more protocol/ports to open on the firewall (<i>-A, &#8211;access</i>). The format of this list is &#8220;+&lt;proto&gt;/&lt;port&gt;&#8230;&lt;proto&gt;/&lt;port&gt;+&#8221;, e.g. &#8220;tcp/22,udp/53&#8221;.</dl>
<p> <code>SPA_SERVER_PORT</code> <i>&lt;port&gt;</i></p>
<dl>
<dd>Set the server port to use for sending the SPA packet (<i>-p, &#8211;server-port</i>).</dl>
<p> <code>SPA_SERVER_PROTO</code> <i>&lt;protocol</i>&gt;</p>
<dl>
<dd>Set the protocol to use for sending the SPA packet (<i>-P, &#8211;server-proto</i>).</dl>
<p> <code>KEY</code> <i>&lt;passphrase&gt;</i></p>
<dl>
<dd>This is the passphrase that is used for SPA packet encryption and applies to both Rijndael or GPG encryption modes. The actual encryption key that is used for Rijndael is derived from the PBKDF1 algorithm, and the GPG key is derived from the specified GPG key ring.</dl>
<p> <code>KEY_BASE64</code> <i>&lt;base64 encoded passphrase&gt;</i></p>
<dl>
<dd>Specify the encryption passphrase as a base64 encoded string. This allows non-ascii characters to be included in the base64-decoded key.</dl>
<p> <code>USE_HMAC</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>Set HMAC mode for authenticated encryption of SPA packets. This will have <code>fwknop</code> prompt the user for a dedicated HMAC key that is independent of the encryption key. Alternatively, the HMAC key can be specified with the <i>HMAC_KEY</i> or <i>HMAC_KEY_BASE64</i> directives (see below).</dl>
<p> <code>HMAC_KEY</code> <i>&lt;key&gt;</i></p>
<dl>
<dd>Specify the HMAC key for authenticated encryption of SPA packets. This supports both Rijndael and GPG encryption modes, and is applied according to the encrypt-then-authenticate model.</dl>
<p> <code>HMAC_KEY_BASE64</code> <i>&lt;base64 encoded key&gt;</i></p>
<dl>
<dd>Specify the HMAC key as a base64 encoded string. This allows non-ascii characters to be included in the base64-decoded key.</dl>
<p> <code>HMAC_DIGEST_TYPE</code> <i>&lt;digest algorithm&gt;</i></p>
<dl>
<dd>Set the HMAC digest algorithm used for authenticated encryption of SPA packets. Choices are: <code>MD5</code>, <code>SHA1</code>, <code>SHA256</code> (the default), <code>SHA384</code>, and <code>SHA512</code>.</dl>
<p> <code>SPA_SOURCE_PORT</code> <i>&lt;port&gt;</i></p>
<dl>
<dd>Set the source port to use for sending the SPA packet (<i>-S, &#8211;source-port</i>).</dl>
<p> <code>FW_TIMEOUT</code> <i>&lt;seconds&gt;</i></p>
<dl>
<dd>Set the firewall rule timeout value (<i>-f, &#8211;fw-timeout</i>).</dl>
<p> <code>RESOLVE_IP_HTTPS</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>Set to <i>Y</i> to automatically resolve the externally routable IP associated with the <code>fwknop</code> client. This is done over SSL via <i>wget</i> in <i>&#8211;secure-protocol</i> mode against the IP resolution service available at <i><a rel="nofollow" href="https://www.cipherdyne.org/cgi-bin/myip">https://www.cipherdyne.org/cgi-bin/myip</a></i>.</dl>
<p> <code>RESOLVE_HTTP_ONLY</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>When the <code>fwknop</code> client is instructed to resolve the external client IP, this option can be used to force an <i>HTTP</i> connection instead of an <i>HTTPS</i> connection when set to <i>Y</i>. This option is useful when <i>wget</i> is not installed on the local OS, or when it is not compiled against an SSL library.</dl>
<p> <code>RESOLVE_URL</code> <i>&lt;url&gt;</i></p>
<dl>
<dd>Set to a URL that will be used for resolving the source IP address (<i>&#8211;resolve-url</i>).</dl>
<p> <code>WGET_CMD</code> <i>&lt;wget full path&gt;</i></p>
<dl>
<dd>Set the full path to the <i>wget</i> command (used for client IP resolution).</dl>
<p> <code>TIME_OFFSET</code> <i>&lt;time&gt;</i></p>
<dl>
<dd>Set a value to apply to the timestamp in the SPA packet. This can be either a positive or negative value (<i>&#8211;time-offset-plus/minus</i>).</dl>
<p> <code>ENCRYPTION_MODE</code> <i>&lt;mode&gt;</i></p>
<dl>
<dd>Specify the encryption mode when AES is used. This variable is a synonym for the <i>-M, &#8211;encryption-mode</i> command line argument. In general, it is recommended to not include this argument and let the default (CBC) apply. Note that the string &#8220;legacy&#8221; can be specified in order to generate SPA packets with the old initialization vector strategy used by versions of <code>fwknop</code> prior to 2.5.</dl>
<p> <code>DIGEST_TYPE</code> <i>&lt;digest algorithm&gt;</i></p>
<dl>
<dd>Set the SPA message digest type (<i>-m, &#8211;digest-type</i>). Choices are: <code>MD5</code>, <code>SHA1</code>, <code>SHA256</code> (the default), <code>SHA384</code>, and <code>SHA512</code>.</dl>
<p> <code>USE_GPG</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>Set to <i>Y</i> to specify the use of GPG for encryption (<i>&#8211;gpg-encryption</i>).</dl>
<p> <code>USE_GPG_AGENT</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>Set to <i>Y</i> to have <code>fwknop</code> interface with a GPG agent instance for the GPG key password (<i>&#8211;gpg-agent</i>). Agent information itself is specified with the <i>GPG_AGENT_INFO</i> environmental variable.</dl>
<p> <code>GPG_SIGNING_PW</code> <i>&lt;passphrase&gt;</i></p>
<dl>
<dd>This is the passphrase that is used for signing SPA packet data in GPG encryption mode, and is a synonym for the <i>KEY</i> variable (i.e. the signing passphrase can be specified with the <i>KEY</i> variable instead). The SPA packet is encrypted with the remote server key and signed with the local client key.</dl>
<p> <code>GPG_SIGNING_PW_BASE64</code> <i>&lt;base64 encoded passphrase&gt;</i></p>
<dl>
<dd>Specify the GPG signing passphrase as a base64 encoded string. This allows non-ascii characters to be included in the base64-decoded key.</dl>
<p> <code>GPG_SIGNER</code> <i>&lt;key ID or Name&gt;</i></p>
<dl>
<dd>Specify the GPG key name or ID for signing the GPG-encrypted SPA data (<i>&#8211;gpg-signer-key</i>).</dl>
<p> <code>GPG_RECIPIENT</code> <i>&lt;key ID or Name&gt;</i></p>
<dl>
<dd>Specify the GPG key name or ID for the recipient of the GPG-encrypted SPA data (<i>&#8211;gpg-recipient-key</i>).</dl>
<p> <code>GPG_HOMEDIR</code> <i>&lt;dir&gt;</i></p>
<dl>
<dd>Specify the GPG home directory (<i>&#8211;gpg-home-dir</i>). Defaults to <i>~/.gnupg</i>.</dl>
<p> <code>GPG_EXE</code> <i>&lt;path&gt;</i></p>
<dl>
<dd>Specify the path to GPG (<i>&#8211;gpg-exe</i>). Defaults to <i>/usr/bin/gpg</i>.</dl>
<p> <code>SPOOF_USER</code> <i>&lt;user&gt;</i></p>
<dl>
<dd>Set the username in the SPA data to the specified value (<i>-U, &#8211;spoof-user</i>).</dl>
<p> <code>SPOOF_SOURCE_IP</code> <i>&lt;IP&gt;</i></p>
<dl>
<dd>Set the source IP of the outgoing SPA packet to the specified value (<i>-Q, &#8211;spoof-source</i>).</dl>
<p> <code>RAND_PORT</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>Send the SPA packet over a randomly assigned port (<i>-r, &#8211;rand-port</i>).</dl>
<p> <code>KEY_FILE</code> <i>&lt;file&gt;</i></p>
<dl>
<dd>Load an encryption key/password from a file (<i>-G, &#8211;get-key</i>).</dl>
<p> <code>HTTP_USER_AGENT</code> <i>&lt;agent string&gt;</i></p>
<dl>
<dd>Set the HTTP User-Agent for resolving the external IP via -R, or for sending SPA packets over HTTP (<i>-u, &#8211;user-agent</i>).</dl>
<p> <code>USE_WGET_USER_AGENT</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>Allow default <code>wget</code> User-Agent string to be used when resolving the external IP instead of a User-Agent supplied by the <code>fwknop</code> client.</dl>
<p> <code>NAT_ACCESS</code> <i>&lt;internalIP:forwardPort&gt;</i></p>
<dl>
<dd>Gain NAT access to an internal service protected by the fwknop server (<i>-N, &#8211;nat-access</i>).</dl>
<p> <code>NAT_LOCAL</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>Access a local service via a forwarded port on the fwknopd server system (<i>&#8211;nat-local</i>).</dl>
<p> <code>NAT_PORT</code> <i>&lt;port&gt;</i></p>
<dl>
<dd>Specify the port to forward to access a service via NAT (<i>&#8211;nat-port</i>).</dl>
<p> <code>NAT_RAND_PORT</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>Have the fwknop client assign a random port for NAT access (<i>&#8211;nat-rand-port</i>).</dl>

<h2>Spa Packet Spoofing</h2>
<p>Because <code>fwknop</code> places the IP to be allowed through the firewall within the encrypted SPA payload (unless <code>-s</code> is used which is not recommended and can be prohibited in the <code>fwknopd</code> server configuration), SPA packets can easily be spoofed, and this is a good thing in this context. That is, the source IP of an SPA packet is ignored by the <code>fwknopd</code> daemon (when the <i>REQUIRE_SOURCE_ADDRESS</i> variable is set in the <i>/etc/fwknop/access.conf</i> file) and only the IP that is contained within an authenticated and properly decrypted SPA packet is granted access through the firewall. This makes it possible to make it appear as though, say, <a rel="nofollow" href="http://www.yahoo.com">www.yahoo.com</a> is trying to authenticate to a target system but in reality the actual connection will come from a seemingly unrelated IP.</p>
<h2>Examples</h2>
<p>The following examples illustrate the command line arguments that could be supplied to the fwknop client in a few situations:</p>
<h3>Quick start</h3>
<p>The most effective and easiest way to use <code>fwknop</code> is to have the client generate both an encryption key and an HMAC key, and then save them to the &#8220;$HOME/.fwknoprc&#8221; file along with access request specifics. The keys will also need to be transferred to the system where <code>fwknopd</code> is running. The also client supports a separate set of encryption and HMAC keys for each SPA destination if multiple fwknopd servers are running on different systems. </p>
<p> So, assuming that the IP <i>2.2.2.2</i> is the system where <code>fwknopd</code> is deployed and SSH is protected by the firewall on that system in a default-drop stance, run the client like so to generate encryption and HMAC keys: </p>
<dl>
<dd>
<pre> $ fwknop -A tcp/22 --use-hmac -R -D 2.2.2.2 --key-gen --save-rc-stanza --verbose
 [+] Wrote Rijndael and HMAC keys to rc file: /home/user/.fwknoprc</pre>
</dl>
<p> With the access request arguments and encryption and HMAC keys generated and saved in &#8220;$HOME/.fwknoprc&#8221;, the keys themselves need to be transferred to the <i>2.2.2.2</i> system where fwknopd is running. As always, this should be done via some secure means such as SSH before SPA is enabled and SSHD is blocked by the firewall. Here is what the new <i>2.2.2.2</i> stanza looks like in the <i>~/.fwknoprc</i> file: </p>
<dl>
<dd>
<pre> $ tail -n 8 /home/user/.fwknoprc
 [2.2.2.2]
 ACCESS tcp/22
 SPA_SERVER 2.2.2.2
 KEY_BASE64 HvUtIOramehLGKimD4ECXOzinaH4h3U8H1WXum7b54Q=
 HMAC_KEY_BASE64 DLeLf93a3yBT2vhEpM+dWlirGta5GU+jdyG5uXp4461HgOtbqMem4gX0Bp2PJGzYZlbbcavcOM00UPm+0GqkXA==
 USE_HMAC Y
 VERBOSE Y
 RESOLVE_IP_HTTPS Y</pre>
</dl>
<p> The keys are base64 encoded blobs of random data, and both the <code>KEY_BASE64</code> and <code>HMAC_KEY_BASE64</code> lines should be copied verbatim and placed within the <i>/etc/fwknop/access.conf</i> file on <i>2.2.2.2</i>. Once this is done, <code>fwknopd</code> can be started on that system, a default-drop policy against SSH connections can be put in place, and then access to SSH is managed via fwknop. To access SSH, just use the <code>-n</code> argument to reference the <i>2.2.2.2</i> stanza out of the .fwknoprc file (some <code>&#8211;verbose</code> output is included for illustration): </p>
<dl>
<dd>
<pre> $ fwknop -n 2.2.2.2
 FKO Field Values:
 =================
 Random Value: 8950423288486978
 Username: mbr
 Timestamp: 1370194770
 FKO Version: 2.5
 Message Type: 1 (Access msg)
 Message String: 1.1.1.1,tcp/22
 Nat Access: &lt;NULL&gt;
 Server Auth: &lt;NULL&gt;
 Client Timeout: 0 (seconds)
 Digest Type: 3 (SHA256)
 HMAC Type: 3 (SHA256)
 Encryption Type: 1 (Rijndael)
 Encryption Mode: 2 (CBC)
 ...
 $ ssh -l user 2.2.2.2
 user [at] 2.2.2.2's password:</pre>
</dl>
<h3>Access mode examples</h3>
<p>The most common usage of <code>fwknop</code> is to gain access to SSH running on a remote system that has the <code>fwknopd</code> daemon deployed along with a default-drop firewall policy. The following command illustrates this where IP <i>1.1.1.1</i> is the IP to be allowed through the firewall running on <i>3.3.3.3</i> (note that the <i>/etc/fwknop/access.conf</i> file consumed by <code>fwknopd</code> will need to have matching encryption and HMAC keys, and configuration specifics can be found in the <i><a href="/docs/linux/man/8-fwknopd/">fwknopd</a>(8)</i> manual page). Also, note the examples below prompt the user to supply the encryption and HMAC keys via stdin instead of writing them to disk as in the case of using the &#8220;$HOME/.fwknoprc&#8221; file in the example above. However, all of the following examples can be converted to using the ~/.fwknoprc file just by adding the <code>&#8211;save-rc-stanza</code> argument: </p>
<dl>
<dd>
<pre> $ fwknop -A tcp/22 --use-hmac -a 1.1.1.1 -D 3.3.3.3
 Enter encryption key:
 Enter HMAC key:
 $ ssh -l user 3.3.3.3
 user [at] 3.3.3.3's password:</pre>
</dl>
<p> If the <code>&#8211;verbose</code> flag is added to the command line, then some SPA packet specifics are printed to stdout (not all output is shown for brevity): </p>
<dl>
<dd>
<pre> $ fwknop -A tcp/22 --use-hmac -a 1.1.1.1 -D 3.3.3.3 --verbose
 Enter encryption key:
 Enter HMAC key:
 Random Value: 1916307060193417
 Username: mbr
 Timestamp: 1368498909
 FKO Version: 2.5
 Message Type: 1 (Access msg)
 Message String: 1.1.1.1,tcp/22
 Nat Access: &lt;NULL&gt;
 Server Auth: &lt;NULL&gt;
 Client Timeout: 0 (seconds)
 Digest Type: 3 (SHA256)
 HMAC Type: 3 (SHA256)
 Encryption Type: 1 (Rijndael)
 Encryption Mode: 2 (CBC)</pre>
</dl>
<p> Simultaneous access to multiple services is also supported, and here is an example of requesting access to both <i>SSH</i> and <i>OpenVPN</i> on <i>3.3.3.3</i>: </p>
<dl>
<dd>
<pre> $ fwknop -A &quot;tcp/22,tcp/1194&quot; --use-hmac -a 1.1.1.1 -D 3.3.3.3</pre>
</dl>
<p> There are many cases where an <code>fwknop</code> client is deployed on a network behind a NAT device and the externally routable IP is not known to the user. In this case, use the IP resolution service available at <i><a rel="nofollow" href="https://www.cipherdyne.org/cgi-bin/myip">https://www.cipherdyne.org/cgi-bin/myip</a></i> via the <code>-R</code> command line switch in order to derive the external client IP address. This is a safer method of acquiring the client IP address than using the <code>-s</code> option mentioned earlier in this manual page because the source IP is put within the encrypted packet instead of having the <code>fwknopd</code> daemon grant the requested access from whatever IP address the SPA packet originates (i.e. using <code>-s</code> opens the possibility of a MITM attack): </p>
<dl>
<dd>
<pre> $ fwknop -A tcp/22 --use-hmac -R -D 3.3.3.3</pre>
</dl>
<p> Use the Single Packet Authorization mode to gain access to <i>SSH</i> and this time use GnuPG keys to encrypt and decrypt: </p>
<dl>
<dd>
<pre> $ fwknop -A tcp/22 --use-hmac --gpg-sign ABCD1234 --gpg--recipient 1234ABCD -R -D 3.3.3.3</pre>
</dl>
<p> Instruct the fwknop server running at 3.3.3.3 to allow 1.1.1.1 to connect to <i>SSH</i>, but spoof the authorization packet from an IP associated with <i><a rel="nofollow" href="http://www.yahoo.com">www.yahoo.com</a></i> (requires root on the <code>fwknop</code> client OS): </p>
<dl>
<dd>
<pre> # fwknop --spoof-src &quot;<a rel="nofollow" href="http://www.yahoo.com">www.yahoo.com</a>&quot; -A tcp/22 --use-hmac -a 1.1.1.1 -D 3.3.3.3</pre>
</dl>
<p> When <code>fwknopd</code> is running on an iptables firewall with systems deployed behind it, it is possible to take advantage of the NAT capabilities offered by iptables in order to transparently reach systems behind the firewall via SPA. Here is an example where the <code>fwknop</code> client is used to gain access to SSH running on the non-routable IP <i>192.168.10.23</i> that is deployed on the network behind <i>3.3.3.3</i>. In this case, the SSH connection made to <i>3.3.3.3</i> is translated via NAT to the <i>192.168.10.2</i> system automatically: </p>
<dl>
<dd>
<pre> $ fwknop -A tcp/22 -N 192.168.10.2:22 -R -D 3.3.3.3</pre>
</dl>
<h2>Backwards Compatibility</h2>
<p>With the <i>2.5</i> release, <code>fwknop</code> underwent significant changes in its usage of cryptography including the addition of support for HMAC authenticated encryption for both Rijndael and GnuPG modes, ensuring the proper usage of PBKDF1 for key derivation when SPA packets are encrypted with Rijndael, and several bugs were fixed from previous versions of fwknop. In general, this implies that when Rijndael is used, SPA packets produced by the <i>2.5</i> release are incompatible with previous versions of fwknop. The GnuPG encryption mode is unaffected by these updates. However, even with Rijndael is used, backwards compatibility is supported through setting the <i>legacy</i> encryption mode with <code>-M</code> on the fwknop client command line and/or the <i>ENCRYPTION_MODE</i> variable in the <i>/etc/fwknop/access.conf</i> file. This way, a pre-2.5 server can decrypt SPA packets produced by a 2.5 and later client (set <i>-M legacy</i>), and a 2.5 and later server can decrypt SPA packets produced by pre-2.5 clients (set <i>ENCRYPTION_MODE legacy</i> in the access.conf file). Note that HMAC is only supported as of 2.5 and is an optional feature, so backwards compatibility is only for configurations that don&#8217;t use an HMAC on either side. It is strongly recommended to upgrade all fwknop clients and servers to 2.5 and use the new HMAC mode for properly authenticated SPA communications. The backwards compatibility support is used to make it easier to upgrade clients and servers with a phased approach. </p>
<p> For emphasis, if the <code>fwknopd</code> server is upgraded to 2.5 (or later), but older clients cannot be upgraded at the same time, then for each <i>SOURCE</i> stanza in the <i>/etc/fwknop/access.conf</i> file, add the following line: </p>
<dl>
<dd>
<pre> ENCRYPTION_MODE legacy</pre>
</dl>
<p> In addition, if the <i>KEY</i> variable has an encryption key longer than 16 bytes, it will need to be truncated to 16 characters in the <i>access.conf</i> file in order for pre-2.5 clients to work properly. This limitation is fixed in 2.5, and provides additional motiviation for upgrading all clients and servers to 2.5 or later. </p>
<p> Now, flipping the scenario around, if the <code>fwknop</code> clients are upgraded but the <code>fwknopd</code> server is still at a pre-2.5 version, then add the <i>-M legacy</i> argument to the fwknop command line: </p>
<dl>
<dd>
<pre> $ fwknop -A tcp/22 -M legacy -R -D 2.2.2.2</pre>
</dl>
<h2>Dependencies</h2>
<p>The <code>fwknop</code> client requires <i>libfko</i> which is normally included with both source and binary distributions, and is a dedicated library developed by the fwknop project. Whenever the <code>fwknopd</code> server is used, <i>libpcap</i> is a required dependency. However, the upcoming <i>2.6</i> release will offer a UDP listener mode along with privilege separation support and will not require libpcap in this mode. In UDP listener mode, even though fwknopd binds to a UDP port, SPA packets are never acknowledged so from an attacker&#8217;s perspective there is no difference between fwknopd sniffing the wire passively vs. listening on a UDP socket in terms of what can be scanned for. </p>
<p> For GPG functionality, GnuPG must also be correctly installed and configured along with the <i>libgpgme</i> library. </p>
<p> To take advantage of all of the authentication and access management features of the <code>fwknopd</code> daemon/service a functioning <i>iptables</i>, <i>ipfw</i>, or <i>pf</i> firewall is required on the underlying operating system.</p>
<h2>Diagnostics</h2>
<p>The most comprehensive way to gain diagnostic information on <code>fwknop</code> is to run the test suite <i>test-fwknop.pl</i> script located in the <i>test/</i> directory in the fwknop sources. The test suite sends fwknop through a large number of run time tests, has <i>valgrind</i> support, validates both SPA encryption and HMAC results against OpenSSL, and even has its own built in fuzzer for SPA communications (and fwknop in version 2.6.4 supports the <i>American Fuzzy Lop</i> (AFL) from Michal Zalewski as well). For more basic diagnostic information, <code>fwknop</code> can be executed with the <code>-T</code> (or <code>&#8211;test</code>) command line option. This will have <code>fwknop</code> simply create and print the SPA packet information, then run it through a decrypt/decode cycle and print it again. In addition, the <code>&#8211;verbose</code> command line switch is useful to see various SPA packet specifics printed to stdout.</p>
