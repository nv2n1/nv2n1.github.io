<p>fwknopd &#8211; Firewall Knock Operator Daemon</p>
<h2>Synopsis</h2>
<p><code>fwknopd</code> [<i>options</i>]</p>
<h2>Description</h2>
<p><code>fwknopd</code> is the server component for the FireWall Knock Operator, and is responsible for monitoring and processing Single Packet Authorization (SPA) packets that are generated by <code>fwknop</code> clients, modifying a firewall or ACL policy to allow the desired access after authenticating and decrypting a valid SPA packet (in that order), and removing access after a configurable timeout. </p>
<p> The main application of this program is to conceal services such as <i>SSH</i> with an additional layer of security in order to make the exploitation of vulnerabilities (both 0-day and unpatched code) much more difficult. In addition, services that are concealed in this fashion naturally cannot be scanned for with <i>Nmap</i>. </p>
<p> The main configuration for <code>fwknopd</code> is maintained within two files: <i>fwknopd.conf</i> and <i>access.conf</i>. The default location for these files is determined at package configuration (typically <i>/etc/fwknop</i>). The configuration variables within these files are described below.</p>
<h2>Command-Line Options</h2>
<p><code>-i, &#8211;interface</code>=<i>&lt;interface&gt;</i></p>
<dl>
<dd>Manually specify interface on which to sniff, e.g. &#8220;-i eth0&#8221;. This option is not usually needed because the &#8220;PCAP_INTF&#8221; keyword in the <i>fwknopd.conf</i> file defines the sniffing interface.</dl>
<p> <code>-f, &#8211;foreground</code></p>
<dl>
<dd>Run <code>fwknopd</code> in the foreground instead of becoming a daemon. When run in the foreground, message that would go to the log would instead be sent to stderr. This mode is usually used when testing and/or debugging.</dl>
<p> <code>&#8211;fw-list</code></p>
<dl>
<dd>List only firewall rules that any running <code>fwknopd</code> daemon has created and then exit.</dl>
<p> <code>-a, &#8211;access-file</code>=<i>&lt;access-file&gt;</i></p>
<dl>
<dd>Specify the location of the <i>access.conf</i> file. If this option is not given, <i>fwknopd</i> will use the compile-time default location (typically <i>/etc/fwknop/access.conf</i>).</dl>
<p> <code>-c, &#8211;config</code>=<i>&lt;config-file&gt;</i></p>
<dl>
<dd>Specify the location of the <i>fwknopd.conf</i> file. If this option is not given, <i>fwknopd</i> will use the default location (typically <i>/etc/fwknop/fwknopd.conf</i>.</dl>
<p> <code>-C, &#8211;packet-limit</code>=<i>&lt;n&gt;</i></p>
<dl>
<dd>Specify the number of candidate SPA packets to process and exit when this limit is reached.</dl>
<p> <code>-d, &#8211;digest-file</code>=<i>&lt;digest-file&gt;</i></p>
<dl>
<dd>Specify the location of the <i>digest.cache</i> file. If this option is not given, <i>fwknopd</i> will use the compile-time default location (typically <i>/var/fwknop/digest.cache</i>).</dl>
<p> <code>-D, &#8211;dump-config</code></p>
<dl>
<dd>Dump the configuration values that <code>fwknopd</code> derives from the <i>/etc/fwknop/fwknopd.conf</i> (or override files) and <i>/etc/fwknop/access.conf</i> on stderr.</dl>
<p> <code>&#8211;dump-serv-err-codes</code></p>
<dl>
<dd>Dump all possible <code>fwknopd</code> error codes to stdout and exit. This option is rarely needed in practice, and was added to assist with test coverage.</dl>
<p> <code>&#8211;fault-injection-tag</code>=<i>&lt;tag&gt;</i></p>
<dl>
<dd>This option is only used for fault injection testing when <code>fwknop</code> is compiled to support the libfiu library (see: <i><a rel="nofollow" href="http://blitiri.com.ar/p/libfiu/">http://blitiri.com.ar/p/libfiu/</a></i>). Under normal circumstances this option is not used, and any packaged version of fwknop will not have code compiled in so this capability is not enabled at run time. It is documented here for completeness. version of fwknop will not have code compiled in to enable this capability at run time. It is documented here for completeness.</dl>
<p> <code>-A, &#8211;afl-fuzzing</code></p>
<dl>
<dd>Instruct <code>fwknopd</code> to acquire SPA packets directly from stdin in support of fuzzing operations from the <i>American Fuzzy Lop</i> (AFL) fuzzer written by Michal Zalewski. This requires that <code>fwknop</code> is compiled with the <i>&#8211;enable-afl-fuzzing</i> argument to the <code>configure</code> script as this allows encryption/digest short circuiting in a manner necessary for AFL to function properly. The benefit of this strategy is that AFL can fuzz the SPA packet decoding routines implemented by <code>libfko</code>.</dl>
<p> <code>&#8211;fw-list-all</code></p>
<dl>
<dd>List all firewall rules including those that have nothing to do with <code>fwknopd</code>.</dl>
<p> <code>&#8211;fw-flush</code></p>
<dl>
<dd>Flush any firewall rules created by a running <code>fwknopd</code> process. This option allows the used to easily delete <code>fwknopd</code> firewall rules without having to wait for them to be timed out.</dl>
<p> <code>-K, &#8211;kill</code></p>
<dl>
<dd>Kill the current <code>fwknopd</code> process. This provides a quick and easy way to stop <code>fwknopd</code> without having to look in the process table.</dl>
<p> <code>&#8211;exit-parse-config</code></p>
<dl>
<dd>Parse config files (<i>/etc/fwknop/fwknopd.conf</i>, <i>/etc/fwknop/access.conf</i>, the digest cache file, etc.) and exit. This provides a way to test whether the config files are properly structured without having to start processing network traffic.</dl>
<p> <code>-l, &#8211;locale</code>=<i>&lt;locale&gt;</i></p>
<dl>
<dd>Set/override the system default locale setting.</dl>
<p> <code>&#8211;no-ipt-check-support</code></p>
<dl>
<dd>Disable the usage of the iptables <i>-C</i> option. This is not normally needed, and is only useful on older Linux distributions where iptables does not have <i>-C</i> support.</dl>
<p> <code>-O, &#8211;override-config</code>=<i>&lt;file&gt;</i></p>
<dl>
<dd>Override config variable values that are normally read from the <i>/etc/fwknop/fwknopd.conf</i> file with values from the specified file. Multiple override config files can be given as a comma-separated list.</dl>
<p> <code>&#8211;key-gen</code></p>
<dl>
<dd>Have <code>fwknopd</code> generate both Rijndael and HMAC keys that can be used for SPA packet encryption and authentication. These keys are derived from /dev/urandom and then base64 encoded before being printed to stdout, and are meant to be manually included in a stanza within the <i>/etc/fwknop/access.conf</i> file. Such keys are generally more secure than passphrases.</dl>
<p> <code>&#8211;key-gen-file</code>=<i>&lt;file&gt;</i></p>
<dl>
<dd>Write generated keys to the specified file. Note that the file is overwritten if it already exists. If this option is not given, then <code>&#8211;key-gen</code> writes the keys to stdout.</dl>
<p> <code>&#8211;key-len</code>=<i>&lt;length&gt;</i></p>
<dl>
<dd>Specify the number of bytes for a generated Rijndael key. The maximum size is currently 128 bytes.</dl>
<p> <code>&#8211;hmac-key-len</code>=<i>&lt;length&gt;</i></p>
<dl>
<dd>Specify the number of bytes for a generated HMAC key. The maximum size is currently 128 bytes.</dl>
<p> <code>-p, &#8211;pid-file</code>=<i>&lt;pid-file&gt;</i></p>
<dl>
<dd>Specify the location of the <i>fwknopd.pid</i> file. If this option is not given, <i>fwknopd</i> will use the compile-time default location (typically <i>/var/fwknop/fwknopd.pid</i>).</dl>
<p> <code>-P, &#8211;pcap-filter</code>=<i>&lt;filter&gt;</i></p>
<dl>
<dd>Specify a Berkeley packet filter statement on the <code>fwknopd</code> command line. This overrides the value of the PCAP_FILTER variable taken from the <i>/etc/fwknop/fwknopd.conf</i> file.</dl>
<p> <code>&#8211;pcap-file</code>=<i>&lt;pcap-file&gt;</i></p>
<dl>
<dd>This option instructs <code>fwknopd</code> to read packet data from a pcap file instead of sniffing an interface directly. This mode is usually used for debugging purposes, and will disable SPA packet age checking unless it is manually enabled in the <i>/etc/fwknop/fwknopd.conf</i> file.</dl>
<p> <code>&#8211;pcap-any-direction</code></p>
<dl>
<dd>Allow <code>fwknopd</code> to sniff SPA packets regardless of whether they are received on the sniffing interface or sent from the sniffing interface. In the later case, this can be useful to have fwknopd sniff SPA packets that are forwarded through a system and destined for a different network. If the sniffing interface is the egress interface for such packets (and hence SPA packets are sent by this interface instead of received), then this option will need to used in order for <code>fwknopd</code> to see them. The default is to only sniff packets that are received on the sniffing interface. Note that this setting is independent of promiscuous mode.</dl>
<p> <code>-R, &#8211;restart</code></p>
<dl>
<dd>Restart the currently running <code>fwknopd</code> processes. This option will preserve the command line options that were supplied to the original <code>fwknopd</code> process but will force <code>fwknopd</code> to re-read the <i>fwknopd.conf</i> and <i>/etc/fwknop/access.conf</i> files. This will also force a flush of the current &#8220;FWKNOP&#8221; iptables chain(s).</dl>
<p> <code>&#8211;rotate-digest-cache</code></p>
<dl>
<dd>Rotate the digest cache file by renaming it to &#8220;&lt;name&gt;-old&#8221;, and starting a new one. The digest cache file is typically found in <i>/var/fwknop/digest.cache</i>.</dl>
<p> <code>-r, &#8211;run-dir</code>=<i>&lt;path&gt;</i></p>
<dl>
<dd>Specify the directory where <code>fwknopd</code> writes run time state files. The default is <i>/var</i>.</dl>
<p> <code>-S, &#8211;status</code></p>
<dl>
<dd>Display the status of any <code>fwknopd</code> processes that may or not be running. If there is an existing fwknopd process then 0 is returned for the exit status and 1 is returned otherwise.</dl>
<p> <code>&#8211;syslog-enable</code></p>
<dl>
<dd>Allow messages to be sent to syslog even if the foreground mode is set.</dl>
<p> <code>-t, &#8211;test</code></p>
<dl>
<dd>Run <code>fwknopd</code> in test mode. This instructs <code>fwknopd</code> to acquire and process SPA packets, but not manipulate firewall rules or execute commands that are provided by SPA clients. This option is mostly useful for the fuzzing tests in the test suite to ensure broad code coverage under adverse conditions.</dl>
<p> <code>-U, &#8211;udp-server</code></p>
<dl>
<dd>Run <code>fwknopd</code> in UDP server mode so that SPA packets are acquired via a UDP socket directly without having to use libpcap. See the discussion of the &#8220;ENABLE_UDP_SERVER&#8221; configuration variable below for more information.</dl>
<p> <code>-v, &#8211;verbose</code></p>
<dl>
<dd>Run <code>fwknopd</code> in verbose mode. This can option can be specified multiple times to increase the verbosity of the output to the system log file (or to the screen if running in the foreground).</dl>
<p> <code>-h, &#8211;help</code></p>
<dl>
<dd>Display usage information and exit.</dl>
<p> <code>-V, &#8211;Version</code></p>
<dl>
<dd>Display version information and exit.</dl>
<h2>Fwknopd Config And Access Variables</h2>
<p><code>fwknopd</code> references the <i>/etc/fwknop/fwknopd.conf</i> file for configuration variables that define its operational parameters (what network interface and port to sniff, what features to enable/disable, etc.). The <i>fwknopd.conf</i> file does not define any access control directives. </p>
<p> The access control directives are contained in the <i>/etc/fwknop/access.conf</i> file. Access control directives define encryption keys and level of access that is granted to an fwknop client that has generated the appropriate encrypted SPA message.</p>
<h3>Fwknopd.Conf Variables</h3>
<p>This section list the more prominent configuration variables used by <code>fwknopd</code>. It is not a complete list. There are directives for the type of firewall used by <code>fwknopd</code> (i.e. <i>iptables</i>, <i>ipfw</i>, or <i>pf</i>). You will want to make sure to check these to make sure they have appropriate values. See the <i>/etc/fwknop/fwknopd.conf</i> file for the full list and corresponding details. </p>
<p> <code>PCAP_INTF</code> <i>&lt;interface&gt;</i></p>
<dl>
<dd>Specify the ethernet interface on which <code>fwknopd</code> will sniff packets.</dl>
<p> <code>ENABLE_PCAP_PROMISC</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>By default <code>fwknopd</code> puts the pcap interface into promiscuous mode. Set this to &#8220;N&#8221; to disable that behavior (non-promiscuous).</dl>
<p> <code>PCAP_FILTER</code> <i>&lt;pcap filter spec&gt;</i></p>
<dl>
<dd>Define the filter used for <i>PCAP</i> modes; <code>fwknopd</code> defaults to UDP port 62201. However, if an <code>fwknop</code> client uses the <code>&#8211;rand-port</code> option to send the SPA packet over a random port, then this variable should be updated to something like &#8220;udp dst portrange 10000-65535&#8221;.</dl>
<p> <code>ENABLE_SPA_PACKET_AGING</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>This instructs <code>fwknopd</code> to not honor SPA packets that have an old time stamp. The value for &#8220;old&#8221; is defined by the &#8220;MAX_SPA_PACKET_AGE&#8221; variable. If &#8220;ENABLE_SPA_PACKET_AGING&#8221; is set to &#8220;N&#8221;, <code>fwknopd</code> will not use the client time stamp at all.</dl>
<p> <code>MAX_SPA_PACKET_AGE</code> <i>&lt;seconds&gt;</i></p>
<dl>
<dd>Defines the maximum age (in seconds) that an SPA packet will be accepted. This requires that the client system is in relatively close time synchronization with the <code>fwknopd</code> server system (NTP is good). The default age is 120 seconds (two minutes).</dl>
<p> <code>ENABLE_DIGEST_PERSISTENCE</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>Track digest sums associated with previous SPA packets processed by <code>fwknopd</code>. This allows digest sums to remain persistent across executions of <code>fwknopd</code>. The default is &#8220;Y&#8221;. If set to &#8220;N&#8221;, <code>fwknopd</code> will not check incoming SPA packet data against any previously save digests. It is a good idea to leave this feature on to reduce the possibility of being vulnerable to a replay attack.</dl>
<p> <code>RULES_CHECK_THRESHOLD</code> <i>&lt;count&gt;</i></p>
<dl>
<dd>Defines the number of times firewall rule expiration times must be checked before a &quot;deep&quot; check is run. This allows <code>fwknopd</code> to remove rules that contain a proper <i>exp</i><i>&lt;time&gt;</i> even if a third party program added them instead of <code>fwknopd</code>. The default value for this variable is 20, and this typically results in this check being run every two seconds or so. To disable this type of checking altogether, set this variable to zero.</dl>
<p> <code>ENABLE_IPT_FORWARDING</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>Allow SPA clients to request access to services through an iptables firewall instead of just to it (i.e. access through the FWKNOP_FORWARD chain instead of the INPUT chain).</dl>
<p> <code>ENABLE_IPT_LOCAL_NAT</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>Allow SPA clients to request access to a local socket via NAT. This still puts an ACCEPT rule into the FWKNOP_INPUT chain, but a different port is translated via DNAT rules to the real one. So, the user would do &#8220;ssh -p &lt;port&gt;&#8221; to access the local service (see the <code>&#8211;NAT-local</code> and <code>&#8211;NAT-rand-port</code> on the <code>fwknop</code> client command line).</dl>
<p> <code>ENABLE_IPT_SNAT</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>Set this to &#8220;Y&#8221; to enable a corresponding SNAT rule. By default, if forwarding access is enabled (see the &#8220;ENABLE_IPT_FORWARDING&#8221; variable above), then <code>fwknopd</code> creates DNAT rules for incoming connections, but does not also complement these rules with SNAT rules at the same time. In some situations, internal systems may not have a route back out for the source address of the incoming connection, so it is necessary to also apply SNAT rules so that the internal systems see the IP of the internal interface where <code>fwknopd</code> is running.</dl>
<p> <code>SNAT_TRANSLATE_IP</code> <i>&lt;ip_address&gt;</i></p>
<dl>
<dd>Specify the IP address for SNAT. This functionality is only enabled when &#8220;ENABLE_IPT_SNAT&#8221; is set to &#8220;Y&#8221; and by default SNAT rules are built with the MASQUERADE target (since then the internal IP does not have to be defined here in the <i>/etc/fwknop/fwknopd.conf</i> file), but if you want <code>fwknopd</code> to use the SNAT target, you must also define an IP address with the &#8220;SNAT_TRANSLATE_IP&#8221; variable. Note that this variable is generally deprecated in favor of the &#8220;FORCE_SNAT&#8221; variable in the <i>/etc/fwknop/access.conf</i> file which enables per-stanza control over the SNAT IP.</dl>
<p> <code>ENABLE_IPT_OUTPUT</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>Add ACCEPT rules to the FWKNOP_OUTPUT chain. This is usually only useful if there are no state tracking rules to allow connection responses out and the OUTPUT chain has a default-drop stance.</dl>
<p> <code>MAX_SNIFF_BYTES</code> <i>&lt;bytes&gt;</i></p>
<dl>
<dd>Specify the the maximum number of bytes to sniff per frame. 1500 is the default.</dl>
<p> <code>FLUSH_IPT_AT_INIT</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>Flush all existing rules in the fwknop chains at <code>fwknopd</code> start time. The default is &#8220;Y&#8221;.</dl>
<p> <code>FLUSH_IPT_AT_EXIT</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>Flush all existing rules in the fwknop chains when <code>fwknopd</code> is stopped or otherwise exits cleanly. The default is &#8220;Y&#8221;.</dl>
<p> <code>EXIT_AT_INTF_DOWN</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>When <code>fwknopd</code> is sniffing an interface, if the interface is administratively downed or unplugged, fwknopd will cleanly exit and an assumption is made that any process monitoring infrastructure like systemd or upstart will restart it. However, if fwknopd is not being monitored by systemd, upstart, or anything else, this behavior can be disabled with the &#8220;EXIT_AT_INTF_DOWN&#8221; variable. If disabled, fwknopd will try to recover when a downed interface comes back up.</dl>
<p> <code>GPG_HOME_DIR</code> <i>&lt;path&gt;</i></p>
<dl>
<dd>If GPG keys are used instead of a Rijndael symmetric key, this is the default GPG keys directory. Note that each access stanza in <i>/etc/fwknop/access.conf</i> can specify its own GPG directory to override this default. If not set here or in an <i>access.conf</i> stanza, then the <i>$HOME/.gnupg</i> directory of the user running <code>fwknopd</code> (most likely root).</dl>
<p> <code>GPG_EXE</code> <i>&lt;path&gt;</i></p>
<dl>
<dd>Specify the path to GPG, and defaults to <i>/usr/bin/gpg</i> if not set.</dl>
<p> <code>LOCALE</code> <i>&lt;locale&gt;</i></p>
<dl>
<dd>Set the locale (via the LC_ALL variable). This can be set to override the default system locale.</dl>
<p> <code>ENABLE_SPA_OVER_HTTP</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>Allow <code>fwknopd</code> to acquire SPA data from HTTP requests (generated with the fwknop client in <code>&#8211;HTTP</code> mode). Note that when this is enabled, the &#8220;PCAP_FILTER&#8221; variable would need to be updated to sniff traffic over TCP/80 connections and a web server should be running on the same server as <code>fwknopd</code>.</dl>
<p> <code>ENABLE_TCP_SERVER</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>Enable the fwknopd TCP server. This is a &quot;dummy&quot; TCP server that will accept TCP connection requests on the specified TCPSERV_PORT. If set to &quot;Y&quot;, fwknopd will fork off a child process to listen for, and accept incoming TCP request. This server only accepts the request. It does not otherwise communicate. This is only to allow the incoming SPA over TCP packet which is detected via PCAP. The connection is closed after 1 second regardless. Note that fwknopd still only gets its data via pcap, so the filter defined by PCAP_FILTER needs to be updated to include this TCP port.</dl>
<p> <code>TCPSERV_PORT</code> <i>&lt;port&gt;</i></p>
<dl>
<dd>Set the port number that the &#8220;dummy&#8221; TCP server listens on. This server is only spawned when &#8220;ENABLE_TCP_SERVER&#8221; is set to &#8220;Y&#8221;.</dl>
<p> <code>ENABLE_UDP_SERVER</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>Enable the <code>fwknopd</code> UDP server. This instructs <code>fwknopd</code> to acquire SPA packets via a UDP socket directly without having to use libpcap. When this mode is enabled, <code>fwknop</code> should be compiled with <code>&#8211;enable-udp-server</code> (passed to the <code>configure</code> script) so that libpcap can be removed as a dependency. As one would expect, when the UDP server is used, no incoming packets are ever acknowledged by <code>fwknopd</code> and therefore collecting SPA packets in this mode is a good alternative to sniffing the wire directly.</dl>
<p> <code>UDPSERV_PORT</code> <i>&lt;port&gt;</i></p>
<dl>
<dd>Set the port number that the UDP server listens on. This server is only spawned when &#8220;ENABLE_UDP_SERVER&#8221; is set to &#8220;Y&#8221;.</dl>
<p> <code>PCAP_DISPATCH_COUNT</code> <i>&lt;count&gt;</i></p>
<dl>
<dd>Sets the number of packets that are processed when the <code>pcap_dispatch()</code> call is made. The default is zero, since this allows <code>fwknopd</code> to process as many packets as possible in the corresponding callback where the SPA handling routine is called for packets that pass a set of prerequisite checks. However, if <code>fwknopd</code> is running on a platform with an old version of libpcap, it may be necessary to change this value to a positive non-zero integer. More information can be found in the <code><a href="/docs/linux/man/3-pcap_dispatch/">pcap_dispatch</a>(3)</code> man page.</dl>
<p> <code>PCAP_LOOP_SLEEP</code> <i>&lt;microseconds&gt;</i></p>
<dl>
<dd>Sets the number of microseconds to passed as an argument to usleep() in the pcap loop. The default is 10000, or 1/10th of a second.</dl>
<p> <code>ENABLE_PCAP_ANY_DIRECTION</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>Controls whether fwknopd is permitted to sniff SPA packets regardless of whether they are received on the sniffing interface or sent from the sniffing interface. In the later case, this can be useful to have fwknopd sniff SPA packets that are forwarded through a system and destined for a different network. If the sniffing interface is the egress interface for such packets, then this variable will need to be set to &quot;Y&quot; in order for fwknopd to see them. The default is &quot;N&quot; so that fwknopd only looks for SPA packets that are received on the sniffing interface (note that this is independent of promiscuous mode).</dl>
<p> <code>SYSLOG_IDENTITY</code> <i>&lt;identity&gt;</i></p>
<dl>
<dd>Override syslog identity on message logged by <code>fwknopd</code>. The defaults are usually ok.</dl>
<p> <code>SYSLOG_FACILITY</code> <i>&lt;facility&gt;</i></p>
<dl>
<dd>Override syslog facility. The &#8220;SYSLOG_FACILITY&#8221; variable can be set to</dl>
<p> <code>ENABLE_DESTINATION_RULE</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>Controls whether <code>fwknopd</code> will set the destination field on the firewall rule to the destination address specified on the incoming SPA packet. This is useful for interfaces with multiple IP addresses hosting separate services. If &#8220;ENABLE_IPT_OUTPUT&#8221; is set to &#8220;Y&#8221;, the source field of the firewall rule is set. FORWARD and SNAT rules are not affected however, DNAT rules will also have their destination field set. The default is &#8220;N&#8221;, which sets the destination field to 0.0.0.0/0 (any).</dl>
<p> <code>FWKNOP_RUN_DIR</code> <i>&lt;path&gt;</i></p>
<dl>
<dd>Specify the directory where <code>fwknopd</code> writes run time state files. The default is <i>/var</i>.</dl>
<h3>Access.Conf Variables</h3>
<p>This section describes the access control directives in the <i>/etc/fwknop/access.conf</i> file. Theses directives define encryption keys and level of access that is granted to <code>fwknop</code> clients that have generated the appropriate encrypted message. </p>
<p> The <i>access.conf</i> variables described below provide the access directives for the SPA packets with a source (or embedded request) IP that matches an address or network range defined by the &#8220;SOURCE&#8221; variable. All variables following &#8220;SOURCE&#8221; apply to the source <i>stanza</i>. Each &#8220;SOURCE&#8221; directive starts a new stanza. </p>
<p> <code>SOURCE</code> <i>&lt;IP,..,IP/NET,..,NET/ANY&gt;</i></p>
<dl>
<dd>This defines the source address from which the SPA packet will be accepted. The string &#8220;ANY&#8221; is also accepted if a valid SPA packet should be honored from any source IP. Every authorization stanza in <i>/etc/fwknop/access.conf</i> definition must start with the &#8220;SOURCE&#8221; keyword. Networks should be specified in CIDR notation (e.g. &#8220;192.168.10.0/24&#8221;), and individual IP addresses can be specified as well. Also, multiple IP&#8217;s and/or networks can be defined as a comma separated list (e.g. &#8220;192.168.10.0/24,10.1.1.123&#8221;)</dl>
<p> <code>DESTINATION</code> <i>&lt;IP,..,IP/NET,..,NET/ANY&gt;</i></p>
<dl>
<dd>This defines the destination address for which the SPA packet will be accepted. The string &#8220;ANY&#8221; is also accepted if a valid SPA packet should be honored to any destination IP. Networks should be specified in CIDR notation (e.g. &#8220;192.168.10.0/24&#8221;), and individual IP addresses can be specified as well. Also, multiple IP&#8217;s and/or networks can be defined as a comma separated list (e.g. &#8220;192.168.10.0/24,10.1.1.123&#8221;)</dl>
<p> <code>OPEN_PORTS</code> <i>&lt;proto/port&gt;,&#8230;,&lt;proto/port&gt;</i></p>
<dl>
<dd>Define a set of ports and protocols (tcp or udp) that will be opened if a valid knock sequence is seen. If this entry is not set, <code>fwknopd</code> will attempt to honor any proto/port request specified in the SPA data (unless of it matches any &#8220;RESTRICT_PORTS&#8221; entries). Multiple entries are comma-separated.</dl>
<p> <code>RESTRICT_PORTS</code> <i>&lt;proto/port&gt;,&#8230;,&lt;proto/port&gt;</i></p>
<dl>
<dd>Define a set of ports and protocols (tcp or udp) that are explicitly <code>not</code> allowed regardless of the validity of the incoming SPA packet. Multiple entries are comma-separated.</dl>
<p> <code>KEY</code> <i>&lt;passphrase&gt;</i></p>
<dl>
<dd>Define the symmetric key used for decrypting an incoming SPA packet that is encrypted by the <code>fwknop</code> client with Rijndael. The actual encryption key that is used is derived from the standard PBKDF1 algorithm. This variable is required for all SPA packets unless GnuPG is used instead (see the GPG variables below).</dl>
<p> <code>KEY_BASE64</code> <i>&lt;base64 encoded passphrase&gt;</i></p>
<dl>
<dd>Same as the <code>KEY</code> option above, but specify the symmetric key as a base64 encoded string. This allows non-ascii characters to be included in the base64-decoded key.</dl>
<p> <code>HMAC_KEY</code> <i>&lt;key&gt;</i></p>
<dl>
<dd>Specify the HMAC key for authenticated encryption of SPA packets. This supports both Rijndael and GPG encryption modes, and is applied according to the encrypt-then-authenticate model.</dl>
<p> <code>HMAC_KEY_BASE64</code> <i>&lt;base64 encoded key&gt;</i></p>
<dl>
<dd>Specify the HMAC key as a base64 encoded string. This allows non-ascii characters to be included in the base64-decoded key.</dl>
<p> <code>FW_ACCESS_TIMEOUT</code> <i>&lt;seconds&gt;</i></p>
<dl>
<dd>Define the length of time access will be granted by <code>fwknopd</code> through the firewall after a valid knock sequence from a source IP address. If &#8220;FW_ACCESS_TIMEOUT&#8221; is not set then the default timeout of 30 seconds will automatically be set.</dl>
<p> <code>ENCRYPTION_MODE</code> <i>&lt;mode&gt;</i></p>
<dl>
<dd>Specify the encryption mode when AES is used. The default is CBC mode, but other modes can be selected such as OFB and CFB. In general, it is recommended to not use this variable and leave it as the default. Note that the string &#8220;legacy&#8221; can be specified in order to generate SPA packets with the old initialization vector strategy used by versions of <code>fwknop</code> before 2.5. With the 2.5 release, <code>fwknop</code> uses PBKDF1 for key derivation.</dl>
<p> <code>HMAC_DIGEST_TYPE</code> <i>&lt;digest algorithm&gt;</i></p>
<dl>
<dd>Specify the digest algorithm for incoming SPA packet authentication. Must be one of <code>MD5</code>, <code>SHA1</code>, <code>SHA256</code>, <code>SHA384</code>, or <code>SHA512</code>. This is an optional field, and if not specified then <code>fwknopd</code> defaults to using SHA256 if the access stanza requires an HMAC.</dl>
<p> <code>ACCESS_EXPIRE</code> <i>&lt;MM/DD/YYYY&gt;</i></p>
<dl>
<dd>Defines an expiration date for the access stanza in MM/DD/YYYY format. All SPA packets that match an expired stanza will be ignored. This parameter is optional.</dl>
<p> <code>ACCESS_EXPIRE_EPOCH</code> <i>&lt;seconds&gt;</i></p>
<dl>
<dd>Defines an expiration date for the access stanza as the epoch time, and is useful if a more accurate expiration time needs to be given than the day resolution offered by the ACCESS_EXPIRE variable above. All SPA packets that match an expired stanza will be ignored. This parameter is optional.</dl>
<p> <code>ENABLE_CMD_EXEC</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>This instructs <code>fwknopd</code> to accept complete commands that are contained within an authorization packet. Any such command will be executed on the <code>fwknopd</code> server as the user specified by the &#8220;CMD_EXEC_USER&#8221; or as the user that started <code>fwknopd</code> if that is not set.</dl>
<p> <code>ENABLE_CMD_SUDO_EXEC</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd><code>sudo</code> provides a powerful means of restricting the sets of commands that users can execute via the &#8220;sudoers&#8221; file. By enabling this feature (and in &#8220;ENABLE_CMD_EXEC&#8221; mode), all incoming commands from valid SPA packets will be prefixed by &#8220;/path/to/sudo -u &lt;user&gt; -g &lt;group&gt;&#8221; where the path to sudo is set by the &#8220;SUDO_EXE&#8221; variable, &#8220;&lt;user&gt;&#8221; is set by the &#8220;CMD_SUDO_EXEC_USER&#8221; variable (default is &#8220;root&#8221; if not set), and &#8220;&lt;group&gt;&#8221; is set by &#8220;CMD_SUDO_EXEC_GROUP&#8221; (default is also &#8220;root&#8221; if not set).</dl>
<p> <code>CMD_EXEC_USER</code> <i>&lt;username&gt;</i></p>
<dl>
<dd>Specify the user (via setuid) that will execute a command contained within a SPA packet. If this variable is not given, fwknopd will execute the command as the user it is running as (most likely root). Setting this to a non-root user such as &#8220;nobody&#8221; is highly recommended if elevated permissions are not needed.</dl>
<p> <code>CMD_SUDO_EXEC_USER</code> <i>&lt;username&gt;</i></p>
<dl>
<dd>Specify the user (via &#8220;sudo -u &lt;user&gt;&#8221;) that will execute a command contained within a SPA packet. If this variable is not given, fwknopd will assume the command should be executed as root.</dl>
<p> <code>CMD_EXEC_GROUP</code> <i>&lt;groupname&gt;</i></p>
<dl>
<dd>Specify the group (via setgid) that will execute a command contained within a SPA packet. If this variable is not given, fwknopd will execute the command as the user it is running as (most likely root). Setting this to a non-root user such as &#8220;nobody&#8221; is highly recommended if elevated permissions are not needed.</dl>
<p> <code>CMD_SUDO_EXEC_GROUP</code> <i>&lt;groupname&gt;</i></p>
<dl>
<dd>Specify the group (via &#8220;sudo -gu &lt;group&gt;&#8221;) that will execute a command contained within a SPA packet. If this variable is not given, fwknopd will assume the command should be executed as root.</dl>
<p> <code>SUDO_EXE</code> <i>&lt;path&gt;</i></p>
<dl>
<dd>Define the path to the sudo binary. Default is &#8220;/usr/bin/sudo&#8221;.</dl>
<p> <code>REQUIRE_USERNAME</code> <i>&lt;username&gt;</i></p>
<dl>
<dd>Require a specific username from the client system as encoded in the SPA data. This variable is optional and if not specified, the username data in the SPA data is ignored.</dl>
<p> <code>REQUIRE_SOURCE_ADDRESS</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>Force all SPA packets to contain a real IP address within the encrypted data. This makes it impossible to use the <code>-s</code> command line argument on the <code>fwknop</code> client command line, so either <code>-R</code> has to be used to automatically resolve the external address (if the client behind a NAT) or the client must know the external IP and set it via the <code>-a</code> argument.</dl>
<p> <code>REQUIRE_SOURCE_ADDRESS</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>Synonym for &#8220;REQUIRE_SOURCE_ADDRESS&#8221;.</dl>
<p> <code>FORCE_NAT</code> <i>&lt;IP&gt; &lt;PORT&gt;</i></p>
<dl>
<dd>For any valid SPA packet, force the requested connection to be NAT&#8217;d through to the specified (usually internal) IP and port value. This is useful if there are multiple internal systems running a service such as SSHD, and you want to give transparent access to only one internal system for each stanza in the access.conf file. This way, multiple external users can each directly access only one internal system per SPA key.</dl>
<p> <code>FORCE_SNAT</code> <i>&lt;IP&gt;</i></p>
<dl>
<dd>For any valid SPA packet, add an SNAT rule in addition to any DNAT rule created with a corresponding (required) FORCE_NAT variable. This is analogous to &#8220;SNAT_TRANSLATE_IP&#8221; from the <i>/etc/fwknop/fwknopd.conf</i> file except that it is per access stanza and overrides any value set with &#8220;SNAT_TRANSLATE_IP&#8221;. This is useful for situations where an incoming NAT&#8217;d connection may be otherwise unanswerable due to routing constraints (i.e. the system receiving the SPA authenticated connection has a default route to a different device than the SPA system itself).</dl>
<p> <code>FORCE_MASQUERADE</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>This is similar to the &#8220;FORCE_SNAT&#8221; variable, except that it is not necessary to also specify an IP address for SNAT rules because the MASQUERADE target is used instead.</dl>
<p> <code>FORWARD_ALL</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>In NAT scenarios, control whether all traffic is forwarded through the <code>fwknopd</code> system as opposed to just forwarding connections to specific services as requested by the <code>fwknop</code> client.</dl>
<p> <code>DISABLE_DNAT</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>Control whether DNAT rules are created in FORCE_NAT scenarios. This is mainly used in conjunction with the FORWARD_ALL variable to allow <code>fwknopd</code> to act essentially as an SPA gateway. I.e., the <code>fwknop</code> client is used to gain access via SPA to the broader Internet after being granted an IP via DHCP, but prior to sending the SPA packet all traffic is blocked by default to the Internet.</dl>
<p> <code>GPG_DECRYPT_ID</code> <i>&lt;keyID&gt;</i></p>
<dl>
<dd>Define a GnuPG key ID to use for decrypting SPA messages that have been encrypted by an <code>fwknop</code> client. This keyword is required for authentication that is based on GPG keys. The GPG key ring on the client must have imported and signed the <code>fwknopd</code> server key, and vice versa. It is ok to use a sensitive personal GPG key on the client, but each <code>fwknopd</code> server should have its own GPG key that is generated specifically for fwknop communications. The reason for this is that the decryption password for the server key must be placed within the <i>/etc/fwknop/access.conf</i> file for <code>fwknopd</code> to function (it has to be able to decrypt SPA messages that have been encrypted with the server&#8217;s public key). For more information on using fwknop with GnuPG keys, see the following link: &#8220;<a rel="nofollow" href="http://www.cipherdyne.org/fwknop/docs/gpghowto.html">http://www.cipherdyne.org/fwknop/docs/gpghowto.html</a>&#8220;.</dl>
<p> <code>GPG_DECRYPT_PW</code> <i>&lt;decrypt password&gt;</i></p>
<dl>
<dd>Specify the decryption password for the gpg key defined by the &#8220;GPG_DECRYPT_ID&#8221; above. This is a required field for gpg-based authentication.</dl>
<p> <code>GPG_ALLOW_NO_PW</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>Allow <code>fwknopd</code> to leverage a GnuPG key pair that does not have an associated password. While this may sound like a controversial deployment mode, in automated environments it makes sense because &quot;there is usually no way to store a password more securely than on the secret keyring itself&quot; according to: &#8220;<a rel="nofollow" href="http://www.gnupg.org/faq/GnuPG-FAQ.html#how-can-i-use-gnupg-in-an-automated-environment">http://www.gnupg.org/faq/GnuPG-FAQ.html#how-can-i-use-gnupg-in-an-automated-environment</a>&#8220;. Using this feature and removing the passphrase from a GnuPG key pair is useful in some environments where libgpgme is forced to use gpg-agent and/or pinentry to collect a passphrase.</dl>
<p> <code>GPG_REQUIRE_SIG</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>With this setting set to <i>Y</i>, fwknopd check all GPG-encrypted SPA messages for a signature (signed by the sender&#8217;s key). If the incoming message is not signed, the decryption process will fail. If not set, the default is <i>Y</i>.</dl>
<p> <code>GPG_DISABLE_SIG</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>Disable signature verification for incoming SPA messages. This is not a recommended setting, and the default is <i>N</i>.</dl>
<p> <code>GPG_IGNORE_SIG_VERIFY_ERROR</code> <i>&lt;Y/N&gt;</i></p>
<dl>
<dd>Setting this will allow fwknopd to accept incoming GPG-encrypted packets that are signed, but the signature did not pass verification (i.e. the signer key was expired, etc.). This setting only applies if the GPG_REQUIRE_SIG is also set to <i>Y</i>.</dl>
<p> <code>GPG_REMOTE_ID</code> <i>&lt;keyID,&#8230;,keyID&gt;</i></p>
<dl>
<dd>Define a list of gpg key ID&#8217;s that are required to have signed any incoming SPA message that has been encrypted with the <code>fwknopd</code> server key. This ensures that the verification of the remote user is accomplished via a strong cryptographic mechanism. Signature verification is enabled by default, and can only be disabled if &#8220;GPG_DISABLE_SIG&#8221; is set to <i>Y</i> (not a recommended setting). Separate multiple entries with a comma.</dl>
<p> <code>GPG_FINGERPRINT_ID</code> <i>&lt;keyID,&#8230;,keyID&gt;</i></p>
<dl>
<dd>Specify a set of full-length GnuPG key fingerprints instead of the shorter key identifiers set with the &#8220;GPG_REMOTE_ID&#8221; variable. Here is an example fingerprint for one of the fwknop test suite keys: <i>00CC95F05BC146B6AC4038C9E36F443C6A3FAD56</i>.</dl>
<p> <code>GPG_HOME_DIR</code> <i>&lt;path&gt;</i></p>
<dl>
<dd>Define the path to the GnuPG directory to be used by the <code>fwknopd</code> server. If this keyword is not specified within <i>/etc/fwknop/access.conf</i> then <code>fwknopd</code> will default to using the <i>/root/.gnupg</i> directory for the server key(s) for incoming SPA packets handled by the matching <i>access.conf</i> stanza.</dl>
<p> <code>GPG_EXE</code> <i>&lt;path&gt;</i></p>
<dl>
<dd>Define the path to the GnuPG executable. If this keyword is not specified within <i>/etc/fwknop/access.conf</i> then <code>fwknopd</code> will default to using <i>/usr/bin/gpg</i>.</dl>

<h2>Dependencies</h2>
<p><code>fwknopd</code> requires <i>libfko</i> which is normally included with both source and binary distributions, and is a dedicated library developed by the fwknop project. </p>
<p> For packet sniffing, <code>fwknopd</code> currently requires libpcap, but future versions will (optionally) remove this as a dependency. </p>
<p> For GPG functionality, GnuPG must also be correctly installed and configured along with the libgpgme library. </p>
<p> To take advantage of all of the authentication and access management features of the <code>fwknopd</code> daemon/service a functioning iptables, ipfw, or pf firewall is required on the underlying operating system.</p>
<h2>Diagnostics</h2>
<p><code>fwknopd</code> can be run in debug mode by combining the <code>-f, &#8211;foreground</code> and the <code>-v, &#8211;verbose</code> command line options. This will disable daemon mode execution, and print verbose information to the screen on stderr as packets are received. </p>
<p> The most comprehensive way to gain diagnostic information on <code>fwknopd</code> is to run the test suite <i>test-fwknop.pl</i> script located in the <i>test/</i> directory in the fwknop sources. The test suite runs sends fwknop through a large number of run time tests, has <i>valgrind</i> support, validates both SPA encryption and HMAC results against OpenSSL, and even has its own built in fuzzer for SPA communications.</p>
