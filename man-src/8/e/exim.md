<p>exim &#8211; a Mail Transfer Agent</p>
<h2>Synopsis</h2>
<pre><code>exim [options] arguments ...</code>
<code>mailq [options] arguments ...</code>
<code>rsmtp [options] arguments ...</code>
<code>rmail [options] arguments ...</code>
<code>runq [options] arguments ...</code>
<code>newaliases [options] arguments ...</code></pre>
<h2>Description</h2>
<p>Exim is a mail transfer agent (MTA) developed at the University of Cambridge. It is a large program with very many facilities. For a full specification, see the reference manual. This man page contains only a description of the command line options. It has been automatically generated from the reference manual source, hopefully without too much mangling. </p>
<p> Like other MTAs, Exim replaces Sendmail, and is normally called by user agents (MUAs) using the path <i>/usr/sbin/sendmail</i> when they submit messages for delivery (some operating systems use <i>/usr/lib/sendmail</i>). This path is normally set up as a symbolic link to the Exim binary. It may also be used by boot scripts to start the Exim daemon. Many of Exim&#8217;s command line options are compatible with Sendmail so that it can act as a drop-in replacement.</p>
<h2>Default Action</h2>
<p>If no options are present that require a specific action (such as starting the daemon or a queue runner, testing an address, receiving a message in a specific format, or listing the queue), and there are no arguments on the command line, Exim outputs a brief message about itself and exits. </p>
<p> However, if there is at least one command line argument, <code>-bm</code> (accept a local message on the standard input, with the arguments specifying the recipients) is assumed. Thus, for example, if Exim is installed in <i>/usr/sbin</i>, you can send a message from the command line like this: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>/usr/sbin/exim -i&nbsp;<wbr>&lt;recipient-address(es)&gt;<br />
&nbsp;<wbr>&nbsp;<wbr>&lt;message content, including all the header lines&gt;<br />
&nbsp;<wbr>&nbsp;<wbr>CTRL-D </p>
<p> The <code>-i</code> option prevents a line containing just a dot from terminating the message. Only an end-of-file (generated by typing CTRL-D if the input is from a terminal) does so.</p>
<h2>Setting Options By Program Name</h2>
<p>If an Exim binary is called using one of the names listed in this section (typically via a symbolic link), certain options are assumed.</p>
<dl>
<dt><code>mailq</code></p>
<dd>Behave as if the option <code>-bp</code> were present before any other options. The <code>-bp</code> option requests a listing of the contents of the mail queue on the standard output.</p>
<dt><code>rsmtp</code></p>
<dd>Behaves as if the option <code>-bS</code> were present before any other options, for compatibility with Smail. The <code>-bS</code> option is used for reading in a number of messages in batched SMTP format.</p>
<dt><code>rmail</code></p>
<dd>Behave as if the <code>-i</code> and <code>-oee</code> options were present before any other options, for compatibility with Smail. The name <code>rmail</code> is used as an interface by some UUCP systems. The <code>-i</code> option specifies that a dot on a line by itself does not terminate a non-SMTP message; <code>-oee</code> requests that errors detected in non-SMTP messages be reported by emailing the sender.</p>
<dt><code>runq</code></p>
<dd>Behave as if the option <code>-q</code> were present before any other options, for compatibility with Smail. The <code>-q</code> option causes a single queue runner process to be started. It processes the queue once, then exits.</p>
<dt><code>newaliases</code></p>
<dd>Behave as if the option <code>-bi</code> were present before any other options, for compatibility with Sendmail. This option is used for rebuilding Sendmail&#8217;s alias file. Exim does not have the concept of a single alias file, but can be configured to run a specified command if called with the <code>-bi</code> option.</dl>
<h2>Options</h2>
<dl>
<dt><code>&#8212;</code></p>
<dd>This is a pseudo-option whose only purpose is to terminate the options and therefore to cause subsequent command line items to be treated as arguments rather than options, even if they begin with hyphens.</p>
<dt><code>&#8211;help</code></p>
<dd>This option causes Exim to output a few sentences stating what it is. The same output is generated if the Exim binary is called with no options and no arguments.</p>
<dt><code>&#8211;version</code></p>
<dd>This option is an alias for <code>-bV</code> and causes version information to be displayed.</p>
<dt><code>-Ac</code></p>
<dd><code>-Am</code> These options are used by Sendmail for selecting configuration files and are ignored by Exim.</p>
<dt><code>-B</code>&lt;<i>type</i>&gt;</p>
<dd>This is a Sendmail option for selecting 7 or 8 bit processing. Exim is 8-bit clean; it ignores this option.</p>
<dt><code>-bd</code></p>
<dd>This option runs Exim as a daemon, awaiting incoming SMTP connections. Usually the <code>-bd</code> option is combined with the <code>-q</code>&lt;<i>time</i>&gt; option, to specify that the daemon should also initiate periodic queue runs. </p>
<p> The <code>-bd</code> option can be used only by an admin user. If either of the <code>-d</code> (debugging) or <code>-v</code> (verifying) options are set, the daemon does not disconnect from the controlling terminal. When running this way, it can be stopped by pressing ctrl-C. </p>
<p> By default, Exim listens for incoming connections to the standard SMTP port on all the host&#8217;s running interfaces. However, it is possible to listen on other ports, on multiple ports, and only on specific interfaces. </p>
<p> When a listening daemon is started without the use of <code>-oX</code> (that is, without overriding the normal configuration), it writes its process id to a file called exim-daemon.pid in Exim&#8217;s spool directory. This location can be overridden by setting PID_FILE_PATH in Local/Makefile. The file is written while Exim is still running as root. </p>
<p> When <code>-oX</code> is used on the command line to start a listening daemon, the process id is not written to the normal pid file path. However, <code>-oP</code> can be used to specify a path on the command line if a pid file is required. </p>
<p> The SIGHUP signal can be used to cause the daemon to re-execute itself. This should be done whenever Exim&#8217;s configuration file, or any file that is incorporated into it by means of the <code>.include</code> facility, is changed, and also whenever a new version of Exim is installed. It is not necessary to do this when other files that are referenced from the configuration (for example, alias files) are changed, because these are reread each time they are used.</p>
<dt><code>-bdf</code></p>
<dd>This option has the same effect as <code>-bd</code> except that it never disconnects from the controlling terminal, even when no debugging is specified.</p>
<dt><code>-be</code></p>
<dd>Run Exim in expansion testing mode. Exim discards its root privilege, to prevent ordinary users from using this mode to read otherwise inaccessible files. If no arguments are given, Exim runs interactively, prompting for lines of data. Otherwise, it processes each argument in turn. </p>
<p> If Exim was built with USE_READLINE=yes in Local/Makefile, it tries to load the <code>libreadline</code> library dynamically whenever the <code>-be</code> option is used without command line arguments. If successful, it uses the readline() function, which provides extensive line-editing facilities, for reading the test data. A line history is supported. </p>
<p> Long expansion expressions can be split over several lines by using backslash continuations. As in Exim&#8217;s run time configuration, white space at the start of continuation lines is ignored. Each argument or data line is passed through the string expansion mechanism, and the result is output. Variable values from the configuration file (for example, <i>$qualify_domain</i>) are available, but no message-specific values (such as <i>$message_exim_id</i>) are set, because no message is being processed (but see <code>-bem</code> and <code>-Mset</code>). </p>
<p> <code>Note</code>: If you use this mechanism to test lookups, and you change the data files or databases you are using, you must exit and restart Exim before trying the same lookup again. Otherwise, because each Exim process caches the results of lookups, you will just get the same result as before.</p>
<dt><code>-bem</code> &lt;<i>filename</i>&gt;</p>
<dd>This option operates like <code>-be</code> except that it must be followed by the name of a file. For example: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>exim -bem&nbsp;<wbr>/tmp/testmessage </p>
<p> The file is read as a message (as if receiving a locally-submitted non-SMTP message) before any of the test expansions are done. Thus, message-specific variables such as <i>$message_size</i> and <i>$header_from:</i> are available. However, no <i>Received:</i> header is added to the message. If the <code>-t</code> option is set, recipients are read from the headers in the normal way, and are shown in the <i>$recipients</i> variable. Note that recipients cannot be given on the command line, because further arguments are taken as strings to expand (just like <code>-be</code>).</p>
<dt><code>-bF</code> &lt;<i>filename</i>&gt;</p>
<dd>This option is the same as <code>-bf</code> except that it assumes that the filter being tested is a system filter. The additional commands that are available only in system filters are recognized.</p>
<dt><code>-bf</code> &lt;<i>filename</i>&gt;</p>
<dd>This option runs Exim in user filter testing mode; the file is the filter file to be tested, and a test message must be supplied on the standard input. If there are no message-dependent tests in the filter, an empty file can be supplied. </p>
<p> If you want to test a system filter file, use <code>-bF</code> instead of <code>-bf</code>. You can use both <code>-bF</code> and <code>-bf</code> on the same command, in order to test a system filter and a user filter in the same run. For example: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>exim -bF&nbsp;<wbr>/system/filter -bf&nbsp;<wbr>/user/filter&nbsp;<wbr>&lt;/test/message </p>
<p> This is helpful when the system filter adds header lines or sets filter variables that are used by the user filter. </p>
<p> If the test filter file does not begin with one of the special lines </p>
<p>&nbsp;<wbr>&nbsp;<wbr>#&nbsp;<wbr>Exim filter<br />
&nbsp;<wbr>&nbsp;<wbr>#&nbsp;<wbr>Sieve filter </p>
<p> it is taken to be a normal .forward file, and is tested for validity under that interpretation. </p>
<p> The result of an Exim command that uses <code>-bf</code>, provided no errors are detected, is a list of the actions that Exim would try to take if presented with the message for real. More details of filter testing are given in the separate document entitled <i>Exim&#8217;s interfaces to mail filtering</i>. </p>
<p> When testing a filter file, the envelope sender can be set by the <code>-f</code> option, or by a &quot;From &quot; line at the start of the test message. Various parameters that would normally be taken from the envelope recipient address of the message can be set by means of additional command line options (see the next four options).</p>
<dt><code>-bfd</code> &lt;<i>domain</i>&gt;</p>
<dd>This sets the domain of the recipient address when a filter file is being tested by means of the <code>-bf</code> option. The default is the value of <i>$qualify_domain</i>.</p>
<dt><code>-bfl</code> &lt;<i>local part</i>&gt;</p>
<dd>This sets the local part of the recipient address when a filter file is being tested by means of the <code>-bf</code> option. The default is the username of the process that calls Exim. A local part should be specified with any prefix or suffix stripped, because that is how it appears to the filter when a message is actually being delivered.</p>
<dt><code>-bfp</code> &lt;<i>prefix</i>&gt;</p>
<dd>This sets the prefix of the local part of the recipient address when a filter file is being tested by means of the <code>-bf</code> option. The default is an empty prefix.</p>
<dt><code>-bfs</code> &lt;<i>suffix</i>&gt;</p>
<dd>This sets the suffix of the local part of the recipient address when a filter file is being tested by means of the <code>-bf</code> option. The default is an empty suffix.</p>
<dt><code>-bh</code> &lt;<i>IP address</i>&gt;</p>
<dd>This option runs a fake SMTP session as if from the given IP address, using the standard input and output. The IP address may include a port number at the end, after a full stop. For example: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>exim -bh 10.9.8.7.1234<br />
&nbsp;<wbr>&nbsp;<wbr>exim -bh fe80::a00:20ff:fe86:a061.5678 </p>
<p> When an IPv6 address is given, it is converted into canonical form. In the case of the second example above, the value of <i>$sender_host_address</i> after conversion to the canonical form is fe80:0000:0000:0a00:20ff:fe86:a061.5678. </p>
<p> Comments as to what is going on are written to the standard error file. These include lines beginning with &quot;LOG&quot; for anything that would have been logged. This facility is provided for testing configuration options for incoming messages, to make sure they implement the required policy. For example, you can test your relay controls using <code>-bh</code>. </p>
<p> <code>Warning 1</code>: You can test features of the configuration that rely on ident (RFC 1413) information by using the <code>-oMt</code> option. However, Exim cannot actually perform an ident callout when testing using <code>-bh</code> because there is no incoming SMTP connection. </p>
<p> <code>Warning 2</code>: Address verification callouts are also skipped when testing using <code>-bh</code>. If you want these callouts to occur, use <code>-bhc</code> instead. </p>
<p> Messages supplied during the testing session are discarded, and nothing is written to any of the real log files. There may be pauses when DNS (and other) lookups are taking place, and of course these may time out. The <code>-oMi</code> option can be used to specify a specific IP interface and port if this is important, and <code>-oMaa</code> and <code>-oMai</code> can be used to set parameters as if the SMTP session were authenticated. </p>
<p> The <i>exim_checkaccess</i> utility is a &quot;packaged&quot; version of <code>-bh</code> whose output just states whether a given recipient address from a given host is acceptable or not. </p>
<p> Features such as authentication and encryption, where the client input is not plain text, cannot easily be tested with <code>-bh</code>. Instead, you should use a specialized SMTP test program such as <code>swaks</code>.</p>
<dt><code>-bhc</code> &lt;<i>IP address</i>&gt;</p>
<dd>This option operates in the same way as <code>-bh</code>, except that address verification callouts are performed if required. This includes consulting and updating the callout cache database.</p>
<dt><code>-bi</code></p>
<dd>Sendmail interprets the <code>-bi</code> option as a request to rebuild its alias file. Exim does not have the concept of a single alias file, and so it cannot mimic this behaviour. However, calls to /usr/lib/sendmail with the <code>-bi</code> option tend to appear in various scripts such as NIS make files, so the option must be recognized. </p>
<p> If <code>-bi</code> is encountered, the command specified by the <code>bi_command</code> configuration option is run, under the uid and gid of the caller of Exim. If the <code>-oA</code> option is used, its value is passed to the command as an argument. The command set by <code>bi_command</code> may not contain arguments. The command can use the <i>exim_dbmbuild</i> utility, or some other means, to rebuild alias files if this is required. If the <code>bi_command</code> option is not set, calling Exim with <code>-bi</code> is a no-op.</p>
<dt><code>-bI:help</code></p>
<dd>We shall provide various options starting -bI: for querying Exim for information. The output of many of these will be intended for machine consumption. This one is not. The <code>-bI:help</code> option asks Exim for a synopsis of supported options beginning -bI:. Use of any of these options shall cause Exim to exit after producing the requested output.</p>
<dt><code>-bI:dscp</code></p>
<dd>This option causes Exim to emit an alphabetically sorted list of all recognised DSCP names.</p>
<dt><code>-bI:sieve</code></p>
<dd>This option causes Exim to emit an alphabetically sorted list of all supported Sieve protocol extensions on stdout, one per line. This is anticipated to be useful for ManageSieve (RFC 5804) implementations, in providing that protocol&#8217;s SIEVE capability response line. As the precise list may depend upon compile-time build options, which this option will adapt to, this is the only way to guarantee a correct response.</p>
<dt><code>-bm</code></p>
<dd>This option runs an Exim receiving process that accepts an incoming, locally-generated message on the standard input. The recipients are given as the command arguments (except when <code>-t</code> is also present &#8211; see below). Each argument can be a comma-separated list of RFC 2822 addresses. This is the default option for selecting the overall action of an Exim call; it is assumed if no other conflicting option is present. </p>
<p> If any addresses in the message are unqualified (have no domain), they are qualified by the values of the <code>qualify_domain</code> or <code>qualify_recipient</code> options, as appropriate. The <code>-bnq</code> option (see below) provides a way of suppressing this for special cases. </p>
<p> Policy checks on the contents of local messages can be enforced by means of the non-SMTP ACL. </p>
<p> The return code is zero if the message is successfully accepted. Otherwise, the action is controlled by the <code>-oe</code><i>x</i> option setting &#8211; see below. </p>
<p> The format of the message must be as defined in RFC 2822, except that, for compatibility with Sendmail and Smail, a line in one of the forms </p>
<p>&nbsp;<wbr>&nbsp;<wbr>From sender Fri Jan&nbsp;<wbr>&nbsp;<wbr>5 12:55 GMT 1997<br />
&nbsp;<wbr>&nbsp;<wbr>From sender Fri, 5 Jan 97 12:55:01 </p>
<p> (with the weekday optional, and possibly with additional text after the date) is permitted to appear at the start of the message. There appears to be no authoritative specification of the format of this line. Exim recognizes it by matching against the regular expression defined by the <code>uucp_from_pattern</code> option, which can be changed if necessary. </p>
<p> The specified sender is treated as if it were given as the argument to the <code>-f</code> option, but if a <code>-f</code> option is also present, its argument is used in preference to the address taken from the message. The caller of Exim must be a trusted user for the sender of a message to be set in this way.</p>
<dt><code>-bmalware</code> &lt;<i>filename</i>&gt;</p>
<dd>This debugging option causes Exim to scan the given file or directory (depending on the used scanner interface), using the malware scanning framework. The option of <code>av_scanner</code> influences this option, so if <code>av_scanner</code>&#8216;s value is dependent upon an expansion then the expansion should have defaults which apply to this invocation. ACLs are not invoked, so if <code>av_scanner</code> references an ACL variable then that variable will never be populated and <code>-bmalware</code> will fail. </p>
<p> Exim will have changed working directory before resolving the filename, so using fully qualified pathnames is advisable. Exim will be running as the Exim user when it tries to open the file, rather than as the invoking user. This option requires admin privileges. </p>
<p> The <code>-bmalware</code> option will not be extended to be more generally useful, there are better tools for file-scanning. This option exists to help administrators verify their Exim and AV scanner configuration.</p>
<dt><code>-bnq</code></p>
<dd>By default, Exim automatically qualifies unqualified addresses (those without domains) that appear in messages that are submitted locally (that is, not over TCP/IP). This qualification applies both to addresses in envelopes, and addresses in header lines. Sender addresses are qualified using <code>qualify_domain</code>, and recipient addresses using <code>qualify_recipient</code> (which defaults to the value of <code>qualify_domain</code>). </p>
<p> Sometimes, qualification is not wanted. For example, if <code>-bS</code> (batch SMTP) is being used to re-submit messages that originally came from remote hosts after content scanning, you probably do not want to qualify unqualified addresses in header lines. (Such lines will be present only if you have not enabled a header syntax check in the appropriate ACL.) </p>
<p> The <code>-bnq</code> option suppresses all qualification of unqualified addresses in messages that originate on the local host. When this is used, unqualified addresses in the envelope provoke errors (causing message rejection) and unqualified addresses in header lines are left alone.</p>
<dt><code>-bP</code></p>
<dd>If this option is given with no arguments, it causes the values of all Exim&#8217;s main configuration options to be written to the standard output. The values of one or more specific options can be requested by giving their names as arguments, for example: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>exim -bP qualify_domain hold_domains </p>
<p> However, any option setting that is preceded by the word &quot;hide&quot; in the configuration file is not shown in full, except to an admin user. For other users, the output is as in this example: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>mysql_servers&nbsp;<wbr>=&nbsp;<wbr>&lt;value not displayable&gt; </p>
<p> If <code>config</code> is given as an argument, the config is output, as it was parsed, any include file resolved, any comment removed. </p>
<p> If <code>config_file</code> is given as an argument, the name of the run time configuration file is output. (<code>configure_file</code> works too, for backward compatibility.) If a list of configuration files was supplied, the value that is output here is the name of the file that was actually used. </p>
<p> If the <code>-n</code> flag is given, then for most modes of <code>-bP</code> operation the name will not be output. </p>
<p> If <code>log_file_path</code> or <code>pid_file_path</code> are given, the names of the directories where log files and daemon pid files are written are output, respectively. If these values are unset, log files are written in a sub-directory of the spool directory called <code>log</code>, and the pid file is written directly into the spool directory. </p>
<p> If <code>-bP</code> is followed by a name preceded by +, for example, </p>
<p>&nbsp;<wbr>&nbsp;<wbr>exim -bP&nbsp;<wbr>+local_domains </p>
<p> it searches for a matching named list of any type (domain, host, address, or local part) and outputs what it finds. </p>
<p> If one of the words <code>router</code>, <code>transport</code>, or <code>authenticator</code> is given, followed by the name of an appropriate driver instance, the option settings for that driver are output. For example: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>exim -bP transport local_delivery </p>
<p> The generic driver options are output first, followed by the driver&#8217;s private options. A list of the names of drivers of a particular type can be obtained by using one of the words <code>router_list</code>, <code>transport_list</code>, or <code>authenticator_list</code>, and a complete list of all drivers with their option settings can be obtained by using <code>routers</code>, <code>transports</code>, or <code>authenticators</code>. </p>
<p> If <code>environment</code> is given as an argument, the set of environment variables is output, line by line. Using the <code>-n</code> flag suppresses the value of the variables. </p>
<p> If invoked by an admin user, then <code>macro</code>, <code>macro_list</code> and <code>macros</code> are available, similarly to the drivers. Because macros are sometimes used for storing passwords, this option is restricted. The output format is one item per line.</p>
<dt><code>-bp</code></p>
<dd>This option requests a listing of the contents of the mail queue on the standard output. If the <code>-bp</code> option is followed by a list of message ids, just those messages are listed. By default, this option can be used only by an admin user. However, the <code>queue_list_requires_admin</code> option can be set false to allow any user to see the queue. </p>
<p> Each message on the queue is displayed as in the following example: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>25m&nbsp;<wbr>&nbsp;<wbr>2.9K 0t5C6f-0000c8-00&nbsp;<wbr>&lt;alice [at] wonderland.fict.example&gt;<br />
&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>red.king [at] looking-glass.fict.example<br />
&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&nbsp;<wbr>&lt;other addresses&gt; </p>
<p> The first line contains the length of time the message has been on the queue (in this case 25 minutes), the size of the message (2.9K), the unique local identifier for the message, and the message sender, as contained in the envelope. For bounce messages, the sender address is empty, and appears as &quot;&lt;&gt;&quot;. If the message was submitted locally by an untrusted user who overrode the default sender address, the user&#8217;s login name is shown in parentheses before the sender address. </p>
<p> If the message is frozen (attempts to deliver it are suspended) then the text &quot;*** frozen ***&quot; is displayed at the end of this line. </p>
<p> The recipients of the message (taken from the envelope, not the headers) are displayed on subsequent lines. Those addresses to which the message has already been delivered are marked with the letter D. If an original address gets expanded into several addresses via an alias or forward file, the original is displayed with a D only when deliveries for all of its child addresses are complete.</p>
<dt><code>-bpa</code></p>
<dd>This option operates like <code>-bp</code>, but in addition it shows delivered addresses that were generated from the original top level address(es) in each message by alias or forwarding operations. These addresses are flagged with &quot;+D&quot; instead of just &quot;D&quot;.</p>
<dt><code>-bpc</code></p>
<dd>This option counts the number of messages on the queue, and writes the total to the standard output. It is restricted to admin users, unless <code>queue_list_requires_admin</code> is set false.</p>
<dt><code>-bpr</code></p>
<dd>This option operates like <code>-bp</code>, but the output is not sorted into chronological order of message arrival. This can speed it up when there are lots of messages on the queue, and is particularly useful if the output is going to be post-processed in a way that doesn&#8217;t need the sorting.</p>
<dt><code>-bpra</code></p>
<dd>This option is a combination of <code>-bpr</code> and <code>-bpa</code>.</p>
<dt><code>-bpru</code></p>
<dd>This option is a combination of <code>-bpr</code> and <code>-bpu</code>.</p>
<dt><code>-bpu</code></p>
<dd>This option operates like <code>-bp</code> but shows only undelivered top-level addresses for each message displayed. Addresses generated by aliasing or forwarding are not shown, unless the message was deferred after processing by a router with the <code>one_time</code> option set.</p>
<dt><code>-brt</code></p>
<dd>This option is for testing retry rules, and it must be followed by up to three arguments. It causes Exim to look for a retry rule that matches the values and to write it to the standard output. For example: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>exim -brt bach.comp.mus.example<br />
&nbsp;<wbr>&nbsp;<wbr>Retry rule:&nbsp;<wbr>*.comp.mus.example&nbsp;<wbr>&nbsp;<wbr>F,2h,15m;&nbsp;<wbr>F,4d,30m; </p>
<p>&nbsp;<wbr>The first argument, which is required, can be a complete address in the form <i>local_part [at] domain</i>, or it can be just a domain name. If the second argument contains a dot, it is interpreted as an optional second domain name; if no retry rule is found for the first argument, the second is tried. This ties in with Exim&#8217;s behaviour when looking for retry rules for remote hosts &#8211; if no rule is found that matches the host, one that matches the mail domain is sought. Finally, an argument that is the name of a specific delivery error, as used in setting up retry rules, can be given. For example: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>exim -brt haydn.comp.mus.example quota_3d<br />
&nbsp;<wbr>&nbsp;<wbr>Retry rule:&nbsp;<wbr>*@haydn.comp.mus.example quota_3d&nbsp;<wbr>&nbsp;<wbr>F,1h,15m</p>
<dt><code>-brw</code></p>
<dd>This option is for testing address rewriting rules, and it must be followed by a single argument, consisting of either a local part without a domain, or a complete address with a fully qualified domain. Exim outputs how this address would be rewritten for each possible place it might appear.</p>
<dt><code>-bS</code></p>
<dd>This option is used for batched SMTP input, which is an alternative interface for non-interactive local message submission. A number of messages can be submitted in a single run. However, despite its name, this is not really SMTP input. Exim reads each message&#8217;s envelope from SMTP commands on the standard input, but generates no responses. If the caller is trusted, or <code>untrusted_set_sender</code> is set, the senders in the SMTP MAIL commands are believed; otherwise the sender is always the caller of Exim. </p>
<p> The message itself is read from the standard input, in SMTP format (leading dots doubled), terminated by a line containing just a single dot. An error is provoked if the terminating dot is missing. A further message may then follow. </p>
<p> As for other local message submissions, the contents of incoming batch SMTP messages can be checked using the non-SMTP ACL. Unqualified addresses are automatically qualified using <code>qualify_domain</code> and <code>qualify_recipient</code>, as appropriate, unless the <code>-bnq</code> option is used. </p>
<p> Some other SMTP commands are recognized in the input. HELO and EHLO act as RSET; VRFY, EXPN, ETRN, and HELP act as NOOP; QUIT quits, ignoring the rest of the standard input. </p>
<p> If any error is encountered, reports are written to the standard output and error streams, and Exim gives up immediately. The return code is 0 if no error was detected; it is 1 if one or more messages were accepted before the error was detected; otherwise it is 2. </p>
<dt><code>-bs</code></p>
<dd>This option causes Exim to accept one or more messages by reading SMTP commands on the standard input, and producing SMTP replies on the standard output. SMTP policy controls, as defined in ACLs are applied. Some user agents use this interface as a way of passing locally-generated messages to the MTA. </p>
<p> In this usage, if the caller of Exim is trusted, or <code>untrusted_set_sender</code> is set, the senders of messages are taken from the SMTP MAIL commands. Otherwise the content of these commands is ignored and the sender is set up as the calling user. Unqualified addresses are automatically qualified using <code>qualify_domain</code> and <code>qualify_recipient</code>, as appropriate, unless the <code>-bnq</code> option is used. </p>
<p> The <code>-bs</code> option is also used to run Exim from <i>inetd</i>, as an alternative to using a listening daemon. Exim can distinguish the two cases by checking whether the standard input is a TCP/IP socket. When Exim is called from <i>inetd</i>, the source of the mail is assumed to be remote, and the comments above concerning senders and qualification do not apply. In this situation, Exim behaves in exactly the same way as it does when receiving a message via the listening daemon.</p>
<dt><code>-bt</code></p>
<dd>This option runs Exim in address testing mode, in which each argument is taken as a recipient address to be tested for deliverability. The results are written to the standard output. If a test fails, and the caller is not an admin user, no details of the failure are output, because these might contain sensitive information such as usernames and passwords for database lookups. </p>
<p> If no arguments are given, Exim runs in an interactive manner, prompting with a right angle bracket for addresses to be tested. </p>
<p> Unlike the <code>-be</code> test option, you cannot arrange for Exim to use the readline() function, because it is running as <i>root</i> and there are security issues. </p>
<p> Each address is handled as if it were the recipient address of a message (compare the <code>-bv</code> option). It is passed to the routers and the result is written to the standard output. However, any router that has <code>no_address_test</code> set is bypassed. This can make <code>-bt</code> easier to use for genuine routing tests if your first router passes everything to a scanner program. </p>
<p> The return code is 2 if any address failed outright; it is 1 if no address failed outright but at least one could not be resolved for some reason. Return code 0 is given only when all addresses succeed. </p>
<p> <code>Note</code>: When actually delivering a message, Exim removes duplicate recipient addresses after routing is complete, so that only one delivery takes place. This does not happen when testing with <code>-bt</code>; the full results of routing are always shown. </p>
<p> <code>Warning</code>: <code>-bt</code> can only do relatively simple testing. If any of the routers in the configuration makes any tests on the sender address of a message, you can use the <code>-f</code> option to set an appropriate sender when running <code>-bt</code> tests. Without it, the sender is assumed to be the calling user at the default qualifying domain. However, if you have set up (for example) routers whose behaviour depends on the contents of an incoming message, you cannot test those conditions using <code>-bt</code>. The <code>-N</code> option provides a possible way of doing such tests.</p>
<dt><code>-bV</code></p>
<dd>This option causes Exim to write the current version number, compilation number, and compilation date of the <i>exim</i> binary to the standard output. It also lists the DBM library that is being used, the optional modules (such as specific lookup types), the drivers that are included in the binary, and the name of the run time configuration file that is in use. </p>
<p> As part of its operation, <code>-bV</code> causes Exim to read and syntax check its configuration file. However, this is a static check only. It cannot check values that are to be expanded. For example, although a misspelt ACL verb is detected, an error in the verb&#8217;s arguments is not. You cannot rely on <code>-bV</code> alone to discover (for example) all the typos in the configuration; some realistic testing is needed. The <code>-bh</code> and <code>-N</code> options provide more dynamic testing facilities.</p>
<dt><code>-bv</code></p>
<dd>This option runs Exim in address verification mode, in which each argument is taken as a recipient address to be verified by the routers. (This does not involve any verification callouts). During normal operation, verification happens mostly as a consequence processing a <code>verify</code> condition in an ACL. If you want to test an entire ACL, possibly including callouts, see the <code>-bh</code> and <code>-bhc</code> options. </p>
<p> If verification fails, and the caller is not an admin user, no details of the failure are output, because these might contain sensitive information such as usernames and passwords for database lookups. </p>
<p> If no arguments are given, Exim runs in an interactive manner, prompting with a right angle bracket for addresses to be verified. </p>
<p> Unlike the <code>-be</code> test option, you cannot arrange for Exim to use the readline() function, because it is running as <i>exim</i> and there are security issues. </p>
<p> Verification differs from address testing (the <code>-bt</code> option) in that routers that have <code>no_verify</code> set are skipped, and if the address is accepted by a router that has <code>fail_verify</code> set, verification fails. The address is verified as a recipient if <code>-bv</code> is used; to test verification for a sender address, <code>-bvs</code> should be used. </p>
<p> If the <code>-v</code> option is not set, the output consists of a single line for each address, stating whether it was verified or not, and giving a reason in the latter case. Without <code>-v</code>, generating more than one address by redirection causes verification to end successfully, without considering the generated addresses. However, if just one address is generated, processing continues, and the generated address must verify successfully for the overall verification to succeed. </p>
<p> When <code>-v</code> is set, more details are given of how the address has been handled, and in the case of address redirection, all the generated addresses are also considered. Verification may succeed for some and fail for others. </p>
<p> The return code is 2 if any address failed outright; it is 1 if no address failed outright but at least one could not be resolved for some reason. Return code 0 is given only when all addresses succeed. </p>
<p> If any of the routers in the configuration makes any tests on the sender address of a message, you should use the <code>-f</code> option to set an appropriate sender when running <code>-bv</code> tests. Without it, the sender is assumed to be the calling user at the default qualifying domain.</p>
<dt><code>-bvs</code></p>
<dd>This option acts like <code>-bv</code>, but verifies the address as a sender rather than a recipient address. This affects any rewriting and qualification that might happen.</p>
<dt><code>-bw</code></p>
<dd>This option runs Exim as a daemon, awaiting incoming SMTP connections, similarly to the <code>-bd</code> option. All port specifications on the command-line and in the configuration file are ignored. Queue-running may not be specified. </p>
<p> In this mode, Exim expects to be passed a socket as fd 0 (stdin) which is listening for connections. This permits the system to start up and have inetd (or equivalent) listen on the SMTP ports, starting an Exim daemon for each port only when the first connection is received. </p>
<p> If the option is given as <code>-bw</code>&lt;<i>time</i>&gt; then the time is a timeout, after which the daemon will exit, which should cause inetd to listen once more.</p>
<dt><code>-C</code> &lt;<i>filelist</i>&gt;</p>
<dd>This option causes Exim to find the run time configuration file from the given list instead of from the list specified by the CONFIGURE_FILE compile-time setting. Usually, the list will consist of just a single file name, but it can be a colon-separated list of names. In this case, the first file that exists is used. Failure to open an existing file stops Exim from proceeding any further along the list, and an error is generated. </p>
<p> When this option is used by a caller other than root, and the list is different from the compiled-in list, Exim gives up its root privilege immediately, and runs with the real and effective uid and gid set to those of the caller. However, if a TRUSTED_CONFIG_LIST file is defined in Local/Makefile, that file contains a list of full pathnames, one per line, for configuration files which are trusted. Root privilege is retained for any configuration file so listed, as long as the caller is the Exim user (or the user specified in the CONFIGURE_OWNER option, if any), and as long as the configuration file is not writeable by inappropriate users or groups. </p>
<p> Leaving TRUSTED_CONFIG_LIST unset precludes the possibility of testing a configuration using <code>-C</code> right through message reception and delivery, even if the caller is root. The reception works, but by that time, Exim is running as the Exim user, so when it re-executes to regain privilege for the delivery, the use of <code>-C</code> causes privilege to be lost. However, root can test reception and delivery using two separate commands (one to put a message on the queue, using <code>-odq</code>, and another to do the delivery, using <code>-M</code>). </p>
<p> If ALT_CONFIG_PREFIX is defined in Local/Makefile, it specifies a prefix string with which any file named in a <code>-C</code> command line option must start. In addition, the file name must not contain the sequence /../. However, if the value of the <code>-C</code> option is identical to the value of CONFIGURE_FILE in Local/Makefile, Exim ignores <code>-C</code> and proceeds as usual. There is no default setting for ALT_CONFIG_PREFIX; when it is unset, any file name can be used with <code>-C</code>. </p>
<p> ALT_CONFIG_PREFIX can be used to confine alternative configuration files to a directory to which only root has access. This prevents someone who has broken into the Exim account from running a privileged Exim with an arbitrary configuration file. </p>
<p> The <code>-C</code> facility is useful for ensuring that configuration files are syntactically correct, but cannot be used for test deliveries, unless the caller is privileged, or unless it is an exotic configuration that does not require privilege. No check is made on the owner or group of the files specified by this option.</p>
<dt><code>-D</code>&lt;<i>macro</i>&gt;=&lt;<i>value</i>&gt;</p>
<dd>This option can be used to override macro definitions in the configuration file. However, like <code>-C</code>, if it is used by an unprivileged caller, it causes Exim to give up its root privilege. If DISABLE_D_OPTION is defined in Local/Makefile, the use of <code>-D</code> is completely disabled, and its use causes an immediate error exit. </p>
<p> If WHITELIST_D_MACROS is defined in Local/Makefile then it should be a colon-separated list of macros which are considered safe and, if <code>-D</code> only supplies macros from this list, and the values are acceptable, then Exim will not give up root privilege if the caller is root, the Exim run-time user, or the CONFIGURE_OWNER, if set. This is a transition mechanism and is expected to be removed in the future. Acceptable values for the macros satisfy the regexp: ^[A-Za-z0-9_/.-]*$ </p>
<p> The entire option (including equals sign if present) must all be within one command line item. <code>-D</code> can be used to set the value of a macro to the empty string, in which case the equals sign is optional. These two commands are synonymous: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>exim -DABC&nbsp;<wbr>&nbsp;<wbr>&#8230;<br />
&nbsp;<wbr>&nbsp;<wbr>exim -DABC=&nbsp;<wbr>&#8230; </p>
<p> To include spaces in a macro definition item, quotes must be used. If you use quotes, spaces are permitted around the macro name and the equals sign. For example: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>exim&nbsp;<wbr>&#8216;-D ABC&nbsp;<wbr>=&nbsp;<wbr>something&#8217;&nbsp;<wbr>&#8230; </p>
<p> <code>-D</code> may be repeated up to 10 times on a command line. Only macro names up to 22 letters long can be set.</p>
<dt><code>-d</code>&lt;<i>debug options</i>&gt;</p>
<dd>This option causes debugging information to be written to the standard error stream. It is restricted to admin users because debugging output may show database queries that contain password information. Also, the details of users&#8217; filter files should be protected. If a non-admin user uses <code>-d</code>, Exim writes an error message to the standard error stream and exits with a non-zero return code. </p>
<p> When <code>-d</code> is used, <code>-v</code> is assumed. If <code>-d</code> is given on its own, a lot of standard debugging data is output. This can be reduced, or increased to include some more rarely needed information, by directly following <code>-d</code> with a string made up of names preceded by plus or minus characters. These add or remove sets of debugging data, respectively. For example, <code>-d+filter</code> adds filter debugging, whereas <code>-d-all+filter</code> selects only filter debugging. <p> The all option excludes memory when used as +all, but includes it for -all. The reason for this is that +all is something that people tend to use when generating debug output for Exim maintainers. If +memory is included, an awful lot of output that is very rarely of interest is generated, so it now has to be explicitly requested. However, -all does turn everything off. </p>
<p> The resolver option produces output only if the DNS resolver was compiled with DEBUG enabled. This is not the case in some operating systems. Also, unfortunately, debugging output from the DNS resolver is written to stdout rather than stderr. </p>
<p> The default (<code>-d</code> with no argument) omits expand, filter, interface, load, memory, pid, resolver, and timestamp. However, the pid selector is forced when debugging is turned on for a daemon, which then passes it on to any re-executed Exims. Exim also automatically adds the pid to debug lines when several remote deliveries are run in parallel. </p>
<p> The timestamp selector causes the current time to be inserted at the start of all debug output lines. This can be useful when trying to track down delays in processing. </p>
<p> If the <code>debug_print</code> option is set in any driver, it produces output whenever any debugging is selected, or if <code>-v</code> is used.</p>
<dt><code>-dd</code>&lt;<i>debug options</i>&gt;</p>
<dd>This option behaves exactly like <code>-d</code> except when used on a command that starts a daemon process. In that case, debugging is turned off for the subprocesses that the daemon creates. Thus, it is useful for monitoring the behaviour of the daemon without creating as much output as full debugging does.</p>
<dt><code>-dropcr</code></p>
<dd>This is an obsolete option that is now a no-op. It used to affect the way Exim handled CR and LF characters in incoming messages.</p>
<dt><code>-E</code></p>
<dd>This option specifies that an incoming message is a locally-generated delivery failure report. It is used internally by Exim when handling delivery failures and is not intended for external use. Its only effect is to stop Exim generating certain messages to the postmaster, as otherwise message cascades could occur in some situations. As part of the same option, a message id may follow the characters <code>-E</code>. If it does, the log entry for the receipt of the new message contains the id, following &quot;R=&quot;, as a cross-reference.</p>
<dt><code>-e</code><i>x</i></p>
<dd>There are a number of Sendmail options starting with <code>-oe</code> which seem to be called by various programs without the leading <code>o</code> in the option. For example, the <code>vacation</code> program uses <code>-eq</code>. Exim treats all options of the form <code>-e</code><i>x</i> as synonymous with the corresponding <code>-oe</code><i>x</i> options.</p>
<dt><code>-F</code> &lt;<i>string</i>&gt;</p>
<dd>This option sets the sender&#8217;s full name for use when a locally-generated message is being accepted. In the absence of this option, the user&#8217;s <i>gecos</i> entry from the password data is used. As users are generally permitted to alter their <i>gecos</i> entries, no security considerations are involved. White space between <code>-F</code> and the &lt;<i>string</i>&gt; is optional.</p>
<dt><code>-f</code> &lt;<i>address</i>&gt;</p>
<dd>This option sets the address of the envelope sender of a locally-generated message (also known as the return path). The option can normally be used only by a trusted user, but <code>untrusted_set_sender</code> can be set to allow untrusted users to use it. </p>
<p> Processes running as root or the Exim user are always trusted. Other trusted users are defined by the <code>trusted_users</code> or <code>trusted_groups</code> options. In the absence of <code>-f</code>, or if the caller is not trusted, the sender of a local message is set to the caller&#8217;s login name at the default qualify domain. </p>
<p> There is one exception to the restriction on the use of <code>-f</code>: an empty sender can be specified by any user, trusted or not, to create a message that can never provoke a bounce. An empty sender can be specified either as an empty string, or as a pair of angle brackets with nothing between them, as in these examples of shell commands: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>exim -f&nbsp;<wbr>&#8216;&lt;&gt;&#8217;&nbsp;<wbr>user [at] domain<br />
&nbsp;<wbr>&nbsp;<wbr>exim -f&nbsp;<wbr>&quot;&quot;&nbsp;<wbr>user [at] domain </p>
<p> In addition, the use of <code>-f</code> is not restricted when testing a filter file with <code>-bf</code> or when testing or verifying addresses using the <code>-bt</code> or <code>-bv</code> options. </p>
<p> Allowing untrusted users to change the sender address does not of itself make it possible to send anonymous mail. Exim still checks that the <i>From:</i> header refers to the local user, and if it does not, it adds a <i>Sender:</i> header, though this can be overridden by setting <code>no_local_from_check</code>. </p>
<p> White space between <code>-f</code> and the &lt;<i>address</i>&gt; is optional (that is, they can be given as two arguments or one combined argument). The sender of a locally-generated message can also be set (when permitted) by an initial &quot;From &quot; line in the message &#8211; see the description of <code>-bm</code> above &#8211; but if <code>-f</code> is also present, it overrides &quot;From &quot;.</p>
<dt><code>-G</code></p>
<dd>This option is equivalent to an ACL applying: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>control&nbsp;<wbr>=&nbsp;<wbr>suppress_local_fixups </p>
<p> for every message received. Note that Sendmail will complain about such bad formatting, where Exim silently just does not fix it up. This may change in future. </p>
<p> As this affects audit information, the caller must be a trusted user to use this option.</p>
<dt><code>-h</code> &lt;<i>number</i>&gt;</p>
<dd>This option is accepted for compatibility with Sendmail, but has no effect. (In Sendmail it overrides the &quot;hop count&quot; obtained by counting <i>Received:</i> headers.)</p>
<dt><code>-i</code></p>
<dd>This option, which has the same effect as <code>-oi</code>, specifies that a dot on a line by itself should not terminate an incoming, non-SMTP message. I can find no documentation for this option in Solaris 2.4 Sendmail, but the <i>mailx</i> command in Solaris 2.4 uses it. See also <code>-ti</code>.</p>
<dt><code>-L</code> &lt;<i>tag</i>&gt;</p>
<dd>This option is equivalent to setting <code>syslog_processname</code> in the config file and setting <code>log_file_path</code> to syslog. Its use is restricted to administrators. The configuration file has to be read and parsed, to determine access rights, before this is set and takes effect, so early configuration file errors will not honour this flag. </p>
<p> The tag should not be longer than 32 characters.</p>
<dt><code>-M</code> &lt;<i>message id</i>&gt; &lt;<i>message id</i>&gt; &#8230;</p>
<dd>This option requests Exim to run a delivery attempt on each message in turn. If any of the messages are frozen, they are automatically thawed before the delivery attempt. The settings of <code>queue_domains</code>, <code>queue_smtp_domains</code>, and <code>hold_domains</code> are ignored. </p>
<p> Retry hints for any of the addresses are overridden &#8211; Exim tries to deliver even if the normal retry time has not yet been reached. This option requires the caller to be an admin user. However, there is an option called <code>prod_requires_admin</code> which can be set false to relax this restriction (and also the same requirement for the <code>-q</code>, <code>-R</code>, and <code>-S</code> options). </p>
<p> The deliveries happen synchronously, that is, the original Exim process does not terminate until all the delivery attempts have finished. No output is produced unless there is a serious error. If you want to see what is happening, use the <code>-v</code> option as well, or inspect Exim&#8217;s main log.</p>
<dt><code>-Mar</code> &lt;<i>message id</i>&gt; &lt;<i>address</i>&gt; &lt;<i>address</i>&gt; &#8230;</p>
<dd>This option requests Exim to add the addresses to the list of recipients of the message (&quot;ar&quot; for &quot;add recipients&quot;). The first argument must be a message id, and the remaining ones must be email addresses. However, if the message is active (in the middle of a delivery attempt), it is not altered. This option can be used only by an admin user.</p>
<dt><code>-MC</code> &lt;<i>transport</i>&gt; &lt;<i>hostname</i>&gt; &lt;<i>sequence number</i>&gt; &lt;<i>message id</i>&gt;</p>
<dd>This option is not intended for use by external callers. It is used internally by Exim to invoke another instance of itself to deliver a waiting message using an existing SMTP connection, which is passed as the standard input. This must be the final option, and the caller must be root or the Exim user in order to use it.</p>
<dt><code>-MCA</code></p>
<dd>This option is not intended for use by external callers. It is used internally by Exim in conjunction with the <code>-MC</code> option. It signifies that the connection to the remote host has been authenticated.</p>
<dt><code>-MCD</code></p>
<dd>This option is not intended for use by external callers. It is used internally by Exim in conjunction with the <code>-MC</code> option. It signifies that the remote host supports the ESMTP DSN extension.</p>
<dt><code>-MCG</code></p>
<dd>This option is not intended for use by external callers. It is used internally by Exim in conjunction with the <code>-MC</code> option. It signifies that an alternate queue is used, named by the following option.</p>
<dt><code>-MCP</code></p>
<dd>This option is not intended for use by external callers. It is used internally by Exim in conjunction with the <code>-MC</code> option. It signifies that the server to which Exim is connected supports pipelining.</p>
<dt><code>-MCQ</code> &lt;<i>process id</i>&gt; &lt;<i>pipe fd</i>&gt;</p>
<dd>This option is not intended for use by external callers. It is used internally by Exim in conjunction with the <code>-MC</code> option when the original delivery was started by a queue runner. It passes on the process id of the queue runner, together with the file descriptor number of an open pipe. Closure of the pipe signals the final completion of the sequence of processes that are passing messages through the same SMTP connection.</p>
<dt><code>-MCS</code></p>
<dd>This option is not intended for use by external callers. It is used internally by Exim in conjunction with the <code>-MC</code> option, and passes on the fact that the SMTP SIZE option should be used on messages delivered down the existing connection.</p>
<dt><code>-MCT</code></p>
<dd>This option is not intended for use by external callers. It is used internally by Exim in conjunction with the <code>-MC</code> option, and passes on the fact that the host to which Exim is connected supports TLS encryption.</p>
<dt><code>-Mc</code> &lt;<i>message id</i>&gt; &lt;<i>message id</i>&gt; &#8230;</p>
<dd>This option requests Exim to run a delivery attempt on each message in turn, but unlike the <code>-M</code> option, it does check for retry hints, and respects any that are found. This option is not very useful to external callers. It is provided mainly for internal use by Exim when it needs to re-invoke itself in order to regain root privilege for a delivery. However, <code>-Mc</code> can be useful when testing, in order to run a delivery that respects retry times and other options such as <code>hold_domains</code> that are overridden when <code>-M</code> is used. Such a delivery does not count as a queue run. If you want to run a specific delivery as if in a queue run, you should use <code>-q</code> with a message id argument. A distinction between queue run deliveries and other deliveries is made in one or two places.</p>
<dt><code>-Mes</code> &lt;<i>message id</i>&gt; &lt;<i>address</i>&gt;</p>
<dd>This option requests Exim to change the sender address in the message to the given address, which must be a fully qualified address or &quot;&lt;&gt;&quot; (&quot;es&quot; for &quot;edit sender&quot;). There must be exactly two arguments. The first argument must be a message id, and the second one an email address. However, if the message is active (in the middle of a delivery attempt), its status is not altered. This option can be used only by an admin user.</p>
<dt><code>-Mf</code> &lt;<i>message id</i>&gt; &lt;<i>message id</i>&gt; &#8230;</p>
<dd>This option requests Exim to mark each listed message as &quot;frozen&quot;. This prevents any delivery attempts taking place until the message is &quot;thawed&quot;, either manually or as a result of the <code>auto_thaw</code> configuration option. However, if any of the messages are active (in the middle of a delivery attempt), their status is not altered. This option can be used only by an admin user.</p>
<dt><code>-Mg</code> &lt;<i>message id</i>&gt; &lt;<i>message id</i>&gt; &#8230;</p>
<dd>This option requests Exim to give up trying to deliver the listed messages, including any that are frozen. However, if any of the messages are active, their status is not altered. For non-bounce messages, a delivery error message is sent to the sender, containing the text &quot;cancelled by administrator&quot;. Bounce messages are just discarded. This option can be used only by an admin user.</p>
<dt><code>-Mmad</code> &lt;<i>message id</i>&gt; &lt;<i>message id</i>&gt; &#8230;</p>
<dd>This option requests Exim to mark all the recipient addresses in the messages as already delivered (&quot;mad&quot; for &quot;mark all delivered&quot;). However, if any message is active (in the middle of a delivery attempt), its status is not altered. This option can be used only by an admin user.</p>
<dt><code>-Mmd</code> &lt;<i>message id</i>&gt; &lt;<i>address</i>&gt; &lt;<i>address</i>&gt; &#8230;</p>
<dd>This option requests Exim to mark the given addresses as already delivered (&quot;md&quot; for &quot;mark delivered&quot;). The first argument must be a message id, and the remaining ones must be email addresses. These are matched to recipient addresses in the message in a case-sensitive manner. If the message is active (in the middle of a delivery attempt), its status is not altered. This option can be used only by an admin user.</p>
<dt><code>-Mrm</code> &lt;<i>message id</i>&gt; &lt;<i>message id</i>&gt; &#8230;</p>
<dd>This option requests Exim to remove the given messages from the queue. No bounce messages are sent; each message is simply forgotten. However, if any of the messages are active, their status is not altered. This option can be used only by an admin user or by the user who originally caused the message to be placed on the queue.</p>
<dt><code>-Mset</code> &lt;<i>message id</i>&gt;</p>
<dd>This option is useful only in conjunction with <code>-be</code> (that is, when testing string expansions). Exim loads the given message from its spool before doing the test expansions, thus setting message-specific variables such as <i>$message_size</i> and the header variables. The <i>$recipients</i> variable is made available. This feature is provided to make it easier to test expansions that make use of these variables. However, this option can be used only by an admin user. See also <code>-bem</code>.</p>
<dt><code>-Mt</code> &lt;<i>message id</i>&gt; &lt;<i>message id</i>&gt; &#8230;</p>
<dd>This option requests Exim to &quot;thaw&quot; any of the listed messages that are &quot;frozen&quot;, so that delivery attempts can resume. However, if any of the messages are active, their status is not altered. This option can be used only by an admin user.</p>
<dt><code>-Mvb</code> &lt;<i>message id</i>&gt;</p>
<dd>This option causes the contents of the message body (-D) spool file to be written to the standard output. This option can be used only by an admin user.</p>
<dt><code>-Mvc</code> &lt;<i>message id</i>&gt;</p>
<dd>This option causes a copy of the complete message (header lines plus body) to be written to the standard output in RFC 2822 format. This option can be used only by an admin user.</p>
<dt><code>-Mvh</code> &lt;<i>message id</i>&gt;</p>
<dd>This option causes the contents of the message headers (-H) spool file to be written to the standard output. This option can be used only by an admin user.</p>
<dt><code>-Mvl</code> &lt;<i>message id</i>&gt;</p>
<dd>This option causes the contents of the message log spool file to be written to the standard output. This option can be used only by an admin user.</p>
<dt><code>-m</code></p>
<dd>This is apparently a synonym for <code>-om</code> that is accepted by Sendmail, so Exim treats it that way too.</p>
<dt><code>-N</code></p>
<dd>This is a debugging option that inhibits delivery of a message at the transport level. It implies <code>-v</code>. Exim goes through many of the motions of delivery &#8211; it just doesn&#8217;t actually transport the message, but instead behaves as if it had successfully done so. However, it does not make any updates to the retry database, and the log entries for deliveries are flagged with &quot;*&gt;&quot; rather than &quot;=&gt;&quot;. </p>
<p> Because <code>-N</code> discards any message to which it applies, only root or the Exim user are allowed to use it with <code>-bd</code>, <code>-q</code>, <code>-R</code> or <code>-M</code>. In other words, an ordinary user can use it only when supplying an incoming message to which it will apply. Although transportation never fails when <code>-N</code> is set, an address may be deferred because of a configuration problem on a transport, or a routing problem. Once <code>-N</code> has been used for a delivery attempt, it sticks to the message, and applies to any subsequent delivery attempts that may happen for that message.</p>
<dt><code>-n</code></p>
<dd>This option is interpreted by Sendmail to mean &quot;no aliasing&quot;. For normal modes of operation, it is ignored by Exim. When combined with <code>-bP</code> it makes the output more terse (suppresses option names, environment values and config pretty printing).</p>
<dt><code>-O</code> &lt;<i>data</i>&gt;</p>
<dd>This option is interpreted by Sendmail to mean set option. It is ignored by Exim.</p>
<dt><code>-oA</code> &lt;<i>file name</i>&gt;</p>
<dd>This option is used by Sendmail in conjunction with <code>-bi</code> to specify an alternative alias file name. Exim handles <code>-bi</code> differently; see the description above.</p>
<dt><code>-oB</code> &lt;<i>n</i>&gt;</p>
<dd>This is a debugging option which limits the maximum number of messages that can be delivered down one SMTP connection, overriding the value set in any smtp transport. If &lt;<i>n</i>&gt; is omitted, the limit is set to 1.</p>
<dt><code>-odb</code></p>
<dd>This option applies to all modes in which Exim accepts incoming messages, including the listening daemon. It requests &quot;background&quot; delivery of such messages, which means that the accepting process automatically starts a delivery process for each message received, but does not wait for the delivery processes to finish. </p>
<p> When all the messages have been received, the reception process exits, leaving the delivery processes to finish in their own time. The standard output and error streams are closed at the start of each delivery process. This is the default action if none of the <code>-od</code> options are present. </p>
<p> If one of the queueing options in the configuration file (<code>queue_only</code> or <code>queue_only_file</code>, for example) is in effect, <code>-odb</code> overrides it if <code>queue_only_override</code> is set true, which is the default setting. If <code>queue_only_override</code> is set false, <code>-odb</code> has no effect.</p>
<dt><code>-odf</code></p>
<dd>This option requests &quot;foreground&quot; (synchronous) delivery when Exim has accepted a locally-generated message. (For the daemon it is exactly the same as <code>-odb</code>.) A delivery process is automatically started to deliver the message, and Exim waits for it to complete before proceeding. </p>
<p> The original Exim reception process does not finish until the delivery process for the final message has ended. The standard error stream is left open during deliveries. </p>
<p> However, like <code>-odb</code>, this option has no effect if <code>queue_only_override</code> is false and one of the queueing options in the configuration file is in effect. </p>
<p> If there is a temporary delivery error during foreground delivery, the message is left on the queue for later delivery, and the original reception process exits.</p>
<dt><code>-odi</code></p>
<dd>This option is synonymous with <code>-odf</code>. It is provided for compatibility with Sendmail.</p>
<dt><code>-odq</code></p>
<dd>This option applies to all modes in which Exim accepts incoming messages, including the listening daemon. It specifies that the accepting process should not automatically start a delivery process for each message received. Messages are placed on the queue, and remain there until a subsequent queue runner process encounters them. There are several configuration options (such as <code>queue_only</code>) that can be used to queue incoming messages under certain conditions. This option overrides all of them and also <code>-odqs</code>. It always forces queueing.</p>
<dt><code>-odqs</code></p>
<dd>This option is a hybrid between <code>-odb</code>/<code>-odi</code> and <code>-odq</code>. However, like <code>-odb</code> and <code>-odi</code>, this option has no effect if <code>queue_only_override</code> is false and one of the queueing options in the configuration file is in effect. </p>
<p> When <code>-odqs</code> does operate, a delivery process is started for each incoming message, in the background by default, but in the foreground if <code>-odi</code> is also present. The recipient addresses are routed, and local deliveries are done in the normal way. However, if any SMTP deliveries are required, they are not done at this time, so the message remains on the queue until a subsequent queue runner process encounters it. Because routing was done, Exim knows which messages are waiting for which hosts, and so a number of messages for the same host can be sent in a single SMTP connection. The <code>queue_smtp_domains</code> configuration option has the same effect for specific domains. See also the <code>-qq</code> option.</p>
<dt><code>-oee</code></p>
<dd>If an error is detected while a non-SMTP message is being received (for example, a malformed address), the error is reported to the sender in a mail message. </p>
<p> Provided this error message is successfully sent, the Exim receiving process exits with a return code of zero. If not, the return code is 2 if the problem is that the original message has no recipients, or 1 for any other error. This is the default <code>-oe</code><i>x</i> option if Exim is called as <i>rmail</i>.</p>
<dt><code>-oem</code></p>
<dd>This is the same as <code>-oee</code>, except that Exim always exits with a non-zero return code, whether or not the error message was successfully sent. This is the default <code>-oe</code><i>x</i> option, unless Exim is called as <i>rmail</i>.</p>
<dt><code>-oep</code></p>
<dd>If an error is detected while a non-SMTP message is being received, the error is reported by writing a message to the standard error file (stderr). The return code is 1 for all errors.</p>
<dt><code>-oeq</code></p>
<dd>This option is supported for compatibility with Sendmail, but has the same effect as <code>-oep</code>.</p>
<dt><code>-oew</code></p>
<dd>This option is supported for compatibility with Sendmail, but has the same effect as <code>-oem</code>.</p>
<dt><code>-oi</code></p>
<dd>This option, which has the same effect as <code>-i</code>, specifies that a dot on a line by itself should not terminate an incoming, non-SMTP message. Otherwise, a single dot does terminate, though Exim does no special processing for other lines that start with a dot. This option is set by default if Exim is called as <i>rmail</i>. See also <code>-ti</code>.</p>
<dt><code>-oitrue</code></p>
<dd>This option is treated as synonymous with <code>-oi</code>.</p>
<dt><code>-oMa</code> &lt;<i>host address</i>&gt;</p>
<dd>A number of options starting with <code>-oM</code> can be used to set values associated with remote hosts on locally-submitted messages (that is, messages not received over TCP/IP). These options can be used by any caller in conjunction with the <code>-bh</code>, <code>-be</code>, <code>-bf</code>, <code>-bF</code>, <code>-bt</code>, or <code>-bv</code> testing options. In other circumstances, they are ignored unless the caller is trusted. </p>
<p> The <code>-oMa</code> option sets the sender host address. This may include a port number at the end, after a full stop (period). For example: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>exim -bs -oMa 10.9.8.7.1234 </p>
<p> An alternative syntax is to enclose the IP address in square brackets, followed by a colon and the port number: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>exim -bs -oMa&nbsp;<wbr>[10.9.8.7]:1234 </p>
<p> The IP address is placed in the <i>$sender_host_address</i> variable, and the port, if present, in <i>$sender_host_port</i>. If both <code>-oMa</code> and <code>-bh</code> are present on the command line, the sender host IP address is taken from whichever one is last.</p>
<dt><code>-oMaa</code> &lt;<i>name</i>&gt;</p>
<dd>See <code>-oMa</code> above for general remarks about the <code>-oM</code> options. The <code>-oMaa</code> option sets the value of <i>$sender_host_authenticated</i> (the authenticator name). This option can be used with <code>-bh</code> and <code>-bs</code> to set up an authenticated SMTP session without actually using the SMTP AUTH command.</p>
<dt><code>-oMai</code> &lt;<i>string</i>&gt;</p>
<dd>See <code>-oMa</code> above for general remarks about the <code>-oM</code> options. The <code>-oMai</code> option sets the value of <i>$authenticated_id</i> (the id that was authenticated). This overrides the default value (the caller&#8217;s login id, except with <code>-bh</code>, where there is no default) for messages from local sources.</p>
<dt><code>-oMas</code> &lt;<i>address</i>&gt;</p>
<dd>See <code>-oMa</code> above for general remarks about the <code>-oM</code> options. The <code>-oMas</code> option sets the authenticated sender value in <i>$authenticated_sender</i>. It overrides the sender address that is created from the caller&#8217;s login id for messages from local sources, except when <code>-bh</code> is used, when there is no default. For both <code>-bh</code> and <code>-bs</code>, an authenticated sender that is specified on a MAIL command overrides this value.</p>
<dt><code>-oMi</code> &lt;<i>interface address</i>&gt;</p>
<dd>See <code>-oMa</code> above for general remarks about the <code>-oM</code> options. The <code>-oMi</code> option sets the IP interface address value. A port number may be included, using the same syntax as for <code>-oMa</code>. The interface address is placed in <i>$received_ip_address</i> and the port number, if present, in <i>$received_port</i>.</p>
<dt><code>-oMm</code> &lt;<i>message reference</i>&gt;</p>
<dd>See <code>-oMa</code> above for general remarks about the <code>-oM</code> options. The <code>-oMm</code> option sets the message reference, e.g. message-id, and is logged during delivery. This is useful when some kind of audit trail is required to tie messages together. The format of the message reference is checked and will abort if the format is invalid. The option will only be accepted if exim is running in trusted mode, not as any regular user. </p>
<p> The best example of a message reference is when Exim sends a bounce message. The message reference is the message-id of the original message for which Exim is sending the bounce.</p>
<dt><code>-oMr</code> &lt;<i>protocol name</i>&gt;</p>
<dd>See <code>-oMa</code> above for general remarks about the <code>-oM</code> options. The <code>-oMr</code> option sets the received protocol value that is stored in <i>$received_protocol</i>. However, it does not apply (and is ignored) when <code>-bh</code> or <code>-bs</code> is used. For <code>-bh</code>, the protocol is forced to one of the standard SMTP protocol names. For <code>-bs</code>, the protocol is always &quot;local-&quot; followed by one of those same names. For <code>-bS</code> (batched SMTP) however, the protocol can be set by <code>-oMr</code>.</p>
<dt><code>-oMs</code> &lt;<i>host name</i>&gt;</p>
<dd>See <code>-oMa</code> above for general remarks about the <code>-oM</code> options. The <code>-oMs</code> option sets the sender host name in <i>$sender_host_name</i>. When this option is present, Exim does not attempt to look up a host name from an IP address; it uses the name it is given.</p>
<dt><code>-oMt</code> &lt;<i>ident string</i>&gt;</p>
<dd>See <code>-oMa</code> above for general remarks about the <code>-oM</code> options. The <code>-oMt</code> option sets the sender ident value in <i>$sender_ident</i>. The default setting for local callers is the login id of the calling process, except when <code>-bh</code> is used, when there is no default.</p>
<dt><code>-om</code></p>
<dd>In Sendmail, this option means &quot;me too&quot;, indicating that the sender of a message should receive a copy of the message if the sender appears in an alias expansion. Exim always does this, so the option does nothing.</p>
<dt><code>-oo</code></p>
<dd>This option is ignored. In Sendmail it specifies &quot;old style headers&quot;, whatever that means.</p>
<dt><code>-oP</code> &lt;<i>path</i>&gt;</p>
<dd>This option is useful only in conjunction with <code>-bd</code> or <code>-q</code> with a time value. The option specifies the file to which the process id of the daemon is written. When <code>-oX</code> is used with <code>-bd</code>, or when <code>-q</code> with a time is used without <code>-bd</code>, this is the only way of causing Exim to write a pid file, because in those cases, the normal pid file is not used.</p>
<dt><code>-or</code> &lt;<i>time</i>&gt;</p>
<dd>This option sets a timeout value for incoming non-SMTP messages. If it is not set, Exim will wait forever for the standard input. The value can also be set by the <code>receive_timeout</code> option.</p>
<dt><code>-os</code> &lt;<i>time</i>&gt;</p>
<dd>This option sets a timeout value for incoming SMTP messages. The timeout applies to each SMTP command and block of data. The value can also be set by the <code>smtp_receive_timeout</code> option; it defaults to 5 minutes.</p>
<dt><code>-ov</code></p>
<dd>This option has exactly the same effect as <code>-v</code>.</p>
<dt><code>-oX</code> &lt;<i>number or string</i>&gt;</p>
<dd>This option is relevant only when the <code>-bd</code> (start listening daemon) option is also given. It controls which ports and interfaces the daemon uses. When <code>-oX</code> is used to start a daemon, no pid file is written unless <code>-oP</code> is also present to specify a pid file name.</p>
<dt><code>-pd</code></p>
<dd>This option applies when an embedded Perl interpreter is linked with Exim. It overrides the setting of the <code>perl_at_start</code> option, forcing the starting of the interpreter to be delayed until it is needed.</p>
<dt><code>-ps</code></p>
<dd>This option applies when an embedded Perl interpreter is linked with Exim. It overrides the setting of the <code>perl_at_start</code> option, forcing the starting of the interpreter to occur as soon as Exim is started.</p>
<dt><code>-p</code>&lt;<i>rval</i>&gt;:&lt;<i>sval</i>&gt;</p>
<dd>For compatibility with Sendmail, this option is equivalent to </p>
<p>&nbsp;<wbr>&nbsp;<wbr>-oMr&nbsp;<wbr>&lt;<i>rval</i>&gt;&nbsp;<wbr>-oMs&nbsp;<wbr>&lt;<i>sval</i>&gt; </p>
<p> It sets the incoming protocol and host name (for trusted callers). The host name and its colon can be omitted when only the protocol is to be set. Note the Exim already has two private options, <code>-pd</code> and <code>-ps</code>, that refer to embedded Perl. It is therefore impossible to set a protocol value of d or s using this option (but that does not seem a real limitation).</p>
<dt><code>-q</code></p>
<dd>This option is normally restricted to admin users. However, there is a configuration option called <code>prod_requires_admin</code> which can be set false to relax this restriction (and also the same requirement for the <code>-M</code>, <code>-R</code>, and <code>-S</code> options). </p>
<p> If other commandline options do not specify an action, the <code>-q</code> option starts one queue runner process. This scans the queue of waiting messages, and runs a delivery process for each one in turn. It waits for each delivery process to finish before starting the next one. A delivery process may not actually do any deliveries if the retry times for the addresses have not been reached. Use <code>-qf</code> (see below) if you want to override this. </p>
<p> If the delivery process spawns other processes to deliver other messages down passed SMTP connections, the queue runner waits for these to finish before proceeding. </p>
<p> When all the queued messages have been considered, the original queue runner process terminates. In other words, a single pass is made over the waiting mail, one message at a time. Use <code>-q</code> with a time (see below) if you want this to be repeated periodically. </p>
<p> Exim processes the waiting messages in an unpredictable order. It isn&#8217;t very random, but it is likely to be different each time, which is all that matters. If one particular message screws up a remote MTA, other messages to the same MTA have a chance of getting through if they get tried first. </p>
<p> It is possible to cause the messages to be processed in lexical message id order, which is essentially the order in which they arrived, by setting the <code>queue_run_in_order</code> option, but this is not recommended for normal use.</p>
<dt><code>-q</code>&lt;<i>qflags</i>&gt;</p>
<dd>The <code>-q</code> option may be followed by one or more flag letters that change its behaviour. They are all optional, but if more than one is present, they must appear in the correct order. Each flag is described in a separate item below.</p>
<dt><code>-qq&#8230;</code></p>
<dd>An option starting with <code>-qq</code> requests a two-stage queue run. In the first stage, the queue is scanned as if the <code>queue_smtp_domains</code> option matched every domain. Addresses are routed, local deliveries happen, but no remote transports are run. </p>
<p> The hints database that remembers which messages are waiting for specific hosts is updated, as if delivery to those hosts had been deferred. After this is complete, a second, normal queue scan happens, with routing and delivery taking place as normal. Messages that are routed to the same host should mostly be delivered down a single SMTP connection because of the hints that were set up during the first queue scan. This option may be useful for hosts that are connected to the Internet intermittently.</p>
<dt><code>-q[q]i&#8230;</code></p>
<dd>If the <i>i</i> flag is present, the queue runner runs delivery processes only for those messages that haven&#8217;t previously been tried. (<i>i</i> stands for &quot;initial delivery&quot;.) This can be helpful if you are putting messages on the queue using <code>-odq</code> and want a queue runner just to process the new messages.</p>
<dt><code>-q[q][i]f&#8230;</code></p>
<dd>If one <i>f</i> flag is present, a delivery attempt is forced for each non-frozen message, whereas without <i>f</i> only those non-frozen addresses that have passed their retry times are tried.</p>
<dt><code>-q[q][i]ff&#8230;</code></p>
<dd>If <i>ff</i> is present, a delivery attempt is forced for every message, whether frozen or not.</p>
<dt><code>-q[q][i][f[f]]l</code></p>
<dd>The <i>l</i> (the letter &quot;ell&quot;) flag specifies that only local deliveries are to be done. If a message requires any remote deliveries, it remains on the queue for later delivery.</p>
<dt><code>-q[q][i][f[f]][l][G&lt;name&gt;[/&lt;time&gt;]]]</code></p>
<dd>If the <i>G</i> flag and a name is present, the queue runner operates on the queue with the given name rather than the default queue. The name should not contain a <i>/</i> character. For a periodic queue run (see below) append to the name a slash and a time value. </p>
<p> If other commandline options specify an action, a <i>-qG&lt;name&gt;</i> option will specify a queue to operate on. For example: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>exim -bp -qGquarantine<br />
&nbsp;<wbr>&nbsp;<wbr>mailq -qGquarantine<br />
&nbsp;<wbr>&nbsp;<wbr>exim -qGoffpeak -Rf&nbsp;<wbr>@special.domain.example</p>
<dt><code>-q</code>&lt;<i>qflags</i>&gt; &lt;<i>start id</i>&gt; &lt;<i>end id</i>&gt;</p>
<dd>When scanning the queue, Exim can be made to skip over messages whose ids are lexically less than a given value by following the <code>-q</code> option with a starting message id. For example: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>exim -q 0t5C6f-0000c8-00 </p>
<p> Messages that arrived earlier than 0t5C6f-0000c8-00 are not inspected. If a second message id is given, messages whose ids are lexically greater than it are also skipped. If the same id is given twice, for example, </p>
<p>&nbsp;<wbr>&nbsp;<wbr>exim -q 0t5C6f-0000c8-00 0t5C6f-0000c8-00 </p>
<p> just one delivery process is started, for that message. This differs from <code>-M</code> in that retry data is respected, and it also differs from <code>-Mc</code> in that it counts as a delivery from a queue run. Note that the selection mechanism does not affect the order in which the messages are scanned. There are also other ways of selecting specific sets of messages for delivery in a queue run &#8211; see <code>-R</code> and <code>-S</code>.</p>
<dt><code>-q</code>&lt;<i>qflags</i>&gt;&lt;<i>time</i>&gt;</p>
<dd>When a time value is present, the <code>-q</code> option causes Exim to run as a daemon, starting a queue runner process at intervals specified by the given time value. This form of the <code>-q</code> option is commonly combined with the <code>-bd</code> option, in which case a single daemon process handles both functions. A common way of starting up a combined daemon at system boot time is to use a command such as </p>
<p>&nbsp;<wbr>&nbsp;<wbr>/usr/exim/bin/exim -bd -q30m </p>
<p> Such a daemon listens for incoming SMTP calls, and also starts a queue runner process every 30 minutes. </p>
<p> When a daemon is started by <code>-q</code> with a time value, but without <code>-bd</code>, no pid file is written unless one is explicitly requested by the <code>-oP</code> option.</p>
<dt><code>-qR</code>&lt;<i>rsflags</i>&gt; &lt;<i>string</i>&gt;</p>
<dd>This option is synonymous with <code>-R</code>. It is provided for Sendmail compatibility.</p>
<dt><code>-qS</code>&lt;<i>rsflags</i>&gt; &lt;<i>string</i>&gt;</p>
<dd>This option is synonymous with <code>-S</code>.</p>
<dt><code>-R</code>&lt;<i>rsflags</i>&gt; &lt;<i>string</i>&gt;</p>
<dd>The &lt;<i>rsflags</i>&gt; may be empty, in which case the white space before the string is optional, unless the string is <i>f</i>, <i>ff</i>, <i>r</i>, <i>rf</i>, or <i>rff</i>, which are the possible values for &lt;<i>rsflags</i>&gt;. White space is required if &lt;<i>rsflags</i>&gt; is not empty. </p>
<p> This option is similar to <code>-q</code> with no time value, that is, it causes Exim to perform a single queue run, except that, when scanning the messages on the queue, Exim processes only those that have at least one undelivered recipient address containing the given string, which is checked in a case-independent way. If the &lt;<i>rsflags</i>&gt; start with <i>r</i>, &lt;<i>string</i>&gt; is interpreted as a regular expression; otherwise it is a literal string. </p>
<p> If you want to do periodic queue runs for messages with specific recipients, you can combine <code>-R</code> with <code>-q</code> and a time value. For example: </p>
<p>&nbsp;<wbr>&nbsp;<wbr>exim -q25m -R&nbsp;<wbr>@special.domain.example </p>
<p> This example does a queue run for messages with recipients in the given domain every 25 minutes. Any additional flags that are specified with <code>-q</code> are applied to each queue run. </p>
<p> Once a message is selected for delivery by this mechanism, all its addresses are processed. For the first selected message, Exim overrides any retry information and forces a delivery attempt for each undelivered address. This means that if delivery of any address in the first message is successful, any existing retry information is deleted, and so delivery attempts for that address in subsequently selected messages (which are processed without forcing) will run. However, if delivery of any address does not succeed, the retry information is updated, and in subsequently selected messages, the failing address will be skipped. </p>
<p> If the &lt;<i>rsflags</i>&gt; contain <i>f</i> or <i>ff</i>, the delivery forcing applies to all selected messages, not just the first; frozen messages are included when <i>ff</i> is present. </p>
<p> The <code>-R</code> option makes it straightforward to initiate delivery of all messages to a given domain after a host has been down for some time. When the SMTP command ETRN is accepted by its ACL, its default effect is to run Exim with the <code>-R</code> option, but it can be configured to run an arbitrary command instead.</p>
<dt><code>-r</code></p>
<dd>This is a documented (for Sendmail) obsolete alternative name for <code>-f</code>.</p>
<dt><code>-S</code>&lt;<i>rsflags</i>&gt; &lt;<i>string</i>&gt;</p>
<dd>This option acts like <code>-R</code> except that it checks the string against each message&#8217;s sender instead of against the recipients. If <code>-R</code> is also set, both conditions must be met for a message to be selected. If either of the options has <i>f</i> or <i>ff</i> in its flags, the associated action is taken.</p>
<dt><code>-Tqt</code> &lt;<i>times</i>&gt;</p>
<dd>This is an option that is exclusively for use by the Exim testing suite. It is not recognized when Exim is run normally. It allows for the setting up of explicit &quot;queue times&quot; so that various warning/retry features can be tested.</p>
<dt><code>-t</code></p>
<dd>When Exim is receiving a locally-generated, non-SMTP message on its standard input, the <code>-t</code> option causes the recipients of the message to be obtained from the <i>To:</i>, <i>Cc:</i>, and <i>Bcc:</i> header lines in the message instead of from the command arguments. The addresses are extracted before any rewriting takes place and the <i>Bcc:</i> header line, if present, is then removed. </p>
<p> If the command has any arguments, they specify addresses to which the message is <i>not</i> to be delivered. That is, the argument addresses are removed from the recipients list obtained from the headers. This is compatible with Smail 3 and in accordance with the documented behaviour of several versions of Sendmail, as described in man pages on a number of operating systems (e.g. Solaris 8, IRIX 6.5, HP-UX 11). However, some versions of Sendmail <i>add</i> argument addresses to those obtained from the headers, and the O&#8217;Reilly Sendmail book documents it that way. Exim can be made to add argument addresses instead of subtracting them by setting the option <code>extract_addresses_remove_arguments</code> false. </p>
<p> If there are any <code>Resent-</code> header lines in the message, Exim extracts recipients from all <i>Resent-To:</i>, <i>Resent-Cc:</i>, and <i>Resent-Bcc:</i> header lines instead of from <i>To:</i>, <i>Cc:</i>, and <i>Bcc:</i>. This is for compatibility with Sendmail and other MTAs. (Prior to release 4.20, Exim gave an error if <code>-t</code> was used in conjunction with <code>Resent-</code> header lines.) </p>
<p> RFC 2822 talks about different sets of <code>Resent-</code> header lines (for when a message is resent several times). The RFC also specifies that they should be added at the front of the message, and separated by <i>Received:</i> lines. It is not at all clear how <code>-t</code> should operate in the present of multiple sets, nor indeed exactly what constitutes a &quot;set&quot;. In practice, it seems that MUAs do not follow the RFC. The <code>Resent-</code> lines are often added at the end of the header, and if a message is resent more than once, it is common for the original set of <code>Resent-</code> headers to be renamed as <code>X-Resent-</code> when a new set is added. This removes any possible ambiguity.</p>
<dt><code>-ti</code></p>
<dd>This option is exactly equivalent to <code>-t</code> <code>-i</code>. It is provided for compatibility with Sendmail.</p>
<dt><code>-tls-on-connect</code></p>
<dd>This option is available when Exim is compiled with TLS support. It forces all incoming SMTP connections to behave as if the incoming port is listed in the <code>tls_on_connect_ports</code> option.</p>
<dt><code>-U</code></p>
<dd>Sendmail uses this option for &quot;initial message submission&quot;, and its documentation states that in future releases, it may complain about syntactically invalid messages rather than fixing them when this flag is not set. Exim ignores this option.</p>
<dt><code>-v</code></p>
<dd>This option causes Exim to write information to the standard error stream, describing what it is doing. In particular, it shows the log lines for receiving and delivering a message, and if an SMTP connection is made, the SMTP dialogue is shown. Some of the log lines shown may not actually be written to the log if the setting of <code>log_selector</code> discards them. Any relevant selectors are shown with each log line. If none are shown, the logging is unconditional.</p>
<dt><code>-x</code></p>
<dd>AIX uses <code>-x</code> for a private purpose (&quot;mail from a local mail program has National Language Support extended characters in the body of the mail item&quot;). It sets <code>-x</code> when calling the MTA from its <code>mail</code> command. Exim ignores this option.</p>
<dt><code>-X</code> &lt;<i>logfile</i>&gt;</p>
<dd>This option is interpreted by Sendmail to cause debug information to be sent to the named file. It is ignored by Exim.</p>
<dt><code>-z</code> &lt;<i>log-line</i>&gt;</p>
<dd>This option writes its argument to Exim&#8217;s logfile. Use is restricted to administrators; the intent is for operational notes. Quotes should be used to maintain a multi-word item as a single argument, under most shells. </p>
</dl>
