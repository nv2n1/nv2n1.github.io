<h3>Introduction</h3>
<p> This document describes the API changes the library users should be aware of before upgrading to each respective version. It is our plan to have the amount of changes requiring changing the client code go to a minimum after the library hits the 1.0.0 version. </p>
<p> Depracated API items (classes, methods, etc.) are designated as such in this document. The first release where support for such items can be dropped entirely must be issued at <i>least five months</i> after the issue of the release that announced the deprecation and at the same time have, relatively to the deprecating release, either:</p>
<dl>
<dt>&bull;</p>
<dd> a higher major version number, or</p>
<dt>&bull;</p>
<dd> a higher minor version number, or</p>
<dt>&bull;</p>
<dd> a patchlevel number that is <i>by at least five</i> greater. </p>
<p> These criteria are likely to tighten in the future as hawkey matures. </p>
<p> Actual changes in the API are then announced in this document as well. ABI changes including changes in functions&#8217; parameter counts or types or removal of public symbols from <code>libhawkey</code> imply an increase in the library&#8217;s SONAME version.</dl>
<h3>Changes in 0.2.10</h3>
<h3>Python bindings</h3>
<p> <code>Query.filter()</code> now returns a new instance of <code>Query</code>, the same as the original with the new filtering applied. This allows for greater flexibility handling the <code>Query</code> objects and resembles the way <code>QuerySets</code> behave in Django. </p>
<p> In practice the following code will stop working as expected: </p>
<pre>
q = hawkey.Query(self.sack)
q.filter(name__eq=&quot;flying&quot;)
# processing the query ...
</pre>
<p> It needs to be changed to: </p>
<pre>
q = hawkey.Query(self.sack)
q = q.filter(name__eq=&quot;flying&quot;)
# processing the query ...
</pre>
<p> The original semantics is now available via the <code>Query.filterm()</code> method, so the following will also work: </p>
<pre>
q = hawkey.Query(self.sack)
q.filterm(name__eq=&quot;flying&quot;)
# processing the query ...
</pre>
<h3>Changes in 0.2.11</h3>
<h3>Python bindings</h3>
<p> In Python&#8217;s <code>Package</code> instances accessors for string attributes now return None instead of the empty string if the attribute is missing (for instance a <code>pkg.sourcerpm</code> now returns None if <code>pkg</code> is a source rpm package already). </p>
<p> This change is towards a more conventional Python practice. Also, this leaves the empty string return value free to be used when it is actually the case.</p>
<h3>Changes in 0.3.0</h3>
<h3>Core</h3>
<h3>Query: key for reponame filtering</h3>
<p> The Query key value used for filtering by the repo name is <code>HY_PKG_REPONAME</code> now (was <code>HY_PKG_REPO</code>). The old value was misleading.</p>
<h3>Repo initialization</h3>
<p> <code>hy_repo_create()</code> for Repo object initialization now needs to be passed a name of the repository.</p>
<h3>Query installs obsoleted</h3>
<p> All Goal methods accepting Query as the means of selecting packages, such as <code>hy_goal_install_query()</code> have been replaced with their Selector counterparts. Selector structures have been introduced for the particular purpose of specifying a package that best matches the given criteria and at the same time is suitable for installation. For a discussion of this decision see <i>rationale_selectors</i>.</p>
<h3>Python bindings</h3>
<h3>Query: filtering by repository with the reponame key</h3>
<p> Similar change happened in Python, the following constructs: </p>
<pre>
q = q.filter(repo=&quot;updates&quot;)
</pre>
<p> need to be changed to: </p>
<pre>
q = q.filter(reponame=&quot;updates&quot;)
</pre>
<p> The old version of this didn&#8217;t allow using the same string to both construct the query and dynamically get the reponame attribute from the returned packages (used e.g. in DNF to search by user-specified criteria).</p>
<h3>Package: removed methods for direct EVR comparison</h3>
<p> The following will no longer work: </p>
<pre>
if pkg.evr_eq(some_other_pkg):
    ...
</pre>
<p> Instead use the result of <code>pkg.evr_cmp</code>, for instance: </p>
<pre>
if pkg.evr_cmp(some_other_pkg) == 0:
    ...
</pre>
<p> This function compares only the EVR part of a package, not the name. Since it rarely make sense to compare versions of packages of different names, the following is suggested: </p>
<pre>
if pkg == some_other_pkg:
    ...
</pre>
<h3>Repo initialization</h3>
<p> All instantiations of <code>hawkey.Repo</code> now must be given the name of the Repo. The following will now fail: </p>
<pre>
r = hawkey.Repo()
r.name = &quot;fedora&quot;
</pre>
<p> Use this instead: </p>
<pre>
r = hawkey.Repo(&quot;fedora&quot;)
</pre>
<h3>Query installs obsoleted</h3>
<p> See <i>changes_query_installs</i> in the C section. In Python Queries will no longer work as goal target specifiers, the following will fail: </p>
<pre>
q = hawkey.Query(sack)
q.filter(name=&quot;gimp&quot;)
goal.install(query=q)
</pre>
<p> Instead use: </p>
<pre>
sltr = hawkey.Selector(sack)
sltr.set(name=&quot;gimp&quot;)
goal.install(select=sltr)
</pre>
<p> Or a convenience notation: </p>
<pre>
goal.install(name=&quot;gimp&quot;)
</pre>
<h3>Changes in 0.3.1</h3>
<h3>Query: <code>hy_query_filter_package_in()</code> takes a new parameter</h3>
<p> <code>keyname</code> parameter was added to the function signature. The new parameter allows filtering by a specific relation to the resulting packages, for instance: </p>
<pre>
hy_query_filter_package_in(q, HY_PKG_OBSOLETES, HY_EQ, pset)
</pre>
<p> only leaves the packages obsoleting a package in <code>pset</code> a part of the result.</p>
<h3>Removed <code>hy_query_filter_obsoleting()</code></h3>
<p> The new version of <code>hy_query_filter_package_in()</code> handles this now, see above. </p>
<p> In Python, the following is no longer supported: </p>
<pre>
q = query.filter(obsoleting=1)
</pre>
<p> The equivalent new syntax is: </p>
<pre>
installed = hawkey.Query(sack).filter(reponame=SYSTEM_REPO_NAME)
q = query.filter(obsoletes=installed)
</pre>
<h3>Changes in 0.3.2</h3>
<h3>Removed <code>hy_packagelist_of_obsoletes</code>.</h3>
<p> The function was not systematic. Same result is achieved by obtaining obsoleting reldeps from a package and then trying to find the installed packages that provide it. In Python: </p>
<pre>
q = hawkey.Query(sack).filter(reponame=SYSTEM_REPO_NAME, provides=pkg.obsoletes)
</pre>
<h3>Changes in 0.3.3</h3>
<h3>Renamed <code>hy_package_get_nvra</code> to <code>hy_package_get_nevra</code></h3>
<p> The old name was by error, the functionality has not changed: this function has always returned the full NEVRA, skipping the epoch part when it&#8217;s 0.</p>
<h3>Changes in 0.3.4</h3>
<h3>Python bindings</h3>
<h3><code>pkg.__repr__()</code> is more verbose now</h3>
<p> Previously, <code>repr(pkg)</code> would yield for instance <code>&lt;_hawkey.Package object, id: 5&gt;</code>. Now more complete information is present, including the package&#8217;s NEVRA and repository: <code>&lt;hawkey.Package object id 5, foo-2-9\.noarch, @System&gt;</code>. </p>
<p> Also notice that the representation now mentions the final <code>hawkey.Package</code> type, not <code>_hawkey.Package</code>. Note that these are currently the same.</p>
<h3>Changes in 0.3.8</h3>
<h3>Core</h3>
<h3>New parameter <code>rootdir</code> to <code>hy_sack_create()</code></h3>
<p> <code>hy_sack_create()</code> now accepts third argument, <code>rootdir</code>. This can be used to tell Hawkey that we are intending to do transactions in a changeroot, not in the current root. It effectively makes use of the RPM database found under <code>rootdir</code>. To make your code compile in 0.3.8 without changing functionality, change: </p>
<pre>
HySack sack = hy_sack_create(cachedir, arch);
</pre>
<p> to: </p>
<pre><code>
HySack sack = hy_sack_create(cachedir, arch, NULL);
</code></pre>
<h3>Python bindings</h3>
<h3>Forms recognized by <code>Subject</code> are no longer an instance-scope setting</h3>
<p> It became necessary to differentiate between the default forms used by <code>subject.nevra_possibilities()</code> and <code>subject.nevra_possibilities_real()</code>. Therefore there is little sense in setting the default form for an entire <code>Subject</code> instance. The following code: </p>
<pre>
subj = hawkey.Subject(&quot;input&quot;, form=hawkey.FORM_NEVRA)
result = list(subj.nevra_possibilities())
</pre>
<p> is thus replaced by: </p>
<pre>
subj = hawkey.Subject(&quot;input&quot;)
result = list(subj.nevra_possibilities(form=hawkey.FORM_NEVRA))
</pre>
<h3>Changes in 0.3.9</h3>
<h3>Core</h3>
<h3>Flags for <code>hy_sack_create</code></h3>
<p> <code>hy_sack_create()</code> now accepts fourth argument, <code>flags</code>, introduced to modify the sack behavior with boolean flags. Currently only one flag is supported, <code>HY_MAKE_CACHE_DIR</code>, which causes the cache directory to be created if it doesn&#8217;t exist yet. To preserve the previous behavior, change the following: </p>
<pre>
HySack sack = hy_sack_create(cachedir, arch, rootdir);
</pre>
<p> into: </p>
<pre>
HySack sack = hy_sack_create(cachedir, arch, rootdir, HY_MAKE_CACHE_DIR);
</pre>
<h3><code>hy_sack_get_cache_path</code> is renamed to <code>hy_sack_get_cache_dir</code></h3>
<p> Update your code by mechanically replacing the name.</p>
<h3>Python bindings</h3>
<h3><code>make_cache_dir</code> for Sack&#8217;s constructor</h3>
<p> A new sack by default no longer automatically creates the cache directory. To get the old behavior, append <code>make_cache_dir=True</code> to the <code>Sack.__init__()</code> arguments, that is change the following: </p>
<pre>
sack = hawkey.Sack(...)
</pre>
<p> to: </p>
<pre>
sack = hawkey.Sack(..., make_cache_dir=True)
</pre>
<h3><code>cache_path</code> property of <code>Sack</code> renamed to <code>cache_dir</code></h3>
<p> Reflects the similar change in C API.</p>
<h3>Changes in 0.3.11</h3>
<h3>Core</h3>
<h3><code>hy_goal_package_obsoletes()</code> removed, <code>hy_goal_list_obsoleted_by_package()</code> provided instead</h3>
<p> <code>hy_goal_package_obsoletes()</code> was flawed in that it only returned a single obsoleted package (in general, package can obsolete arbitrary number of packages and upgrade a package of the same name which is also reported as an obsolete). Use <code>hy_goal_list_obsoleted_by_package()</code> instead, to see the complete set of packages that inclusion of the given package in an RPM transaction will cause to be removed.</p>
<h3><code>hy_goal_list_erasures()</code> does not report obsoletes</h3>
<p> In other words, <code>hy_goal_list_erasures()</code> and <code>hy_goal_list_obsoleted()</code> return disjoint sets.</p>
<h3>Python bindings</h3>
<p> Directly reflecting the <i>core changes</i>. In particular, instead of: </p>
<pre>
obsoleted_pkg = goal.package_obsoletes(pkg)
</pre>
<p> use: </p>
<pre>
obsoleted = goal.obsoleted_by_package(pkg) # list
obsoleted_pkg = obsoleted[0]
</pre>
<h3>Changes in 0.4.5</h3>
<h3>Core</h3>
<h3>Query: <code>hy_query_filter_latest()</code> now filter latest packages ignoring architecture</h3>
<p> For old function behavior use new function <code>hy_query_filter_latest_per_arch()</code></p>
<h3>Python bindings</h3>
<p> In Python&#8217;s <code>Query</code> option <code>latest</code> in <code>Query.filter()</code> now filter only the latest packages ignoring architecture. The original semantics for filtering latest packages for each arch is now available via <code>latest_per_arch</code> option. </p>
<p> For example there are these packages in sack: </p>
<p>glibc &#8211; 2.17 &#8211; 4.fc19.x86_64 glibc &#8211; 2.16 &#8211; 24.fc18.x86_64 glibc &#8211; 2.16 &#8211; 24.fc18.i686 &gt;&gt;&gt; q = hawkey.Query(self.sack).filter(name = &#8220;glibc&#8221;) &gt;&gt;&gt; map(str, q.filter(latest = True))<br />
                                                                                                                                                      [&#8216;glibc-2.17-4.fc19.x86_64&#8217;] &gt;&gt;&gt;<br />
                                                                                               map(str, q.filter(latest_per_arch = True))<br />
                                                                                                   [&#8216;glibc-2.17-4.fc19.x86_64&#8217;, &#8216;glibc-2.16-24.fc18.i686&#8217;]</p>
<h3>Changes in 0.4.13</h3>
<h3>Core</h3>
<h3>Deprecated <code>hy_package_get_update_*</code></h3>
<p> The functions were deprecated because there can be multiple advisories referring to a single package. Please use the new function <code>hy_package_get_advisories()</code> which returns all these advisories. New functions <code>hy_advisory_get_*</code> provide the data retrieved by the deprecated functions. </p>
<p> The only exception is the <code>hy_package_get_update_severity()</code> which will be dropped without any replacement. However advisory types and severity levels are distinguished from now and the type is accessible via <code>hy_advisory_get_type()</code>. Thus enum <code>HyUpdateSeverity</code> was also deprecated. A new <code>HyAdvisoryType</code> should be used instead. </p>
<p> The old functions will be dropped after 2014-07-07.</p>
<h3>Changes in 0.4.15</h3>
<h3>Core</h3>
<h3><code>hy_goal_write_debugdata()</code> takes a directory parameter</h3>
<p> <code>hy_goal_write_debugdata()</code> has a new <i>const char *dir</i> argument to communicate the target directory for the debugging data. The old call: </p>
<pre>
hy_goal_write_debugdata(goal);
</pre>
<p> should be changed to achieve the same behavior to: </p>
<pre>
hy_goal_write_debugdata(goal, &quot;./debugdata&quot;);
</pre>
<h3>Python bindings</h3>
<h3><code>Goal.write_debugdata()</code> takes a directory parameter</h3>
<p> Analogous to <i>core changes</i>.</p>
<h3>Package: string attributes are represented by Unicode object</h3>
<p> Attributes <code>baseurl</code>, <code>location</code>, <code>sourcerpm</code>, <code>version</code>, <code>release</code>, <code>name</code>, <code>arch</code>, <code>description</code>, <code>evr</code>, <code>license</code>, <code>packager</code>, <code>reponame</code>, <code>summary</code> and <code>url</code> of Package object return Unicode string.</p>
<h3>Changes in 0.4.18</h3>
<h3>Core</h3>
<h3>Deprecated <code>hy_advisory_get_filenames</code></h3>
<p> The function was deprecated because we need more information about packages listed in an advisory than just file names. Please use the new function <code>hy_advisory_get_packages()</code> in combination with <code>hy_advisorypkg_get_string()</code> to obtain the data originally provided by the deprecated function. </p>
<p> The old function will be dropped after 2014-10-15 AND no sooner than in 0.4.21.</p>
<h3>Python bindings</h3>
<h3><code>Repo()</code> does not accept <code>cost</code> keyword argument</h3>
<p> Instead of: </p>
<pre>
r = hawkey.Repo('name', cost=30)
</pre>
<p> use: </p>
<pre>
r = hawkey.Repo('name')
r.cost = 30
</pre>

<h3>Setup</h3>
<p> First of, make sure hawkey is installed on your system, this should work from your terminal: </p>
<pre>
&gt;&gt;&gt; import hawkey
</pre>
<h3>The Sack Object</h3>
<p> <i>Sack</i> is an abstraction for a collection of packages. Sacks in hawkey are toplevel objects carrying much of hawkey&#8217;s of functionality. You&#8217;ll want to create one: </p>
<pre>
&gt;&gt;&gt; sack = hawkey.Sack()
&gt;&gt;&gt; len(sack)
0
</pre>
<p> Initially, the sack contains no packages.</p>
<h3>Loading RPMDB</h3>
<p> hawkey is a lib for listing, querying and resolving dependencies of <i>packages</i> from <i>repositories</i>. On most linux distributions you always have at least <i>the system repo</i> (in Fedora it is the RPM database). To load it: </p>
<pre>
&gt;&gt;&gt; sack.load_system_repo()
&gt;&gt;&gt; len(sack)
1683
</pre>
<p> Hawkey always knows the name of every repository. The system repository is always set to <code>hawkey.SYSTEM_REPO_NAME</code>. and the client is responsible for naming the available repository metadata.</p>
<h3>Loading Repositories</h3>
<p> Let&#8217;s be honest here: all the fun in packaging comes from packages you haven&#8217;t installed yet. Information about them, their <i>metadata</i>, can be obtained from different sources and typically they are downloaded from an HTTP mirror (another possibilities are FTP server, NFS mount, DVD distribution media, etc.). Hawkey does not provide any means to discover and obtain the metadata locally: it is up to the client to provide valid readable paths to the repository metadata XML files. Structures used for passing the information to hawkey are the hawkey <code>Repos</code>. Suppose we somehow obtained the metadata and placed it in <code>/home/akozumpl/tmp/repodata</code>. We can then load the metadata into hawkey: </p>
<pre>
&gt;&gt;&gt; path = &quot;/home/akozumpl/tmp/repodata/%s&quot;
&gt;&gt;&gt; repo = hawkey.Repo(&quot;experimental&quot;)
&gt;&gt;&gt; repo.repomd_fn = path % &quot;repomd.xml&quot;
&gt;&gt;&gt; repo.primary_fn = path % &quot;f7753a2636cc89d70e8aaa1f3c08413ab78462ca9f48fd55daf6dedf9ab0d5db-primary.xml.gz&quot;
&gt;&gt;&gt; repo.filelists_fn = path % &quot;0261e25e8411f4f5e930a70fa249b8afd5e86bb9087d7739b55be64b76d8a7f6-filelists.xml.gz&quot;
&gt;&gt;&gt; sack.load_repo(repo, load_filelists=True)
&gt;&gt;&gt; len(sack)
1685
</pre>
<p> The number of packages in the Sack will increase by the number of packages found in the repository (two in this case, it is an experimental repo after all).</p>
<h3>Case for Loading the Filelists</h3>
<p> What the <code>load_filelists=True</code> argument to <code>load_repo()</code> above does is instruct hawkey to process the <code>&lt;hash&gt;filelists.xml.gz</code> file we passed in and which contains structured list of absolute paths to all files of all packages within the repo. This information can be used for two purposes:</p>
<dl>
<dt>&bull;</p>
<dd> Finding a package providing given file. For instance, you need the file <code>/usr/share/man/man3/fprintf.3.gz</code> which is not installed. Consulting filelists (directly or through hawkey) can reveal the file is in the <code>man-pages</code> package.</p>
<dt>&bull;</p>
<dd> Depsolving. Some packages require concrete files as their dependencies. To know if these are resolvable and how, the solver needs to know what package provides what files. </p>
<p> Some files provided by a package (e.g those in <code>/usr/bin</code>) are always visible even without loading the filelists. Well-behaved packages requiring only those can be thus resolved directly. Unortunately, there are packages that don&#8217;t behave and it is hard to tell in advance when you&#8217;ll deal with one. </p>
<p> The strategy for using <code>load_filelists=True</code> is thus:</p>
<dt>&bull;</p>
<dd> Use it if you know you&#8217;ll do resolving (i.e. you&#8217;ll use <code>Goal</code>).</p>
<dt>&bull;</p>
<dd> Use it if you know you&#8217;ll be trying to match files to their packages.</p>
<dt>&bull;</p>
<dd> Use it if you are not sure.</dl>
<h3>Building and Reusing the Repo Cache</h3>
<p> Internally to hold the package information and perform canonical resolving hawkey uses <i>Libsolv</i>. One great benefit this library offers is providing writing and reading of metadata cache files in libsolv&#8217;s own binary format (files with <code>.solv</code> extension, typically). At a cost of few hundreds of milliseconds, using the solv files reduces repo load times from seconds to tens of milliseconds. It is thus a good idea to write and use the solv files every time you plan to use the same repo for more than one Sack (which is at least every time your hawkey program is run). To do that use <code>build_cache=True</code> with <code>load_repo()</code> and <code>load_system_repo()</code>: </p>
<pre>
&gt;&gt;&gt; sack = hawkey.Sack(make_cache_dir=True)
&gt;&gt;&gt; sack.load_system_repo(build_cache=True)
</pre>
<p> By default, Hawkey creates <code>@System.cache</code> under the <code>/var/tmp/hawkey-&lt;your_login&gt;-&lt;random_hash&gt;</code> directory. This is the hawkey cache directory, which you can always delete later (deleting the cache files in the process). The <code>.solv</code> files are picked up automatically the next time you try to create a hawkey sack. Except for a much higher speed of the operation this will be completely transparent to you: </p>
<pre>
&gt;&gt;&gt; s2 = hawkey.Sack()
&gt;&gt;&gt; s2.load_system_repo()
</pre>
<p> By the way, the cache directory (if not set otherwise) also contains a logfile with some boring debugging information.</p>
<h3>Queries</h3>
<p> Query is the means in hawkey of finding a package based on one or more criteria (name, version, repository of origin). Its interface is loosely based on <i>Django&#8217;s QuerySets</i>, the main concepts being:</p>
<dl>
<dt>&bull;</p>
<dd> a fresh Query object matches all packages in the Sack and the selection is gradually narrowed down by calls to <code>Query.filter()</code></p>
<dt>&bull;</p>
<dd> applying a <code>Query.filter()</code> does not start to evaluate the Query, i.e. the Query is lazy. Query is only evaluated when we explicitly tell it to or when we start to iterate it.</p>
<dt>&bull;</p>
<dd> use Python keyword arguments to <code>Query.filter()</code> to specify the filtering criteria. </p>
<p> For instance, let&#8217;s say I want to find all installed packages which name ends with <code>gtk</code>: </p>
<pre>
&gt;&gt;&gt; q = hawkey.Query(sack).filter(reponame=hawkey.SYSTEM_REPO_NAME, name__glob='*gtk')
&gt;&gt;&gt; for pkg in q:
...     print str(pkg)
...
NetworkManager-gtk-1:0.9.4.0-9.git20120521.fc17.x86_64
authconfig-gtk-6.2.1-1.fc17.x86_64
clutter-gtk-1.2.0-1.fc17.x86_64
libchamplain-gtk-0.12.2-1.fc17.x86_64
libreport-gtk-2.0.10-3.fc17.x86_64
pinentry-gtk-0.8.1-6.fc17.x86_64
python-slip-gtk-0.2.20-2.fc17.noarch
transmission-gtk-2.50-2.fc17.x86_64
usermode-gtk-1.109-1.fc17.x86_64
webkitgtk-1.8.1-2.fc17.x86_64
xdg-user-dirs-gtk-0.9-1.fc17.x86_64
</pre>
<p> Or I want to find the latest version of all <code>python</code> packages the Sack knows of: </p>
<pre>
&gt;&gt;&gt; q.clear()
&gt;&gt;&gt; q = q.filter(name='python', latest_per_arch=True)
&gt;&gt;&gt; for pkg in q:
...     print str(pkg)
...
python-2.7.3-6.fc17.x86_64
</pre>
<p> You can also test a <code>Query</code> for its truth value. It will be true whenever the query matched at least one package: </p>
<pre>
&gt;&gt;&gt; q = hawkey.Query(sack).filter(file='/boot/vmlinuz-3.3.4-5.fc17.x86_64')
&gt;&gt;&gt; if q:
...     print 'match'
...
match
&gt;&gt;&gt; q = hawkey.Query(sack).filter(file='/booty/vmlinuz-3.3.4-5.fc17.x86_64')
&gt;&gt;&gt; if q:
...     print 'match'
...
&gt;&gt;&gt; if not q:
...     print 'no match'
...
no match
</pre>
<p> <code>NOTE:</code> If the Query hasn&#8217;t been evaluated already then it is evaluated whenever it&#8217;s length is taken (either via <code>len(q)</code> or <code>q.count()</code>), when it is tested for truth and when it is explicitly evaluated with <code>q.run()</code>.</dl>
<h3>Resolving things with Goals</h3>
<p> Many <code>Sack</code> sessions culminate in a bout of dependency resolving, that is answering a question along the lines of &quot;I have a package X in a repository here, what other packages do I need to install/update to have X installed and all its dependencies recursively satisfied?&quot; Suppose we want to install <i>the RTS game Spring</i>. First let&#8217;s locate the latest version of the package in repositories: </p>
<pre>
&gt;&gt;&gt; q = hawkey.Query(sack).filter(name='spring', latest_per_arch=True)
&gt;&gt;&gt; pkg = hawkey.Query(sack).filter(name='spring', latest_per_arch=True)[0]
&gt;&gt;&gt; str(pkg)
'spring-88.0-2.fc17.x86_64'
&gt;&gt;&gt; pkg.reponame
'fedora'
</pre>
<p> Then build the <code>Goal</code> object and tell it our goal is installing the <code>pkg</code>. Then we fire off the libsolv&#8217;s dependency resolver by running the goal: </p>
<pre>
&gt;&gt;&gt; g = hawkey.Goal(sack)
&gt;&gt;&gt; g.install(pkg)
&gt;&gt;&gt; g.run()
True
</pre>
<p> <code>True</code> as a return value here indicates that libsolv could find a solution to our goal. This is not always the case, there are plenty of situations when there is no solution, the most common one being a package should be installed but one of its dependencies is missing from the sack. </p>
<p> The three methods <code>Goal.list_installs()</code>, <code>Goal.list_upgrades()</code> and <code>Goal.list_erasures()</code> can show which packages should be installed/upgraded/erased to satisfy the packaging goal we set out to achieve (the mapping of <code>str()</code> over the results below ensures human readable package names instead of numbers are presented): </p>
<p>&gt;&gt;&gt; map(str, g.list_installs())<br />
        [&#8216;spring-88.0-2.fc17.x86_64&#8217;, &#8216;spring-installer-20090316-10.fc17.x86_64&#8217;, &#8216;springlobby-0.139-3.fc17.x86_64&#8217;, &#8216;spring-maps-default-0.1-8.fc17.noarch&#8217;, &#8216;wxBase-2.8.12-4.fc17.x86_64&#8217;, &#8216;wxGTK-2.8.12-4.fc17.x86_64&#8217;, &#8216;rb_libtorrent-0.15.9-1.fc17.x86_64&#8217;, &#8216;GeoIP-1.4.8-2.1.fc17.x86_64&#8217;] &gt;&gt;&gt;<br />
    map(str, g.list_upgrades())<br />
        [] &gt;&gt;&gt;<br />
    map(str, g.list_erasures())<br />
        []</p>
<p> So what does it tell us? That given the state of the given system and the given repository we used, 8 packages need to be installed, <code>spring-88.0-2.fc17.x86_64</code> itself included. No packages need to be upgraded or erased.</p>
<h3>Selector Installs</h3>
<p> For certain simple and commonly used queries we can do installs directly. Instead of executing a query however we instantiate and pass the <code>Goal.install()</code> method a <code>Selector</code>: </p>
<pre>
&gt;&gt;&gt; g = hawkey.Goal(sack)
&gt;&gt;&gt; sltr = hawkey.Selector(sack).set(name='emacs-nox')
&gt;&gt;&gt; g.install(select=sltr)
&gt;&gt;&gt; g.run()
True
&gt;&gt;&gt; map(str, g.list_installs())
['spring-88.0-2.fc17.x86_64', 'spring-installer-20090316-10.fc17.x86_64', 'springlobby-0.139-3.fc17.x86_64', 'spring-maps-default-0.1-8.fc17.noarch', 'wxBase-2.8.12-4.fc17.x86_64', 'wxGTK-2.8.12-4.fc17.x86_64', 'rb_libtorrent-0.15.9-1.fc17.x86_64', 'GeoIP-1.4.8-2.1.fc17.x86_64']
&gt;&gt;&gt; len(g.list_upgrades())
0
&gt;&gt;&gt; len(g.list_erasures())
0
</pre>
<p> Notice we arrived at the same result as before, when a query was constructed and iterated first. What <code>Selector</code> does when passed to <code>Goal.install()</code> is tell hawkey to examine its settings and without evaluating it as a <code>Query</code> it instructs libsolv to find <i>the best matching package</i> for it and add that for installation. It saves user some decisions like which version should be installed or what architecture (this gets very relevant with multiarch libraries). </p>
<p> So Selectors usually only install a single package. If you mean to install <i>all packages</i> matching an arbitrarily complex query, just use the method describe above: </p>
<pre>
&gt;&gt;&gt; map(goal.install, q)
</pre>

<h3>Sack&#8212;The fundamental hawkey structure</h3>
<dl>
<dt><code>class hawkey.Sack</code></p>
<dd> Instances of <code>hawkey.Sack</code> represent collections of packages. An application typically needs at least one instance because it provides much of the hawkey&#8217;s functionality. </p>
<p> <code>WARNING:</code> Any package instance is not supposed to work interchangeably between <code>hawkey.Query</code>, <code>hawkey.Selector</code> or <code>hawkey.Goal</code> created from different <code>hawkey.Sack</code>. Usually for common tasks there is no need to initialize two or more <i>Sacks</i> in your program. Sacks cannot be deeply copied.</p>
<dt><code>cache_dir</code></p>
<dd> A read-only string property giving the path to the location where a metadata cache is stored.</p>
<dt><code>installonly</code></p>
<dd> A write-only sequence of strings property setting the provide names of packages that should only ever be installed, never upgraded.</p>
<dt><code>installonly_limit</code></p>
<dd> A write-only integer property setting how many installonly packages with the same name are allowed to be installed concurrently. If <code>0</code>, any number of packages can be installed.</p>
<dt><code>__init__(cachedir=_CACHEDIR, arch=_ARCH, rootdir=_ROOTDIR, pkgcls=hawkey.Package, pkginitval=None, make_cache_dir=False, logfile=_LOGFILE)</code></p>
<dd> Initialize the sack with a default cache directory, log file location set to <code>hawkey.log</code> in the cache directory, an automatically detected architecture and the current root (<code>/</code>) as an installroot. The cache is disabled by default. </p>
<p> <i>cachedir</i> is a string giving a path of a cache location. </p>
<p> <i>arch</i> is a string specifying an architecture. </p>
<p> <i>rootdir</i> is a string giving a path to an installroot. </p>
<p> <i>pkgcls</i> is a class of packages retrieved from the sack. The class&#8217; <code>__init__</code> method must accept two arguments. The first argument is a tuple of the sack and the ID of the package. The second argument is the <i>pkginitval</i> argument. <i>pkginitval</i> cannot be <code>None</code> if <i>pkgcls</i> is specified. </p>
<p> <i>make_cache_dir</i> is a boolean that specifies whether the cache should be used to speedup loading of repositories or not (see <i>building_and_reusing_the_repo_cache-label</i>). </p>
<p> <i>logfile</i> is a string giving a path of a log file location.</p>
<dt><code>__len__()</code></p>
<dd> Returns the number of the packages loaded into the sack.</p>
<dt><code>add_cmdline_package(filename)</code></p>
<dd> Add a package to a command line repository and return it. The package is specified as a string <i>filename</i> of an RPM file. The command line repository will be automatically created if doesn&#8217;t exist already. It could be referenced later by <code>hawkey.CMDLINE_REPO_NAME</code> name.</p>
<dt><code>add_excludes(packages)</code></p>
<dd> Add a sequence of packages that cannot be fetched by Queries nor Selectors.</p>
<dt><code>add_includes(packages)</code></p>
<dd> Add a sequence of the only packages that can be fetched by Queries or Selectors. </p>
<p> This is the inverse operation of <code>add_excludes()</code>. Any package that is not in the union of all the included packages is excluded. This works in conjunction with exclude and doesn&#8217;t override it. So, if you both include and exclude the same package, the package is considered excluded no matter of the order.</p>
<dt><code>disable_repo(name)</code></p>
<dd> Disable the repository identified by a string <i>name</i>. Packages in that repository cannot be fetched by Queries nor Selectors.</p>
<dt><code>enable_repo(name)</code></p>
<dd> Enable the repository identified by a string <i>name</i>. Packages in that repository can be fetched by Queries or Selectors. </p>
<p> <code>WARNING:</code> Execution of <code>add_excludes()</code>, <code>add_includes()</code>, <code>disable_repo()</code> or <code>enable_repo()</code> methods could cause inconsistent results in previously evaluated <code>Query</code>, <code>Selector</code> or <code>Goal</code>. The rule of thumb is to exclude/include packages, enable/disable repositories at first and then do actual computing using <code>Query</code>, <code>Selector</code> or <code>Goal</code>. For more details see <i>developer discussion</i>.</p>
<dt><code>evr_cmp(evr1, evr2)</code></p>
<dd> Compare two EVR strings and return a negative integer if <i>evr1</i> &lt; <i>evr2</i>, zero if <i>evr1</i> == <i>evr2</i> or a positive integer if <i>evr1</i> &gt; <i>evr2</i>.</p>
<dt><code>get_running_kernel()</code></p>
<dd> Detect and return the package of the currently running kernel. If the package cannot be found, <code>None</code> is returned.</p>
<dt><code>list_arches()</code></p>
<dd> List strings giving all the supported architectures.</p>
<dt><code>load_system_repo(repo=None, build_cache=False)</code></p>
<dd> Load the information about the packages in the system repository (in Fedora it is the RPM database) into the sack. This makes the dependency solving aware of the already installed packages. The system repository is always set to <code>hawkey.SYSTEM_REPO_NAME</code>. The information is not written to the cache by default. </p>
<p> <i>repo</i> is an optional <code>Repo</code> object that represents the system repository. The object is updated during the loading. </p>
<p> <i>build_cache</i> is a boolean that specifies whether the information should be written to the cache (see <i>building_and_reusing_the_repo_cache-label</i>).</p>
<dt><code>load_repo(repo, build_cache=False, load_filelists=False, load_presto=False, load_updateinfo=False)</code></p>
<dd> Load the information about the packages in a <code>Repo</code> into the sack. This makes the dependency solving aware of these packages. The information is not written to the cache by default. </p>
<p> <i>repo</i> is the <code>Repo</code> object to be processed. At least its <code>Repo.repomd_fn</code> must be set. If the cache has to be updated, <code>Repo.primary_fn</code> is needed too. Some information about the loading process and some results of it are written into the internal state of the repository object. </p>
<p> <i>build_cache</i> is a boolean that specifies whether the information should be written to the cache (see <i>building_and_reusing_the_repo_cache-label</i>). </p>
<p> <i>load_filelists</i>, <i>load_presto</i> and <i>load_updateinfo</i> are booleans that specify whether the <code>Repo.filelists_fn</code>, <code>Repo.presto_fn</code> and <code>Repo.updateinfo_fn</code> files of the repository should be processed. These files may contain information needed for dependency solving, downloading or querying of some packages. Enable it if you are not sure (see <i>case_for_loading_the_filelists-label</i>).</dl>
<h3>Error handling</h3>
<p> When an error or an unexpected event occurs during a Hawkey routine, an exception is raised:</p>
<dl>
<dt>&bull;</p>
<dd> if it is a general error that could be common to other Python programs, one of the standard Python built-in exceptions is raised. For instance, <code>IOError</code> and <code>TypeError</code> can be raised from Hawkey.</p>
<dt>&bull;</p>
<dd> programming errors within Hawkey that cause unexpected or invalid states raise the standard <code>AssertionError</code>. These should be reported as bugs against Hawkey.</p>
<dt>&bull;</p>
<dd> programming errors due to incorrect use of the library usually produce <code>hawkey.ValueException</code> or one of its subclasses, <code>QueryException</code> (poorly formed Query) or <code>ArchException</code> (unrecognized architecture).</p>
<dt>&bull;</p>
<dd> sometimes there is a close call between blaming the error on an input parameter or on something else, beyond the programmer&#8217;s control. <code>hawkey.RuntimeException</code> is generally used in this case.</p>
<dt>&bull;</p>
<dd> <code>hawkey.ValidationException</code> is raised when a function call performs a preliminary check before proceeding with the main operation and this check fails. </p>
<p> The class hierarchy for Hawkey exceptions is: </p>
<pre><code>
+ --hawkey.Exception + --hawkey.ValueException | +--hawkey.QueryException | +--hawkey.ArchException + --hawkey.RuntimeException + --hawkey.ValidationException
</code></pre>
</dl>

<h2>DESIGN RATIONALE</h2>
<h3>Selectors are not Queries</h3>
<p> Since both a Query and a Selector work to limit the set of all Sack&#8217;s packages to a subset, it can be suggested the two concepts should be the same and e.g. Queries should be used for Goal specifications instead of Selectors: </p>
<pre>
// create sack, goal, ...
HyQuery q = hy_query_create(sack);
hy_query_filter(q, HY_PKG_NAME, HY_EQ, &quot;anaconda&quot;)
hy_goal_install_query(q)
</pre>
<p> This arrangment was in fact used in hawkey prior to version 0.3.0, just because Queries looked like a convenient structure to hold this kind of information. It was unfortunately confusing for the programmers: notice how evaluating the Query <code>q</code> would generally produce several packages (<code>anaconda</code> for different architectures and then different versions) but somehow when the same Query is passed into the goal methods it always results in up to one pacakge selected for the operation. This is a principal discrepancy. Further, Query is universal and allows one to limit the package set with all sorts of criteria, matched in different ways (substrings, globbing, set operation) while Selectors only support few. Finally, while a fresh Query with no filters applied corresponds to all packages of the Sack, a fresh Selector with no limits set is of no meaning. </p>
<p> An alternative to introducing a completely different concept was adding a separate constructor function for Query, one that would from the start designate the Query to only accept settings compatible with its purpose of becoming the selecting element in a Goal operation (in Python this would probably be implemented as a subclass of Query). But that would break client&#8217;s assumptions about Query (<i>the unofficial C++ FAQ</i> takes up the topic). </p>
<p> <i>Implementation note</i>: Selectors reflect the kind of specifications that can be directly translated into Libsolv jobs, without actually searching for a concrete package to put there. In other words, Selectors are specifically designed not to iterate over the package data (with exceptions, like glob matching) like Queries do. While Hawkey mostly aims to hide any twists and complexities of the underlying library, in this case the combined reasons warrant a concession. </p>
