<h2>Description</h2>
<pre> ____ _ _
 | _ \| |_| |__
 | |_) | __| '_ \ ``Only those who attempt
 | __/| |_| | | | the absurd can achieve
 |_| \__|_| |_| the impossible.''</pre>
<p><code>Pth</code> is a very portable <font SIZE="-1">POSIX/ANSI-C</font> based library for Unix platforms which provides non-preemptive priority-based scheduling for multiple threads of execution (aka `multithreading&#8217;) inside event-driven applications. All threads run in the same address space of the application process, but each thread has its own individual program counter, run-time stack, signal mask and <tt>&quot;errno&quot;</tt> variable. </p>
<p> The thread scheduling itself is done in a cooperative way, i.e., the threads are managed and dispatched by a priority- and event-driven non-preemptive scheduler. The intention is that this way both better portability and run-time performance is achieved than with preemptive scheduling. The event facility allows threads to wait until various types of internal and external events occur, including pending I/O on file descriptors, asynchronous signals, elapsed timers, pending I/O on message ports, thread and process termination, and even results of customized callback functions. </p>
<p> <code>Pth</code> also provides an optional emulation <font SIZE="-1">API</font> for <font SIZE="-1">POSIX</font>.1c threads (`Pthreads&#8217;) which can be used for backward compatibility to existing multithreaded applications. See <code>Pth</code>&#8216;s <i><a href="/docs/linux/man/3-pthread/">pthread</a></i>(3) manual page for details. </p>
<p> <code>Threading Background</code> </p>
<p> When programming event-driven applications, usually servers, lots of regular jobs and one-shot requests have to be processed in parallel. To efficiently simulate this parallel processing on uniprocessor machines, we use `multitasking&#8217; &#8212; that is, we have the application ask the operating system to spawn multiple instances of itself. On Unix, typically the kernel implements multitasking in a preemptive and priority-based way through heavy-weight processes spawned with <i><a href="/docs/linux/man/2-fork/">fork</a></i>(2). These processes usually do <i>not</i> share a common address space. Instead they are clearly separated from each other, and are created by direct cloning a process address space (although modern kernels use memory segment mapping and copy-on-write semantics to avoid unnecessary copying of physical memory). </p>
<p> The drawbacks are obvious: Sharing data between the processes is complicated, and can usually only be done efficiently through shared memory (but which itself is not very portable). Synchronization is complicated because of the preemptive nature of the Unix scheduler (one has to use <i>atomic</i> locks, etc). The machine&#8217;s resources can be exhausted very quickly when the server application has to serve too many long-running requests (heavy-weight processes cost memory). And when each request spawns a sub-process to handle it, the server performance and responsiveness is horrible (heavy-weight processes cost time to spawn). Finally, the server application doesn&#8217;t scale very well with the load because of these resource problems. In practice, lots of tricks are usually used to overcome these problems &#8211; ranging from pre-forked sub-process pools to semi-serialized processing, etc. </p>
<p> One of the most elegant ways to solve these resource- and data-sharing problems is to have multiple <i>light-weight</i> threads of execution inside a single (heavy-weight) process, i.e., to use <i>multithreading</i>. Those <i>threads</i> usually improve responsiveness and performance of the application, often improve and simplify the internal program structure, and most important, require less system resources than heavy-weight processes. Threads are neither the optimal run-time facility for all types of applications, nor can all applications benefit from them. But at least event-driven server applications usually benefit greatly from using threads. </p>
<p> <code>The World of Threading</code> </p>
<p> Even though lots of documents exists which describe and define the world of threading, to understand <code>Pth</code>, you need only basic knowledge about threading. The following definitions of thread-related terms should at least help you understand thread programming enough to allow you to use <code>Pth</code>.</p>
<dl>
<dt><code>o</code> <code>process</code> vs. <code>thread</code></p>
<dd>A process on Unix systems consists of at least the following fundamental ingredients: <i>virtual memory table</i>, <i>program code</i>, <i>program counter</i>, <i>heap memory</i>, <i>stack memory</i>, <i>stack pointer</i>, <i>file descriptor set</i>, <i>signal table</i>. On every process switch, the kernel saves and restores these ingredients for the individual processes. On the other hand, a thread consists of only a private program counter, stack memory, stack pointer and signal table. All other ingredients, in particular the virtual memory, it shares with the other threads of the same process.</p>
<dt><code>o</code> <code>kernel-space</code> vs. <code>user-space</code> threading</p>
<dd>Threads on a Unix platform traditionally can be implemented either inside kernel-space or user-space. When threads are implemented by the kernel, the thread context switches are performed by the kernel without the application&#8217;s knowledge. Similarly, when threads are implemented in user-space, the thread context switches are performed by an application library, without the kernel&#8217;s knowledge. There also are hybrid threading approaches where, typically, a user-space library binds one or more user-space threads to one or more kernel-space threads (there usually called light-weight processes &#8211; or in short LWPs). </p>
<p> User-space threads are usually more portable and can perform faster and cheaper context switches (for instance via <i><a href="/docs/linux/man/2-swapcontext/">swapcontext</a></i>(2) or <i><a href="/docs/linux/man/3-setjmp/">setjmp</a></i>(3)/<i><a href="/docs/linux/man/3-longjmp/">longjmp</a></i>(3)) than kernel based threads. On the other hand, kernel-space threads can take advantage of multiprocessor machines and don&#8217;t have any inherent I/O blocking problems. Kernel-space threads are usually scheduled in preemptive way side-by-side with the underlying processes. User-space threads on the other hand use either preemptive or non-preemptive scheduling.</p>
<dt><code>o</code> <code>preemptive</code> vs. <code>non-preemptive</code> thread scheduling</p>
<dd>In preemptive scheduling, the scheduler lets a thread execute until a blocking situation occurs (usually a function call which would block) or the assigned timeslice elapses. Then it detracts control from the thread without a chance for the thread to object. This is usually realized by interrupting the thread through a hardware interrupt signal (for kernel-space threads) or a software interrupt signal (for user-space threads), like <tt>&quot;SIGALRM&quot;</tt> or <tt>&quot;SIGVTALRM&quot;</tt>. In non-preemptive scheduling, once a thread received control from the scheduler it keeps it until either a blocking situation occurs (again a function call which would block and instead switches back to the scheduler) or the thread explicitly yields control back to the scheduler in a cooperative way.</p>
<dt><code>o</code> <code>concurrency</code> vs. <code>parallelism</code></p>
<dd>Concurrency exists when at least two threads are <i>in progress</i> at the same time. Parallelism arises when at least two threads are <i>executing</i> simultaneously. Real parallelism can be only achieved on multiprocessor machines, of course. But one also usually speaks of parallelism or <i>high concurrency</i> in the context of preemptive thread scheduling and of <i>low concurrency</i> in the context of non-preemptive thread scheduling.</p>
<dt><code>o</code> <code>responsiveness</code></p>
<dd>The responsiveness of a system can be described by the user visible delay until the system responses to an external request. When this delay is small enough and the user doesn&#8217;t recognize a noticeable delay, the responsiveness of the system is considered good. When the user recognizes or is even annoyed by the delay, the responsiveness of the system is considered bad.</p>
<dt><code>o</code> <code>reentrant</code>, <code>thread-safe</code> and <code>asynchronous-safe</code> functions</p>
<dd>A reentrant function is one that behaves correctly if it is called simultaneously by several threads and then also executes simultaneously. Functions that access global state, such as memory or files, of course, need to be carefully designed in order to be reentrant. Two traditional approaches to solve these problems are caller-supplied states and thread-specific data. </p>
<p> Thread-safety is the avoidance of <i>data races</i>, i.e., situations in which data is set to either correct or incorrect value depending upon the (unpredictable) order in which multiple threads access and modify the data. So a function is thread-safe when it still behaves semantically correct when called simultaneously by several threads (it is not required that the functions also execute simultaneously). The traditional approach to achieve thread-safety is to wrap a function body with an internal mutual exclusion lock (aka `mutex&#8217;). As you should recognize, reentrant is a stronger attribute than thread-safe, because it is harder to achieve and results especially in no run-time contention between threads. So, a reentrant function is always thread-safe, but not vice versa. </p>
<p> Additionally there is a related attribute for functions named asynchronous-safe, which comes into play in conjunction with signal handlers. This is very related to the problem of reentrant functions. An asynchronous-safe function is one that can be called safe and without side-effects from within a signal handler context. Usually very few functions are of this type, because an application is very restricted in what it can perform from within a signal handler (especially what system functions it is allowed to call). The reason mainly is, because only a few system functions are officially declared by <font SIZE="-1">POSIX</font> as guaranteed to be asynchronous-safe. Asynchronous-safe functions usually have to be already reentrant.
</dl>
<p> <code>User-Space Threads</code> </p>
<p> User-space threads can be implemented in various way. The two traditional approaches are:</p>
<dl>
<dt><code>1.</code></p>
<dd><code>Matrix-based explicit dispatching between small units of execution:</code> </p>
<p> Here the global procedures of the application are split into small execution units (each is required to not run for more than a few milliseconds) and those units are implemented by separate functions. Then a global matrix is defined which describes the execution (and perhaps even dependency) order of these functions. The main server procedure then just dispatches between these units by calling one function after each other controlled by this matrix. The threads are created by more than one jump-trail through this matrix and by switching between these jump-trails controlled by corresponding occurred events. </p>
<p> This approach gives the best possible performance, because one can fine-tune the threads of execution by adjusting the matrix, and the scheduling is done explicitly by the application itself. It is also very portable, because the matrix is just an ordinary data structure, and functions are a standard feature of <font SIZE="-1">ANSI</font> C. </p>
<p> The disadvantage of this approach is that it is complicated to write large applications with this approach, because in those applications one quickly gets hundreds(!) of execution units and the control flow inside such an application is very hard to understand (because it is interrupted by function borders and one always has to remember the global dispatching matrix to follow it). Additionally, all threads operate on the same execution stack. Although this saves memory, it is often nasty, because one cannot switch between threads in the middle of a function. Thus the scheduling borders are the function borders.</p>
<dt><code>2.</code></p>
<dd><code>Context-based implicit scheduling between threads of execution:</code> </p>
<p> Here the idea is that one programs the application as with forked processes, i.e., one spawns a thread of execution and this runs from the begin to the end without an interrupted control flow. But the control flow can be still interrupted &#8211; even in the middle of a function. Actually in a preemptive way, similar to what the kernel does for the heavy-weight processes, i.e., every few milliseconds the user-space scheduler switches between the threads of execution. But the thread itself doesn&#8217;t recognize this and usually (except for synchronization issues) doesn&#8217;t have to care about this. </p>
<p> The advantage of this approach is that it&#8217;s very easy to program, because the control flow and context of a thread directly follows a procedure without forced interrupts through function borders. Additionally, the programming is very similar to a traditional and well understood <i><a href="/docs/linux/man/2-fork/">fork</a></i>(2) based approach. </p>
<p> The disadvantage is that although the general performance is increased, compared to using approaches based on heavy-weight processes, it is decreased compared to the matrix-approach above. Because the implicit preemptive scheduling does usually a lot more context switches (every user-space context switch costs some overhead even when it is a lot cheaper than a kernel-level context switch) than the explicit cooperative/non-preemptive scheduling. Finally, there is no really portable <font SIZE="-1">POSIX/ANSI-C</font> based way to implement user-space preemptive threading. Either the platform already has threads, or one has to hope that some semi-portable package exists for it. And even those semi-portable packages usually have to deal with assembler code and other nasty internals and are not easy to port to forthcoming platforms.</dl>
<p> So, in short: the matrix-dispatching approach is portable and fast, but nasty to program. The thread scheduling approach is easy to program, but suffers from synchronization and portability problems caused by its preemptive nature. </p>
<p> <code>The Compromise of Pth</code> </p>
<p> But why not combine the good aspects of both approaches while avoiding their bad aspects? That&#8217;s the goal of <code>Pth</code>. <code>Pth</code> implements easy-to-program threads of execution, but avoids the problems of preemptive scheduling by using non-preemptive scheduling instead. </p>
<p> This sounds like, and is, a useful approach. Nevertheless, one has to keep the implications of non-preemptive thread scheduling in mind when working with <code>Pth</code>. The following list summarizes a few essential points:</p>
<dl>
<dt><code>o</code></p>
<dd><code>Pth provides maximum portability, but </code><font SIZE="-1"><code>NOT</code></font><code> the fanciest features</code>. </p>
<p> This is, because it uses a nifty and portable <font SIZE="-1">POSIX/ANSI-C</font> approach for thread creation (and this way doesn&#8217;t require any platform dependent assembler hacks) and schedules the threads in non-preemptive way (which doesn&#8217;t require unportable facilities like <tt>&quot;SIGVTALRM&quot;</tt>). On the other hand, this way not all fancy threading features can be implemented. Nevertheless the available facilities are enough to provide a robust and full-featured threading system.</p>
<dt><code>o</code></p>
<dd><code>Pth increases the responsiveness and concurrency of an event-driven application, but </code><font SIZE="-1"><code>NOT</code></font><code> the concurrency of number-crunching applications</code>. </p>
<p> The reason is the non-preemptive scheduling. Number-crunching applications usually require preemptive scheduling to achieve concurrency because of their long <font SIZE="-1">CPU</font> bursts. For them, non-preemptive scheduling (even together with explicit yielding) provides only the old concept of `coroutines&#8217;. On the other hand, event driven applications benefit greatly from non-preemptive scheduling. They have only short <font SIZE="-1">CPU</font> bursts and lots of events to wait on, and this way run faster under non-preemptive scheduling because no unnecessary context switching occurs, as it is the case for preemptive scheduling. That&#8217;s why <code>Pth</code> is mainly intended for server type applications, although there is no technical restriction.</p>
<dt><code>o</code></p>
<dd><code>Pth requires thread-safe functions, but </code><font SIZE="-1"><code>NOT</code></font><code> reentrant functions</code>. </p>
<p> This nice fact exists again because of the nature of non-preemptive scheduling, where a function isn&#8217;t interrupted and this way cannot be reentered before it returned. This is a great portability benefit, because thread-safety can be achieved more easily than reentrance possibility. Especially this means that under <code>Pth</code> more existing third-party libraries can be used without side-effects than it&#8217;s the case for other threading systems.</p>
<dt><code>o</code></p>
<dd><code>Pth doesn&#8217;t require any kernel support, but can </code><font SIZE="-1"><code>NOT</code></font><code> benefit from multiprocessor machines</code>. </p>
<p> This means that <code>Pth</code> runs on almost all Unix kernels, because the kernel does not need to be aware of the <code>Pth</code> threads (because they are implemented entirely in user-space). On the other hand, it cannot benefit from the existence of multiprocessors, because for this, kernel support would be needed. In practice, this is no problem, because multiprocessor systems are rare, and portability is almost more important than highest concurrency.
</dl>
<p> <code>The life cycle of a thread</code> </p>
<p> To understand the <code>Pth</code> Application Programming Interface (<font SIZE="-1">API</font>), it helps to first understand the life cycle of a thread in the <code>Pth</code> threading system. It can be illustrated with the following directed graph: </p>
<pre> NEW
 |
 V
 +---&gt; READY ---+
 | ^ |
 | | V
 WAITING &lt;--+-- RUNNING
 |
 : V
 SUSPENDED DEAD</pre>
<p>When a new thread is created, it is moved into the <font SIZE="-1"><code>NEW</code></font> queue of the scheduler. On the next dispatching for this thread, the scheduler picks it up from there and moves it to the <font SIZE="-1"><code>READY</code></font> queue. This is a queue containing all threads which want to perform a <font SIZE="-1">CPU</font> burst. There they are queued in priority order. On each dispatching step, the scheduler always removes the thread with the highest priority only. It then increases the priority of all remaining threads by 1, to prevent them from `starving&#8217;. </p>
<p> The thread which was removed from the <font SIZE="-1"><code>READY</code></font> queue is the new <font SIZE="-1"><code>RUNNING</code></font> thread (there is always just one <font SIZE="-1"><code>RUNNING</code></font> thread, of course). The <font SIZE="-1"><code>RUNNING</code></font> thread is assigned execution control. After this thread yields execution (either explicitly by yielding execution or implicitly by calling a function which would block) there are three possibilities: Either it has terminated, then it is moved to the <font SIZE="-1"><code>DEAD</code></font> queue, or it has events on which it wants to wait, then it is moved into the <font SIZE="-1"><code>WAITING</code></font> queue. Else it is assumed it wants to perform more <font SIZE="-1">CPU</font> bursts and immediately enters the <font SIZE="-1"><code>READY</code></font> queue again. </p>
<p> Before the next thread is taken out of the <font SIZE="-1"><code>READY</code></font> queue, the <font SIZE="-1"><code>WAITING</code></font> queue is checked for pending events. If one or more events occurred, the threads that are waiting on them are immediately moved to the <font SIZE="-1"><code>READY</code></font> queue. </p>
<p> The purpose of the <font SIZE="-1"><code>NEW</code></font> queue has to do with the fact that in <code>Pth</code> a thread never directly switches to another thread. A thread always yields execution to the scheduler and the scheduler dispatches to the next thread. So a freshly spawned thread has to be kept somewhere until the scheduler gets a chance to pick it up for scheduling. That is what the <font SIZE="-1"><code>NEW</code></font> queue is for. </p>
<p> The purpose of the <font SIZE="-1"><code>DEAD</code></font> queue is to support thread joining. When a thread is marked to be unjoinable, it is directly kicked out of the system after it terminated. But when it is joinable, it enters the <font SIZE="-1"><code>DEAD</code></font> queue. There it remains until another thread joins it. </p>
<p> Finally, there is a special separated queue named <font SIZE="-1"><code>SUSPENDED</code></font>, to where threads can be manually moved from the <font SIZE="-1"><code>NEW</code></font>, <font SIZE="-1"><code>READY</code></font> or <font SIZE="-1"><code>WAITING</code></font> queues by the application. The purpose of this special queue is to temporarily absorb suspended threads until they are again resumed by the application. Suspended threads do not cost scheduling or event handling resources, because they are temporarily completely out of the scheduler&#8217;s scope. If a thread is resumed, it is moved back to the queue from where it originally came and this way again enters the schedulers scope.</p>
<h2>Application Programming Interface (Api)</h2>
<p>In the following the <code>Pth</code> <i>Application Programming Interface</i> (<font SIZE="-1">API</font>) is discussed in detail. With the knowledge given above, it should now be easy to understand how to program threads with this <font SIZE="-1">API</font>. In good Unix tradition, <code>Pth</code> functions use special return values (<tt>&quot;NULL&quot;</tt> in pointer context, <tt>&quot;FALSE&quot;</tt> in boolean context and <tt>&quot;-1&quot;</tt> in integer context) to indicate an error condition and set (or pass through) the <tt>&quot;errno&quot;</tt> system variable to pass more details about the error to the caller. </p>
<p> <code>Global Library Management</code> </p>
<p> The following functions act on the library as a whole. They are used to initialize and shutdown the scheduler and fetch information from it.</p>
<dl>
<dt>int <code>pth_init</code>(void);</p>
<dd>This initializes the <code>Pth</code> library. It has to be the first <code>Pth</code> <font SIZE="-1">API</font> function call in an application, and is mandatory. It&#8217;s usually done at the begin of the <i>main()</i> function of the application. This implicitly spawns the internal scheduler thread and transforms the single execution unit of the current process into a thread (the `main&#8217; thread). It returns <tt>&quot;TRUE&quot;</tt> on success and <tt>&quot;FALSE&quot;</tt> on error.</p>
<dt>int <code>pth_kill</code>(void);</p>
<dd>This kills the <code>Pth</code> library. It should be the last <code>Pth</code> <font SIZE="-1">API</font> function call in an application, but is not really required. It&#8217;s usually done at the end of the main function of the application. At least, it has to be called from within the main thread. It implicitly kills all threads and transforms back the calling thread into the single execution unit of the underlying process. The usual way to terminate a <code>Pth</code> application is either a simple `<tt>&quot;pth_exit(0);&quot;</tt>&#8216; in the main thread (which waits for all other threads to terminate, kills the threading system and then terminates the process) or a `<tt>&quot;pth_kill(); exit(0)&quot;</tt>&#8216; (which immediately kills the threading system and terminates the process). The <i>pth_kill()</i> return immediately with a return code of <tt>&quot;FALSE&quot;</tt> if it is not called from within the main thread. Else it kills the threading system and returns <tt>&quot;TRUE&quot;</tt>.</p>
<dt>long <code>pth_ctrl</code>(unsigned long <i>query</i>, &#8230;);</p>
<dd>This is a generalized query/control function for the <code>Pth</code> library. The argument <i>query</i> is a bitmask formed out of one or more <tt>&quot;PTH_CTRL_&quot;</tt><i></i><font SIZE="-1"><i>XXXX</i></font><i></i> queries. Currently the following queries are supported:</p>
<dl>
<dd>
<dl>
<dt>&quot;PTH_CTRL_GETTHREADS&quot;</p>
<dd>This returns the total number of threads currently in existence. This query actually is formed out of the combination of queries for threads in a particular state, i.e., the <tt>&quot;PTH_CTRL_GETTHREADS&quot;</tt> query is equal to the OR-combination of all the following specialized queries: </p>
<p> <tt>&quot;PTH_CTRL_GETTHREADS_NEW&quot;</tt> for the number of threads in the new queue (threads created via <i><a href="/docs/linux/man/3-pth_spawn/">pth_spawn</a></i>(3) but still not scheduled once), <tt>&quot;PTH_CTRL_GETTHREADS_READY&quot;</tt> for the number of threads in the ready queue (threads who want to do <font SIZE="-1">CPU</font> bursts), <tt>&quot;PTH_CTRL_GETTHREADS_RUNNING&quot;</tt> for the number of running threads (always just one thread!), <tt>&quot;PTH_CTRL_GETTHREADS_WAITING&quot;</tt> for the number of threads in the waiting queue (threads waiting for events), <tt>&quot;PTH_CTRL_GETTHREADS_SUSPENDED&quot;</tt> for the number of threads in the suspended queue (threads waiting to be resumed) and <tt>&quot;PTH_CTRL_GETTHREADS_DEAD&quot;</tt> for the number of threads in the new queue (terminated threads waiting for a join).</p>
<dt>&quot;PTH_CTRL_GETAVLOAD&quot;</p>
<dd>This requires a second argument of type `<tt>&quot;float *&quot;</tt>&#8216; (pointer to a floating point variable). It stores a floating point value describing the exponential averaged load of the scheduler in this variable. The load is a function from the number of threads in the ready queue of the schedulers dispatching unit. So a load around 1.0 means there is only one ready thread (the standard situation when the application has no high load). A higher load value means there a more threads ready who want to do <font SIZE="-1">CPU</font> bursts. The average load value updates once per second only. The return value for this query is always 0.</p>
<dt>&quot;PTH_CTRL_GETPRIO&quot;</p>
<dd>This requires a second argument of type `<tt>&quot;pth_t&quot;</tt>&#8216; which identifies a thread. It returns the priority (ranging from <tt>&quot;PTH_PRIO_MIN&quot;</tt> to <tt>&quot;PTH_PRIO_MAX&quot;</tt>) of the given thread.</p>
<dt>&quot;PTH_CTRL_GETNAME&quot;</p>
<dd>This requires a second argument of type `<tt>&quot;pth_t&quot;</tt>&#8216; which identifies a thread. It returns the name of the given thread, i.e., the return value of <i><a href="/docs/linux/man/3-pth_ctrl/">pth_ctrl</a></i>(3) should be casted to a `<tt>&quot;char *&quot;</tt>&#8216;.</p>
<dt>&quot;PTH_CTRL_DUMPSTATE&quot;</p>
<dd>This requires a second argument of type `<tt>&quot;FILE *&quot;</tt>&#8216; to which a summary of the internal <code>Pth</code> library state is written to. The main information which is currently written out is the current state of the thread pool.</p>
<dt>&quot;PTH_CTRL_FAVOURNEW&quot;</p>
<dd>This requires a second argument of type `<tt>&quot;int&quot;</tt>&#8216; which specified whether the <font SIZE="-1"><code>GNU</code></font><code> Pth</code> scheduler favours new threads on startup, i.e., whether they are moved from the new queue to the top (argument is <tt>&quot;TRUE&quot;</tt>) or middle (argument is <tt>&quot;FALSE&quot;</tt>) of the ready queue. The default is to favour new threads to make sure they do not starve already at startup, although this slightly violates the strict priority based scheduling.</dl>
</dl>
<dl>
<dd>The function returns <tt>&quot;-1&quot;</tt> on error.</dl>
<dt>long <code>pth_version</code>(void);</p>
<dd>This function returns a hex-value `0x<i>V</i><i></i><font SIZE="-1"><i>RR</i></font><i></i><i>T</i><i></i><font SIZE="-1"><i>LL</i></font><i></i>&#8216; which describes the current <code>Pth</code> library version. <i>V</i> is the version, <i></i><font SIZE="-1"><i>RR</i></font><i></i> the revisions, <i></i><font SIZE="-1"><i>LL</i></font><i></i> the level and <i>T</i> the type of the level (alphalevel=0, betalevel=1, patchlevel=2, etc). For instance <code>Pth</code> version 1.0b1 is encoded as 0x100101. The reason for this unusual mapping is that this way the version number is steadily <i>increasing</i>. The same value is also available under compile time as <tt>&quot;PTH_VERSION&quot;</tt>.
</dl>
<p> <code>Thread Attribute Handling</code> </p>
<p> Attribute objects are used in <code>Pth</code> for two things: First stand-alone/unbound attribute objects are used to store attributes for to be spawned threads. Bounded attribute objects are used to modify attributes of already existing threads. The following attribute fields exists in attribute objects:</p>
<dl>
<dt>&quot;PTH_ATTR_PRIO&quot; (read-write) [<tt>&quot;int&quot;]</p>
<dd>Thread Priority between &quot;PTH_PRIO_MIN&quot;</tt> and <tt>&quot;PTH_PRIO_MAX&quot;</tt>. The default is <tt>&quot;PTH_PRIO_STD&quot;</tt>.</p>
<dt>&quot;PTH_ATTR_NAME&quot; (read-write) [<tt>&quot;char *&quot;]</p>
<dd>Name of thread (up to 40 characters are stored only), mainly for debugging purposes.</p>
<dt>&quot;PTH_ATTR_DISPATCHES&quot;</tt> (read-write) [<tt>&quot;int&quot;]</p>
<dd>In bounded attribute objects, this field is incremented every time the context is switched to the associated thread.</p>
<dt>&quot;PTH_ATTR_JOINABLE&quot;</tt> (read-write&gt; [<tt>&quot;int&quot;]</p>
<dd>The thread detachment type, &quot;TRUE&quot;</tt> indicates a joinable thread, <tt>&quot;FALSE&quot;</tt> indicates a detached thread. When a thread is detached, after termination it is immediately kicked out of the system instead of inserted into the dead queue.</p>
<dt>&quot;PTH_ATTR_CANCEL_STATE&quot; (read-write) [<tt>&quot;unsigned int&quot;]</p>
<dd>The thread cancellation state, i.e., a combination of &quot;PTH_CANCEL_ENABLE&quot;</tt> or <tt>&quot;PTH_CANCEL_DISABLE&quot;</tt> and <tt>&quot;PTH_CANCEL_DEFERRED&quot;</tt> or <tt>&quot;PTH_CANCEL_ASYNCHRONOUS&quot;</tt>.</p>
<dt>&quot;PTH_ATTR_STACK_SIZE&quot; (read-write) [<tt>&quot;unsigned int&quot;]</p>
<dd>The thread stack size in bytes. Use lower values than 64 </tt><font SIZE="-1"><tt>KB</tt></font><tt> with great care!</p>
<dt>&quot;PTH_ATTR_STACK_ADDR&quot;</tt> (read-write) [<tt>&quot;char *&quot;]</p>
<dd>A pointer to the lower address of a chunk of </tt><i><a href="/docs/linux/man/3-malloc/">malloc</a></i>(3)&#8217;ed memory for the stack.</p>
<dt>&quot;PTH_ATTR_TIME_SPAWN&quot; (read-only) [<tt>&quot;pth_time_t&quot;]</p>
<dd>The time when the thread was spawned. This can be queried only when the attribute object is bound to a thread.</p>
<dt>&quot;PTH_ATTR_TIME_LAST&quot;</tt> (read-only) [<tt>&quot;pth_time_t&quot;]</p>
<dd>The time when the thread was last dispatched. This can be queried only when the attribute object is bound to a thread.</p>
<dt>&quot;PTH_ATTR_TIME_RAN&quot;</tt> (read-only) [<tt>&quot;pth_time_t&quot;]</p>
<dd>The total time the thread was running. This can be queried only when the attribute object is bound to a thread.</p>
<dt>&quot;PTH_ATTR_START_FUNC&quot;</tt> (read-only) [<tt>&quot;void *(*)(void *)&quot;]</p>
<dd>The thread start function. This can be queried only when the attribute object is bound to a thread.</p>
<dt>&quot;PTH_ATTR_START_ARG&quot;</tt> (read-only) [<tt>&quot;void *&quot;]</p>
<dd>The thread start argument. This can be queried only when the attribute object is bound to a thread.</p>
<dt>&quot;PTH_ATTR_STATE&quot;</tt> (read-only) [<tt>&quot;pth_state_t&quot;]</p>
<dd>The scheduling state of the thread, i.e., either &quot;PTH_STATE_NEW&quot;</tt>, <tt>&quot;PTH_STATE_READY&quot;</tt>, <tt>&quot;PTH_STATE_WAITING&quot;</tt>, or <tt>&quot;PTH_STATE_DEAD&quot;</tt> This can be queried only when the attribute object is bound to a thread.</p>
<dt>&quot;PTH_ATTR_EVENTS&quot; (read-only) [<tt>&quot;pth_event_t&quot;]</p>
<dd>The event ring the thread is waiting for. This can be queried only when the attribute object is bound to a thread.</p>
<dt>&quot;PTH_ATTR_BOUND&quot;</tt> (read-only) [<tt>&quot;int&quot;]</p>
<dd>Whether the attribute object is bound (&quot;TRUE&quot;</tt>) to a thread or not (<tt>&quot;FALSE&quot;</tt>).</dl>
<p> The following <font SIZE="-1">API</font> functions can be used to handle the attribute objects:</p>
<dl>
<dt>pth_attr_t <code>pth_attr_of</code>(pth_t <i>tid</i>);</p>
<dd>This returns a new attribute object <i>bound</i> to thread <i>tid</i>. Any queries on this object directly fetch attributes from <i>tid</i>. And attribute modifications directly change <i>tid</i>. Use such attribute objects to modify existing threads.</p>
<dt>pth_attr_t <code>pth_attr_new</code>(void);</p>
<dd>This returns a new <i>unbound</i> attribute object. An implicit <i>pth_attr_init()</i> is done on it. Any queries on this object just fetch stored attributes from it. And attribute modifications just change the stored attributes. Use such attribute objects to pre-configure attributes for to be spawned threads.</p>
<dt>int <code>pth_attr_init</code>(pth_attr_t <i>attr</i>);</p>
<dd>This initializes an attribute object <i>attr</i> to the default values: <tt>&quot;PTH_ATTR_PRIO&quot;</tt> := <tt>&quot;PTH_PRIO_STD&quot;</tt>, <tt>&quot;PTH_ATTR_NAME&quot;</tt> := `<tt>&quot;unknown&quot;</tt>&#8216;, <tt>&quot;PTH_ATTR_DISPATCHES&quot;</tt> := <tt>0</tt>, <tt>&quot;PTH_ATTR_JOINABLE&quot;</tt> := <tt>&quot;TRUE&quot;</tt>, <tt>&quot;PTH_ATTR_CANCELSTATE&quot;</tt> := <tt>&quot;PTH_CANCEL_DEFAULT&quot;</tt>, <tt>&quot;PTH_ATTR_STACK_SIZE&quot;</tt> := 64*1024 and <tt>&quot;PTH_ATTR_STACK_ADDR&quot;</tt> := <tt>&quot;NULL&quot;</tt>. All other <tt>&quot;PTH_ATTR_*&quot;</tt> attributes are read-only attributes and don&#8217;t receive default values in <i>attr</i>, because they exists only for bounded attribute objects.</p>
<dt>int <code>pth_attr_set</code>(pth_attr_t <i>attr</i>, int <i>field</i>, &#8230;);</p>
<dd>This sets the attribute field <i>field</i> in <i>attr</i> to a value specified as an additional argument on the variable argument list. The following attribute <i>fields</i> and argument pairs can be used: </p>
<pre> PTH_ATTR_PRIO int
 PTH_ATTR_NAME char *
 PTH_ATTR_DISPATCHES int
 PTH_ATTR_JOINABLE int
 PTH_ATTR_CANCEL_STATE unsigned int
 PTH_ATTR_STACK_SIZE unsigned int
 PTH_ATTR_STACK_ADDR char *</pre>
<dt>int <code>pth_attr_get</code>(pth_attr_t <i>attr</i>, int <i>field</i>, &#8230;);</p>
<dd>This retrieves the attribute field <i>field</i> in <i>attr</i> and stores its value in the variable specified through a pointer in an additional argument on the variable argument list. The following <i>fields</i> and argument pairs can be used: </p>
<pre> PTH_ATTR_PRIO int *
 PTH_ATTR_NAME char **
 PTH_ATTR_DISPATCHES int *
 PTH_ATTR_JOINABLE int *
 PTH_ATTR_CANCEL_STATE unsigned int *
 PTH_ATTR_STACK_SIZE unsigned int *
 PTH_ATTR_STACK_ADDR char **
 PTH_ATTR_TIME_SPAWN pth_time_t *
 PTH_ATTR_TIME_LAST pth_time_t *
 PTH_ATTR_TIME_RAN pth_time_t *
 PTH_ATTR_START_FUNC void *(**)(void *)
 PTH_ATTR_START_ARG void **
 PTH_ATTR_STATE pth_state_t *
 PTH_ATTR_EVENTS pth_event_t *
 PTH_ATTR_BOUND int *</pre>
<dt>int <code>pth_attr_destroy</code>(pth_attr_t <i>attr</i>);</p>
<dd>This destroys a attribute object <i>attr</i>. After this <i>attr</i> is no longer a valid attribute object.
</dl>
<p> <code>Thread Control</code> </p>
<p> The following functions control the threading itself and make up the main <font SIZE="-1">API</font> of the <code>Pth</code> library.</p>
<dl>
<dt>pth_t <code>pth_spawn</code>(pth_attr_t <i>attr</i>, void *(*<i>entry</i>)(void *), void *<i>arg</i>);</p>
<dd>This spawns a new thread with the attributes given in <i>attr</i> (or <tt>&quot;PTH_ATTR_DEFAULT&quot;</tt> for default attributes &#8211; which means that thread priority, joinability and cancel state are inherited from the current thread) with the starting point at routine <i>entry</i>; the dispatch count is not inherited from the current thread if <i>attr</i> is not specified &#8211; rather, it is initialized to zero. This entry routine is called as `pth_exit(<i>entry</i>(<i>arg</i>))&#8217; inside the new thread unit, i.e., <i>entry</i>&#8216;s return value is fed to an implicit <i><a href="/docs/linux/man/3-pth_exit/">pth_exit</a></i>(3). So the thread can also exit by just returning. Nevertheless the thread can also exit explicitly at any time by calling <i><a href="/docs/linux/man/3-pth_exit/">pth_exit</a></i>(3). But keep in mind that calling the <font SIZE="-1">POSIX</font> function <i><a href="/docs/linux/man/3-exit/">exit</a></i>(3) still terminates the complete process and not just the current thread. </p>
<p> There is no <code>Pth</code>-internal limit on the number of threads one can spawn, except the limit implied by the available virtual memory. <code>Pth</code> internally keeps track of thread in dynamic data structures. The function returns <tt>&quot;NULL&quot;</tt> on error.</p>
<dt>int <code>pth_once</code>(pth_once_t *<i>ctrlvar</i>, void (*<i>func</i>)(void *), void *<i>arg</i>);</p>
<dd>This is a convenience function which uses a control variable of type <tt>&quot;pth_once_t&quot;</tt> to make sure a constructor function <i>func</i> is called only once as `<i>func</i>(<i>arg</i>)&#8217; in the system. In other words: Only the first call to <i><a href="/docs/linux/man/3-pth_once/">pth_once</a></i>(3) by any thread in the system succeeds. The variable referenced via <i>ctrlvar</i> should be declared as `<tt>&quot;pth_once_t&quot;</tt> <i>variable-name</i> = <tt>&quot;PTH_ONCE_INIT&quot;</tt>;&#8217; before calling this function.</p>
<dt>pth_t <code>pth_self</code>(void);</p>
<dd>This just returns the unique thread handle of the currently running thread. This handle itself has to be treated as an opaque entity by the application. It&#8217;s usually used as an argument to other functions who require an argument of type <tt>&quot;pth_t&quot;</tt>.</p>
<dt>int <code>pth_suspend</code>(pth_t <i>tid</i>);</p>
<dd>This suspends a thread <i>tid</i> until it is manually resumed again via <i><a href="/docs/linux/man/3-pth_resume/">pth_resume</a></i>(3). For this, the thread is moved to the <font SIZE="-1"><code>SUSPENDED</code></font> queue and this way is completely out of the scheduler&#8217;s event handling and thread dispatching scope. Suspending the current thread is not allowed. The function returns <tt>&quot;TRUE&quot;</tt> on success and <tt>&quot;FALSE&quot;</tt> on errors.</p>
<dt>int <code>pth_resume</code>(pth_t <i>tid</i>);</p>
<dd>This function resumes a previously suspended thread <i>tid</i>, i.e. <i>tid</i> has to stay on the <font SIZE="-1"><code>SUSPENDED</code></font> queue. The thread is moved to the <font SIZE="-1"><code>NEW</code></font>, <font SIZE="-1"><code>READY</code></font> or <font SIZE="-1"><code>WAITING</code></font> queue (dependent on what its state was when the <i><a href="/docs/linux/man/3-pth_suspend/">pth_suspend</a></i>(3) call were made) and this way again enters the event handling and thread dispatching scope of the scheduler. The function returns <tt>&quot;TRUE&quot;</tt> on success and <tt>&quot;FALSE&quot;</tt> on errors.</p>
<dt>int <code>pth_raise</code>(pth_t <i>tid</i>, int <i>sig</i>)</p>
<dd>This function raises a signal for delivery to thread <i>tid</i> only. When one just raises a signal via <i><a href="/docs/linux/man/3-raise/">raise</a></i>(3) or <i><a href="/docs/linux/man/2-kill/">kill</a></i>(2), its delivered to an arbitrary thread which has this signal not blocked. With <i><a href="/docs/linux/man/3-pth_raise/">pth_raise</a></i>(3) one can send a signal to a thread and its guarantees that only this thread gets the signal delivered. But keep in mind that nevertheless the signals <i>action</i> is still configured <i>process</i>-wide. When <i>sig</i> is 0 plain thread checking is performed, i.e., `<tt>&quot;pth_raise(tid, 0)&quot;</tt>&#8216; returns <tt>&quot;TRUE&quot;</tt> when thread <i>tid</i> still exists in the <font SIZE="-1"><code>PTH</code></font> system but doesn&#8217;t send any signal to it.</p>
<dt>int <code>pth_yield</code>(pth_t <i>tid</i>);</p>
<dd>This explicitly yields back the execution control to the scheduler thread. Usually the execution is implicitly transferred back to the scheduler when a thread waits for an event. But when a thread has to do larger <font SIZE="-1">CPU</font> bursts, it can be reasonable to interrupt it explicitly by doing a few <i><a href="/docs/linux/man/3-pth_yield/">pth_yield</a></i>(3) calls to give other threads a chance to execute, too. This obviously is the cooperating part of <code>Pth</code>. A thread <i>has not</i> to yield execution, of course. But when you want to program a server application with good response times the threads should be cooperative, i.e., when they should split their <font SIZE="-1">CPU</font> bursts into smaller units with this call. </p>
<p> Usually one specifies <i>tid</i> as <tt>&quot;NULL&quot;</tt> to indicate to the scheduler that it can freely decide which thread to dispatch next. But if one wants to indicate to the scheduler that a particular thread should be favored on the next dispatching step, one can specify this thread explicitly. This allows the usage of the old concept of <i>coroutines</i> where a thread/routine switches to a particular cooperating thread. If <i>tid</i> is not <tt>&quot;NULL&quot;</tt> and points to a <i>new</i> or <i>ready</i> thread, it is guaranteed that this thread receives execution control on the next dispatching step. If <i>tid</i> is in a different state (that is, not in <tt>&quot;PTH_STATE_NEW&quot;</tt> or <tt>&quot;PTH_STATE_READY&quot;</tt>) an error is reported. </p>
<p> The function usually returns <tt>&quot;TRUE&quot;</tt> for success and only <tt>&quot;FALSE&quot;</tt> (with <tt>&quot;errno&quot;</tt> set to <tt>&quot;EINVAL&quot;</tt>) if <i>tid</i> specified an invalid or still not new or ready thread.</p>
<dt>int <code>pth_nap</code>(pth_time_t <i>naptime</i>);</p>
<dd>This functions suspends the execution of the current thread until <i>naptime</i> is elapsed. <i>naptime</i> is of type <tt>&quot;pth_time_t&quot;</tt> and this way has theoretically a resolution of one microsecond. In practice you should neither rely on this nor that the thread is awakened exactly after <i>naptime</i> has elapsed. It&#8217;s only guarantees that the thread will sleep at least <i>naptime</i>. But because of the non-preemptive nature of <code>Pth</code> it can last longer (when another thread kept the <font SIZE="-1">CPU</font> for a long time). Additionally the resolution is dependent of the implementation of timers by the operating system and these usually have only a resolution of 10 microseconds or larger. But usually this isn&#8217;t important for an application unless it tries to use this facility for real time tasks.</p>
<dt>int <code>pth_wait</code>(pth_event_t <i>ev</i>);</p>
<dd>This is the link between the scheduler and the event facility (see below for the various <i>pth_event_xxx()</i> functions). It&#8217;s modeled like <i><a href="/docs/linux/man/2-select/">select</a></i>(2), i.e., one gives this function one or more events (in the event ring specified by <i>ev</i>) on which the current thread wants to wait. The scheduler awakes the thread when one ore more of them occurred or failed after tagging them as such. The <i>ev</i> argument is a <i>pointer</i> to an event ring which isn&#8217;t changed except for the tagging. <i><a href="/docs/linux/man/3-pth_wait/">pth_wait</a></i>(3) returns the number of occurred or failed events and the application can use <i><a href="/docs/linux/man/3-pth_event_status/">pth_event_status</a></i>(3) to test which events occurred or failed.</p>
<dt>int <code>pth_cancel</code>(pth_t <i>tid</i>);</p>
<dd>This cancels a thread <i>tid</i>. How the cancellation is done depends on the cancellation state of <i>tid</i> which the thread can configure itself. When its state is <tt>&quot;PTH_CANCEL_DISABLE&quot;</tt> a cancellation request is just made pending. When it is <tt>&quot;PTH_CANCEL_ENABLE&quot;</tt> it depends on the cancellation type what is performed. When its <tt>&quot;PTH_CANCEL_DEFERRED&quot;</tt> again the cancellation request is just made pending. But when its <tt>&quot;PTH_CANCEL_ASYNCHRONOUS&quot;</tt> the thread is immediately canceled before <i><a href="/docs/linux/man/3-pth_cancel/">pth_cancel</a></i>(3) returns. The effect of a thread cancellation is equal to implicitly forcing the thread to call `<tt>&quot;pth_exit(PTH_CANCELED)&quot;</tt>&#8216; at one of his cancellation points. In <code>Pth</code> thread enter a cancellation point either explicitly via <i><a href="/docs/linux/man/3-pth_cancel_point/">pth_cancel_point</a></i>(3) or implicitly by waiting for an event.</p>
<dt>int <code>pth_abort</code>(pth_t <i>tid</i>);</p>
<dd>This is the cruel way to cancel a thread <i>tid</i>. When it&#8217;s already dead and waits to be joined it just joins it (via `<tt>&quot;pth_join(&quot;</tt><i>tid</i><tt>&quot;, NULL)&quot;</tt>&#8216;) and this way kicks it out of the system. Else it forces the thread to be not joinable and to allow asynchronous cancellation and then cancels it via `<tt>&quot;pth_cancel(&quot;</tt><i>tid</i><tt>&quot;)&quot;</tt>&#8216;.</p>
<dt>int <code>pth_join</code>(pth_t <i>tid</i>, void **<i>value</i>);</p>
<dd>This joins the current thread with the thread specified via <i>tid</i>. It first suspends the current thread until the <i>tid</i> thread has terminated. Then it is awakened and stores the value of <i>tid</i>&#8216;s <i><a href="/docs/linux/man/3-pth_exit/">pth_exit</a></i>(3) call into *<i>value</i> (if <i>value</i> and not <tt>&quot;NULL&quot;</tt>) and returns to the caller. A thread can be joined only when it has the attribute <tt>&quot;PTH_ATTR_JOINABLE&quot;</tt> set to <tt>&quot;TRUE&quot;</tt> (the default). A thread can only be joined once, i.e., after the <i><a href="/docs/linux/man/3-pth_join/">pth_join</a></i>(3) call the thread <i>tid</i> is completely removed from the system.</p>
<dt>void <code>pth_exit</code>(void *<i>value</i>);</p>
<dd>This terminates the current thread. Whether it&#8217;s immediately removed from the system or inserted into the dead queue of the scheduler depends on its join type which was specified at spawning time. If it has the attribute <tt>&quot;PTH_ATTR_JOINABLE&quot;</tt> set to <tt>&quot;FALSE&quot;</tt>, it&#8217;s immediately removed and <i>value</i> is ignored. Else the thread is inserted into the dead queue and <i>value</i> remembered for a subsequent <i><a href="/docs/linux/man/3-pth_join/">pth_join</a></i>(3) call by another thread.
</dl>
<p> <code>Utilities</code> </p>
<p> Utility functions.</p>
<dl>
<dt>int <code>pth_fdmode</code>(int <i>fd</i>, int <i>mode</i>);</p>
<dd>This switches the non-blocking mode flag on file descriptor <i>fd</i>. The argument <i>mode</i> can be <tt>&quot;PTH_FDMODE_BLOCK&quot;</tt> for switching <i>fd</i> into blocking I/O mode, <tt>&quot;PTH_FDMODE_NONBLOCK&quot;</tt> for switching <i>fd</i> into non-blocking I/O mode or <tt>&quot;PTH_FDMODE_POLL&quot;</tt> for just polling the current mode. The current mode is returned (either <tt>&quot;PTH_FDMODE_BLOCK&quot;</tt> or <tt>&quot;PTH_FDMODE_NONBLOCK&quot;</tt>) or <tt>&quot;PTH_FDMODE_ERROR&quot;</tt> on error. Keep in mind that since <code>Pth</code> 1.1 there is no longer a requirement to manually switch a file descriptor into non-blocking mode in order to use it. This is automatically done temporarily inside <code>Pth</code>. Instead when you now switch a file descriptor explicitly into non-blocking mode, <i><a href="/docs/linux/man/3-pth_read/">pth_read</a></i>(3) or <i><a href="/docs/linux/man/3-pth_write/">pth_write</a></i>(3) will never block the current thread.</p>
<dt>pth_time_t <code>pth_time</code>(long <i>sec</i>, long <i>usec</i>);</p>
<dd>This is a constructor for a <tt>&quot;pth_time_t&quot;</tt> structure which is a convenient function to avoid temporary structure values. It returns a <i>pth_time_t</i> structure which holds the absolute time value specified by <i>sec</i> and <i>usec</i>.</p>
<dt>pth_time_t <code>pth_timeout</code>(long <i>sec</i>, long <i>usec</i>);</p>
<dd>This is a constructor for a <tt>&quot;pth_time_t&quot;</tt> structure which is a convenient function to avoid temporary structure values. It returns a <i>pth_time_t</i> structure which holds the absolute time value calculated by adding <i>sec</i> and <i>usec</i> to the current time.</p>
<dt>Sfdisc_t *<code>pth_sfiodisc</code>(void);</p>
<dd>This functions is always available, but only reasonably usable when <code>Pth</code> was built with <code>Sfio</code> support (<tt>&quot;--with-sfio&quot;</tt> option) and <tt>&quot;PTH_EXT_SFIO&quot;</tt> is then defined by <tt>&quot;pth.h&quot;</tt>. It is useful for applications which want to use the comprehensive <code>Sfio</code> I/O library with the <code>Pth</code> threading library. Then this function can be used to get an <code>Sfio</code> discipline structure (<tt>&quot;Sfdisc_t&quot;</tt>) which can be pushed onto <code>Sfio</code> streams (<tt>&quot;Sfio_t&quot;</tt>) in order to let this stream use <i><a href="/docs/linux/man/3-pth_read/">pth_read</a></i>(3)/<i><a href="/docs/linux/man/2-pth_write/">pth_write</a></i>(2) instead of <i><a href="/docs/linux/man/2-read/">read</a></i>(2)/<i><a href="/docs/linux/man/2-write/">write</a></i>(2). The benefit is that this way I/O on the <code>Sfio</code> stream does only block the current thread instead of the whole process. The application has to <i><a href="/docs/linux/man/3-free/">free</a></i>(3) the <tt>&quot;Sfdisc_t&quot;</tt> structure when it is no longer needed. The Sfio package can be found at <a rel="nofollow" href="http://www.research.att.com/sw/tools/sfio/.">http://www.research.att.com/sw/tools/sfio/.</a>
</dl>
<p> <code>Cancellation Management</code> </p>
<p> <code>Pth</code> supports <font SIZE="-1">POSIX</font> style thread cancellation via <i><a href="/docs/linux/man/3-pth_cancel/">pth_cancel</a></i>(3) and the following two related functions:</p>
<dl>
<dt>void <code>pth_cancel_state</code>(int <i>newstate</i>, int *<i>oldstate</i>);</p>
<dd>This manages the cancellation state of the current thread. When <i>oldstate</i> is not <tt>&quot;NULL&quot;</tt> the function stores the old cancellation state under the variable pointed to by <i>oldstate</i>. When <i>newstate</i> is not <tt>0</tt> it sets the new cancellation state. <i>oldstate</i> is created before <i>newstate</i> is set. A state is a combination of <tt>&quot;PTH_CANCEL_ENABLE&quot;</tt> or <tt>&quot;PTH_CANCEL_DISABLE&quot;</tt> and <tt>&quot;PTH_CANCEL_DEFERRED&quot;</tt> or <tt>&quot;PTH_CANCEL_ASYNCHRONOUS&quot;</tt>. <tt>&quot;PTH_CANCEL_ENABLE|PTH_CANCEL_DEFERRED&quot;</tt> (or <tt>&quot;PTH_CANCEL_DEFAULT&quot;</tt>) is the default state where cancellation is possible but only at cancellation points. Use <tt>&quot;PTH_CANCEL_DISABLE&quot;</tt> to complete disable cancellation for a thread and <tt>&quot;PTH_CANCEL_ASYNCHRONOUS&quot;</tt> for allowing asynchronous cancellations, i.e., cancellations which can happen at any time.</p>
<dt>void <code>pth_cancel_point</code>(void);</p>
<dd>This explicitly enter a cancellation point. When the current cancellation state is <tt>&quot;PTH_CANCEL_DISABLE&quot;</tt> or no cancellation request is pending, this has no side-effect and returns immediately. Else it calls `<tt>&quot;pth_exit(PTH_CANCELED)&quot;</tt>&#8216;.
</dl>
<p> <code>Event Handling</code> </p>
<p> <code>Pth</code> has a very flexible event facility which is linked into the scheduler through the <i><a href="/docs/linux/man/3-pth_wait/">pth_wait</a></i>(3) function. The following functions provide the handling of event rings.</p>
<dl>
<dt>pth_event_t <code>pth_event</code>(unsigned long <i>spec</i>, &#8230;);</p>
<dd>This creates a new event ring consisting of a single initial event. The type of the generated event is specified by <i>spec</i>. The following types are available:</p>
<dl>
<dd>
<dl>
<dt>&quot;PTH_EVENT_FD&quot;</p>
<dd>This is a file descriptor event. One or more of <tt>&quot;PTH_UNTIL_FD_READABLE&quot;</tt>, <tt>&quot;PTH_UNTIL_FD_WRITEABLE&quot;</tt> or <tt>&quot;PTH_UNTIL_FD_EXCEPTION&quot;</tt> have to be OR-ed into <i>spec</i> to specify on which state of the file descriptor you want to wait. The file descriptor itself has to be given as an additional argument. Example: `<tt>&quot;pth_event(PTH_EVENT_FD|PTH_UNTIL_FD_READABLE, fd)&quot;</tt>&#8216;.</p>
<dt>&quot;PTH_EVENT_SELECT&quot;</p>
<dd>This is a multiple file descriptor event modeled directly after the <i><a href="/docs/linux/man/2-select/">select</a></i>(2) call (actually it is also used to implement <i><a href="/docs/linux/man/3-pth_select/">pth_select</a></i>(3) internally). It&#8217;s a convenient way to wait for a large set of file descriptors at once and at each file descriptor for a different type of state. Additionally as a nice side-effect one receives the number of file descriptors which causes the event to be occurred (using <font SIZE="-1">BSD</font> semantics, i.e., when a file descriptor occurred in two sets it&#8217;s counted twice). The arguments correspond directly to the <i><a href="/docs/linux/man/2-select/">select</a></i>(2) function arguments except that there is no timeout argument (because timeouts already can be handled via <tt>&quot;PTH_EVENT_TIME&quot;</tt> events). </p>
<p> Example: `<tt>&quot;pth_event(PTH_EVENT_SELECT, &amp;rc, nfd, rfds, wfds, efds)&quot;</tt>&#8216; where <tt>&quot;rc&quot;</tt> has to be of type `<tt>&quot;int *&quot;</tt>&#8216;, <tt>&quot;nfd&quot;</tt> has to be of type `<tt>&quot;int&quot;</tt>&#8216; and <tt>&quot;rfds&quot;</tt>, <tt>&quot;wfds&quot;</tt> and <tt>&quot;efds&quot;</tt> have to be of type `<tt>&quot;fd_set *&quot;</tt>&#8216; (see <i><a href="/docs/linux/man/2-select/">select</a></i>(2)). The number of occurred file descriptors are stored in <tt>&quot;rc&quot;</tt>.</p>
<dt>&quot;PTH_EVENT_SIGS&quot;</p>
<dd>This is a signal set event. The two additional arguments have to be a pointer to a signal set (type `<tt>&quot;sigset_t *&quot;</tt>&#8216;) and a pointer to a signal number variable (type `<tt>&quot;int *&quot;</tt>&#8216;). This event waits until one of the signals in the signal set occurred. As a result the occurred signal number is stored in the second additional argument. Keep in mind that the <code>Pth</code> scheduler doesn&#8217;t block signals automatically. So when you want to wait for a signal with this event you&#8217;ve to block it via <i><a href="/docs/linux/man/2-sigprocmask/">sigprocmask</a></i>(2) or it will be delivered without your notice. Example: `<tt>&quot;sigemptyset(&amp;set); sigaddset(&amp;set, SIGINT); pth_event(PTH_EVENT_SIG, &amp;set, &amp;sig);&quot;</tt>&#8216;.</p>
<dt>&quot;PTH_EVENT_TIME&quot;</p>
<dd>This is a time point event. The additional argument has to be of type <tt>&quot;pth_time_t&quot;</tt> (usually on-the-fly generated via <i><a href="/docs/linux/man/3-pth_time/">pth_time</a></i>(3)). This events waits until the specified time point has elapsed. Keep in mind that the value is an absolute time point and not an offset. When you want to wait for a specified amount of time, you&#8217;ve to add the current time to the offset (usually on-the-fly achieved via <i><a href="/docs/linux/man/3-pth_timeout/">pth_timeout</a></i>(3)). Example: `<tt>&quot;pth_event(PTH_EVENT_TIME, pth_timeout(2,0))&quot;</tt>&#8216;.</p>
<dt>&quot;PTH_EVENT_MSG&quot;</p>
<dd>This is a message port event. The additional argument has to be of type <tt>&quot;pth_msgport_t&quot;</tt>. This events waits until one or more messages were received on the specified message port. Example: `<tt>&quot;pth_event(PTH_EVENT_MSG, mp)&quot;</tt>&#8216;.</p>
<dt>&quot;PTH_EVENT_TID&quot;</p>
<dd>This is a thread event. The additional argument has to be of type <tt>&quot;pth_t&quot;</tt>. One of <tt>&quot;PTH_UNTIL_TID_NEW&quot;</tt>, <tt>&quot;PTH_UNTIL_TID_READY&quot;</tt>, <tt>&quot;PTH_UNTIL_TID_WAITING&quot;</tt> or <tt>&quot;PTH_UNTIL_TID_DEAD&quot;</tt> has to be OR-ed into <i>spec</i> to specify on which state of the thread you want to wait. Example: `<tt>&quot;pth_event(PTH_EVENT_TID|PTH_UNTIL_TID_DEAD, tid)&quot;</tt>&#8216;.</p>
<dt>&quot;PTH_EVENT_FUNC&quot;</p>
<dd>This is a custom callback function event. Three additional arguments have to be given with the following types: `<tt>&quot;int (*)(void *)&quot;</tt>&#8216;, `<tt>&quot;void *&quot;</tt>&#8216; and `<tt>&quot;pth_time_t&quot;</tt>&#8216;. The first is a function pointer to a check function and the second argument is a user-supplied context value which is passed to this function. The scheduler calls this function on a regular basis (on his own scheduler stack, so be very careful!) and the thread is kept sleeping while the function returns <tt>&quot;FALSE&quot;</tt>. Once it returned <tt>&quot;TRUE&quot;</tt> the thread will be awakened. The check interval is defined by the third argument, i.e., the check function is polled again not until this amount of time elapsed. Example: `<tt>&quot;pth_event(PTH_EVENT_FUNC, func, arg, pth_time(0,500000))&quot;</tt>&#8216;.</dl>
</dl>
<dl>
<dd></dl>
<dt>unsigned long <code>pth_event_typeof</code>(pth_event_t <i>ev</i>);</p>
<dd>This returns the type of event <i>ev</i>. It&#8217;s a combination of the describing <tt>&quot;PTH_EVENT_XX&quot;</tt> and <tt>&quot;PTH_UNTIL_XX&quot;</tt> value. This is especially useful to know which arguments have to be supplied to the <i><a href="/docs/linux/man/3-pth_event_extract/">pth_event_extract</a></i>(3) function.</p>
<dt>int <code>pth_event_extract</code>(pth_event_t <i>ev</i>, &#8230;);</p>
<dd>When <i><a href="/docs/linux/man/3-pth_event/">pth_event</a></i>(3) is treated like <i><a href="/docs/linux/man/3-sprintf/">sprintf</a></i>(3), then this function is <i><a href="/docs/linux/man/3-sscanf/">sscanf</a></i>(3), i.e., it is the inverse operation of <i><a href="/docs/linux/man/3-pth_event/">pth_event</a></i>(3). This means that it can be used to extract the ingredients of an event. The ingredients are stored into variables which are given as pointers on the variable argument list. Which pointers have to be present depends on the event type and has to be determined by the caller before via <i><a href="/docs/linux/man/3-pth_event_typeof/">pth_event_typeof</a></i>(3). </p>
<p> To make it clear, when you constructed <i>ev</i> via `<tt>&quot;ev = pth_event(PTH_EVENT_FD, fd);&quot;</tt>&#8216; you have to extract it via `<tt>&quot;pth_event_extract(ev, &amp;fd)&quot;</tt>&#8216;, etc. For multiple arguments of an event the order of the pointer arguments is the same as for <i><a href="/docs/linux/man/3-pth_event/">pth_event</a></i>(3). But always keep in mind that you have to always supply <i>pointers</i> to <i>variables</i> and these variables have to be of the same type as the argument of <i><a href="/docs/linux/man/3-pth_event/">pth_event</a></i>(3) required.</p>
<dt>pth_event_t <code>pth_event_concat</code>(pth_event_t <i>ev</i>, &#8230;);</p>
<dd>This concatenates one or more additional event rings to the event ring <i>ev</i> and returns <i>ev</i>. The end of the argument list has to be marked with a <tt>&quot;NULL&quot;</tt> argument. Use this function to create real events rings out of the single-event rings created by <i><a href="/docs/linux/man/3-pth_event/">pth_event</a></i>(3).</p>
<dt>pth_event_t <code>pth_event_isolate</code>(pth_event_t <i>ev</i>);</p>
<dd>This isolates the event <i>ev</i> from possibly appended events in the event ring. When in <i>ev</i> only one event exists, this returns <tt>&quot;NULL&quot;</tt>. When remaining events exists, they form a new event ring which is returned.</p>
<dt>pth_event_t <code>pth_event_walk</code>(pth_event_t <i>ev</i>, int <i>direction</i>);</p>
<dd>This walks to the next (when <i>direction</i> is <tt>&quot;PTH_WALK_NEXT&quot;</tt>) or previews (when <i>direction</i> is <tt>&quot;PTH_WALK_PREV&quot;</tt>) event in the event ring <i>ev</i> and returns this new reached event. Additionally <tt>&quot;PTH_UNTIL_OCCURRED&quot;</tt> can be OR-ed into <i>direction</i> to walk to the next/previous occurred event in the ring <i>ev</i>.</p>
<dt>pth_status_t <code>pth_event_status</code>(pth_event_t <i>ev</i>);</p>
<dd>This returns the status of event <i>ev</i>. This is a fast operation because only a tag on <i>ev</i> is checked which was either set or still not set by the scheduler. In other words: This doesn&#8217;t check the event itself, it just checks the last knowledge of the scheduler. The possible returned status codes are: <tt>&quot;PTH_STATUS_PENDING&quot;</tt> (event is still pending), <tt>&quot;PTH_STATUS_OCCURRED&quot;</tt> (event successfully occurred), <tt>&quot;PTH_STATUS_FAILED&quot;</tt> (event failed).</p>
<dt>int <code>pth_event_free</code>(pth_event_t <i>ev</i>, int <i>mode</i>);</p>
<dd>This deallocates the event <i>ev</i> (when <i>mode</i> is <tt>&quot;PTH_FREE_THIS&quot;</tt>) or all events appended to the event ring under <i>ev</i> (when <i>mode</i> is <tt>&quot;PTH_FREE_ALL&quot;</tt>).
</dl>
<p> <code>Key-Based Storage</code> </p>
<p> The following functions provide thread-local storage through unique keys similar to the <font SIZE="-1">POSIX</font> <code>Pthread</code> <font SIZE="-1">API</font>. Use this for thread specific global data.</p>
<dl>
<dt>int <code>pth_key_create</code>(pth_key_t *<i>key</i>, void (*<i>func</i>)(void *));</p>
<dd>This created a new unique key and stores it in <i>key</i>. Additionally <i>func</i> can specify a destructor function which is called on the current threads termination with the <i>key</i>.</p>
<dt>int <code>pth_key_delete</code>(pth_key_t <i>key</i>);</p>
<dd>This explicitly destroys a key <i>key</i>.</p>
<dt>int <code>pth_key_setdata</code>(pth_key_t <i>key</i>, const void *<i>value</i>);</p>
<dd>This stores <i>value</i> under <i>key</i>.</p>
<dt>void *<code>pth_key_getdata</code>(pth_key_t <i>key</i>);</p>
<dd>This retrieves the value under <i>key</i>.
</dl>
<p> <code>Message Port Communication</code> </p>
<p> The following functions provide message ports which can be used for efficient and flexible inter-thread communication.</p>
<dl>
<dt>pth_msgport_t <code>pth_msgport_create</code>(const char *<i>name</i>);</p>
<dd>This returns a pointer to a new message port. If name <i>name</i> is not <tt>&quot;NULL&quot;</tt>, the <i>name</i> can be used by other threads via <i><a href="/docs/linux/man/3-pth_msgport_find/">pth_msgport_find</a></i>(3) to find the message port in case they do not know directly the pointer to the message port.</p>
<dt>void <code>pth_msgport_destroy</code>(pth_msgport_t <i>mp</i>);</p>
<dd>This destroys a message port <i>mp</i>. Before all pending messages on it are replied to their origin message port.</p>
<dt>pth_msgport_t <code>pth_msgport_find</code>(const char *<i>name</i>);</p>
<dd>This finds a message port in the system by <i>name</i> and returns the pointer to it.</p>
<dt>int <code>pth_msgport_pending</code>(pth_msgport_t <i>mp</i>);</p>
<dd>This returns the number of pending messages on message port <i>mp</i>.</p>
<dt>int <code>pth_msgport_put</code>(pth_msgport_t <i>mp</i>, pth_message_t *<i>m</i>);</p>
<dd>This puts (or sends) a message <i>m</i> to message port <i>mp</i>.</p>
<dt>pth_message_t *<code>pth_msgport_get</code>(pth_msgport_t <i>mp</i>);</p>
<dd>This gets (or receives) the top message from message port <i>mp</i>. Incoming messages are always kept in a queue, so there can be more pending messages, of course.</p>
<dt>int <code>pth_msgport_reply</code>(pth_message_t *<i>m</i>);</p>
<dd>This replies a message <i>m</i> to the message port of the sender.
</dl>
<p> <code>Thread Cleanups</code> </p>
<p> Per-thread cleanup functions.</p>
<dl>
<dt>int <code>pth_cleanup_push</code>(void (*<i>handler</i>)(void *), void *<i>arg</i>);</p>
<dd>This pushes the routine <i>handler</i> onto the stack of cleanup routines for the current thread. These routines are called in <font SIZE="-1">LIFO</font> order when the thread terminates.</p>
<dt>int <code>pth_cleanup_pop</code>(int <i>execute</i>);</p>
<dd>This pops the top-most routine from the stack of cleanup routines for the current thread. When <i>execute</i> is <tt>&quot;TRUE&quot;</tt> the routine is additionally called.
</dl>
<p> <code>Process Forking</code> </p>
<p> The following functions provide some special support for process forking situations inside the threading environment.</p>
<dl>
<dt>int <code>pth_atfork_push</code>(void (*<i>prepare</i>)(void *), void (*)(void *<i>parent</i>), void (*)(void *<i>child</i>), void *<i>arg</i>);</p>
<dd>This function declares forking handlers to be called before and after <i><a href="/docs/linux/man/3-pth_fork/">pth_fork</a></i>(3), in the context of the thread that called <i><a href="/docs/linux/man/3-pth_fork/">pth_fork</a></i>(3). The <i>prepare</i> handler is called before <i><a href="/docs/linux/man/2-fork/">fork</a></i>(2) processing commences. The <i>parent</i> handler is called after <i><a href="/docs/linux/man/2-fork/">fork</a></i>(2) processing completes in the parent process. The <i>child</i> handler is called after <i><a href="/docs/linux/man/2-fork/">fork</a></i>(2) processing completed in the child process. If no handling is desired at one or more of these three points, the corresponding handler can be given as <tt>&quot;NULL&quot;</tt>. Each handler is called with <i>arg</i> as the argument. </p>
<p> The order of calls to <i><a href="/docs/linux/man/3-pth_atfork_push/">pth_atfork_push</a></i>(3) is significant. The <i>parent</i> and <i>child</i> handlers are called in the order in which they were established by calls to <i><a href="/docs/linux/man/3-pth_atfork_push/">pth_atfork_push</a></i>(3), i.e., <font SIZE="-1">FIFO</font>. The <i>prepare</i> fork handlers are called in the opposite order, i.e., <font SIZE="-1">LIFO</font>.</p>
<dt>int <code>pth_atfork_pop</code>(void);</p>
<dd>This removes the top-most handlers on the forking handler stack which were established with the last <i><a href="/docs/linux/man/3-pth_atfork_push/">pth_atfork_push</a></i>(3) call. It returns <tt>&quot;FALSE&quot;</tt> when no more handlers couldn&#8217;t be removed from the stack.</p>
<dt>pid_t <code>pth_fork</code>(void);</p>
<dd>This is a variant of <i><a href="/docs/linux/man/2-fork/">fork</a></i>(2) with the difference that the current thread only is forked into a separate process, i.e., in the parent process nothing changes while in the child process all threads are gone except for the scheduler and the calling thread. When you really want to duplicate all threads in the current process you should use <i><a href="/docs/linux/man/2-fork/">fork</a></i>(2) directly. But this is usually not reasonable. Additionally this function takes care of forking handlers as established by <i><a href="/docs/linux/man/3-pth_fork_push/">pth_fork_push</a></i>(3).
</dl>
<p> <code>Synchronization</code> </p>
<p> The following functions provide synchronization support via mutual exclusion locks (<code>mutex</code>), read-write locks (<code>rwlock</code>), condition variables (<code>cond</code>) and barriers (<code>barrier</code>). Keep in mind that in a non-preemptive threading system like <code>Pth</code> this might sound unnecessary at the first look, because a thread isn&#8217;t interrupted by the system. Actually when you have a critical code section which doesn&#8217;t contain any <i>pth_xxx()</i> functions, you don&#8217;t need any mutex to protect it, of course. </p>
<p> But when your critical code section contains any <i>pth_xxx()</i> function the chance is high that these temporarily switch to the scheduler. And this way other threads can make progress and enter your critical code section, too. This is especially true for critical code sections which implicitly or explicitly use the event mechanism.</p>
<dl>
<dt>int <code>pth_mutex_init</code>(pth_mutex_t *<i>mutex</i>);</p>
<dd>This dynamically initializes a mutex variable of type `<tt>&quot;pth_mutex_t&quot;</tt>&#8216;. Alternatively one can also use static initialization via `<tt>&quot;pth_mutex_t mutex = PTH_MUTEX_INIT&quot;</tt>&#8216;.</p>
<dt>int <code>pth_mutex_acquire</code>(pth_mutex_t *<i>mutex</i>, int <i>try</i>, pth_event_t <i>ev</i>);</p>
<dd>This acquires a mutex <i>mutex</i>. If the mutex is already locked by another thread, the current threads execution is suspended until the mutex is unlocked again or additionally the extra events in <i>ev</i> occurred (when <i>ev</i> is not <tt>&quot;NULL&quot;</tt>). Recursive locking is explicitly supported, i.e., a thread is allowed to acquire a mutex more than once before its released. But it then also has be released the same number of times until the mutex is again lockable by others. When <i>try</i> is <tt>&quot;TRUE&quot;</tt> this function never suspends execution. Instead it returns <tt>&quot;FALSE&quot;</tt> with <tt>&quot;errno&quot;</tt> set to <tt>&quot;EBUSY&quot;</tt>.</p>
<dt>int <code>pth_mutex_release</code>(pth_mutex_t *<i>mutex</i>);</p>
<dd>This decrements the recursion locking count on <i>mutex</i> and when it is zero it releases the mutex <i>mutex</i>.</p>
<dt>int <code>pth_rwlock_init</code>(pth_rwlock_t *<i>rwlock</i>);</p>
<dd>This dynamically initializes a read-write lock variable of type `<tt>&quot;pth_rwlock_t&quot;</tt>&#8216;. Alternatively one can also use static initialization via `<tt>&quot;pth_rwlock_t rwlock = PTH_RWLOCK_INIT&quot;</tt>&#8216;.</p>
<dt>int <code>pth_rwlock_acquire</code>(pth_rwlock_t *<i>rwlock</i>, int <i>op</i>, int <i>try</i>, pth_event_t <i>ev</i>);</p>
<dd>This acquires a read-only (when <i>op</i> is <tt>&quot;PTH_RWLOCK_RD&quot;</tt>) or a read-write (when <i>op</i> is <tt>&quot;PTH_RWLOCK_RW&quot;</tt>) lock <i>rwlock</i>. When the lock is only locked by other threads in read-only mode, the lock succeeds. But when one thread holds a read-write lock, all locking attempts suspend the current thread until this lock is released again. Additionally in <i>ev</i> events can be given to let the locking timeout, etc. When <i>try</i> is <tt>&quot;TRUE&quot;</tt> this function never suspends execution. Instead it returns <tt>&quot;FALSE&quot;</tt> with <tt>&quot;errno&quot;</tt> set to <tt>&quot;EBUSY&quot;</tt>.</p>
<dt>int <code>pth_rwlock_release</code>(pth_rwlock_t *<i>rwlock</i>);</p>
<dd>This releases a previously acquired (read-only or read-write) lock.</p>
<dt>int <code>pth_cond_init</code>(pth_cond_t *<i>cond</i>);</p>
<dd>This dynamically initializes a condition variable variable of type `<tt>&quot;pth_cond_t&quot;</tt>&#8216;. Alternatively one can also use static initialization via `<tt>&quot;pth_cond_t cond = PTH_COND_INIT&quot;</tt>&#8216;.</p>
<dt>int <code>pth_cond_await</code>(pth_cond_t *<i>cond</i>, pth_mutex_t *<i>mutex</i>, pth_event_t <i>ev</i>);</p>
<dd>This awaits a condition situation. The caller has to follow the semantics of the <font SIZE="-1">POSIX</font> condition variables: <i>mutex</i> has to be acquired before this function is called. The execution of the current thread is then suspended either until the events in <i>ev</i> occurred (when <i>ev</i> is not <tt>&quot;NULL&quot;</tt>) or <i>cond</i> was notified by another thread via <i><a href="/docs/linux/man/3-pth_cond_notify/">pth_cond_notify</a></i>(3). While the thread is waiting, <i>mutex</i> is released. Before it returns <i>mutex</i> is reacquired.</p>
<dt>int <code>pth_cond_notify</code>(pth_cond_t *<i>cond</i>, int <i>broadcast</i>);</p>
<dd>This notified one or all threads which are waiting on <i>cond</i>. When <i>broadcast</i> is <tt>&quot;TRUE&quot;</tt> all thread are notified, else only a single (unspecified) one.</p>
<dt>int <code>pth_barrier_init</code>(pth_barrier_t *<i>barrier</i>, int <i>threshold</i>);</p>
<dd>This dynamically initializes a barrier variable of type `<tt>&quot;pth_barrier_t&quot;</tt>&#8216;. Alternatively one can also use static initialization via `<tt>&quot;pth_barrier_t barrier = PTH_BARRIER_INIT(&quot;</tt><i>threadhold</i><tt>&quot;)&quot;</tt>&#8216;.</p>

<dd>This function reaches a barrier <i>barrier</i>. If this is the last thread (as specified by <i>threshold</i> on init of <i>barrier</i>) all threads are awakened. <p> <code>User-Space Context</code> </p>
<p> The following functions provide a stand-alone sub-API for user-space context switching. It internally is based on the same underlying machine context switching mechanism the threads in <font SIZE="-1"><code>GNU</code></font><code> Pth</code> are based on. Hence these functions you can use for implementing your own simple user-space threads. The <tt>&quot;pth_uctx_t&quot;</tt> context is somewhat modeled after <font SIZE="-1">POSIX</font> <i><a href="/docs/linux/man/3-ucontext/">ucontext</a></i>(3). </p>
<p> The time required to create (via <i><a href="/docs/linux/man/3-pth_uctx_make/">pth_uctx_make</a></i>(3)) a user-space context can range from just a few microseconds up to a more dramatical time (depending on the machine context switching method which is available on the platform). On the other hand, the raw performance in switching the user-space contexts is always very good (nearly independent of the used machine context switching method). For instance, on an Intel Pentium-III <font SIZE="-1">CPU</font> with 800Mhz running under FreeBSD 4 one usually achieves about 260,000 user-space context switches (via <i><a href="/docs/linux/man/3-pth_uctx_switch/">pth_uctx_switch</a></i>(3)) per second.</p>
<dl>
<dt>int <code>pth_uctx_create</code>(pth_uctx_t *<i>uctx</i>);</p>
<dd>This function creates a user-space context and stores it into <i>uctx</i>. There is still no underlying user-space context configured. You still have to do this with <i><a href="/docs/linux/man/3-pth_uctx_make/">pth_uctx_make</a></i>(3). On success, this function returns <tt>&quot;TRUE&quot;</tt>, else <tt>&quot;FALSE&quot;</tt>.</p>
<dt>int <code>pth_uctx_make</code>(pth_uctx_t <i>uctx</i>, char *<i>sk_addr</i>, size_t <i>sk_size</i>, const sigset_t *<i>sigmask</i>, void (*<i>start_func</i>)(void *), void *<i>start_arg</i>, pth_uctx_t <i>uctx_after</i>);</p>
<dd>This function makes a new user-space context in <i>uctx</i> which will operate on the run-time stack <i>sk_addr</i> (which is of maximum size <i>sk_size</i>), with the signals in <i>sigmask</i> blocked (if <i>sigmask</i> is not <tt>&quot;NULL&quot;</tt>) and starting to execute with the call <i>start_func</i>(<i>start_arg</i>). If <i>sk_addr</i> is <tt>&quot;NULL&quot;</tt>, a stack is dynamically allocated. The stack size <i>sk_size</i> has to be at least 16384 (16KB). If the start function <i>start_func</i> returns and <i>uctx_after</i> is not <tt>&quot;NULL&quot;</tt>, an implicit user-space context switch to this context is performed. Else (if <i>uctx_after</i> is <tt>&quot;NULL&quot;</tt>) the process is terminated with <i><a href="/docs/linux/man/3-exit/">exit</a></i>(3). This function is somewhat modeled after <font SIZE="-1">POSIX</font> <i><a href="/docs/linux/man/3-makecontext/">makecontext</a></i>(3). On success, this function returns <tt>&quot;TRUE&quot;</tt>, else <tt>&quot;FALSE&quot;</tt>.</p>
<dt>int <code>pth_uctx_switch</code>(pth_uctx_t <i>uctx_from</i>, pth_uctx_t <i>uctx_to</i>);</p>
<dd>This function saves the current user-space context in <i>uctx_from</i> for later restoring by another call to <i><a href="/docs/linux/man/3-pth_uctx_switch/">pth_uctx_switch</a></i>(3) and restores the new user-space context from <i>uctx_to</i>, which previously had to be set with either a previous call to <i><a href="/docs/linux/man/3-pth_uctx_switch/">pth_uctx_switch</a></i>(3) or initially by <i><a href="/docs/linux/man/3-pth_uctx_make/">pth_uctx_make</a></i>(3). This function is somewhat modeled after <font SIZE="-1">POSIX</font> <i><a href="/docs/linux/man/3-swapcontext/">swapcontext</a></i>(3). If <i>uctx_from</i> or <i>uctx_to</i> are <tt>&quot;NULL&quot;</tt> or if <i>uctx_to</i> contains no valid user-space context, <tt>&quot;FALSE&quot;</tt> is returned instead of <tt>&quot;TRUE&quot;</tt>. These are the only errors possible.</p>
<dt>int <code>pth_uctx_destroy</code>(pth_uctx_t <i>uctx</i>);</p>
<dd>This function destroys the user-space context in <i>uctx</i>. The run-time stack associated with the user-space context is deallocated only if it was not given by the application (see <i>sk_addr</i> of <i><a href="/docs/linux/man/3-pth_uctx_create/">pth_uctx_create</a></i>(3)). If <i>uctx</i> is <tt>&quot;NULL&quot;</tt>, <tt>&quot;FALSE&quot;</tt> is returned instead of <tt>&quot;TRUE&quot;</tt>. This is the only error possible.
</dl>

<p> <code>Standard <font SIZE="-1">POSIX</font> Replacement <font SIZE="-1">API</font></code> </p>
<p> The following functions are standard replacements functions for the <font SIZE="-1">POSIX</font> <font SIZE="-1">API</font>. The difference is mainly that they suspend the current thread only instead of the whole process in case the file descriptors will block.</p>
<dl>
<dt>int <code>pth_nanosleep</code>(const struct timespec *<i>rqtp</i>, struct timespec *<i>rmtp</i>);</p>
<dd>This is a variant of the <font SIZE="-1">POSIX</font> <i><a href="/docs/linux/man/3-nanosleep/">nanosleep</a></i>(3) function. It suspends the current threads execution until the amount of time in <i>rqtp</i> elapsed. The thread is guaranteed to not wake up before this time, but because of the non-preemptive scheduling nature of <code>Pth</code>, it can be awakened later, of course. If <i>rmtp</i> is not <tt>&quot;NULL&quot;</tt>, the <tt>&quot;timespec&quot;</tt> structure it references is updated to contain the unslept amount (the request time minus the time actually slept time). The difference between <i><a href="/docs/linux/man/3-nanosleep/">nanosleep</a></i>(3) and <i><a href="/docs/linux/man/3-pth_nanosleep/">pth_nanosleep</a></i>(3) is that that <i><a href="/docs/linux/man/3-pth_nanosleep/">pth_nanosleep</a></i>(3) suspends only the execution of the current thread and not the whole process.</p>
<dt>int <code>pth_usleep</code>(unsigned int <i>usec</i>);</p>
<dd>This is a variant of the 4.3BSD <i><a href="/docs/linux/man/3-usleep/">usleep</a></i>(3) function. It suspends the current threads execution until <i>usec</i> microseconds (= <i>usec</i>*1/1000000 sec) elapsed. The thread is guaranteed to not wake up before this time, but because of the non-preemptive scheduling nature of <code>Pth</code>, it can be awakened later, of course. The difference between <i><a href="/docs/linux/man/3-usleep/">usleep</a></i>(3) and <i><a href="/docs/linux/man/3-pth_usleep/">pth_usleep</a></i>(3) is that that <i><a href="/docs/linux/man/3-pth_usleep/">pth_usleep</a></i>(3) suspends only the execution of the current thread and not the whole process.</p>
<dt>unsigned int <code>pth_sleep</code>(unsigned int <i>sec</i>);</p>
<dd>This is a variant of the <font SIZE="-1">POSIX</font> <i><a href="/docs/linux/man/3-sleep/">sleep</a></i>(3) function. It suspends the current threads execution until <i>sec</i> seconds elapsed. The thread is guaranteed to not wake up before this time, but because of the non-preemptive scheduling nature of <code>Pth</code>, it can be awakened later, of course. The difference between <i><a href="/docs/linux/man/3-sleep/">sleep</a></i>(3) and <i><a href="/docs/linux/man/3-pth_sleep/">pth_sleep</a></i>(3) is that <i><a href="/docs/linux/man/3-pth_sleep/">pth_sleep</a></i>(3) suspends only the execution of the current thread and not the whole process.</p>
<dt>pid_t <code>pth_waitpid</code>(pid_t <i>pid</i>, int *<i>status</i>, int <i>options</i>);</p>
<dd>This is a variant of the <font SIZE="-1">POSIX</font> <i><a href="/docs/linux/man/2-waitpid/">waitpid</a></i>(2) function. It suspends the current threads execution until <i>status</i> information is available for a terminated child process <i>pid</i>. The difference between <i><a href="/docs/linux/man/2-waitpid/">waitpid</a></i>(2) and <i><a href="/docs/linux/man/3-pth_waitpid/">pth_waitpid</a></i>(3) is that <i><a href="/docs/linux/man/3-pth_waitpid/">pth_waitpid</a></i>(3) suspends only the execution of the current thread and not the whole process. <dt>int <code>pth_system</code>(const char *<i>cmd</i>);</p>
<dd>This is a variant of the <font SIZE="-1">POSIX</font> <i><a href="/docs/linux/man/3-system/">system</a></i>(3) function. It executes the shell command <i>cmd</i> with Bourne Shell (<tt>&quot;sh&quot;</tt>) and suspends the current threads execution until this command terminates. The difference between <i><a href="/docs/linux/man/3-system/">system</a></i>(3) and <i><a href="/docs/linux/man/3-pth_system/">pth_system</a></i>(3) is that <i><a href="/docs/linux/man/3-pth_system/">pth_system</a></i>(3) suspends only the execution of the current thread and not the whole process. For more details about the arguments and return code semantics see <i><a href="/docs/linux/man/3-system/">system</a></i>(3).</p>
<dt>int <code>pth_sigmask</code>(int <i>how</i>, const sigset_t *<i>set</i>, sigset_t *<i>oset</i>)</p>
<dd>This is the <code>Pth</code> thread-related equivalent of <font SIZE="-1">POSIX</font> <i><a href="/docs/linux/man/2-sigprocmask/">sigprocmask</a></i>(2) respectively <i><a href="/docs/linux/man/3-pthread_sigmask/">pthread_sigmask</a></i>(3). The arguments <i>how</i>, <i>set</i> and <i>oset</i> directly relate to <i><a href="/docs/linux/man/2-sigprocmask/">sigprocmask</a></i>(2), because <code>Pth</code> internally just uses <i><a href="/docs/linux/man/2-sigprocmask/">sigprocmask</a></i>(2) here. <dt>int <code>pth_sigwait</code>(const sigset_t *<i>set</i>, int *<i>sig</i>);</p>
<dd>This is a variant of the <font SIZE="-1">POSIX</font>.1c <i><a href="/docs/linux/man/3-sigwait/">sigwait</a></i>(3) function. The important point is that the signal is not delivered to a signal handler. Instead it&#8217;s caught by the scheduler only in order to awake the <i>pth_sigwait()</i> call. The trick and noticeable point here is that this way you get an asynchronous aware application that is written completely synchronously. When you think about the problem of <i>asynchronous safe</i> functions you should recognize that this is a great benefit.</p>

The difference between <i><a href="/docs/linux/man/2-connect/">connect</a></i>(2) and <i><a href="/docs/linux/man/3-pth_connect/">pth_connect</a></i>(3) is that <i><a href="/docs/linux/man/3-pth_connect/">pth_connect</a></i>(3) suspends only the execution of the current thread and not the whole process. The difference between <i><a href="/docs/linux/man/2-accept/">accept</a></i>(2) and <i><a href="/docs/linux/man/3-pth_accept/">pth_accept</a></i>(3) is that <i><a href="/docs/linux/man/3-pth_accept/">pth_accept</a></i>(3) suspends only the execution of the current thread and not the whole process. <dt>int <code>pth_select</code>(int <i>nfd</i>, fd_set *<i>rfds</i>, fd_set *<i>wfds</i>, fd_set *<i>efds</i>, struct timeval *<i>timeout</i>);</p>
