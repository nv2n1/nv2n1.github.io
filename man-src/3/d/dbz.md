<h2 class="name">NAME</h2>
<p> dbzinit, dbzfresh, dbzagain, dbzclose, dbzexists, dbzfetch, dbzstore, dbzsync, dbzsize, dbzgetoptions, dbzsetoptions, dbzdebug &#8211; database routines </p>
<h2>SYNOPSIS</h2>
<pre><code>
#include &lt;inn/dbz.h&gt;
bool dbzinit(const char *base) bool dbzclose(void) bool dbzfresh(const char *base, long size) bool dbzagain(const char *base, const char *oldbase) bool dbzexists(const HASH key)
    off_t dbzfetch(const HASH key) bool dbzfetch(const HASH key, void *ivalue)
        DBZSTORE_RESULT dbzstore(const HASH key, off_t offset)
            DBZSTORE_RESULT dbzstore(const HASH key, void *ivalue) bool dbzsync(void) long dbzsize(long nentries) void dbzgetoptions(dbzoptions *opt) void dbzsetoptions(const dbzoptions opt)
</code></pre>
<h2>DESCRIPTION</h2>
<p> These functions provide an indexing system for rapid random access to a text file (the <i>base </i> <i>file</i>). </p>
<p> <i>Dbz</i> stores offsets into the base text file for rapid retrieval. All retrievals are keyed on a hash value that is generated by the <i>HashMessageID()</i> function. </p>
<p> <i>Dbzinit</i> opens a database, an index into the base file <i>base</i>, consisting of files <i>base</i><code>.dir</code> , <i>base</i><code>.index</code> , and <i>base</i><code>.hash</code> which must already exist. (If the database is new, they should be zero-length files.) Subsequent accesses go to that database until <i>dbzclose</i> is called to close the database. </p>
<p> <i>Dbzfetch</i> searches the database for the specified <i>key</i>, returning the corresponding <i>value</i> if any, if <i>&lt;&#8211;enable-tagged-hash at configure&gt;</i> is specified. If <i>&lt;&#8211;enable-tagged-hash at configure&gt;</i> is not specified, it returns true and content of <i>ivalue</i> is set. <i>Dbzstore</i> stores the <i>key &#8211; value</i> pair in the database, if <i>&lt;&#8211;enable-tagged-hash at configure&gt;</i> is specified. If <i>&lt;&#8211;enable-tagged-hash at configure&gt;</i> is not specified, it stores the content of <i>ivalue</i>. <i>Dbzstore</i> will fail unless the database files are writable. <i>Dbzexists </i> will verify whether or not the given hash exists or not. Dbz is optimized for this operation and it may be significantly faster than <i>dbzfetch()</i>. </p>
<p> <i>Dbzfresh</i> is a variant of <i>dbzinit</i> for creating a new database with more control over details. </p>
<p> <i>Dbzfresh</i>&#8216;s <i>size</i> parameter specifies the size of the first hash table within the database, in key-value pairs. Performance will be best if the number of key-value pairs stored in the database does not exceed about 2/3 of <i>size</i>. (The <i>dbzsize</i> function, given the expected number of key-value pairs, will suggest a database size that meets these criteria.) Assuming that an <i>fseek</i> offset is 4 bytes, the <code>.index</code> file will be <i>4 * size</i> bytes. The <code>.hash</code> file will be <i>DBZ_INTERNAL_HASH_SIZE * size</i> bytes (the <code>.dir</code> file is tiny and roughly constant in size) until the number of key-value pairs exceeds about 80% of <i>size</i>. (Nothing awful will happen if the database grows beyond 100% of <i>size</i>, but accesses will slow down quite a bit and the <code>.index</code> and <code>.hash</code> files will grow somewhat.) </p>
<p> <i>Dbz</i> stores up to <font SIZE="-1">DBZ_INTERNAL_HASH_SIZE</font> bytes of the message-id&#8217;s hash in the <code>.hash</code> file to confirm a hit. This eliminates the need to read the base file to handle collisions. This replaces the tagmask feature in previous dbz releases. </p>
<p> A <i>size</i> of &#8220;0&#8221; given to <i>dbzfresh</i> is synonymous with the local default; the normal default is suitable for tables of 5,000,000 key-value pairs. Calling <i>dbzinit(name)</i> with the empty name is equivalent to calling <i>dbzfresh(name, 0)</i>. </p>
<p> When databases are regenerated periodically, as in news, it is simplest to pick the parameters for a new database based on the old one. This also permits some memory of past sizes of the old database, so that a new database size can be chosen to cover expected fluctuations. <i>Dbzagain</i> is a variant of <i>dbzinit</i> for creating a new database as a new generation of an old database. The database files for <i>oldbase</i> must exist. <i>Dbzagain</i> is equivalent to calling <i>dbzfresh</i> with a <i>size</i> equal to the result of applying <i>dbzsize</i> to the largest number of entries in the <i>oldbase</i> database and its previous 10 generations. </p>
<p> When many accesses are being done by the same program, <i>dbz</i> is massively faster if its first hash table is in memory. If the &#8220;pag_incore&#8221; flag is set to INCORE_MEM, an attempt is made to read the table in when the database is opened, and <i>dbzclose</i> writes it out to disk again (if it was read successfully and has been modified). <i>Dbzsetoptions</i> can be used to set the <code>pag_incore </code> and <code>exists_incore </code> flag to new value which should be &#8220;INCORE_NO&#8221;, &#8220;INCORE_MEM&#8221;, or &#8220;INCORE_MMAP&#8221; for the <code>.hash</code> and <code>.index </code> files separately; this does not affect the status of a database that has already been opened. The default is &#8220;INCORE_NO&#8221; for the <code>.index </code> file and &#8220;INCORE_MMAP&#8221; for the <code>.hash </code> file. The attempt to read the table in may fail due to memory shortage; in this case <i>dbz</i> fails with an error. <i>Store</i>s to an in-memory database are not (in general) written out to the file until <i>dbzclose</i> or <i>dbzsync</i>, so if robustness in the presence of crashes or concurrent accesses is crucial, in-memory databases should probably be avoided or the <code>writethrough</code> option should be set to &#8220;true&#8221;; </p>
<p> If the <code>nonblock</code> option is &#8220;true&#8221;, then writes to the <code>.hash</code> and <code>.index</code> files will be done using non-blocking I/O. This can be significantly faster if your platform supports non-blocking I/O with files. </p>
<p> <i>Dbzsync</i> causes all buffers etc. to be flushed out to the files. It is typically used as a precaution against crashes or concurrent accesses when a <i>dbz</i>-using process will be running for a long time. It is a somewhat expensive operation, especially for an in-memory database. </p>
<p> Concurrent reading of databases is fairly safe, but there is no (inter)locking, so concurrent updating is not. </p>
<p> An open database occupies three <i>stdio</i> streams and two file descriptors; Memory consumption is negligible (except for <i>stdio</i> buffers) except for in-memory databases.</p>

<h2>DIAGNOSTICS</h2>
<p> Functions returning <i>bool</i> values return &#8220;true&#8221; for success, &#8220;false&#8221; for failure. Functions returning <i>off_t</i> values return a value with <i>-1</i> for failure. <i>Dbzinit</i> attempts to have <i>errno</i> set plausibly on return, but otherwise this is not guaranteed. An <i>errno</i> of <code>EDOM</code> from <i>dbzinit</i> indicates that the database did not appear to be in <i>dbz</i> format. </p>
<p> If <font SIZE="-1">DBZTEST</font> is defined at compile-time then a <i>main()</i> function will be included. This will do performance tests and integrity test.</p>

<h2>BUGS</h2>
<p> Unlike <i>dbm</i>, <i>dbz</i> will refuse to <i>dbzstore</i> with a key already in the database. The user is responsible for avoiding this. </p>
<p> The RFC5322 case mapper implements only a first approximation to the hideously-complex RFC5322 case rules. </p>
<p> <i>Dbz</i> no longer tries to be call-compatible with <i>dbm</i> in any way. </p>
